1 IP addresses & subnets

Explain like I'm 5

An IP address is a house number for a machine. The subnet is the street: houses on the same street talk directly; anything else goes via the post office (the gateway).

  • An IPv4 address is 32 bits, written as 4 octets (0–255) in dotted decimal: 192.168.1.50.
  • Every address = network part + host part. The subnet mask (or CIDR prefix) says where the split is.
  • CIDR notation /n = the first n bits are the network. 192.168.1.50/24 → network 192.168.1.0, host .50.
  • The default gateway is the router IP on your subnet (usually .1). Packets for any other network are sent to it.
# 192.168.10.37/28 in binary — the mask's 1-bits mark the network part
IP      192      .168      .10       .37
        11000000 .10101000 .00001010 .0010|0101
Mask    11111111 .11111111 .11111111 .1111|0000   = 255.255.255.240  (/28 → 28 ones)
                                          ^ network | host (4 bits → 16 addresses)

CIDR cheat table

Usable hosts = 2(32 − n) − 2 (the first address is the network address, the last is the broadcast).

Worked example: which subnet is 192.168.10.37/28 in?
  1. Host bits = 32 − 28 = 4 → block size = 24 = 16 addresses.
  2. Blocks in the last octet start at 0, 16, 32, 48… → 37 falls in the block starting at 32.
  3. Network = 192.168.10.32, broadcast = 32 + 15 = 192.168.10.47.
  4. Usable = .33 – .46 → 14 hosts (16 − 2).

Same method: 10.0.0.0/16 → 65,534 hosts (10.0.0.1–10.0.255.254); 10.0.1.0/24 → 254 hosts (10.0.1.1–10.0.1.254) and it sits inside the /16. (AWS reserves 5 IPs per subnet, so a /24 there gives 251 — see Session 21.)

IPv6 glimpse

  • 128 bits, 8 groups of 4 hex digits: 2404:6800:4007:080f:0000:0000:0000:200e.
  • Shorten: drop leading zeros in a group, replace one run of zero groups with :: → 2404:6800:4007:80f::200e.
  • ::1 = loopback, fe80::/10 = link-local (every interface gets one), /64 = standard subnet size. Exists because IPv4's ~4.3 billion addresses ran out.
Common mistakes
  • "A /24 has 256 hosts" — it has 256 addresses, 254 usable.
  • Smaller prefix = bigger network: /16 (65k) is larger than /24 (256).
  • Two subnets in one VPC must not overlap: 10.0.1.0/24 and 10.0.1.128/25 overlap → AWS rejects it.
Recap IPv4 = 32 bits; /n = network bits; hosts = 232−n − 2. ip a shows your addresses, ip route shows the gateway.

2 Public vs private IP

Explain like I'm 5

A private IP is your hostel room number — unique inside the hostel only. The public IP is the hostel's street address; the reception desk (NAT) forwards letters to the right room.

  • Public IP: globally unique, routable on the internet, assigned by ISPs / cloud providers (an EC2 public IP, your router's WAN IP).
  • Private IP: reusable inside any LAN/VPC, never routed on the internet. Defined by RFC 1918.

NAT: how private machines reach the internet

NAT (Network Address Translation) on the router rewrites the private source IP:port to its public IP:port and remembers the mapping for the reply.

Laptop 192.168.1.23:52344 ──▶ Router (NAT) ──▶ 203.0.113.45:40001 ──▶ github.com 140.82.112.3:443
                              table: 203.0.113.45:40001 ⇄ 192.168.1.23:52344
Reply  ◀── 192.168.1.23:52344 ◀── router looks up the table ◀── 140.82.112.3:443 → 203.0.113.45:40001
  • Outbound connections work automatically. Inbound to a private IP needs port forwarding (home router) or a public IP / load balancer (cloud).
  • In AWS: an Internet Gateway does 1:1 NAT for instances with public IPs; a NAT Gateway gives private subnets outbound-only internet (Session 21).
$ ip -4 -br a show enp0s3      # the IP the machine thinks it has
enp0s3           UP             192.168.1.50/24
$ curl ifconfig.me             # the IP the internet sees (after NAT)
203.0.113.45

The container has its own loopback. Docker forwards host:8080 to the container's eth0 IP, where nothing listens.

Recap Private = 10/8, 172.16/12, 192.168/16, not internet-routable; NAT maps them to a public IP. Servers (and every container) must listen on 0.0.0.0, not 127.0.0.1.

3 Ports & sockets

Explain like I'm 5

The IP finds the building; the port is the flat number inside it. Port 22 is SSH's flat, port 5432 is Postgres's flat.

  • A port is a 16-bit number (0–65535) that identifies one process's endpoint on a host.
  • A socket = IP + port, e.g. 192.168.1.50:3000. A TCP connection is identified by the 5-tuple: protocol, src IP, src port, dst IP, dst port.
  • Listening (server) uses a fixed known port. Connecting (client) gets a random ephemeral port from the OS.

Common mistakes (real Node errors) 
Error: listen EADDRINUSE: address already in use :::3000   # another process owns 3000
Error: listen EACCES: permission denied 0.0.0.0:80        # non-root binding a port < 1024

Find the owner: sudo ss -tlnp | grep :3000 or sudo lsof -i :3000, then stop it or change PORT. For port 80, run on 3000 and put nginx / a load balancer / Docker -p 80:3000 in front.

$ sudo lsof -i :3000

Recap Socket = IP:port. Servers listen on known ports (22, 80, 443, 5432…); clients use ephemeral ports. EADDRINUSE → find the owner with ss -tlnp / lsof -i.

4 TCP vs UDP

Explain like I'm 5

TCP is a phone call: you say hello first and confirm every sentence was heard. UDP is shouting announcements: fast, but nobody confirms they heard you.

TCPUDP
ConnectionConnection-oriented (3-way handshake first)Connectionless — just send datagrams
ReliabilityACKs + retransmission; guaranteed deliveryBest effort; packets may be lost
OrderingIn order (sequence numbers)No ordering
Flow / congestion controlYes (window size, slow start)No
Header size20–60 bytes8 bytes
Speed / latencyHigher overheadLower latency
Used byHTTP/1.1 & HTTP/2, SSH, PostgreSQL, Redis, SMTPDNS queries, DHCP, NTP, VoIP/video calls, games, HTTP/3 (QUIC)

The 3-way handshake

  Laptop 192.168.1.23:52410                        taskflow-api 192.168.1.50:3000
        │ ── SYN        seq=x ─────────────────────────▶ │   "can we talk?"
        │ ◀─ SYN-ACK    seq=y, ack=x+1 ───────────────── │   "yes, can you hear me?"
        │ ── ACK        ack=y+1 ───────────────────────▶ │   "yes" → ESTABLISHED
        │ ══ GET /health HTTP/1.1 ═════════════════════▶ │
        │ ◀═ HTTP/1.1 200 OK {"status":"ok"} ═══════════ │
        │ ── FIN ──▶  ◀── ACK, FIN ──  ── ACK ──▶        │   4-step close

You can watch it happen with tcpdump (flags: S = SYN, S. = SYN-ACK, . = ACK, P = push data, F = FIN):

$ sudo tcpdump -i lo -n 'tcp port 3000'      # in terminal 2: curl localhost:3000/health
10:31:02.114201 IP 127.0.0.1.52410 > 127.0.0.1.3000: Flags [S], seq 1849302211, win 65495, length 0
10:31:02.114215 IP 127.0.0.1.3000 > 127.0.0.1.52410: Flags [S.], seq 2210331876, ack 1849302212, win 65483, length 0
10:31:02.114228 IP 127.0.0.1.52410 > 127.0.0.1.3000: Flags [.], ack 1, win 512, length 0
10:31:02.114310 IP 127.0.0.1.52410 > 127.0.0.1.3000: Flags [P.], seq 1:84, ack 1, win 512, length 83: HTTP: GET /health HTTP/1.1
Example: testing TCP vs UDP ports 
$ nc -zv 192.168.1.50 5432          # TCP: real handshake → trustworthy answer
Connection to 192.168.1.50 5432 port [tcp/postgresql] succeeded!
$ nc -zuv 8.8.8.8 53                # UDP: no handshake → "succeeded" only means no error came back
Connection to 8.8.8.8 53 port [udp/domain] succeeded!

For UDP services, test the protocol itself (dig @8.8.8.8 google.com) rather than trusting nc -u.

Key takeaway

DNS uses UDP 53 for normal queries (one small question, one small answer — a handshake would double the latency) and falls back to TCP 53 for large responses and zone transfers. Firewalls must allow both.

Recap TCP = handshake, reliable, ordered (web, SSH, databases). UDP = fire-and-forget, fast (DNS, streaming, QUIC). SYN → SYN-ACK → ACK opens every TCP connection.

5 DNS

Explain like I'm 5

DNS is the internet's phonebook: you know the name (github.com), DNS tells you the number (140.82.112.3).

Resolution flow

curl https://api.taskflow.example.com/health
 1. Application / browser cache ─────────────── hit? done
 2. OS: /etc/hosts  (nsswitch "hosts: files dns") ── match? done
 3. OS stub resolver cache (systemd-resolved @ 127.0.0.53)
 4. Recursive resolver (ISP / 8.8.8.8 / 1.1.1.1 / AWS VPC .2) ── cached? done
        │ not cached → it walks the tree:
        ├──▶ 5. Root server  "."            → "ask the .com TLD servers"
        ├──▶ 6. TLD server   ".com"         → "ask ns1.exampledns.net (authoritative)"
        └──▶ 7. Authoritative server        → "A 203.0.113.10, TTL 300"
 8. Answer cached at each level for TTL seconds → curl connects to 203.0.113.10:443

Record types

TypeMapsExample
Aname → IPv4api.taskflow.example.com. 300 IN A 203.0.113.10
AAAAname → IPv6api… IN AAAA 2001:db8::10
CNAMEname → another name (alias)www.taskflow.example.com. IN CNAME taskflow-alb-123.ap-south-1.elb.amazonaws.com.
MXdomain → mail server (with priority)example.com. IN MX 10 mail.example.com.
TXTarbitrary textSPF, domain-ownership verification, Let's Encrypt DNS-01 challenge
NSzone → its authoritative name serversexample.com. IN NS ns1.exampledns.net.
PTRIP → name (reverse DNS)8.8.8.8 → dns.google.
  • TTL (seconds) = how long resolvers may cache the answer. TTL 300 → after you change the record, some users see the old IP for up to 5 min. Lower the TTL a day before a migration.
  • A CNAME can't sit at the zone apex (example.com itself) alongside other records — clouds offer "alias" records instead.

/etc/resolv.conf (Ubuntu, managed by systemd-resolved)
# This is /run/systemd/resolve/stub-resolv.conf managed by man:systemd-resolved(8).
# Do not edit.

LineMeaning
nameserver 127.0.0.53Send queries to the local systemd-resolved stub (it caches and forwards to the real upstream DNS). Up to 3 nameserver lines allowed.
options edns0 trust-adAllow larger UDP responses (EDNS0); trust the DNSSEC "authenticated data" bit from this server.
search .Domains appended to short names (. = none). Kubernetes pods get search taskflow.svc.cluster.local svc.cluster.local … — Session 11.

Common mistake: "dig says NXDOMAIN but curl works" 
$ dig +short taskflow.local            # dig talks to DNS servers directly — ignores /etc/hosts

HTTPS = HTTP + TLS

  • TLS gives encryption (no eavesdropping), integrity (no tampering) and authentication (you're talking to the real server). Default port 443.
  • Handshake (TLS 1.3, simplified): ClientHello (supported ciphers, SNI hostname) → ServerHello + certificate → both derive a shared session key → encrypted HTTP flows.
  • A certificate binds a public key to names (subject / SAN), is signed by a CA (issuer), and has notBefore / notAfter dates. Trust chain: leaf → intermediate → root CA in the OS trust store.
  • Free certs: Let's Encrypt (certbot; cert-manager in K8s — Session 12).

Common mistakes
  • Concluding "server is down" from a failed ping — test the actual TCP port.
  • Testing with curl localhost on the server and declaring victory — that bypasses the firewall and the bind-address problem. Test from outside too.
  • Running ss -tulpn without sudo → the Process column is empty for other users' processes.
Recap Walk the ladder: DNS → reachability → port (refused vs timeout) → listen address → firewall/SG → app logs. nc -zv and ss -tlnp answer most "unreachable" questions.

★ Putting it all together

The big idea

When you open https://api.taskflow.example.com/tasks: DNS turns the name into an IP; your private IP is NATed to a public one; TCP does a handshake to port 443; TLS proves the server's identity and encrypts; then an HTTP GET goes in and a 200 with JSON comes back. Every DevOps tool later in the course — Docker port mapping, Kubernetes Services, Ingress, security groups — is just configuring one of these layers, and every outage is debugged by walking them in order.

Quick self-check

How many usable hosts are in 10.0.2.0/27? What are the first and last usable IPs?

32 − 27 = 5 host bits → 25 = 32 addresses − 2 = 30 usable: 10.0.2.1 to 10.0.2.30 (network .0, broadcast .31).

Is 172.20.5.9 public or private? What about 172.32.0.1?

172.20.5.9 is private (inside 172.16.0.0/12 = 172.16–172.31). 172.32.0.1 is outside that range → public.

curl localhost:3000/health works on the server, but not from your laptop. ss -tlnp shows 127.0.0.1:3000. Explain and fix.

The app is bound to loopback, so only processes on the same host can connect. Make it listen on 0.0.0.0 (e.g. HOST=0.0.0.0), restart, then make sure the firewall/security group allows TCP 3000.

nc -zv host 5432 says "Connection refused" on one server and "timed out" on another. What does each tell you?

Refused: packets reached the host and it replied with a reset → nothing listening on 5432 (service down, wrong port, or bound to 127.0.0.1). Timed out: packets were silently dropped → firewall / security group / routing / wrong IP.

Why does DNS use UDP, and when does it switch to TCP?

A query and answer are tiny, so a TCP handshake would roughly double latency; UDP sends one packet each way. TCP 53 is used when the response is too big for UDP (truncated, TC flag) and for zone transfers.

nginx in front of taskflow-api returns 502 on one request and 504 on another. What's the difference?

502 Bad Gateway: nginx got no valid response from the upstream (api down, connection refused, wrong port). 504 Gateway Timeout: the upstream accepted the request but didn't answer within nginx's timeout (slow handler / DB).

You added 192.168.49.2 taskflow.local to /etc/hosts. Browser works, dig taskflow.local returns nothing. Is something broken?

No. dig queries DNS servers directly and ignores /etc/hosts. Apps use the OS resolver (nsswitch: files, then dns). Check with getent hosts taskflow.local.
