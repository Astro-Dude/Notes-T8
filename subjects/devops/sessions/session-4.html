1 IP addresses & subnets

The problem

Your friend tries TaskFlow's API from their laptop:

$ curl --connect-timeout 5 http://api.taskflow.example.com:3000/health
curl: (28) Failed to connect to api.taskflow.example.com port 3000 after 5002 ms: Timeout was reached

Something between their laptop and your Node process is broken. Each part of that URL belongs to a different layer, and each layer can fail on its own:

 http://   api.taskflow.example.com   :3000    /health
   │                  │                 │         └─ path inside the app ............. HTTP (§6)
   │                  │                 └─ which program on that machine .............. port (§3)
   │                  └─ a name, turned into an IP address ............. DNS (§5) → IP (§1–2)
   └─ the language spoken once connected (http = plain, https = encrypted) .. HTTP over TCP (§4, §6–7)

You'll crack this exact failure in section 8. Start at the bottom: a packet needs an address, and your laptop must decide where to send it. It reaches the TaskFlow VM on the same Wi-Fi directly, but GitHub only through the router. How does it know which is which?

The idea

An IPv4 address is 32 bits, written as four 8-bit numbers (octets, 0–255): 192.168.1.50. Every address has a network part (which network) and a host part (which machine on it). CIDR notation /n says the first n bits are the network part. The same split written as an address is the subnet mask.

# 192.168.10.37/28: the mask's 1-bits mark the network part
IP      192      .168      .10       .37
        11000000 .10101000 .00001010 .0010|0101
Mask    11111111 .11111111 .11111111 .1111|0000   = 255.255.255.240  (/28 → 28 ones)
                              network ◀───┘└───▶ host (4 bits → 16 addresses)

Your machine uses that split to make one decision for every packet:

laptop 192.168.1.23/24
  ├─▶ 192.168.1.50   first 24 bits match (192.168.1.x) → same network → deliver directly
  └─▶ 140.82.112.3   no match → hand it to the default gateway 192.168.1.1 (the router)

The default gateway is the router's address on your network, usually .1. It forwards everything that isn't local.

Think of it like this

A campus postal system (this page reuses it throughout). The network part is the campus, the host part the building number: /24 means "the first three numbers name the campus". Mail for a building on your own campus you deliver yourself. Everything else goes to the campus gate (the default gateway), which knows the roads outside.

See it: your addresses and your gateway

$ ip -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s3           UP             192.168.1.50/24 metric 100 fe80::a00:27ff:fe3a:915c/64
docker0          DOWN           172.17.0.1/16
TokenMeaning
ipThe Linux network tool (package iproute2). It replaces the old ifconfig.
-brBrief: one line per interface
aShort for address: show the addresses on each interface

The enp0s3 line says this VM is host .50 on network 192.168.1.0/24 (cloud VMs name the NIC eth0 or ens5). lo is loopback (section 2) and docker0 is Docker's bridge (Session 8). The decision from the diagram, as the kernel stores it:

$ ip route
default via 192.168.1.1 dev enp0s3 proto dhcp src 192.168.1.50 metric 100
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 linkdown
192.168.1.0/24 dev enp0s3 proto kernel scope link src 192.168.1.50 metric 100

192.168.1.0/24 … scope link means "directly attached: deliver directly". default via 192.168.1.1 means "everything else goes to the gateway". When several routes match, the most specific one (longest prefix) wins.

What it does not do: show the address the internet sees. ip a lists only the addresses configured on this machine, and none of them is public here (section 2).

Build it up: subnet math

How many machines fit in a network? The host part has 32 − n bits, so there are 2(32 − n) addresses. Two are reserved: the first (host bits all 0) is the network address and the last (all 1) is the broadcast address. So usable hosts = 2(32 − n) − 2.

Worked example: which subnet is 192.168.10.37/28 in?
  1. Host bits = 32 − 28 = 4, so the block size is 24 = 16 addresses.
  2. Blocks in the last octet start at 0, 16, 32, 48… and 37 falls in the block starting at 32.
  3. Network = 192.168.10.32, broadcast = 32 + 15 = 192.168.10.47.
  4. Usable = .33 – .46, which is 14 hosts (16 − 2).

Check your arithmetic the way you'd check it on a server. Python's ipaddress module ships with every Ubuntu:

$ python3 -c "import ipaddress as i; n = i.ip_interface('192.168.10.37/28').network; print(n, n.netmask, n[1], n[-2], n.broadcast_address)"
192.168.10.32/28 255.255.255.240 192.168.10.33 192.168.10.46 192.168.10.47

Network, mask, first usable, last usable, broadcast: the same as the worked example. Likewise 10.0.0.0/16 → 65,534 hosts and 10.0.1.0/24 → 254 hosts, sitting inside the /16 (AWS reserves 5 IPs per subnet, so 251 there; Session 21). Now the cheat table:

IPv6 in one minute

IPv4's ~4.3 billion addresses ran out, so IPv6 uses 128 bits, 8 groups of 4 hex digits: 2404:6800:4007:080f:0000:0000:0000:200e. Drop leading zeros and replace one run of zero groups with :: → 2404:6800:4007:80f::200e. ::1 = loopback, fe80::/10 = link-local (every interface has one), /64 = the standard subnet.

Exam trap

"A /24 has 256 hosts." ✗ 256 addresses, 254 usable: the network and broadcast addresses are reserved.

"/24 is bigger than /16, because 24 > 16." ✗ A bigger prefix = more network bits, fewer host bits. /16 has 65,536 addresses, /24 has 256.

"A VPC can have subnets 10.0.1.0/24 and 10.0.1.128/25." ✗ They overlap (.128–.255 is in both), so AWS rejects the second.

Remember

IP = network part + host part · /n = how many bits name the network.
Usable hosts = 2(32 − n) − 2.
Same network → deliver directly · anything else → default gateway.

Mastery check
Q1. How many usable hosts are in 10.0.2.0/27? What are the first and last usable IPs?

32 − 27 = 5 host bits, so 25 = 32 addresses, minus 2 = 30 usable: 10.0.2.1 to 10.0.2.30. .0 is the network address and .31 is the broadcast.

Q2. Predict: your laptop is 192.168.1.23/24 and sends a packet to 192.168.2.10. Direct, or via the gateway? What changes if the laptop's prefix were /16?

With /24 the first 24 bits must match, and 192.168.1 ≠ 192.168.2, so it goes to the gateway. With /16 only 192.168 must match, so the laptop treats 192.168.2.10 as local and delivers it directly on the Wi-Fi.

Q3. Fill in: 10.0.0.0/16 holds ________ addresses and can be split into ________ /24 subnets of ________ usable hosts each.

65,536 · 256 · 254 (251 in AWS, which reserves 5 per subnet).

Q4. On a server, ip route has no default via … line. What can the server still reach, and what can't it?

Only machines on its directly attached networks (the scope link routes). Everything else, the internet included, fails with "Network is unreachable": no route says where non-local packets go.

2 Public vs private IP & NAT

The problem

Ask the VM for its address, then ask the internet:

$ ip -4 -br a show enp0s3        # what the machine thinks its IP is
enp0s3           UP             192.168.1.50/24
$ curl ifconfig.me               # what the internet sees
203.0.113.45

Two different answers, and both are right. Stranger still, your friend's laptop on their home Wi-Fi is also 192.168.1.23, exactly like yours. Internet addresses are supposed to be unique, so how can two machines share one?

The idea

A public IP is globally unique and routable on the internet, handed out by ISPs and cloud providers. A private IP comes from ranges reserved by RFC 1918, which any home, college or VPC can reuse, because internet routers never route them. The router in between does NAT (Network Address Translation): it rewrites the private source address to its own public one and remembers the mapping so the reply finds its way back.

Laptop 192.168.1.23:52344 ──▶ Router (NAT) ──▶ 203.0.113.45:40001 ──▶ github.com 140.82.112.3:443
                              table: 203.0.113.45:40001 ⇄ 192.168.1.23:52344
Reply  ◀── 192.168.1.23:52344 ◀── router looks up the table ◀── 140.82.112.3:443 → 203.0.113.45:40001
Think of it like this

Back on the campus. Building numbers are private IPs: they only mean something inside, and every campus has a "Building 23". The campus street address is the public IP, unique in the country. The gate guard is NAT: they stamp the campus address on every outgoing letter and log which building sent it, so the reply reaches the right building. A letter from outside that matches no log entry has nowhere to go, which is why the internet can't simply connect in to your laptop.

See it

TokenMeaning
ip -4 -br a show enp0s3-4 = IPv4 only, show enp0s3 = just that interface. The address configured on the machine.
curl ifconfig.meAsk a public web service "which IP did my request come from?" That is your address after NAT.

That solves the puzzle. 192.168.1.50 is the VM's building number inside the campus, and 203.0.113.45 is the router's public address, shared by every device behind it. Your friend's 192.168.1.23 and yours never meet on the internet: each leaves home as its own router's public IP.

What it does not do: curl ifconfig.me says nothing about whether anyone can connect in. NAT only creates mappings for connections that start inside.

In the cloud

An EC2 instance gets a private IP from its subnet (say 10.0.1.25), the only address ip a shows. Its public IP lives in AWS's Internet Gateway, which does 1:1 NAT between the two. Instances in private subnets have no public IP and go out through a NAT Gateway, outbound only (Session 21).

Exam trap

"Anyone who knows my laptop's 192.168.1.23 can connect to it over the internet." ✗ Private addresses are never routed there. Outsiders only see the router's public IP.

"172.32.0.1 is private." ✗ The block is 172.16–172.31, so it's public.

"NAT lets the internet reach machines behind the router." ✗ Only connections that start inside. Inbound needs port forwarding, a public IP or a load balancer.

Remember

Private = 10/8 · 172.16/12 · 192.168/16: reusable, never routed on the internet.
NAT = many private addresses share one public one, outbound only.

Mastery check
Q1. Public or private: 172.20.5.9, 172.32.0.1, 10.200.0.4, 192.169.1.1?

Private, public, private, public. 172.20 is inside 172.16–172.31. 172.32 is just outside it. 10.x is always private. 192.169 isn't 192.168.

Q2. Predict: TaskFlow runs on your home laptop. Your friend, on another network, runs curl http://203.0.113.45:3000/health (your router's public IP). What happens, and why?

It fails, usually as a timeout. The packet reaches your router, but no NAT mapping exists for an inbound connection to 3000, so the router can't tell which machine should get it and drops it. You'd need port forwarding (3000 → 192.168.1.23:3000) or a server with a public IP.

Q3. Fill in: NAT rewrites the ________ IP and port of outgoing packets to the router's ________ IP, and keeps a ________ so replies reach the right machine.

Source · public · translation table (mapping).

3 Ports & listening addresses

The problem

The TaskFlow VM at 192.168.1.50 runs SSH, PostgreSQL and the Node API at the same time. A packet arrives for 192.168.1.50. Which of the three gets it? And here is a puzzle you will hit in your first week:

shaurya@taskflow-vm:~$ curl localhost:3000/health
{"status":"ok"}
laptop$ curl http://192.168.1.50:3000/health
curl: (7) Failed to connect to 192.168.1.50 port 3000 after 2 ms: Couldn't connect to server

The app works on the server and is unreachable from one metre away.

The idea

A port is a 16-bit number (0–65535) that picks out one program's endpoint on a host, and a socket is IP + port: 192.168.1.50:3000. A server listens on a fixed, known port. A client connects from a random ephemeral port its OS picks. A TCP connection is identified by its 5-tuple: protocol, source IP, source port, destination IP, destination port.

 laptop 192.168.1.23                         taskflow-vm 192.168.1.50
 browser  :52410 ───────── TCP ─────────────▶ :3000  node (taskflow-api)
 ssh      :52344 ───────── TCP ─────────────▶ :22    sshd
                                              :5432  postgres (listening, nobody connected)
 one connection = (TCP, 192.168.1.23, 52410, 192.168.1.50, 3000)
Think of it like this

If the IP is the building, the port is the flat number inside it. A listening program lives in that flat and answers the door: SSH in flat 22, Postgres in flat 5432. A visitor writes their own randomly chosen flat number as the return address (the ephemeral port), so the reply reaches the right person.

See it: who is connected right now

$ ss -tn
State  Recv-Q Send-Q   Local Address:Port      Peer Address:Port  Process
ESTAB  0      0         192.168.1.50:22        192.168.1.23:52344
ESTAB  0      0         192.168.1.50:3000      192.168.1.23:52410
TokenMeaning
ssSocket statistics: lists sockets (it replaces the old netstat)
-tTCP sockets only
-nNumeric: show 22, not ssh, and skip DNS lookups

Server side: fixed ports (22, 3000). Laptop side: ephemeral ones (52344, 52410). What it does not do: list servers waiting for connections. Plain ss -t shows established connections only; add -l for listeners.

app.listen(PORT, HOST, () => {
  console.log(`taskflow-api listening on ${HOST}:${PORT}`);

Exam trap

"curl localhost:3000 works on the server, so the app is reachable." ✗ localhost takes the loopback path and skips the network, the bind address and the firewall. Test from another machine.

"The client connects from port 3000 too." ✗ Only the server side is 3000. The client uses an ephemeral port, different for every connection.

Remember

Socket = IP:port · servers listen on known ports, clients use random ones.
127.0.0.1 = this machine only · 0.0.0.0 = every interface.

Mastery check
Q1. Two browser tabs on the same laptop both talk to 192.168.1.50:3000. Same client IP, same server IP and port. How does the server keep the connections apart?

Each connection gets its own ephemeral source port (say 52410 and 52411), so the 5-tuples differ. The kernel delivers each packet to the matching connection.

Q2. sudo ss -tlnp shows 127.0.0.1:5432 for postgres. Can taskflow-api on another VM connect? What would it see?

No. Postgres only accepts loopback connections, so the remote API gets "Connection refused". The fix is Postgres's listen_addresses setting (plus pg_hba.conf and the firewall). For a database, local-only is often exactly what you want.

Q3. Predict: the app listens on 192.168.1.50:3000 (not 0.0.0.0). On the server you run curl localhost:3000. Result?

It fails to connect. localhost is 127.0.0.1, and nothing listens on 127.0.0.1:3000. curl 192.168.1.50:3000 would work, from the server and from other machines.

4 TCP vs UDP

The problem

Different traffic needs different guarantees:

POST /tasks {"title":"Write S4 notes"}   → must arrive complete, in order, exactly once
"What is the IP of github.com?"           → one tiny question, one tiny answer: speed matters most
One frame of a video call                 → if it's late it's useless: skip it, don't resend

One set of rules can't be ideal for all three, so the internet has two transport protocols.

The idea

TCP is connection-oriented: a 3-way handshake first, then every byte numbered, acknowledged and resent if lost, with slow-down under congestion. UDP is connectionless: independent datagrams with an 8-byte header, no handshake, no acknowledgements, no ordering. Fast, but packets can be lost.

  Laptop 192.168.1.23:52410                        taskflow-api 192.168.1.50:3000
        │ ── SYN        seq=x ─────────────────────────▶ │   "can we talk?"
        │ ◀─ SYN-ACK    seq=y, ack=x+1 ───────────────── │   "yes, can you hear me?"
        │ ── ACK        ack=y+1 ───────────────────────▶ │   "yes" → ESTABLISHED
        │ ══ GET /health HTTP/1.1 ═════════════════════▶ │
        │ ◀═ HTTP/1.1 200 OK {"status":"ok"} ═══════════ │
        │ ── FIN ──▶  ◀── ACK, FIN ──  ── ACK ──▶        │   4-step close
Think of it like this

TCP is a registered courier. They phone ahead to check someone is home (the handshake), number every page, get a signature for each delivery (ACK) and resend anything that went missing. UDP is a postcard. You drop it in the box and hope. Nobody confirms anything, which is exactly why it's quick.

See it: watch a handshake

$ sudo tcpdump -i lo -n 'tcp port 3000'      # then, in terminal 2: curl localhost:3000/health
10:31:02.114201 IP 127.0.0.1.52410 > 127.0.0.1.3000: Flags [S], seq 1849302211, win 65495, length 0
10:31:02.114215 IP 127.0.0.1.3000 > 127.0.0.1.52410: Flags [S.], seq 2210331876, ack 1849302212, win 65483, length 0
10:31:02.114228 IP 127.0.0.1.52410 > 127.0.0.1.3000: Flags [.], ack 1, win 512, length 0
10:31:02.114310 IP 127.0.0.1.52410 > 127.0.0.1.3000: Flags [P.], seq 1:84, ack 1, win 512, length 83: HTTP: GET /health HTTP/1.1
TokenMeaning
tcpdump -i loCapture packets on the loopback interface (needs root)
-n · 'tcp port 3000'Don't resolve names · only capture TCP traffic to or from port 3000
[S] · [S.] · [.]SYN · SYN-ACK · ACK: the handshake
[P.] · [F.]Push data (here, the HTTP request) · FIN (closing)

What it does not do: the handshake carries no data. Look at length 0 on the first three packets. The HTTP request travels only in the fourth, which is why every new TCP connection costs one round trip before any data moves.

Build it up: testing TCP and UDP ports

$ nc -zv 192.168.1.50 5432          # TCP: a real handshake, so the answer is trustworthy
Connection to 192.168.1.50 5432 port [tcp/postgresql] succeeded!
$ nc -zuv 8.8.8.8 53                # UDP: no handshake, so "succeeded" only means no error came back
Connection to 8.8.8.8 53 port [udp/domain] succeeded!

nc (netcat) opens a raw connection: -z = just test, -v = report, -u = UDP. With no handshake to rely on, test a UDP service by speaking its protocol (dig @8.8.8.8 google.com, section 5).

Why DNS picked UDP

A DNS lookup is one small question and one small answer, so a handshake first would double the wait. DNS uses UDP 53 for normal queries and falls back to TCP 53 for large responses and zone transfers, so firewalls must allow both.

Exam trap

"UDP is unreliable, so nothing important uses it." ✗ DNS, DHCP and video calls all run on UDP. When an app needs reliability on top of UDP it builds its own, as QUIC does for HTTP/3.

"HTTP always runs over TCP." ✗ HTTP/1.1 and HTTP/2 do. HTTP/3 runs over QUIC, which runs over UDP.

"nc -zu … succeeded proves the UDP port is open." ✗ With no handshake, silence looks the same as success.

Remember

TCP = handshake, reliable, ordered (web, SSH, databases).
UDP = fire-and-forget, fast (DNS, video, QUIC).
SYN → SYN-ACK → ACK, then data.

Mastery check
Q1. TCP or UDP: SSH · a Postgres query · a DNS lookup · a Google Meet video stream · HTTP/3?

TCP · TCP · UDP (TCP for big answers) · UDP · UDP (QUIC). Rule of thumb: if losing a byte corrupts the result, use TCP. If late data is worthless, use UDP.

Q2. Predict: your laptop sends a SYN to 192.168.1.50:3000, but nothing is listening there. What comes back, and what does curl print? What if a firewall silently drops the SYN instead?

The server's kernel replies RST (reset) at once, and curl prints "Couldn't connect to server" (connection refused). If a firewall drops the SYN, nothing comes back; the client retries, then gives up with a timeout. Section 8 turns this into a diagnostic.

Q3. Fill in: the client sends ________, the server replies ________, the client answers ________, and only then does ________ flow.

SYN · SYN-ACK · ACK · application data (for example, the HTTP request).

5 DNS

The problem

Nobody types 142.250.183.142, and a server's IP changes every time you move it. So names have to be turned into IPs. That raises its own puzzle:

$ grep taskflow /etc/hosts
192.168.1.50    taskflow.local api.taskflow.local
$ curl -s http://taskflow.local:3000/health     # works
{"status":"ok"}
$ dig +short taskflow.local                     # …and the lookup tool finds nothing?
$

And when you move api.taskflow.example.com to a new server, some users keep hitting the old one for an hour.

The idea

DNS (Domain Name System) is a distributed directory that maps names to records, mostly IP addresses. Your OS checks /etc/hosts first. If there's no match, it asks a recursive resolver, which walks the tree from the root to the TLD to the domain's own authoritative server. Every level caches the answer for its TTL (time to live, in seconds).

curl https://api.taskflow.example.com/health
 1. Application / browser cache ─────────────── hit? done
 2. OS: /etc/hosts  (nsswitch "hosts: files dns") ── match? done
 3. OS stub resolver cache (systemd-resolved @ 127.0.0.53)
 4. Recursive resolver (ISP / 8.8.8.8 / 1.1.1.1 / AWS VPC .2) ── cached? done
        │ not cached → it walks the tree:
        ├──▶ 5. Root server  "."            → "ask the .com TLD servers"
        ├──▶ 6. TLD server   ".com"         → "ask ns1.exampledns.net (authoritative)"
        └──▶ 7. Authoritative server        → "A 203.0.113.10, TTL 300"
 8. Answer cached at each level for TTL seconds → curl connects to 203.0.113.10:443
Think of it like this

DNS is the campus directory. You check your own contacts list first (/etc/hosts). Otherwise you ring directory enquiries (the recursive resolver). The operator asks the national index (root) who handles ".com", asks .com who handles "example.com", then asks that company's receptionist (the authoritative server), and remembers the answer for TTL seconds, even if it changes meanwhile.

See it: one lookup

Exam trap

"TTL is how long a DNS record exists." ✗ TTL is how long resolvers may cache the answer.

"dig returns nothing, so the hosts-file entry is broken." ✗ dig never reads /etc/hosts. Check with getent hosts.

"Put a CNAME on example.com pointing to the load balancer." ✗ The zone apex can't be a CNAME. Use an A record or the cloud's alias record.

Remember

Mastery check
Q1. /etc/hosts maps api.taskflow.local → 192.168.1.50, and DNS says 192.168.1.60. Which IP does curl use? Which does dig show?

curl uses 192.168.1.50, because the OS resolver checks files before DNS (hosts: files dns in /etc/nsswitch.conf). dig shows 192.168.1.60, because it only asks DNS.

Q2. Which record type? (a) www → an AWS load balancer's hostname (b) where mail for example.com goes (c) proving to Let's Encrypt that you own the domain (d) 8.8.8.8 → dns.google

(a) CNAME · (b) MX · (c) TXT · (d) PTR.

Q3. One name returns status: NXDOMAIN, another status: SERVFAIL. What does each suggest you check?

NXDOMAIN: the name doesn't exist, so check for a typo or a missing record in the zone. SERVFAIL: the lookup itself broke (the authoritative servers are unreachable or misconfigured, or DNSSEC failed), so try dig @8.8.8.8 and dig +trace to see where.

6 HTTP

The problem

TCP gives you a reliable pipe of bytes and nothing more. The API still needs to know what you want (list tasks or create one?), which site you mean (one IP can host many), what format your data is in and who you are, and you need to know whether it worked. Both sides must agree on a format.

The idea

HTTP is that format, and in HTTP/1.1 it is plain text. A request is a request line (method, path, version), headers, a blank line and an optional body. A response is a status line (version, code, reason), headers, a blank line and a body.

Request (laptop → API)                         Response (API → laptop)
POST /tasks HTTP/1.1         ← request line     HTTP/1.1 201 Created            ← status line
Host: 192.168.1.50:3000      ← headers start    Content-Type: application/json
Content-Type: application/json                 Content-Length: 46
Content-Length: 26
                             ← blank line = headers end
{"title":"Write S4 notes"}   ← body (26 bytes)  {"id":1,"title":"Write S4 notes","done":false}
Think of it like this

HTTP is the agreed letter format inside the courier's envelope. The first line says what you want ("POST to /tasks"), the headers are labels (who it's for, what language, how long), then a blank line and the letter. The reply starts with a stamp, the status code: 201 Created, 404 Not Found.

Mastery check
Q1. nginx in front of taskflow-api returns 502 on one request and 504 on another. What's the difference?

502 Bad Gateway: nginx got no valid response from the upstream (the api is down, refused the connection, or is on the wrong port). 504 Gateway Timeout: the upstream accepted the request but didn't answer within nginx's timeout (a slow handler or DB query).

Q2. Spot the bug: curl -X POST localhost:3000/tasks -d '{"title":"x"}' fails, but the same command with -H "Content-Type: application/json" returns 201. Why?

Without the header, curl -d labels the body application/x-www-form-urlencoded, so express.json() skips it. Express 5 leaves req.body undefined, reading title from it throws, and you get a 500 (Express 4 set {}, giving a 400). The server trusts Content-Type, not your intentions.

Q3. Predict: you send the same POST /tasks twice, then the same PUT /tasks/1 {"title":"A","done":true} twice. How many tasks exist, and what state is task 1 in?

Two tasks, because POST isn't idempotent. Task 1 is {"title":"A","done":true} after the first PUT and unchanged by the second, because PUT is idempotent.

7 HTTPS & TLS

The problem

Section 6 showed that HTTP/1.1 is plain text. On college Wi-Fi that means:

laptop ── POST /login {"password":"hunter2"} ──▶ Wi-Fi router ──▶ ISP ──▶ … ──▶ server
          Authorization: Bearer eyJhbGciOi…            ▲ readable, and editable, at every hop

Anyone on the path can read your token and change the response. And how do you know that 203.0.113.10 really is your API, and not an impostor someone pointed your DNS at?

The idea

HTTPS = HTTP inside a TLS tunnel, on port 443. TLS gives encryption (nobody can read it), integrity (nobody can change it undetected) and authentication (it's the real server). The server proves who it is with a certificate: a public key bound to names (the SAN, Subject Alternative Names), signed by a CA (certificate authority) your OS trusts, valid between two dates.

 client                                                  server (api.taskflow.example.com)
   │ ── ClientHello: TLS versions, ciphers, SNI = "api.taskflow.example.com" ──▶ │
   │ ◀── ServerHello + certificate (signed by a CA) ─────────────────────────── │
   │     client checks: CA trusted? name matches the SAN? not expired?           │
   │ ◀════ both derive the same session key (TLS 1.3: one round trip) ═══════▶ │
   │ ════ encrypted HTTP: GET /tasks, Authorization: … ═════════════════════════▶ │
 trust chain: leaf cert → intermediate CA → root CA in the OS trust store
Think of it like this

The courier now carries a sealed, tamper-evident envelope (encryption and integrity). Before handing it over, the recipient shows an ID card (the certificate) from an authority you trust (the CA), and the name on it must match the address you wrote (the SAN). The postman still sees which building it goes to (the IP and SNI name), never what's inside.

Exam trap

"HTTPS hides which website I'm visiting." ✗ The path, headers and body are encrypted, but the destination IP and the SNI hostname are visible.

"SSL is the current protocol." ✗ SSL is long deprecated. Today it's TLS 1.2 or 1.3, even though people still say "SSL certificate".

"The padlock means the site is safe." ✗ It means the connection is encrypted to whoever holds that certificate. A phishing site can have a valid certificate too.

Remember

HTTPS = HTTP + TLS on 443: encryption + integrity + authentication.
Certificate = public key + names (SAN) + dates, signed by a CA.

Mastery check
Q1. TaskFlow's dev certificate is for taskflow.local. You open https://192.168.1.50 and the browser warns you. Why, and what's the fix?

The host in the URL (192.168.1.50) isn't in the certificate's SAN, so authentication fails even though encryption would work. Browse via https://taskflow.local (map it in /etc/hosts), or issue a certificate that includes the IP.

Q2. You call https://api.taskflow.example.com/tasks with a Bearer token on café Wi-Fi. What can someone sniffing the Wi-Fi see, and what can't they?

They can see your DNS lookup (unless it's encrypted), the destination IP, the SNI hostname, and the timing and size of the traffic. They can't see the path /tasks, the headers (so not the token), or the body.

Q3. Predict: curl http://github.com with no flags. What do you see, and what changes with -L?

Nothing visible. The reply is a 301 with an empty body (Content-Length: 0) and a Location: https://github.com/ header, which curl only shows with -i. -L follows the redirect, does the TLS handshake and prints the HTTPS page.

Two bugs, and the timeout came from the firewall. Fixing only the bind address would change nothing for your friend; fixing only the firewall would turn the timeout into "refused". The ladder found both.

Exam trap

"ping fails, so the server is down." ✗ ICMP is often blocked. Test the actual TCP port.

"Connection refused means a firewall is blocking me." ✗ Usually the opposite: you reached the host and nothing listens there. Firewalls that drop packets cause timeouts.

Remember

DNS → reachable → port → listen address → firewall → app logs.
Refused = reached, nobody listening · Timed out = dropped on the way.

Mastery check
Q1. You run ss -tulpn without sudo and the Process column is empty for port 3000. Is nothing listening?

Something is listening, because the socket line is there. Without root, ss can't show processes owned by other users. Re-run it with sudo.

Q2. traceroute shows hops 1–4 fine, then * * * for every hop up to 30. Where would you look?

At the boundary after hop 4. Either a device there drops everything (a firewall or broken router), or the destination itself drops probes. Then test the real service port with nc -zv, because traceroute probes may be filtered while TCP 443 works fine.

Q3. Put these in ladder order and name what each one rules out: sudo ss -tlnp, dig +short, nc -zv, journalctl -u taskflow.

dig (the name resolves to the right IP) → nc -zv (the path and firewall let the port through) → ss -tlnp (the app listens on the right address and port) → journalctl (what the app itself did with the request).

★ Putting it all together

The big idea

When you open https://api.taskflow.example.com/tasks, DNS turns the name into an IP. Your laptop sees it isn't local and sends the packet to the default gateway, which NATs your private address to its public one. TCP does a handshake with port 443, TLS proves the server's identity and encrypts everything, then an HTTP GET goes in and a 200 with JSON comes back. Every later DevOps tool (Docker port mapping, Kubernetes Services, Ingress, security groups) configures one of these layers, and every outage is debugged by walking them in order.

Final mastery check — combine everything
Q1. List every step between typing https://api.taskflow.example.com/tasks and seeing JSON, and name one command that tests each step.

(1) Name → IP: dig +short / getent hosts. (2) Not local, so to the default gateway and NAT: ip route, traceroute. (3) TCP handshake to 443: nc -zv host 443. (4) TLS and the certificate check: curl -v / openssl s_client. (5) HTTP request and status: curl -v. (6) On the server, the app listening and logging: ss -tlnp, journalctl.

Q2. EC2 instance: private 10.0.1.25, public 13.233.10.20. The security group allows TCP 3000 from anywhere, but the app listens on 127.0.0.1:3000. Does your friend's curl http://13.233.10.20:3000 get refused or time out? Why?

Refused. The Internet Gateway NATs the SYN to 10.0.1.25, the security group lets it through, and nothing listens on 10.0.1.25:3000, so the kernel replies RST. Fix: HOST=0.0.0.0.

Q3. Same instance, the app fixed to 0.0.0.0:3000, but the security group only allows port 22. Refused or timeout? Which command proves it from your laptop?

Timeout: the security group silently drops the SYN. nc -zv -w 3 13.233.10.20 3000 → "timed out" while port 22 succeeds. Fix: an inbound rule for TCP 3000.

Q4. Your home Wi-Fi is 192.168.1.0/24, and the college VPN also hands out 192.168.1.0/24. With the VPN up, you can't reach the college server 192.168.1.10. Why?

The two private ranges overlap. Your routing table treats 192.168.1.10 as directly attached on the Wi-Fi, so the packet is delivered locally and never enters the VPN tunnel. Fix: non-overlapping ranges, or a more specific route for the server.

Q5. nginx (taskflow-web, port 80) proxies /api to http://127.0.0.1:3000 on the same host. Users get 502, and sudo ss -tlnp | grep 3000 prints nothing. What happened, and what's your next command?

Nothing listens on 3000, so nginx's upstream connection is refused: a 502. The API crashed or never started. Next: systemctl status taskflow and journalctl -u taskflow -n 50.

Q6. You moved api.taskflow.example.com (TTL 3600) to a new server. dig +short on your laptop shows the new IP, but your friend's shows the old one, so their curl hits the dead server. Explain, and say how you'd check what the authoritative server says.

Their resolver cached the old A record and serves it until the TTL runs out (up to an hour). dig +trace or dig @<authoritative NS> shows the source of truth. Next time, lower the TTL before migrating.

Q7. curl https://taskflow.local prints "SSL certificate problem: self-signed certificate", and dig taskflow.local returns nothing. Which layers worked, and which one failed?

The name resolved through /etc/hosts (which dig ignores), TCP to 443 connected, and TLS got as far as the certificate check. Only trust failed: no CA your system trusts signed it. Add your dev CA to the trust store, or use -k for a one-off test.
