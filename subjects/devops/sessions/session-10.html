1 Pods

The problem

Session 9 used the word "pod" everywhere without explaining it. Look at this line again:

NAME                     READY   STATUS    RESTARTS   AGE
hello-6d9f7c8b5d-p8wzn   1/1     Running   0          48s

READY 1/1: one out of one what? And why does Kubernetes schedule "pods" instead of just containers, the way Docker does?

The idea

A Pod is the smallest thing Kubernetes runs: one or more containers that always live together. They're scheduled onto the same node, share one network namespace (one IP, and they reach each other on localhost), can share volumes, and are created and deleted as a unit. READY 1/1 means 1 of the pod's 1 containers is ready. Most pods hold exactly one app container.

 Pod taskflow-api                      IP 10.244.0.5   (one IP for the whole pod)
 ┌─────────────────────────────────────────────────────┐
 │  pause container: holds the network namespace       │
 │  ┌────────────────┐           ┌────────────────┐    │
 │  │ container  api │◀─localhost─▶│ (optional 2nd) │    │
 │  │ listens :3000  │           │  container     │    │
 │  └───────┬────────┘           └───────┬────────┘    │
 │          └────── shared volume ───────┘             │
 └─────────────────────────────────────────────────────┘
   always on ONE node · started and deleted as a unit · replaced, never repaired
Think of it like this

Back in Session 9's restaurant, a pod is a cook's station. One or more cooks (containers) work at it. They share one phone extension (the pod IP) and one counter (volumes), and the station sits in exactly one kitchen (node). If a station breaks, nobody repairs it: the managers set up a fresh one somewhere, with a new name and a new extension.

See it: TaskFlow as a Pod

One-time setup for every Kubernetes page from here on (namespaces are Session 15):

$ minikube start
$ kubectl create namespace taskflow
$ kubectl config set-context --current --namespace=taskflow   # so you can skip -n taskflow

This is Session 9's pod plus the fields a real pod needs:

pod.yaml
apiVersion: v1                       # Pods live in the core API group → just "v1"
kind: Pod
metadata:
  name: taskflow-api                  # unique per namespace, lowercase + digits + '-'
  namespace: taskflow
  labels:                             # tags that selectors match on (section 4)
    app: taskflow-api
    tier: backend
spec:
  containers:
    - name: api                       # container name, used with -c
      image: shauryav/taskflow-api:1.0.0
      imagePullPolicy: IfNotPresent   # pull only if the node doesn't have it
      ports:
        - containerPort: 3000           # documentation + lets Services refer to it
      env:
        - name: PORT
          value: "3000"                 # env values are always strings → quote numbers
      resources:
        requests: { cpu: 100m, memory: 128Mi }   # reserved by the scheduler
        limits:   { cpu: 500m, memory: 256Mi }   # hard cap (memory over → OOMKilled)
  restartPolicy: Always               # default; kubelet restarts crashed containers

Exam trap

"A pod is just Kubernetes' word for a container." ✗ A pod wraps one or more containers that share an IP, localhost and volumes. The pod is what gets scheduled and gets an IP.

"containerPort: 3000 publishes the port, like docker run -p." ✗ It's informational. Other pods can reach the pod IP on 3000 anyway, and outside access comes from a Service (S11).

Remember

Pod = 1+ containers · one IP · one node · one lifecycle. Replaced, never repaired.
Debug loop: get -o wide → describe (Events!) → logs → exec.

Mastery check
Q1. A pod shows READY 1/2. What does that mean?

The pod has 2 containers and only 1 is ready. Find out which with kubectl describe pod, then kubectl logs POD -c NAME.

Q2. You delete taskflow-api (this bare pod) and run kubectl get pods. What do you see, compared with deleting a pod of Session 9's hello Deployment?

Nothing: No resources found. A bare pod has no controller to recreate it. The Deployment's pod came back because a ReplicaSet reconciles its count (section 5).

Q3. The image is shauryav/taskflow-api with no tag. Which two things change compared with :1.0.0?

It means :latest, a moving tag (Session 6), and imagePullPolicy defaults to Always, so every start re-pulls. Pin real tags.

2 Sidecars & init containers

The problem

Two TaskFlow headaches. The API writes a log file that a log shipper should read, without baking the shipper into the API image. And the API starts faster than Postgres, so every fresh deploy begins with crashes:

Error: connect ECONNREFUSED 10.96.48.200:5432
    at TCPConnectWrap.afterConnect [as oncomplete] (node:net:1611:16)

Both need a container that isn't the app but must stick to it.

The idea

A sidecar is a second container in the same pod. It shares localhost and can mount the same volume, so it can read the app's files or proxy its traffic. An init container runs to completion, in order, before any app container starts. If it fails, the app never starts, and the kubelet retries it.

 time ─────────────────────────────────────────────────────────────▶
 init: wait-for-db  ██████████ exit 0
                               app: api        ████████████████████████
                               sidecar: log-agent ███████████████████████
 STATUS:  Init:0/1             PodInitializing → Running (2/2)
Think of it like this

At the cook's station, a sidecar is a helper who works alongside the cook all shift, at the same counter, on the same phone line (plating, or carrying the log book to the office). An init container is the prep cook: he sets up the station (checks the gas is on, i.e. that the DB answers), then leaves. Only then do the cooks start.

See it: a log-shipping sidecar

sidecar-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: taskflow-api-logs
  labels:
    app: taskflow-demo                # deliberately NOT app=taskflow-api (see section 5)
spec:
  volumes:
    - name: logs
      emptyDir: {}                    # scratch dir, lives as long as the Pod
  containers:
    - name: api                       # main container
      image: shauryav/taskflow-api:1.0.0
      env:
        - name: LOG_FILE              # TaskFlow also writes logs here when set
          value: /var/log/taskflow/app.log
      ports:
        - containerPort: 3000
      volumeMounts:
        - name: logs
          mountPath: /var/log/taskflow
    - name: log-agent                 # sidecar: stands in for fluent-bit / a log shipper
      image: busybox:1.36
      command: ["sh", "-c", "tail -n+1 -F /var/log/taskflow/app.log"]
      volumeMounts:
        - name: logs
          mountPath: /var/log/taskflow
          readOnly: true
FieldMeaning
spec.volumes[].emptyDir: {}A pod-level scratch directory, created empty and deleted with the pod (Session 13)
volumeMounts (in each container)Where that container sees the volume. Both mount logs at the same path, so they see the same files.
commandReplaces the image's ENTRYPOINT (Session 7). tail -F follows the file even before it exists.
readOnly: trueThe sidecar can read the logs but not change them
 
$ kubectl apply -f sidecar-pod.yaml
$ kubectl get pod taskflow-api-logs
NAME                READY   STATUS    RESTARTS   AGE
taskflow-api-logs   2/2     Running   0          12s          # 2/2 = both containers ready
$ kubectl logs taskflow-api-logs
Defaulted container "api" out of: api, log-agent      # always pass -c with multi-container pods
TaskFlow API listening on port 3000
$ kubectl logs taskflow-api-logs -c log-agent             # the sidecar is reading the shared file
TaskFlow API listening on port 3000
$ kubectl exec taskflow-api-logs -c log-agent -- wget -qO- localhost:3000/health
{"status":"ok"}                                 # busybox reached the api via localhost

What it does not do: scale separately. The two containers always come in pairs: three replicas means three APIs and three log agents.

Build it up: wait for the database

pod-with-init.yaml
apiVersion: v1
kind: Pod
metadata:
  name: taskflow-api-init
  labels:
    app: taskflow-demo
spec:
  initContainers:                     # all must exit 0, in order, before "containers" start
    - name: wait-for-db
      image: postgres:16-alpine       # only for its pg_isready binary
      command: ["sh", "-c",
        "until pg_isready -h taskflow-db -p 5432; do echo waiting for db; sleep 2; done"]
  containers:
    - name: api
      image: shauryav/taskflow-api:1.0.0
      ports:
        - containerPort: 3000
$ kubectl get pod taskflow-api-init -w
NAME                READY   STATUS            RESTARTS   AGE
taskflow-api-init   0/1     Init:0/1          0          5s     # 0 of 1 init containers done
taskflow-api-init   0/1     PodInitializing   0          41s
taskflow-api-init   1/1     Running           0          43s
$ kubectl logs taskflow-api-init -c wait-for-db
taskflow-db:5432 - no response
waiting for db
taskflow-db:5432 - accepting connections

until … done loops until pg_isready succeeds (Session 3), and taskflow-db is a Service name that resolves once the DB Service exists (Session 11). A native sidecar (GA since Kubernetes 1.33) is declared under initContainers with restartPolicy: Always. It then starts before the app and stops after it, which suits log shippers and proxies.

Exam trap

"Put the API and Postgres in one pod so they're close together." ✗ You couldn't scale them separately, and a DB restart would take the API with it. Use two pods and a Service.

"Two containers in one pod can both listen on port 3000." ✗ They share one network namespace, so the second fails with EADDRINUSE.

Remember

Sidecar = runs alongside, shares localhost + volumes. Init = runs first, to completion, in order.
Multi-container pods: always pass -c NAME.

Mastery check
Q1. A pod has shown Init:0/1 for 3 minutes. What does it mean, and what do you run?

The first init container hasn't finished, so the app hasn't started. Run kubectl logs POD -c wait-for-db (and describe). Usually the DB or its Service isn't up yet.

Q2. Predict: the sidecar runs wget localhost:3000. Which container answers, and why?

The api container. Both containers share the pod's network namespace, so localhost is the same interface for both.

Q3. Spot the bug: the log-agent mounts the volume at /logs and tails /var/log/taskflow/app.log.

The mount path and the tailed path don't match. The agent sees the shared files under /logs, so /var/log/taskflow/app.log doesn't exist in its filesystem. tail -F just waits forever. Mount at the same path, or tail /logs/app.log.

3 Pod lifecycle

The problem

Two puzzles from the first week:

$ kubectl get pod taskflow-api
NAME           READY   STATUS             RESTARTS      AGE
taskflow-api   0/1     CrashLoopBackOff   4 (30s ago)   3m
$ kubectl get pod taskflow-api -o jsonpath='{.status.phase}'
Running                                # puzzle 1: crashing, yet "Running"?
$ time kubectl delete pod taskflow-api
pod "taskflow-api" deleted
real	0m31.2s                         # puzzle 2: why 30 seconds, every time?

The idea

Kubernetes tracks two levels. The pod has a phase, one word for the whole pod. Each container has a state (Waiting / Running / Terminated) with a reason. The STATUS column shows the most interesting container reason, not the phase. What happens when a container exits is decided by the pod's restartPolicy, carried out locally by the kubelet.

             scheduled, pulling images, init containers running
  Pending ──────────────────────────────────────────▶ Running ── all containers exit 0, no restart ─▶ Succeeded
     │                                                 │  ▲
     │                                                 │  └─ crashed container restarted in place: still Running
     │                                                 └──── a container fails and isn't restarted ──▶ Failed
     └── node unreachable, at any time ──▶ Unknown
Think of it like this

The phase is the sign on the station: "being set up", "open", "finished", "closed down". The container state is each cook's condition. A cook who faints is sent back to work by the head chef (the kubelet), and the sign stays "open". The chef waits a little longer after every faint: 10 s, 20 s, 40 s… That waiting is CrashLoopBackOff.

See it: phase vs STATUS

That solves puzzle 1. CrashLoopBackOff is a container Waiting reason: the container keeps crashing and the kubelet is waiting before the next restart. The phase stays Running because restartPolicy: Always means it's never finished. (-o jsonpath='{.status.phase}' reads one field from status.) What it does not do: create a new pod. A restart keeps the name, IP and node, and only RESTARTS goes up. Terminating isn't a phase either, just the STATUS of a pod that's shutting down.

Build it up

The full tables

PhaseMeaningTypical cause

Restarts happen in the same pod on the same node. The delay doubles each time (10 s, 20 s, 40 s …) up to 5 minutes, and resets after 10 minutes of running cleanly. Find the crash reason with kubectl logs POD --previous, the logs of the instance that died.

It's Session 6's docker stop with a 30-second clock. A 31-second delete means the app ignored SIGTERM and was killed at the deadline, usually because of shell-form CMD npm start: sh is PID 1 and never passes the signal to Node. Use CMD ["node","server.js"] (Session 7) and handle it:

server.js (excerpt)
process.on('SIGTERM', () => {
  console.log('SIGTERM received, closing server');
  server.close(() => process.exit(0));   // stop accepting, finish open requests, exit 0
});

kubectl delete pod x --grace-period=0 --force skips all of this. Keep it for pods stuck on dead nodes.

Exam trap

"CrashLoopBackOff is a pod phase." ✗ It's a container Waiting reason. The phase is usually Running. The five phases are Pending, Running, Succeeded, Failed and Unknown.

"restartPolicy moves a crashing pod to another node." ✗ The kubelet restarts the container in place, on the same node. Only controllers create replacement pods, and they put them wherever the scheduler says.

Remember

Phase = the pod (Pending → Running → Succeeded/Failed, + Unknown). State = each container (Waiting/Running/Terminated + reason).
delete = SIGTERM → 30 s → SIGKILL.

Mastery check
Q1. A container crashes and RESTARTS goes 0 → 1, but the pod's name and IP don't change. Who restarted it? How is that different from deleting the pod?

The kubelet restarted the container in place (restartPolicy Always). Deleting the pod makes its controller create a new pod, with a new name and IP, possibly on another node.

Q2. Predict the final phase: a pod with restartPolicy: Never whose only container exits 1. Then the same with OnFailure.

Never: Failed. OnFailure: the kubelet restarts it with back-off, so it stays Running and STATUS cycles through Error and CrashLoopBackOff. If it eventually exits 0, it ends Succeeded.

Q3. A STATUS of OOMKilled: which state, what exit code, and which field do you change?

A Terminated container that went over its memory limit, killed with exit 137 (128 + SIGKILL). Raise resources.limits.memory or fix the leak.

Q4. Every kubectl delete pod of your API takes ~30 s, and logs never show "SIGTERM received". Name the likely Dockerfile bug.

Shell-form CMD (CMD npm start or CMD node server.js). sh is PID 1 and doesn't forward SIGTERM, so Node never hears it and gets SIGKILLed at 30 s. Use CMD ["node","server.js"].

4 Labels & selectors

The problem

Pod names are random (hello-6d9f7c8b5d-zr7tm) and change with every replacement. So how does a controller know which pods are "its" three? How will a Service (S11) know where to send traffic, or you which pods to delete? Matching on names would break the moment a pod is replaced.

The idea

A label is a key/value pair on any object: app=taskflow-api, tier=backend, env=dev. A selector is a query over labels. ReplicaSets, Deployments, Services and NetworkPolicies all find their pods this way, which makes labels the glue of Kubernetes.

 pod taskflow-api     app=taskflow-api   tier=backend    ◀── picked by  tier=backend
 pod taskflow-web     app=taskflow-web   tier=frontend
 pod taskflow-db      app=taskflow-db    tier=backend    ◀── picked by  tier=backend

 selector  app=taskflow-api                  → 1 pod
 selector  tier=backend                      → 2 pods (api + db)
 selector  app=taskflow-api,tier=backend     → 1 pod  (comma = AND)
Think of it like this

Labels are the aprons and badges on each station: "API", "backend". A selector is the manager shouting "everyone in an API apron, step forward". It doesn't matter what a cook is called or where they stand, only what they're wearing.

See it: tag and query

$ kubectl apply -f pod.yaml                 # section 1's pod: app=taskflow-api, tier=backend
$ kubectl run taskflow-web --image=nginx:1.27-alpine --labels="app=taskflow-web,tier=frontend"
pod/taskflow-web created
$ kubectl get pods --show-labels
NAME           READY   STATUS    RESTARTS   AGE   LABELS
taskflow-api   1/1     Running   0          2m    app=taskflow-api,tier=backend
taskflow-web   1/1     Running   0          10s   app=taskflow-web,tier=frontend
$ kubectl get pods -l app=taskflow-api,tier=backend
NAME           READY   STATUS    RESTARTS   AGE
taskflow-api   1/1     Running   0          3m
TokenMeaning
kubectl run NAME --image=…Create one bare pod imperatively
--labels="k=v,k2=v2"Labels to put on it
--show-labelsAdd a LABELS column
-l app=taskflow-api,tier=backendSelector: only pods with both labels (comma = AND)

What it does not do: labels don't change the pod's behaviour at all. They're only there to be selected. Annotations are key/values too, but they can't be selected at all. They hold notes for tools, like kubernetes.io/change-cause (section 7).

Build it up

$ kubectl label pod taskflow-api env=dev                # add
pod/taskflow-api labeled
$ kubectl label pod taskflow-api env=prod --overwrite    # change (needs --overwrite)
$ kubectl label pod taskflow-api env-                   # remove: key followed by '-'

$ kubectl get pods -l 'tier in (backend,frontend)'      # set-based; quote it for the shell
$ kubectl get pods -l 'tier!=frontend'
$ kubectl get pods -l '!env'                            # pods WITHOUT an env label
$ kubectl get pods -L tier                              # show one label as a column
NAME           READY   STATUS    RESTARTS   AGE   TIER

taskflow-web   1/1     Running   0          1m    frontend
$ kubectl delete pods -l 'tier in (backend,frontend)'   # bulk delete by label

pod "taskflow-web" deleted

In YAML, controllers write selectors in two forms, ANDed together:

selector:
  matchLabels:                 # equality: app == taskflow-api AND tier == backend
    app: taskflow-api
    tier: backend
  matchExpressions:            # set-based
    - { key: env,    operator: In,     values: [dev, staging] }
    - { key: track,  operator: NotIn,  values: [canary] }
    - { key: team,   operator: Exists }          # no values for Exists / DoesNotExist
FormOperatorskubectl equivalentSupported by
Equality (matchLabels)=, ==, !=-l app=taskflow-api,tier!=frontendEverything, including Services (as a plain map)
Set-based (matchExpressions)In, NotIn, Exists, DoesNotExist-l 'env in (dev,staging)', -l '!env'ReplicaSet, Deployment, Job, DaemonSet, NetworkPolicy, but not Service

Keep one small label set everywhere: app, plus tier/env if you need them. The official recommended keys (app.kubernetes.io/name, …/component) are what Helm charts use (Session 17).

Exam trap

"A Deployment knows its pods by their names." ✗ Only by labels, through its selector. A pod's name is never used for ownership.

"A Service selector can use matchExpressions." ✗ Service spec.selector is a plain equality map.

Remember

Labels tag · selectors query · comma = AND.
Controllers and Services own pods purely by label match.

Mastery check
Q1. Using the diagram's three pods, which pods does each select: -l tier=backend, -l 'app in (taskflow-web,taskflow-db)', -l 'tier!=backend'?

api + db · web + db · web.

Q2. You want to record "deployed by CI run #412" on a Deployment. Label or annotation?

Annotation. Nobody will select on it, and annotation values can be long free text. Labels are for grouping and selecting.

Q3. Write the matchExpressions for "env is dev or staging, and the pod has no canary label at all".

- { key: env, operator: In, values: [dev, staging] } and - { key: canary, operator: DoesNotExist }.

5 ReplicaSets

The problem

Section 1's bare pod runs on node-2. node-2 dies, and nobody recreates the pod. You also want three of them, not one, and you don't want to write pod-1.yaml, pod-2.yaml, pod-3.yaml by hand.

The idea

A ReplicaSet (RS) keeps exactly replicas pods matching its selector running, and stamps out new ones from its template when the count is short. It's Session 9's reconcile loop: count matching pods, compare with desired, create or delete.

 ReplicaSet taskflow-api-rs     replicas: 3     selector: app=taskflow-api
      │  every change: count pods with app=taskflow-api … found 2
      │  desired 3 − actual 2 = 1 → create 1 pod from the template
      ▼
 [taskflow-api-rs-d4f9w]  [taskflow-api-rs-m8hzt]  [taskflow-api-rs-q2vbn]  ← new
       names = <rs-name>-<5 random chars>
Think of it like this

A ReplicaSet is a shift manager with exactly one rule: "always 3 stations in API aprons". He counts aprons, not names. One station breaks? He sets up another from the station blueprint (the template). There are four? He closes one.

See it: self-healing

replicaset.yaml
apiVersion: apps/v1                  # workload controllers live in the "apps" group
kind: ReplicaSet
metadata:
  name: taskflow-api-rs
spec:
  replicas: 3                         # desired number of Pods
  selector:                           # which Pods this RS counts as "mine"
    matchLabels:
      app: taskflow-api
  template:                           # Pod blueprint used when it must create one
    metadata:
      labels:                         # MUST satisfy the selector above
        app: taskflow-api
    spec:
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0
          ports:
            - containerPort: 3000
FieldMeaning
spec.replicasDesired count (default 1)
spec.selectorThe label query that defines ownership. Required in apps/v1.
spec.templateA full pod spec minus apiVersion/kind. Its pods are named <rs-name>-<5 random chars>.
template.metadata.labelsMust match the selector, or the API server rejects the ReplicaSet

Common mistakes
  • Template labels that don't match the selector:
    The ReplicaSet "taskflow-api-rs" is invalid: spec.template.metadata.labels: Invalid value: ...: `selector` does not match template `labels`
  • Adoption: if section 1's bare taskflow-api pod (labelled app=taskflow-api) is still running, the RS adopts it. You'll see it plus only 2 new pods.
Exam trap

"A ReplicaSet only manages the pods it created." ✗ It manages every pod matching its selector that has no other owner. That's why the sidecar and init demo pods used app: taskflow-demo.

"Changing a ReplicaSet's image rolls out the new version." ✗ Only new pods get it. Rollouts are a Deployment feature.

Remember

ReplicaSet = selector + replicas + template. It replaces missing pods and never updates live ones.
You use it through a Deployment.

Mastery check
Q1. Predict: the RS wants 3. You create a bare pod by hand with label app=taskflow-api. What happens?

The RS now counts 4 matching pods (your pod has no owner, so it's adopted) and deletes one to get back to 3. That might be your hand-made pod.

Q2. You remove the app label from one of the RS's pods (kubectl label pod X app-). What happens to that pod and to the count?

The pod no longer matches, so the RS releases it (it keeps running as an orphan) and creates a new pod to get back to 3. That's a handy trick for pulling a pod out to debug it.

Q3. Fill in: an RS's pods are named ________ + ________; its template labels must ________ its selector.

The RS name · 5 random characters · match (satisfy).

6 Deployments & scaling

The problem

Section 5 left you with a ReplicaSet that heals but can't upgrade. You need something that, when the image changes, brings up pods with the new template, retires the old ones gradually, and keeps the old version on file in case you need it back.

The idea

A Deployment manages ReplicaSets, which manage pods, and you only ever edit the Deployment. Every change to its spec.template (image, env, resources, template labels) creates a new ReplicaSet, a new revision. Changing replicas doesn't: it just resizes the current ReplicaSet.

Deployment  taskflow-api                       # you edit this: replicas, strategy, template
   └── ReplicaSet  taskflow-api-6d8f7c9b5d     # one per template version (revision)
          ├── Pod  taskflow-api-6d8f7c9b5d-2xkqp
          ├── Pod  taskflow-api-6d8f7c9b5d-9hj4w
          └── Pod  taskflow-api-6d8f7c9b5d-tz8mn
Think of it like this

The Deployment is the head of the menu. He owns the recipe card (the template) and tells a shift manager (ReplicaSet) how many stations to run. When the recipe changes, he doesn't rewrite the old manager's rule. He appoints a new manager for the new recipe and moves stations across, keeping old recipe cards in a drawer.

See it: TaskFlow's real Deployment

k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
  labels:
    app: taskflow-api
  annotations:
    kubernetes.io/change-cause: "deploy 1.0.0"   # shown in rollout history (section 7)
spec:
  replicas: 3
  revisionHistoryLimit: 10             # old ReplicaSets kept for rollback (default 10)
  selector:                           # immutable after creation
    matchLabels:
      app: taskflow-api
  strategy:
    type: RollingUpdate               # default; alternative: Recreate
    rollingUpdate:
      maxSurge: 1                     # at most 1 Pod ABOVE replicas during an update
      maxUnavailable: 0               # never go BELOW replicas ready → zero downtime
  minReadySeconds: 5                  # Pod must be Ready 5s before it counts as Available
  progressDeadlineSeconds: 600        # mark rollout failed after 10 min without progress
  template:
    metadata:
      labels:
        app: taskflow-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0
          ports:
            - name: http                    # named port, used by the Service (Session 11)
              containerPort: 3000
          env:
            - name: PORT
              value: "3000"
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          readinessProbe:                   # Pod gets traffic only after /health answers (details: Session 13)
            httpGet: { path: /health, port: http }
            periodSeconds: 5

Exam trap

"Scaling from 3 to 5 creates a new revision." ✗ replicas isn't part of the template, so the same RS just grows. Only template changes create revisions.

"kubectl scale permanently sets the replica count." ✗ It lasts until the next apply of a file with a different replicas, or until an HPA changes it.

Remember

Deployment → ReplicaSet (one per template version) → Pods.
Template change = new RS = new revision · replicas change = same RS.

Mastery check
Q1. Which of these create a new ReplicaSet: (a) replicas 3 → 5, (b) new image tag, (c) a new env var, (d) changing maxSurge, (e) adding a template label?

(b), (c) and (e): they change spec.template. Scaling and strategy changes don't create a revision.

Q2. get deploy shows READY 3/3 UP-TO-DATE 1 AVAILABLE 3. What's going on?

A rollout is in progress. All 3 pods are ready and serving, but only 1 runs the newest template. The other 2 are still on the old ReplicaSet.

Q3. You change the Deployment's selector to app: api and apply. What happens?

The API server rejects it: spec.selector is immutable in apps/v1 ("field is immutable"). You'd have to delete and recreate the Deployment.

7 Rolling updates & rollbacks

The problem

TaskFlow 1.1.0 is ready, and users are on 1.0.0 right now. You want zero failed requests during the switch. And when 1.2.0 turns out to be broken at 3 p.m., you want one command to go back.

The idea

On a template change the Deployment creates a new ReplicaSet, then scales it up while scaling the old one down, a few pods at a time. Two numbers set the pace: maxSurge (pods allowed above replicas) and maxUnavailable (pods allowed missing below it). The old ReplicaSet stays at 0, so rolling back just scales it up again.

 replicas 3 · maxSurge 1 · maxUnavailable 0          ● ready   ○ starting
 step    old RS (1.0.0)   new RS (1.1.0)   pods   ready ≥ 3?
 start   ● ● ●                               3       ✓
 1       ● ● ●            ○                  4       ✓   surge: a 4th pod is allowed
 2       ● ●              ●                  3       ✓   new pod Ready → one old pod goes
 3       ● ●              ● ○                4       ✓
 4       ●                ● ●                3       ✓
 5       ●                ● ● ○              4       ✓
 done                     ● ● ●              3       ✓   old RS kept at 0 → instant rollback
Think of it like this

Switching recipes during dinner service. You may open one extra station (maxSurge 1) and may never be short of a station (maxUnavailable 0). So you open a new-recipe station, wait until it's actually cooking (Ready), close an old one, and repeat. The old recipe card goes in the drawer. If the new dish is a disaster, you pull the old card back out.

See it: roll out 1.1.0

With maxUnavailable 0, the broken pod never replaced a working one. progressDeadlineSeconds made rollout status fail so CI can alert, and undo scaled revision 2's ReplicaSet back up under a new number. Three more verbs: rollout pause → several set image/set resources → rollout resume gives one rollout for all the changes. rollout restart replaces every pod with the same spec (after a ConfigMap change, for example) by stamping a kubectl.kubernetes.io/restartedAt annotation on the template.

RollingUpdate vs Recreate

RollingUpdate (default)Recreate
HowNew pods up gradually, old ones down graduallyKill all old pods, then start new ones

Exam trap

"rollout undo fixes the problem for good." ✗ It changes the cluster, not your YAML. The next kubectl apply of the file still saying 1.2.0 re-deploys the bad image. Fix the file too.

"A rolling update means only one version is ever live." ✗ Old and new pods serve side by side during the rollout. Only Recreate guarantees one version, and the price is downtime.

Remember

Template change → new RS up, old RS down, within maxSurge / maxUnavailable.
status (watch) · history (list) · undo [--to-revision=N] (go back).

Mastery check
Q1. replicas 10, maxSurge 25%, maxUnavailable 25%. What are the most pods at once and the fewest available during a rollout?

maxSurge = ceil(2.5) = 3, so at most 13 pods. maxUnavailable = floor(2.5) = 2, so at least 8 available.

Q2. History shows revisions 1, 2, 3. You run kubectl rollout undo. What does history show now, and which image runs?

1, 3, 4. Revision 2's template is re-used and becomes revision 4, so revision 2's image runs (1.1.0 here).

Q3. Spot the bug: kubectl set image deployment/taskflow-api taskflow-api=shauryav/taskflow-api:1.1.0

The part before = must be the container name, which is api. kubectl answers error: unable to find container named "taskflow-api".

Q4. A migration renames a DB column that 1.0.0 still reads. Which strategy do you pick, and what do you accept?

Recreate, because the two versions must never run together. You accept brief downtime. (Or do the change in two compatible releases and keep RollingUpdate.)

★ Putting it all together

The big idea

A Pod runs the TaskFlow container (plus any sidecar or init container) on one node with one IP, and the kubelet restarts its containers in place. It can't survive its node on its own. Labels let a ReplicaSet count "its" pods and replace any that disappear. A Deployment sits on top: each new template (image 1.1.0) gets a new ReplicaSet, pods shift from old to new within maxSurge/maxUnavailable, and old ReplicaSets stay at 0 so rollout undo is instant. In practice you write one k8s/deployment.yaml and never touch ReplicaSets or pods directly.

Final mastery check — combine everything
Q1. A bare pod, a ReplicaSet's pod and a Deployment's pod each have their container crash once. Then each pod is deleted. Describe what happens in each case, and who acts.

Crash: in all three the kubelet restarts the container in place (restartPolicy Always), and RESTARTS becomes 1. Delete: the bare pod is gone for good. The RS's pod is replaced by the ReplicaSet controller. The Deployment's pod is replaced by its ReplicaSet too, because the Deployment never manages pods directly.

Q2. During a rollout to 1.1.0 (maxSurge 1, maxUnavailable 0), the new pod sits at 0/1 Running forever. What does the rollout do, what do users see, and what are your next two commands?

The readiness probe never passes, so the pod never counts as ready. maxUnavailable 0 means no old pod is removed, so the rollout stalls and users stay on 1.0.0 untouched. After progressDeadlineSeconds, rollout status fails. Next: kubectl describe pod / kubectl logs on the new pod to see why /health fails, then kubectl rollout undo if you can't fix it quickly.

Q3. You add tier: backend to the Deployment's template labels only, and apply. Does that roll out? Does the selector still match?

Yes, it rolls out: template labels are part of the template, so you get a new RS and new pods. The selector (app: taskflow-api) still matches, because a selector only needs its labels to be a subset of the pod's labels.

Q4. After kubectl rollout undo fixed a bad 1.2.0 release, a teammate runs kubectl apply -f k8s/ to "sync everything". What happens, and why?

1.2.0 rolls out again. undo changed only the cluster, and the file in Git still says 1.2.0. Since apply makes the cluster match the file, fix the file (and commit it) as part of every rollback.

Q5. kubectl get pods shows CrashLoopBackOff on all 3 new pods right after a rollout, while the old pods are gone. Which Deployment setting allowed that, and which commands diagnose and recover?

maxUnavailable above 0 (e.g. the 25% default), likely with no readiness probe, so "started" counted as ready and old pods were removed too early. Diagnose with kubectl logs POD --previous and describe. Recover with kubectl rollout undo, then add a readiness probe and set maxUnavailable 0.

Q6. A pod has an init container wait-for-db and a sidecar. It shows Init:0/1. Is the sidecar running? Is the pod in any Service? What phase is it in?

No: regular containers, the sidecar included, start only after all init containers succeed (only a native sidecar in initContainers with restartPolicy: Always would be running). It isn't Ready, so no Service sends it traffic. Its phase is Pending.
