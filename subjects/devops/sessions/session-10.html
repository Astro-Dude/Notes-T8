1 Pods

Explain like I'm 5

A container is a person; a Pod is a small flat. People in the same flat share the address (IP) and the fridge (volumes).

  • A Pod is the smallest thing Kubernetes schedules: one or more containers that always run together on the same node.
  • Containers in a Pod share one network namespace (same IP, talk over localhost) and can share volumes.
  • Pods are disposable: if one dies it is not "repaired" — a controller (ReplicaSet/Deployment) makes a new Pod with a new name and IP.
  • Rule of thumb: one app container per Pod. Add a second container only if it must live and die with the first (sidecar).

One-time setup used on every K8s page (namespaces are covered in Session 15):

$ minikube start
$ kubectl create namespace taskflow
namespace/taskflow created
$ kubectl config set-context --current --namespace=taskflow   # so you can skip -n taskflow
Context "minikube" modified.

A single-container Pod

pod.yaml
apiVersion: v1                       # Pods live in the core API group → just "v1"
kind: Pod
metadata:
  name: taskflow-api                  # unique per namespace, lowercase + digits + '-'
  namespace: taskflow
  labels:                             # tags that selectors match on (§3)
    app: taskflow
    tier: api
spec:
  containers:
    - name: api                       # container name, used with -c
      image: shauryav/taskflow-api:1.0.0
      imagePullPolicy: IfNotPresent   # pull only if the node doesn't have it
      ports:
        - containerPort: 3000           # documentation + lets Services refer to it
      env:
        - name: PORT
          value: "3000"                 # env values are always strings → quote numbers
      resources:
        requests: { cpu: 100m, memory: 128Mi }   # reserved by the scheduler
        limits:   { cpu: 500m, memory: 256Mi }   # hard cap (memory over → OOMKilled)
  restartPolicy: Always               # default; kubelet restarts crashed containers
FieldMeaningGotcha
apiVersion: v1API group/version. Core objects (Pod, Service, ConfigMap) are v1; Deployment/ReplicaSet are apps/v1.Wrong version → no matches for kind "Pod" in version ...
metadata.labelsKey/value tags. Services and controllers find Pods by labels, never by name.Keys/values ≤ 63 chars, no spaces.
spec.containers[]List of containers (at least one). Each needs name + image.It's a list → every item starts with -.
imageregistry/user/repo:tag; no registry = Docker Hub.No tag = :latest, which also flips imagePullPolicy to Always.
imagePullPolicyIfNotPresent (default for pinned tags) · Always · Never.Re-pushed the same tag? Nodes with IfNotPresent keep the old image.
containerPortPort the app listens on. Informational — it does not open or publish anything.Unlike Docker -p, you reach it via a Service (Session 11).
resourcesrequests = guaranteed share used for scheduling; limits = ceiling. 100m = 0.1 CPU.Details + QoS classes in Session 15.
restartPolicyPod-wide: Always / OnFailure / Never (see §2).Deployments only allow Always.

Multi-container Pod (sidecar)

The API writes its log file to a shared emptyDir volume; a sidecar streams it. Both containers also share localhost.

sidecar-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: taskflow-api-logs
  labels:
    app: taskflow-demo                # deliberately NOT app=taskflow (see §4 adoption gotcha)
spec:
  volumes:
    - name: logs
      emptyDir: {}                    # scratch dir, lives as long as the Pod
  containers:
    - name: api                       # main container
      image: shauryav/taskflow-api:1.0.0
      env:
        - name: LOG_FILE              # TaskFlow also writes logs here when set
          value: /var/log/taskflow/app.log
      ports:
        - containerPort: 3000
      volumeMounts:
        - name: logs
          mountPath: /var/log/taskflow
    - name: log-agent                 # sidecar: stands in for fluent-bit / a log shipper
      image: busybox:1.36
      command: ["sh", "-c", "tail -n+1 -F /var/log/taskflow/app.log"]
      volumeMounts:
        - name: logs
          mountPath: /var/log/taskflow
          readOnly: true
$ kubectl apply -f sidecar-pod.yaml
pod/taskflow-api-logs created
$ kubectl get pod taskflow-api-logs
NAME                READY   STATUS    RESTARTS   AGE
taskflow-api-logs   2/2     Running   0          12s          # 2/2 = both containers ready
$ kubectl logs taskflow-api-logs
Defaulted container "api" out of: api, log-agent      # always pass -c with multi-container pods
TaskFlow API listening on port 3000
$ kubectl logs taskflow-api-logs -c log-agent             # the sidecar is reading the shared file
TaskFlow API listening on port 3000
$ kubectl exec taskflow-api-logs -c log-agent -- wget -qO- localhost:3000/health
{"status":"ok"}                                 # busybox reached the api via localhost
Native sidecars (K8s 1.33+, GA)

You can declare a sidecar under initContainers with restartPolicy: Always. It then starts before and stops after the main container — useful for log shippers and proxies.

Common mistakes
  • Putting the API and Postgres in one Pod. You can't scale them separately and a DB restart kills the API. Use two Pods + a Service.
  • Two containers in one Pod both listening on port 3000 → second one fails with EADDRINUSE (shared network namespace).
  • Creating bare Pods for real workloads. Nothing recreates them if the node dies — use a Deployment (§5).
Recap Pod = 1+ containers sharing IP, localhost and volumes, scheduled together. Pods are cattle: replaced, never repaired. Core loop: apply → get -o wide → describe → logs → exec → delete.

2 Pod lifecycle

Explain like I'm 5

The Pod has a big status on its door (phase); each container inside has its own small mood (state).

Pod phases (.status.phase)

PhaseMeaningTypical cause
PendingAccepted by the API server, but not all containers are running yet.Waiting for a node (scheduling), pulling images, running init containers.
RunningBound to a node, all containers created, at least one running (or restarting).Normal state for servers like TaskFlow.
SucceededAll containers exited with code 0 and won't restart.A finished Job (Session 15).
FailedAll containers stopped, at least one with non-zero exit / killed, no restart.restartPolicy: Never + app error.
UnknownControl plane can't get the Pod's state.Node lost contact (kubelet down, network split).

Container states

StateReasons you'll see in STATUSMeaning
WaitingContainerCreating, PodInitializing, ErrImagePull, ImagePullBackOff, CrashLoopBackOff, CreateContainerConfigErrorNot running yet (or waiting between restarts).
RunningRunningProcess is up; describe shows Started: time.
TerminatedCompleted (exit 0), Error (non-zero), OOMKilled (137)Process ended; exit code + reason recorded.
Example: STATUS column ≠ phase 
$ kubectl get pod taskflow-api
NAME           READY   STATUS             RESTARTS      AGE
taskflow-api   0/1     CrashLoopBackOff   4 (30s ago)   3m
$ kubectl get pod taskflow-api -o jsonpath='{.status.phase}'
Running

STATUS shows the most interesting container reason. The phase is still Running because the kubelet keeps restarting it. Terminating is also not a phase.

restartPolicy and back-off

restartPolicyRestarts container when…Used by
Always (default)it exits for any reasonDeployments, ReplicaSets, DaemonSets (only value allowed)
OnFailureit exits non-zeroJobs that should retry
NeverneverJobs, one-off debug Pods
  • Restarts happen in the same Pod on the same node (RESTARTS goes up, name/IP stay).
  • Delay between restarts doubles: 10s, 20s, 40s … capped at 5 min = CrashLoopBackOff. Reset after 10 min of running fine.

Init containers

Run to completion, in order, before app containers start. Classic use: wait for the database.

pod-with-init.yaml
apiVersion: v1
kind: Pod
metadata:
  name: taskflow-api-init
  labels:
    app: taskflow-demo
spec:
  initContainers:                     # all must exit 0 before "containers" start
    - name: wait-for-db
      image: postgres:16-alpine       # only for its pg_isready binary
      command: ["sh", "-c",
        "until pg_isready -h taskflow-db -p 5432; do echo waiting for db; sleep 2; done"]
  containers:
    - name: api
      image: shauryav/taskflow-api:1.0.0
      ports:
        - containerPort: 3000
$ kubectl get pod taskflow-api-init -w
NAME                READY   STATUS            RESTARTS   AGE
taskflow-api-init   0/1     Init:0/1          0          5s     # 0 of 1 init containers done
taskflow-api-init   0/1     PodInitializing   0          41s
taskflow-api-init   1/1     Running           0          43s
$ kubectl logs taskflow-api-init -c wait-for-db
taskflow-db:5432 - no response
waiting for db
taskflow-db:5432 - accepting connections

taskflow-db is a Service name — it resolves once the DB Service exists (Session 11).

process.on('SIGTERM', () => {
  console.log('SIGTERM received, closing server');

Common mistakes
  • CMD npm start (shell form) → sh is PID 1, Node never sees SIGTERM, every delete waits the full 30 s then SIGKILLs. Use exec form CMD ["node","server.js"] (Session 7).

Recap Phases: Pending → Running → Succeeded/Failed (+ Unknown). Container states: Waiting / Running / Terminated with reasons. Init containers gate startup. Termination = SIGTERM → 30 s grace → SIGKILL.

3 Labels & selectors

Explain like I'm 5

Labels are name stickers; a selector is "everyone wearing a red sticker, step forward".

  • A label is a key/value pair on any object: app=taskflow, tier=api, env=dev.
  • A selector is a query over labels. ReplicaSets, Deployments, Services and NetworkPolicies all find their Pods this way — that's the glue of Kubernetes.
  • Annotations are also key/values but are not selectable — for notes like kubernetes.io/change-cause (§6).
$ kubectl apply -f pod.yaml
$ kubectl run taskflow-web --image=nginx:1.27-alpine --labels="app=taskflow,tier=web"

matchLabels vs matchExpressions (in YAML)

selector:
  matchLabels:                 # equality: app == taskflow AND tier == api
    app: taskflow
    tier: api
  matchExpressions:            # set-based; ANDed with matchLabels
    - { key: env,    operator: In,     values: [dev, staging] }
    - { key: track,  operator: NotIn,  values: [canary] }
    - { key: team,   operator: Exists }          # no values for Exists / DoesNotExist
FormOperatorskubectl equivalentSupported by
Equality-based (matchLabels)=, ==, !=-l app=taskflow,tier!=webEverything, incl. Services (plain map only)
Set-based (matchExpressions)In, NotIn, Exists, DoesNotExist-l 'env in (dev,staging)', -l '!env'ReplicaSet, Deployment, Job, DaemonSet, NetworkPolicy — not Service
Key takeaway

Use the same small label set everywhere (app, tier, optionally env/version). The official recommended keys are app.kubernetes.io/name, app.kubernetes.io/component, etc. — Helm charts use them (Session 17).

Recap Labels tag objects; selectors query them (-l on the CLI, matchLabels/matchExpressions in YAML). Controllers and Services own Pods purely through label matches.

4 ReplicaSets

Explain like I'm 5

A ReplicaSet is a teacher counting heads: "I need 3 kids wearing the taskflow sticker". One leaves, she fetches another.

  • A ReplicaSet (RS) keeps exactly replicas Pods matching its selector running, creating Pods from its template.
  • It runs a reconciliation loop: count matching Pods → compare with desired → create or delete. That's self-healing.
replicaset.yaml
apiVersion: apps/v1                  # workload controllers live in the "apps" group
kind: ReplicaSet
metadata:
  name: taskflow-api-rs
spec:
  replicas: 3                         # desired number of Pods
  selector:                           # which Pods this RS counts as "mine"
    matchLabels:
      app: taskflow
      tier: api
  template:                           # Pod blueprint used when it must create one
    metadata:
      labels:                         # MUST satisfy the selector above
        app: taskflow
        tier: api
    spec:
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0
          ports:
            - containerPort: 3000
FieldMeaning
spec.replicasDesired count (default 1).
spec.selectorLabel query defining ownership. Required in apps/v1.
spec.templateA full Pod spec minus apiVersion/kind; its Pods get names <rs-name>-<5 random chars>.
template.metadata.labelsMust match the selector, otherwise the API rejects the object (below).

Example: why you don't create ReplicaSets directly

Nothing changed: an RS only uses the template for new Pods. No rolling update, no history, no rollback. A Deployment adds all of that by managing ReplicaSets for you. Clean up: kubectl delete rs taskflow-api-rs (deletes its Pods too; --cascade=orphan keeps them).

Common mistakes
  • Template labels don't match the selector:
    The ReplicaSet "taskflow-api-rs" is invalid: spec.template.metadata.labels: Invalid value: ...: `selector` does not match template `labels`
  • Adoption: a leftover bare Pod with app=taskflow,tier=api (from §1) is adopted by the RS, so you see it plus only 2 new Pods. Selectors match any Pod with those labels, not just ones the RS created.
Recap RS = selector + replicas + template; it replaces deleted Pods. It can't roll out a new version, so you always use it through a Deployment.

5 Deployments & scaling

Explain like I'm 5

The Deployment is the principal: she tells a teacher (ReplicaSet) how many kids to keep, and swaps in a new teacher when the rules change.

  • A Deployment manages ReplicaSets, which manage Pods. You only ever edit the Deployment.
  • Every change to spec.template (image, env, resources, template labels) creates a new ReplicaSet = a new revision. Changing replicas does not.
k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
  labels:
    app: taskflow
    tier: api
  annotations:
    kubernetes.io/change-cause: "deploy 1.0.0"   # shown in rollout history (§6)
spec:
  replicas: 3
  revisionHistoryLimit: 10             # old ReplicaSets kept for rollback (default 10)
  selector:                           # immutable after creation
    matchLabels:
      app: taskflow
      tier: api
  strategy:
    type: RollingUpdate               # default; alternative: Recreate
    rollingUpdate:
      maxSurge: 1                     # at most 1 Pod ABOVE replicas during an update
      maxUnavailable: 0               # never go BELOW replicas ready → zero downtime
  minReadySeconds: 5                  # Pod must be Ready 5s before it counts as Available
  progressDeadlineSeconds: 600        # mark rollout failed after 10 min without progress
  template:
    metadata:
      labels:
        app: taskflow
        tier: api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0
          ports:
            - name: http                    # named port, used by the Service (Session 11)
              containerPort: 3000
          env:
            - name: PORT
              value: "3000"
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          readinessProbe:                   # Pod gets traffic only after /health answers (details: Session 13)
            httpGet: { path: /health, port: http }
            periodSeconds: 5
FieldWhat it doesWhy it matters
replicasDesired Pod count.Leave it out if an HPA controls scaling (Session 13).
revisionHistoryLimitHow many old (scaled-to-0) ReplicaSets to keep.Each kept RS is a rollback target. 0 = no rollback.
selectorWhich Pods belong to this Deployment.Immutable in apps/v1; changing it = delete + recreate.
strategyHow old Pods are replaced (§6).maxSurge/maxUnavailable default to 25% each.
minReadySecondsExtra wait before a ready Pod is "available".Catches Pods that pass readiness then crash a second later.
progressDeadlineSecondsRollout timeout.After it, rollout status exits non-zero → CI can fail the deploy.
templateThe Pod spec. Any change here = new revision.Same fields as pod.yaml.
readinessProbeHealth check deciding "ready for traffic".Without it, a rolling update treats "container started" as ready.

Common mistake

That's exactly what just happened: kubectl scale to 5, then kubectl apply -f with replicas: 3 → silently back to 3. Make the YAML in Git the source of truth (edit the number, then apply); with an HPA, remove replicas from the YAML entirely.

Recap Deployment → ReplicaSet (one per template version) → Pods. Scale with kubectl scale or by editing replicas + apply; scaling reuses the same RS.

6 Rolling updates & rollbacks

Explain like I'm 5

Changing the team one player at a time so there are always enough on the field — and calling the old players back if the new one trips.

maxSurge and maxUnavailable, with numbers

  • maxSurge: how many Pods may exist above replicas during the update (percent rounds up).
  • maxUnavailable: how many may be missing below replicas (percent rounds down). Both can't be 0.
replicasmaxSurgemaxUnavailableMax Pods at onceMin availableCharacter

425% → 125% → 153Defaults

RollingUpdate vs Recreate

RollingUpdate (default)Recreate
HowNew Pods up gradually, old ones down graduallyKill all old Pods, then start new ones
DowntimeNone (with readiness probes)Yes, between old down and new ready
Two versions live at once?Yes, briefly — app/API/DB schema must be backward compatibleNever
Extra capacityUp to maxSurge PodsNone
Use forStateless web/API services (TaskFlow API)Apps that can't run two versions together, single-writer volumes
YAMLtype: RollingUpdate + rollingUpdate: blockstrategy: { type: Recreate } (no rollingUpdate block)
Common mistakes
  • --record is deprecated — use the kubernetes.io/change-cause annotation (best: set it in the YAML next to the image).
  • kubectl annotate without --overwrite fails when the annotation already exists.
  • rollout undo changes the cluster, not your YAML. Fix the file too, or the next apply re-deploys the bad image.
  • Re-using a tag (:latest) means set image to the "same" value does nothing. Use unique tags (git SHA / semver).
Recap Template change → new RS → rolling replace limited by maxSurge/maxUnavailable. Watch with rollout status, inspect with rollout history, revert with rollout undo [--to-revision=N].

★ Putting it all together

The big idea

A Pod runs the TaskFlow container but can't survive on its own. Labels let a ReplicaSet count "its" Pods and replace any that die. A Deployment sits on top: each new template (e.g. image 1.1.0) gets a new ReplicaSet, and the Deployment shifts Pods from old to new within maxSurge/maxUnavailable, keeping old ReplicaSets so rollout undo is instant. In practice you write one k8s/deployment.yaml and never touch ReplicaSets or Pods directly.

Quick self-check

replicas: 10, maxSurge: 25%, maxUnavailable: 25%. What is the max Pod count and the min available Pods during a rollout?

maxSurge = ceil(2.5) = 3 → at most 13 Pods. maxUnavailable = floor(2.5) = 2 → at least 8 available.

Which of these create a new ReplicaSet: (a) replicas 3 → 5, (b) new image tag, (c) new env var, (d) changing maxSurge?

(b) and (c) — they change spec.template. Scaling and strategy changes don't create a revision.

A container crashes and RESTARTS goes 0 → 1, but the Pod name is the same. Who restarted it? How is that different from deleting the Pod?

The kubelet restarted the container in place (restartPolicy Always). Deleting the Pod makes the ReplicaSet create a new Pod with a new name and IP.

A Pod shows Init:0/1 for 3 minutes. What does it mean and what do you run?

The first init container hasn't finished, so app containers haven't started. Run kubectl logs POD -c wait-for-db (and describe) — usually the DB Service isn't up yet.

History shows revisions 1, 2, 3. You run kubectl rollout undo. What does history show now?

1, 3, 4 — revision 2's template is re-used and becomes revision 4.

What is the Pod phase of a Pod whose STATUS is CrashLoopBackOff?

Usually Running. CrashLoopBackOff is a container Waiting reason, not a phase.

When would you pick Recreate over RollingUpdate?

When two versions must never run together (incompatible DB schema change) or the Pod uses a single-writer volume. You accept brief downtime.
