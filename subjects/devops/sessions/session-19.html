1 DevSecOps & shift-left

The problem: green pipeline, four disasters

TaskFlow 1.0 ships through Session 18's ci.yml: lint ✓, tests ✓, build ✓, publish ✓. Then:

Day 3   GET /tasks?status=x' OR '1'='1 returns every user's tasks          ← a bug in YOUR code
Day 5   advisory: body-parser 1.20.2 has a DoS bug (CVE-2024-45590)          ← a bug in a DEPENDENCY
Day 8   AWS billing alert: crypto-miners using the key in scripts/deploy.sh   ← a SECRET in git history
Day 12  security report: cross-spawn CVE-2024-21538 inside the image         ← a bug in the BASE IMAGE

Every test passed, because tests check that features work, not that they're safe. And deploys are still you typing kubectl on your laptop with :latest. This page fixes all five, one pipeline job at a time.

The idea

DevSecOps makes security checks automated pipeline stages that the whole team owns, instead of one security review at the end. Shift-left means running each check at the earliest stage that can see the problem: a SQL injection caught in a PR is a 2-line fix; found in production it's an incident, a hotfix and maybe a data leak.

 Plan ─▶ Code ─▶ Commit / PR ───────▶ Build ─────▶ Registry ───▶ Deploy ───▶ Run
          │          │                   │             │             │           │
       IDE lint   gitleaks (secrets)   docker build  Trivy         security    DAST (ZAP)
       pre-commit CodeQL/Semgrep (SAST) (buildx)     (image CVEs)  gates +     runtime
       hooks      npm audit (SCA)                    re-scans      approval    monitoring
                  Dependabot PRs
 ◀────────────── shift LEFT: found earlier = cheaper and faster to fix ──────────────
Think of it like this

Session 18's kitchen again: taste as you cook, not at the customer's table. SAST proofreads your own recipe for dangerous steps. SCA checks the supplier's recall list for every ingredient you bought. Secret scanning makes sure the safe's code isn't written on the menu. Image scanning opens the sealed meal box, including what the box maker packed. A gate is the inspector who can stop service.

See it: one command per disaster

Each scanner is a CLI that exits non-zero when it finds something. You'll meet each one properly in sections 5–8:

$ semgrep scan --config p/javascript --error                 # disaster 1: SQL built from req.query → exit 1
$ npm audit --audit-level=high --omit=dev                    # disaster 2: body-parser <1.20.3      → exit 1
$ gitleaks git --redact                                      # disaster 3: aws-access-token          → exit 1
$ trivy image --severity HIGH,CRITICAL --exit-code 1 shauryav/taskflow-api:1.0   # disaster 4 → exit 1

Put each in a pipeline step and a finding fails the job. That is all a security gate is (section 9).

What it does not do: fix anything, or overlap. npm audit can't see the SQL injection, and Semgrep can't see the vulnerable package, so a real pipeline stacks several scanners.

Exam trap

"All tests pass, so the code is secure." ✗ Tests check behaviour you thought of. None of the four disasters broke a test.

"DevSecOps means the security team signs off before each release." ✗ That's the old end-of-line model. DevSecOps automates the checks in every pipeline run and makes developers own the fixes.

Remember

SAST = your code · SCA = other people's code you depend on · secrets = credentials in git · image scan = everything inside the final image.
Shift left: found earlier = cheaper to fix.

Mastery check
Q1. Which scanner catches each: (a) res.send(eval(req.body.expr)) in server.js, (b) lodash 4.17.20 in the lockfile, (c) a committed .env with the DB password, (d) an OpenSSL CVE in the Alpine base?

(a) SAST: user input reaches a dangerous sink in your code. (b) SCA: a known-vulnerable dependency version. (c) Secret scanning. (d) Image scanning: it's an OS package, invisible to the lockfile.

Q2. Your professor says: "SAST and DAST are the same thing; DAST is just the newer name." Agree?

No. SAST reads the source without running it (white-box, early, in the PR). DAST attacks a running app from outside (black-box, late, on staging). They find different bugs.

Q3. A team runs every scanner once, the night before each quarterly release. What goes wrong?

Findings arrive months after the code was written, in one huge batch, and block the release. Shift-left runs them on every PR, so each author fixes a few findings while the code is fresh.

2 Docker build in the pipeline

The problem

Session 18 built the image by hand: docker build, docker save | gzip into a ~55 MB artifact, docker load in the next job, then push with a Docker Hub token. Every run starts on a fresh VM, so every layer is rebuilt:

#9 [build 4/7] RUN --mount=type=cache,target=/root/.npm npm ci
#9 DONE 38.6s                        # every run, even when package-lock.json didn't change

You also compute the tag by hand, and nothing in the image records which commit it came from.

The idea

Docker's four official actions do it properly in one job. setup-buildx starts a BuildKit builder, login authenticates to the registry, metadata computes tags and labels from the git event, and build-push builds and pushes in one step, keeping the layer cache in GitHub's Actions cache between runs.

 checkout ─▶ setup-buildx ─▶ login ghcr.io ─▶ metadata ─▶ build-push ──push──▶ ghcr.io/shauryav/taskflow-api
              (BuildKit)     (GITHUB_TOKEN)   tags+labels     │   ▲                 :<full sha>  :main
                                                              ▼   │ cache-from / cache-to: type=gha
                                                       GitHub Actions cache (image layers)
Think of it like this

A central bakery instead of your home oven: the same settings every time, every loaf stamped with its batch number (labels), yesterday's prepared dough reused (cache), and the loaf goes straight onto a labelled shelf (the registry).

See it: the one-line version

$ docker buildx build --platform linux/amd64 -t ghcr.io/shauryav/taskflow-api:3f9c2e1 --push .
TokenMeaning
docker buildx buildBuild with BuildKit (the builder behind docker build, with more options)
--platform linux/amd64Target CPU. Your M-series Mac would otherwise build arm64, which x86 servers can't run
-t ghcr.io/…:3f9c2e1The full image name: registry / owner / repository : tag (section 3)
--push / .Push straight to the registry instead of loading locally / the build context

What it does not do: log in (you need docker login ghcr.io first), choose tags for you, or keep a cache between CI runs. The actions add exactly those three things.

Build it up: the build-push job

The four actions, in order: docker/setup-buildx-action@v3 (BuildKit builder, needed for the Actions cache and multi-platform builds), docker/login-action@v3 (docker login to Docker Hub / GHCR / ECR / ACR), docker/metadata-action@v5 (tags + OCI labels from the git event) and docker/build-push-action@v6 (docker buildx build, optionally pushing).

.github/workflows/ci-cd.yml — the build-push job (full file in section 10)
  build-push:
    name: Build & push image
    needs: [sast, sca, secret-scan]          # only after every scan passed (sections 5–7)
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write                        # lets GITHUB_TOKEN push to ghcr.io
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Log in to GHCR
        if: github.event_name != 'pull_request'   # PRs build but never push
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}    # automatic token, no PAT needed
      - name: Compute tags & labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}           # ghcr.io/shauryav/taskflow-api
          tags: |
            type=sha,prefix=,format=long     # :3f9c2e1d…  (full commit SHA = github.sha)
            type=ref,event=branch            # :main
            type=ref,event=pr                # :pr-42
            type=semver,pattern={{version}}  # :1.4.0   (on git tag v1.4.0)
            type=semver,pattern={{major}}.{{minor}}   # :1.4
      - name: Build (push on main / tags)
        uses: docker/build-push-action@v6
        with:
          context: .                         # uses ./Dockerfile (multi-stage, Session 7)
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha               # reuse layers from earlier runs
          cache-to: type=gha,mode=max        # mode=max also caches build-stage layers
LineWhy it's there
permissions: packages: writeThe default GITHUB_TOKEN can't push packages. Without it: denied: permission_denied: write_package (HTTP 403).
if: github.event_name != 'pull_request'Fork PRs get no secrets, and you don't want images of unmerged code in the registry.
id: meta + steps.meta.outputs.tagsThe id lets the next step read this step's outputs (a newline-separated tag list).
type=sha,prefix=,format=longThe default is sha-3f9c2e1. Empty prefix + long format gives exactly ${{ github.sha }}, which the deploy job uses.
push: ${{ … != 'pull_request' }}An expression that is false on PRs: the image is built (proving the Dockerfile works) but not pushed.
cache-from/to: type=ghaBuildKit layer cache in the GitHub Actions cache. Unchanged npm ci layer → the build drops from ~90 s to ~15 s.

Per event: a push to main gets :<sha> + :main; the git tag v1.4.0 gets :<sha>, :1.4.0, :1.4 and :latest (metadata-action adds latest on semver tag pushes by default); PR #42 computes :pr-42 but pushes nothing. Section 10 has the full event table.

Exam trap

"PRs skip the image build." ✗ They build it, which proves the Dockerfile still works; they just don't push.

"metadata-action builds the image." ✗ It only computes names and labels. build-push-action builds.

Remember

buildx + login + metadata + build-push = the standard image job.
PRs build · main and tags push · cache with type=gha.

Mastery check
Q1. Predict: you push the git tag v2.0.1. Which tags are pushed? Is there a :2?

:<full sha>, :2.0.1, :2.0 and :latest. No :2: there's no {{major}} pattern. No :main either, because the event is a tag, not a branch.

Q2. Someone deletes id: meta. What happens on the next push to main?

steps.meta.outputs.tags is now empty, so build-push has nothing to push to and buildx fails with ERROR: tag is needed when pushing to registry.

Q3. The second run changes only server.js. Which Dockerfile steps are slow, and why?

npm ci shows CACHED: its inputs (the package files) didn't change and the layer came back from the type=gha cache. COPY . . and every step after it (npm test, npm prune) re-run, because the copied code changed.

3 Container registry & tags

The problem

CI pushed the image. The cluster tries to pull it:

$ kubectl -n taskflow get pods
NAME                            READY   STATUS             RESTARTS   AGE
taskflow-api-7c9d8f6b5d-x2k4q   0/1     ImagePullBackOff   0          2m
$ kubectl -n taskflow describe pod taskflow-api-7c9d8f6b5d-x2k4q | grep Failed
  Warning  Failed  12s  kubelet  Failed to pull image "ghcr.io/shauryav/taskflow-api:3f9c2e1d…": … failed to fetch anonymous token: unexpected status … 401 Unauthorized

And a second, quieter problem: production used to run :latest, and nobody could say which commit that was.

The idea

A container registry stores images as repository:tag and serves them by content digest; the cluster pulls from it, so CI pushes to it. GHCR (GitHub Container Registry) is built into GitHub: the workflow pushes with its own GITHUB_TOKEN plus packages: write. Tag every deployable image with something that never moves: the commit SHA.

 ghcr.io / shauryav / taskflow-api : 3f9c2e1d8a7b…   ← what Kubernetes deploys (never moves)
 └registry┘ └owner─┘  └repository─┘ : main             ← moves on every push to main
                                     : 1.4.0 / 1.4      ← release names for humans (1.4 moves)
                                     @sha256:9b1c…      ← digest: the content itself
Think of it like this

Same as Session 6: a tag is like a git branch name (movable), a digest like a commit SHA (fixed). A SHA tag is a shelf label you promise never to move: the batch number, not "today's special".

See it: which commit is in this image?

$ echo "$CR_PAT" | docker login ghcr.io -u shauryav --password-stdin   # classic PAT with read:packages
Login Succeeded
$ docker pull ghcr.io/shauryav/taskflow-api:main
$ docker inspect --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}' ghcr.io/shauryav/taskflow-api:main
3f9c2e1d8a7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d

The label metadata-action wrote (section 2) ties the image to its commit. --password-stdin keeps the token out of shell history.

What it does not do: make the image public. New GHCR packages are private, which explains the 401: the cluster pulled anonymously. Either make the package public (package settings) or give the cluster a pull secret:

$ kubectl -n taskflow create secret docker-registry ghcr-pull \
    --docker-server=ghcr.io --docker-username=shauryav --docker-password="$CR_PAT"
secret/ghcr-pull created                      # then list it under the pod spec's imagePullSecrets (Session 12)

Common mistakes
  • Uppercase in the image name → invalid reference format: repository name must be lowercase. github.repository_owner can be ShauryaV, so hard-code the lowercase name.
  • Image built on an M-series Mac fails on EC2/x86 nodes with exec format error: build in CI, or locally with docker buildx build --platform linux/amd64.
Exam trap

"Pushing to GHCR from CI needs a personal access token stored as a secret." ✗ The workflow's GITHUB_TOKEN with packages: write is enough. A PAT is only for you or the cluster pulling from outside.

"CI pushed a new :main, so Kubernetes rolls it out." ✗ The pod spec still says :main; nothing in it changed, so no rollout happens.

Remember

Deploy the SHA tag, never latest.
GHCR = GITHUB_TOKEN + packages: write; new packages are private.

Mastery check
Q1. The pipeline pushed fine, but pods show ImagePullBackOff with 401 Unauthorized from ghcr.io. Give two fixes.

The package is private and the node pulls anonymously. Make the GHCR package public, or create a docker-registry secret with a read:packages token and reference it in imagePullSecrets.

Q2. Your professor writes image: ghcr.io/shauryav/taskflow-api:latest in the Deployment, "because CI always pushes the newest". Give three problems.

You can't tell which commit is running; re-applying the same tag triggers no rollout; nodes may have cached different "latest" images; and there's no previous tag to roll back to. Deploy the SHA tag instead.

Q3. You built the image on your M-series Mac and pushed it by hand; the EC2 node logs exec format error. Why doesn't the CI-built image have this problem?

The Mac builds linux/arm64; EC2 x86 nodes need linux/amd64. The GitHub runner is amd64, so CI builds the right architecture (or pass --platform linux/amd64 locally).

4 Kubernetes deployment from CI

The problem

You paste your laptop's minikube kubeconfig into a secret and run Helm from a GitHub-hosted runner:

Run helm upgrade --install taskflow ./charts/taskflow …
Error: Kubernetes cluster unreachable: Get "https://192.168.49.2:8443/version": dial tcp 192.168.49.2:8443: i/o timeout

That's Session 18's runner puzzle. 192.168.49.2 is a private address on your laptop, unreachable from GitHub's cloud. Worse, that kubeconfig is cluster-admin: anyone who can edit the workflow could own the cluster.

The idea

A deploy job needs four things: a runner that can reach the API server, a narrowly scoped credential, one command that updates, waits and rolls back on failure, and a human approval for production.

 image-scan ✓ ─▶ deploy   environment: production   ⏸ waits until shauryav approves
                   │  secret KUBECONFIG_B64 → ServiceAccount allowed only in namespace taskflow
                   ▼
                 helm upgrade --install taskflow ./charts/taskflow --set image.tag=<sha> --atomic --wait
                   ├─ new pods Ready within 5 min ─▶ release deployed ✓ ─▶ rollout status ✓
                   └─ not Ready in time ───────────▶ rolled back to the previous revision, job ✗
Think of it like this

The delivery van's key opens only TaskFlow's room (a scoped ServiceAccount), the head chef signs before the van leaves (environment approval), and if the customer refuses the new dish, the old one goes back on the table (--atomic).

ApproachCommand in CIProsCons
kubectlkubectl set image + rollout statusSimple, no chart neededOnly changes the image; config drifts from Git
Helm (used here)helm upgrade --install … --set image.tag=SHA --atomicVersioned releases, auto-rollback, one command for all manifestsNeeds a chart (Session 17)
GitOps (Session 22)CI commits the new tag to Git; Argo CD pulls itCluster credentials never leave the clusterMore moving parts

See it: the smallest deploy

$ kubectl -n taskflow set image deployment/taskflow-api api=ghcr.io/shauryav/taskflow-api:${GITHUB_SHA}
deployment.apps/taskflow-api image updated
$ kubectl -n taskflow rollout status deployment/taskflow-api --timeout=120s
Waiting for deployment "taskflow-api" rollout to finish: 1 out of 3 new replicas have been updated...
deployment "taskflow-api" successfully rolled out

set image deployment/taskflow-api api=… changes the image of the container named api in the Session 10 Deployment, which starts a rolling update. rollout status waits for it and exits non-zero if it fails or times out, so a CI step goes red.

What it does not do: roll back, or change anything except the image. Config in Git (env vars, replicas, the chart) drifts from what's running. Helm fixes both.

Build it up: the Helm deploy job

How the runner gets cluster access, simplest first:

  • kubeconfig in an environment secret (base64) for a ServiceAccount bound to a Role in namespace taskflow (Session 16), never your cluster-admin config.
  • Cloud OIDC: GitHub issues a short-lived token that AWS/GCP/Azure trusts, so no long-lived secret (snippet below).
  • Self-hosted runner that can reach the cluster. For the minikube project: a runner on your laptop, a cloud cluster, or Argo CD pulling (Session 22).
.github/workflows/ci-cd.yml — the deploy job (full file in section 10)
  deploy:
    name: Deploy to Kubernetes
    needs: image-scan                        # never deploy an unscanned image
    if: github.ref == 'refs/heads/main'      # main only — not PRs, not tags
    runs-on: ubuntu-latest                   # kubectl is pre-installed on GitHub runners
    environment: production                  # pauses for required reviewers; unlocks env secrets
    concurrency:
      group: deploy-production               # one deploy at a time…
      cancel-in-progress: false              # …and never kill a deploy halfway
    steps:
      - uses: actions/checkout@v4            # we need ./charts/taskflow
      - uses: azure/setup-helm@v4
        with:
          version: v3.22.0                   # pin Helm 3 (Helm 4 renamed --atomic)
      - name: Write kubeconfig
        env:
          KUBECONFIG_B64: ${{ secrets.KUBECONFIG_B64 }}   # secret → env var, not inline in the script
        run: |
          mkdir -p ~/.kube
          echo "$KUBECONFIG_B64" | base64 -d > ~/.kube/config
          chmod 600 ~/.kube/config
      - name: Helm upgrade
        run: |
          helm upgrade --install taskflow ./charts/taskflow \
            --namespace taskflow --create-namespace \
            -f charts/taskflow/values-prod.yaml \
            --set image.repository=${{ env.IMAGE }} \
            --set image.tag=${{ github.sha }} \
            --atomic --wait --timeout 5m
      - name: Verify rollout
        run: kubectl -n taskflow rollout status deployment/taskflow-api --timeout=120s
LineMeaning
needs / if / concurrencyOnly after the image scan passes, only for pushes to main, one deploy at a time: a second one queues instead of cancelling the first.
environment: productionLinks the job to the production environment: required reviewers, wait timer, "only main may deploy", and secrets that exist only there.
azure/setup-helm@v4 + version: v3.22.0Install a pinned Helm 3, so a Helm 4 release can't change flag names under you.
env: KUBECONFIG_B64: ${{ secrets… }}Passing the secret via env keeps it out of the generated script text; GitHub masks it as ***. base64 -d restores the file, chmod 600 makes it private.
helm upgrade --install … --set image.tag=${{ github.sha }}Install the first time, upgrade after: release taskflow from charts/taskflow (Session 17) with the prod values, deploying exactly the image this run built and scanned (the full-SHA tag from section 2).
--atomic --wait --timeout 5mWait until pods are Ready; if not within 5 min, roll back to the previous revision and fail the job.
rollout statusA second check that the Deployment really finished. The chart names it taskflow-api via fullnameOverride (Session 17).

Exam trap

"If the deploy fails, users get an outage until someone fixes it." ✗ The rolling update keeps old pods serving until new ones are Ready, and --atomic rolls the release back.

"environment: production is just a label on the job." ✗ It pauses for reviewers, restricts branches, and is the only way the job sees the environment's secrets.

Remember

Deploy = scoped credential → helm upgrade --install --set image.tag=SHA --atomic --wait → rollout status, behind environment: production.

Mastery check
Q1. The new pods crash because an env var is missing. Predict what the deploy job shows and what serves users afterwards.

Helm waits up to 5 minutes for Ready pods, then --atomic rolls back to the previous revision and the job goes red. The old pods never stopped serving, so users see the previous version throughout.

Q2. Two merges land a minute apart. What does concurrency: { group: deploy-production, cancel-in-progress: false } do to the second deploy?

It waits until the first finishes, then runs (after its own approval). It never cancels a deploy halfway, which could leave a release mid-upgrade.

Q3. Spot the risk: run: echo "${{ secrets.KUBECONFIG_B64 }}" | base64 -d > ~/.kube/config.

The secret is pasted into the script text before bash runs, so it sits in the generated script on disk and invites injection mistakes. Map it to env: and use "$KUBECONFIG_B64", as the job does.

5 SAST: scan your own code

The problem: disaster 1

Mastery check
Q1. Why does gitleaks in CI need fetch-depth: 0?

actions/checkout fetches only the latest commit by default. A secret added and "deleted" in older commits (like 8f2c1d4) would be missed; depth 0 fetches the full history.

Q2. A developer commits with git commit --no-verify, skipping the hook. What still stops the key?

Q3. An AWS key was pushed to a public repo an hour ago. What's step 1, and why not "rewrite history" first?

Deactivate/rotate the key in IAM now and check CloudTrail. Bots may already have it; rewriting history doesn't reach existing clones, forks or caches, so the key stays usable until it's revoked.

A tag can be moved to malicious code, as happened in March 2026, and the job runs it with access to your secrets. Pin to the full commit SHA with a version comment and let Dependabot bump it.

9 Security gates

The problem

Every scanner is in the pipeline now. Two ways a disaster still ships:

run: npm audit --audit-level=high || true          ← someone silenced a noisy scan: always exit 0, always green
"Merge without waiting for requirements to be met" ← or a red PR is merged anyway / pushed straight to main

The idea

A security gate is a check that can stop the pipeline. A scan that only prints a report is not a gate. The mechanism is a chain, and it needs every link:

 tool exits 1 ─▶ step ✗ ─▶ job ✗ ─▶ jobs that need it: skipped ─▶ PR check ✗ ─▶ branch protection: merge blocked
                                                                  push to main: deploy never starts
 humans:  environment: production ─▶ ⏸ required reviewer must approve the deploy
Think of it like this

A turnstile at the kitchen door: no green ticket from every inspector, no entry to the dining room. || true is propping the turnstile open.

Common mistakes

Required check not listed in branch protection: GitHub only offers checks that ran in the last 7 days, and the name must match the job's name: exactly (matrix jobs look like Unit tests (20)).
Gate in report-only mode: Trivy defaults to exit-code 0; npm audit without --audit-level fails on any low finding, which is so noisy that people add || true and the gate is gone.

Exam trap

"continue-on-error: true on the scan step still blocks, because the log shows the error." ✗ The job counts as successful, so everything that needs it runs. Same effect as || true.

"Branch protection alone protects production." ✗ It guards merges. The scan jobs and needs: guard the deploy, and the environment reviewer guards the final step.

Remember

A scan is a gate only if it exits non-zero AND something depends on it.
Machines: exit codes + needs: · Merges: required checks · Humans: environment reviewers.

Mastery check
Q1. Spot the bug in a job: run: trivy image --severity HIGH,CRITICAL "$IMAGE:$GITHUB_SHA". The report shows 2 CRITICAL, and the deploy goes ahead.

No --exit-code 1: Trivy exits 0 by default, so the step and job pass and deploy runs. The report is not a gate until the exit code is.

Q2. You want to require "Image scan (Trivy)" in branch protection, but it isn't in the list of checks. Two likely reasons?

It hasn't run in the last 7 days (it only runs on pushes to main and tags, never on PRs), or the name doesn't match the job's name: exactly. Requiring it wouldn't help much anyway: on PRs the job is skipped by its if:, and GitHub reports a skipped job as success.

Q3. A release is blocked by Trivy on a CVE with no real exposure. What's the right way through the gate, and what's the wrong one?

Right: add the CVE to .trivyignore with a reason, an owner and an exp: date, reviewed in a PR. Wrong: exit-code: "0", || true or continue-on-error, which silently remove the gate for every future CVE.

10 The complete pipeline: ci-cd.yml

The problem

You've built six jobs in sections 2–8, plus Session 18's test job. Wired into one file, they must run fast checks first, scans in parallel, build only when every scan passes, and deploy only main, after a human approves.

                ┌─▶ sast         (CodeQL)    ─┐
 test ──────────┼─▶ sca          (npm audit) ─┼─▶ build-push ──▶ image-scan ──▶ deploy
 (lint + unit)  └─▶ secret-scan  (gitleaks)  ─┘   (GHCR)          (Trivy)        (Helm, env: production,
                                                  PR: build only   main/tags      main only, approval)
 any ✗  ⇒  every job to its right is skipped  ⇒  nothing reaches the cluster

This file replaces Session 18's ci.yml: the same test job, plus scans, image build and deploy. (Splitting it into ci.yml for PR checks and cd.yml for build + deploy on main works the same way.)

.github/workflows/ci-cd.yml
name: CI/CD

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]                    # release tags like v1.4.0
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read                        # least privilege; jobs add what they need

concurrency:
  group: ci-cd-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}   # cancel stale PR runs only

env:
  IMAGE: ghcr.io/shauryav/taskflow-api  # lowercase!
  NODE_VERSION: "20"

jobs:
  # ---------- 1. fast feedback ----------
  test:
    name: Unit tests
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test

  # ---------- 2. security scans (run in parallel) ----------
  sast:
    name: SAST (CodeQL)
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
      actions: read
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v4
        with:
          languages: javascript-typescript
          build-mode: none
          queries: security-extended
      - uses: github/codeql-action/analyze@v4
        with:
          category: "/language:javascript-typescript"

  sca:
    name: SCA (npm audit)
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm audit --audit-level=high --omit=dev   # reads package-lock.json, no install needed

  secret-scan:
    name: Secret scan (gitleaks)
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  # ---------- 3. build & push ----------
  build-push:
    name: Build & push image
    needs: [sast, sca, secret-scan]
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Log in to GHCR
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Compute tags & labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,prefix=,format=long
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
      - name: Build (push on main / tags)
        uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ---------- 4. scan the pushed image ----------
  image-scan:
    name: Image scan (Trivy)
    needs: build-push
    if: github.event_name != 'pull_request'   # PR images were not pushed
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: read                    # pull the (private) image from GHCR
    steps:
      - uses: actions/checkout@v4       # for .trivyignore
      - uses: docker/login-action@v3    # Trivy reuses Docker's registry credentials
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: aquasecurity/trivy-action@v0.36.0   # pin to a commit SHA in real projects (section 8)
        with:
          image-ref: ${{ env.IMAGE }}:${{ github.sha }}
          format: table
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: "1"
          trivyignores: .trivyignore

  # ---------- 5. deploy ----------
  deploy:
    name: Deploy to Kubernetes
    needs: image-scan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    concurrency:
      group: deploy-production
      cancel-in-progress: false
    steps:
      - uses: actions/checkout@v4
      - uses: azure/setup-helm@v4
        with:
          version: v3.22.0
      - name: Write kubeconfig
        env:
          KUBECONFIG_B64: ${{ secrets.KUBECONFIG_B64 }}
        run: |
          mkdir -p ~/.kube
          echo "$KUBECONFIG_B64" | base64 -d > ~/.kube/config
          chmod 600 ~/.kube/config
      - name: Helm upgrade
        run: |
          helm upgrade --install taskflow ./charts/taskflow \
            --namespace taskflow --create-namespace \
            -f charts/taskflow/values-prod.yaml \
            --set image.repository=${{ env.IMAGE }} \
            --set image.tag=${{ github.sha }} \
            --atomic --wait --timeout 5m
      - name: Verify rollout
        run: kubectl -n taskflow rollout status deployment/taskflow-api --timeout=120s

Mastery check
Q1. Predict: on a push to main, secret-scan fails. Which jobs run, and what's in GHCR afterwards?

test ✓, then sast, sca and secret-scan all run in parallel (secret-scan ✗). build-push, image-scan and deploy are skipped. Nothing new is pushed to GHCR.

Q2. Someone replaces the sast job's permissions: block with just packages: write, "to be safe". What breaks?

Every unlisted permission becomes none: checkout loses contents: read (fatal on a private repo), and CodeQL can't upload results without security-events: write. Meanwhile the job gains a write permission it never needed.

Q3. You push the tag v1.4.0. Does it reach production? Why?

No. Tests, scans, build-push (tags :sha, :1.4.0, :1.4, :latest) and image-scan run, but deploy has if: github.ref == 'refs/heads/main' and the ref is refs/tags/v1.4.0.

★ Putting it all together

The big idea

Every TaskFlow commit goes through one pipeline: tests, then parallel scans of the code (CodeQL), its dependencies (npm audit + Dependabot) and its history (gitleaks). Only then is an image built and pushed to GHCR under the commit SHA, scanned whole by Trivy, and deployed with Helm after a human approves. Each scanner is a gate because it exits non-zero; needs: and branch protection make a failed gate stop everything after it.

Final mastery check — combine everything
Q1. Walk a push to main through ci-cd.yml: what runs in parallel, what is pushed where, what's scanned, what waits for a human, and which tag reaches the cluster?

test runs first; then sast, sca and secret-scan in parallel. When all pass, build-push builds with the type=gha cache and pushes ghcr.io/shauryav/taskflow-api:<full sha> and :main. image-scan pulls the SHA tag and runs Trivy with --exit-code 1. deploy pauses for approval in production, then helm upgrade --set image.tag=<sha> --atomic rolls out that exact image.

Q2. Dependabot's PR "bump express" is all green. After merging, the push run goes red at image-scan. How can the PR be green but main red?

image-scan never runs on PRs (PR images aren't pushed), so the PR only proved tests, SAST, SCA and secrets. On main, Trivy scanned the whole image and found something npm audit can't see, such as an OS or npm-internal package in the base image, or a CVE published since. Fix the base (--pull or a newer tag) or record an accepted risk in .trivyignore.

Q3. Your professor says: "We run Trivy on the image, so npm audit is redundant." Agree?

Partly true, mostly no. Trivy does read the image's package.json files, but here it runs only on main, after the image is built and pushed. npm audit runs on every PR, minutes after the change, before anything is built: that's shift-left. Different stages, different costs.

Q4. The deploy job fails because the new pods crash (a Secret key is missing). What runs in the cluster, what does the run show, and how do you redeploy the last good version without new code?

--atomic rolled back, so the previous revision is still serving and the deploy job is red. Redeploy the last good build with helm rollback taskflow <rev> -n taskflow, or re-run the deploy with the previous SHA as image.tag. SHA tags make "the last good version" unambiguous.

Q5. Suppose deploy used --set image.tag=main instead of ${{ github.sha }}. Name two things that break.

The scanned image and the deployed image may differ: another merge can move :main between image-scan and deploy, so an unscanned image could ship. And Helm sees the same tag string, so pods may not roll at all; rollback targets become ambiguous too.

Q6. List every credential the pipeline uses and the narrowest scope each needs.

GITHUB_TOKEN: contents: read everywhere; plus security-events: write + actions: read for sast, pull-requests: read for secret-scan, packages: write for build-push, packages: read for image-scan. KUBECONFIG_B64: an environment secret for a ServiceAccount limited to namespace taskflow (or OIDC with id-token: write instead). The cluster's GHCR pull secret: a token with only read:packages.
