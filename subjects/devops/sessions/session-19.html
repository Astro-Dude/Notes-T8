1 DevSecOps & shift-left

Explain like I'm 5

Instead of one security guard checking the finished house, a small inspector checks every brick as it's laid. Fixing a bad brick is cheap; fixing a finished wall is not.

  • DevSecOps = security built into every stage of the DevOps loop, automated in the pipeline, owned by the whole team (not a separate team at the end).
  • Shift-left = run checks as early (left) as possible. A SQL injection caught in a PR costs a 2-line fix; the same bug found in production costs an incident, a hotfix and maybe a data leak.
  • Each scanner answers a different question, so a real pipeline stacks several of them.

Key takeaway

SAST = your code, SCA = other people's code you depend on, secret scanning = credentials, image scanning = everything inside the final image (OS + runtime + node_modules).

Recap DevSecOps automates security checks at every stage; shift-left moves them as early as possible. Different scanners catch different classes of problem.

2 Docker build in the pipeline & container registry

Explain like I'm 5

The factory (CI) bakes every cake the same way and puts it on a labelled shelf (the registry). Nobody bakes production cakes in their own kitchen.

  • Why build in CI, not on your laptop: clean, repeatable environment; every image traces to a commit; nobody needs registry passwords locally; always linux/amd64 (your M-series Mac builds arm64).
  • A container registry stores and serves images. The cluster pulls from it, so CI pushes to it.
ActionJob
docker/setup-buildx-action@v3Starts a BuildKit builder (needed for the GitHub Actions cache and multi-platform builds).
docker/login-action@v3Runs docker login against Docker Hub / GHCR / ECR / ACR.
docker/metadata-action@v5Computes image tags + OCI labels from the git event (branch, tag, SHA, PR).
docker/build-push-action@v6Runs docker buildx build and optionally pushes.
.github/workflows/ci-cd.yml — the build-push job (full file in §7)
  build-push:
    name: Build & push image
    needs: [sast, sca, secret-scan]          # only after every scan passed
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write                        # lets GITHUB_TOKEN push to ghcr.io
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Log in to GHCR
        if: github.event_name != 'pull_request'   # PRs build but never push
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}    # automatic token, no PAT needed
      - name: Compute tags & labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}           # ghcr.io/shauryav/taskflow-api
          tags: |
            type=sha,prefix=,format=long     # :3f9c2e1d…  (full commit SHA = github.sha)
            type=ref,event=branch            # :main
            type=ref,event=pr                # :pr-42
            type=semver,pattern={{version}}  # :1.4.0   (on git tag v1.4.0)
            type=semver,pattern={{major}}.{{minor}}   # :1.4
      - name: Build (push on main / tags)
        uses: docker/build-push-action@v6
        with:
          context: .                         # uses ./Dockerfile (multi-stage, Session 7)
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha               # reuse layers from earlier runs
          cache-to: type=gha,mode=max        # mode=max also caches build-stage layers
LineWhy it's there
permissions: packages: writeThe default GITHUB_TOKEN can't push packages. Without it the push fails with denied: permission_denied: write_package (HTTP 403).
if: github.event_name != 'pull_request'PRs from forks get no secrets, and you don't want images for unmerged code in the registry.
id: meta + steps.meta.outputs.tagsThe id lets a later step read this step's outputs (a newline-separated tag list).
type=sha,prefix=,format=longDefault is sha-3f9c2e1. Empty prefix + long format gives exactly ${{ github.sha }}, which the deploy job uses.
cache-from/to: type=ghaStores BuildKit layer cache in the GitHub Actions cache. Unchanged npm ci layer → build drops from ~90 s to ~15 s.

Tagging strategy

TagMoves?Use it for
:latestYes, every pushLocal experiments only. Never in a K8s manifest.
:mainYes"Newest build of main", e.g. a dev environment.
:<git-sha>No (by convention)Deployments. Traceable to a commit; rollback = redeploy the previous SHA.
:1.4.0 / :1.41.4.0 fixed, 1.4 movesReleases for humans.
@sha256:9b1c… (digest)Never (content hash)Strongest pin; what admission policies and SBOMs reference.

Why latest is bad for deploys: you can't tell which code is running, kubectl apply with the same tag doesn't trigger a rollout, two nodes may cache different "latest" images, and there's nothing to roll back to.

Common mistakes

Uppercase in the image name → invalid reference format: repository name must be lowercase. github.repository_owner can be ShauryaV, so hard-code the lowercase name.
Image built on an M-series Mac fails on EC2/x86 nodes with exec format error: build in CI, or locally with docker buildx build --platform linux/amd64.
New GHCR packages are private. The cluster gets ImagePullBackOff until you make the package public or add a pull secret:

$ kubectl -n taskflow create secret docker-registry ghcr-pull \
    --docker-server=ghcr.io --docker-username=shauryav --docker-password="$CR_PAT"
secret/ghcr-pull created
# then list it under the pod spec's imagePullSecrets (Session 12)
Recap buildx + login + metadata + build-push = the standard image job. Push only from main/tags, tag every image with the full git SHA, cache layers with type=gha.

3 Deploying to Kubernetes from CI

Explain like I'm 5

CI gets a key to the cluster and says "run version 3f9c2e1 now". The key must open only the TaskFlow room, and a grown-up presses "approve" before it goes in.

ApproachCommand in CIProsCons
kubectlkubectl set image + rollout statusSimple, no chart neededOnly changes the image; config drifts from Git
Helm (used here)helm upgrade --install … --set image.tag=SHA --atomicVersioned releases, auto-rollback, one command for all manifestsNeeds a chart (Session 17)
GitOps (Session 22)CI commits the new tag to Git; Argo CD pulls itCluster credentials never leave the clusterMore moving parts

How the runner gets cluster access

  • kubeconfig in a secret — simplest. Store it base64-encoded as an environment secret. Use a ServiceAccount bound to a Role in namespace taskflow (Session 16), not your cluster-admin config.
  • Cloud OIDC — no long-lived secret. GitHub issues a short-lived token; AWS/GCP/Azure trusts it (snippet below).
  • Self-hosted runner on a machine that can reach the cluster (runs-on: self-hosted).
Common mistake: deploying to minikube from GitHub-hosted runners

A minikube kubeconfig points to https://192.168.49.2:8443 and to cert files on your laptop. A runner in GitHub's cloud can't reach it: dial tcp 192.168.49.2:8443: i/o timeout. For the project, either run a self-hosted runner on your laptop, use a cloud cluster, or let Argo CD pull (Session 22).

.github/workflows/ci-cd.yml — the deploy job (full file in §7)
  deploy:
    name: Deploy to Kubernetes
    needs: image-scan                        # never deploy an unscanned image
    if: github.ref == 'refs/heads/main'      # main only — not PRs, not tags
    runs-on: ubuntu-latest                   # kubectl is pre-installed on GitHub runners
    environment: production                  # pauses for required reviewers; unlocks env secrets
    concurrency:
      group: deploy-production               # one deploy at a time…
      cancel-in-progress: false              # …and never kill a deploy halfway
    steps:
      - uses: actions/checkout@v4            # we need ./charts/taskflow
      - uses: azure/setup-helm@v4
        with:
          version: v3.22.0                   # pin Helm 3 (Helm 4 renamed --atomic)
      - name: Write kubeconfig
        env:
          KUBECONFIG_B64: ${{ secrets.KUBECONFIG_B64 }}   # secret → env var, not inline in the script
        run: |
          mkdir -p ~/.kube
          echo "$KUBECONFIG_B64" | base64 -d > ~/.kube/config
          chmod 600 ~/.kube/config
      - name: Helm upgrade
        run: |
          helm upgrade --install taskflow ./charts/taskflow \
            --namespace taskflow --create-namespace \
            -f charts/taskflow/values-prod.yaml \
            --set image.repository=${{ env.IMAGE }} \
            --set image.tag=${{ github.sha }} \
            --atomic --wait --timeout 5m
      - name: Verify rollout
        run: kubectl -n taskflow rollout status deployment/taskflow-api --timeout=120s
LineMeaning
environment: productionLinks the job to the production environment: required reviewers, wait timer, "only main may deploy", and secrets that exist only there.
env: KUBECONFIG_B64: ${{ secrets… }}Passing secrets through env keeps them out of the generated script text. GitHub masks them as *** in logs.
--set image.tag=${{ github.sha }}Deploys exactly the image this run built and scanned (the full-SHA tag from §2).
--atomic --wait --timeout 5mWait until pods are Ready; if not within 5 min, roll back to the previous revision automatically and fail the job.
rollout statusSecond check that the Deployment really finished. Non-zero exit = red job. The chart names it taskflow-api via fullnameOverride (Session 17).

4 SAST & SCA

Explain like I'm 5

SAST proof-reads the essay you wrote. SCA checks whether the books you copied quotes from have been recalled.

SAST — scan your own code

  • Parses the code without running it, tracks data from a source (user input like req.query) to a sink (dangerous call like pool.query). Catches injection, XSS, path traversal, weak crypto.
  • Limits: false positives; can't see runtime config or the deployed environment (that's DAST's job).
server.js — vulnerable (excerpt)
app.get('/tasks', async (req, res) => {
  const sql = `SELECT * FROM tasks WHERE status = '${req.query.status}'`;   // ❌ user input inside SQL text
  const { rows } = await pool.query(sql);
  res.json(rows);
});
$ curl -s "http://localhost:3000/tasks?status=x'%20OR%20'1'='1"      # status = x' OR '1'='1
[{"id":1,"title":"Buy milk","status":"done"},{"id":2,"title":"Ship v1","status":"todo"}, … every row …]
server.js — fixed
app.get('/tasks', async (req, res) => {
  const { rows } = await pool.query(
    'SELECT * FROM tasks WHERE status = $1',   // ✅ placeholder
    [req.query.status]                         // value sent separately, never parsed as SQL
  );
  res.json(rows);
});

LineMeaning

Common mistakes

CodeQL on a private repo needs GitHub Code Security (paid); public repos are free. And don't enable CodeQL "default setup" in Settings and commit codeql.yml — the advanced workflow's upload is rejected while default setup is on.

5 Secret scanning

Explain like I'm 5

Git never forgets. Once your house key is in a commit, everyone who clones the repo has a copy, even if you later delete it.

  • Targets: cloud keys (AKIA…), GitHub tokens (ghp_…), DB URLs with passwords, private keys, kubeconfigs, .env files.
  • Bots scan public GitHub continuously; a leaked AWS key can be abused within minutes.
  • Scanners match known token formats (regex) plus high-entropy strings, in files and every commit in history.

AlertsContinuous on the repoGitHub secret scanning alerts (+ partner notification: e.g. AWS is told and quarantines the key)

Fix before it's public: remove the line, git commit --amend (or git reset --soft HEAD~1 and recommit), push again. The CI job (§7) is the backstop:

  secret-scan:
    runs-on: ubuntu-latest

False positive (e.g. a test fixture)? Add its Fingerprint line to .gitleaksignore, or end the line with a gitleaks:allow comment.

A secret leaked — what now (in this order)

  1. Revoke / rotate it immediately (IAM → deactivate key, regenerate token). Assume it's compromised.
  2. Check what it was used for (AWS CloudTrail, GitHub audit log).
  3. Move it to a proper store (GitHub secret, AWS Secrets Manager, K8s Secret) and read it from env.
  4. Purge it from history, force-push, tell collaborators to re-clone.
  5. Add the pre-commit hook so it can't happen again.
$ pip install git-filter-repo
$ echo 'AKIA4EXAMPLEKEY7QXA==>REMOVED' > replacements.txt     # literal==>replacement
$ git filter-repo --replace-text replacements.txt         # rewrites every commit (removes 'origin' remote)
$ git filter-repo --invert-paths --path .env              # or: delete a whole file from all history
$ git remote add origin git@github.com:shauryav/taskflow.git && git push --force --all
Common mistake

"I deleted the file in a new commit, so it's fine." It isn't: git log -p still shows it, and forks/clones already have it. Rewriting history doesn't help either if you skip step 1. Rotation is the only real fix.

Recap Layer it: pre-commit hook → push protection → gitleaks in CI with fetch-depth: 0. If a secret leaks: rotate first, then clean history.

Explain like I'm 5

You checked your own ingredients (SCA), but the lunchbox (base image) came with extra snacks. Trivy opens the box and checks everything inside.

  • An image = base OS packages (Alpine apk / Debian apt) + runtime (Node, npm) + your node_modules. SCA on your lockfile misses the first two.
  • Trivy (Aqua Security) reads the layers, lists every package and matches them against vulnerability databases. It can also find secrets and misconfigurations.

Real incident: pin third-party actions to a commit SHA

In March 2026 attackers with stolen credentials force-pushed almost every version tag of aquasecurity/trivy-action (and published a malicious Trivy v0.69.4). 7 Security gates & the complete pipeline

Explain like I'm 5

A gate is a turnstile: no green ticket from every scanner, no entry to production.

  • A security gate is a check that can stop the pipeline. A scan that only prints a report is not a gate.
  • Mechanism: the tool exits non-zero → step fails → job fails → every job that needs it is skipped → branch protection blocks the merge.
Gate typeTaskFlow implementation
Automated thresholdnpm audit --audit-level=high; gitleaks (any leak = exit 1); Trivy --exit-code 1 --severity CRITICAL,HIGH; Semgrep --error; CodeQL check fails on new High+ alerts.
Policy (merge)Branch protection / ruleset on main: PR required, 1 approval, required status checks, no force-push.
Manualenvironment: production with required reviewers.
Exceptions.trivyignore with exp:, .gitleaksignore, Dependabot ignore, CodeQL "dismiss alert" with a reason. Always reviewed in a PR.
Branch protection setting (Settings → Branches → rule for main)Why
Require a pull request before merging · 1 approval · dismiss stale approvalsNo direct pushes; new commits need a fresh review.
Require status checks: Unit tests, SAST (CodeQL), SCA (npm audit), Secret scan (gitleaks), Build & push image, CodeQLMerge button stays grey until all pass.
Require branches to be up to date before mergingChecks ran against the latest main.
Do not allow bypassing · block force pushesAdmins follow the rules too.

This file replaces Session 18's ci.yml: same test job, plus scans, image build and deploy. (Splitting it into ci.yml for PR checks and cd.yml for build + deploy on main works the same way.)

.github/workflows/ci-cd.yml
name: CI/CD

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]                    # release tags like v1.4.0
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read                        # least privilege; jobs add what they need

concurrency:
  group: ci-cd-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}   # cancel stale PR runs only

env:
  IMAGE: ghcr.io/shauryav/taskflow-api  # lowercase!
  NODE_VERSION: "20"

jobs:
  # ---------- 1. fast feedback ----------
  test:
    name: Unit tests
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test

  # ---------- 2. security scans (run in parallel) ----------
  sast:
    name: SAST (CodeQL)
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
      actions: read
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v4
        with:
          languages: javascript-typescript
          build-mode: none
          queries: security-extended
      - uses: github/codeql-action/analyze@v4
        with:
          category: "/language:javascript-typescript"

  sca:
    name: SCA (npm audit)
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm audit --audit-level=high --omit=dev   # reads package-lock.json, no install needed

  secret-scan:
    name: Secret scan (gitleaks)
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  # ---------- 3. build & push ----------
  build-push:
    name: Build & push image
    needs: [sast, sca, secret-scan]
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Log in to GHCR
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Compute tags & labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,prefix=,format=long
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
      - name: Build (push on main / tags)
        uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ---------- 4. scan the pushed image ----------
  image-scan:
    name: Image scan (Trivy)
    needs: build-push
    if: github.event_name != 'pull_request'   # PR images were not pushed
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: read                    # pull the (private) image from GHCR
    steps:
      - uses: actions/checkout@v4       # for .trivyignore
      - uses: docker/login-action@v3    # Trivy reuses Docker's registry credentials
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: aquasecurity/trivy-action@v0.36.0   # pin to a commit SHA in real projects (§6)
        with:
          image-ref: ${{ env.IMAGE }}:${{ github.sha }}
          format: table
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: "1"
          trivyignores: .trivyignore

  # ---------- 5. deploy ----------
  deploy:
    name: Deploy to Kubernetes
    needs: image-scan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    concurrency:
      group: deploy-production
      cancel-in-progress: false
    steps:
      - uses: actions/checkout@v4
      - uses: azure/setup-helm@v4
        with:
          version: v3.22.0
      - name: Write kubeconfig
        env:
          KUBECONFIG_B64: ${{ secrets.KUBECONFIG_B64 }}
        run: |
          mkdir -p ~/.kube
          echo "$KUBECONFIG_B64" | base64 -d > ~/.kube/config
          chmod 600 ~/.kube/config
      - name: Helm upgrade
        run: |
          helm upgrade --install taskflow ./charts/taskflow \
            --namespace taskflow --create-namespace \
            -f charts/taskflow/values-prod.yaml \
            --set image.repository=${{ env.IMAGE }} \
            --set image.tag=${{ github.sha }} \
            --atomic --wait --timeout 5m
      - name: Verify rollout
        run: kubectl -n taskflow rollout status deployment/taskflow-api --timeout=120s

Common mistakes

Required check not listed in branch protection: GitHub only offers checks that ran in the last 7 days, and the name must match the job's name: exactly (matrix jobs look like Unit tests (20)).
Gate in report-only mode: Trivy defaults to exit-code 0, npm audit without --audit-level fails on any low finding (too noisy, so people add || true and the gate is gone).
Image pushed before scanning: here a vulnerable image can sit in GHCR but is never deployed. Stricter variant: build with load: true, scan locally in the same job, push only if clean.

★ Putting it all together

The big idea

Every TaskFlow commit now goes through one pipeline: tests, then three parallel scans of the code (CodeQL), its dependencies (npm audit + Dependabot) and its history (gitleaks). Only then is an image built and pushed to GHCR under the commit SHA, scanned again as a whole by Trivy, and deployed to Kubernetes with Helm after a human approves. Every scanner is a gate because it exits non-zero, and branch protection plus needs: make sure a failed gate stops everything after it.

Quick self-check

What's the difference between SAST and SCA? Give a TaskFlow example of each.

SAST analyses your own source for insecure patterns (SQL built from req.query.status). SCA checks third-party packages against known CVEs (body-parser 1.20.2 → CVE-2024-45590).

Why deploy :3f9c2e1… instead of :latest?

A SHA tag is immutable and traceable to a commit; changing it triggers a rollout; rollback = redeploy the previous SHA. latest moves, so you can't tell what's running and re-applying it changes nothing.

An AWS key was pushed to a public repo an hour ago. What's step 1?

Deactivate/rotate the key in IAM immediately and check CloudTrail. Rewriting history comes after; it doesn't help with clones and forks.

What do severity: CRITICAL,HIGH, ignore-unfixed: true, exit-code: "1" do together?

Fail the job only if the image has a High/Critical vulnerability that has a fixed version available. Lower severities and unpatched issues don't block.

The build job fails with 403 Forbidden pushing to ghcr.io. Most likely fix?

Add permissions: packages: write to the job (and log in with GITHUB_TOKEN). Also check the image name is lowercase.

Why does gitleaks in CI need fetch-depth: 0?

actions/checkout fetches only the latest commit by default; a secret added and "deleted" in older commits would be missed. Depth 0 fetches the full history.

Dependabot alerts vs security updates vs version updates?

Alerts notify about vulnerable deps; security updates auto-open PRs to the minimum fixed version; version updates open scheduled PRs for all deps and are the only one that needs dependabot.yml.
