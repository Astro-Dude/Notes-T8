1 Monitoring vs observability

The problem: everything is green, and users are failing

Friday, 14:05. Three users message you: "I can't add tasks." You open the TaskFlow dashboard:

taskflow-api pods      2/2 Running
CPU (api)              31 %
GET /health            200 OK
alerts firing          none

You watch CPU, crashes and the health check because those are the failures you predicted. Nothing measures this one. Section 2 finds the cause; section 6 writes the alert that would have caught it.

The idea

Monitoring watches signals you picked in advance and alerts when one crosses a threshold. It answers "is it broken?" for failures you predicted (known unknowns). Observability is a property of the system: how well you can work out what's happening inside from what it emits (metrics, logs, traces), even for failures nobody predicted (unknown unknowns). It answers "why?". Monitoring is its automated part.

 MONITORING: questions written down before the incident
   CPU > 80%?    pod restarting?    /health != 200?    5xx ratio > 5%?
        │ any "yes" → alert                 all "no" → green dashboard
        ▼
 OBSERVABILITY: questions you only think of during the incident
   "Only POST /tasks?"   "Since the 14:00 deploy?"   "Which call inside the request is slow?"
        └─ answered by slicing metrics, logs and traces by labels and trace ID (section 2)
Think of it like this

A hospital ward. Monitoring is the bedside alarm: it beeps above a limit set in advance. Observability is what the doctor can examine afterwards (vitals chart, nurses' notes, test records) to diagnose what no alarm covers. The ward stays with us: Prometheus is the nurse on rounds, Alertmanager the nurses' station, Grafana the wall display, Argo CD the nurse who follows the prescription.

See it: what the dashboard should have shown

Google's SRE book names four golden signals for any service. Here they are for TaskFlow at 14:05:

Signal       TaskFlow measurement                normal    at 14:05
Latency      p95 of POST /tasks                  0.12 s    1.8 s
Traffic      requests per second                 5.0       5.0
Errors       share of requests answered 5xx      0.1 %     6 %     ← what users feel
Saturation   postgres-0 memory vs its limit      40 %      99 %    ← the cause

Latency and errors are symptoms: users feel them. CPU and pod counts are possible causes. The green dashboard watched only causes, and the wrong ones. The rule: alert on symptoms, debug with causes.

What the golden signals do not do: explain anything. They say that POST /tasks fails; why needs logs and traces. Two shorter checklists: RED (Rate, Errors, Duration) for services like taskflow-api, USE (Utilisation, Saturation, Errors) for resources such as nodes and disks.

Exam trap

"Monitoring and observability are competing approaches." ✗ Monitoring is a subset of observability. You still need alerts; observability adds the data to explain them.

"Page the on-call engineer when CPU passes 80%." ✗ That's a cause. High CPU with happy users isn't an incident. Page on symptoms (errors, latency).

Remember

Monitoring → is it broken? (known unknowns) · Observability → why? (unknown unknowns)
Golden signals: latency · traffic · errors · saturation. Alert on symptoms.

Mastery check
Q1. Your professor says: "We have 40 dashboards, so our system is observable." Correct?

No. Dashboards answer questions chosen in advance (monitoring). Observability means answering new questions mid-incident, from correlated data you can slice any way.

Q2. Monitoring or observability? (a) "Is the 5xx ratio above 5%?" (b) "Which route started failing after the 14:00 deploy, and on which pod?"

(a) Monitoring: a predefined threshold. (b) Observability: a question invented during the incident, answered by slicing by route, pod and time.

Q3. Name the golden signal: (a) 5 req/s (b) p95 1.8 s (c) Postgres at 99% of its memory limit (d) 6% of requests return 500.

(a) Traffic · (b) Latency · (c) Saturation · (d) Errors.

2 Metrics, logs & traces

The problem

Back to 14:05. A number says 6% of requests fail, and that's all a number can say. Which requests? Where does the time go: nginx, the API, Redis, Postgres? What did the code report?

The idea

Three kinds of telemetry, three questions. Metrics are numbers over time with a name and labels: cheap, kept for everything, they tell you that something is wrong. Traces follow one request through every service as timed steps (spans): where. Logs are timestamped event records, ideally one JSON object per line: what. To jump between them they share fields: the same labels, and the same traceId on a trace and its log lines.

 METRIC  error ratio for route="/tasks" jumps at 14:00                   → THAT  (which route, since when)
    │ pick one failing POST /tasks request from 14:05
    ▼
 TRACE   4bf92f35…  POST /tasks 1840 ms; the pg INSERT span takes 1820 ms ✗ → WHERE (the database call)
    │ search the logs for traceId=4bf92f35…
    ▼
 LOG     "insert into tasks failed: connection terminated unexpectedly"  → WHAT  (the DB dropped us)
Think of it like this

Metrics are the vitals written down every 15 minutes, logs the nurse's notes ("14:05 chest pain"), a trace the patient's journey card (triage 5 min, X-ray 40 min). The patient ID on all three is the trace ID.

See it: one failing request, three views

trace 4bf92f35… (waterfall)

That solves section 1's incident: Postgres kept being killed for exceeding its memory limit (kubectl describe pod postgres-0 → Reason: OOMKilled, Exit Code: 137, Session 6), and the green dashboard never watched it. What collecting them does not do: link them. Without the traceId in the log you'd grep by timestamp.

Exam trap

"OpenTelemetry is a database for traces." ✗ OTel produces and transports telemetry. Tempo, Jaeger, Prometheus and Loki store it.

"Logs make metrics unnecessary: just count log lines." ✗ Logs cost far more to store and query at volume. Metrics are the cheap, always-on layer you alert on.

Remember

Metrics → that · Traces → where · Logs → what.
Link them with a shared traceId and shared labels.

Mastery check
Q1. Which pillar first? (a) "p95 has doubled since 14:00" (b) "for this slow request, which service is slow?" (c) "what error did the API print for request 4bf92f35…?"

(a) Metrics: a trend. (b) Traces: the spans show where the time went. (c) Logs, filtered by that traceId.

Q2. Your API writes logs to /var/log/taskflow/app.log inside the container. Why is kubectl logs empty?

The runtime only captures stdout and stderr. The file sits in the writable layer, where no collector looks, and vanishes with the pod. Log JSON lines to stdout.

Q3. Spot the bug: new client.Counter({ name: 'http_requests_total', labelNames: ['method', 'path', 'user_id'] }), with path set to req.originalUrl.

Every distinct label value is a new time series. path gets one per task ID and user_id one per user, so the series count explodes and can take Prometheus down (high cardinality). Use the route template (/tasks/:id); put IDs in logs and traces.

3 Prometheus: pull model & metric types

The problem

TaskFlow's request count is a variable inside the Node process. You want a 24-hour graph of it, for two pods today and six tomorrow, without the app knowing where graphs live. And when a pod dies you want to be told.

The idea

Prometheus (CNCF graduated) is a scraper, a time-series database (TSDB), a query language (PromQL) and a rule engine. It pulls: the app serves its current numbers as text at GET /metrics, and every scrape_interval (often 15 s) Prometheus fetches the page from each target and stores one timestamped sample per number. A time series is one metric name plus one unique set of labels.

                      ┌────────────── Prometheus server ──────────────┐
 taskflow-api:3000 ◀──┤ scrape (pull)  →  TSDB (local disk)  →  PromQL ├──▶ Grafana (dashboards)
 node-exporter:9100 ◀─┤      ▲                     │                    │
 kube-state-metrics ◀─┤      │ targets from        ▼                    │
                      │  service discovery    rule engine ──alerts──────┼──▶ Alertmanager ──▶ Slack / email / PagerDuty
                      │  (static, kubernetes_sd, ServiceMonitor)        │    (group, dedupe, silence, route)
                      └─────────────────────────────────────────────────┘
 batch job ──push──▶ Pushgateway ◀── scrape

Software without /metrics gets an exporter: node_exporter (host, :9100), postgres_exporter (:9187), kube-state-metrics (K8s objects), blackbox_exporter (probes URLs). Short-lived jobs push to the Pushgateway, which Prometheus scrapes.

Think of it like this

The nurse does rounds: every 15 minutes she reads each bed's monitor (/metrics) into the chart (TSDB). Patients don't phone in, so an empty bed is noticed next round (up = 0); a collapsed patient would never phone. An exporter gives a screenless machine a screen.

http_requests_total{method="POST",route="/tasks",status="201"} 214

Instrument TaskFlow with prom-client

server.js (metrics part)
const express = require('express');
const client = require('prom-client');              // npm install prom-client
const app = express();

client.collectDefaultMetrics();                         // free process_* and nodejs_* metrics

const httpRequests = new client.Counter({
  name: 'http_requests_total',                         // counters end in _total
  help: 'HTTP requests handled',
  labelNames: ['method', 'route', 'status'],
});
const httpDuration = new client.Histogram({
  name: 'http_request_duration_seconds',               // base unit = seconds
  help: 'HTTP request latency',
  labelNames: ['method', 'route'],
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5],             // bucket upper bounds (le)
});

app.use((req, res, next) => {
  const stopTimer = httpDuration.startTimer();
  res.on('finish', () => {
    const route = req.route ? req.route.path : 'unmatched';   // '/tasks/:id', never '/tasks/42'
    httpRequests.inc({ method: req.method, route, status: res.statusCode });
    stopTimer({ method: req.method, route });
  });
  next();
});

app.get('/metrics', async (req, res) => {
  res.set('Content-Type', client.register.contentType);   // Prometheus 3 fails scrapes without a valid one
  res.send(await client.register.metrics());
});

Per request, the middleware times the response, then adds 1 to the counter and records the duration, labelled with the route template. The histogram's part of the page:

Exam trap

"Apps push their metrics to the Prometheus server." ✗ Prometheus pulls. Only the Pushgateway receives pushes, for short-lived jobs.

"The le="0.25" bucket counts requests between 0.1 s and 0.25 s." ✗ It counts every request ≤ 0.25 s (1018 here).

Remember

Prometheus pulls /metrics. One series = name + one label set.
Counter ↑ only (use rate) · Gauge ↕ · Histogram = cumulative buckets.

Mastery check
Q1. Counter, gauge or histogram? (a) tasks created since start (b) DB connections in use now (c) how long each request took.

(a) Counter: it only grows. (b) Gauge: up and down. (c) Histogram: you want percentiles across pods.

Q2. From the output above: how many GET /tasks requests took more than 0.1 s but at most 0.25 s?

1018 − 961 = 57. Subtract neighbouring buckets, because each includes everything below it.

Q3. Predict: the API pod restarts at 14:10. What happens to the raw value of http_requests_total? Is history lost?

It drops to 0: the counter lived in the old process. No history is lost, since Prometheus stored the samples, and rate() treats the drop as a reset (section 5).

4 Scraping TaskFlow: prometheus.yml

The problem

You start Prometheus in Docker Compose next to TaskFlow and give it the address that works in your browser:

$ curl -s localhost:3000/metrics | head -1                # from your laptop
# HELP process_cpu_user_seconds_total Total user CPU time spent in seconds.
# Prometheus → Status → Target health
taskflow-api   http://localhost:3000/metrics   DOWN   dial tcp [::1]:3000: connect: connection refused

Same URL, two answers. It's solved at the end of this section.

The idea

prometheus.yml lists scrape jobs, and each job lists targets (host:port). Every series scraped from a target gets two labels automatically: job (the job's name) and instance (the target). In Compose a target is a service name on a network Prometheus shares with the app.

 Compose network "backend"
 prometheus:9090 ──GET /metrics every 10 s──▶ api:3000             job="taskflow-api"
   reads         ──────────────────────────▶ node-exporter:9100   job="node"
   prometheus.yml ─────────────────────────▶ localhost:9090 (itself) job="prometheus"
       │ firing alerts ──▶ alertmanager:9093
       ▲ PromQL queries ── grafana:3000 (host port 3001)
Think of it like this

prometheus.yml is the rounds list: bed numbers (targets) grouped by ward (job), and every reading is tagged with both. Inside the Prometheus container, "localhost" means the nurse's own desk, not the patient's bed.

See it: the smallest config

scrape_configs:
  - job_name: taskflow-api
    static_configs:
      - targets: ["api:3000"]

One job (job="taskflow-api") with one fixed target: Compose service api, container port 3000 (instance="api:3000"). Defaults: every 1 minute, path /metrics, HTTP. What it does not do: make the app serve /metrics (prom-client does) or join the app's network (Compose does).

5 PromQL

The problem

Graph http_requests_total as it is and you get lines that only climb, dropping to zero at every pod restart. Useless. What you want to know: requests per second, the percentage that fails, and how slow the slowest 5% are.

The idea

PromQL turns stored series into answers. An instant vector is one latest value per series (http_requests_total). A range vector is a window of samples per series (http_requests_total[5m]), which only functions accept. The workhorse is rate(), the per-second increase over the window. Then you aggregate with sum, avg, max….

 http_requests_total{status=~"5.."}[5m]       range vector: the last 5 min of samples, per series
        │ rate()                               per-second increase, per series (handles restarts)
        ▼
 {route="/tasks",status="500",pod="a"} 0.2    {route="/tasks",status="500",pod="b"} 0.1
        │ sum()                                add the series together
        ▼
 {} 0.3        ← 5xx per second, whole app
        │ ÷  sum(rate(http_requests_total[5m]))  = 5.0
        ▼
 0.06          → 6 % error ratio
Think of it like this

The chart says 1,250 ml of IV fluid since admission: a counter. The doctor wants the drip speed, which is rate(): (1,250 − 1,100) ml over 30 minutes. A new bag restarts at zero and you carry on from it, as rate() does with resets.

See it: your first query

$ curl -s localhost:9090/api/v1/query --data-urlencode 'query=up' | jq -r '.data.result[] | "\(.metric.job) \(.value[1])"'
node 1
prometheus 1
taskflow-api 1
TokenMeaning
/api/v1/queryThe HTTP API for an instant query (what the UI's Query page uses)

Worked example: rate and p95 by hand
  • rate: the total counter is 18 400 at 14:00:00 and 19 900 at 14:05:00 → (19 900 − 18 400) / 300 s = 5.0 req/s. If 0.3 req/s are 5xx, the error ratio is 0.3 / 5.0 = 6%.
  • p95 from section 3's buckets (1039 requests): rank = 0.95 × 1039 ≈ 987. le="0.1" holds 961 and le="0.25" 1018, so p95 is in 0.1–0.25 s: 0.1 + 0.15 × (987 − 961) / (1018 − 961) ≈ 0.169 s. histogram_quantile does this, so it's only as good as your buckets.
Exam trap

"Aggregate first, then rate: rate(sum(…))." ✗ Always sum(rate(…)). rate must see each series alone to spot its resets. A sum of counters drops whenever one pod restarts.

"For the p95 across pods, average each pod's p95." ✗ Percentiles don't average. Sum the buckets (sum by (le)), then call histogram_quantile once.

"rate(x[15s]) with 15 s scrapes is most precise." ✗ It needs two samples in the window and often returns nothing. Use ≥ 4× the scrape interval.

Remember

Counters: rate first, then sum: sum(rate(x[5m])).
p95 = histogram_quantile(0.95, sum by (le) (rate(x_bucket[5m]))).

Q3. Predict: the buckets go up to 2.5 s and the real p99 is 4 s. What does histogram_quantile(0.99, …) return?

6 Alerting: rules & Alertmanager

The problem

Nobody watches graphs at 3 a.m., and you heard about section 1's incident from users. You want Prometheus to notice the 6% error ratio itself and message the right person once, not 200 times.

The idea

Alerting rules live in Prometheus, which runs each rule's PromQL every evaluation_interval. If the query keeps returning series for longer than for, the alert fires and goes to Alertmanager, which groups, deduplicates, routes, silences and inhibits, then notifies Slack, email or PagerDuty.

A good monitor doesn't page for one high reading: "above 120 for 5 minutes" (for). Pages go to the nurses' station (Alertmanager), which bundles ten beeps into one call, sends critical ones to the on-call doctor and stays quiet during planned surgery (a silence).

See it: one rule, one outage

The smallest useful rule: alert: TaskflowApiDown, expr: up{job="taskflow-api"} == 0, for: 1m. Read it as "if a taskflow-api target has failed its scrapes for a whole minute, raise TaskflowApiDown" (the full file is below). Cause an outage:

Build it up

The alert that would have caught section 1

monitoring/alerts.yml
groups:
  - name: taskflow                      # rules in a group are evaluated together, in order
    rules:

        expr: |
          sum(rate(http_requests_total{job="taskflow-api", status=~"5.."}[5m]))
            /
          sum(rate(http_requests_total{job="taskflow-api"}[5m]))

Q1. Predict: the error ratio is 8% for 3 minutes, then 2%. Does HighErrorRate (for: 5m) fire?

9 GitOps & Git as the source of truth

The problem

Friday night, production is broken, and nobody can answer the basic questions:

What version is running?        "Whatever the last CI run deployed… unless someone ran kubectl edit."
Who set replicas to 5, and why? No record.
How do we go back?              Re-run last week's pipeline and hope.
Why does CI hold cluster-admin? Because it runs kubectl against production.

All four come from one fact: the real state of the cluster lives only in the cluster.

The idea

GitOps: declare the desired state of the running system in Git, and let an agent inside the cluster (Argo CD, Flux) keep pulling it and making reality match. It's the reconciliation loop (Session 9) one level up, with desired state from Git instead of the last kubectl apply.

PUSH (classic CI/CD, Session 19)
  dev ──push──▶ GitHub ──▶ Actions runner ──helm upgrade / kubectl apply──▶ cluster
                           (holds the kubeconfig = cluster-admin credentials outside the cluster)

PULL (GitOps)
  dev ──push──▶ GitHub ◀──watch/poll── Argo CD (runs INSIDE the cluster) ──apply──▶ cluster
                                       (credentials never leave the cluster; drift is reverted)
Think of it like this

Git is the prescription chart. The ward nurse (the agent) keeps the patient on exactly what it says and takes no verbal orders; changing treatment means a new, reviewed prescription (a PR). Push is a doctor adjusting the drip himself: he needs keys to every ward, and nobody notices a visitor fiddling later.

Build it up: the Application

argocd/taskflow.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: taskflow
  namespace: argocd                          # Applications live in Argo CD's namespace
  finalizers:
    - resources-finalizer.argocd.argoproj.io # deleting the app also deletes its K8s resources
spec:
  project: default                           # AppProject: limits allowed repos/clusters/namespaces
  source:
    repoURL: https://github.com/shauryav/taskflow.git
    targetRevision: main                     # branch, tag or commit SHA to track
    path: charts/taskflow                    # folder inside the repo
    helm:
      valueFiles:
        - values-prod.yaml                   # relative to path; like helm -f
  destination:
    server: https://kubernetes.default.svc   # "this cluster" (where Argo CD runs)
    namespace: taskflow                      # target namespace for the chart's resources
  syncPolicy:
    automated:                               # sync on every Git change (no manual "Sync" click)
      prune: true                            # delete resources that were removed from Git
      selfHeal: true                         # revert manual changes made in the cluster
    syncOptions:
      - CreateNamespace=true                 # create "taskflow" if missing
FieldMeaning / gotcha
source.repoURLA public repo works as is. Private: argocd repo add https://github.com/shauryav/taskflow.git --username shauryav --password <PAT> first.
helm.valueFilesArgo CD runs the equivalent of helm template and applies the output. No Helm release exists: nothing in helm list, and helm rollback doesn't apply.
automatedWithout it the app shows OutOfSync until you click Sync or run argocd app sync.
pruneOff by default for safety: removing a file from Git won't delete the live object unless this is true.
selfHealRe-sync when the live state drifts from Git (after a 5 s self-heal timeout by default).

Two statuses, two questions

Sync status: does the cluster match Git?Health status: is it working?
Synced: live objects match what Git rendersHealthy: e.g. the Deployment has all replicas available
OutOfSync: Git changed, or someone changed the clusterProgressing: rollout under way
Unknown: couldn't render or compare (bad repo URL, chart error)Degraded: failed (CrashLoopBackOff, rollout deadline exceeded); also Missing, Suspended

They're independent: Synced + Degraded means Git was applied faithfully and what it asks for is crashing. Fix Git, not the cluster.

Exam trap

"Synced means the app works." ✗ Sync only compares Git with the cluster. Health says whether it works.

"Argo CD installs the chart as a Helm release." ✗ It renders the chart and applies plain manifests; helm list shows nothing.

Remember

Application = Git repo + path + values → cluster + namespace.
Sync = does it match Git? · Health = does it work?

Mastery check
Q1. Spot the bug: the Application has metadata.namespace: taskflow. It's created fine, but nothing ever deploys.

By default Argo CD only watches Applications in its own namespace, argocd. spec.destination.namespace is where the app's resources go.

Q2. Predict: you delete templates/hpa.yaml from the chart and push. What happens to the live HPA with prune: true? With prune: false?

With prune, Argo CD deletes it on the next sync. Without, the HPA stays and the app shows OutOfSync, with that resource marked as needing pruning.

Q3. Same Application, no syncPolicy. You commit a new tag. What does argocd app get show, and when does the rollout happen?

OutOfSync once Argo CD fetches the commit. Nothing rolls out until someone runs argocd app sync taskflow (or clicks Sync): still GitOps, with a manual gate.

The problem: two surprises

The idea

With automated sync, Git is the only way to change production. A merge flows to the cluster with no human step, manual changes are undone, and rollbacks are Git changes too.

Mastery check
Q1. Predict: automated with prune: true but selfHeal: false. Someone scales to 5 replicas. What happens, and until when?

It stays at 5, OutOfSync. Without selfHeal, automated sync only fires for a new Git revision, so the next commit (or a manual sync) restores 2.

Q2. Put in order: Argo CD marks OutOfSync · Trivy passes · rolling update · CI commits image.tag · PR merged · image pushed as :sha.

PR merged → image pushed as :sha → Trivy passes → CI commits image.tag → Argo CD marks OutOfSync → rolling update.

Q3. The chart has the HPA on. On-call runs kubectl scale … --replicas=5. Who changes it back, and why not Argo CD?

The HPA, at its next 15 s evaluation. Argo CD doesn't: with autoscaling on, the chart omits replicas, so it isn't desired state.

★ Putting it all together

The big idea

TaskFlow exposes RED metrics on /metrics; Prometheus pulls them (static list in Compose, ServiceMonitor on Kubernetes); PromQL turns counters into rates, error ratios and p95; rules fire on symptoms and Alertmanager pages once; Grafana draws it; logs and traces explain why. Deployment is GitOps: CI builds an immutable :<sha> image and commits the tag, and Argo CD pulls it, syncs and reverts drift. Git is the source of truth; git revert is the rollback.

Final mastery check — combine everything
Q1. A release goes out at 14:00 and HighErrorRate fires at 14:06. Walk from the Slack message to the fix, naming the tool at each step.

Alertmanager posts in #taskflow-alerts. Grafana, split by route: only POST /tasks fails since 14:00. A failing trace (Tempo/Jaeger) shows the failing span; its traceId finds the log line (Loki). argocd app history confirms the 14:00 sync was a new tag. git revert the bump; Argo CD syncs the old image and the alert resolves.

Q2. Argo CD shows Synced/Healthy and the ServiceMonitor exists, yet up{namespace="taskflow"} returns nothing. Three causes and how to check each?

(1) No release: monitoring label (kubectl get servicemonitor -n taskflow --show-labels). (2) matchLabels misses the Service's labels (kubectl get svc -n taskflow --show-labels). (3) endpoints.port isn't a named Service port (kubectl get svc taskflow-api -o yaml). Synced/Healthy says nothing about scraping.

Q3. Product wants a page when POST /tasks p95 stays above 500 ms for 10 minutes. Which metric type, query and rule fields?

A histogram with a 0.5 bucket. expr: histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{method="POST",route="/tasks"}[5m]))) > 0.5, for: 10m, labels: {severity: warning}; on Kubernetes, in a PrometheusRule labelled release: monitoring.

Q4. At 01:00 a teammate fixes a crash with kubectl set env deploy/taskflow-api LOG_LEVEL=debug. By 01:01 the crash is back and LOG_LEVEL is gone. Explain, and give the right fix.

selfHeal re-applied Git's version of the Deployment, rolling out pods without the variable. Put env.LOG_LEVEL in values-prod.yaml via a PR and let Argo CD sync.

Q5. Correct every error: "Grafana scrapes our pods every 15 s and stores the data. Argo CD pushes our manifests from GitHub Actions. To roll back we run argocd app rollback."

(1) Prometheus scrapes and stores; Grafana draws. (2) Argo CD runs inside the cluster and pulls; Actions only pushes the image and commits the tag. (3) With auto-sync on, rollback is refused: use git revert.
