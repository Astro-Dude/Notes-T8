1 The Linux File System

Explain like I'm 5

Linux has one big tree that starts at a single root, /. Every file, disk, and even running program hangs somewhere on that tree — there are no C: or D: drives.

  • Everything starts at /. Extra disks are mounted into the tree (e.g. at /mnt/data).
  • "Everything is a file": devices live in /dev, running processes appear in /proc.
  • Names are case-sensitive (App.js ≠ app.js); names starting with . are hidden (.env, .bashrc).
  • The layout follows the FHS (Filesystem Hierarchy Standard).
$ ls -l /

drwxr-xr-x   4 root root 4096 Oct  1 09:12 boot

Paths

  • Absolute path starts at /: /opt/taskflow/server.js — works from anywhere.
  • Relative path starts from the current directory: scripts/deploy.sh.
  • . = this directory, .. = parent, ~ = your home, cd - = previous directory.
$ cd /opt/taskflow/scripts
$ cd ..            # up one level
$ pwd
/opt/taskflow
$ cd ~ && pwd
/home/shaurya
$ cd -            # back to where you were
/opt/taskflow
$ cat /proc/loadavg   # a "file" generated live by the kernel
0.52 0.41 0.30 1/118 4410
Common mistake

Keeping anything important in /tmp — Ubuntu empties it at boot. App data goes in /var/lib/<app> or /opt/<app>, config in /etc/<app>, logs in /var/log/<app>.

Recap One tree from /. Config → /etc, logs → /var/log, apps → /opt, binaries → /usr/bin, users → /home. Absolute paths start with /; relative ones don't.

Create, copy, move, delete

3 Users & Groups

Explain like I'm 5

Every person and every program gets a name badge (user) and belongs to clubs (groups). The badge decides which doors (files) open.

  • Each user has a numeric UID; root is UID 0 and can do anything.
  • UID < 1000 = system users for services (no login), UID ≥ 1000 = humans.
  • Each user has one primary group (GID) and any number of supplementary groups (sudo, docker…).
  • Run services as their own unprivileged user (taskflow), never as root — a bug then can't wreck the whole box.

/etc/passwd — one line per account

$ grep -E "^(root|shaurya|taskflow):" /etc/passwd

shaurya:x:1000:1000:Shaurya Verma:/home/shaurya:/bin/bash
taskflow:x:999:999::/home/taskflow:/usr/sbin/nologin

Also: group changes apply at the next login. After usermod -aG docker shaurya, log out and back in (or run newgrp docker).

4 File Permissions

Explain like I'm 5

Every file has three locks — one for its owner, one for its group, one for everyone else — and each lock says whether you may read, write or run it.

Decoding ls -l

$ ls -l /opt/taskflow/scripts/deploy.sh
-rwxr-xr-x 1 shaurya devs 35 Oct  9 10:20 deploy.sh

 -   rwx   r-x   r-x   1   shaurya   devs   35   Oct  9 10:20   deploy.sh
 │   └┬┘   └┬┘   └┬┘   │      │        │     │         │            └─ name
 │    │     │     │    │      │        │     │         └─ last modified
 │    │     │     │    │      │        │     └─ size in bytes
 │    │     │     │    │      │        └─ group owner
 │    │     │     │    │      └─ user owner
 │    │     │     │    └─ hard-link count
 │    │     │     └─ others (everyone else): r-x
 │    │     └─ group (devs): r-x
 │    └─ user/owner (shaurya): rwx
 └─ type: - file, d directory, l symlink, c/b char/block device, s socket, p pipe
BitOn a fileOn a directory
r (4)Read the contentsList the names inside (ls)
w (2)Modify the contentsCreate, delete, rename entries (needs x too)
x (1)Execute it as a program/scriptEnter it (cd) and access files inside by name
Example: a directory with r but no x 
$ chmod 644 box           # rw-r--r-- on a DIRECTORY
$ ls box
a.txt
$ ls -l box
ls: cannot access 'box/a.txt': Permission denied
total 0
-????????? ? ? ? ?            ? a.txt
$ cat box/a.txt
cat: box/a.txt: Permission denied
$ cd box
bash: cd: box: Permission denied

You can read the names (r) but not reach the files (no x). Directories almost always need x: use 755, not 644.

chmod — numeric and symbolic

Add the digits per class: r=4, w=2, x=1. 7=rwx, 6=rw-, 5=r-x, 4=r--, 0=---.

Models -lTypical use
755rwxr-xr-xScripts, binaries, directories
644rw-r--r--Normal files (server.js, configs without secrets)
600rw-------Secrets: .env, taskflow.env, ~/.ssh/id_ed25519
400r--------AWS .pem keys
700rwx------Private dirs (~/.ssh)
775rwxrwxr-xShared team directory

$ ./hello.sh
bash: ./hello.sh: Permission denied
$ chmod +x hello.sh && ls -l hello.sh       # +x = add execute for u, g and o
-rwxr-xr-x 1 shaurya shaurya 28 Oct  9 11:41 hello.sh
$ chmod u=rwx,g=rx,o= hello.sh && ls -l hello.sh   # = sets exactly
-rwxr-x--- 1 shaurya shaurya 28 Oct  9 11:41 hello.sh
$ chmod g-x,o+r hello.sh && ls -l hello.sh        # - removes, + adds
-rwxr--r-- 1 shaurya shaurya 28 Oct  9 11:41 hello.sh
$ chmod 600 .env && ls -l .env
-rw------- 1 shaurya shaurya 10 Oct  9 10:20 .env
$ sudo chown -R taskflow:taskflow /opt/taskflow /var/log/taskflow   # owner:group, -R recursive
$ sudo chgrp devs /srv/shared                                       # change group only

umask — default permissions for new files

New files start from 666, new directories from 777; the umask bits are removed.

$ umask
0022                                 # 666-022 → 644 files, 777-022 → 755 dirs
$ touch f1; mkdir d1; ls -ld f1 d1
drwxr-xr-x 2 shaurya shaurya 4096 Oct  9 11:41 d1
-rw-r--r-- 1 shaurya shaurya    0 Oct  9 11:41 f1
$ umask 077; touch f2; mkdir d2; ls -ld f2 d2     # private by default (good for backup scripts)
drwx------ 2 shaurya shaurya 4096 Oct  9 11:41 d2
-rw------- 1 shaurya shaurya    0 Oct  9 11:41 f2

Some Ubuntu logins show 0002 (user-private groups) → files 664, dirs 775. The arithmetic is the same.

Special bits: setuid, setgid, sticky

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 72056 May 30  2024 /usr/bin/passwd   # s in owner x slot = setuid
$ ls -ld /tmp
drwxrwxrwt 12 root root 4096 Oct  9 10:15 /tmp            # t in others x slot = sticky

5 Processes & Signals

Explain like I'm 5

A program is a recipe; a process is someone actually cooking it right now. Each cook gets a number (PID), and you can tap them on the shoulder with signals: "please stop" or "STOP NOW".

  • Every process has a PID and a parent (PPID). PID 1 is systemd, the ancestor of everything.
  • A daemon is a background process with no terminal (sshd, cron, our taskflow service).

ps — snapshot of processes

$ ps aux | head -1; ps aux | grep [n]ode     # [n]ode trick: don't match the grep itself
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND

Common mistakes
  • Reaching for kill -9 first: the app can't flush logs, close DB connections or finish requests. Send kill (SIGTERM), wait ~10 s, then -9.
  • Running the API with node server.js & in an SSH session: it dies or is orphaned when you disconnect and never restarts after a crash or reboot. nohup is a stop-gap — use a systemd service (next topic).
Recap ps aux / ps -ef / pgrep -a to find, top to watch, kill (15) before kill -9. &, jobs, fg, bg, Ctrl+Z for job control; nohup, nice for long tasks.

6 Services with systemd

Explain like I'm 5

systemd is the building manager: it starts every program at boot, restarts the ones that fall over, and keeps a diary (the journal) of what each one said.

  • systemd is PID 1 on Ubuntu. It manages units: .service (a daemon), .timer (scheduled job), .socket, .target (group of units, e.g. multi-user.target = normal server boot).
  • Unit files: packages install into /usr/lib/systemd/system/; yours go in /etc/systemd/system/ (which also overrides packaged ones).
  • systemctl controls units; journalctl reads their logs.

The TaskFlow unit file

/etc/systemd/system/taskflow.service
[Unit]
# shown in status and logs
Description=TaskFlow API (Node.js)
Documentation=https://github.com/shauryav/taskflow
# start after the network is up, and pull that target in
After=network-online.target
Wants=network-online.target

[Service]
# the ExecStart process IS the service
Type=simple
# run unprivileged, not as root
User=taskflow
Group=taskflow
# cd here before starting
WorkingDirectory=/opt/taskflow
Environment=NODE_ENV=production
Environment=PORT=3000
# secrets (DATABASE_URL); leading "-" = OK if the file is missing
EnvironmentFile=-/etc/taskflow/taskflow.env
# absolute path to the binary (check with: which node)
ExecStart=/usr/bin/node /opt/taskflow/server.js
# restart on crash (non-zero exit or killed by a signal), 5 s apart
Restart=on-failure
RestartSec=5
# stdout/stderr go to journald (this is the default anyway)
StandardOutput=journal
StandardError=journal

[Install]
# "systemctl enable" hooks the service into normal boot
WantedBy=multi-user.target
Comments in unit files

systemd only treats # (or ;) as a comment at the start of a line. RestartSec=5 # wait makes the value 5 # wait; systemd logs Failed to parse sec value, ignoring: 5 # wait and silently drops the setting. logrotate is the same (rotate 7 # keep → bad rotation count). Put comments on their own line.

DirectiveDetails & alternatives
After= vs Wants=After only orders startup; Wants actually starts the other unit. You usually need both. Add postgresql.service to both if the DB runs on the same box.
Type=simpleDefault. forking = old daemons that background themselves; oneshot = a script that runs and exits; notify = app tells systemd when ready.
User= / Group=The account must exist (else status 217/USER).
WorkingDirectory=Must exist (else 200/CHDIR). Relative paths in the app resolve from here.
Environment= / EnvironmentFile=Inline KEY=value, or one per line in a file. systemd reads the file as root, so it can be root:root 600.
ExecStart=Full path to the program. Wrong path → 203/EXEC. No shell features (|, >, &&) unless you wrap in /bin/bash -c '…'.
Restart=no (default) · on-failure · always (even after a clean exit 0) · on-abnormal.
StandardOutput=journal (default) or append:/var/log/taskflow/app.log to write a file instead (then journalctl won't show it).
WantedBy=multi-user.targetsystemctl enable creates a symlink in multi-user.target.wants/ → starts at boot.

Key takeaway

enable = "at boot", start = "now". After a fresh install you need both (enable --now); after editing a unit file you need daemon-reload then restart.

By default systemd records everything a service prints on stdout and stderr at priority info. So journalctl -u taskflow -p err prints -- No entries -- even while the app crashes; use plain -u taskflow and grep.

Rotate app logs so they don't fill the disk

/etc/logrotate.d/taskflow
# every .log file in the TaskFlow log directory
/var/log/taskflow/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
DirectiveMeaning
dailyRotate once a day (weekly, monthly, or size 100M)
rotate 7Keep 7 old files; older ones are deleted
compress + delaycompressgzip old files (app.log.2.gz…) but leave the newest one (app.log.1) plain
missingok / notifemptyNo error if a log is missing / skip empty logs
copytruncateCopy the log, then truncate the original in place, so an app that keeps the file open carries on writing

★ Putting it all together

The big idea

A production Linux box follows conventions: code in /opt/taskflow, config in /etc/taskflow, logs in /var/log/taskflow. TaskFlow runs as its own taskflow user with tight permissions (600 on the env file), as a systemd service that starts at boot and restarts on crashes. When it breaks you check systemctl status, read journalctl -u taskflow, then look at disk, memory, ports and permissions — the same habits you'll later use inside containers and Kubernetes pods.

Quick self-check

Decode -rwxr-x--- 1 shaurya devs 35 Oct 9 deploy.sh. Can user deploy (member of devs) edit it? Run it?

Owner shaurya: rwx; group devs: r-x; others: none (mode 750). deploy can read and run it, but not edit it (no w for group).

What's the numeric mode for rw-r-----, and when would you use 600 instead of 644?

640. Use 600 for anything secret (.env, private keys) so only the owner can read it; 644 lets everyone read.

You ran sudo usermod -G docker shaurya and now sudo fails. Why, and what should you have typed?

-G without -a replaced all supplementary groups, removing sudo. Correct: sudo usermod -aG docker shaurya (then log in again).

systemctl enable taskflow finished, but curl localhost:3000 fails. What did you forget?

enable only configures start at boot. Start it now with systemctl start taskflow (or use enable --now).

systemctl status shows status=203/EXEC. What's wrong?

systemd couldn't execute the ExecStart= binary — usually a wrong path (e.g. /usr/local/bin/node when it's /usr/bin/node) or a script without x. Check which node, fix, daemon-reload, restart.

Difference between SIGTERM and SIGKILL? Which does kill PID send?

SIGTERM (15) asks politely and can be caught for graceful shutdown; SIGKILL (9) kills immediately and can't be caught. Plain kill sends SIGTERM.

Disk is 99% full. Which commands find the culprit, and why prefer truncate over rm for a live log?

df -h, then du -xh --max-depth=1 /var | sort -h drilling down. A deleted file that a process still holds open keeps using space; truncating empties it in place and frees the space immediately.
