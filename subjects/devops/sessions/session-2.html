1 The Linux file system

The problem

Your teammate says "TaskFlow is on web-01, go fix it." You SSH into the Ubuntu server for the first time. There's no desktop, no C: drive, no Program Files. ls / prints twenty short, cryptic names. Somewhere in there are the app's code, its config, its logs and its password file, and you have to know where to look before you can fix anything.

The idea

Linux has one tree that starts at the root, /. Extra disks are mounted into it (at /mnt/data, say) instead of getting a drive letter. Every top-level directory has a fixed job, set by the FHS (Filesystem Hierarchy Standard), so every Linux server is laid out the same way:

/                        the root of ONE tree (no C:, no D:)
├── etc/        config        /etc/taskflow/taskflow.env, /etc/systemd/system/taskflow.service
├── opt/        add-on apps   /opt/taskflow/server.js
├── var/        data that grows
│   └── log/    logs          /var/log/taskflow/app.log
├── home/       users' homes  /home/shaurya  (= ~ for shaurya)
├── root/       root's home   (not /home/root)
├── usr/bin/    programs      /usr/bin/node   (/bin is a link to it)
├── tmp/        scratch       emptied at every boot
├── proc/       live kernel + process info, generated on the fly (not on disk)
└── dev/        devices       /dev/null, /dev/nvme0n1

Two more rules: names are case-sensitive (App.js ≠ app.js), and names starting with . are hidden (.env, .bashrc).

Think of it like this

The server is an office building, and we'll use it all session. /etc is the policy binder, /var/log the logbook, /home the staff desks, and /root the manager's office, kept apart from the staff area. /opt is floor space rented to an outside company (TaskFlow). /tmp is the whiteboard that's wiped every night. /proc is the CCTV screen: a live view, not a filing cabinet.

ls lists a directory, -l asks for the long format (type + permissions, owner, group, size, date, name; decoded in section 5), and / is the directory to list.

The first letter of each line is the type: d directory, l symlink. bin -> usr/bin means /bin is just a pointer: modern Ubuntu keeps all programs in /usr/bin ("merged /usr"). Notice proc has size 0 and root is drwx------, so only root can enter it. What ls does not do: show hidden files (add -a) or descend into subdirectories (add -R).

Paths: absolute and relative

An absolute path starts at / (/opt/taskflow/server.js) and works from anywhere. A relative path starts from wherever you are now (scripts/deploy.sh). . means this directory, .. the parent, ~ your home, and cd - takes you back to the previous one.

$ cd /opt/taskflow/scripts
$ cd ..            # up one level
$ pwd              # print working directory
/opt/taskflow
$ cd ~ && pwd
/home/shaurya
$ cd -            # back to where you were
/opt/taskflow
$ which node       # which program runs when you type "node"
/usr/bin/node
$ man tar          # the manual for any command (q to quit); tar --help for a quick summary
$ cat /proc/loadavg   # a "file" the kernel generates as you read it
0.52 0.41 0.30 1/118 4410

/proc/loadavg is listed with size 0, yet cat prints data. The kernel writes the content at the moment you read it, which is why it's "everything is a file" and not "everything is on disk".

Exam trap

"The root user's home is /home/root." ✗ It's /root. And / (the root directory) is not /root (root's home).

"/tmp is a fine place for app data." ✗ Ubuntu empties it at boot. Data goes in /var/lib/<app> or /opt/<app>, config in /etc/<app>, logs in /var/log/<app>.

"Files in /proc are stored on disk." ✗ It's a virtual filesystem generated live by the kernel.

Remember

Config → /etc · logs → /var/log · app → /opt · programs → /usr/bin · homes → /home (root's → /root).
Absolute starts with /; relative starts from where you are.

Mastery check
Q1. Predict: you're in /opt/taskflow/scripts. You run cd ../.., then pwd, then cd -. What prints?

pwd prints /opt (two levels up). cd - prints and returns to /opt/taskflow/scripts.

Q2. Where do these go? (a) TaskFlow's env file with the DB password, (b) its log, (c) the nightly backup archives, (d) a tarball you're about to unpack and delete.

(a) /etc/taskflow/ · (b) /var/log/taskflow/ · (c) /var/backups/taskflow/ (under /var, because it grows) · (d) /tmp, which is fine precisely because it gets wiped.

Q3. Predict: node opt/taskflow/server.js works when you're in /. What happens if you run the same command from /home/shaurya?

It fails with Cannot find module '/home/shaurya/opt/taskflow/server.js'. The path is relative, so it resolves from the current directory. The absolute path /opt/taskflow/server.js works from anywhere.

2 Working with files

The problem

You're shipping a new TaskFlow version by hand: make a working folder, copy the scripts across, rename one, clean up, and pack a backup. Two commands in, two errors:

$ mkdir /tmp/demo/a/b/c
mkdir: cannot create directory '/tmp/demo/a/b/c': No such file or directory
$ cp scripts /tmp/demo/
cp: -r not specified; omitting directory 'scripts'

Both commands are almost right. Each is missing one flag. File commands are literal: they do exactly what you ask and nothing more.

The idea

A handful of verbs do all file work: ls list, mkdir make a directory, touch create an empty file, cp copy, mv move or rename, rm remove, and tar to pack many files into one. Three flags come up again and again: -p (create parents), -r (recursive, for directories) and -f (force: no questions, no errors).

             cp -r   copy: both exist afterwards
 scripts/  ───────────▶ /tmp/demo/scripts/
             mv      move or rename: only the new name exists
 deploy.sh ───────────▶ deploy-v2.sh
             rm -rf  delete: no recycle bin, no undo
 /tmp/demo ───────────▶ (gone)

See it: look before you touch

$ ls -lah /opt/taskflow
total 72K
drwxr-xr-x 4 shaurya shaurya 4.0K Oct  9 10:20 .
drwxr-xr-x 3 root    root    4.0K Oct  9 10:02 ..
-rw-r--r-- 1 shaurya shaurya   10 Oct  9 10:20 .env
drwxr-xr-x 3 shaurya shaurya 4.0K Oct  9 10:20 node_modules
-rw-r--r-- 1 shaurya shaurya  41K Oct  9 10:20 package-lock.json
-rw-r--r-- 1 shaurya shaurya  161 Oct  9 10:20 package.json
drwxr-xr-x 2 shaurya shaurya 4.0K Oct  9 10:20 scripts
-rw-r--r-- 1 shaurya shaurya  264 Oct  9 10:20 server.js
$ ls -lt              # newest first;  ls -ltr = oldest first
TokenMeaning
-lLong format (one file per line, with details)
-aAll: include hidden names, plus . (this dir) and .. (parent). That's how .env shows up.
-hHuman-readable sizes: 41K instead of 41324
-t / -rSort by modification time / reverse the order

What it does not do: change anything. Running ls (and pwd) before every destructive command is the cheapest safety habit on Linux.

Build it up

Create, copy, move, delete

$ mkdir -p /tmp/demo/a/b/c        # -p: create parents, no error if it exists (fixes error 1)
$ touch notes.txt                   # create an empty file / update its timestamp
$ cp server.js server.js.bak        # copy a file
$ cp -r scripts /tmp/demo/          # -r: copy a directory recursively (fixes error 2)
$ mv /tmp/demo/scripts/deploy.sh /tmp/demo/scripts/deploy-v2.sh   # move = rename
$ ls /tmp/demo/scripts
deploy-v2.sh
$ rm notes.txt                      # delete a file (no recycle bin!)
$ rm /tmp/demo
rm: cannot remove '/tmp/demo': Is a directory
$ rm -rf /tmp/demo                  # -r recursive, -f force: no prompts, no errors

If the target of mv or cp is an existing directory, the file goes inside it. Otherwise the target is the new name. Same command, two meanings, so ls first.

rm -rf has no undo

Double-check the path before pressing Enter, especially with variables. If $APP_DIR is empty, rm -rf "$APP_DIR"/* becomes rm -rf /*. Use rm -ri to confirm each file, and see set -u in Session 3.

Pack and unpack: tar

$ tar --exclude=node_modules -czvf taskflow-backup.tar.gz -C /opt taskflow
taskflow/
taskflow/package-lock.json
taskflow/.env
taskflow/package.json
taskflow/server.js
taskflow/scripts/
taskflow/scripts/deploy.sh
$ tar -tzf taskflow-backup.tar.gz | head -3        # -t: list contents without extracting
$ mkdir -p /tmp/restore && tar -xzvf taskflow-backup.tar.gz -C /tmp/restore   # -x extract into -C dir
tar flagMeaning
-c / -x / -tCreate / extract / list
-zgzip compression (.tar.gz); -j bzip2, -J xz
-v / -f fileVerbose (list files) / archive file name. f takes the next word, so it must come last in a bundle: -czvf name.tar.gz.
-C dirChange to dir first, so the archive stores taskflow/…, not /opt/taskflow/…
--exclude=PATTERNSkip matching paths. GNU tar applies it only to paths that come after it.

Put --exclude last and tar refuses:

$ tar -czvf b.tar.gz -C /opt taskflow --exclude=node_modules
tar: The following options were used after non-option arguments.  These options are positional and affect only arguments that follow them.  Please, rearrange them properly.
tar: --exclude 'node_modules' has no effect
tar: Exiting with failure status due to previous errors

To download a release onto the server: curl -fsSLO URL (-f fail on 4xx/5xx, -sS quiet but show errors, -L follow redirects, -O keep the remote file name) or wget URL.

Exam trap

"rm moves files to a trash can." ✗ On a server the file is gone. Only backups bring it back.

"tar -czvf makes a zip file." ✗ -z is gzip. A .tar.gz is a tar archive compressed with gzip, not a .zip.

Remember

-p parents · -r recursive · -f force (no questions, no undo).
tar: c create · x extract · t list · z gzip · v verbose · f file (always last).

Mastery check
Q1. Spot the bug: tar -cvfz backup.tar.gz taskflow

f takes the next word as the archive name, and the next word is z. tar creates an archive called z, then tries to add backup.tar.gz as a member: tar: backup.tar.gz: Cannot stat: No such file or directory, exit 2, and no compression. Fix: tar -czvf backup.tar.gz taskflow.

Q2. Predict: mv server.js old. What happens if old is an existing directory, and what if it doesn't exist?

Existing directory: the file moves inside, becoming old/server.js. No such name: server.js is renamed to a file called old.

Q3. Why does the backup command use -C /opt taskflow instead of just /opt/taskflow?

With -C /opt, paths inside the archive start at taskflow/, so you can extract it anywhere (-C /tmp/restore). Otherwise they'd start opt/taskflow/ (tar strips the leading /), which nests awkwardly wherever you unpack.

3 Reading & searching text

The problem

Users say GET /tasks "sometimes" fails. TaskFlow's access log on web-01 has two million lines, far too many to scroll or open in an editor. You need three numbers: how many 500s, from which clients, and how slow the failing requests were.

The idea

Linux gives you small tools that each do one job on text, line by line: show some lines, keep matching lines, cut out a column, sort, count. You chain them with a pipe, |, which sends one tool's output into the next one's input (the full story of pipes is in Session 3):

 access.log ─▶ awk '{print $5}' ─▶ sort ─▶ uniq -c ─▶ sort -rn ─▶ screen
 10 lines      200 200 201 404 …   200      5 200      5 200
               (column 5 only)     200 …    1 201      2 500
                                   (grouped)(counted)  (biggest first)

See it: the ends of a file

$ head -n 3 /var/log/taskflow/access.log   # first 3 lines
2026-10-09T10:15:02 203.0.113.7 GET /health 200 2ms
2026-10-09T10:15:04 198.51.100.23 GET /tasks 200 14ms
2026-10-09T10:15:09 203.0.113.7 POST /tasks 201 31ms
$ tail -n 2 /var/log/taskflow/access.log   # last 2 lines
2026-10-09T10:15:41 198.51.100.23 GET /tasks 500 91ms
2026-10-09T10:15:45 203.0.113.7 GET /tasks 200 13ms
$ tail -f /var/log/taskflow/app.log        # follow: print new lines as they arrive (Ctrl+C to stop)
$ less /var/log/syslog                     # page through: Space/b = page, /text = search, n = next, G = end, q = quit

-n 3 sets how many lines. -f keeps the file open and prints each new line as it's written, which is how you watch a live service. cat prints a whole file at once, so use it for short ones only. What these do not do: change the file. Reading tools are always safe.

Exam trap

"uniq removes all duplicate lines." ✗ Only adjacent ones, which is why you sort first.

"find -mtime +7 finds files changed in the last 7 days." ✗ +7 means more than 7 days ago. The last 7 days is -mtime -7.

"grep -v means verbose." ✗ It inverts the match: print lines that don't match.

Remember

Mastery check
Q1. Predict the output of grep -c "GET" access.log on the 10-line sample.

8. Every line except the two POSTs contains GET.

Q2. Write a one-liner that prints the most requested path, with its count.

awk '{print $4}' access.log | sort | uniq -c | sort -rn | head -1 → 7 /tasks. Same shape as the status-code pipeline, with field 4 instead of 5.

Q3. Spot the bug: in a directory containing app.log, you run find . -name *.log and it misses sub/old.log.

The shell expanded *.log to app.log before find ran, so find only looked for files named exactly app.log. Quote the pattern: find . -name "*.log".

4 Users & groups

The problem

A previous admin ran TaskFlow as root because "it was easier". Then a bug in one npm package let a request like GET /static/../../etc/shadow read any file. Because the process was root, the attacker could read every password hash on the server, and could have written anywhere too. One small bug became a full server compromise.

The idea

Every process runs as some user, and the kernel checks that user's rights on every file access. Users have a numeric UID. root (UID 0) skips the permission checks entirely. Services get their own unprivileged system users, so a bug can only reach what that user owns. Groups give several users shared access.

UID 0        root        skips permission checks: can read, write, kill anything
UID 1–999    system      service accounts: taskflow, postgres, www-data (no interactive login)
UID 1000+    humans      shaurya (1000), deploy (1001)

/etc/passwd  who exists           shaurya:x:1000:1000:Shaurya Verma:/home/shaurya:/bin/bash
/etc/shadow  their password hash  (readable by root only)
/etc/group   who is in which group  devs:x:1002:shaurya,deploy
Think of it like this

In the office building, every person and every robot wears an ID badge (UID) and belongs to departments (groups). Doors check the badge. root holds the master key. TaskFlow should be a contractor with a badge that opens only its own rented floor, so if it's tricked, the damage stays on that floor.

See it: who am I?

$ whoami

$ id
uid=1000(shaurya) gid=1000(shaurya) groups=1000(shaurya),27(sudo),1002(devs)

groups=…,27(sudo),1002(devs)Supplementary groups: sudo lets you run admin commands; devs is a team group

Managing users and groups

$ sudo useradd -m -s /bin/bash deploy        # -m create /home/deploy, -s login shell (default is /bin/sh)
$ sudo passwd deploy                         # set a password (prompts twice)
$ sudo groupadd devs
$ sudo usermod -aG devs,sudo deploy          # -a APPEND to the supplementary groups -G
$ id deploy
uid=1001(deploy) gid=1001(deploy) groups=1001(deploy),27(sudo),1002(devs)
$ sudo useradd --system --no-create-home --shell /usr/sbin/nologin taskflow   # service account, UID < 1000
$ sudo gpasswd -d deploy devs; sudo userdel -r deploy   # remove from one group; delete user + home

The -a in usermod -aG is the most important letter on this page. Without it, -G replaces the whole supplementary list. Here it silently removed sudo:

$ sudo usermod -G devs deploy
$ id deploy
uid=1001(deploy) gid=1001(deploy) groups=1001(deploy),1002(devs)

Exam trap

"The x in /etc/passwd means the user has no password." ✗ It means "the hash is in /etc/shadow". A locked account shows ! or * in shadow.

"sudo asks for root's password." ✗ It asks for yours. su asks for the target user's.

"usermod -G docker shaurya adds shaurya to docker." ✗ It replaces all supplementary groups. Use -aG.

Remember

passwd = who exists · shadow = password hashes · group = who's in what.
Every service gets its own nologin user. Always usermod -aG.

Mastery check
Q1. Decode: postgres:x:113:121:PostgreSQL administrator,,,:/var/lib/postgresql:/bin/bash

5 File permissions

The problem

$ ./deploy.sh
bash: ./deploy.sh: Permission denied
$ ssh -i taskflow-key.pem ubuntu@13.233.10.20
…
Permissions 0644 for 'taskflow-key.pem' are too open.

Two "permission" errors pointing opposite ways. The script is missing a permission it needs. The key has too many, and SSH refuses to use a private key that other users could read.

The idea

Every file has an owner, a group, and three sets of three bits: what the owner, the group and everyone else may do. r = read, w = write, x = execute. The kernel checks them in order, owner first: if you're the owner, only the owner bits count.

Think of it like this

Every door in the office building has three keyholes: one for its owner, one for the owner's department, one for visitors. A file is a document: r lets you read it, w write on it, x use it as a machine. A directory is a room: r lets you read the name plates, x lets you walk in, and w lets you put things in or take things out.

Exam trap

"chmod 777 fixes Permission denied." ✗ It works by letting everyone modify the file. Check ls -l on the file and each parent directory, then fix the owner (chown) or the group membership.

Mastery check
Q1. -rwxr-x--- 1 shaurya devs 35 Oct 9 deploy.sh. Can user deploy (a member of devs) edit it? Run it? Can user intern (not in devs) read it?

Mode 750. deploy gets the group bits r-x: it can read and run the script but not edit it. intern falls under others (---), so it can't even read it.

Q2. Predict: you run umask 027, then touch report.txt and mkdir logs. What modes do they get?

File: 666 − 027 → 640 (rw-r-----). Directory: 777 − 027 → 750 (rwxr-x---). Strictly the umask bits are masked off rather than subtracted, which only differs when a digit would go below zero.

Q3. TaskFlow (user taskflow) logs EACCES: permission denied, open '/var/log/taskflow/app.log'. The file is -rw-r--r-- root root. Fix it without 777.

The file belongs to root, and taskflow only gets the "others" bits r--. Give it to the service: sudo chown -R taskflow:taskflow /var/log/taskflow. Now the owner bits rw- apply, and nobody else gains write access.

6 Processes & signals

The problem

TaskFlow is stuck at 100% CPU. It was started by the system, not from your terminal, so there's no window to press Ctrl+C in. You need to find which process it is among the hundred or so on the box, and stop it, ideally without killing the requests it's in the middle of.

The idea

A process is a running instance of a program. Each has a PID, a parent (PPID), an owning user and a state. They form a tree rooted at systemd, PID 1. A daemon is a background process with no terminal. You talk to a process by sending it a signal, a small numbered message from the kernel such as "please exit" or "stop now".

systemd (PID 1)
├── sshd (812) ── sshd: shaurya (2201) ── bash (2210) ── top (2290)   ← your terminal session
├── cron (640)
└── node /opt/taskflow/server.js (4321)  user: taskflow, TTY: ?        ← a daemon, started by systemd

kill 4321      → SIGTERM (15): "please finish and exit"  → the app can clean up
kill -9 4321   → SIGKILL (9):  the kernel ends it now    → no cleanup, can't be caught
Think of it like this

Processes are workers in the building, each with a numbered job ticket (PID) and the name of whoever assigned the job (PPID). SIGTERM is a manager saying "finish what you're doing and go home". SIGKILL is security escorting them out mid-sentence. SIGHUP traditionally means "re-read the policy binder".

"kill -9 is the normal way to stop a process." ✗ It skips cleanup: logs aren't flushed, DB connections aren't closed, in-flight requests fail. Send kill (SIGTERM), wait about 10 s, and only then -9.

Mastery check
Q1. Predict: you run kill 4321 on TaskFlow, and on another day kill -9 4321. What appears in its log each time, and what happens to an in-flight request?

SIGTERM: the handler logs "SIGTERM received, shutting down", the request finishes, and the process exits 0. SIGKILL: nothing is logged, because the process never runs another instruction, and the in-flight request fails.

Q2. top shows load average 3.9. Is the server overloaded if nproc prints 4? If it prints 2?

On 4 CPUs it's busy but coping, with about one runnable process per CPU. On 2 CPUs about two processes are waiting for every CPU, so it's overloaded. Load only means something relative to the CPU count.

Q3. You run sleep 300 &, then fg, then Ctrl+Z, then bg. What state is the job in after each step?

Running in the background → running in the foreground (it holds your terminal) → Stopped (SIGTSTP, T in ps) → running in the background again (SIGCONT).

7 Services with systemd

The problem

Mon 14:00  you start TaskFlow with:  nohup node server.js &
Tue 02:14  it crashes on a bad request                → stays down until someone notices at 09:30
Thu 03:00  Ubuntu reboots for a kernel patch          → TaskFlow doesn't come back at all

The app itself is fine. Nothing is supervising it: nothing starts it at boot or restarts it when it dies.

The idea

systemd is PID 1 on Ubuntu, the first process and the parent of every service. It manages units described by small text files: .service (a daemon), .timer (a scheduled job), .socket, and .target (a group of units; multi-user.target is normal server boot). A service unit says how to start the program, as which user, with which environment, and what to do when it exits. You control units with systemctl and read their logs with journalctl. Packages install unit files in /usr/lib/systemd/system/; yours go in /etc/systemd/system/, which also overrides packaged ones.

boot ─▶ systemd (PID 1) ─▶ multi-user.target ─▶ taskflow.service ─▶ /usr/bin/node server.js (PID 4321)
                                   ▲                                         │ crashes (exit 1)
                    "enabled" = linked into this target                      ▼
                                                     Restart=on-failure: wait RestartSec=5 s, start again
Think of it like this

systemd is the building manager. Each unit file is a worker's contract: what job, whose badge, which shift. enable puts the worker on the morning roster, so they start when the building opens (boot). start calls them in right now. Restart=on-failure means that if they collapse, the manager sends a replacement within 5 seconds. And the manager keeps the diary (the journal).

See it: the smallest unit

/etc/systemd/system/taskflow.service (first version)
[Unit]
Description=TaskFlow API

[Service]
ExecStart=/usr/bin/node /opt/taskflow/server.js

[Install]
WantedBy=multi-user.target

Three sections: [Unit] describes it, [Service] says what to run, and [Install] says which boot target enable should attach it to. This already starts at boot once enabled. What it does not do: restart after a crash (the default is Restart=no), run as a non-root user (so you're back to section 4's root problem), load the DB password, or set the working directory. The real unit adds exactly those.

Mastery check
Q1. systemctl enable taskflow succeeded, but curl localhost:3000 fails. What did you forget?

enable only arranges a start at the next boot. Start it now with systemctl start taskflow, or use enable --now next time.

Q2. systemctl status shows status=203/EXEC. What's wrong?

Q3. Predict, with Restart=on-failure: (a) sudo kill -9 4321, (b) sudo systemctl stop taskflow, (c) the app calls process.exit(0).

Q4. Spot the bug: RestartSec=5 # wait five seconds

systemd only recognises comments at the start of a line, so the value becomes 5 # wait five seconds. It logs "Failed to parse sec value, ignoring" and falls back to the default delay. Move the comment onto its own line.

8 Logs

The problem

When TaskFlow ran in your terminal, its errors scrolled past on screen. Now it's a service with no terminal, so where does console.log go? And someone tried hundreds of SSH passwords overnight: where is that recorded? If you don't know where the logs are, every outage turns into guessing.

The idea

There are two kinds of log. systemd's journal captures the stdout and stderr of every service plus kernel messages, stored in a structured, indexed form that you query with journalctl. And there are classic text files in /var/log, written by rsyslog and by apps. You read the journal with filters (unit, time, priority) and the files with the tools from section 3.

                                   └─▶ rsyslog ──▶ /var/log/syslog, /var/log/auth.log, /var/log/kern.log
 nginx, apps writing files ─────────────────────▶ /var/log/nginx/, /var/log/taskflow/

Mastery check
Q1. TaskFlow crashed some time before last night's reboot. Which journalctl command shows its last lines from before the reboot?

journalctl -u taskflow -b -1 -n 50. -b -1 selects the previous boot (this needs a persistent journal, which Ubuntu has by default).

Q2. journalctl -u taskflow -p err says -- No entries --, but the app is clearly throwing errors. Why?

systemd logs everything a service prints at priority info, including stderr. Filtering to err hides the stack traces. Drop -p and grep for Error instead.

Q3. The TaskFlow process vanished with no error in its own log. Where do you look, and for what?

sudo dmesg -T | grep -i oom (or journalctl -k): the kernel's OOM killer leaves Out of memory: Killed process 4321 (node). A process killed with SIGKILL can't log anything itself.

9 Basic troubleshooting

The problem

Friday, 11:02, ten minutes after you deployed a new version:

$ curl -s localhost:3000/health || echo "DOWN"
DOWN

The temptation is to start changing things: reinstall, reboot, chmod 777. Don't. Ask questions in a fixed order, and each answer tells you where to look next.

The idea

Troubleshooting is a ladder that goes from cheap, broad checks to narrow ones. You've already met every tool on it:

1. Is it running?          systemctl status taskflow                 (section 7)
2. What did it say?        journalctl -u taskflow -n 50              (section 8)
3. Is the box healthy?     df -h · free -h · top                     (disk, memory, CPU)
4. Who has the port?       sudo ss -tulpn | grep 3000 · lsof -i :3000
5. Can it read its files?  ls -l on the file + every parent · id taskflow   (sections 4–5)

See it: walk the ladder

Mastery check
Q1. status shows activating (auto-restart) and status=1/FAILURE. What does that tell you, and what's your next command?

The process starts, exits with 1 (an app-level error), and systemd keeps restarting it: a crash loop. Next: journalctl -u taskflow -n 50 to read the error the app printed before exiting.

Q2. df -h says 99% full. You delete a 10 GB log with rm, and df still says 99%. Why, and how do you get the space back?

A process still has the file open, so the data stays on disk until that file handle closes. Find it with sudo lsof +L1, then restart that service. Next time use truncate -s 0.

Q3. curl localhost:3000 fails, but systemctl status taskflow says active (running). Which rung next, and what might you find?

Rung 4: sudo ss -tulpn | grep node to see which port and address it's actually listening on. Perhaps PORT in the env file is 8080, or the app bound to another interface. Then rung 2 (the logs) to confirm.

★ Putting it all together

The big idea

A production Linux box follows conventions: code in /opt/taskflow, config in /etc/taskflow, logs in /var/log/taskflow. TaskFlow runs as its own taskflow user with tight permissions (600 on the env file), as a systemd service that starts at boot and restarts on crashes. Stopping it means SIGTERM first, so it can shut down gracefully. When it breaks you climb the same ladder every time: systemctl status, journalctl -u taskflow, then disk, memory, ports and permissions. You'll use the same habits inside containers and Kubernetes pods.

Final mastery check — combine everything
Q1. After a deploy, the journal shows EACCES: permission denied, open '/var/log/taskflow/app.log' and status says activating (auto-restart). Explain both lines and fix it properly.

The app runs as taskflow (User=), but the deploy recreated the log file as root, so taskflow only has the "others" bits and can't write. The app exits with an error, and Restart=on-failure keeps restarting it: a crash loop. Fix the ownership with sudo chown -R taskflow:taskflow /var/log/taskflow, then sudo systemctl restart taskflow. Not chmod 777.

Q2. You edit taskflow.service to add Environment=PORT=8080, run systemctl restart taskflow, and curl localhost:8080 fails while curl localhost:3000 works. Why, and which command proves the port?

systemd is still using the old unit, because you skipped daemon-reload (restart even printed a warning). sudo ss -tulpn | grep node shows it still listening on *:3000. Run sudo systemctl daemon-reload, then restart.

Q3. sudo systemctl stop taskflow takes exactly 90 seconds every time. What's happening, and how do you confirm it?

stop sends SIGTERM and waits up to TimeoutStopSec (90 s by default) before SIGKILL. The app isn't exiting on SIGTERM: perhaps the handler is missing or server.close() never finishes. journalctl -u taskflow will show State 'stop-sigterm' timed out. Killing. and no "SIGTERM received" line.

Q4. Using only commands from this page, find the client IP with the most failed SSH logins and check whether it ever logged in successfully.

sudo grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head -1 gives the top IP. Then sudo grep "Accepted" /var/log/auth.log | grep 203.0.113.50: no output means it never got in.

Q5. Write the five commands, in order, that create a deploy user, let them run admin commands and read the team folder, and verify it, without breaking their existing groups.

sudo useradd -m -s /bin/bash deploy → sudo passwd deploy → sudo usermod -aG sudo,devs deploy (with -a!) → sudo chgrp devs /srv/shared && sudo chmod 2775 /srv/shared → id deploy. They need to log in again for the groups to apply.

Q6. The server rebooted overnight. TaskFlow is up, but /tmp/taskflow-uploads is empty and yesterday's backups are gone. What went wrong, and where should each have lived?

/tmp is emptied at boot. The service itself came back because it's enabled. Uploads are app data, so they belong in /var/lib/taskflow (or /opt/taskflow/data). Backups belong in /var/backups/taskflow, owned by the right user with a private mode such as 700.
