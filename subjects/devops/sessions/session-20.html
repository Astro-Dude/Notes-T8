1 What is Infrastructure as Code?

Explain like I'm 5

Instead of building a Lego house from memory every time, you write the instruction booklet once. Anyone can rebuild the exact same house from it.

Infrastructure as Code (IaC) = servers, networks, databases and DNS described in text files, kept in Git, and created by a tool instead of by clicking in a web console.

ClickOps (console clicking) problemHow IaC fixes it
Dev and prod drift apart; nobody remembers which boxes were tickedRepeatable: same files → same infra, every environment
Someone opens port 22 to the world; nobody noticesReviewable: infra changes go through PRs and terraform plan
"Who changed the security group last Tuesday?"Versioned: git log / git revert
Running a setup script twice creates two VPCsIdempotent: apply twice → second run changes nothing
Rebuilding after a region outage takes daysAutomatable: one terraform apply in CI
Forgotten test servers keep billingterraform destroy removes everything it created

Declarative vs imperative

Imperative (AWS CLI script) — how, step by step. Run it twice, get two VPCs:

$ aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query Vpc.VpcId --output text
vpc-0a1b2c3d4e5f67890
$ aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query Vpc.VpcId --output text
vpc-0f9e8d7c6b5a43210      # oops — a second, duplicate VPC

Declarative (Terraform) — what the end state is. The tool works out the steps and does nothing if it already matches:

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

Recap IaC = infra in versioned files. Terraform is declarative and idempotent: you describe the end state, it computes and applies the difference.

2 Terraform architecture & HCL

Explain like I'm 5

Terraform Core is the project manager, providers are translators who speak "AWS" or "Docker", and the state file is the manager's notebook of what's already built.

Terraform loads every *.tf file in the folder as one configuration. File names (main.tf, variables.tf…) are convention only; order inside and across files doesn't matter.

Recap Core builds a graph and a diff; providers talk to APIs; state remembers real IDs. HCL = blocks with labels, argument = expression, nested blocks.

3 Providers

Explain like I'm 5

A provider is a travel adapter: Terraform has one plug shape, and each provider converts it to the socket of one platform.

  • A provider is a plugin that knows one API: hashicorp/aws, hashicorp/azurerm, hashicorp/google, hashicorp/kubernetes, kreuzwerker/docker, integrations/github…
  • Address = registry.terraform.io/NAMESPACE/TYPE, written short as NAMESPACE/TYPE. Tiers: official (HashiCorp), partner, community.
  • The provider's type is the prefix of its resources: provider aws → aws_instance, aws_vpc; provider docker → docker_container.

The hands-on project for this page — an nginx container managed by Terraform (needs only Docker running locally):

tf-docker-demo/
├── providers.tf        terraform {} block + provider "docker"
├── variables.tf        inputs (§5)
├── main.tf             resources (§4)
├── outputs.tf          values printed after apply (§5)
├── terraform.tfvars    values for the inputs (§5)
├── .terraform.lock.hcl created by init — COMMIT it
└── .terraform/         created by init — provider binaries, DON'T commit
tf-docker-demo/providers.tf
terraform {
  required_version = ">= 1.10.0"          # refuse to run on an older Terraform CLI

  required_providers {
    docker = {                            # local name used in this config
      source  = "kreuzwerker/docker"      # registry.terraform.io/kreuzwerker/docker
      version = "~> 4.0"                  # any 4.x, never 5.0
    }
  }
}

provider "docker" {
  # host defaults to $DOCKER_HOST, else unix:///var/run/docker.sock (Docker Desktop / Linux)
  # Colima users: host = "unix:///Users/shaurya/.colima/default/docker.sock"
}
ConstraintAllowsTypical use
= 4.6.0 (or "4.6.0")Exactly 4.6.0Rarely — blocks patches
>= 1.10.01.10.0 and anything newerrequired_version
~> 4.0≥ 4.0, < 5.0 (rightmost number may grow)Providers — new features, no breaking major
~> 4.6.0≥ 4.6.0, < 4.7.0 (patches only)Very cautious pinning
>= 5.0, < 7.0A rangeModules supporting two majors

The constraint says what's allowed; .terraform.lock.hcl records what was actually chosen (exact version + checksums), so your teammate and CI get the same 4.6.0. terraform init -upgrade moves to the newest allowed version and rewrites the lock file.

The AWS provider (used from Session 21)

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "ap-south-1"            # Mumbai — every resource below is created here
  # profile = "taskflow"           # optional named profile from ~/.aws/credentials
}

Where the AWS provider finds credentials (first match wins): provider arguments → env vars AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY / AWS_SESSION_TOKEN → ~/.aws/credentials + ~/.aws/config (written by aws configure or aws sso login) → EC2/ECS role. In CI use OIDC (Session 19).

Common mistake

Writing access_key = "AKIA…" and secret_key = "…" inside provider "aws". The keys end up in Git history (see secret scanning, Session 19). Keep credentials in env vars or ~/.aws/, never in .tf files.

Recap Declare providers in required_providers with source + ~> constraint, configure them in provider blocks, commit the lock file, keep credentials out of code.

4 Resources & data sources

Explain like I'm 5

A resource is "please build this". A data source is "please look this up for me" — Terraform only reads it, never builds or deletes it.

  • Syntax: resource "<TYPE>" "<NAME>" { … }. The address is TYPE.NAME (e.g. docker_container.web) and must be unique in the folder.
  • Arguments = what you set (name, ports). Attributes = what the provider reports back, often only after creation (id, image_id) — shown as (known after apply) in a plan.
  • Reference an attribute with TYPE.NAME.ATTRIBUTE.
tf-docker-demo/main.tf
# = docker pull nginx:1.27-alpine
resource "docker_image" "nginx" {
  name         = "nginx:${var.nginx_tag}"     # "nginx:1.27-alpine" from terraform.tfvars
  keep_locally = false                        # terraform destroy also removes the image
}

# = docker run -d --name taskflow-web --restart unless-stopped -p 8080:80 nginx:1.27-alpine
resource "docker_container" "web" {
  name    = var.container_name
  image   = docker_image.nginx.image_id         # reference → implicit dependency on the image
  restart = "unless-stopped"

  ports {
    internal = 80                             # nginx listens on 80 inside the container
    external = var.external_port              # host port (8080)
  }
}
LineMeaning
resource "docker_image" "nginx"Type from the docker provider; nginx is our local name (not the Docker name).
image = docker_image.nginx.image_idUses the image's ID attribute (sha256:…). Because of this reference, Terraform pulls the image first and replaces the container if the image changes.
ports { }Nested block, repeatable (one block per published port). Same as -p 8080:80.
restartDocker restart policy (Session 6).

Dependencies

ImplicitExplicit (depends_on)
HowOne resource references another's attributedepends_on = [aws_route_table_association.public]
WhenAlmost always (preferred)Hidden dependency Terraform can't see in the arguments
Examplecontainer → docker_image.nginx.image_idEC2 whose user_data runs apt-get needs the internet route to exist first, but never references it (Session 21)

Terraform builds a graph from these edges, creates independent resources in parallel (default 10 at a time), and destroys in reverse order. See it with terraform graph.

count and for_each (many copies from one block)

resource "docker_container" "worker" {
  count = 3                                     # docker_container.worker[0], [1], [2]
  name  = "taskflow-worker-${count.index}"      # taskflow-worker-0, -1, -2
  image = docker_image.nginx.image_id
}

resource "docker_container" "env" {
  for_each = { blue = 8081, green = 8082 }      # docker_container.env["blue"], ["green"]
  name     = "taskflow-web-${each.key}"         # each.key = blue | green
  image    = docker_image.nginx.image_id
  ports {
    internal = 80
    external = each.value                       # each.value = 8081 | 8082
  }
}

Instances identified byIndex [0], [1]Key ["blue"]
Remove a middle itemLater items shift index → get destroyed and recreatedOnly that one is destroyed
Best forN identical copies; on/off switch count = var.enabled ? 1 : 0Copies that differ by name/config

Data sources

A taste of AWS (Session 21 builds on it): look up the account ID, then use it in a globally unique bucket name.

aws-demo/main.tf
data "aws_caller_identity" "current" {}        # read-only: who am I? (account_id, arn)

resource "aws_s3_bucket" "logs" {
  bucket = "taskflow-logs-${data.aws_caller_identity.current.account_id}"   # bucket names are global
}

resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id                 # implicit dependency: bucket first
  versioning_configuration {
    status = "Enabled"
  }
}

Other common data sources: data "aws_ami" (latest Ubuntu image ID), data "aws_availability_zones", data "aws_vpc" (an existing VPC). In a plan they show as <= read (data resources) or just Reading… Read complete.

lifecycle { } argumentEffect
prevent_destroy = trueAny plan that would destroy it errors out (state bucket, prod DB).
create_before_destroy = trueOn replacement, create the new one first (+/-) → less downtime.
ignore_changes = [tags]Don't fight changes made outside Terraform to these arguments.
Recap resource "TYPE" "NAME" creates; data reads. References create the dependency graph; depends_on only for hidden dependencies; prefer for_each over count for named items.

5 Variables, locals & outputs

Explain like I'm 5

Variables are the blanks on a form, .tfvars is the filled-in form, outputs are the receipt Terraform hands back.

tf-docker-demo/variables.tf
variable "container_name" {
  description = "Name of the nginx container"   # shown in prompts and docs
  type        = string
  default     = "taskflow-web"                  # optional: no default → value is required
}

variable "external_port" {
  description = "Host port mapped to nginx's port 80"
  type        = number
  default     = 8080

  validation {                                  # checked at plan time
    condition     = var.external_port >= 1024 && var.external_port <= 65535
    error_message = "external_port must be between 1024 and 65535."
  }
}

variable "nginx_tag" {
  description = "nginx image tag"
  type        = string
  default     = "1.27-alpine"
}

variable "db_password" {                        # not used by nginx — shows a secret input
  description = "Example secret; set via TF_VAR_db_password"
  type        = string
  sensitive   = true                            # hidden in plan/apply output
  default     = null
}
FieldMeaning
typestring, number, bool, list(string), set(string), map(string), object({ name = string, port = number }), any. Wrong type → error before anything runs.
defaultUsed when no value is given. Without one, Terraform prompts (var.x Enter a value:) or fails in CI.
validationcondition must be true, else error_message is shown. Several blocks allowed.
sensitive = truePrints (sensitive value) in plans. Still stored in plain text in state.
tf-docker-demo/terraform.tfvars
# Loaded automatically. Non-secret values only — this file is committed.
container_name = "taskflow-web"
external_port  = 8080
nginx_tag      = "1.27-alpine"

Ways to set a variable — precedence (later wins)

  1. default in the variable block
  2. Environment variable TF_VAR_external_port=9000
  3. terraform.tfvars, then terraform.tfvars.json
  4. *.auto.tfvars / *.auto.tfvars.json (alphabetical)
  5. -var 'external_port=9090' and -var-file=prod.tfvars on the command line, in the order given
Example: which port wins?

default 8080, export TF_VAR_external_port=9000, terraform.tfvars says 8081, and you run terraform apply -var external_port=9090 → 9090. Drop the -var → 8081 (tfvars beats env vars).

Locals

locals {

Common mistakes

Leaving out sensitive = true on that output → Error: Output refers to sensitive values.
Thinking sensitive means encrypted: it only hides console output. terraform output -raw db_password and the state file both show it in plain text.

Recap variables.tf declares inputs (type, default, validation, sensitive); terraform.tfvars fills them; CLI -var wins. Locals de-duplicate; outputs expose results (-raw for scripts).

Common mistakes

-auto-approve on your laptop skips the only human check — fine in CI after a reviewed plan, risky otherwise.
-target=docker_container.web applies a slice of the config and can leave state inconsistent; use only to recover from errors.
Running plan before init → Error: Inconsistent dependency lock file / Required plugins are not installed. Run terraform init.

Recap init (providers + backend) → fmt/validate → plan -out=tfplan (read the summary line and symbols) → apply tfplan → destroy. Re-running with no changes is a no-op.

Explain like I'm 5

FieldMeaning
version / terraform_versionState file format (4) and the CLI that last wrote it.
serialIncremented on every write; a stale copy with a lower serial is refused.
lineageUnique ID of this state's history, so states of different projects can't be mixed up.

attributes.idThe real object's ID: the link between your code and the running container.

Why state existsDetail
MappingConfig address ↔ real ID. Without it Terraform can't tell "my container" from any other.
MetadataDependencies, so it can destroy in the right order even after you delete the code.
PerformanceCached attributes; large setups can skip slow API reads.
CollaborationWith a shared, locked backend, the whole team works on one source of truth.
Never commit state to Git

It contains every attribute in plain text, including DB passwords and private keys. Two people applying from their own copies overwrite each other. Use a remote backend instead.

Remote backend: S3 with locking

Create the bucket once, by hand (chicken-and-egg: the backend must exist before Terraform can use it):

$ aws s3api create-bucket --bucket shauryav-taskflow-tfstate --region ap-south-1 \
    --create-bucket-configuration LocationConstraint=ap-south-1
{
    "Location": "http://shauryav-taskflow-tfstate.s3.amazonaws.com/"
}
$ aws s3api put-bucket-versioning --bucket shauryav-taskflow-tfstate \
    --versioning-configuration Status=Enabled      # every state write kept → recover from mistakes
infra/backend.tf
terraform {
  backend "s3" {
    bucket       = "shauryav-taskflow-tfstate"        # must already exist
    key          = "taskflow/dev/terraform.tfstate"   # object path; one key per environment
    region       = "ap-south-1"
    encrypt      = true                               # server-side encryption of the state object
    use_lockfile = true                               # lock via an S3 .tflock object (Terraform ≥ 1.10)
    # dynamodb_table = "terraform-locks"              # OLD way: DynamoDB table with key "LockID" — deprecated
  }
}
ArgumentMeaning
bucket / keyWhere the state object lives: s3://shauryav-taskflow-tfstate/taskflow/dev/terraform.tfstate.
use_lockfileBefore writing, Terraform creates …/terraform.tfstate.tflock with a conditional write; a second apply fails instead of corrupting state. Needs s3:GetObject/PutObject/DeleteObject on that key.
dynamodb_tablePre-1.10 locking. Still works, deprecated; new projects use use_lockfile.

★ Putting it all together

The big idea

Terraform turns infrastructure into reviewed, versioned code. You declare providers and resources in HCL, feed them variables, and read results from outputs. init fetches the provider plugins, plan diffs config against state and reality, apply makes the change and records real IDs in state. Because state is Terraform's memory (and full of secrets), it lives in a locked, versioned S3 bucket, never in Git. Session 21 uses exactly this workflow to build a VPC and an EC2 instance running TaskFlow.

Quick self-check

Which versions does version = "~> 5.0" allow? And "~> 5.31.0"?

~> 5.0: ≥ 5.0 and < 6.0. ~> 5.31.0: ≥ 5.31.0 and < 5.32.0 (patches only).

What does -/+ mean in a plan, and what causes it?

Destroy then create a replacement. An argument the API can't change in place was modified (marked # forces replacement), e.g. the container image or an EC2 AMI.

Which of these go into Git: main.tf, .terraform/, .terraform.lock.hcl, terraform.tfstate, tfplan?

Commit main.tf and .terraform.lock.hcl. Ignore .terraform/ (binaries), terraform.tfstate (secrets, conflicts) and tfplan.

default = 8080, TF_VAR_external_port=9000, terraform.tfvars = 8081, CLI -var external_port=9090. Which value is used?

9090. CLI flags have the highest precedence; without it, 8081 (tfvars beats env vars, which beat the default).

Implicit vs explicit dependency — when do you need depends_on?

Implicit comes from referencing another resource's attribute (preferred). Use depends_on only when a resource needs another one to exist but doesn't reference it, e.g. an EC2 whose boot script needs the internet route.

Someone deleted the container with docker rm -f. What does the next terraform plan show?

"Objects have changed outside of Terraform … has been deleted", then a plan to create it again (1 to add). apply restores it; -refresh-only would just update state.

Why lock state, and how does the S3 backend do it on Terraform ≥ 1.10?

Two concurrent applies would overwrite each other's state. use_lockfile = true creates a .tflock object with a conditional write; a second run gets "Error acquiring the state lock".
