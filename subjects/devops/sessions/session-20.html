1 What is Infrastructure as Code?

The problem: ClickOps

You build TaskFlow's dev environment in the AWS console: a VPC, two subnets, a security group and an EC2 instance. That's about 40 clicks, and none of them is written down. Then the requests start:

Week 1    dev built by hand in the console             no record of what was clicked
Week 3    "make staging identical to dev"              which boxes did you tick?
Week 5    port 22 is open to 0.0.0.0/0                 who changed it, and when?
Week 8    the region has an outage                     rebuild everything from memory
Month 6   a forgotten test server is still billing     nobody knew it existed

All five are the same bug. The infrastructure exists only as the result of clicks, and you can't diff, review or replay clicks.

The idea

Infrastructure as Code (IaC) means describing servers, networks, databases and DNS in text files, keeping the files in Git, and letting a tool create the real thing from them. The files become the source of truth. Changing the infrastructure means changing a file, so it goes through a pull request like any other code.

 ClickOps                                     Infrastructure as Code
 you ──clicks──▶ console ──▶ dev              you ──edit──▶ main.tf ──git push──▶ PR + review
     ──clicks──▶ console ──▶ staging ≠ dev                                          │
     (no history, can't be repeated)                         terraform plan   (preview the diff)
                                                                                    │
                                                             terraform apply ───────┼──▶ dev
                                                                                    ├──▶ staging   same files
                                                                                    └──▶ prod      = same infra
Think of it like this

ClickOps is building a house by standing on site shouting "wall here, window there". IaC is handing the builder an architect's blueprint: anyone can build the identical house from it, two versions can be compared line by line, and it still shows what the house should look like after someone knocks a hole in a wall. This page keeps the picture: your .tf files are the blueprint, Terraform is the contractor.

See it: imperative vs declarative

There are two ways to write infrastructure down. The imperative way is a list of steps, for example AWS CLI commands. Run the same "create a VPC" line twice:

$ aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query Vpc.VpcId --output text
vpc-0a1b2c3d4e5f67890
$ aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query Vpc.VpcId --output text
vpc-0f9e8d7c6b5a43210      # a second, duplicate VPC

aws ec2 is the CLI's EC2 API (VPCs live there), create-vpc always creates a new VPC, --cidr-block is the range (Session 4), and --query … --output text prints just the ID. The script says how and has no idea a VPC already exists. The declarative way says what should exist:

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

Terraform compares this with what it built before. The first run creates the VPC. The second run finds that reality already matches and prints No changes. (you'll see it happen in section 6). That property is called idempotency: running again without edits changes nothing.

What it does not do: a .tf file on its own does nothing. It's only a description. Nothing happens until Terraform reads it and you approve the plan.

Build it up: what IaC buys you

Each pain maps to a property: repeatable (staging = dev, same files), reviewable (port 22 caught in a PR and a plan), versioned (git log answers who and when), idempotent (safe to run twice), automatable (the outage rebuild and the forgotten server are one apply or destroy away).

Exam trap

"Terraform and Ansible do the same job." ✗ Terraform provisions (the VPC, the instance); Ansible configures machines that exist. Teams use both.

"A Bash script of AWS CLI commands is declarative IaC." ✗ It's code, but imperative: a second run creates duplicates.

"Idempotent means the tool refuses to run twice." ✗ It runs every time and changes nothing when reality already matches.

Remember

Imperative = HOW (a list of steps) · Declarative = WHAT (the end state)
Provisioning = which machines exist · Config management = what's on them

Mastery check
Q1. A script creates a VPC, a subnet and an EC2 instance with AWS CLI commands. You run it twice, then apply the equivalent Terraform config twice. How many VPCs exist in each case?

Script: two of everything, because every create-* call makes a new object. Terraform: one of each, because the second apply finds nothing to change.

Q2. Provisioning or configuration management? (a) Terraform for an S3 bucket, (b) Ansible installing Docker on three servers, (c) a CloudFormation VPC, (d) a boot script running docker run.

(a) and (c) provision. (b) and (d) configure software on machines that already exist.

Q3. True or false: "Kubernetes YAML isn't IaC, because kubectl applies it step by step."

False. A manifest is declarative desired state (Session 9): you write "3 replicas" and controllers keep making it true. Same idea as Terraform, for objects inside a cluster.

2 Terraform architecture & HCL

The problem

AWS alone has hundreds of services, each with its own API. Add Azure, GCP, Docker, Kubernetes and GitHub. How can one terraform binary speak all of those APIs? And when you run it again next week, how does it know what it already built?

The idea

Terraform splits the work three ways. Terraform Core (the terraform binary) reads your .tf files, builds a dependency graph and works out what must change, but it knows nothing about AWS. Providers are separate plugins, one per platform, that turn "create an aws_vpc" into real API calls. The state records what was built, so next week Core has something to compare against.

   *.tf files ─────┐
   (desired state)  ▼
             ┌─────────────────┐   reads/writes   ┌───────────────────────────┐
  you ─────▶ │ Terraform Core  │◀───────────────▶ │ State (terraform.tfstate) │
  terraform  │ (the CLI binary)│                  │ local file or S3 backend  │
  plan/apply │ graph + diff    │                  └───────────────────────────┘
             └───────┬─────────┘
                     │ gRPC plugin protocol
        ┌────────────┼──────────────────┬──────────────────────┐
        ▼            ▼                  ▼                      ▼
  hashicorp/aws  kreuzwerker/docker  hashicorp/kubernetes     …   (providers, downloaded by init)
        │            │                  │
        ▼            ▼                  ▼
    AWS APIs    Docker daemon      K8s API server                  (real infrastructure)
Think of it like this

The .tf files are the blueprint. Core is the general contractor: it reads the blueprint and writes the work order but lays no bricks. Providers are specialist crews, each speaking one site's language (AWS, Docker). State is the contractor's logbook: "blueprint item web = container 7d3e…".

Where state is kept and locked is the backend's job: local disk by default, S3 in section 8.

See it: HCL, the language

You write Terraform in HCL (HashiCorp Configuration Language). Everything is a block: a type, some labels, then a body in braces.

# block type  label 1 (resource type)  label 2 (your local name)
resource      "aws_s3_bucket"          "logs" {
  bucket        = "taskflow-logs-${var.environment}"   # argument = expression; "${…}" inserts a value
  force_destroy = var.environment != "prod"            # a bool expression

  tags = {                                             # a map argument: it HAS an "="
    Project = "taskflow"
  }

  lifecycle {                                          # a nested block: NO "=" sign
    prevent_destroy = false
  }
}
// comments: #, // or /* … */

You can try expressions without any cloud at all. terraform console is an interactive calculator for HCL. This folder only contains variable "environment" { default = "dev" }:

$ terraform console
> "taskflow-${var.environment}"
"taskflow-dev"
> var.environment == "prod" ? 3 : 1
1
> length(["ap-south-1a", "ap-south-1b"])
2
> cidrsubnet("10.0.0.0/16", 8, 1)
"10.0.1.0/24"
> exit

That's interpolation, a conditional, a function on a list, and a networking function you'll need in Session 21. What it does not do: console never creates or changes anything. It only evaluates expressions.

Build it up: the block types you'll meet

BlockPurposeSection
terraform { }Required Terraform and provider versions, the backend3, 8
provider "aws" { }Configure a provider (region, profile)3
resource "type" "name" { }Something Terraform creates and manages4
data "type" "name" { }Read something that already exists4
variable / locals / outputInputs / internal named values / results printed after apply5
import / moved / moduleAdopt existing infra / rename without destroying / reuse a folder of .tf7

Terraform loads every *.tf file in the folder as one configuration. Names like main.tf are only a convention, and block order doesn't matter. The workflow for the rest of the page is init (§3) → plan → apply → destroy (§6).

Exam trap

"Terraform runs main.tf top to bottom, so the VPC must come first." ✗ It reads all the .tf files at once and orders the work by the dependency graph (section 4).

"Terraform Core calls the AWS API." ✗ Core never talks to a cloud. The provider plugin makes every API call.

Remember

Core = plans · Providers = talk to APIs · State = remembers
All *.tf files in one folder = one configuration; order doesn't matter.

Mastery check
Q1. AWS launches a new service. To manage it with Terraform, do you upgrade Core or the AWS provider?

The AWS provider. Core is generic; each resource type lives in the provider plugin, which is released separately.

Q2. Spot both bugs: resource "aws_s3_bucket" "logs" { tags { Project = "taskflow" } lifecycle = { prevent_destroy = true } }

tags is a map argument: write tags = { … } (Terraform says Unsupported block type … use the equals sign). lifecycle is a nested block: no = (otherwise Unsupported argument).

Q3. Fill in: in resource "aws_vpc" "main", aws_vpc is the ________ (from the ________ provider), main is the ________, and other blocks refer to it as ________.

Resource type · aws · local name · aws_vpc.main (for example aws_vpc.main.id).

3 Providers & terraform init

The problem

Your teammate clones the repo, opens the Terraform folder and runs a plan straight away:

$ terraform plan
╷
│ Error: Required plugins are not installed
│
│ The installed provider plugins are not consistent with the packages
│ selected in the dependency lock file:
│   - registry.terraform.io/kreuzwerker/docker: there is no package for registry.terraform.io/kreuzwerker/docker 4.6.0 cached in .terraform/providers
│ …
│   terraform init
╵

Every .tf file is there. So what's missing, and how does the error already know the exact version, 4.6.0?

The idea

A provider is a separate program (a plugin binary) that Core starts and talks to. Your config only names the providers it needs and which versions are acceptable, in a required_providers block. terraform init downloads them from the Terraform Registry into a hidden .terraform/ folder, and records the exact version it picked, with checksums, in .terraform.lock.hcl.

 providers.tf                              registry.terraform.io
 required_providers {                     ┌───────────────────────────────┐
   docker = {                             │ kreuzwerker/docker            │
     source  = "kreuzwerker/docker" ─────▶│   3.x … 4.5.0  4.6.0 ✔ newest │
     version = "~> 4.0"                   │ hashicorp/aws   5.x  6.x      │
   }                                      └───────────────┬───────────────┘
 }                                   terraform init:      │ download + verify checksum
                                                          ▼
   .terraform/providers/…/docker/4.6.0/darwin_arm64/   the binary          → git-ignored
   .terraform.lock.hcl   version = "4.6.0" + hashes    the exact choice    → COMMITTED
Think of it like this

init hires the crews named in the contract from an agency, the Terraform Registry. The version constraint is the job ad: "any 4.x Docker crew". The lock file records exactly whom you hired (4.6.0, plus an ID check), so your teammate and CI get the same crew instead of whoever is newest that day.

See it: one provider, one init

This page's project is an nginx container managed by Terraform. It only needs Docker running on your laptop:

tf-docker-demo/
├── providers.tf          terraform {} block + provider "docker"   (this section)
├── main.tf               resources                                (§4)
├── variables.tf          inputs                                   (§5)
├── terraform.tfvars      values for the inputs                    (§5)
├── outputs.tf            values printed after apply               (§5)
├── .terraform.lock.hcl   written by init: COMMIT it
└── .terraform/           written by init: provider binaries, DON'T commit
tf-docker-demo/providers.tf
terraform {
  required_version = ">= 1.10.0"          # refuse to run on an older Terraform CLI

  required_providers {
    docker = {                            # local name used in this config
      source  = "kreuzwerker/docker"      # = registry.terraform.io/kreuzwerker/docker
      version = "~> 4.0"                  # any 4.x, never 5.0
    }
  }
}

provider "docker" {
  # host defaults to $DOCKER_HOST, else unix:///var/run/docker.sock (Docker Desktop / Linux)
  # Colima users: host = "unix:///Users/shaurya/.colima/default/docker.sock"
}

source is NAMESPACE/TYPE on the Registry, whose providers come in tiers: official (hashicorp/aws), partner, community (kreuzwerker/docker). The type is the prefix of its resources: docker_image, aws_vpc.

That solves the puzzle: the clone had the committed lock file but not the git-ignored .terraform/, so plan knew the version and couldn't find it. terraform init installs exactly 4.6.0. What it does not do: init creates no container and never contacts Docker. It only prepares the folder (providers, modules, backend), so it's always safe to re-run, and needed again after adding a provider or module or changing the backend.

Build it up

Version constraints

ConstraintAllowsTypical use
= 4.6.0 (or "4.6.0")Exactly 4.6.0Rarely: it blocks patches
>= 1.10.01.10.0 and anything newerrequired_version

The lock file

tf-docker-demo/.terraform.lock.hcl
# This file is maintained automatically by "terraform init".
# Manual edits may be lost in future updates.

provider "registry.terraform.io/kreuzwerker/docker" {
  version     = "4.6.0"                 # exact version chosen
  constraints = "~> 4.0"                # copied from required_providers
  hashes = [                            # checksums: a tampered binary fails init
    "h1:Qm7tZ0vXc4yP2kR9mJ1sL8wN3bF6hD5aE0uT7iY2oGk=",
    "zh:0a3c5e9f2b7d1c8e4a6f0b2d9c7e5a3f1b8d6c4e2a0f9b7d5c3e1a8f6b4d2c0e",
    # … one zh: hash per OS/architecture …
  ]
}

The constraint says what's allowed. The lock file says what was chosen. To move to a newer allowed version on purpose, run terraform init -upgrade, which rewrites the lock file, then commit it.

The AWS provider (used in Session 21)

Declared the same way, aws = { source = "hashicorp/aws", version = "~> 5.0" }, and configured with a region:

provider "aws" {
  region = "ap-south-1"            # Mumbai: every resource below is created here
  # profile = "taskflow"           # optional named profile from ~/.aws/credentials
}

Credentials, first match wins: provider arguments → env vars AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY / AWS_SESSION_TOKEN → ~/.aws/credentials + ~/.aws/config (from aws configure or aws sso login) → the machine's IAM role (EC2/ECS). In CI, use OIDC (Session 19).

Exam trap

"Add .terraform.lock.hcl to .gitignore." ✗ Commit the lock file. Ignore .terraform/, which holds the downloaded binaries.

"Put access_key = "AKIA…" in the provider block so it just works." ✗ The key ends up in Git history, where secret scanners and attackers find it (Session 19). Use environment variables, ~/.aws/ or OIDC.

Remember

required_providers = what you need · init = download it · lock file = exactly what you got (commit it)
~> 4.0 = any 4.x, never 5.0

Mastery check
Q1. Which versions does version = "~> 5.0" allow? And "~> 5.31.0"?

~> 5.0: ≥ 5.0 and < 6.0. ~> 5.31.0: ≥ 5.31.0 and < 5.32.0 (patches only). Only the rightmost number you wrote may grow.

Q2. Your laptop uses docker provider 4.6.0, the CI runner installed 4.7.1, and the plans differ. What wasn't committed, and what's the fix?

The lock file. Commit .terraform.lock.hcl and CI's init installs exactly 4.6.0. Upgrade on purpose with terraform init -upgrade in a PR.

Q3. You add hashicorp/aws to required_providers and run terraform plan. Predict the result.

Error: Inconsistent dependency lock file … hashicorp/aws: required by this configuration but no version is selected. Run terraform init: it downloads the provider and adds it to the lock file.

4 Resources & data sources

The problem

Here's TaskFlow's web server the way you started it by hand in Session 6:

$ docker pull nginx:1.27-alpine
$ docker run -d --name taskflow-web --restart unless-stopped -p 8080:80 nginx:1.27-alpine

That's two imperative steps. For Terraform to create it, change it, and one day delete it, you describe the end state instead: "an image nginx:1.27-alpine exists, and a container named taskflow-web runs it on port 8080".

The idea

A resource block says "this object should exist". In resource "TYPE" "NAME" the type comes from a provider and the name is your label; together they form the address docker_container.web, unique in the folder. Arguments are what you set. Attributes are what the provider reports back once the object exists (id, image_id). Using another resource's attribute is also a dependency, and Terraform orders the work by it.

                         you set (arguments)               provider reports back (attributes)
 docker_image.nginx      name = "nginx:1.27-alpine"   ──▶   image_id = "sha256:4c1c…"
          │                                                          │
          │  reference: image = docker_image.nginx.image_id  ◀───────┘
          ▼  (this is also a dependency edge)
 docker_container.web    image, name, restart, ports  ──▶   id = "7d3e5f…"

 apply order:   image, then container        destroy order:   container, then image
Think of it like this

A resource is a line in the blueprint: "build a container like this". A data source is "look up where the city's water main is and tell me": the contractor reads it but never builds or demolishes it.

See it: the smallest resource

resource "docker_image" "nginx" {
  name = "nginx:1.27-alpine"
}
TokenMeaning
resourceBlock type: something Terraform creates and manages
"docker_image"Resource type from the docker provider. Creating one pulls an image.
"nginx"Your local name, used only inside Terraform: docker_image.nginx
name = "nginx:1.27-alpine"Argument: which image to pull

Applying this block does what docker pull does. What it does not do: the label nginx isn't a Docker name. Call it "base" and nothing in Docker changes. And writing the block creates nothing until you apply.

Build it up: TaskFlow's web container

tf-docker-demo/main.tf
# = docker pull nginx:1.27-alpine
resource "docker_image" "nginx" {
  name         = "nginx:${var.nginx_tag}"     # "nginx:1.27-alpine" from terraform.tfvars
  keep_locally = false                        # terraform destroy also removes the image
}

# = docker run -d --name taskflow-web --restart unless-stopped -p 8080:80 nginx:1.27-alpine
resource "docker_container" "web" {
  name    = var.container_name
  image   = docker_image.nginx.image_id         # reference → implicit dependency on the image
  restart = "unless-stopped"

  ports {
    internal = 80                             # nginx listens on 80 inside the container
    external = var.external_port              # host port (8080)
  }
}
LineMeaning
keep_locally = falseDestroying this resource also deletes the image from Docker
image = docker_image.nginx.image_idThe image's ID attribute (sha256:…). Because of this reference, Terraform pulls first, and replaces the container whenever the image changes.
ports { internal … external … }A nested block, repeatable (one per published port): -p 8080:80

Dependencies: implicit vs explicit

That reference is an implicit dependency, which is what you want almost always. An explicit depends_on = [aws_route_table_association.public] is only for a hidden dependency no argument shows, like an EC2 boot script that needs the internet route but never references it (Session 21). Independent resources are created in parallel (10 at a time by default); terraform graph prints the graph.

Many copies from one block: count and for_each

resource "docker_container" "worker" {
  count = 3                                     # docker_container.worker[0], [1], [2]
  name  = "taskflow-worker-${count.index}"      # taskflow-worker-0, -1, -2
  image = docker_image.nginx.image_id
}

resource "docker_container" "env" {
  for_each = { blue = 8081, green = 8082 }      # docker_container.env["blue"], ["green"]
  name     = "taskflow-web-${each.key}"         # each.key = blue | green
  image    = docker_image.nginx.image_id
  ports {
    internal = 80
    external = each.value                       # each.value = 8081 | 8082
  }
}
countfor_each
Input · instances named byA number · index [0], [1]A map or toset(list) · key ["blue"]
Remove an item from the middleLater items shift index, so they're changed or recreatedOnly that one is destroyed
Best forN identical copies, or an on/off switch: count = var.enabled ? 1 : 0Copies that differ by name or config

Data sources: read, don't create

A first taste of AWS (Session 21 builds on it). Look up your account ID, then use it to make a globally unique bucket name:

aws-demo/main.tf
data "aws_caller_identity" "current" {}        # read-only: who am I? (account_id, arn)

resource "aws_s3_bucket" "logs" {
  bucket = "taskflow-logs-${data.aws_caller_identity.current.account_id}"   # bucket names are global
}

resource "aws_s3_bucket_versioning" "logs" {
  bucket = aws_s3_bucket.logs.id                 # implicit dependency: bucket first
  versioning_configuration {
    status = "Enabled"
  }
}

Data sources are addressed as data.TYPE.NAME. Other common ones: data "aws_ami" (the newest Ubuntu image ID), data "aws_availability_zones", data "aws_vpc". Plans show them as Reading... Read complete, or <= read if they can only be read during apply.

One more nested block works on any resource. lifecycle { prevent_destroy = true } makes any plan that would destroy it fail (state bucket, prod database). create_before_destroy = true builds the replacement first (+/-) for less downtime. ignore_changes = [tags] stops Terraform fighting changes made outside it.

Exam trap

"Add depends_on everywhere to be safe." ✗ A reference already creates the dependency. Use depends_on only for hidden ones. Extra edges slow plans down and hide the real intent.

"A data source creates the object if it's missing." ✗ It only reads. If nothing matches, the plan fails.

Remember

resource = create & manage · data = read only
A reference (TYPE.NAME.ATTRIBUTE) is also a dependency.
count for N identical copies · for_each for named ones

Mastery check
Q1. Spot the bug: image = "docker_image.nginx.image_id"

The quotes make it a literal string: Docker is asked for an image literally named docker_image.nginx.image_id, and Terraform sees no dependency. Drop the quotes.

Q2. count = length(var.names) with names = ["api", "worker", "cron"]. You delete "api". Predict the plan.

Indexes shift: [0] becomes worker and [1] becomes cron, so both are replaced (their names change), and [2] is destroyed: Plan: 2 to add, 0 to change, 3 to destroy. With for_each = toset(var.names) only ["api"] goes.

5 Variables, locals & outputs

The problem

main.tf needs a container name and a port; staging wants port 9090 and another name; the DB password must never sit in a committed file. Copying the folder to staging/ works for a week, until the copies drift apart.

The idea

Treat the configuration like a function. Variables are its parameters (type, default, validation). Locals are values computed inside. Outputs are its return values, printed after apply and read by scripts. The code stays the same for every environment; only the inputs change.

 inputs                                  the configuration                 results
 terraform.tfvars ──┐                   ┌──────────────────────────┐
 TF_VAR_* env vars ─┼─▶ variables.tf ─▶ │ locals { … }             │ ─▶ outputs.tf ─▶ terraform output
 -var / -var-file ──┘   (type, default, │ main.tf uses var.x and   │    url,             → your shell,
                         validation)    │ local.y                  │    container_id       scripts, CI
                                        └──────────────────────────┘
Think of it like this

You already know this shape: def taskflow_web(container_name="taskflow-web", external_port: int = 8080): …. Parameters with defaults are variables, an assert on the first line is validation, local variables in the body are locals, and the return {"url": …} is an output. Calling it with other arguments is a tfvars file.

See it: one variable, four ways to set it

Declare variable "external_port" { type = number, default = 8080 }, use it as external = var.external_port, and watch the planned output change (only that line shown):

$ terraform plan                                              # nothing set: the default
  + url = "http://localhost:8080"
$ TF_VAR_external_port=9000 terraform plan                    # environment variable
  + url = "http://localhost:9000"
$ echo 'external_port = 8081' > terraform.tfvars
$ TF_VAR_external_port=9000 terraform plan                    # the tfvars file beats the env var
  + url = "http://localhost:8081"
$ TF_VAR_external_port=9000 terraform plan -var external_port=9090   # the CLI flag beats everything
  + url = "http://localhost:9090"

The full precedence order, later wins: (1) default → (2) TF_VAR_external_port → (3) terraform.tfvars, then terraform.tfvars.json (both loaded automatically) → (4) *.auto.tfvars, alphabetically → (5) -var 'external_port=9090' and -var-file=prod.tfvars, in the order given.

What it does not do: a variable can't be computed from a resource (default = aws_vpc.main.id is an error). Values arrive from outside, before planning starts. Use a local for anything computed.

Exam trap

"sensitive = true encrypts the value." ✗ It only hides it in plan/apply output. State holds it in plain text, and output -raw prints it.

"Environment variables override terraform.tfvars." ✗ The reverse: only the default is weaker than TF_VAR_.

Mastery check
Q1. terraform.tfvars says external_port = 8081 and staging.auto.tfvars says 9000. You run terraform plan with no flags. Which port?

9000. *.auto.tfvars files load after terraform.tfvars, and the later value wins.

Q2. Your teammate changes the default of external_port to 80, passes nothing, and gets Invalid value for variable. They didn't set anything, so why?

Validation checks the final value, and that includes the default. 80 fails >= 1024, so even the default is rejected.

Q3. A script runs curl "$(terraform output url)/health" and gets curl: (3) URL rejected: Port number was not a decimal number between 0 and 65535. Why?

Without -raw the output keeps its quotes, so curl receives "http://localhost:8080"/health and the quote after the port breaks the URL. Use terraform output -raw url.

6 plan → apply → destroy

The problem

One day you'll run Terraform in a folder that also manages TaskFlow's production database. Before anything happens you want to know what will be created, what will change, and above all what will be destroyed.

The idea

terraform plan is a dry run over three inputs: your config (what you want), the state (what was built last time) and the real objects, refreshed through the provider (what's there now). It prints the difference as actions. apply carries them out and records the new IDs in state. destroy is a plan to delete everything in state, then an apply.

  config (*.tf)               state (last apply)            real world (refreshed now)
  "web should exist,          "web = container 7d3e…,       "container 7d3e… is running,
   port 8080"                  port 8080"                     port 8080"
            └──────────────────────────┼─────────────────────────────┘
                                       ▼
                 terraform plan   →  + create   ~ update   -/+ replace   - destroy
                                       ▼   you read: "Plan: 2 to add, 0 to change, 0 to destroy."
                 terraform apply  →  provider API calls  →  state updated with real IDs
Think of it like this

plan is the contractor's itemised quote: "build one container, replace one image, demolish nothing". You read it, sign it, and only then does work start. Saving the plan with -out gives you the signed copy: the crew does exactly what's on it and nothing else.

See it: check, then plan

$ terraform fmt -recursive && terraform validate   # canonical style (prints changed files), then syntax + references

Exam trap

"terraform apply applies the plan I reviewed earlier." ✗ Without a file it makes a new plan. apply tfplan runs the saved one, or refuses (Saved plan is stale) if state changed since.

"-/+ is an in-place update." ✗ It destroys and recreates: new ID, maybe a new IP, and whatever was inside is gone.

"terraform destroy deletes everything in the AWS account." ✗ Only what's recorded in this folder's state.

Remember

plan = preview (read-only) · apply = do it + record it in state · destroy = delete what state knows
+ create · ~ in place · -/+ replace · - destroy. Read the summary line first.

Mastery check
Q1. A plan for a one-tag change ends with Plan: 0 to add, 1 to change, 14 to destroy. What do you do?

Stop. A tag change is one ~. Fourteen destroys mean something else is wrong: wrong folder or backend, a deleted .tf file, or a variable that set a count to 0. Read the - lines first.

Q2. Plan shows -/+ aws_instance.app with # forces replacement next to ami. What happens to the server if you apply?

It's terminated and a new one is created: new instance ID, new public IP, local disk gone. Session 21 prevents this with lifecycle { ignore_changes = [ami] }.

Q3. Fill in: plan compares the ________ with the ________ and with the ________; apply then updates the ________.

Configuration · state · real infrastructure (refreshed through the provider) · state.

7 Terraform state

The problem

The nginx container is running. Then your copy of the folder loses terraform.tfstate: a git clean, a new laptop, or a fresh clone. Nothing touched Docker. You plan and apply:

$ docker ps --format '{{.Names}}'
taskflow-web                                 # still running
$ terraform plan | tail -1
Plan: 2 to add, 0 to change, 0 to destroy.    # it wants to create everything again
$ terraform apply -auto-approve
docker_image.nginx: Creating...
docker_image.nginx: Creation complete after 1s [id=sha256:4c1c…nginx:1.27-alpine]
docker_container.web: Creating...
╷
│ Error: Unable to create container: Error response from daemon: Conflict. The container name "/taskflow-web" is already in use by container "7d3e5f1a9b2c…". You have to remove (or rename) that container to be able to reuse that name.
│
│   with docker_container.web,
│   on main.tf line 8, in resource "docker_container" "web":
│    8: resource "docker_container" "web" {

Terraform could read the code and could talk to Docker, yet it didn't recognise its own container. What did it lose?

The idea

The state file maps every address in your config to the real object behind it, plus that object's attributes and dependencies. Plan needs all three columns below. Delete the middle one and Terraform has no way to know that docker_container.web is container 7d3e…, so it assumes nothing exists.

 config (main.tf)              state (terraform.tfstate)                 real world (Docker)
 docker_image.nginx     ◀──▶  docker_image.nginx   = sha256:4c1c…  ◀──▶  image nginx:1.27-alpine
 docker_container.web   ◀──▶  docker_container.web = 7d3e5f1a9b2c… ◀──▶  container taskflow-web
                               + every attribute, + dependencies

 state deleted → middle column empty → "nothing exists" → Plan: 2 to add → name Conflict
Think of it like this

Lose the contractor's logbook and the crew turns up with the blueprint, sees an empty page, and starts building a second house on the same plot, straight into the first.

See it: what Terraform remembers

    …
}

state list prints every managed address; state show ADDR prints one's recorded attributes. What it does not do: neither asks Docker anything. They read the file, so a container deleted by hand still shows up until the next plan refreshes.

For the lost-state problem, the real fix is to get the state back (section 8 keeps every version in S3). For a stateless nginx you could also docker rm -f taskflow-web and apply; a database you'd import or restore.

Exam trap

"Deleting terraform.tfstate deletes the infrastructure." ✗ It deletes Terraform's memory; the objects keep running (and billing), unmanaged.

"terraform state rm deletes the resource." ✗ It only makes Terraform forget it.

"State is just a cache Terraform can rebuild from the cloud." ✗ The cloud doesn't record which object is which address; only import, one object at a time, re-links them.

Remember

State = Terraform's memory: address ↔ real ID.
Lose it and Terraform forgets; it doesn't delete.

Mastery check
Q1. You rename resource "docker_container" "web" to "frontend" and change nothing else. What does plan propose, and how do you avoid it?

Destroy docker_container.web, create docker_container.frontend: one address vanished, a new one appeared. Add moved { from = docker_container.web to = docker_container.frontend } (or terraform state mv) and the plan shows a move, 0 to destroy.

8 Remote state, locking & drift

The problem

10:00   Shaurya: terraform apply     laptop A, its own terraform.tfstate
10:00   Priya:   terraform apply     laptop B, her own, older terraform.tfstate
10:01   both write state: laptop B's copy never learns about the security-group rule
        Shaurya just added, so Priya's next plan deletes it

A state file on one laptop works for one person. A team needs one shared copy, and a rule that only one apply at a time may write it.

The idea

A backend decides where state lives. The S3 backend keeps it as one object in a versioned, encrypted bucket that everyone reads and writes. Before writing, Terraform takes a lock: with use_lockfile = true it creates a .tflock object by a conditional write that fails if one exists, so a second apply errors instead of corrupting state.

 laptop A: terraform apply                 s3://shauryav-taskflow-tfstate/taskflow/dev/
   1. create terraform.tfstate.tflock ──▶    terraform.tfstate          (versioned, encrypted)
   2. read  terraform.tfstate         ◀──    terraform.tfstate.tflock   (exists = locked)
   3. apply, then write new state     ──▶
   4. delete the .tflock              ──▶
 laptop B, during steps 1–4: create .tflock → 412 PreconditionFailed → "Error acquiring the state lock"
Think of it like this

Instead of a copy of the logbook in every crew's van, there's one logbook in the site office and one key to the office. Whoever holds the key writes; everyone else waits. Bucket versioning keeps every old page.

See it: the backend block

Create the bucket once, by hand. It's a chicken-and-egg problem: the backend must exist before Terraform can store state in it.

$ aws s3api create-bucket --bucket shauryav-taskflow-tfstate --region ap-south-1 \
    --create-bucket-configuration LocationConstraint=ap-south-1
{
    "Location": "http://shauryav-taskflow-tfstate.s3.amazonaws.com/"
}
$ aws s3api put-bucket-versioning --bucket shauryav-taskflow-tfstate \
    --versioning-configuration Status=Enabled      # every state write kept → recover from mistakes
infra/backend.tf
terraform {
  backend "s3" {
    bucket       = "shauryav-taskflow-tfstate"        # must already exist
    key          = "taskflow/dev/terraform.tfstate"   # object path; one key per environment
    region       = "ap-south-1"
    encrypt      = true                               # server-side encryption of the state object
    use_lockfile = true                               # lock with an S3 .tflock object (Terraform ≥ 1.10)
    # dynamodb_table = "terraform-locks"              # OLD way: DynamoDB table with key "LockID", deprecated
  }
}
ArgumentMeaning
bucket / keyWhere the state object lives: s3://shauryav-taskflow-tfstate/taskflow/dev/terraform.tfstate
encryptEncrypt the object at rest. Add a tight bucket policy too: state holds secrets.
use_lockfileCreates …/terraform.tfstate.tflock before writing. Needs s3:GetObject, s3:PutObject, s3:DeleteObject on that key. (dynamodb_table is the deprecated pre-1.10 method.)

A new backend means a new init, which offers to copy your local state across:

$ terraform init -migrate-state
Initializing the backend...
Do you want to copy existing state to the new backend?
  …
  Enter a value: yes

Successfully configured the backend "s3"! Terraform will automatically
use this backend unless the backend configuration changes.

What it does not do: the backend block doesn't create the bucket, and it can't read variables (Q3 below). Versioning on the bucket is what lets you restore an older state after a bad apply or an accidental state rm, which turns section 7's lost-state problem into a one-minute fix.

        name = "taskflow-web"
    }

  # docker_container.web will be created
  + resource "docker_container" "web" { … }

Plan: 1 to add, 0 to change, 0 to destroy.

Drift is any difference between reality and state, and the refresh step found it. Two ways to resolve it: terraform apply puts reality back to what the code says (the code wins), while plan -refresh-only / apply -refresh-only updates the state to match reality without touching infrastructure. Use the second to accept a change, then edit the code to match.

Exam trap

"See a lock error? Run force-unlock." ✗ Only if the holder really crashed (check Who, Created). Unlocking a live apply lets two writers corrupt state.

"S3 state locking needs a DynamoDB table." ✗ That's the deprecated method; use_lockfile = true (Terraform ≥ 1.10) locks with an S3 object.

"-refresh-only fixes drift." ✗ It only records reality in state; the next normal plan still undoes the change unless you edit the code.

Remember

Remote backend = one shared state + a lock + versions.
Drift: apply → reality back to the code · -refresh-only → state back to reality.

Mastery check
Q1. You get Error acquiring the state lock, with Who: runner@fv-az123 and Created 40 seconds ago. What do you do?

Wait: a CI apply is running right now. Only if the lock is hours old and that job crashed do you run terraform force-unlock <ID>.

Q2. Someone added a security-group rule in the console, and plan shows ~ to remove it. When do you apply, and what if the rule was right?

If the click was a mistake, apply: the code wins and the rule goes. If the rule is wanted, add it to the code; the next plan shows no changes. -refresh-only alone would record it in state, and the next plan would still remove it.

Q3. Spot the bug: backend "s3" { bucket = var.state_bucket key = "taskflow/${var.env}/terraform.tfstate" }

Backends can't use variables (Error: Variables not allowed); they're read before variables exist. Write literals, or keep a backend-dev.hcl per environment and run terraform init -backend-config=backend-dev.hcl.

★ Putting it all together

The big idea

Terraform turns infrastructure into reviewed, versioned code. You declare providers and resources in HCL, feed in variables, read results from outputs. init fetches the provider plugins (pinned by the lock file) that make the real API calls. plan compares config, state and reality and shows every action first; apply makes it so and records real IDs in state. State is Terraform's memory and full of secrets, so it lives in a locked, versioned S3 bucket, never in Git. Session 21 uses this workflow to build a VPC and an EC2 instance running TaskFlow.

Final mastery check: combine everything
Q1. New laptop, fresh clone, state in S3. List the commands, in order, to safely bump nginx_tag, and say what each one touches.

init: installs the locked provider version and connects the S3 backend. Edit terraform.tfvars; fmt + validate (local only). plan -out=tfplan: takes the lock, reads state from S3, refreshes the real image and container, shows -/+ for both. apply tfplan: locks, replaces both, writes the new state to S3, unlocks. Check with curl "$(terraform output -raw url)".

Q2. A professor says: "Terraform is declarative, so it doesn't need state. It just compares the code with the cloud." Correct this.

To compare, Terraform must know which real object each address is, and the cloud doesn't record that. State holds that mapping, plus attributes and dependencies. Without it Terraform plans to create everything again and hits conflicts (section 7).

Q3. A teammate commits terraform.tfstate and a terraform.tfvars containing db_password. Two problems, two fixes?

(1) The secret is in Git twice, since sensitive doesn't encrypt state: rotate it, purge history, move it to TF_VAR_db_password, ignore *.tfstate*. (2) A committed state goes stale and gets overwritten: move it to S3 with use_lockfile = true and versioning.

Q4. CI runs terraform apply -auto-approve -var external_port=9090; tfvars says 8081. Which port, and what's wrong with the step?

9090: the CLI flag beats tfvars and passes validation. But it applies a fresh plan nobody reviewed. Split it: plan -out=tfplan → review/approval → apply tfplan.

Q5. Someone ran docker rm -f taskflow-web. You then run terraform destroy. Predict the plan.

Destroy refreshes first, notes the container was deleted outside Terraform, and drops it. Only the image is left: Plan: 0 to add, 0 to change, 1 to destroy.
