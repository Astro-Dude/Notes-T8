1 The workflow & kubectl get

The problem

It's the morning after the 1.2.1 release, and two things are wrong:

$ curl -sk -o /dev/null -w '%{http_code}\n' https://taskflow.local/api/tasks
503                                                     # puzzle 1: the API is "down"…
$ kubectl get pods -n taskflow
NAME                            READY   STATUS             RESTARTS      AGE
taskflow-api-7c9d8f6b5d-4kq2x   1/1     Running            0             2d      # …yet these look fine
taskflow-api-7c9d8f6b5d-9wd7t   1/1     Running            0             2d
taskflow-api-6d8f7c9b4-2xkqp    0/1     CrashLoopBackOff   5 (41s ago)   4m10s   # puzzle 2: 1.2.1 won't start
taskflow-db-6b8d9f7c5-k7m2p     1/1     Running            0             2d

The namespace holds Deployments, ReplicaSets, pods, Services, an Ingress, ConfigMaps, Secrets and a PVC. The tempting move is to start poking: delete the pod, redeploy, restart minikube. Each one destroys evidence, and the bug comes back. You need a fixed order of questions instead.

The idea

Every failure leaves a trail, and four commands read it in order. get says where it broke. describe + Events say why, from Kubernetes's side. logs says why from the app's side. exec / debug / port-forward let you test a theory. The STATUS column picks the branch:

kubectl get pods -n taskflow            ← read STATUS, READY, RESTARTS
   │
   ├─ Pending ─────────────────────▶ describe pod → Events: FailedScheduling        (§6)
   ├─ ContainerCreating (stuck) ───▶ describe pod → Events: FailedMount / sandbox
   ├─ ErrImagePull / ImagePullBackOff ▶ describe pod → Events: Failed to pull image  (§5)
   ├─ CreateContainerConfigError ──▶ describe pod → Events: secret/configmap/key     (§5)
   ├─ CrashLoopBackOff / Error / OOMKilled ▶ logs --previous + describe Last State  (§4)
   ├─ Running but READY 0/1 ───────▶ describe pod → Events: Readiness probe failed  (§7)
   └─ Running 1/1, app unreachable ▶ endpoints → selector/targetPort → DNS → ingress (§7)

Still stuck? → kubectl get events --sort-by=.lastTimestamp → exec / debug / port-forward
Think of it like this

An emergency-room doctor. get is triage: a glance at every patient's vital signs on the board. describe is the patient's chart, and its Events are the nurses' notes from the last hour. logs is what the patient says, and --previous is what they said just before they collapsed. exec is examining them up close. A good doctor never starts with surgery. This ER comes back in every section.

See it: read one line of get

In the command, get lists objects, pods is the resource type (po for short), and -n taskflow picks the namespace. The information is in the columns:

Column (for taskflow-api-6d8f7c9b4-2xkqp)ValueWhat it tells you
READY0/1Ready containers / total. 0 means it gets no Service traffic.
STATUSCrashLoopBackOffThe headline, and it picks your branch of the flowchart (here §4).
RESTARTS5 (41s ago)The container has died 5 times; the last restart was 41 s ago.
AGE4m10sA new pod: it came with the release, so suspect the change.

The two old pods are fine, which is exactly why users still have a working API… or should have (puzzle 1 waits for §7).

What it does not do: say why. get is a one-word symptom. The reason is always one command further.

Exam trap

"Find crashing pods with --field-selector=status.phase!=Running." ✗ A CrashLoopBackOff pod's phase is still Running. Read the STATUS column.

"kubectl get all shows everything." ✗ It skips ConfigMaps, Secrets, Ingresses and PVCs. Ask for them: kubectl get cm,secret,ing,pvc -n taskflow.

Remember

get (where) → describe + events (why, K8s) → logs (why, app) → exec (test).
STATUS picks the branch. Never delete the evidence first.

Mastery check
Q1. Output: No resources found in default namespace. Your teammate says "the pods are gone!" Diagnose.

They're looking in default. Add -n taskflow (or -A), or set the context's namespace with kubectl config set-context --current --namespace=taskflow.

Q2. Output: taskflow-api-7c9d8f6b5d-4kq2x 1/1 Running 14 (3h ago) 2d. Healthy?

Not really. It's up right now, but it has died 14 times in 2 days. Something kills it periodically, typically OOM or a liveness failure. Check describe pod → Last State (Reason, Exit Code) and logs --previous.

Q3. A Deployment's pod shows 0/1 Completed and then CrashLoopBackOff. What's the likely bug?

The container's command finishes and exits 0, for example a script instead of a long-running server. Deployments expect a process that never ends, so the kubelet keeps restarting it. Fix the command/CMD.

2 kubectl describe & Events

The problem

get gives you one word, like Pending or CrashLoopBackOff. Pending why? Which component gave up, and what did it say? And when a pod crashed an hour ago and has since recovered, where is the record of what happened?

The idea

kubectl describe prints one object's spec, status and its recent Events in human-readable form. Events are API objects (kind: Event) that the components write as they work. Normal means information, Warning means something failed. They're kept for 1 hour by default (kube-apiserver --event-ttl).

 scheduler    ──▶ Scheduled · FailedScheduling                     ┐
 kubelet      ──▶ Pulling · Pulled · Failed · BackOff ·            ├──▶ Event objects (kept ~1 h)
                  Created · Started · Unhealthy · Killing          │      ├─▶ bottom of kubectl describe …
 controllers  ──▶ ScalingReplicaSet · SuccessfulCreate ·           │      └─▶ kubectl get events / kubectl events
                  FailedCreate · SuccessfulRescale                 ┘

The Reason tells you which component is complaining, which tells you which kind of problem you have.

Think of it like this

The chart at the foot of the bed. The top half is the patient's details and current state. The bottom half is the nurses' notes, timestamped, saying who did what ("scheduler: assigned bed 4", "kubelet: patient collapsed, 5th time"). The notes are shredded after an hour.

Mastery check
Q1. Diagnose: Warning BackOff 7s (x11 over 2m35s) kubelet Back-off restarting failed container api. Who wrote it, what does x11 over 2m35s mean, and what's your next command?

The kubelet. The same event happened 11 times in the last 2m35s, meaning the container keeps dying. Next: kubectl logs POD --previous and the Last State exit code in describe (§4).

Q2. kubectl get deploy taskflow-api shows 0/2, and kubectl get pods -l app=taskflow-api returns nothing. Which object do you describe, and what will you probably see?

The ReplicaSet (kubectl describe rs -n taskflow). The pods were never created, so admission rejected them, and the RS shows FailedCreate, e.g. exceeded quota (Session 15) or a Pod Security violation (Session 16).

Q3. In describe pod, Node: is <none> and Conditions show PodScheduled False. Which component is the problem, and which event Reason do you look for?

The scheduler couldn't place the pod. Look for FailedScheduling, whose message names the reason (resources, selector, taint, PVC). That's §6.

3 logs, exec, debug & port-forward

The problem

A pod is 1/1 Running with zero restarts, and describe shows nothing but Normal events, yet /tasks returns 500. Kubernetes thinks everything is fine, and from its point of view it is. The answer is inside the app: its output, its environment, its network view.

The idea

Four tools, each reaching one layer deeper:

 kubectl logs          → what the app wrote to stdout/stderr (current container, or --previous)
 kubectl exec          → run a command INSIDE the running container (env, files, localhost, DNS)
 kubectl debug         → add a container with tools (image has no shell / container won't stay up)
 kubectl port-forward  → your laptop ──▶ one pod directly, skipping the Service and the Ingress
Think of it like this

logs is listening to what the patient tells you. exec is examining them with what's already in the room. debug is bringing your own instruments when the room is empty. port-forward is walking straight to the patient's bed instead of going through reception.

See it: kubectl logs

$ kubectl logs taskflow-api-7c9d8f6b5d-4kq2x -n taskflow --tail=3 --timestamps
2026-10-09T04:32:10.118263512Z {"level":"info","msg":"GET /health 200 1ms"}
2026-10-09T04:32:12.402118033Z {"level":"error","msg":"GET /tasks 500 14ms","err":"permission denied for table tasks"}
2026-10-09T04:32:15.118904127Z {"level":"info","msg":"GET /health 200 1ms"}
TokenMeaning
logs PODThe container's stdout/stderr, as captured by the runtime on the node
--tail=3Only the last 3 lines (--since=10m works too)
--timestampsPrefix each line with its RFC3339 time

The 500 now has a reason: permission denied for table tasks. That's a database grant, not a Kubernetes problem, and no amount of describe would have shown it.

What it does not do: show logs the app writes to files inside the container (only stdout/stderr), or anything from a pod that's already been deleted. And by default it shows the current container, so after a crash you need --previous.

Exam trap

"Just exec into the crash-looping pod and look around." ✗ You can't exec into a container that isn't running. Use logs --previous, or kubectl debug --copy-to with a shell as the command.

"kubectl port-forward svc/taskflow-api 8080:80 tests the Service's load balancing." ✗ kubectl picks one pod behind the Service and tunnels to it. It bypasses kube-proxy entirely.

Remember

logs = what it said (--previous after a crash) · exec = test from inside · debug = no shell or won't stay up · port-forward = skip Service + Ingress.

Mastery check
Q1. Diagnose: kubectl exec -it POD -- sh prints exec: "sh": executable file not found in $PATH. The pod is Running.

The image has no shell (distroless or scratch). Attach an ephemeral container instead: kubectl debug -it POD --image=busybox:1.36 --target=api.

Q2. curl localhost:8080/health through port-forward pod/… works, but the in-cluster wget taskflow-api/health fails. Which layer is broken?

Not the app: the pod answers directly. The problem is between the Service and the pod (selector, targetPort, readiness, endpoints) or in DNS. That's §7.

Q3. kubectl logs -l app=taskflow-api shows only a few lines per pod, and the error you're hunting isn't there. Why, and what do you add?

With a label selector, kubectl defaults to the last 10 lines per pod. Add --tail=-1 (all lines) or --since=30m, and --prefix to see which pod said what.

4 CrashLoopBackOff & OOMKilled

The problem: puzzle 2, the 1.2.1 release

k8s/deployment.yaml — broken (v1.2.1, env section)
          image: shauryav/taskflow-api:1.2.1
          env:
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef: { name: taskflow-config, key: LOG_LEVEL }
            # the DATABASE_URL block was deleted in a refactor  ← the bug
$ kubectl apply -f k8s/deployment.yaml && kubectl rollout status deploy/taskflow-api -n taskflow
deployment.apps/taskflow-api configured
Waiting for deployment "taskflow-api" rollout to finish: 1 out of 2 new replicas have been updated...
$ kubectl get pods -n taskflow -l app=taskflow-api
NAME                            READY   STATUS             RESTARTS      AGE
taskflow-api-7c9d8f6b5d-4kq2x   1/1     Running            0             2d
taskflow-api-7c9d8f6b5d-9wd7t   1/1     Running            0             2d
taskflow-api-6d8f7c9b4-2xkqp    0/1     CrashLoopBackOff   4 (32s ago)   2m41s

The rollout stalls, and the old pods keep serving, because a rolling update doesn't remove old pods until a new one is ready.

Predict before reading on: §2's events showed the pod scheduled and the image present. Is the cause in the scheduler, the registry, or the app?

The app. Scheduling and pulling succeeded, so the container itself starts and then exits. The evidence is in the previous run's exit code and logs.

The idea

CrashLoopBackOff isn't an error in itself. It means "the container exited, and I'm waiting before restarting it again". The kubelet doubles the wait after every crash and caps it at 5 minutes. The wait resets once the container runs for 10 minutes without crashing. The cause is always in the previous run.

 start ─▶ exit 1 ─▶ wait 10s ─▶ start ─▶ exit 1 ─▶ wait 20s ─▶ … 40s ─▶ 80s ─▶ 160s ─▶ 300s (cap) ─▶ …
 STATUS:  Error      CrashLoopBackOff      Error     CrashLoopBackOff           RESTARTS keeps climbing
          └ evidence: describe → Last State (Reason, Exit Code) · logs --previous
Think of it like this

The patient faints every time they stand up. The nurse helps them up again, but waits a little longer each time: 10 seconds, then 20, then 40. Watching them lie there tells you nothing. You need to know what happened the moment before they fell.

Mastery check
Q1. Diagnose: Last State: Terminated, Reason: Error, Exit Code: 1, and plain kubectl logs POD prints nothing. Next command, and why was the output empty?

kubectl logs POD --previous. Plain logs shows the current container, which has just been restarted and hasn't logged anything yet. The crash's stack trace belongs to the previous instance.

Q2. Diagnose: Reason: OOMKilled, Exit Code: 137, Limits: memory: 128Mi, and kubectl top pod shows 120Mi a minute after each restart. Explain 137 and give two fixes.

137 = 128 + 9: the kernel sent SIGKILL because the container crossed limits.memory. Fixes: raise the limit based on measured peak usage (e.g. 256Mi), and cap the Node heap below it with --max-old-space-size. If usage keeps climbing over time, find the leak.

Q3. Diagnose: CrashLoopBackOff, exit 137, no OOMKilled, and events show Liveness probe failed: HTTP probe failed with statuscode: 404. Is the app broken?

Probably not. The liveness probe hits a path the app doesn't serve (say /healthz instead of /health), so the kubelet kills a healthy container every time. Fix the probe's path or port.

Q4. A release crash-loops, but users see no outage. Why, and what's the fastest recovery?

RollingUpdate keeps the old ReplicaSet's pods until new ones are Ready, so the rollout just stalls. kubectl rollout undo deploy/taskflow-api returns to the previous revision immediately. Then fix the manifest.

5 ImagePullBackOff & CreateContainerConfigError

The problem

k8s/deployment.yaml — broken (image)
          image: shauryav/taskflow-api:1.2      # ← CI pushed "1.2.0", not "1.2"

Predict: why can't logs help here, and where is the evidence?

The container never started, because there's no image to start it from, so it has written nothing. The kubelet's pull attempts are recorded as Events in describe pod.

The idea

Before a container can start, the kubelet must pull its image from the registry. ErrImagePull means a pull just failed. ImagePullBackOff means the kubelet is waiting before retrying, with the same 10 s → 5 min back-off as §4. The registry's answer, quoted in the event, tells you which of four causes it is:

 kubelet ── pull shauryav/taskflow-api:1.2 ──▶ registry
              ◀── "not found / manifest unknown" → typo in name or tag            (case 1)
              ◀── "401 Unauthorized / access denied" → private repo, no creds     (case 2)
              ◀── "429 Too Many Requests"           → Docker Hub rate limit       (case 3)
              ◀── "pull access denied, repository does not exist" for a local-only image (case 4)
Think of it like this

The doctor prescribed a medicine, and the pharmacy can't hand it over. The name is misspelled, it's in a locked cabinet you have no key for, or you've hit today's limit. Until it arrives, the patient can't even start treatment, so there's nothing to listen to (no logs).

Q1. Diagnose: Failed to pull image "ghcr.io/shauryav/taskflow-api:1.2.0": … 401 Unauthorized. The tag definitely exists. Fix?

6 Pending pods

The problem

k8s/deployment.yaml — broken (resources)
          resources:
            requests:
              cpu: "2"            # ← copied from a prod values file; minikube has 2 CPUs total
              memory: 512Mi
$ kubectl get pods -n taskflow -l app=taskflow-api -o wide
NAME                           READY   STATUS    RESTARTS   AGE   IP       NODE     NOMINATED NODE   READINESS GATES
taskflow-api-8d6f5c7b9-tq2lx   0/1     Pending   0          2m    <none>   <none>   <none>           <none>

No IP, no node, after two minutes. Meanwhile kubectl top nodes says the node is only 15% busy.

Predict: the node is 85% idle. Why won't the scheduler place a pod that asks for 2 CPUs?

The scheduler doesn't look at usage. It adds up the requests of the pods already on the node. 2 CPUs allocatable − 1050m already requested = 950m free, which is less than 2, so it never fits.

The idea

Pending with an empty Node: means the scheduler couldn't place the pod. For each pod it filters out nodes that can't take it, then scores the survivors. If zero nodes survive, it writes a FailedScheduling event that says exactly why, as 0/N nodes are available: <count> <reason>, …. The preemption: part says whether evicting lower-priority pods would help (usually not).

 all nodes ─▶ enough unrequested cpu/memory? ─▶ matches nodeSelector/affinity? ─▶ tolerates taints?
          ─▶ its PVCs bound / bindable here? ─▶ free hostPort? ─▶ 0 left → Pending + FailedScheduling
                                                                  ≥1 left → score → bind → kubelet starts it
Think of it like this

The patient is waiting in the lobby for a bed. Every bed is reserved (requests), even if the people in them are asleep (low usage). Or the patient asked for the cardiac ward and this hospital has none (nodeSelector). Or the ward has a "staff only" sign (taint). Or their equipment hasn't arrived (an unbound PVC). The admissions desk writes down which one it was.

See it: read the scheduler's reason

$ kubectl describe pod taskflow-api-8d6f5c7b9-tq2lx -n taskflow | tail -1
  Warning  FailedScheduling  2m    default-scheduler  0/1 nodes are available: 1 Insufficient cpu. preemption: 0/1 nodes are available: 1 No preemption victims found for incoming pod.
$ kubectl describe node minikube | grep -A 6 "Allocated resources"
Allocated resources:
  (Total limits may be over 100 percent, i.e., overcommitted.)
  Resource           Requests     Limits
  --------           --------     ------
  cpu                1050m (52%)  1 (50%)
  memory             668Mi (8%)   1194Mi (15%)
  ephemeral-storage  0 (0%)       0 (0%)

"0/1 nodes are available: 1 Insufficient cpu" reads as: of 1 node, 0 fit, and 1 was ruled out for CPU. Allocated resources confirms it: 1050m is already requested out of 2 cores. Fix: set requests from real usage (kubectl top), here cpu: 100m. Or add capacity: minikube node add, or the Cluster Autoscaler on EKS.

What Pending does not mean: "still downloading". Pulling happens after scheduling, under ContainerCreating.

Mastery check
Q1. Diagnose: 0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient memory. Which nodes were ruled out for what, and what are your options?

The control-plane node was excluded by its taint. The two workers are excluded because their unrequested memory is less than the pod's request. The PVC (kubectl describe pvc taskflow-db-data), whose ProvisioningFailed event names the bad class. storageClassName is immutable on an existing PVC, so you fix the YAML, delete the claim and recreate it.

The problem: puzzle 1, the 503

Back to the morning's first symptom. Every API pod is 1/1 Running, port-forward to a pod works (§3), and yet:

Predict: DNS works and the pods are healthy. Which object is most likely wrong, and which one command checks it?

The idea

The hospital switchboard. The patient is fine and their bedside phone works (port-forward). But the directory might have no entry for the ward you're calling from (DNS, wrong namespace), or the switchboard routes the ward's number to an empty room (selector matches nothing), or to the right room but the wrong extension (targetPort).

Exam trap

"Test the Service from your laptop with curl 10.96.45.12." ✗ ClusterIPs only work inside the cluster. Use a tmp pod or port-forward.

"ping taskflow-api failed, so the Service is down." ✗ ClusterIPs are virtual and usually don't answer ICMP. Test the TCP port with wget or nc.

Remember

Walk the chain: DNS → Service → endpoints → targetPort → ready pod.
<none> = selector mismatch or no ready pods (503) · wrong port = refused (502) · other namespace = svc.namespace.

Mastery check
Q1. Diagnose: endpoints show 10.244.0.14:8080,10.244.0.15:8080, and the ingress returns 502. The pods listen on 3000.

The selector is fine (endpoints exist) but targetPort is 8080, so connections to the pods are refused, which ingress-nginx reports as 502. Set targetPort: http (or 3000).

Q2. Diagnose: from namespace monitoring, wget taskflow-api/metrics → bad address; from inside taskflow it works.

Short names resolve through the pod's own namespace search domain. From monitoring, use taskflow-api.taskflow or the FQDN taskflow-api.taskflow.svc.cluster.local.

Q3. Diagnose: endpoints <none>, kubectl get pods -l app=taskflow-api lists 2 pods, both 0/1 Running. Selector bug?

No, the selector matches (the label query found them). The pods fail readiness, and not-ready pods are left out of the endpoints. describe pod → Readiness probe failed: … shows why.

★ Putting it all together

The big idea

Every TaskFlow failure leaves a trail. STATUS in get says where it broke. describe and Events say why, because the scheduler, the kubelet and the controllers each write down their reason. logs --previous shows what the app said before dying, and exec/debug/port-forward let you test each hop. Use rollout undo while you investigate, then fix the manifest in Git, re-apply, and confirm with rollout status.

Final mastery check — diagnose the output
Q1. kubectl get pods: taskflow-api-… 0/1 CrashLoopBackOff 6. describe: Last State: Terminated, Reason: Error, Exit Code: 1. logs --previous: Error: connect ECONNREFUSED 10.96.200.7:5432. Where's the bug, and what do you check next?

The API crashes because it can't reach Postgres (exit 1, from the app), so the real problem is the database path. Check kubectl get pods -l app=taskflow-db (is it Running and Ready?), then kubectl get endpoints taskflow-db (selector/readiness, §7), and describe the DB pod (Pending on its PVC? §6). Long-term, the API should retry the DB at startup instead of exiting.

Q2. After a deploy: the new pod is Pending, kubectl get pods -A --field-selector=status.phase=Pending shows 6 pods across namespaces, and the HPA shows REPLICAS 10 with max 10. What happened?

The HPA scaled up (Session 13), and the new replicas' requests no longer fit on the nodes, so they're Pending with Insufficient cpu/memory (§6). Confirm with describe pod → FailedScheduling and describe node → Allocated resources. Fix: right-size requests, add nodes (Cluster Autoscaler), or lower maxReplicas.

Q3. kubectl get pods: ImagePullBackOff. kubectl logs POD: container "api" … is waiting to start: trying and failing to pull image. A teammate wants to exec in to check. What's wrong with that plan, and what do you run instead?

There's no container to exec into, and no logs, because it never started (§3, §5). Run kubectl describe pod POD and read the Failed to pull image event: not found → tag typo, 401 → imagePullSecrets, 429 → rate limit.

Q4. Pods are 1/1 Running, but curl https://taskflow.local/api/tasks returns 502, and in-cluster wget taskflow-api/health → Connection refused. get endpoints shows 10.244.0.14:80. Diagnose.

Endpoints exist, so the selector and readiness are fine (§7), but they point at port 80 on the pods: targetPort is wrong (probably omitted, which defaults it to port: 80). The pods listen on 3000, so connections are refused and ingress-nginx returns 502. Set targetPort: http.

Q5. describe pod shows Restart Count: 9, Last State: Reason: Error, Exit Code: 137, OOMKilled not mentioned, and events show Liveness probe failed: … context deadline exceeded only under load. Cause and fix?

Under load, /health answers slower than timeoutSeconds (default 1 s), so liveness fails and the kubelet kills the container (137 = SIGKILL after the grace period, because the busy event loop never finished its SIGTERM handler; it's not an OOM) (§2, §4). Each restart adds load to the other pods. Fix: timeoutSeconds: 2–5, a higher failureThreshold, and a cheap health handler. Check kubectl top for CPU throttling against the limit.

Q6. A pod has been CreateContainerConfigError for 3 hours. describe pod shows no Events at all. Is the cause unknowable now?

No. The events expired (about 1 h TTL, §2), but the error is still current, so the reason is still visible in describe pod → State: Waiting, Reason: CreateContainerConfigError, Message: …, or via -o jsonpath='{.status.containerStatuses[0].state.waiting.message}'. It names the missing Secret, ConfigMap or key (§5).
