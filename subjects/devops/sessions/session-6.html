1 Containers vs virtual machines

Explain like I'm 5

A VM is a whole separate house with its own plumbing. A container is a room in a shared house: own lock and furniture, but the same plumbing (the host's kernel).

The problem: "works on my machine"

Example: TaskFlow on two machines
  • Laptop: Node 20, Postgres 16 → all good. College server: Node 16 → TypeError: tasks.findLast is not a function (added in Node 18).
  • Copying node_modules built on a Mac to Linux → Error: …/bcrypt_lib.node: invalid ELF header (native module compiled for the wrong OS).

A container image packages the app with its runtime, libraries and default config, so shauryav/taskflow-api:1.0 behaves identically on the laptop, in CI and on the server.

  • A container = an ordinary Linux process (or group of them), isolated by the kernel, running from its own filesystem (the image).
  • A virtual machine = a full guest OS with its own kernel, running on virtual hardware provided by a hypervisor.

Docker on Mac / Windows

Linux containers need a Linux kernel, so Docker Desktop runs a small Linux VM behind the scenes (uname -r in a container shows something like …-linuxkit). In the cloud it's the same story: containers run inside EC2 VMs. Containers and VMs are complements, not rivals.

Common mistakes
  • Treating a container like a VM: installing SSH in it, running 5 services in one container. One main process per container; use docker exec to get a shell.
  • Thinking root in a container is harmless — it's the same kernel. Run apps as a non-root user (Session 7: USER node).
Recap VM = virtual hardware + own kernel (heavy, strong isolation). Container = isolated process sharing the host kernel (light, fast). Namespaces isolate, cgroups limit.

2 Docker architecture

Explain like I'm 5

The docker command is a waiter taking your order. The daemon is the kitchen that cooks it. The registry is the supermarket where the kitchen buys ingredients (images).

 docker CLI ── REST API over /var/run/docker.sock ──▶ dockerd  (Docker daemon / "Docker Engine")
 (client: docker run, ps, build…)                       │  manages images, containers, networks, volumes, builds
                                                         │  gRPC
                                                         ▼
                                                    containerd  (pulls & stores images, supervises containers)
                                                         │
                                               containerd-shim-runc-v2  (one per container; keeps it alive if
                                                         │                containerd/dockerd restarts)
                                                         ▼
                                                       runc  (OCI runtime: sets up namespaces + cgroups, execs PID 1, exits)
                                                         ▼
                                              your process, e.g. nginx  (PID 1 inside the container)

 dockerd ◀────── pull / push over HTTPS ──────▶ Registry (Docker Hub docker.io, ghcr.io, ECR …)
ComponentRole
Docker client (docker)CLI that turns your command into REST API calls. Can talk to a local or remote daemon (docker context).
dockerdThe daemon (server). Owns Docker objects, networking, volumes, builds (via BuildKit). Runs as root, managed by systemd (docker.service).
/var/run/docker.sockUnix socket where dockerd listens. Access to it = full control of Docker (= root).
containerdIndustry-standard container runtime manager (also used directly by Kubernetes).
runcLow-level OCI runtime that actually creates the container, then hands over to the shim.
RegistryStores and serves images (Docker Hub is the default).

Common mistakes 
Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?
$ sudo systemctl enable --now docker            # start it (and on every boot)

permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock
$ sudo usermod -aG docker $USER && newgrp docker # add yourself to the docker group (or log out/in)

The docker group is root-equivalent (docker run -v /:/host … can read any file). Only add trusted users; never expose docker.sock to the internet or mount it into untrusted containers.

Images and runtimes follow the OCI (Open Container Initiative) specs, so an image built by Docker runs unchanged on containerd, Podman or Kubernetes (which dropped Docker itself in v1.24 but still runs Docker-built images).

3 Docker images

Explain like I'm 5

An image is a cake mould; containers are the cakes. One mould, many identical cakes — and the mould never changes.

  • An image = a stack of read-only layers (filesystem diffs) + config (default command, env vars, exposed ports, working dir).
  • Image vs container ≈ class vs object: docker run adds a thin writable layer on top; deleting the container deletes that layer (data inside is lost — use volumes, Session 8).
  • Layers are shared and cached: 10 containers from nginx:1.27-alpine store the image once; images with the same base share those layers.
 ┌──────────────────────────────────────────┐  ← container layer: read-write, one per container (copy-on-write)
 ╞══════════════════════════════════════════╡
 │ CMD ["nginx","-g","daemon off;"]   0 B   │  ← metadata-only layers
 │ COPY docker-entrypoint.sh …       8 kB   │
 │ RUN apk add nginx …              39.7 MB │  ← image layers: read-only, shared
 │ alpine base (minirootfs)          ~8 MB  │
 └──────────────────────────────────────────┘

Naming: [registry/][namespace/]repository[:tag | @digest]

Common mistakes
  • Using :latest everywhere — "latest" is just a default tag name, not "newest". Two servers pulling latest a week apart can run different code. Pin versions.
  • Apple Silicon (arm64) Mac running an amd64-only image → exec format error or a platform warning. Use multi-arch images or docker run --platform linux/amd64 … (emulated, slower).
Recap Image = read-only layers + config; container adds a writable layer. Name = registry/namespace/repo:tag; tags move, digests don't. pull, images, image inspect, history, rmi.

4 Docker containers

Explain like I'm 5

docker run bakes a cake from the mould and serves it. exec lets you poke inside the cake; logs lets you hear what it's saying.

docker run [OPTIONS] IMAGE [COMMAND] [ARG...]

$ docker cp ./index.html web:/usr/share/nginx/html/       # host → container (lost when the container is removed)
Successfully copied 2.05kB to web:/usr/share/nginx/html/
Common mistakes
  • docker run nginx -p 8080:80 — -p after the image is passed to nginx as an argument. Flags go before the image.
  • docker run -d ubuntu:24.04 → Exited (0) instantly. A container lives only as long as its PID 1; bash with no terminal exits at once. Run a long-lived process (a server), or -it for a shell.
  • Second container on the same host port: Bind for 0.0.0.0:8080 failed: port is already allocated → pick another host port (-p 8081:80) or stop the first one.
  • docker rm web on a running container → cannot remove container "web": container is running: stop the container before removing or force remove. Use docker stop first, or docker rm -f.
Recap run (with -d -p -e --name -v --restart) → ps → logs -f → exec -it … sh → inspect -f/stats/top/cp. Debug order: ps -a (status + exit code) → logs → inspect.

Explain like I'm 5

A container is born (created), lives (running), naps (paused), goes to sleep (exited) and can wake up again — until you throw it away (removed).

Why did stop take 10 s and exit 137?

The process is PID 1 in its namespace, and the kernel doesn't apply default signal actions to PID 1 — a process that hasn't installed a SIGTERM handler (like sleep, or a Node app without one) ignores it. Docker waits out the grace period and SIGKILLs it. Fix: handle SIGTERM in the app, or run with --init.

server.js (excerpt — graceful shutdown)
const server = app.listen(PORT, HOST);

process.on('SIGTERM', () => {                 // sent by docker stop / Kubernetes
  console.log('SIGTERM received, closing HTTP server');
  server.close(() => process.exit(0));      // finish in-flight requests, then exit 0
});

With this, docker stop api returns in under a second and the status is Exited (0).

★ Putting it all together

The big idea

A container is just a Linux process that namespaces isolate and cgroups limit, started from a layered, read-only image — which is why it's tiny and fast compared to a VM. When you run docker run -d -p 5432:5432 postgres:16, the CLI calls dockerd over its socket, dockerd pulls the image from Docker Hub if needed, and containerd + runc start Postgres as PID 1. From there you drive it through its lifecycle with ps, logs, exec, stop and rm, read its exit code when it dies, and share your own images by tagging and pushing them — Session 7 shows how to build the TaskFlow image properly.

Quick self-check

Give four differences between a container and a VM.

Containers share the host kernel (VMs run their own guest kernel on a hypervisor); containers are MBs vs GBs; start in milliseconds/seconds vs minutes; isolation is process-level (weaker) vs hardware-level (stronger); higher density per host; Linux containers need a Linux kernel while VMs can run any OS.

What are namespaces and cgroups? One line each.

Namespaces control what a process can see (its own PIDs, network, mounts, hostname…). cgroups control how much it can use (memory, CPU, PIDs, I/O).

Trace docker run nginx through Docker's architecture.

The docker CLI sends a REST call to dockerd over /var/run/docker.sock; dockerd finds no local image, so it pulls docker.io/library/nginx:latest from Docker Hub; it asks containerd to create the container; containerd starts a shim, which uses runc to set up namespaces/cgroups and exec nginx as PID 1; output streams back to the CLI.

What does 0.0.0.0:8080->80/tcp in docker ps mean?

Port 8080 on every IPv4 interface of the host is forwarded to port 80 inside the container (TCP). It came from -p 8080:80.

A container shows Exited (137). List the likely causes and how to confirm.

137 = killed by SIGKILL: memory limit exceeded (check docker inspect -f '{{.State.OOMKilled}}' → true), someone ran docker kill, or docker stop's grace period expired because PID 1 ignored SIGTERM.

docker push taskflow-api:1.0 fails with "requested access to the resource is denied". Fix?

The image has no namespace, so Docker targets docker.io/library/taskflow-api, which you can't write to. docker login -u shauryav, docker tag taskflow-api:1.0 shauryav/taskflow-api:1.0, then docker push shauryav/taskflow-api:1.0.

Difference between --restart always and --restart unless-stopped?

Both restart the container whenever it exits. After you manually stop it and then the daemon/host restarts, always brings it back up, while unless-stopped leaves it stopped.
