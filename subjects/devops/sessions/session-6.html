1 Containers vs virtual machines

The problem: "works on my machine"

TaskFlow's API runs fine on your laptop. You copy it to the college server and it crashes:

Your laptop                        College server
Node.js 20                         Node.js 16
Postgres 16                        Postgres 12
macOS (arm64)                      Ubuntu (amd64)
taskflow-api listening on 3000     TypeError: tasks.findLast is not a function

findLast only arrived in Node 18. If you also copy your Mac's node_modules across, you get bcrypt_lib.node: invalid ELF header, because that native module was compiled for macOS. The code is the same on both machines. The environment is not.

The fix is to ship the environment with the code: the runtime, the libraries and the default config, packed into one unit that behaves the same on the laptop, in CI and on the server. There are two ways to build that unit.

The idea

A virtual machine fakes a whole computer. A hypervisor gives each VM virtual hardware, and each VM boots a complete guest OS with its own kernel. A container fakes nothing. It is an ordinary Linux process that the host kernel fences off and gives its own filesystem. Every container on a host shares that one kernel.

          Virtual machines                                  Containers
 ┌─────────┐ ┌─────────┐ ┌─────────┐          ┌─────────┐ ┌─────────┐ ┌─────────┐
 │ App A   │ │ App B   │ │ App C   │          │ App A   │ │ App B   │ │ App C   │
 │ Bins/Lib│ │ Bins/Lib│ │ Bins/Lib│          │ Bins/Lib│ │ Bins/Lib│ │ Bins/Lib│
 │ Guest OS│ │ Guest OS│ │ Guest OS│          └─────────┘ └─────────┘ └─────────┘
 │ +kernel │ │ +kernel │ │ +kernel │          ┌─────────────────────────────────┐
 └─────────┘ └─────────┘ └─────────┘          │ Container engine (Docker)       │
 ┌─────────────────────────────────┐          ├─────────────────────────────────┤
 │ Hypervisor (KVM, ESXi, Hyper-V) │          │ Host OS — ONE shared kernel     │
 ├─────────────────────────────────┤          ├─────────────────────────────────┤
 │ Hardware                        │          │ Hardware (or a cloud VM)        │
 └─────────────────────────────────┘          └─────────────────────────────────┘

Compare the two stacks row by row. Only one row really differs: Guest OS + kernel. VMs repeat it for every app. Containers don't have it at all.

Think of it like this

VMs are separate houses. Each one has its own foundation, plumbing and wiring (its own kernel). Containers are rooms in one hotel. Each room has its own lock and its own furniture (its own files and processes), but every room uses the building's plumbing (the host kernel). Building a house takes months. Opening a room takes a key card.

See it: one kernel, many containers

The smallest proof: ask the host which kernel it runs, then ask a container the same question.

$ uname -r                                    # on the Ubuntu host
6.8.0-85-generic
$ docker run --rm alpine:3.20 uname -r        # inside a container
6.8.0-85-generic
TokenMeaning
dockerThe Docker command-line client
runCreate a container from an image and start it
--rmDelete the container as soon as it exits, because this is a one-off
alpine:3.20The image (alpine, tag 3.20): an ~8 MB Linux userland. Docker downloads it the first time.
uname -rThe command to run inside the container, in place of the image's default command

The version is the same because there is only one kernel. Now ask which OS the container is:

$ docker run --rm alpine:3.20 head -2 /etc/os-release
NAME="Alpine Linux"
ID=alpine

A different "OS" runs on the same kernel. The OS inside a container is only a userland: the files in /bin, /lib and /etc that came with the image.

What it does not do: boot anything. There is no BIOS, no kernel loading, no init system and no login. Docker started one process (uname), which printed a line and exited, and --rm deleted the container, all in well under a second. A VM would still be booting.

Build it up: TaskFlow three ways

TaskFlow needs an API, a database and a web server. Here's the bill each way:

As 3 VMs                                   As 3 containers
api → Ubuntu guest (≈2 GB) + Node + code   api → node:20-alpine + code   (≈180 MB)
db  → Ubuntu guest (≈2 GB) + Postgres      db  → postgres:16             (≈640 MB)
web → Ubuntu guest (≈2 GB) + nginx         web → nginx:1.27-alpine       (≈77 MB)
3 kernels to boot, ≈6 GB of OS before      no extra kernels; each starts in about a
your code even runs                        second; shared base layers stored once

That is why containers win on speed and density. It's also their weak spot. One shared kernel is one shared point of failure, so a VM's isolation is stronger. In the cloud you usually get both, because your containers run inside VMs (EC2 instances).

Exam trap

"Docker creates a lightweight virtual machine for every application." ✗ Wrong. Docker uses no hypervisor, no virtual hardware and no guest kernel. A container is an isolated process on the host's kernel.

"Containers are more isolated than VMs." ✗ It's the other way round. VMs have a hardware-level boundary. Containers share a kernel.

"The kernel is shared, so a Linux host can run Windows containers." ✗ The app has to match the kernel, so Linux containers need a Linux kernel.

Remember

VM = virtual hardware + its own kernel.
Container = isolated process + the host's kernel.

Mastery check
Q1. In one sentence: what is the fundamental difference between a VM and a container?

A VM virtualises hardware and boots its own guest OS and kernel on a hypervisor. A container is an isolated process that shares the host's kernel and brings only its own files.

Q2. Host OS → Docker → Container A (Node.js app) and Container B (Python app). How many kernels are running?

One: the host's. A and B have different userlands (different files and libraries), but neither has a kernel of its own. Both make system calls into the same host kernel.

Q3. Predict: the Ubuntu host runs kernel 6.8.0-85-generic. What does docker run --rm ubuntu:22.04 uname -r print?

6.8.0-85-generic, not Ubuntu 22.04's usual 5.15 kernel. The ubuntu:22.04 image contains 22.04's files but no kernel, so uname reports the host's.

Q4. Fill in: a VM runs on a ________ and boots its own ________; a container is a ________ that shares the host's ________.

Hypervisor · kernel (OS) · process · kernel.

2 Isolation: namespaces & cgroups

The problem

Section 1 said every container shares one kernel. That should worry you:

                       one host kernel
          ┌───────────────────┼───────────────────┐
     taskflow-db         taskflow-api       someone-elses-app
     (Postgres)          (Node)             (buggy, or hostile)

They are all just processes on one kernel. So what stops someone-elses-app from listing Postgres's processes, grabbing port 5432 first, or reading /var/lib/postgresql? And what stops it from eating all 4 GB of RAM until the database gets killed?

The idea

The Linux kernel has two features for this, and Docker switches both on for every container:

  • Namespaces control what a process can see. Each container gets its own view of processes, network, filesystem and hostname.
  • cgroups (control groups) control how much a process can use: memory, CPU, number of processes and disk I/O.
 container A                             container B
 sees:    its own processes (PID 1, 2 …)  sees:    its own processes (PID 1, 2 …)
          its own IP address + ports               its own IP address + ports
          its own files + hostname                 its own files + hostname
 may use: 512 MB RAM, 2 CPUs              may use: 256 MB RAM, 1 CPU
     │        namespaces = the walls  (what you see)        │
     │        cgroups    = the meters (what you use)        │
     └───────────────────── one host kernel ────────────────┘
Think of it like this

Back to the hotel. Namespaces are the walls and the door lock: from inside your room you only see your own things, and every room counts its guests from 1 (each container has its own PID 1). cgroups are each room's circuit breaker: draw more power than your share and the breaker trips (memory) or the lights dim (CPU). Reception (the host) can still see into every room.

See it: namespaces

$ docker run --rm ubuntu:24.04 sh -c 'hostname; ps -e'
efb215124d96
    PID TTY          TIME CMD
      1 ?        00:00:00 sh
      8 ?        00:00:00 ps
TokenMeaning
sh -c '…'Run a tiny shell script inside the container: two commands separated by ;
hostnamePrints the container's own hostname (UTS namespace): its short ID, not your machine's name
ps -eLists every process this container can see (PID namespace)

Notice that there are only two processes, and sh is PID 1. The host is running hundreds of processes, and the PID namespace hides all of them.

What it does not do: hide the container from the host. Isolation works one way only. On the host, the container's processes are ordinary processes with ordinary PIDs (docker top shows them in section 7).

See it: cgroups

$ docker run --rm -m 256m --cpus 0.5 ubuntu:24.04 cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max
268435456
50000 100000
TokenMeaning
-m 256mMemory limit of 256 MiB for this container
--cpus 0.5At most half of one CPU core
/sys/fs/cgroup/memory.maxThe kernel file holding the cgroup's memory cap: 268435456 bytes = 256 × 1024 × 1024
/sys/fs/cgroup/cpu.max50000 100000 = 50 ms of CPU time per 100 ms period, which is half a core

What happens at the limit depends on the resource. Use too much memory and the kernel's OOM killer kills the process, so the container shows Exited (137) (section 8). Use too much CPU and the process is throttled (slowed down), but never killed.

What it does not do: set any limits unless you ask. Without -m and --cpus, a container can use all of the host's memory and CPU.

The full list (for reference)

Linux has seven namespaces, and a container gets its own of each: pid (process tree, so the app is PID 1), net (interfaces, IP, ports, routes), mnt (mounts, so the image's files appear at /), uts (hostname), ipc (shared memory, message queues), user (UID mapping, so root inside can be unprivileged outside, if enabled) and cgroup (its view of the cgroup tree). cgroups can limit memory, CPU, the number of PIDs (which stops a fork bomb) and block I/O.

Exam trap

"Namespaces limit how much memory a container can use." ✗ Namespaces control visibility. cgroups control limits.

"Root inside a container is harmless because the container is isolated." ✗ It's the same kernel. One kernel bug or one careless mount (-v /:/host), and root in the container is root on the host. Run apps as a non-root user (Session 7: USER node).

"The host can't see processes inside a container." ✗ It can. ps aux on the host lists them.

Remember

Namespaces → what you can see (isolation)
cgroups → how much you can use (resource control)

Mastery check
Q1. Container A runs ps aux. Container B is running 20 processes. Why doesn't A see them?

A runs in its own PID namespace, so the kernel shows it only its own process tree. B isn't "unreachable". It just isn't part of A's view of the system.

Q2. You started the API with -m 512m. A memory leak pushes it towards 10 GB. What stops it, and what do you see?

The cgroup memory limit. Once usage passes 512 MiB, the kernel's OOM killer kills the process. The container shows Exited (137), and docker inspect reports OOMKilled: true.

Q3. Fill in: containers share the ________, but use ________ for isolation and ________ for resource control.

Kernel · namespaces · cgroups.

Q4. Predict: a container started with --cpus 0.5 runs a CPU-heavy loop. Is it killed or slowed?

Slowed. It is throttled to 50 ms of CPU per 100 ms. Only going over a memory limit gets a process killed.

Q5. Inside a container your app is PID 1. Is it PID 1 on the host too?

No. The PID namespace gives the container its own numbering. On the host it's an ordinary process with a normal PID such as 12345 (docker top or docker inspect -f '{{.State.Pid}}'). It's one process seen from two views.

3 Docker architecture

The problem

On a fresh Ubuntu server where the Docker service isn't running, type the command you'll use most:

$ docker ps
Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?

The docker command is installed and works, yet it can't do anything on its own. The opposite surprise also happens: start a container in the background, close your terminal, and the container keeps running. Both facts point the same way. The program you type is not the program that runs containers.

The idea

Docker is client–server. The docker command is a client that only sends requests. A background service, the Docker daemon (dockerd), does the work: it pulls images, creates and starts containers, and manages networks and volumes. When the daemon needs an image it doesn't have, it downloads it from a registry, which is Docker Hub by default.

 You
  │  docker run nginx
  ▼
 Docker CLI (client) ── REST API over /var/run/docker.sock ──▶ Docker daemon (dockerd)
                                                                  │ 1. is "nginx" here?
                         Registry (Docker Hub) ◀── 2. no → pull ──┤
                                                                  │ 3. create container
                                                                  ▼ 4. start it
                                                            nginx container
Think of it like this

A restaurant. You are the customer. The CLI is the waiter: it takes your order to the kitchen and brings back the result, but it cooks nothing. The daemon is the kitchen, where all the work happens. The registry is the supermarket the kitchen buys ingredients (images) from when the fridge is empty. If the kitchen is closed, all the waiter can say is "Cannot connect".

See it: hello-world

Docker's own test image prints this exact architecture:

$ docker run hello-world
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
58dee6a49ef1: Pull complete
Digest: sha256:5e23090353324d887c48ad5e5c56d294eab81588df9605b07d1afe895f9cc8f8
Status: Downloaded newer image for hello-world:latest

Hello from Docker!
…
To generate this message, Docker took the following steps:
 1. The Docker client contacted the Docker daemon.
 2. The Docker daemon pulled the "hello-world" image from the Docker Hub.
    (amd64)
 3. The Docker daemon created a new container from that image which runs the
    executable that produces the output you are currently reading.
 4. The Docker daemon streamed that output to the Docker client, which sent it
    to your terminal.

Read it against the diagram. Unable to find image … locally is step 1: the daemon checked its own image store, and because you gave no tag it assumed :latest. Pulling from library/hello-world is step 2. The four numbered lines are steps 1–4 in Docker's own words.

What it does not do: the CLI downloaded nothing and ran nothing. Also, the container didn't keep running: it printed its message and exited. It now sits there stopped, and you'll clean it up in section 8.

Build it up: look inside

Two programs, two versions

$ docker version                 # trimmed

  Version:          29.7.2

The output has a Client block and a Server block because they are two separate programs. If the Server block is missing and you get "Cannot connect", the daemon isn't running or you can't reach its socket. docker info adds daemon-wide details: container and image counts, storage driver, cgroup version, and the Docker Root Dir (/var/lib/docker, where images and volumes live).

The CLI is just an HTTP client

$ ls -l /var/run/docker.sock
srw-rw---- 1 root docker 0 Oct  9 09:58 /var/run/docker.sock      # s = socket; root + group "docker" may use it
$ curl -s --unix-socket /var/run/docker.sock http://localhost/containers/json | jq -r '.[].Names[0]'
/web
/taskflow-db                       # the same data "docker ps" shows

curl talked to the daemon directly and got the container list. All docker ps does is send that same request and format the reply as a table.

Under the hood: the daemon delegates too

 docker CLI ── REST API over /var/run/docker.sock ──▶ dockerd  (Docker daemon / "Docker Engine")
 (client: docker run, ps, build…)                       │  manages images, containers, networks, volumes, builds
                                                         │  gRPC
                                                         ▼
                                                    containerd  (pulls & stores images, supervises containers)
                                                         │
                                               containerd-shim-runc-v2  (one per container; lets it outlive
                                                         │                a containerd restart)
                                                         ▼
                                                       runc  (OCI runtime: sets up namespaces + cgroups, execs PID 1, exits)
                                                         ▼
                                              your process, e.g. nginx  (PID 1 inside the container)

 dockerd ◀────── pull / push over HTTPS ──────▶ Registry (Docker Hub docker.io, ghcr.io, ECR …)

You only ever talk to dockerd, and each layer below it does one job. The shim is why a container survives a containerd restart. With "live-restore": true in the daemon config, containers also keep running while dockerd restarts or is upgraded. dockerd manages four kinds of objects: images and containers (this session), plus volumes and networks (Session 8). Images and runtimes follow the OCI (Open Container Initiative) specs, so an image built by Docker runs unchanged on containerd, Podman or Kubernetes.

The two errors everyone hits 
Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?
$ sudo systemctl enable --now docker            # start it now and on every boot

permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock
$ sudo usermod -aG docker $USER && newgrp docker # join the docker group (or log out and in)

The docker group is equivalent to root: docker run -v /:/host … can read any file on the machine. Add only trusted users, and never expose docker.sock to the internet or mount it into untrusted containers.

Exam trap

"The docker command creates and runs containers." ✗ The CLI only sends API requests. dockerd creates and runs containers, through containerd and runc. That split is why one CLI can control a daemon on another machine.

"Kubernetes removed Docker in v1.24, so Docker images don't run on Kubernetes." ✗ Kubernetes removed dockershim (its built-in Docker Engine integration). It now runs containers through containerd or CRI-O, and Docker-built images are standard OCI images that run fine.

Remember

Client = asks · Daemon = does · Registry = stores
CLI → dockerd → containerd → shim → runc → your process

Mastery check
Q1. You type docker run nginx. Which component receives it first, and which one actually creates the container?

You type into the Docker CLI (the client), which sends a REST request to dockerd over /var/run/docker.sock. dockerd creates the container, delegating to containerd and runc. If the image is missing, the daemon pulls it from the registry. The CLI only shows the progress.

Q2. docker version prints the Client block, then "Cannot connect to the Docker daemon…". What's wrong, and what do you try first on Ubuntu?

The client works but can't reach a daemon, so the daemon isn't running. Check with sudo systemctl status docker and start it with sudo systemctl enable --now docker. If the error says "permission denied" instead, add yourself to the docker group.

Q3. Match dockerd, containerd, runc: (a) serves the API the CLI calls; (b) sets up namespaces/cgroups, execs PID 1, then exits; (c) stores images and supervises containers, and is used by Kubernetes too.

(a) dockerd · (b) runc · (c) containerd.

Q4. Why does curl --unix-socket /var/run/docker.sock http://localhost/containers/json return the same data as docker ps?

The CLI is just an HTTP client for the daemon's REST API on that socket. Both send the same request. The CLI only formats the JSON reply as a table.

4 Docker images: layers

The problem

To run TaskFlow's API you need all of this, in exactly these versions:

Alpine Linux userland  (/bin, /lib, /etc)
Node.js 20 + npm
node_modules           (express, pg, prom-client …)
server.js, package.json
"start it with: node server.js, port 3000"

Installing that by hand on every machine is the "works on my machine" problem all over again. And when you want three copies of the API, they should all start from identical files, without three separate installs, and without one copy's changes leaking into the others.

The idea

An image is a read-only template: a stack of filesystem layers plus a little config (default command, environment variables, working directory, ports). A container is created from an image, and Docker adds one thin writable layer on top for that container alone.

   container 1        container 2        container 3
  ┌───────────┐      ┌───────────┐      ┌───────────┐
  │ writable  │      │ writable  │      │ writable  │   ← one per container, deleted with it
  └─────┬─────┘      └─────┬─────┘      └─────┬─────┘
        └──────────────────┼──────────────────┘
  ┌────────────────────────┴─────────────────────────┐
  │ COPY . .           your code                     │ ← layer 4
  │ RUN npm ci         node_modules                  │ ← layer 3    IMAGE: read-only,
  │ COPY package*.json                               │ ← layer 2    stored once, shared
  │ FROM node:20-alpine   Alpine + Node 20           │ ← layer 1 (really a few)
  └──────────────────────────────────────────────────┘
    + config: CMD ["node","server.js"]  WORKDIR /app  ENV PORT=3000

Each layer holds the files that one build step added or changed. You'll write those steps in a Dockerfile in Session 7. Three things follow from this design:

  • Layers are shared. Three containers from one image store it once. Two images built on the same base share the base layers, on disk and over the network.
  • Layers are cached. Change only server.js and rebuild: Docker reuses the unchanged layers below it (Session 7).
  • Read-only means safe. A container can't damage its image or its siblings. Anything it writes goes into its own writable layer. If it edits a file that came from the image, Docker first copies that file up into the writable layer (copy-on-write).
Think of it like this

Image = class, container = object. The class is a definition and doesn't change when you use it. docker run is new: it gives you a fresh instance. The writable layer is that object's own fields. You can make many objects from one class, and deleting an object doesn't touch the class.

See it: the writable layer

Start two containers from the same image, write a file in one of them, and look for it in the other:

$ docker run -d --name a alpine:3.20 sleep 600
$ docker run -d --name b alpine:3.20 sleep 600
$ docker exec a sh -c 'echo "remember milk" > /note.txt'
$ docker exec a cat /note.txt
remember milk
$ docker exec b cat /note.txt
cat: can't open '/note.txt': No such file or directory
$ docker diff a
A /note.txt
$ docker diff b                  # prints nothing: b hasn't changed anything
TokenMeaning
-dRun in the background (detached)
--name aCall the container a so you can refer to it
sleep 600The container's process: sleep for 10 minutes, which keeps it alive long enough to poke at
docker exec a …Run an extra command inside the running container a (more in section 7)
docker diff aList what changed in a's writable layer compared with the image: A added · C changed · D deleted

Now delete a and start a fresh container from the same image:

$ docker rm -f a
a
$ docker run --rm alpine:3.20 cat /note.txt
cat: can't open '/note.txt': No such file or directory

The note was deleted along with a's writable layer. The image never had it.

What it does not do: writing inside a container never changes the image. The writable layer also isn't storage you can rely on, because docker rm deletes it. Data that must survive, like Postgres's tables, goes in a volume (Session 8).

Build it up: what's actually in an image

$ docker image inspect -f 'cmd={{json .Config.Cmd}} layers={{len .RootFS.Layers}}' alpine:3.20
cmd=["/bin/sh"] layers=1

alpine is one layer of files plus config that says "by default, run /bin/sh". That config is why docker run -it alpine:3.20 drops you into a shell. Real application images have more layers. In section 5 you'll list nginx's layers and prove that two images share some.

Exam trap

"Running a container modifies its image." ✗ Writes go into the container's writable layer. The image is read-only.

"Each container gets its own full copy of the image." ✗ Image layers are stored once and shared. Each container adds only its thin writable layer (copy-on-write).

"Data written inside a container survives docker rm." ✗ It survives stop and start, but rm deletes the writable layer. Use volumes.

Remember

Image = class (read-only layers + config) · Container = object (image + its own writable layer)
One image → many containers.

Mastery check
Q1. Give two advantages of building images out of layers. ("You can make many containers" doesn't count: that's true of any image.)

Storage and transfer efficiency: images with a common base share those layers, so they're stored and downloaded once. Build caching: unchanged layers are reused on rebuild, so builds are fast.

Q2. An image holds Ubuntu + Python + your app. You start 3 containers, and container 1 edits /app/config.py. Does that change the image? Container 2?

Neither. Copy-on-write copies config.py into container 1's writable layer and edits it there. The image layers stay read-only, and container 2 still sees the original file.

Q3. Fill in: the writable layer belongs to the ________ and is deleted by docker ________.

Container · rm. stop keeps it, so the files are still there after start.

Q4. Spot the misconception: "I'll docker exec into the container and apk add curl, so every future container from this image has curl."

The install lands in that one container's writable layer. New containers start from the unchanged image without curl. To change the image you build a new one (a RUN line in a Dockerfile, Session 7).

Q5. Predict docker diff after a container runs rm /etc/motd; mkdir /app; echo x > /app/out.log.

A /app, A /app/out.log, C /etc, D /etc/motd. The deleted file is still in the image. The writable layer only records "deleted here" and hides it.

5 Getting images: pull, tags, build

The problem

You type postgres. Which Postgres: 16 or 17? Built for amd64 or arm64? Downloaded from where? And if you pulled latest in July and your teammate pulled latest today, are you running the same thing? (Not necessarily.)

The idea

Every image has a full name that answers four questions: from where, whose, what, and which version. You usually type the short form and Docker fills in the rest:

  docker.io  /  shauryav  /  taskflow-api  :  1.0
  └registry┘   └namespace┘   └repository┘     └tag┘
   default:     default: library                default:
   docker.io    (= official images)             latest

  nginx   ⇒   docker.io/library/nginx:latest

A tag is a human-readable label that the publisher can move to a newer build. A digest (@sha256:…) is a hash of the image's content, so it can never change. docker pull downloads an image's layers from the registry into the daemon's local image store.

Think of it like this

It's Git again (Session 5). A tag is like a branch name: a movable pointer, so main today isn't main next week. A digest is like a commit SHA: it names one exact content forever. And docker pull is like git fetch: it downloads, but doesn't change anything that's running.

Q1. What is the difference between docker pull nginx and docker run nginx?

Q3. Two servers both run myapp:latest but behave differently. How is that possible, how do you prove it, and how do you prevent it?

Q4. A pull shows 6e771e15690e: Already exists. What did Docker skip, and why could it?

It skipped downloading that layer. Layers are content-addressed, and an identical layer from another image (here, the base layers from taskflow-api:1.0) was already in the local store.

Q5. In the 4-line Dockerfile, when does CMD ["node", "hello.js"] run: during docker build, or later?

Later. CMD only records the default command in the image's config. It runs each time a container starts, unless you override it (docker run taskflow-hello:v1 node -v).

The problem

taskflow-api:1.0 exists only in your laptop's image store. The EC2 server, your teammate and the CI runner all need it. You could docker save it into a 200 MB tarball and scp it around, for every version, forever. Code has GitHub to solve this. Images need the same thing.

The idea

A registry is a server that stores images and serves them over HTTPS. Docker Hub (docker.io) is Docker's default public registry. It holds repositories, one per image (shauryav/taskflow-api), and each repository holds tags (1.0, 1.1, latest). You push once, and anyone with access can pull anywhere.

Q1. docker push taskflow-api:1.0 fails with "requested access to the resource is denied". Why, and which three commands fix it?

7 Docker containers

The problem

You have the postgres:16 image. TaskFlow needs a database that is actually running: in the background, with a user and password, reachable on port 5432, with a name you can type, and with logs you can read when it misbehaves. The image does none of that. All of it is configuration on the container.

The idea

docker run = create a container from an image + start it. Everything between run and the image configures that container. Anything after the image replaces the image's default command:

docker run  -d --name web -p 8080:80   nginx:1.27-alpine   [COMMAND] [ARG…]
            └─────── OPTIONS ──────┘   └───── IMAGE ─────┘   └─ replaces CMD ─┘
              "how to run it"           "what to run"        "run this instead"

A container has its own network namespace (section 2), so its port 80 is invisible from outside until you publish it:

 browser ──▶ localhost:8080 ──── -p 8080:80 ────▶ container 172.17.0.3:80 ──▶ nginx
             └ HOST port ─┘                       └── CONTAINER port ───┘
Think of it like this

Back at the hotel, each room has its own phone extension (the container's port 80), but outsiders can only dial the hotel's main number. -p 8080:80 tells reception: "calls to 8080 go to that room's extension 80." docker run checks a new guest into a new room. docker exec knocks on a room that's already occupied and lets you in.

  • A second container on the same host port fails with Bind for 0.0.0.0:8080 failed: port is already allocated. Pick another host port (-p 8081:80) or stop the first container.
  • curl localhost:8080 works on the server but not from your laptop. -p did its job, but the server's firewall or security group must also allow port 8080 (Session 21). The reverse also applies: -p 127.0.0.1:8080:80 deliberately limits access to the server itself.
Exam trap

"docker run nginx -p 8080:80 publishes port 8080." ✗ Everything after the image goes to the container's command, so nginx receives -p 8080:80 as arguments. Flags go before the image.

"In -p 8080:80, 8080 is the container's port." ✗ The format is HOST:CONTAINER, so 8080 is on the host and 80 is inside.

"docker exec starts a new container." ✗ It runs an extra process inside an existing, running container.

Remember

docker run [OPTIONS] IMAGE [COMMAND]: options before, command after.
-p HOST:CONTAINER = outside:inside.
Debug order: ps -a → logs → exec → inspect.

Mastery check
Q1. Spot the bug: docker run nginx:1.27-alpine -d --name web -p 8080:80

The flags come after the image, so Docker passes them to nginx as its command. The container runs in the foreground with no name and no published port, and nginx probably fails on the unknown arguments. Fix: docker run -d --name web -p 8080:80 nginx:1.27-alpine.

Q2. The API listens on 3000 inside the container. You run it with -p 8080:3000. Which URL works from your laptop, and what does curl localhost:3000 give?

http://localhost:8080 works, because host port 8080 forwards to container port 3000. localhost:3000 gives "connection refused": nothing on the host is listening on 3000.

Q3. You exit the shell from docker exec -it web sh. Does nginx stop? What if you exit from docker run -it ubuntu:24.04 bash instead?

With exec, nginx keeps running: your shell was an extra process, and nginx is still PID 1. With run, bash was PID 1, so the container stops.

Q4. Predict: the API already holds host port 3000, and you run docker run -d -p 3000:80 nginx:1.27-alpine. What happens?

It fails with Bind for 0.0.0.0:3000 failed: port is already allocated, and docker exits 125 (Docker's own error, section 8). Only one container can hold host port 3000, even though nginx uses port 80 inside. (The new container is still created and left in the Created state.) Use another host port, such as -p 3001:80.

8 Container lifecycle

The problem

Three puzzles you'll hit in your first week:

$ docker run -d ubuntu:24.04    # a second later it's gone from docker ps. Crash?
$ docker stop api               # takes exactly 10 seconds, every time. Why 10?
$ sudo reboot                   # afterwards taskflow-db is up but web isn't. Who decided?

All three are lifecycle questions: what state a container is in, what moves it from one state to another, and what happened to its main process.

The idea

A container is always in one state: created → running ⇄ paused → exited → removed. Behind most surprises is one rule: a container runs exactly as long as its main process (PID 1) runs. When PID 1 exits, the container has exited.

   IMAGE ─────────────────────▶ CREATED ───────────────────────▶ RUNNING ◀──────────┐

Think of it like this

A laptop. create = unboxed but switched off. start = power on. pause = sleep mode: everything frozen, memory kept. stop = shut down: it asks programs to save and quit (SIGTERM) and pulls the plug if they don't (SIGKILL), but the disk (the writable layer) is kept. rm = throw it away: the disk is gone, but the factory (the image) can make another one.

Build it up

The main-process rule

$ docker run -d --name ubu ubuntu:24.04
$ docker ps -a --filter name=ubu --format '{{.Names}}\t{{.Command}}\t{{.Status}}'
ubu	"/bin/bash"	Exited (0) 2 seconds ago

That solves puzzle 1. The ubuntu image's default command is bash. With no terminal attached, bash reads end-of-input and exits straight away. PID 1 is gone, so the container has exited. Exit code 0 means this is not a crash. The hello container from section 5 did the same thing: node finished the script. nginx keeps running because nginx -g 'daemon off;' stays in the foreground forever. That's also why each container runs one main process: SSH plus five services inside one container is treating it like a VM.

Why did stop take 10 s and exit 137? (puzzle 2)

The process is PID 1 in its namespace, and the kernel doesn't apply default signal actions to PID 1. A process that hasn't installed a SIGTERM handler (like sleep, or a Node app without one) simply ignores the signal. Docker waits out the grace period, then sends SIGKILL. Fix it by handling SIGTERM in the app, or by running with --init.

server.js (excerpt — graceful shutdown)
const server = app.listen(PORT, HOST);

process.on('SIGTERM', () => {                 // sent by docker stop / Kubernetes
  console.log('SIGTERM received, closing HTTP server');
  server.close(() => process.exit(0));      // finish in-flight requests, then exit 0
});

Installing a handler means SIGTERM is no longer ignored, even though Node is PID 1. server.close() lets in-flight requests finish, then the process exits 0. With this handler, docker stop api returns in under a second with Exited (0) instead of 137.

"Exited (0) means it crashed." ✗ 0 means success: the main process finished.

Mastery check
Q1. You run docker create --name web nginx. Is nginx running? What do docker ps and docker ps -a show?

No. The container exists in the Created state, but no process has started. docker ps (running only) doesn't list it. docker ps -a shows it with STATUS Created. Run docker start web to start it.

Q2. You run docker start web twice. What happens the second time?

Effectively nothing. The container is already running, so Docker prints web and exits 0. It doesn't start a second copy and doesn't raise an error. start acts on an existing container. It never creates one.

Q3. You write a file inside a container, then docker stop and docker start it. Is the file still there? What about after docker rm + a new docker run?

After stop and start, yes: it's the same container with the same writable layer. After rm and a new run, no: rm deleted that writable layer, and the new container starts fresh from the image. Use a volume for anything that must last.

Q4. Your console.log("Hello") container exits immediately, but an nginx container keeps running. Why?

A container runs only while its main process runs. node hello.js prints and finishes, so the container exits with code 0. nginx (started with daemon off;) stays in the foreground serving requests, so PID 1 never ends.

Q5. docker ps -a shows Exited (137) and inspect says OOMKilled=true. What happened, and what are two fixes?

The process went over its cgroup memory limit (-m), so the kernel's OOM killer sent SIGKILL (128 + 9 = 137). Fixes: raise the limit (-m 512m), or find and fix the memory leak or usage spike in the app.

★ Putting it all together

The big idea

A container is just a Linux process that namespaces isolate and cgroups limit, started from a layered, read-only image. That's why it's tiny and fast compared with a VM. When you run docker run -d -p 5432:5432 postgres:16, the CLI calls dockerd over its socket, and dockerd pulls the image from Docker Hub if it's missing. Then containerd and runc start Postgres as PID 1 with a fresh writable layer on top. From there you drive the container through its lifecycle with ps, logs, exec, stop and rm, read its exit code when it dies, and share your own images by tagging and pushing them. Session 7 shows how to build the TaskFlow image properly.

Final mastery check — combine everything
Q1. Fresh Ubuntu server. You run docker run -d --name taskflow-db -e POSTGRES_PASSWORD=devpass -p 5432:5432 postgres:16. List what happens, component by component, and the state the container ends in.

The CLI turns the command into REST calls to dockerd over /var/run/docker.sock. dockerd finds no postgres:16 locally, so it pulls docker.io/library/postgres:16 layer by layer from Docker Hub. It then creates the container (a writable layer on the read-only image layers, plus the env var and port binding) and hands it to containerd. containerd's shim calls runc, which sets up namespaces (own PIDs, own network with a 172.17.x IP, own mounts) and cgroups (no limits, since none were given), execs Postgres as PID 1 and exits. Host port 5432 now forwards to the container's 5432, and -d makes the CLI print the ID and return. The final state is running (Up), for as long as Postgres runs.

Q2. Your teammate pulled shauryav/taskflow-api:latest and /tasks returns 500. It works on your laptop "with the same image". Give two likely causes and the commands that prove each.

(1) It's not the same image. latest moved between your pulls. Compare docker image inspect -f '{{json .RepoDigests}}' shauryav/taskflow-api:latest on both machines. Fix it by deploying :1.1 or a digest. (2) The environment outside the image differs, for example a missing DATABASE_URL or no database reachable. Check docker logs api and docker exec api env. (A third possibility is a CPU architecture mismatch, which shows up as exec format error in the logs.)

Q3. The API runs with -m 256m --restart unless-stopped. Its STATUS keeps flipping to Restarting (137) and RestartCount climbs. Which two features are interacting? How do you confirm, and how do you fix it?

The cgroup memory limit and the restart policy. The app goes over 256 MiB, the OOM killer sends SIGKILL (137), the restart policy starts it again, and the cycle repeats: a crash loop. Confirm with docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}' api → true 7, and watch docker stats. Fix it by giving the app more memory (recreate with a bigger -m) or fixing the leak.

Q4. You run docker rm -f taskflow-db, then the exact same docker run command from section 7 (the one with -v taskflow-pgdata:…). Are your tasks still there? What if the original command had no -v?

With -v: yes. The data lived in the named volume, not in the container's writable layer, and rm only deletes the container. Without -v: the new container starts with an empty database, because nothing connects the old data to it. (The postgres image actually puts its data in an anonymous volume, which is left orphaned. More in Session 8.)

Q5. Correct every error: "The docker CLI boots a small VM for each image. Changes are saved into the image, and docker stop deletes the container."

(1) The daemon does the work (via containerd and runc), not the CLI. (2) It's not a VM. It's an isolated process on the shared host kernel, and it runs per container, not per image. (3) Changes go into the container's writable layer, because images are read-only. (4) stop only moves the container to Exited and keeps its writable layer. rm deletes it.

Q6. You built taskflow-api:1.1 on your laptop. Write the commands, in order, to get it running on a fresh EC2 server so that it survives reboots, then check that it's healthy.

Laptop: docker login -u shauryav → docker tag taskflow-api:1.1 shauryav/taskflow-api:1.1 → docker push shauryav/taskflow-api:1.1. Server: docker run -d --name api -p 3000:3000 -e PORT=3000 --restart unless-stopped shauryav/taskflow-api:1.1 (it pulls automatically). Check with docker ps (Up), docker logs api, then curl localhost:3000/health → {"status":"ok"}. In real use you'd also pass DATABASE_URL.
