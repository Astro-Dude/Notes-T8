Viva trap

"A comment at the end of a line is fine: .env # secrets." ✗ In .gitignore and .dockerignore, # starts a comment only at the start of a line. That line is the pattern .env # secrets, which matches nothing, so .env gets committed. In a Dockerfile the text becomes an argument. Comments go on their own line.

"Require 1 approval on main, to be safe." ✗ On a solo project you can't approve your own PR, so nothing could ever merge. Use 0 approvals plus required status checks.

Viva check
Q1. Predict: with this .gitignore, are .env.production and .env.example committed?

.env.production is ignored (it matches .env.*). .env.example is committed: the later !.env.example re-includes it, and in .gitignore the last matching rule wins.

Q2. You rename the job name: Unit tests to name: Tests. What happens to the next PR?

The ruleset still requires a check called Unit tests, which never reports again, so the PR waits on "Expected — Waiting for status" forever. Re-select the required checks in the ruleset after renaming.

Step 2 — Dockerize (Session 7, Session 8)

Why this step

Kubernetes runs images, not repos. This step produces the one artifact every later step ships, and makes the tests a build gate: if a test fails, no image exists to deploy. The runtime stage keeps only what production needs, so the image is small, non-root and has less for Trivy to flag.

 build stage  (FROM … AS build)                   runtime stage  (FROM … AS runtime)
   npm ci                all deps, incl. jest        + tini (PID 1)        − npm, npx
   COPY . .                                          node_modules  ◀── COPY --from=build (prod deps only)
   RUN npm test          a failing test stops here   package.json, server.js ◀── COPY --from=build
   npm prune --omit=dev  drops jest, supertest       USER node · ENTRYPOINT tini · CMD node server.js
   └─ thrown away after the build                    └─ the only stage that is pushed and deployed

Session 7's final Dockerfile with two changes: NODE_VERSION=22 and npm removed from the runtime stage.

Dockerfile
# syntax=docker/dockerfile:1

# Node major version: 22 is LTS (Node 20 reached end-of-life on 30 Apr 2026)
ARG NODE_VERSION=22

# ================= Stage 1: build — all deps + tests =================
FROM node:${NODE_VERSION}-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
# the build FAILS here if any test fails → no broken image is produced
RUN npm test
# drop devDependencies (jest, supertest) from node_modules
RUN npm prune --omit=dev

# ================= Stage 2: runtime — only what prod needs =================
FROM node:${NODE_VERSION}-alpine AS runtime
# tini: tiny init for PID 1 — forwards signals, reaps zombies
RUN apk add --no-cache tini
# npm/npx are not needed at runtime; their bundled packages are a common source of Trivy HIGH findings
RUN rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx
WORKDIR /app
ENV NODE_ENV=production \
    PORT=3000
LABEL org.opencontainers.image.title="taskflow-api" \
      org.opencontainers.image.source="https://github.com/shauryav/taskflow"
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/package.json /app/server.js ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://127.0.0.1:3000/health || exit 1
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "server.js"]
LineWhy it's there
# syntax=docker/dockerfile:1Parser directive (must be line 1): latest stable Dockerfile syntax via BuildKit.
ARG NODE_VERSION=22One place to change the Node major; override with --build-arg NODE_VERSION=24.
RUN --mount=type=cache … npm ciExact lockfile versions; npm's download cache survives between builds but never lands in a layer.
RUN npm testTests are a build gate: failing test = no image. (So test/ must not be in .dockerignore.)
npm prune --omit=devRemove jest/supertest before copying node_modules to the runtime stage.
rm -rf …npm …npxSmaller attack surface; fixes the npm-bundled CVE that Session 19 parked in .trivyignore (you can delete that entry).
COPY --from=build --chown=node:nodeOnly prod deps + package.json + server.js, owned by the runtime user.
USER nodeNon-root (uid 1000). The chart also sets runAsUser: 1000 because runAsNonRoot can't verify a named user.
HEALTHCHECKFor Docker/Compose only; Kubernetes ignores it and uses the chart's probes.
ENTRYPOINT ["/sbin/tini", "--"] + CMDtini is PID 1 and forwards SIGTERM to node → clean shutdown on pod termination.
Why node 22, not 20?

Node.js 20 reached end-of-life on 30 Apr 2026: its images get no more security fixes, so Trivy keeps finding fixable CVEs and blocks the pipeline. Node 22 is LTS until Apr 2027. TaskFlow needs no code change — switch NODE_VERSION in the Dockerfile and in the workflow together.

Common mistakes
  • npm ci fails with package.json and package-lock.json are not in sync → run npm install locally and commit the updated lockfile.
  • Build fails at RUN npm test with No tests found → you added test/ to .dockerignore.
  • ECONNREFUSED 127.0.0.1:5432 → inside the api container localhost is the api itself; the DB host is db (Compose) or taskflow-db (K8s).
Viva trap

"The HEALTHCHECK line makes Kubernetes restart an unhealthy pod." ✗ Kubernetes ignores it and uses the chart's liveness and readiness probes. HEALTHCHECK only matters to Docker and Compose (the (healthy) in docker compose ps).

"A multi-stage build pushes two images." ✗ Only the final stage becomes the image. The build stage, with jest and the full node_modules, is thrown away.

Viva check
Q1. ps in the container shows PID 1 = tini, PID 7 = node. Without the ENTRYPOINT line, what would PID 1 be, and what does tini do that node as PID 1 wouldn't?

node itself. As PID 1 it gets no default signal handling (Session 6), so SIGTERM is ignored unless the app handles it, and docker stop or a pod deletion waits out the grace period and ends in SIGKILL (137). tini forwards signals to node and reaps zombie processes.

Q2. Predict: you edit only server.js and rebuild. Does npm ci run again? Do the tests?

npm ci is cached: its inputs (package.json, the lockfile and the layers before it) didn't change. COPY . . changed, so it and every later step in the stage rerun, including npm test. That ordering is why the lockfile is copied first (Session 7).

3 Steps 3–4: CI/CD pipeline & security gates

Step 3 — The workflow (Session 18, Session 19)

Why this step

Turn a merge into a tested, scanned, immutable image that the cluster will run, with no human in between. A GitHub-hosted runner can't reach the minikube on your laptop, so the pipeline ends by writing the new tag to Git instead of calling kubectl. Argo CD does the rest from inside the cluster.

 pull_request: test ─┬─ sast ────────┐
                     ├─ sca ─────────┼─▶ build-push (build only, nothing pushed)          → the PR can merge
                     └─ secret-scan ─┘
 push to main: test ─┬─ sast ────────┐
                     ├─ sca ─────────┼─▶ build-push ─▶ image-scan ─▶ bump-tag ─▶ commit on main
                     └─ secret-scan ─┘   (push :sha)   (Trivy)       (values-prod.yaml, [skip ci])
 a red job → every job after it is skipped

.github/workflows/ci-cd.yml
name: CI/CD

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]                    # release tags like v1.4.0
  pull_request:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read                        # least privilege; jobs add what they need

concurrency:
  group: ci-cd-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}   # cancel stale PR runs only

env:
  IMAGE: ghcr.io/shauryav/taskflow-api  # lowercase!
  NODE_VERSION: "22"

jobs:
  # ---------- 1. fast feedback ----------
  test:
    name: Unit tests
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test

  # ---------- 2. security gates (parallel) ----------
  sast:
    name: SAST (CodeQL)
    needs: test
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write            # upload results to the Security tab
      actions: read
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v4
        with:
          languages: javascript-typescript
          build-mode: none
          queries: security-extended
      - uses: github/codeql-action/analyze@v4
        with:
          category: "/language:javascript-typescript"

  sca:
    name: SCA (npm audit)
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm audit --audit-level=high --omit=dev   # fails on high/critical in prod deps

  secret-scan:
    name: Secret scan (gitleaks)
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0                  # full history: a deleted secret is still in old commits
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  # ---------- 3. build & push (multi-arch) ----------
  build-push:
    name: Build & push image
    needs: [sast, sca, secret-scan]
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write                   # push to GHCR with GITHUB_TOKEN
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-qemu-action@v3     # emulates arm64 on the amd64 runner
      - uses: docker/setup-buildx-action@v3
      - name: Log in to GHCR
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Compute tags & labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,prefix=,format=long
            type=ref,event=branch
            type=ref,event=pr
            type=semver,pattern={{version}}
      - name: Build (push on main / tags)
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: ${{ github.event_name != 'pull_request' }}   # PRs only prove it builds
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ---------- 4. scan the pushed image ----------
  image-scan:
    name: Image scan (Trivy)
    needs: build-push
    if: github.event_name != 'pull_request'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: read                    # pull the image from GHCR
    steps:
      - uses: actions/checkout@v4       # for .trivyignore
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: aquasecurity/trivy-action@ed142fd0673e97e23eac54620cfb913e5ce36c25 # v0.36.0
        with:
          image-ref: ${{ env.IMAGE }}:${{ github.sha }}
          format: table
          severity: CRITICAL,HIGH
          ignore-unfixed: true              # only fail on vulns that have a fix
          exit-code: "1"                   # non-zero → job fails → bump-tag never runs
          trivyignores: .trivyignore

  # ---------- 5. deploy the GitOps way ----------
  bump-tag:
    name: GitOps - bump image tag
    needs: image-scan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    concurrency:
      group: bump-tag                   # one tag commit at a time
      cancel-in-progress: false
    steps:
      - uses: actions/checkout@v4
        with:
          token: ${{ secrets.GITOPS_TOKEN }}   # your PAT: GITHUB_TOKEN can't bypass the ruleset
      - name: Point values-prod.yaml at the scanned image
        env:
          TAG: ${{ github.sha }}
        run: |
          yq -i '.image.tag = strenv(TAG)' charts/taskflow/values-prod.yaml
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git commit -am "deploy: taskflow-api ${TAG::7} [skip ci]"
          git push
PieceWhat it does / why
pull_request vs push: mainPRs: tests, the 3 scans and a build without push. Main: also push, Trivy and the tag bump. Tags v*.*.*: push semver images, no bump.
needs: chaintest → (sast, sca, secret-scan in parallel) → build-push → image-scan → bump-tag. A red job stops everything after it.
type=sha,prefix=,format=longTags the image with the full commit SHA — exactly ${{ github.sha }}, which image-scan and bump-tag use.
Scan after pushThe image sits in GHCR, but if Trivy fails, Git never points at it, so it's never deployed. The gate is on the deploy.

Viva check
Q1. A PR is open. Which jobs run, which are skipped, and is the PR "unscanned"?

On a PR only the newest commit matters. On main every merge should end with its own pushed, scanned image and tag commit (traceable and revertable), and cancelling halfway could leave an image pushed but never scanned or deployed.

Viva trap

"targetCPUUtilizationPercentage: 60 means 60% of the node's CPU." ✗ It's 60% of the pod's CPU request (100m here), averaged across pods. That's why a pod with no request shows <unknown>.

"The HPA scales down as soon as the load stops." ✗ Scale-up is immediate, but scale-down waits for a 300 s stabilisation window, so it doesn't flap.

#!/usr/bin/env bash
# scripts/verify.sh — end-to-end smoke test of the TaskFlow deployment.
# Usage: ./scripts/verify.sh        (override with NS=..., HOST=..., INGRESS_IP=...)
set -euo pipefail

NS="${NS:-taskflow}"
HOST="${HOST:-taskflow.local}"
APP="taskflow-api"
DB_POD="postgres-0"
if [[ -z "${INGRESS_IP:-}" ]]; then
  # macOS + docker driver: the Ingress is reachable only via `minikube tunnel` on 127.0.0.1
  if [[ "$(uname)" == "Darwin" ]]; then INGRESS_IP=127.0.0.1; else INGRESS_IP="$(minikube ip)"; fi
fi
URL="http://$HOST"
RESOLVE=(--resolve "$HOST:80:$INGRESS_IP")    # curl resolves HOST to INGRESS_IP: no /etc/hosts needed

passed=0
ok()  { echo "  PASS  $1"; passed=$((passed + 1)); }
die() { echo "  FAIL  $1"; exit 1; }

echo "== Kubernetes (namespace $NS)"
if kubectl rollout status "deploy/$APP" -n "$NS" --timeout=120s >/dev/null; then
  ok "deployment/$APP rolled out"; else die "rollout of $APP did not finish"; fi

ready=$(kubectl get deploy "$APP" -n "$NS" -o jsonpath='{.status.readyReplicas}')
want=$(kubectl get deploy "$APP" -n "$NS" -o jsonpath='{.spec.replicas}')
if [[ "${ready:-0}" -ge 1 && "${ready:-0}" == "$want" ]]; then
  ok "$ready/$want replicas ready"; else die "only ${ready:-0}/$want replicas ready"; fi

if kubectl exec -n "$NS" "$DB_POD" -- pg_isready -U taskflow -d taskflow >/dev/null; then
  ok "postgres accepting connections"; else die "postgres not ready"; fi

echo "== Through the Ingress ($URL -> $INGRESS_IP)"
body=$(curl -fsS --max-time 5 "${RESOLVE[@]}" "$URL/health") || die "GET /health failed"
if [[ "$body" == *'"ok"'* ]]; then ok "GET /health -> $body"; else die "unexpected body: $body"; fi

code=$(curl -sS -o /dev/null -w '%{http_code}' --max-time 5 "${RESOLVE[@]}" \
  -H 'Content-Type: application/json' -d '{"title":"verify.sh smoke test"}' "$URL/tasks" || true)
if [[ "$code" == "201" ]]; then ok "POST /tasks -> $code"; else die "POST /tasks -> $code"; fi

echo "== Autoscaling & monitoring"
cpu=$(kubectl get hpa "$APP" -n "$NS" \
  -o jsonpath='{.status.currentMetrics[0].resource.current.averageUtilization}' || true)
if [[ -n "$cpu" ]]; then ok "HPA sees CPU at ${cpu}%"; else die "HPA has no metrics (metrics-server? cpu requests?)"; fi

kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-prometheus 9090:9090 >/dev/null 2>&1 &
pf=$!
trap 'kill "$pf" 2>/dev/null' EXIT
sleep 3
up=$(curl -s --max-time 5 localhost:9090/api/v1/query \
  --data-urlencode "query=min(up{namespace=\"$NS\",job=\"$APP\"})" || true)
if [[ "$up" == *'"1"]'* ]]; then ok "Prometheus scrapes every $APP pod"; else die "Prometheus target down/missing"; fi

if kubectl get application taskflow -n argocd >/dev/null 2>&1; then
  st=$(kubectl get application taskflow -n argocd -o jsonpath='{.status.sync.status}/{.status.health.status}')
  if [[ "$st" == "Synced/Healthy" ]]; then ok "Argo CD app $st"; else die "Argo CD app is $st"; fi
fi

echo "All $passed checks passed."

Viva trap

"Under set -e, a failing kubectl inside if …; then kills the script." ✗ Commands tested by if, or followed by || / &&, are exempt from set -e. That's why every check is an if or ends in || die, so you see a clear FAIL line instead of a silent exit.

"All PASS proves the pipeline works." ✗ verify.sh checks the running system. Show the green Actions run and the tag-bump commit separately (demo steps 5–6).

Likely viva questions
Walk me through what happens after you merge a PR.

The push to main runs ci-cd.yml: unit tests; then CodeQL, npm audit and gitleaks in parallel; then a multi-arch image tagged with the commit SHA is built and pushed to GHCR; Trivy scans it; bump-tag commits that SHA to values-prod.yaml; Argo CD sees the commit, renders the chart and applies it; the Deployment does a rolling update gated by readiness probes.

Why a multi-stage Dockerfile with tests inside, and why remove npm?

The build stage has dev dependencies and runs the tests (a failing test means no image); only pruned production node_modules and the code reach the runtime stage — smaller, faster pulls, less attack surface. npm isn't used at runtime and its bundled packages are a frequent source of HIGH CVEs that would fail the Trivy gate.

Why tag images with the git SHA instead of latest?

A SHA tag is immutable and traceable to the exact commit, and every deploy becomes a Git change that GitOps can detect and roll back. latest changes underneath you, doesn't change Git (nothing syncs) and makes rollbacks impossible.

SAST vs SCA vs secret scanning vs image scanning — which tool does each in your pipeline?

SAST (flaws in your own code): CodeQL. SCA (known-vulnerable dependencies): npm audit (+ Dependabot PRs). Secret scanning (keys in Git history): gitleaks. Image scanning (OS + library CVEs in the built image): Trivy.

How does a request get from the browser to a pod?

taskflow.local resolves (hosts file) to the ingress-nginx controller → it matches host + path in the Ingress → forwards to Service taskflow-api port 80 (http) → a ready pod's targetPort http (3000). The NetworkPolicy allow-ingress-to-api permits that hop.

Liveness vs readiness — what happens when each fails?

Liveness failing → kubelet restarts the container. Readiness failing → the pod is removed from the Service endpoints (no traffic) but not restarted. During a rolling update, old pods stay until new ones are ready.

How does the HPA decide the replica count? Why might it show <unknown>?

desired = ⌈current × currentUtilisation / target⌉, clamped to min/max, with CPU measured by metrics-server as a % of the pod's request. <unknown> = metrics-server missing or no CPU request set.

Why is Postgres a StatefulSet and not a Deployment? What happens to data if the pod is deleted?

A StatefulSet gives a stable identity (postgres-0, DNS via the headless Service taskflow-db) and a PVC per replica from volumeClaimTemplates. Deleting the pod recreates postgres-0 and re-attaches the same PVC data-postgres-0, so data survives.

Where is the database password, and is it encrypted?

In the Secret taskflow-db-secret, created with kubectl (never committed) and referenced by database.existingSecret. Secrets are only base64-encoded by default; protect them with RBAC and encryption at rest, or use Sealed Secrets / External Secrets for GitOps.

What's a Helm release, and what's the precedence of values?

A release is one installed instance of a chart with its own revision history (stored as Secrets in the namespace). Precedence: chart values.yaml < -f files (later wins) < --set.

Push vs pull deployment — why Argo CD here? What if someone runs kubectl edit?

GitHub-hosted runners can't reach a laptop cluster and shouldn't hold its credentials; Argo CD runs inside and pulls from Git. With selfHeal on, a manual kubectl edit shows OutOfSync and is reverted to what Git says.

How does Prometheus find your pods, and what does rate() do?

The ServiceMonitor (label release: monitoring) selects the chart's Service by labels; the operator turns it into scrape config for every endpoint pod on port http, path /metrics. rate(counter[5m]) = per-second increase averaged over 5 minutes.

The site returns 503. How do you debug it?

503 from nginx = no ready backends. kubectl get pods (READY 0/1?), kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api (empty?), kubectl describe pod for probe failures, kubectl logs --previous for crashes; compare the Service selector with the pod labels.

★ Putting it all together

The big idea

The project is the whole DevOps loop in one repo. Git (behind a ruleset) is the only way in; CI turns each merge into a tested, scanned, immutable ghcr.io/shauryav/taskflow-api:<sha> and records that tag in values-prod.yaml; Helm (rendered by Argo CD or run by you) turns that file into a Deployment behind a Service and an Ingress, scaled by an HPA, next to a Postgres StatefulSet, fenced by Pod Security and NetworkPolicies; Prometheus and Grafana show whether it's healthy and an alert says when it isn't. When something breaks you walk the same path backwards — and verify.sh proves it's fixed.

Final check — combine the steps
Q1. Trivy runs after the image is pushed (Step 3). What stops a vulnerable image from reaching the cluster (Step 6)?

bump-tag has needs: image-scan. If Trivy fails, values-prod.yaml never changes, so Argo CD (or helm upgrade -f values-prod.yaml) keeps deploying the previous, scanned image. The gate is on the deploy, not on the push.

Q2. You merged a PR ten minutes ago and the old version is still running. Walk the chain to find where it stopped.

gh run view: did every job pass? (A failed gate, or bump-tag with GH013 = PAT problem.) git log -1 -- charts/taskflow/values-prod.yaml: is the new SHA committed? argocd app get taskflow: OutOfSync and not polled yet (argocd app sync), or a ComparisonError? kubectl get pods -n taskflow: new pods in ImagePullBackOff (private package) or CrashLoopBackOff?

Q3. The chart sets runAsUser: 1000 although the Dockerfile says USER node. Why both?

The namespace is restricted (Step 5), so the pod needs runAsNonRoot: true. To enforce that, kubelet must check the UID isn't 0, and it can't resolve the name node from the image. Without a numeric UID the pod fails with CreateContainerConfigError.

Q4. Why do the HPA load-test pods run in default and go through the Ingress controller (Steps 5, 7, 8)?

taskflow enforces the restricted Pod Security level, so a plain busybox pod is rejected. Its default-deny NetworkPolicies only let ingress-nginx reach the API. Going through ingress-nginx-controller uses the allowed path, the same one users take.

Q5. verify.sh passes everything except "Prometheus target down/missing", and the app works through the Ingress. Give three causes from three different steps.

Step 5/9: the NetworkPolicy allow-monitoring-to-api is missing, so the target is DOWN with context deadline exceeded. Step 6: serviceMonitor.enabled is false in the values, so no ServiceMonitor is rendered. Step 9: the release label isn't monitoring (or the image lacks /metrics → HTTP 404).

Q6. A teammate "simplifies" the build step to one platform. CI is all green, but on your Apple-silicon minikube the new pods crash with exec format error. Which step broke, how do you prove it, and why didn't CI notice (Steps 2, 3, 10)?

Step 3: without platforms: linux/amd64,linux/arm64 (and QEMU) the image is amd64-only. Prove it with docker buildx imagetools inspect ghcr.io/shauryav/taskflow-api:<sha> | grep Platform (only amd64) and kubectl get node minikube -o jsonpath='{.status.nodeInfo.architecture}' (arm64). CI runs on amd64 runners, so the tests inside the build stage (Step 2) passed there. Restore both platforms.
