1 Why Kubernetes? Desired state

The problem: TaskFlow outgrows one server

In Session 8 one docker compose up -d ran TaskFlow on one server. Now it's popular, so you rent three servers and docker run API containers on each. Then a normal week happens:

02:13  server-2 loses power      → its API containers are gone, and nobody is awake
09:00  traffic triples           → you ssh into each server and start more copies by hand
14:00  deploy taskflow-api 1.1   → stop old, start new, three servers: downtime
14:05  the API moved servers     → the web tier still points at the old server's IP

Docker's --restart policy lives on the host, so it dies with the host. Your start-up script ran once at 09:00 and never finds out. It said what to do. Nothing says what should be true.

The idea

Kubernetes (K8s) is a container orchestrator. You give it a cluster of machines, called nodes, and you store a fact: "there should be 3 replicas of taskflow-api:1.0.0". That fact is the desired state. Programs called controllers then loop forever: observe what's actually running, diff it with the desired state, and act to close the gap. This loop is reconciliation, and it's why Kubernetes is called declarative.

desired state (stored in etcd)             actual state (what is running)
     replicas: 3        ───── compare ─────▶     2 pods running
          ▲                                           │
          │                                           ▼
    you edit YAML                         controller acts: create 1 pod
          └────────────── observe again ◀─────────────┘
Think of it like this

In Session 6 a Docker host was one kitchen. Kubernetes is a restaurant: several kitchens (nodes) and a manager's office (the control plane). You don't walk into kitchens. You hand in an order ticket, "3 × taskflow-api, always", and a shift manager keeps counting what's cooking. Two? Fire one more. A kitchen burns down? Cook it elsewhere. The ticket says what should be true, never "cook one now". This restaurant runs through the next three sessions.

Build it up: a node dies at 02:13

TaskFlow runs replicas: 3 on three nodes. The same loop handles a dead machine, more slowly, because Kubernetes first makes sure the node is really gone:

02:13:00  node-2 loses power; its kubelet stops sending heartbeats
02:13:50  node controller: no heartbeat for ~40–50 s → node-2 is NotReady
02:18:50  after the default 5-minute toleration, node-2's pods are evicted
02:18:51  ReplicaSet controller: desired 3, actual 2 → creates a pod
02:18:52  scheduler puts it on node-1 or node-3 and that kubelet starts it: 3/3, nobody woke up

The jobs this loop takes off you:

From compose.yaml: services.api → Deployment (S10), hostname db → Service (S11), ports: → NodePort/LoadBalancer/Ingress (S11–12), healthcheck → probes (S13). Skip Kubernetes for one small app on one VM, where Compose or systemd is simpler and cheaper.

Exam trap

"Kubernetes replaces Docker." ✗ It doesn't build images or run containers itself. You still build and push images, and a container runtime on each node runs them (section 5). Kubernetes decides what runs where and keeps it running.

"Kubernetes restarts the pod you deleted." ✗ It creates a new pod with a new name and IP. Restarting a crashed container inside the same pod is the kubelet's job (section 5).

Remember

You declare what should be true. Controllers make it true, forever: observe → diff → act.

Mastery check
Q1. server-2 dies at 02:13. With Docker and --restart unless-stopped, what happens to its containers? With Kubernetes?

Docker: nothing, because the restart policy lived on the dead host. Kubernetes marks the node NotReady, evicts its pods, and the controllers recreate them on healthy nodes.

Q2. Predict: hello has 2 replicas and you delete both pods in one command. What does kubectl get pods show 5 seconds later?

Two pods with new names, a few seconds old (maybe still ContainerCreating). Desired 2, actual 0, so the controller creates 2.

Q3. True or false: "Self-healing, scaling and rolling updates are three separate mechanisms."

False in spirit. All three are the same reconcile loop: actual drops (self-healing), you change the desired count (scaling), or you change the desired pod template (rollout, Session 10).

2 Control plane & worker nodes

The problem

Count the jobs in section 1's demo. Somebody stored "2 replicas", noticed a pod was missing, picked a machine for the new one, and started nginx there. There's no single program called "kubernetes": four jobs, four programs, and the exam expects you to know which is which.

The idea

A cluster has two halves. The control plane is the brain: it stores the desired state, decides, and runs the reconcile loops. Worker nodes are the muscle: they run your pods. Every component on both halves talks to one place only, the API server.

Exam trap

"kubelet and kube-proxy are control-plane components." ✗ They run on every node. The control plane is apiserver, etcd, scheduler, controller-manager and cloud-controller-manager.

"Every node runs its own etcd." ✗ etcd belongs to the control plane, usually as a 3- or 5-member cluster. Worker nodes never touch it.

Remember

Control plane decides & remembers: apiserver · etcd · scheduler · controller-manager.
Every node does: kubelet · kube-proxy · container runtime. Everyone talks only to the API server.

Mastery check
Q1. Sort into "control plane" or "every node": kubelet, etcd, kube-proxy, kube-scheduler, containerd, kube-controller-manager.

Control plane: etcd, kube-scheduler, kube-controller-manager (plus kube-apiserver). Every node: kubelet, kube-proxy, containerd.

Q2. kube-proxy-9vq4d has a random suffix; etcd-minikube ends in the node's name. What does that tell you?

A random suffix means a controller stamped it from a template (kube-proxy's DaemonSet). A node-name suffix marks a static pod that the kubelet on minikube started from a file. The API server only shows a mirror of it.

Q3. On EKS, kubectl get pods -n kube-system shows CoreDNS and kube-proxy but no apiserver or etcd. Why?

EKS is managed. AWS runs the control plane in its own account and gives you only the API endpoint, so you see worker nodes and their add-ons.

3 API server & etcd

The problem

Count the writers in section 1's demo: you, a controller, the scheduler, the kubelet. A real cluster adds 50 kubelets, CI pipelines and five teammates. If they all wrote straight into the database, who would check that a pod spec is valid, that you may delete production, or that two writers don't overwrite each other?

The idea

The cluster has one front door. The kube-apiserver is a REST API over HTTPS, and it's the only component that reads or writes etcd, the database holding all cluster state. kubectl, the scheduler, the controllers and every kubelet are just API clients, and every request passes the same checks before anything is stored:

kubectl apply ──HTTPS──▶ kube-apiserver
                           │ 1. Authentication      who are you?        (client cert, token, OIDC)
                           │ 2. Authorization       are you allowed?    (RBAC, S16)
                           │ 3. Mutating admission  fill in defaults, inject sidecars
                           │ 4. Schema validation   is this a valid Deployment?
                           │ 5. Validating admission policies, ResourceQuota
                           ▼
                         etcd (object stored) ──▶ watchers notified (controllers, scheduler, kubelets)
Think of it like this

The API server is the order desk, and etcd is the ticket book behind it. Customers, managers and head chefs all queue at the same desk. It checks who you are and whether you may order that, fills in the blanks, rejects nonsense, and only then writes the ticket in the book. Nobody else touches the book.

See it: kubectl is just an HTTPS client

Build it up: watches and etcd

Watch, don't poll. Components hold a long-lived connection open, and the API server pushes them every change to the objects they care about. That's how the scheduler hears about a new pod within milliseconds.

etcd is a distributed, strongly consistent key-value store. Objects live under keys like /registry/pods/<namespace>/<name>. It uses the Raft consensus algorithm: a write succeeds only when a majority of members (a quorum) agree.

Exam trap

"Two etcd members are safer than one." ✗ The quorum of 2 is 2, so losing either member stops all writes, which is worse than one member. Use 3 or 5.

"Secrets are encrypted in etcd." ✗ Not by default. They're stored base64-encoded unless encryption at rest is configured (Session 12).

Remember

Everyone talks to the API server. Only the API server talks to etcd.
authn → authz → admission → validation → etcd → watchers · quorum = ⌊n/2⌋ + 1

Mastery check
Q1. Spot the misconception: "The scheduler writes its decision straight into etcd."

Only the API server talks to etcd. The scheduler sends an API request (a "binding") like any other client, and it passes the same checks.

Q2. Predict the URL kubectl calls for kubectl get deployments -n taskflow.

GET https://<apiserver>/apis/apps/v1/namespaces/taskflow/deployments. Deployments are in the named group apps/v1, so the path starts with /apis/.

Q3. A 5-member etcd cluster loses two members. Can you still deploy? What if it loses a third?

With 3 of 5 left the quorum (3) is met, so yes. A third loss leaves 2 < 3, so there's no quorum: no writes, which means no deploys, no scaling and no self-healing.

Q4. etcd's disk is wiped and there's no snapshot. Do the running TaskFlow containers stop at once?

No. The kubelets keep the existing containers running. But the cluster has lost its memory of what should exist, so nothing can be viewed, changed or healed. You rebuild from the YAML in Git.

4 Scheduler & controller manager

The problem

A newly stored pod has a spec but no machine: its spec.nodeName is empty. Usually that's fixed within milliseconds. Sometimes it isn't:

$ kubectl get pod taskflow-api-7c9d8b6f4-2xkqz -n taskflow
NAME                           READY   STATUS    RESTARTS   AGE
taskflow-api-7c9d8b6f4-2xkqz   0/1     Pending   0          2m

Who picks the machine, and why would it refuse? And who noticed the missing nginx pod in section 1?

The idea

The kube-scheduler has one job: for every pod without a node, pick a node. It filters out nodes that can't run the pod, scores the rest, and binds the pod to the winner by writing spec.nodeName. It never starts anything. The kube-controller-manager is one binary running dozens of controllers, each one the section 1 loop for one kind of object.

 new taskflow-api pod   nodeName: ""   requests: cpu 500m, memory 512Mi
        │
   FILTER   node-1 ✗ only 300m CPU free      node-2 ✗ taint dedicated=db, not tolerated
        │   node-3 ✓ 1500m / 1Gi free        node-4 ✓ 3 CPU / 5Gi free
        │
   SCORE    node-3 → 48 (memory would be tight)   node-4 → 86 (room to spare, image cached)
        │
   BIND     spec.nodeName = node-4   ──▶  the kubelet on node-4 takes over (section 5)

Other filter reasons: a nodeSelector/affinity mismatch, a host port in use, a volume in another zone. Other score plugins: spread the load, honour affinity preferences, spread replicas apart.

Think of it like this

The scheduler is the floor manager choosing a kitchen for each new order. Not kitchen 1, its burners are booked. Not kitchen 2, it only does desserts. Kitchen 4 has the most room. He writes "kitchen 4" on the ticket and walks away without cooking. The controllers are the shift managers, each watching one kind of ticket and fixing any gap.

See it: the scheduler signs its work

$ kubectl describe pod taskflow-api-7c9d8b6f4-2xkqz -n taskflow | tail -4
Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  3s    default-scheduler  Successfully assigned taskflow/taskflow-api-7c9d8b6f4-2xkqz to node-4

From: default-scheduler names the component. When no node passes the filter, the same place explains the Pending puzzle:

  Warning  FailedScheduling  12s  default-scheduler  0/4 nodes are available: 1 node(s) had untolerated taint {dedicated: db}, 3 Insufficient memory. preemption: …

What it does not do: look at live usage. The filter counts requests (what pods have reserved), so a node idling at 5% CPU but fully reserved still fails. And it places each pod once; it never moves running pods to rebalance.

Build it up: the controllers

ControllerKeeps this true
DeploymentThe right ReplicaSet exists for the current pod template; rolls out new versions (S10)

The cloud-controller-manager runs only on cloud clusters and holds the cloud-specific loops. Its service controller creates a real AWS/Azure/GCP load balancer for a type: LoadBalancer Service (S11). Its node controller labels nodes with zone and instance type and removes deleted VMs, and its route controller sets up pod-network routes. minikube has none, which is why a LoadBalancer's EXTERNAL-IP stays <pending> there.

Exam trap

"The scheduler starts the containers." ✗ It only writes nodeName. That node's kubelet starts them.

"The scheduler moves pods off a node that gets busy." ✗ Each pod is scheduled once. Running pods aren't rebalanced (that takes an add-on such as the descheduler).

Remember

Scheduler: filter → score → bind. It writes nodeName and nothing else.
Controller manager = one reconcile loop per kind of object.

Mastery check
Q1. A pod is Pending with 0/3 nodes are available: 3 Insufficient cpu. Who wrote that, what does it mean, and give two fixes.

kube-scheduler. The pod's CPU request is larger than every node's unreserved CPU. Lower the request, free capacity, or add a node.

Q2. Predict: 2-CPU nodes idle at 10% real CPU, but existing requests reserve 95% of each. A new pod requests 500m. Scheduled?

No. Only 100m is unreserved per node, which is less than 500m. The scheduler counts requests, not live usage.

Q3. Which controller handles: (a) a node stops heartbeating, (b) a Service's ready-pod list, (c) a ReplicaSet with 2 of 3 pods, (d) a Deployment whose image changed?

(a) Node · (b) EndpointSlice · (c) ReplicaSet · (d) Deployment, which creates a new ReplicaSet.

Q4. The same LoadBalancer Service gets an AWS hostname on EKS but stays <pending> on minikube. Why?

The cloud-controller-manager's service controller creates the load balancer through the cloud API. minikube has no cloud and no cloud-controller-manager (Session 11 uses minikube tunnel).

5 kubelet, kube-proxy & the runtime

The problem

After binding, the pod says nodeName: node-4. That's only a string in etcd. Something on node-4 has to notice, pull the image and start the container, and restart it after a 3 a.m. crash without asking a control plane that might be in another building.

The idea

Every node runs three things. The kubelet is the node agent: it watches the API server for pods bound to its node, tells the runtime to start them, runs their health checks, and reports status and heartbeats. The container runtime pulls images and runs the containers through runc, exactly as in Session 6. kube-proxy turns Services into network rules so Service traffic reaches the right pods (Session 11).

                     watch "pods for node-4"

                report status + heartbeats       │ CRI: gRPC over a local socket
                                                 ▼
                                   container runtime (containerd / CRI-O) ──▶ runc ──▶ containers
                                                 │  a tiny "pause" container holds each pod's network namespace
                                                 └─ CNI plugin gives the pod its IP

 kube-apiserver ◀── watch Services + EndpointSlices ── kube-proxy (DaemonSet pod) ──▶ iptables / nftables rules
Think of it like this

The kubelet is the head chef of one kitchen. He checks the order desk for tickets marked with his kitchen, gets the stoves going (the runtime does the cooking), tastes the food (health checks) and phones the desk every few seconds: "kitchen 4, all fine". kube-proxy is the kitchen's intercom wiring, which knows who answers calls for "the API counter".

  • minikube ssh opens a shell on the node; systemctl status proves the kubelet is a systemd service (Session 2).
  • /etc/kubernetes/manifests/ holds the static pod files. The kubelet runs any pod file it finds there without asking the API server, which is how the control plane boots.
  • crictl ps is docker ps for nodes, speaking CRI to the runtime.

What it does not do: the kubelet doesn't choose its pods (the scheduler did), and it doesn't recreate deleted pods (the ReplicaSet controller does). It runs what it's told and restarts crashed containers in place.

Build it up: kube-proxy and the CRI

$ kubectl get daemonset -n kube-system
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR            AGE
kube-proxy   1         1         1       1            1           kubernetes.io/os=linux   25m

A DaemonSet runs one pod per node (Session 15): DESIRED is 1 here, and would be 3 on a 3-node cluster. kube-proxy watches Services and EndpointSlices and rewrites the kernel's iptables or nftables rules. Packets never pass through the kube-proxy process.

The kubelet talks to the runtime through the CRI (Container Runtime Interface), so any CRI runtime plugs in. EKS, GKE and kind use containerd. minikube defaults to Docker Engine through the cri-dockerd adapter (docker://28.4.0 in section 7). Kubernetes dropped its built-in Docker support (dockershim) in v1.24, and Docker-built images still run because they're OCI images.

Exam trap

"kube-proxy forwards every request through itself." ✗ In iptables/nftables mode it only writes kernel rules, and the kernel rewrites the packets.

"If the API server goes down, every container stops." ✗ The kubelets keep running and restarting what they have. They just can't get new work or report status until it returns.

Remember

kubelet = head chef: runs the pods bound to its node, reports back.
runtime = stoves (via CRI) · kube-proxy = writes Service rules, carries no traffic.

Mastery check
Q1. A container crashes. Which component restarts it, and must the control plane be reachable?

The kubelet on that node, following restartPolicy. It's local, so no. The pod keeps its name and IP and RESTARTS goes up by 1.

Q2. You copy a pod YAML into /etc/kubernetes/manifests/, then kubectl delete the pod that appears. What happens?

It's a static pod. You deleted only its mirror, and the kubelet recreates it because the file is still there. Remove the file to remove the pod.

Q3. Fill in: the kubelet talks to the runtime through the ________; a pod gets its IP from a ________ plugin; the ________ container holds the pod's network namespace.

CRI · CNI · pause.

Q4. kube-proxy crashes on node-2. Can node-2's pods still reach existing Services?

Yes, for now, because the rules it already wrote stay in the kernel. New Services and endpoint changes won't reach node-2 until it's back, so node-2 slowly goes stale.

6 What happens on kubectl apply

The problem

The favourite exam question here is "Describe what happens when you run kubectl apply -f deployment.yaml." Most answers stop at "Kubernetes creates the pods". The real answer passes through six components, and kubectl has already printed its reply before most of them start.

The idea

No component calls another. Each one watches the API server for the objects it cares about, does its one job, and writes the result back. The work moves through the cluster like a ticket moving down the rail:

kubectl ──①──▶ kube-apiserver ──②──▶ etcd
                    │
                    ├─③ Deployment controller sees new Deployment → creates ReplicaSet
                    ├─④ ReplicaSet controller sees 0/3 pods       → creates 3 Pods (no node yet)
                    ├─⑤ Scheduler sees unscheduled Pods           → binds each to a node
                    ├─⑥ kubelet on that node sees its Pod          → CRI: pull image, start containers
                    └─⑦ kubelet reports Running/Ready              → API server → etcd
Think of it like this

One ticket, many hands. The desk files it in the book. A shift manager splits "3 × taskflow-api" into three tickets, the floor manager writes a kitchen on each, and each head chef cooks his and calls back "ready". Nobody phoned anybody. They all kept checking the same rail.

See it: apply TaskFlow

k8s/deployment.yaml (minimal; Session 10 adds the rest)
apiVersion: apps/v1                # API group "apps", version v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
  labels:
    app: taskflow-api
spec:
  replicas: 3                      # desired state: 3 pods
  selector:
    matchLabels:
      app: taskflow-api              # which pods this Deployment owns
  template:                          # pod template: every replica is stamped from this
    metadata:
      labels:
        app: taskflow-api            # must match the selector
    spec:
      containers:
      - name: api
        image: shauryav/taskflow-api:1.0.0

        - containerPort: 3000
        resources:

            cpu: 100m                # 0.1 CPU core
            memory: 128Mi

resources.requests100m CPU and 128 MiB reserved: the numbers the scheduler filters on (section 4)

Exam trap

"kubectl apply printed created, so the app is running." ✗ It means the object was stored. Check kubectl get pods or kubectl rollout status (Session 10).

"The Deployment controller creates the pods." ✗ It creates a ReplicaSet, and the ReplicaSet controller creates the pods.

Remember

kubectl → API server → etcd → Deployment ctrl → ReplicaSet ctrl → scheduler → kubelet → runtime → status back.
Nobody calls anybody. Everybody watches the API server.

Mastery check
Q1. Put in order: scheduler binds · ReplicaSet created · kubelet pulls the image · Deployment stored in etcd · Pods created with no node · kubectl prints created.

Deployment stored in etcd → kubectl prints created → ReplicaSet created → Pods created with no node → scheduler binds → kubelet pulls the image.

Q2. Spot the misconception: "The scheduler was down for 5 minutes, so the 3 running TaskFlow pods crashed."

Running pods don't need the scheduler, because their kubelets keep them going. Only new pods would sit in Pending until the scheduler returns.

Q3. Events show Scheduled, Pulling, then Failed … ErrImagePull. Which steps worked, and which component failed?

Steps ① to ⑤ worked. Step ⑥ failed: the kubelet (via the runtime) couldn't pull the image, usually because of a wrong tag or a private registry (Session 14).

Q4. You apply a 3-replica Deployment. get deploy shows 0/3 and no ReplicaSet exists at all. Which component do you suspect?

The kube-controller-manager: step ③ never happened. Check its pod in kube-system and read its logs.

7 Cluster setup, kubectl & kubeconfig

The problem

$ kubectl get pods
The connection to the server localhost:8080 was refused - did you specify the right host or port?

kubectl has no idea which cluster to talk to. The opposite failure is worse: three clusters configured, you think you're on minikube, and you run kubectl delete deployment taskflow-api on production.

The idea

kubectl is an HTTPS client (section 3). Before every command it reads the kubeconfig file, ~/.kube/config, to learn where the API server is, who you are, and which namespace to use by default. A named set of those three is a context, and current-context is the one in use.

 clusters:  minikube → https://192.168.49.2:8443        kind-taskflow → https://127.0.0.1:41263
 users:     minikube → client cert                     kind-taskflow → client cert
                 └────────────┬────────────┘                   └────────────┬────────────┘
 contexts:   minikube = cluster + user + ns taskflow      kind-taskflow = cluster + user
                       ▲
 current-context ──────┘   every kubectl command goes here unless you pass --context
Think of it like this

The kubeconfig is your wallet of staff badges. Each badge (context) names a restaurant (cluster), who you are there (user) and your usual section (namespace). current-context is the badge you're wearing. The wrong badge can still cancel real orders, so check it first.

See it: switch badges

$ kubectl config get-contexts
CURRENT   NAME            CLUSTER         AUTHINFO        NAMESPACE
*         minikube        minikube        minikube        taskflow
          kind-taskflow   kind-taskflow   kind-taskflow
$ kubectl config use-context kind-taskflow

$ kubectl config current-context

$ kubectl config use-context minikube
$ kubectl config set-context --current --namespace=taskflow

* marks the current context, AUTHINFO is the user, and NAMESPACE is the default when you omit -n. What these commands do not do: touch any cluster. They only edit the file on your laptop.

Build it up

8 YAML anatomy & imperative vs declarative

The problem

A teammate hot-fixed production with kubectl run, scale and set image. Today the cluster is rebuilt and nobody knows what was typed. Meanwhile your file-based approach fails the second time you run it:

$ kubectl create -f k8s/pod.yaml
Error from server (AlreadyExists): error when creating "k8s/pod.yaml": pods "taskflow-api" already exists

The idea

Every Kubernetes object has the same shape, and you can send one in two ways: imperatively ("do this now") or declaratively ("make the cluster look like this file"). Files in Git plus kubectl apply is how real projects work.

 apiVersion: v1      ← which API (group/version) understands this kind
 kind: Pod           ← what type of object
 metadata: …         ← identity: name, namespace, labels      (you write)
 spec: …             ← desired state: what you want           (you write)
 status: …           ← actual state: what is really happening (Kubernetes writes)
Think of it like this

Every order ticket is printed on the same form: which form (apiVersion), what kind of order (kind), the name on it (metadata), what you want (spec). The kitchen fills in the bottom box (status). You never write in that box.

See it: TaskFlow's first pod

k8s/pod.yaml
apiVersion: v1                     # group/version — Pods live in the core group "v1"
kind: Pod                          # object type
metadata:                          # identity
  name: taskflow-api                # unique per kind + namespace
  namespace: taskflow
  labels:                           # key/value tags used by selectors (S10, S11)
    app: taskflow-api
    tier: backend
spec:                              # DESIRED state — you write this
  containers:
  - name: api                       # container name inside the pod
    image: shauryav/taskflow-api:1.0.0
    ports:
    - containerPort: 3000           # informational, like EXPOSE
    env:
    - name: PORT
      value: "3000"                 # env values must be strings → quote numbers
FieldWho writes itMeaning
apiVersion · kindYouv1 for core kinds like Pod and Service · object type in CamelCase
metadataYou (Kubernetes adds uid, resourceVersion…)name, namespace, labels (for selecting), annotations (notes for tools)
specYouDesired state, shaped by kind: here one container with image, port and env
statusKubernetes onlyActual state (phase, IPs, conditions). Never in your files.

That solves the opening puzzle. create means "make a new one", so it fails if the object exists. apply means "make it look like this file" and answers created, unchanged or configured however often you run it. You rarely type YAML from scratch, either. kubectl will write it for you without sending anything:

$ kubectl create deployment taskflow-api --image=shauryav/taskflow-api:1.0.0 \
    --replicas=3 --port=3000 -n taskflow --dry-run=client -o yaml > k8s/deployment.yaml
$ grep -n '{}' k8s/deployment.yaml          # the rest is section 6's file, minus resources
13:  strategy: {}
24:        resources: {}
25:status: {}
$ kubectl apply -f k8s/deployment.yaml --dry-run=server     # full server-side validation, nothing saved

--dry-run=client -o yaml builds the object locally and prints it (it works with kubectl run too). The generated file has the same apiVersion, metadata, selector and template as section 6's, plus three empty placeholders: delete status: {}, and fill in or delete strategy: {} and resources: {}. --dry-run=server runs validation and admission without storing anything.

Common mistakes
  • Tabs in YAML → error converting YAML to JSON: yaml: line 7: found character that cannot start any token. Spaces only, 2 per level.
  • Changing env of a running pod and re-applying → The Pod "taskflow-api" is invalid: spec: Forbidden: pod updates may not change fields other than `spec.containers[*].image`, …. Pods are nearly immutable, which is one more reason to use Deployments.
Exam trap

"Put status: phase: Running in the YAML so Kubernetes knows the pod should run." ✗ Kubernetes writes status. What you want goes in spec.

"kubectl apply -f and kubectl create -f are the same." ✗ create fails if the object exists. apply creates or updates, so it's safe to repeat.

Remember

apiVersion · kind · metadata · spec (you) + status (Kubernetes).
create = make new · apply = make it look like this file. Imperative to explore and generate, declarative to run.

Mastery check
Q1. Predict: kubectl create -f pod.yaml twice; kubectl apply -f pod.yaml twice; then apply after changing the image tag.

create: created, then AlreadyExists. apply: unchanged twice (the pod exists), then configured. The image is one of the few fields a live pod lets you change.

Q2. Spot the bug: env: [ { name: PORT, value: 3000 } ]

Env values must be strings. YAML reads 3000 as a number, and the API server rejects it ("cannot unmarshal number … of type string"). Write value: "3000".

Q3. Which dry run catches the typo replica: 3 in a Deployment, and why?

--dry-run=server. It goes through the API server's schema validation, which reports unknown field "spec.replica". A client dry run never reaches the server.

★ Putting it all together

The big idea

Kubernetes is a desired-state machine. You kubectl apply TaskFlow's YAML to the cluster your kubeconfig points at. The API server checks it and stores it in etcd. Controllers turn the Deployment into a ReplicaSet and Pods, the scheduler picks a node for each pod, and that node's kubelet has the runtime start the containers and reports back. Every component only watches the API server, so when a pod, a component or a node fails, the loops see the gap between desired and actual and close it.

Final mastery check — combine everything
Q1. 3 nodes: node-2 is tainted dedicated=db:NoSchedule, node-3 has 200m CPU free, node-1 has plenty. You apply a 3-replica Deployment whose pods request 500m. Narrate it component by component and give the final state.

API server checks and stores it in etcd, and kubectl prints created. Deployment controller → ReplicaSet; ReplicaSet controller → 3 node-less pods. The scheduler filters out node-2 (taint) and node-3 (requests) and binds all three to node-1, whose kubelet pulls the image via the CRI and reports Running. If node-1 only fits two, the third stays Pending with a FailedScheduling event naming both reasons.

Q2. At 02:13 node-3 loses power. Which components notice and act, in order, and what does kubectl get pods show along the way?

Heartbeats stop. After ~40–50 s the node controller marks node-3 NotReady (its pods still look Running). After the 5-minute toleration they're evicted, the ReplicaSet controller creates replacements, the scheduler binds them to healthy nodes, and those kubelets start them. New names and IPs appear and the count returns to 3/3.

Q3. You built a 2-member etcd cluster "for HA" and one member dies. Can you scale TaskFlow? Do its running pods stop?

No scaling: 1 of 2 members is no quorum, so etcd refuses writes. The running pods carry on, because kubelets don't need etcd to keep existing containers alive. Use 3 members.

Q4. Correct every error: "kubectl writes the Deployment into etcd, the scheduler starts the containers, and kube-proxy restarts crashed pods."

(1) kubectl sends it to the API server, the only writer to etcd. (2) The scheduler only binds; the kubelet starts containers through the runtime. (3) The kubelet restarts crashed containers and the ReplicaSet controller replaces deleted pods. kube-proxy only writes Service rules.

Q5. You kubectl delete pod both etcd-minikube and one pod of Deployment hello. Both come back. Who brought back each, and how would you really remove each?

etcd-minikube is a static pod: the kubelet recreates it from /etc/kubernetes/manifests/etcd.yaml, and only removing that file removes it (don't!). The hello pod came back because the ReplicaSet controller reconciles to desired 2. Scale to 0 or delete the Deployment.

Q6. A teammate has contexts for minikube and the college EKS cluster. They kubectl apply -f k8s/, see created, but find nothing in minikube. Give two likely causes and the command that checks each.

(1) The current context was EKS: check kubectl config current-context. (2) It went into taskflow while they're viewing default: check kubectl get pods -A. And since created only means "stored", look for Pending pods or pull errors too.
