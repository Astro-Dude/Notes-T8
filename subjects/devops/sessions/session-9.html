1 Why Kubernetes?

Explain like I'm 5

Docker is one musician. Kubernetes is the conductor of an orchestra: it replaces a musician who faints, adds violins when the hall fills up, and never stops the music to swap sheet music.

  • Kubernetes (K8s) is an open-source container orchestrator: it runs containers across a cluster of machines and keeps them running. Born from Google's Borg, now a CNCF project.
  • Compose (S8) runs containers on one host. In production you need many hosts, and something that reacts when things break at 3 a.m.
Problem at scalePlain Docker / ComposeKubernetes

Scaling--scale api=3, one host, port clasheskubectl scale --replicas=10 across nodes; HPA autoscaling (S13)

Service discovery / LBContainer names on one hostServices: stable IP + DNS + load balancing across nodes (S11)
Placement (bin-packing)You pick the serverScheduler places pods by CPU/memory requests

StorageLocal volumes on one diskPersistentVolumes backed by cloud disks (S13)

Declarative desired state & the reconciliation loop

  • You don't say "start 3 containers" (imperative). You declare "there should be 3 replicas of taskflow-api:1.0" (declarative) and K8s stores that as the desired state.
  • Controllers run a loop forever: observe actual state → diff with desired → act to close the gap.
desired state (stored in etcd)             actual state (what is running)
     replicas: 3        ───── compare ─────▶     2 pods running
          ▲                                           │
          │                                           ▼
    you edit YAML                         controller acts: create 1 pod
          └────────────── observe again ◀─────────────┘
Example: node failure at 02:00

TaskFlow runs replicas: 3 on node-1/2/3. node-2 loses power. ~40–50 s later the node controller marks it NotReady; after the default 5-minute toleration its pod is evicted, the ReplicaSet sees 2/3 and creates a replacement, and the scheduler puts it on node-1 or node-3. Back to 3/3 without anyone waking up.

When not to use K8s: one small app on one VM — Compose or a systemd service is simpler and cheaper.

Recap K8s = orchestration across many machines: self-healing, scaling, rollouts, discovery, bin-packing. You declare desired state; controllers reconcile reality to it, forever.

2 Architecture: control plane & worker nodes

Explain like I'm 5

The control plane is the head office that decides and remembers; worker nodes are the factories that actually do the work and report back.

  • A cluster = one or more control plane nodes (the brain) + worker nodes (run your pods; a pod = one or more containers sharing an IP).
  • Production: 3 control-plane nodes for high availability. Managed K8s (EKS, AKS, GKE) runs the control plane for you. minikube/kind: one node does both jobs.

3 API server & etcd

Explain like I'm 5

The API server is the only receptionist allowed to write in the company's record book (etcd). Everyone — you, the scheduler, every node — has to ask the receptionist.

kube-apiserver

  • A REST API over HTTPS (port 6443 on kubeadm clusters, 8443 on minikube). kubectl, kubelets, the scheduler and controllers are all just API clients.
  • Every request passes the same pipeline before anything is stored:
kubectl apply ──HTTPS──▶ kube-apiserver
                           │ 1. Authentication     who are you?        (client cert, token, OIDC)
                           │ 2. Authorization      are you allowed?    (RBAC, S16)
                           │ 3. Mutating admission  fill defaults, inject sidecars
                           │ 4. Schema validation   is this a valid Deployment?
                           │ 5. Validating admission policies, ResourceQuota
                           ▼
                         etcd (object persisted) ──▶ watchers notified (controllers, scheduler, kubelets)
  • Watch: components keep a long-lived connection and get pushed every change to the objects they care about — that's how work gets triggered without polling etcd.
  • URL layout: core group /api/v1/namespaces/taskflow/pods; named groups /apis/apps/v1/namespaces/taskflow/deployments.

etcd

  • A distributed, strongly consistent key-value store. Every object (pods, deployments, secrets…) lives under keys like /registry/pods/<namespace>/<name>.
  • Uses the Raft consensus algorithm: a write succeeds only when a majority (quorum) of members agree.
  • Lose etcd without a backup = lose the cluster's memory. Running containers keep running, but nothing can be changed or recovered.

Common mistakes
  • Thinking kubectl or the scheduler writes to etcd directly. Only the API server does.
  • Running 2 etcd members "for HA" — quorum is 2, so losing either one stops writes. Worse than 1.
  • Secrets are stored in etcd base64-encoded, not encrypted, unless encryption at rest is configured (S12).
Recap API server: authn → authz → admission → validate → etcd, then notifies watchers. etcd: Raft-replicated KV store of all state; odd member counts; back it up with etcdctl snapshot save.

4 Scheduler & controller manager

Explain like I'm 5

The scheduler is the seating host who picks a table for each new guest. The controllers are managers who keep counting heads and fix anything that doesn't match the plan.

kube-scheduler: filter → score → bind

  1. Watches for pods whose spec.nodeName is empty.
  2. Filter: drop nodes that can't run it — not enough free CPU/memory (by requests), untolerated taints, nodeSelector/affinity mismatch, host port in use, volume in another zone.
  3. Score: rank survivors 0–100 per plugin — spread resource usage, image already on the node, affinity preferences, spreading replicas.
  4. Bind: write the winning node into the pod (spec.nodeName). The scheduler never starts containers — the kubelet does.
Example: placing a taskflow-api pod (requests 500m CPU, 512Mi memory)
NodeFree CPU / memoryOtherFilterScore (illustrative)
node-1300m / 3Gi—❌ Insufficient cpu—
node-22 / 6Gitaint dedicated=db:NoSchedule❌ untolerated taint—
node-31500m / 1Gi—✅48 (memory would be tight)
node-43 / 5Giimage already cached✅86 → chosen

  • One binary running dozens of controllers. Each watches certain objects via the API server and acts to make actual = desired.

cloud-controller-manager

Only on cloud clusters. Splits cloud-specific logic out of core K8s: the service controller creates a real AWS/Azure/GCP load balancer for type: LoadBalancer (S11), the node controller labels nodes with zone/instance type and removes deleted VMs, the route controller sets up pod-network routes. That's why EXTERNAL-IP stays <pending> on minikube.

Common mistake

Deleting pods of a Deployment to "stop the app" — the controller just recreates them. Scale to 0 (kubectl scale deploy/taskflow-api --replicas=0) or delete the Deployment.

Recap Scheduler: filter → score → bind (writes nodeName). Controller manager: many reconcile loops (Deployment, ReplicaSet, Node, EndpointSlice, Job…). Cloud controller manager: the cloud-API bits.

Explain like I'm 5

The kubelet is the factory foreman: it reads orders from head office, tells the machines (container runtime) what to build, and phones back progress. kube-proxy is the factory's switchboard.

What happens when you run kubectl apply -f deployment.yaml

k8s/deployment.yaml (minimal — explained fully in S10)
apiVersion: apps/v1                # API group "apps", version v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
  labels:
    app: taskflow-api
spec:
  replicas: 3                      # desired state: 3 pods
  selector:
    matchLabels:
      app: taskflow-api              # which pods this Deployment owns
  template:                          # pod template: every replica is stamped from this
    metadata:
      labels:
        app: taskflow-api            # must match the selector
    spec:
      containers:
      - name: api
        image: shauryav/taskflow-api:1.0
        ports:
        - containerPort: 3000
        resources:
          requests:                  # what the scheduler reserves on a node
            cpu: 100m                # 0.1 CPU core
            memory: 128Mi

deployment.apps/taskflow-api created
kubectl ──①──▶ kube-apiserver ──②──▶ etcd
                    │
                    ├─③ Deployment controller sees new Deployment → creates ReplicaSet
                    ├─④ ReplicaSet controller sees 0/3 pods       → creates 3 Pods (no node yet)
                    ├─⑤ Scheduler sees unscheduled Pods           → binds each to a node
                    ├─⑥ kubelet on that node sees its Pod          → CRI: pull image, start containers
                    └─⑦ kubelet reports Running/Ready              → API server → etcd
  1. kubectl reads ~/.kube/config, converts YAML → JSON, sends an HTTPS request to /apis/apps/v1/namespaces/taskflow/deployments.
  2. API server authenticates, authorizes, runs admission + validation, stores the Deployment in etcd, replies created. Your command returns here — everything below is asynchronous.
  3. Deployment controller (watching Deployments) creates a ReplicaSet taskflow-api-7c9d8b6f4.
  4. ReplicaSet controller sees 0 of 3 pods → creates 3 Pod objects with empty nodeName.
  5. Scheduler filters + scores nodes, writes nodeName into each pod.
  6. kubelet on that node sees a pod assigned to it → asks containerd (CRI) to create the pod sandbox; the CNI plugin gives it an IP; image pulled; container started.
  7. kubelet reports status → API server → etcd. kubectl get pods now shows Running. (Then the EndpointSlice controller and kube-proxy wire up any matching Service.)

Key takeaway

Components never call each other directly. They all watch the API server and react to object changes. That's why each piece can crash and restart without losing work — the state is in etcd.

Recap kubelet = node agent (pods, CRI, status); kube-proxy = Service rules; runtime = containerd/CRI-O. Apply flow: kubectl → API server → etcd → Deployment ctrl → ReplicaSet ctrl → scheduler → kubelet → status.

7 YAML anatomy & imperative vs declarative

Explain like I'm 5

Every Kubernetes YAML is a form with the same four boxes: what kind of thing, which version of the form, its name tag, and what you want it to be.

k8s/pod.yaml
apiVersion: v1                     # group/version — Pods live in the core group "v1"
kind: Pod                          # object type
metadata:                          # identity
  name: taskflow-api                # unique per kind + namespace
  namespace: taskflow
  labels:                           # key/value tags used by selectors (S10, S11)
    app: taskflow-api
    tier: backend
spec:                              # DESIRED state — you write this
  containers:
  - name: api                       # container name inside the pod
    image: shauryav/taskflow-api:1.0
    ports:
    - containerPort: 3000           # informational, like EXPOSE
    env:
    - name: PORT
      value: "3000"                 # env values must be strings → quote numbers

Common mistakes
  • value: 3000 (unquoted) → Error from server (BadRequest): … json: cannot unmarshal number into Go struct field EnvVar.spec.containers.env.value of type string.
  • Tabs in YAML → error converting YAML to JSON: yaml: line 7: found character that cannot start any token. Spaces only, 2 per level.
  • Editing env of a running pod and re-applying → The Pod "taskflow-api" is invalid: spec: Forbidden: pod updates may not change fields other than `spec.containers[*].image`, …. Pods are nearly immutable — that's why we use Deployments (S10).

Key takeaway

Use imperative commands to explore and to generate YAML; use kubectl apply -f on files in Git to run things. Every TaskFlow manifest in k8s/ follows this.

Recap apiVersion / kind / metadata / spec (you) + status (K8s). create = "make new", apply = "make it look like this file". --dry-run=client -o yaml generates starter YAML.

★ Putting it all together

The big idea

Kubernetes is a desired-state machine. You kubectl apply TaskFlow's YAML; the API server checks it and stores it in etcd; the controller manager turns a Deployment into a ReplicaSet and Pods; the scheduler picks a node for each pod; the kubelet on that node has containerd run the containers and reports back; kube-proxy wires Services to them. Every piece only watches the API server, so if a pod, a component or a whole node fails, the loops notice the gap and close it. kubectl + kubeconfig is your remote control for all of it.

Quick self-check

Which control-plane component is the only one that reads and writes etcd?

kube-apiserver. Scheduler, controllers, kubelets and kubectl all go through it.

A pod is Pending with 0/3 nodes are available: 3 Insufficient cpu. Which component wrote that and what does it mean?

kube-scheduler (event source default-scheduler). No node passed the filter step: the pod's CPU requests exceed every node's unreserved CPU. Lower requests, free capacity, or add nodes.

You delete one pod of a 3-replica Deployment and a new pod appears seconds later. Which components made that happen, in order?

ReplicaSet controller (in kube-controller-manager) sees 2/3 and creates a Pod object → scheduler binds it to a node → kubelet on that node starts it via the container runtime.

How many failures does a 5-member etcd cluster tolerate, and why use odd numbers?

2 (quorum = 3). An even count adds a member without adding fault tolerance (4 members still tolerate only 1).

kubelet vs kube-proxy — one line each.

kubelet: node agent that runs/monitors the pods assigned to its node via CRI and reports status. kube-proxy: programs iptables/IPVS rules on each node so Service virtual IPs reach the right pods.

What happens if you run kubectl create -f pod.yaml twice? kubectl apply -f pod.yaml twice?

create fails the second time with AlreadyExists. apply is idempotent: unchanged (or configured if the file changed).

What three things does a kubeconfig context bind together?

A cluster (API server URL + CA), a user (credentials) and optionally a default namespace.
