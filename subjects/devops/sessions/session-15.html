1 Namespaces

The problem

Since Session 9 you've typed -n taskflow on nearly every command. Here's why. Suppose you and Riya share one minikube and both deploy into default, the namespace you get when you don't name one:

$ kubectl apply -f k8s/deployment.yaml           # you, Monday
deployment.apps/taskflow-api created
$ kubectl apply -f riya/deployment.yaml          # Riya, Tuesday: same name, her own image
deployment.apps/taskflow-api configured       # not "created": she just replaced yours

Both files say name: taskflow-api, so Kubernetes treated hers as an edit of yours. And names are only the first clash: her load test can take your CPU, and whoever may delete her pods may delete yours.

The idea

A namespace is a named partition inside one cluster. Names only have to be unique within a namespace, and the namespace is the unit you attach rules to: quotas (section 4), RBAC and NetworkPolicies (Session 16).

               one cluster: one API server, the same nodes underneath
 ┌─ ns: taskflow ───────────────┐ ┌─ ns: riya-demo ──────────────┐ ┌─ ns: kube-system ─┐
 │ deploy/taskflow-api          │ │ deploy/taskflow-api          │ │ coredns, etcd,    │
 │ svc/taskflow-db              │ │ svc/taskflow-db              │ │ kube-proxy …      │
 │ quota 2 CPU · devs read-only │ │ quota 1 CPU                  │ └───────────────────┘
 └──────────────────────────────┘ └──────────────────────────────┘
   same names, no clash ✔           pods can still reach each other across namespaces
 nodes, PersistentVolumes, StorageClasses: in NO namespace, shared by everyone
Think of it like this

The cluster is one office building and its floors are the nodes. A namespace is a company renting space, with its own staff list (both can employ an "Asha"), budget and keycards. The walls between companies are glass until security adds locks (NetworkPolicies).

See it: two teams, one name

$ kubectl create namespace riya-demo
namespace/riya-demo created
$ kubectl apply -f riya/deployment.yaml -n riya-demo
deployment.apps/taskflow-api created
$ kubectl get deploy -A | grep -E 'NAMESPACE|taskflow-api'
NAMESPACE   NAME           READY   UP-TO-DATE   AVAILABLE   AGE
riya-demo   taskflow-api   1/1     1            1           20s
taskflow    taskflow-api   2/2     2            2           6d

-n riya-demo targets that namespace for any objects whose YAML names none (same flag for get, logs, delete). -A lists all namespaces, with a NAMESPACE column.

What it does not do: -n doesn't create a missing namespace (namespaces "riya-demo" not found), and the namespace blocks no traffic. Riya's pods can still call TaskFlow's API.

Every cluster starts with four namespaces (kubectl get ns lists them, plus taskflow):

Built-in namespaceContains
defaultAnything created without -n or metadata.namespace. Don't run real apps here.
kube-systemControl plane and add-ons: kube-apiserver, etcd, scheduler, controller-manager, CoreDNS, kube-proxy, metrics-server
kube-publicReadable by everyone, even unauthenticated users. Holds the cluster-info ConfigMap.
kube-node-leaseOne Lease per node: the kubelet's heartbeat, which is how the control plane notices a dead node

Build it up

k8s/namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: taskflow                      # lowercase DNS label, ≤ 63 chars
  labels:
    app.kubernetes.io/part-of: taskflow
    env: dev                          # labels let NetworkPolicies / Pod Security select namespaces

A Namespace has no namespace: field, since it can't live inside another one. Kubernetes also adds the label kubernetes.io/metadata.name: taskflow by itself, which Session 16's policies use.

$ kubectl apply -f k8s/namespace.yaml           # fresh cluster; or: kubectl create namespace taskflow
namespace/taskflow created

# stop typing -n taskflow: change the current context's default namespace
$ kubectl config set-context --current --namespace=taskflow
Context "minikube" modified.
$ kubectl config view --minify -o jsonpath='{..namespace}{"\n"}'
taskflow

# the manifest names one namespace, the flag names another → refused
$ kubectl apply -f k8s/deployment.yaml -n default
error: the namespace from the provided object "taskflow" does not match the namespace "default". You must pass '--namespace=taskflow' to perform this operation.

Not everything lives in a namespace

Calling across namespaces

A short Service name is completed with the caller's own namespace (the DNS search list from Session 11). From elsewhere, use <service>.<namespace> or the full name:

# Prometheus lives in "monitoring" (section 6) and scrapes the API in "taskflow"
$ kubectl run tmp -n monitoring --rm -it --image=busybox:1.36 --restart=Never -- \
    wget -qO- -T 3 http://taskflow-api.taskflow.svc.cluster.local/health
{"status":"ok"}
pod "tmp" deleted
Common mistakes

kubectl delete namespace taskflow deletes everything in it, PVCs included (and, with reclaim policy Delete, the disks). There is no undo. A namespace stuck in Terminating holds an object whose finalizer can't finish: kubectl get ns taskflow -o yaml → status.conditions names it.

Exam trap

"Namespaces isolate pods on the network." ✗ They separate names and the scope of rules. Traffic flows freely until a NetworkPolicy blocks it.

"Each namespace gets its own nodes." ✗ Nodes are cluster-scoped and shared, unless you add scheduling rules (Session 16).

Remember

Namespace = separate names + a scope for rules, not a network wall.
-n one · -A all · set-context --current --namespace = change your default · other namespace? call svc.ns

Mastery check
Q1. k8s/deployment.yaml says namespace: taskflow. Predict kubectl apply -f k8s/deployment.yaml -n default.

Refused: the namespace in the object doesn't match default. -n only fills in a namespace the file leaves out. It never silently overrides one.

Q2. A pod in monitoring runs wget http://taskflow-api/health and gets bad address 'taskflow-api', but http://taskflow-api.taskflow/health works. Why?

The short name was completed with the pod's own namespace, giving taskflow-api.monitoring.svc.cluster.local, which doesn't exist. .taskflow names the right one.

Q3. True or false: "A PersistentVolume lives in the namespace of the PVC that claims it."

False. The PVC is namespaced; the PV is cluster-scoped, like nodes. kubectl get pv takes no -n.

2 Requests & limits

The problem

Two puzzles from one minikube node (2 CPUs, 4 GB). First:

$ kubectl top nodes
NAME       CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
minikube   104m         5%     1450Mi          37%              # nearly idle…
$ kubectl scale deploy taskflow-api -n taskflow --replicas=10
$ kubectl get pods -n taskflow --field-selector=status.phase=Pending
NAME                            READY   STATUS    RESTARTS   AGE
taskflow-api-7c9d8f6b5d-x8k2p   0/1     Pending   0          40s     # …yet pod 10 won't fit
$ kubectl describe pod taskflow-api-7c9d8f6b5d-x8k2p -n taskflow | tail -1
  Warning  FailedScheduling  40s   default-scheduler  0/1 nodes are available: 1 Insufficient cpu. preemption: 0/1 nodes are available: 1 No preemption victims found for incoming pod.

Second: an API pod restarts with OOMKilled while the node has 2.5 GB free. A node with room to spare refuses one pod and kills another.

The idea

Each container can declare two numbers per resource. The request is what it reserves: the scheduler adds up requests per node and places a pod only where its request still fits. The limit is a hard ceiling, enforced by the kernel's cgroups (Session 6).

 one container's memory
 0 ───────────── 128Mi ────────────────────────── 256Mi ──────────▶
                 request                          limit
 ├── reserved ──┤├── allowed if the node has spare ──┤├ over → OOMKilled (exit 137)
   the SCHEDULER adds these up                         the KERNEL enforces this
 CPU: same picture (100m request, 500m limit), but over the limit → throttled, never killed
Think of it like this

A request is the desks you reserve at reception, which books floors by reservations, not by who's sitting there. A limit is your circuit breaker from Session 6: too much power (memory) trips it; too much CPU only dims the lights.

See it: the resources block

k8s/deployment.yaml — container resources (excerpt)
          resources:
            requests:            # guaranteed minimum; what the SCHEDULER uses to pick a node
              cpu: 100m          # 0.1 core
              memory: 128Mi      # 128 × 2^20 bytes
            limits:              # hard ceiling, enforced by the kubelet / Linux cgroups
              cpu: 500m          # above this → throttled
              memory: 256Mi      # above this → OOMKilled (exit 137)
UnitMeansExample
CPU 11 vCPU / core / hyperthreadcpu: "2" = two cores
CPU m (millicores)1/1000 of a core250m = a quarter core; 0.1 = 100m
Memory Ki Mi GiPowers of 2 (1Mi = 1,048,576 B)256Mi = 268,435,456 bytes
Memory k M GPowers of 10 (1M = 1,000,000 B)256M ≈ 244Mi
Memory mmilli-bytes (!)256m = 0.256 bytes, a typo that breaks the pod

What it does not do: a request doesn't cap usage, and a limit reserves nothing (so a node's limits can total over 100%).

Build it up: solving both puzzles

$ kubectl describe node minikube | grep -A5 'Allocated resources'
Allocated resources:
  (Total limits may be over 100 percent, i.e., overcommitted.)
  Resource           Requests      Limits
  --------           --------      ------
  cpu                1950m (97%)   5200m (260%)
  memory             1462Mi (37%)  2834Mi (72%)
Worked example: puzzle 1

Allocatable CPU is 2000m; everything else on the node (control plane, CoreDNS, ingress…) requests 1050m, leaving 950m. At 100m per API pod, 9 pods fit (1050m + 900m = 1950m). Pod 10 needs 100m, only 50m is unreserved, so it's Pending: Insufficient cpu at 5% real usage.

Puzzle 2: the OOM kill belongs to the container, not the node.

$ kubectl get pod taskflow-api-7c9d8f6b5d-4kq2x -n taskflow \
    -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason} {.status.containerStatuses[0].lastState.terminated.exitCode}{"\n"}'
OOMKilled 137

The container passed its own 256Mi limit, and its cgroup doesn't care what the node has free. (Session 14 diagnosed this symptom; now you know who enforces it.)

requestslimits
Used byScheduler (fits if allocatable − sum of requests ≥ this), HPA percentages, eviction rankingKubelet + kernel cgroups at runtime
CPU above itAllowed if the node has idle CPUThrottled (CFS quota: 500m = 50 ms per 100 ms). Slower, not killed.
Memory above itAllowed, but first in line for eviction under node memory pressureOOMKilled, container restarted
If omittedDefaults to the limit if a limit is set; otherwise 0Unlimited (up to the node)

Rule of thumb: request ≈ typical usage, limit ≈ peak. A tight CPU limit on an API shows up as slow p95 latency, not errors.

Exam trap

"The scheduler places pods by how much CPU they actually use." ✗ It counts requests. A node at 5% usage can be full.

"A container over its CPU limit is killed." ✗ It's throttled. Only going over the memory limit kills it (OOMKilled, 137).

Remember

request = reservation (the scheduler counts it) · limit = ceiling (the kernel enforces it)
CPU over the limit → throttled · memory over the limit → OOMKilled

Mastery check
Q1. requests: {cpu: 250m, memory: 256Mi}, limits: {cpu: 500m, memory: 256Mi}. The container reaches 300Mi and 700m CPU. What happens to each?

Memory is over the limit, so it's OOMKilled (137) and restarted. CPU is throttled to 500m: slower, never killed.

Q2. Fill in: 0.25 cores = ____m · 1Gi = ____Mi · 512M ≈ ____Mi · 512m of memory = ____ bytes.

250 · 1024 · 488 · 0.512, which is a typo for 512Mi.

Q3. The HPA from Session 13 shows <unknown>/50% on a Deployment with no resources block. Why?

CPU utilisation is a percentage of the request. With no request there's nothing to divide by. Add requests.cpu.

3 QoS classes

The problem

A memory leak pushes the node to its limit, and the kubelet must evict pods to save it. On the node:

debug          busybox you forgot about    no resources set
taskflow-api   ×2                          requests 100m/128Mi, limits 500m/256Mi
postgres-0     the database                requests = limits = 500m/512Mi

You'd want debug gone first and Postgres last. The kubelet doesn't know what matters to you, only what you declared in section 2.

The idea

From requests and limits alone, Kubernetes puts every pod in a QoS class (quality of service), and evicts by class under node memory pressure:

 node short on memory → kubelet evicts in this order:
   1st   BestEffort   no requests or limits anywhere          debug
   2nd   Burstable    something set, but not "req == lim"     taskflow-api
                      (the pod furthest over its request goes first)
   last  Guaranteed   every container: cpu AND memory set,    postgres-0
                      requests == limits
Think of it like this

A power cut in the building. Reception cuts tenants with no contract first, then those on a flexible contract using more than they booked, and the fixed, fully paid contracts last.

See it

$ kubectl get pods -n taskflow -o custom-columns='NAME:.metadata.name,QOS:.status.qosClass'
NAME                            QOS
debug                           BestEffort
taskflow-api-7c9d8f6b5d-4kq2x   Burstable
postgres-0                      Guaranteed

-o custom-columns='HEADER:.json.path,…' prints only the fields you name. What it does not do: let you set the class. qosClass lives under status, so it's computed. Change requests and limits instead.

Build it up: the rules

ClassRuleTaskFlow example
GuaranteedEvery container sets cpu and memory, with requests == limitsPostgres: requests: {cpu: 500m, memory: 512Mi}, limits: {cpu: 500m, memory: 512Mi}
BurstableAt least one request or limit set, but not GuaranteedAPI: requests 100m/128Mi, limits 500m/256Mi
BestEffortNo requests or limits on any containerkubectl run debug --image=busybox:1.36

Setting only limits (cpu and memory) also gives Guaranteed, as requests default to the limits.

Exam trap

"Guaranteed pods are never killed." ✗ One that passes its own memory limit is still OOMKilled. Guaranteed only means "evicted last when the node runs short".

"memory requests == limits makes a pod Guaranteed." ✗ CPU must match too, in every container, sidecars included.

Remember

Guaranteed (req = lim, cpu + memory, every container) › Burstable › BestEffort (nothing set)
Node short on memory: BestEffort first, Guaranteed last.

Mastery check
Q1. Classify: (a) requests 250m/256Mi, limits 500m/256Mi · (b) only limits: {cpu: 1, memory: 1Gi} · (c) an app container with req == lim plus a sidecar with nothing set.

(a) Burstable: CPU request ≠ limit. (b) Guaranteed: requests default to the limits. (c) Burstable: every container must qualify.

Q2. Node memory pressure: debug (BestEffort), API pod A using 120Mi (request 128Mi), API pod B using 240Mi (request 128Mi), postgres-0 (Guaranteed). Predict the eviction order.

debug → B (furthest over its request) → A → postgres-0. The kubelet stops once enough memory is free, so usually only the first one or two go.

4 ResourceQuota & LimitRange

The problem

Namespaces gave you and Riya separate names, not separate budgets. Her load test scales to 30 pods and reserves the node's CPU, so your rollout waits:

$ kubectl get pods -n riya-demo --no-headers | wc -l
30
$ kubectl get pods -n taskflow | grep Pending
taskflow-api-86f7d6c5b9-lm4zt   0/1     Pending   0          3m       # Insufficient cpu

The idea

A ResourceQuota caps a namespace's total: sums of requests and limits, plus object counts. A LimitRange sets rules for each container: a minimum, a maximum and defaults for containers that declare nothing. Both are checked at admission, so neither kills a running pod.

 kubectl apply (new pod) ──▶ API server admission
   1. LimitRange     no resources?    → inject defaults (100m/128Mi → 500m/256Mi)
                     too big / small? → reject "maximum cpu usage per Container is 2…"
   2. ResourceQuota  used + this pod ≤ hard?  no → reject "exceeded quota …"
   3. stored in etcd → the scheduler places it
Think of it like this

The quota is the company's lease: "20 desks and 2 kW in total". The LimitRange is its office policy: "nobody gets more than 2 desks, and if you don't ask, you get 1".

See it: a budget for taskflow

k8s/quota.yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: taskflow-quota
  namespace: taskflow                 # applies to this namespace only
spec:
  hard:
    requests.cpu: "2"                 # sum of all pods' CPU requests ≤ 2 cores
    requests.memory: 4Gi
    limits.cpu: "4"                   # sum of all CPU limits ≤ 4 cores
    limits.memory: 8Gi
    pods: "20"                        # object counts
    persistentvolumeclaims: "5"
    requests.storage: 50Gi            # total PVC size
    services.loadbalancers: "0"       # no cloud LBs from this namespace (use the Ingress)
    count/deployments.apps: "10"      # count/<resource>.<group> works for any type

Counts also exist for services, secrets and configmaps; storage can be capped per class (gp3.storageclass.storage.k8s.io/requests.storage).

$ kubectl apply -f k8s/quota.yaml
resourcequota/taskflow-quota created
$ kubectl describe quota taskflow-quota -n taskflow

limits.cpu              1500m  4

requests.storage        5Gi    50Gi
services.loadbalancers  0      0      # Used = 2 API pods (100m/128Mi → 500m/256Mi) + Postgres (500m/512Mi, req = lim)

What it does not do: touch running pods. An over-budget namespace only has new objects refused. And there's a side effect that surprises everyone:

$ kubectl run tmp -n taskflow --image=busybox:1.36 --restart=Never -- sleep 3600
Error from server (Forbidden): pods "tmp" is forbidden: failed quota: taskflow-quota: must specify limits.cpu for: tmp; limits.memory for: tmp; requests.cpu for: tmp; requests.memory for: tmp

Once a quota covers CPU and memory, every new pod must declare them. The quota can't add up numbers that don't exist.

Build it up: LimitRange fills in the blanks

k8s/limitrange.yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: taskflow-limits
  namespace: taskflow
spec:
  limits:
    - type: Container
      defaultRequest: {cpu: 100m, memory: 128Mi}   # injected when a container sets no request
      default:        {cpu: 500m, memory: 256Mi}   # injected when a container sets no LIMIT
      min:            {cpu: 50m,  memory: 64Mi}    # reject anything smaller
      max:            {cpu: "2",  memory: 2Gi}     # reject anything bigger
    - type: PersistentVolumeClaim
      min: {storage: 1Gi}
      max: {storage: 20Gi}                         # no single PVC above 20Gi

{cpu: 100m, memory: 128Mi} is YAML flow style: the same map written on one line. You'll see it in a few files below.

Container              memory    64Mi  2Gi   128Mi            256Mi          -

$ kubectl get pod tmp -n taskflow -o jsonpath='{.spec.containers[0].resources}{"\n"}'

Exam trap

"Applying a ResourceQuota evicts pods that are over budget." ✗ Quotas act at admission. Running pods stay; only new ones are refused.

"A Deployment over quota fails at kubectl apply." ✗ The Deployment is accepted, and its ReplicaSet's pod creations fail. Look for FailedCreate events.

Remember

Quota = the namespace's total · LimitRange = each container's min / max / defaults.
Deploy them as a pair: the defaults stop the quota's "must specify" error.

Mastery check
Q1. With the LimitRange above, a container sets only limits: {cpu: 300m}. What CPU request and what memory values does it end up with?

CPU request 300m: when only a limit is given, the request defaults to that limit, not to defaultRequest. Memory gets the defaults: request 128Mi, limit 256Mi.

Q2. Two API replicas each request cpu: 1, and the quota's requests.cpu is "2". You change the image. Predict the rolling update (Session 10, maxSurge 1).

It stalls. The surge pod would make the total 3 cores, so the new ReplicaSet gets FailedCreate: exceeded quota and the two old pods keep running. Leave headroom in the quota, or use maxSurge: 0, maxUnavailable: 1.

Q3. Spot the bug: a PVC in taskflow asks for storage: 30Gi.

The LimitRange caps a single PVC at 20Gi, so it's rejected. It fits the quota's 50Gi total, but each PVC must also pass the per-item rule.

5 StatefulSets

The problem

Since Session 13, Postgres has run as a one-replica Deployment with one PVC. Give it a second replica:

$ kubectl scale deploy taskflow-db -n taskflow --replicas=2
$ kubectl get pods -n taskflow -l app=taskflow-db
NAME                          READY   STATUS             RESTARTS      AGE
taskflow-db-6b8d9f7c5-k7m2p   1/1     Running            0             3d
taskflow-db-6b8d9f7c5-q4n8w   0/1     CrashLoopBackOff   3 (20s ago)   90s
$ kubectl logs taskflow-db-6b8d9f7c5-q4n8w -n taskflow
FATAL:  lock file "postmaster.pid" already exists
HINT:  Is another postmaster (PID 1) running in data directory "/var/lib/postgresql/data/pgdata"?

Every Deployment replica comes from one template, so both pods mount the same PVC, and two Postgres servers can't share a data directory. The names are random hashes that change on every restart, too.

The idea

A StatefulSet gives each pod a stable identity: an ordinal name (postgres-0, -1…), a stable DNS name through a headless Service, and its own PVC from volumeClaimTemplates that follows it to any node. Pods start and stop in order.

 Deployment                                StatefulSet
 taskflow-db-6b8d9f7c5-k7m2p ─┐            postgres-0 ──▶ PVC data-postgres-0
 taskflow-db-6b8d9f7c5-q4n8w ─┴─▶ ONE PVC  postgres-1 ──▶ PVC data-postgres-1
 random names, any order                   postgres-2 ──▶ PVC data-postgres-2
                                           start 0 → 1 → 2 · stop 2 → 1 → 0
                                           DNS: postgres-0.taskflow-db.taskflow.svc.cluster.local
Think of it like this

Deployment pods are hot-desking temps: interchangeable and nameless. StatefulSet pods are named employees with an assigned desk and a personal locker. When postgres-0 comes back from leave, it gets the same name and the same locker (PVC), files still inside.

See it: identity survives deletion

$ kubectl apply -f k8s/postgres.yaml             # the full file is below
service/taskflow-db created
statefulset.apps/postgres created
$ kubectl get pods,pvc -n taskflow -l app=taskflow-db
NAME             READY   STATUS    RESTARTS   AGE
pod/postgres-0   1/1     Running   0          2m

NAME                                    STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
persistentvolumeclaim/data-postgres-0   Bound    pvc-2b9e7c41-6d3a-4f8e-a1c5-9e0d7b3f6a28   5Gi        RWO            standard       2m
$ kubectl delete pod postgres-0 -n taskflow
pod "postgres-0" deleted
$ kubectl get pods -n taskflow -l app=taskflow-db -w
NAME         READY   STATUS              RESTARTS   AGE
postgres-0   0/1     ContainerCreating   0          1s
postgres-0   1/1     Running             0          9s     # same name, re-attached to data-postgres-0, data intact

What it does not do: replicate data. Each pod gets its own empty disk (see the trap below).

Build it up: the file

k8s/postgres.yaml (replaces the Session 13 Deployment version)
# --- headless Service: DNS returns pod IPs directly, gives each pod a name ---
apiVersion: v1
kind: Service
metadata:
  name: taskflow-db                   # the API still connects to "taskflow-db:5432"
  namespace: taskflow
spec:
  clusterIP: None                     # headless: no virtual IP, no kube-proxy load balancing
  selector:
    app: taskflow-db
  ports:
    - name: postgres
      port: 5432
      targetPort: postgres
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres                      # pods: postgres-0, postgres-1, …
  namespace: taskflow
  labels:
    app: taskflow-db
spec:
  serviceName: taskflow-db            # MUST name the headless Service → per-pod DNS
  replicas: 1

6 DaemonSets

The problem

Prometheus (Session 22) needs CPU, memory and disk numbers from every node: one metrics agent per node. Try a Deployment with replicas: 3 on 3 nodes:

Deployment, replicas: 3                       what you actually need
lab-worker          node-exporter ×2          lab-control-plane   node-exporter
lab-worker2         node-exporter ×1          lab-worker          node-exporter
lab-control-plane   (none)                    lab-worker2         node-exporter
new node added      (none)                    new node added      node-exporter, automatically

The idea

A DaemonSet runs exactly one pod on every eligible node. It has no replicas field: the node count decides, and new nodes get a pod automatically. It's for node agents: log shippers (Fluent Bit), metrics (node-exporter), networking (Calico, Cilium, kindnet, kube-proxy) and CSI plugins. nodeSelector narrows "eligible"; tolerations admit tainted nodes such as the control plane.

Think of it like this

Every floor needs one fire warden. You don't hire "three wardens" and hope they spread out. You say "one per floor", and a new floor gets its warden on opening day.

See it: your cluster already runs some

A 3-node kind cluster shows it best, because kind taints its control-plane node:

Exam trap

"A DaemonSet runs on every node." ✗ On every eligible node: nodeSelector, affinity and untolerated taints shrink the count.

Mastery check
Q1. On the 3-node kind cluster, node-exporter shows DESIRED = 2. What's missing from the YAML?

The toleration for node-role.kubernetes.io/control-plane:NoSchedule. Without it the control-plane node repels the pod, leaving only the 2 workers eligible.

Q2. Predict: you add a fourth worker. What happens to node-exporter, and to the taskflow-api Deployment?

7 Jobs

The problem

TaskFlow needs its tasks table created once, before the API serves traffic. The only controller you know is a Deployment:

$ kubectl create deployment migrate -n taskflow --image=busybox:1.36 -- echo "migration done"
deployment.apps/migrate created
$ kubectl logs deploy/migrate -n taskflow
migration done
$ kubectl get pods -n taskflow -l app=migrate
NAME                      READY   STATUS             RESTARTS      AGE
migrate-6d9f8b7c5-r2k4x   0/1     CrashLoopBackOff   4 (31s ago)   2m

It succeeded, so why is it crash-looping? Deployment pods have restartPolicy: Always: they exist to keep running, so a finished process is restarted, even after exit 0. A bare kubectl run --restart=Never pod runs once, but nothing retries it if it fails.

The idea

A Job runs pods until a set number succeed (exit 0), then stops. Failures are retried up to backoffLimit (default 6) with exponential back-off: 10 s, 20 s, 40 s… capped at 6 minutes. Finished pods are kept so you can read their logs.

 Job taskflow-migrate  (completions: 1, backoffLimit: 3)
   pod 1 ── exit 1 ✘ ─ wait 10s ─ pod 2 ── exit 1 ✘ ─ wait 20s ─ pod 3 ── exit 0 ✔ → Job Complete
   four failures in a row instead → Job Failed (BackoffLimitExceeded)

 Deployment: exit 0 → restart → exit 0 → restart …  → CrashLoopBackOff
Think of it like this

A Deployment is permanent staff: leave your desk and HR replaces you at once. A Job is a contractor: done means gone, and a botched job means hiring another, up to backoffLimit times.

See it: the smallest Job

$ kubectl delete deployment migrate -n taskflow
$ kubectl create job hello -n taskflow --image=busybox:1.36 -- echo "migration done"
job.batch/hello created
$ kubectl get jobs,pods -n taskflow -l job-name=hello
NAME              STATUS     COMPLETIONS   DURATION   AGE
job.batch/hello   Complete   1/1           4s         10s

NAME              READY   STATUS      RESTARTS   AGE
pod/hello-7bq2m   0/1     Completed   0          10s
$ kubectl logs job/hello -n taskflow
migration done

create job uses the defaults (1 completion, restartPolicy: Never, backoffLimit 6); everything after -- is the command. Pods get the label job-name=hello, and logs job/hello finds the pod for you.

What it does not do: clean up or run again. The Completed pod stays until you delete the Job (or ttlSecondsAfterFinished expires), and a finished Job never re-runs.

Build it up: the real migration

k8s/migrate-job.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: taskflow-migrations
  namespace: taskflow
data:
  001_create_tasks.sql: |             # idempotent: safe if the Job retries
    CREATE TABLE IF NOT EXISTS tasks (
      id         SERIAL PRIMARY KEY,
      title      TEXT        NOT NULL,
      done       BOOLEAN     NOT NULL DEFAULT false,
      created_at TIMESTAMPTZ NOT NULL DEFAULT now()
    );
---
apiVersion: batch/v1
kind: Job
metadata:
  name: taskflow-migrate
  namespace: taskflow
spec:
  completions: 1                      # successful pods needed (default 1)
  parallelism: 1                      # pods running at once (default 1)
  backoffLimit: 3                     # after 3 retries (4 pods total) → Job Failed
  activeDeadlineSeconds: 300          # hard stop after 5 min, retries or not
  ttlSecondsAfterFinished: 3600       # auto-delete Job + pods 1 h after finishing
  template:
    spec:
      restartPolicy: Never            # failed pod is kept for logs; Job creates a new one
      containers:
        - name: migrate
          image: postgres:16          # used only for its psql client
          command: ["psql", "-v", "ON_ERROR_STOP=1", "-f", "/migrations/001_create_tasks.sql"]
          env:                        # libpq reads PG* variables
            - {name: PGHOST, value: taskflow-db}
            - {name: PGUSER, value: taskflow}
            - {name: PGDATABASE, value: taskflow}
            - name: PGPASSWORD
              valueFrom:
                secretKeyRef:
                  name: taskflow-db-secret
                  key: POSTGRES_PASSWORD
          resources:                  # declared explicitly (the LimitRange would fill them in)
            requests: {cpu: 100m, memory: 64Mi}
            limits: {cpu: 500m, memory: 128Mi}
          volumeMounts:
            - {name: migrations, mountPath: /migrations, readOnly: true}
      volumes:
        - name: migrations
          configMap: {name: taskflow-migrations}   # each key becomes a file
LineWhy it's there
CREATE TABLE IF NOT EXISTSA retry or re-run must be harmless: every Job step should be safe to run twice
ON_ERROR_STOP=1Without it psql exits 0 even when a statement fails, and the Job would report success
PGHOST … PGPASSWORDStandard libpq variables, so psql needs no connection flags. The password comes from taskflow-db-secret.
activeDeadlineSecondsWall-clock limit for the whole Job. It beats backoffLimit: at 300 s the Job fails, whatever the retry count.
configMap volumeKey 001_create_tasks.sql appears as the file /migrations/001_create_tasks.sql

restartPolicyOn failurePick when
NeverPod stays Error; the Job creates a new podYou want each failed attempt's logs (as above)

Exam trap

"A Job's pod can use restartPolicy: Always." ✗ Rejected: Unsupported value: "Always": supported values: "OnFailure", "Never". "Always" is what made the Deployment loop.

"backoffLimit: 3 means 3 pods in total." ✗ It's 3 retries: 4 failed pods before the Job is marked Failed.

Remember

Deployment = keep it running · Job = run until it succeeds, then stop.
restartPolicy Never (new pod per try) or OnFailure (same pod) · backoffLimit = retries.

Mastery check
Q1. Same broken password, but restartPolicy: OnFailure. Predict kubectl get pods -l job-name=taskflow-migrate when the Job gives up.

One pod, not four. Its container was restarted in place, so RESTARTS climbs instead of new pods appearing, and only the last two attempts' logs survive (logs and logs --previous).

Q2. backoffLimit: 3, activeDeadlineSeconds: 30, and every attempt hangs 60 s before failing. How many pods run, and why does the Job fail?

One. The 30-second deadline expires during the first attempt, so the Job fails with DeadlineExceeded before any retry. The deadline beats the retry count.

Q3. Spot the bug: a seed Job runs INSERT INTO tasks (title) VALUES ('Welcome'), and its pod failed once with a network timeout after the insert.

The retry inserts the row again: duplicates. Job steps must be idempotent, e.g. INSERT … ON CONFLICT DO NOTHING on a unique key.

8 CronJobs

The problem

TaskFlow needs a pg_dump backup every night at 02:00. Session 3 used crontab, but on which machine? Your laptop sleeps at 2 AM; a node's crontab dies with the node. And once it runs in the cluster, a puzzle: a backup set for 0 2 * * * fires at 07:30 IST.

The idea

A CronJob is a Job template plus a cron schedule. Every tick creates a Job, which creates the pod: CronJob → Job → Pod, like Deployment → ReplicaSet → Pod. Each Job is named after its scheduled time in minutes since the Unix epoch.

 CronJob taskflow-db-backup   schedule "0 2 * * *", timeZone Asia/Kolkata
   ├─ 02:00 Oct 10 ─▶ Job taskflow-db-backup-29859630 ─▶ Pod …-29859630-kx8p2 ─▶ pg_dump ✔
   ├─ 02:00 Oct 11 ─▶ Job taskflow-db-backup-29861070 ─▶ Pod …                ─▶ pg_dump ✔
   └─ keeps the last 3 successful Jobs and the last 1 failed one (history limits)
Think of it like this

The building's nightly cleaning rota. The rota (CronJob) cleans nothing: each night it books a fresh crew (a Job), and the crew does the work (the pod). If last night's crew is still busy, concurrencyPolicy decides what tonight's does.

See it: one tick a minute

$ kubectl create cronjob tick -n taskflow --image=busybox:1.36 --schedule="*/1 * * * *" -- date
cronjob.batch/tick created
$ kubectl get cronjob,jobs -n taskflow          # about 90 seconds later (older Jobs trimmed)
NAME                 SCHEDULE      TIMEZONE   SUSPEND   ACTIVE   LAST SCHEDULE   AGE
cronjob.batch/tick   */1 * * * *   <none>     False     0        30s             95s

NAME                      STATUS     COMPLETIONS   DURATION   AGE
job.batch/tick-29860321   Complete   1/1           4s         30s
$ kubectl delete cronjob tick -n taskflow        # also deletes its Jobs and pods

--schedule takes Session 3's 5 cron fields (minute hour day-of-month month day-of-week). tick-29860321 is the Job for the 08:01 UTC tick, in minutes since 1 Jan 1970. TIMEZONE <none> means the controller-manager's clock, usually UTC.

What it does not do: run when you create it. Nothing happens until the next matching minute. To test now, use kubectl create job --from=cronjob/… (below).

Build it up: the nightly backup

k8s/backup-cronjob.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: taskflow-backups
  namespace: taskflow
spec:
  accessModes: ["ReadWriteOnce"]
  resources: {requests: {storage: 10Gi}}   # default StorageClass
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: taskflow-db-backup
  namespace: taskflow
spec:
  schedule: "0 2 * * *"               # min hour day-of-month month day-of-week → 02:00 daily
  timeZone: "Asia/Kolkata"            # without it: controller-manager's zone, usually UTC
  concurrencyPolicy: Forbid           # don't start if last night's run is still going
  startingDeadlineSeconds: 600        # missed by > 10 min (controller down)? skip this run
  successfulJobsHistoryLimit: 3       # keep 3 finished Jobs (default 3)
  failedJobsHistoryLimit: 1           # keep 1 failed Job (default 1)
  suspend: false                      # true = pause the schedule
  jobTemplate:                        # a normal Job spec, stamped out on each tick
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 1800
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: pg-dump
              image: postgres:16
              command: ["/bin/sh", "-c"]
              args:
                - >-
                  pg_dump -h taskflow-db -U taskflow -d taskflow -Fc
                  -f /backups/taskflow-$(date +%Y%m%d-%H%M).dump &&
                  find /backups -name '*.dump' -mtime +7 -delete &&
                  ls -lh /backups
              env:
                - name: PGPASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: taskflow-db-secret
                      key: POSTGRES_PASSWORD
              resources:
                requests: {cpu: 100m, memory: 128Mi}
                limits: {cpu: 500m, memory: 256Mi}
              volumeMounts:
                - {name: backups, mountPath: /backups}
          volumes:
            - name: backups
              persistentVolumeClaim: {claimName: taskflow-backups}
FieldMeaning
schedule5-field cron, as in crontab; @daily and friends work too
timeZoneIANA zone name (stable since 1.27). Leave it out and "0 2 * * *" runs at 02:00 UTC = 07:30 IST: the puzzle.
concurrencyPolicyAllow (default: overlapping runs OK) · Forbid (skip the new run) · Replace (kill the old run, start the new one)
startingDeadlineSecondsHow late a missed run may still start. Without it, a controller that missed more than 100 schedules stops scheduling the CronJob.
jobTemplateExactly a Job's spec from section 7
args: - >-Folded block: the lines join into one shell command. Kubernetes only expands $(VAR) for env vars it knows, so $(date …) reaches the shell intact.
-Fc · find … -mtime +7 -deleteCustom-format dump (restore with pg_restore) · retention: delete dumps older than 7 days

More schedules: */15 * * * * every 15 minutes · 0 9 * * 1-5 09:00 Monday–Friday · 30 23 * * 0 23:30 every Sunday · 0 0 1 * * midnight on the 1st of each month.

"A CronJob runs its pod directly." ✗ CronJob → Job → Pod. The Job layer adds retries (backoffLimit) and history.

Mastery check
Q1. An hourly backup (0 * * * *) usually takes 20 minutes, but tonight takes 70. What happens at the next tick under Allow, Forbid and Replace?

Allow: a second dump runs alongside the first. Forbid: that tick is skipped and the running dump finishes. Replace: the running Job is killed and a fresh one starts. Forbid suits backups.

Q2. Write the schedule for "every weekday at 18:30 IST", and say which other field you must set.

30 18 * * 1-5 with timeZone: "Asia/Kolkata". Without it, it runs at 18:30 UTC: midnight IST.

Q3. The controller-manager was down from 01:50 to 02:20. Does the 02:00 backup run with startingDeadlineSeconds: 600? With it unset?

With 600: no. At 02:20 the run is 20 minutes late, past the 10-minute deadline, so it's skipped. Unset: yes, it starts as soon as the controller is back.

9 Choosing a workload type

The problem

TaskFlow now runs five kinds of process: always-on and interchangeable (the API), always-on with a disk per copy (Postgres), one per machine (node-exporter), once (the migration) and nightly (the backup). The exam will hand you a sixth. Three questions decide: does the work finish? Does it need one copy per node? Does each copy need its own name and disk?

Does the work finish?
 ├─ yes → on a schedule?  ── yes → CronJob
 │                        └─ no  → Job
 └─ no (long-running)
      ├─ one copy per node? ───────────────────────── yes → DaemonSet

In building terms: hot-desking temps (Deployment), named employees with lockers (StatefulSet), a fire warden per floor (DaemonSet), a contractor for one task (Job) and the nightly cleaning rota (CronJob).

Exam trap

Mastery check
Q1. Pick the controller: (a) a Redis cache that may lose its data · (b) Fluent Bit shipping every node's logs · (c) a monthly invoice report · (d) a 3-broker Kafka cluster · (e) re-indexing search once after a release.

(a) Deployment: a cache needs no stable identity. (b) DaemonSet. (c) CronJob (0 0 1 * *). (d) StatefulSet: each broker needs its own name and disk. (e) Job.

Q2. True or false: "StatefulSets are for anything that writes to disk."

False. A single-replica app with one PVC works as a Deployment (with strategy: Recreate). You need a StatefulSet when each replica needs its own name and volume.

★ Putting it all together

The big idea

TaskFlow lives in the taskflow namespace, under a ResourceQuota (total budget) and a LimitRange (per-pod defaults and caps). A pod's requests decide where it fits, its limits whether it's throttled or OOMKilled, and both together its QoS class, which decides who is evicted first. Each component runs under the controller that fits its lifecycle: Deployment (API), StatefulSet (Postgres, with a stable name, DNS and PVC), DaemonSet (node-exporter), Job (migration) and CronJob (nightly pg_dump).

Final mastery check — combine everything
Q1. With section 4's quota and LimitRange in place, you run kubectl run debug -n taskflow --image=busybox:1.36 -- sleep 3600. Is it accepted? What resources and what QoS class does it get?

Accepted. The LimitRange injects 100m/128Mi requests and 500m/256Mi limits, which also satisfies the quota's "must specify" rule. Requests ≠ limits, so it's Burstable, not BestEffort, although you set nothing.

Q2. Under load the HPA wants 10 API replicas, but kubectl get deploy shows 7/10 and nothing errored. Where's the error, what does it say, and what are two fixes?

In the ReplicaSet's FailedCreate events: "exceeded quota: taskflow-quota, requested: limits.cpu=500m, used: limits.cpu=4, limited: limits.cpu=4" (1500m + 5 × 500m = 4000m). Raise the quota's limits.cpu, or lower the per-pod CPU limit or the HPA's maxReplicas.

Q3. You move the backup CronJob into a new ops namespace. At 02:00 its pod never starts. After you fix that, it fails with could not translate host name "taskflow-db". Explain and fix both.

(1) secretKeyRef only reads Secrets in the pod's own namespace (CreateContainerConfigError): create taskflow-db-secret in ops. (2) The short name now resolves as taskflow-db.ops…: use -h taskflow-db.taskflow.

Q4. Correct every error: "Run Postgres as a Deployment with replicas: 3 for HA, give it no limits so it's never OOMKilled, and it'll be Guaranteed QoS."

(1) Deployment replicas share one PVC (the lock-file crash): use a StatefulSet. (2) Even then, 3 replicas are 3 separate databases; HA needs replication. (3) No limits means BestEffort or Burstable, evicted before Guaranteed. (4) Guaranteed needs requests == limits for cpu and memory, in every container.

Q5. A node is drained for maintenance (Session 16). Predict what happens to postgres-0, to that node's node-exporter pod, and to a running taskflow-migrate pod.

postgres-0 comes back elsewhere with the same name and re-attaches data-postgres-0 (if the volume can move). The node-exporter pod belongs to that node and isn't moved, hence drain's --ignore-daemonsets. The Job pod is evicted and replaced, so the migration may run twice: idempotent SQL again.
