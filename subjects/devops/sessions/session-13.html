1 Volumes: emptyDir, hostPath & friends

Explain like I'm 5

A container's filesystem is a whiteboard wiped on every restart. A volume is a notebook handed to the pod; a PersistentVolume is a locker that's still there after the pod is gone.

  • A container's writable layer is ephemeral: container restarts → files written there are lost.
  • A volume is declared once at pod level (spec.volumes) and mounted into each container that needs it (containers[].volumeMounts).
  • Two lifetimes matter: pod-lifetime (emptyDir — dies with the pod) vs independent (PVC → PV — outlives pods).
Volume typeLifetimeUse forWatch out
emptyDirPod. Survives container restarts, deleted when the pod is removed from the node.Scratch space, caches, sharing files between containers in one pod.medium: Memory = tmpfs; counts toward the container's memory limit.
hostPathNode. A directory on the node's disk.Node agents only (log collectors reading /var/log, node-exporter reading /proc).Pod sees different data on each node; security risk (can mount /). Never for app data.
configMap / secretTied to the ConfigMap/Secret object.Config files, certs (Session 12).Read-only; with subPath updates are NOT propagated.
persistentVolumeClaimIndependent of pods — until the PVC is deleted.Databases, uploads — anything that must survive.Covered in §2–§3.
nfs, csi, projected, downwardAPIVariesNetwork shares, cloud disks, combining sources, exposing pod metadata as files.Usually used through PVs, not directly.

emptyDir: two containers sharing a folder

emptydir-demo.yaml
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
  namespace: taskflow
spec:
  containers:
    - name: writer
      image: busybox:1.36
      command: ["sh", "-c", "while true; do date >> /cache/heartbeat.log; sleep 5; done"]
      volumeMounts:
        - name: cache                  # must match a name under spec.volumes
          mountPath: /cache            # where it appears inside THIS container
    - name: reader
      image: busybox:1.36
      command: ["sh", "-c", "until [ -f /cache/heartbeat.log ]; do sleep 1; done; tail -f /cache/heartbeat.log"]
      volumeMounts:
        - name: cache
          mountPath: /cache
          readOnly: true               # reader can't modify the file
  volumes:
    - name: cache
      emptyDir:
        sizeLimit: 100Mi               # pod is evicted if it writes more than this
  • The volume name links spec.volumes to each container's volumeMounts; each container may mount it at a different mountPath.
  • On the node it lives at /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/cache.

hostPath (snippet — for node agents only)

pod.spec.volumes (snippet)
volumes:
  - name: varlog
    hostPath:
      path: /var/log           # a directory on the NODE, not in the image
      type: Directory          # must already exist; DirectoryOrCreate / File / FileOrCreate / Socket also valid
Common mistake

Using hostPath for Postgres data "because it works on minikube". On a 3-node cluster the pod gets rescheduled to another node and sees an empty directory — the data is still on the old node. Use a PVC.

Recap Declare in spec.volumes, mount with volumeMounts. emptyDir = pod-lifetime scratch/shared space; hostPath = node agents only; real data → PVC.

2 PersistentVolume & PersistentVolumeClaim

Explain like I'm 5

The PVC is an order slip ("5 GB, one writer"); the PV is the actual disk handed over. The pod only ever shows the slip.

  • PersistentVolume (PV): a cluster-scoped object representing a real piece of storage (EBS volume, NFS share, a node directory). Created by an admin (static) or a provisioner (dynamic, §3).
  • PersistentVolumeClaim (PVC): a namespaced request: size + access mode + StorageClass.
  • Binding: the control plane finds a PV with the same storageClassName, whose access modes include the requested ones and capacity ≥ request, and binds them 1:1 (exclusive, even if the PV is bigger).
  • The pod references only the PVC: volumes[].persistentVolumeClaim.claimName. App manifests stay storage-agnostic.

Static provisioning: an admin-made PV

pv-manual.yaml
apiVersion: v1
kind: PersistentVolume                 # cluster-scoped: no namespace
metadata:
  name: taskflow-pv-manual
spec:
  capacity:
    storage: 5Gi                       # size this PV offers
  volumeMode: Filesystem               # default; "Block" = raw device
  accessModes:
    - ReadWriteOnce                    # RWO: mountable read-write by one node
  persistentVolumeReclaimPolicy: Retain  # keep data when the claim is deleted
  storageClassName: manual             # PVC must ask for the same class to bind
  hostPath:
    path: /data/taskflow-pg            # minikube persists /data across restarts
FieldMeaningGotcha
capacity.storageSize offered. Units Mi, Gi, Ti.For hostPath it isn't enforced — just a label for matching.
accessModesWhat the backend supports (table below).A matching rule, not a lock (except RWOP).
persistentVolumeReclaimPolicyWhat happens to the PV when its PVC is deleted.Manually created PVs default to Retain; dynamic ones to Delete.
storageClassNameGroups PVs; a PVC only binds PVs of its class."" = "no class" (static only).
hostPath / nfs / csiThe actual backend. Exactly one.Real clusters use csi (e.g. ebs.csi.aws.com).

Access modes (exam favourite)

ModeShortMeaningTypical backends
ReadWriteOnceRWORead-write by one node (several pods on that same node can share it).AWS EBS, GCE PD, Azure Disk, hostPath

Reclaim policies & PV lifecycle

PolicyWhen the PVC is deleted…Use when
RetainPV → Released; data kept; admin must clean up / re-use manually.Production databases (protects against an accidental kubectl delete pvc).
DeletePV and the real disk are deleted.Dev/test, dynamic provisioning default.

PV phases: Available → Bound → Released (claim gone) / Failed. PVC phases: Pending → Bound (or Lost if its PV vanished).

The claim

  name: pg-manual-claim

spec:
  accessModes:

  storageClassName: manual             # same class as the PV → static binding

Example: asked for 2Gi, got 5Gi

The PVC requested 2Gi but CAPACITY shows 5Gi: binding is to a whole PV. The other 3Gi can't be given to anyone else. (VOLUMEATTRIBUTESCLASS is a newer column for tuning IOPS; <unset> is normal.)

Retain in action — delete the claim, the PV keeps the data but can't be re-bound until you clear its claimRef:

$ kubectl delete pvc pg-manual-claim -n taskflow
persistentvolumeclaim "pg-manual-claim" deleted
$ kubectl get pv taskflow-pv-manual
NAME                 CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM                      STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
taskflow-pv-manual   5Gi        RWO            Retain           Released   taskflow/pg-manual-claim   manual         <unset>                          9m
$ kubectl patch pv taskflow-pv-manual -p '{"spec":{"claimRef":null}}'   # → Available again, data still on disk
persistentvolume/taskflow-pv-manual patched
Common mistakes
  • PVC without storageClassName on minikube gets the default class standard → a new PV is provisioned and your manual PV stays Available. Put the same class on both (or storageClassName: "").
  • PVC stuck Pending: no PV matches (too small, wrong access mode, class typo). kubectl describe pvc → Events tell you which.
  • PVC stuck Terminating: a pod still uses it (kubernetes.io/pvc-protection finalizer). Delete the pod first.
Recap PV = the disk (cluster-scoped), PVC = the request (namespaced), binding is 1:1 by class + access mode + size. Retain keeps data, Delete destroys it.

3 StorageClass & dynamic provisioning

Explain like I'm 5

Instead of an admin pre-building lockers, a StorageClass is a vending machine: put in a PVC, out comes a brand-new PV.

  Pod ──volumes.claimName──▶ PVC ──────binds 1:1──────▶ PV ──backed by──▶ real disk
                             "5Gi, RWO,                 "pvc-8f6c…, 5Gi"   (EBS vol / hostPath dir / NFS)
                              class: gp3"                    ▲
                                 │                            │ creates (dynamic)
                                 └──storageClassName──▶ StorageClass ──provisioner──▶ CSI driver
                                                         "gp3"            ebs.csi.aws.com
  • StorageClass (SC): cluster-scoped "type of storage" + the provisioner (CSI driver) that creates disks of that type.
  • Dynamic provisioning: a PVC naming an SC triggers the provisioner → a PV called pvc-<uid> is created and bound automatically.
  • One SC can be marked default; PVCs that omit storageClassName get it.
$ kubectl get storageclass        # minikube
NAME                 PROVISIONER                RECLAIMPOLICY   VOLUMEBINDINGMODE   ALLOWVOLUMEEXPANSION   AGE
standard (default)   k8s.io/minikube-hostpath   Delete          Immediate           false                  3d

kind's default is standard with rancher.io/local-path and WaitForFirstConsumer. On EKS you define your own, e.g. gp3:

storageclass-gp3.yaml (EKS)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # PVCs without a class get this one
provisioner: ebs.csi.aws.com           # AWS EBS CSI driver creates the volumes
parameters:                            # passed to the provisioner as-is (driver-specific)
  type: gp3                            # EBS volume type
  csi.storage.k8s.io/fstype: ext4
  encrypted: "true"
reclaimPolicy: Delete                  # default; Retain for prod DBs
volumeBindingMode: WaitForFirstConsumer  # create the disk only after the pod is scheduled
allowVolumeExpansion: true             # lets you grow a PVC later
FieldMeaning
provisionerWhich driver makes the PV. Examples: ebs.csi.aws.com, pd.csi.storage.gke.io, disk.csi.azure.com, k8s.io/minikube-hostpath.
parametersOpaque key/values for that driver (disk type, IOPS, encryption). Values must be strings.
reclaimPolicyCopied into every PV this class creates. Default Delete.
volumeBindingModeImmediate (default): provision as soon as the PVC exists. WaitForFirstConsumer: wait until a pod using it is scheduled, then create the disk in that pod's zone.
allowVolumeExpansionIf true, increase spec.resources.requests.storage on the PVC to grow it. Shrinking is never allowed.
is-default-class annotationMarks the default SC (shown as (default)).
Example: why WaitForFirstConsumer on EKS

EBS volumes live in one AZ. With Immediate, the disk may be created in ap-south-1a while the scheduler puts the pod on a node in ap-south-1b → it can never attach. With WFFC the PVC shows Pending with event waiting for first consumer to be created before binding — that's normal, not an error.

# --- 2. Postgres itself (Session 15 upgrades this to a StatefulSet) ---

kind: Deployment
metadata:
  name: taskflow-db
  namespace: taskflow
spec:
  replicas: 1                          # one writer; 2 replicas would NOT replicate data
  strategy:
    type: Recreate                     # stop old pod before starting new → RWO disk is free
  selector:
    matchLabels:
      app: taskflow-db
  template:
    metadata:
      labels:
        app: taskflow-db
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports:
            - name: postgres
              containerPort: 5432
          env:
            - name: POSTGRES_DB
              value: taskflow
            - name: POSTGRES_USER
              value: taskflow
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: taskflow-db-secret
                  key: POSTGRES_PASSWORD
            - name: PGDATA                               # sub-directory of the mount: a fresh ext4
              value: /var/lib/postgresql/data/pgdata     # disk has lost+found, which initdb rejects
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
          readinessProbe:                # probes explained in §6
            exec:
              command: ["pg_isready", "-U", "taskflow", "-d", "taskflow"]
            periodSeconds: 5
          livenessProbe:
            tcpSocket:
              port: postgres
            initialDelaySeconds: 30
            periodSeconds: 10
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data          # Postgres 16 image data dir
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: taskflow-db-data  # ← the PVC above, same namespace
---
# --- 3. Stable name "taskflow-db" for the API's DATABASE_URL ---

4 Metrics Server & kubectl top

Explain like I'm 5

Metrics Server is the cluster's thermometer: it reads every pod's current CPU and memory so kubectl top and the HPA can see them.

kubelet (cAdvisor) ──/metrics/resource──▶ metrics-server ──▶ metrics.k8s.io API ──▶ kubectl top
  on every node        scraped every 15s     latest values      (API aggregation)    HPA controller
                                             in memory only
  • Metrics Server is a cluster add-on (a Deployment in kube-system). Not installed by default on minikube/kind; EKS offers it as an add-on.
  • Keeps only the latest value per pod/node — no history, no dashboards. For that use Prometheus (Session 22).
  • Without it: kubectl top fails and CPU/memory HPAs show <unknown>.

5 Horizontal Pod Autoscaler (HPA)

Explain like I'm 5

The HPA is a thermostat for pods: average CPU above the set point → add pods; below → remove some, always staying between min and max.

  • The HorizontalPodAutoscaler changes spec.replicas of a Deployment / StatefulSet (anything with a scale subresource — not DaemonSets).
  • The controller loop runs every 15 s in kube-controller-manager, reads metrics, computes a desired count, clamps it to [minReplicas, maxReplicas].
  • Horizontal = more pods. Vertical (VPA, separate add-on) = bigger requests per pod. Cluster Autoscaler / Karpenter = more nodes.
  • Requirement: CPU utilization is measured as a % of resources.requests.cpu. No request → no percentage → <unknown>.

The relevant part of taskflow-api (full Deployment in §6):

k8s/deployment.yaml (excerpt)
          resources:
            requests:
              cpu: 100m          # 50% target ⇒ HPA aims for 50m average per pod
              memory: 128Mi
            limits:
              cpu: 500m          # lets a pod burst to 500% of its request
              memory: 256Mi
k8s/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: taskflow-api
  namespace: taskflow
spec:
  scaleTargetRef:                      # WHAT to scale
    apiVersion: apps/v1
    kind: Deployment
    name: taskflow-api
  minReplicas: 2                       # floor: keep 2 for availability
  maxReplicas: 10                      # ceiling: cost / quota guard
  metrics:
    - type: Resource                   # CPU/memory from metrics-server
      resource:
        name: cpu
        target:
          type: Utilization            # % of requests.cpu
          averageUtilization: 50       # keep the average pod at 50%
  behavior:                            # optional: how fast to scale (values below = defaults, except scaleDown policy)
    scaleUp:
      stabilizationWindowSeconds: 0    # react immediately
      selectPolicy: Max                # pick whichever policy allows MORE change
      policies:
        - type: Percent
          value: 100                   # at most double…
          periodSeconds: 15
        - type: Pods
          value: 4                     # …or +4 pods, per 15 s
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300  # use the highest recommendation of the last 5 min (no flapping)
      policies:
        - type: Percent
          value: 50                    # remove at most half the pods per minute
          periodSeconds: 60
FieldMeaning
autoscaling/v2Current API (multiple metrics, behavior). autoscaling/v1 only supports targetCPUUtilizationPercentage.
scaleTargetRefThe workload whose replicas the HPA controls. Must be in the same namespace.
metrics[].typeResource (pod cpu/memory), ContainerResource (one container), Pods (custom per-pod metric e.g. requests/s), Object (metric of another object, e.g. Ingress), External (e.g. SQS queue length). Non-Resource types need a metrics adapter (Prometheus Adapter, KEDA).
target.typeUtilization (% of request, Resource only) · AverageValue (absolute per pod, e.g. 200Mi) · Value (total, Object/External).
behavior.*.stabilizationWindowSecondsLook-back window; scale-down uses the max recommendation in the window so a brief dip doesn't kill pods.
behavior.*.policiesRate limits per periodSeconds. selectPolicy: Max|Min|Disabled.

The formula

HPA algorithm

desiredReplicas = ceil( currentReplicas × currentMetric ÷ targetMetric ), then clamped to min/max and limited by behavior. No action if the ratio is within ±10% of 1.0 (tolerance 0.1). With several metrics, the HPA computes each and takes the largest.

Worked example: TaskFlow under load (request 100m, target 50%)
TimePodsAvg CPUCalculationResult
idle24% (4m)ceil(2 × 4/50) = 1clamped to min → 2
load starts2190% (190m)ceil(2 × 190/50) = ceil(7.6) = 8scaleUp policy: max(2×100% → 4, 2+4 → 6) → 6
+30 s663%ceil(6 × 63/50) = ceil(7.56) = 88
+60 s848%ratio 0.96 — within tolerancestays 8
load stops80%ceil(8 × 0/50) = 0 → min 2waits 300 s, then −50%/min: 8 → 4 → 2

Total load ≈ 380m of CPU throughout; it's just spread over more pods.

Common mistakes
  • cpu: <unknown>/50%: metrics-server missing, or a container has no requests.cpu (event FailedGetResourceMetric … missing request for cpu), or pods just started — wait a minute.
  • replicas: 2 left in deployment.yaml: every kubectl apply resets the count to 2, fighting the HPA. Remove the field once an HPA owns the Deployment.
  • Scaling Node.js on memory: memory usually stays high after the load is gone (V8 heap), so it scales up and rarely back down. Prefer CPU or requests/second.
  • maxReplicas higher than the cluster can fit: new pods sit in Pending (Session 14) or hit a ResourceQuota (Session 15).
Recap HPA (autoscaling/v2) = ceil(current × actual/target), clamped to min/max, rate-limited by behavior. Needs metrics-server + CPU requests. Watch it with kubectl get hpa -w.

6 Liveness, readiness & startup probes

Explain like I'm 5

Startup: "are you awake yet?" Readiness: "can you take customers right now?" Liveness: "are you frozen?" — a frozen worker is replaced, a busy one just gets no new customers.

  • A probe is a health check the kubelet runs against a container on a schedule.
  • Without probes Kubernetes only knows "the process is running" — a deadlocked Node app or one still connecting to Postgres looks healthy and gets traffic.

The full TaskFlow API Deployment

k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
  labels:
    app: taskflow-api
spec:
  # no "replicas:" — the HPA (§5) owns the count
  selector:
    matchLabels:
      app: taskflow-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0                # old pod is removed only after a new one is READY
  template:
    metadata:
      labels:
        app: taskflow-api
    spec:
      containers:
        - name: api
          image: shauryav/taskflow-api:1.2.0
          ports:
            - name: http               # named port: probes & Service refer to "http"
              containerPort: 3000
          envFrom:
            - configMapRef:
                name: taskflow-config  # LOG_LEVEL etc. (Session 12)
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: taskflow-db-secret
                  key: DATABASE_URL
          resources:
            requests:
              cpu: 100m                # HPA % is relative to this
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
          startupProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 2
            failureThreshold: 30       # up to 30 × 2 s = 60 s to boot
          readinessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3        # 3 × 5 s = 15 s failing → out of the Service
            successThreshold: 1        # 1 success → back in
          livenessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3        # 3 × 10 s = 30 s hung → restart
LineWhy
maxUnavailable: 0 + readinessZero-downtime rollouts: Kubernetes only removes an old pod once a new one passes readiness. Without readiness, "Running" = "ready" and users hit pods still booting.
port: httpNamed port — change containerPort once, probes follow.
Same /health for all threeTaskFlow has one health endpoint. A bigger app adds /ready (checks warm caches/deps) and keeps /health process-only.
timeoutSeconds: 2Default 1 s is tight for a busy Node event loop; spurious timeouts cause restarts.
Worked example: timing math (failureThreshold × periodSeconds)
  • Boot budget: startup 30 × 2 s = 60 s. A pod still failing at 60 s is restarted.
  • Event loop blocks at t = 0: readiness fails at ~5, 10, 15 s → pod leaves the Service at ≈15 s. Liveness fails at ~10, 20, 30 s → restart at ≈30 s (each attempt can add the 2 s timeout).
  • Between 15 s and 30 s the pod gets no traffic but isn't killed — if it recovers (a long GC pause), no restart happens.
  • Without a startup probe you'd need livenessProbe.initialDelaySeconds: 60; if a cold start ever takes 70 s → killed at boot → CrashLoopBackOff forever. (Postgres in §3 uses initialDelaySeconds: 30 — fine for a fast DB, a startupProbe is the cleaner option.)

Common mistakes
  • Liveness that checks the database: Postgres restarts for 20 s → every API pod fails liveness → all restart at once (restart storm) → DB is back but the API is in CrashLoopBackOff. Liveness checks only the process.
  • No readiness probe: pods get traffic while booting → 502/503 from the Ingress during every rollout.
  • Wrong port/path: probe on 80 (the Service port) instead of 3000 (the container port), or /healthz when the app serves /health → 404 → never ready.
  • Liveness too aggressive (timeoutSeconds: 1, failureThreshold: 1): one slow response under load = restart, which adds more load to the others.
Key takeaway

Readiness controls traffic, liveness controls restarts, startup protects slow boots. Their budget is always failureThreshold × periodSeconds.

Recap Probes = kubelet health checks (httpGet/tcpSocket/exec/grpc). Readiness failing → 0/1, no endpoints; liveness failing → restart; startup gates the other two.

★ Putting it all together

The big idea

TaskFlow's Postgres stores its data on a PVC that the standard (or gp3) StorageClass provisioned, so deleting the pod loses nothing. The API declares CPU requests, which lets Metrics Server + the HPA keep average CPU at 50% by running 2–10 replicas. Startup, readiness and liveness probes make sure each of those replicas only gets traffic once it's ready and is restarted if it hangs — so autoscaling and rolling updates never send users to a broken pod.

Quick self-check

A PVC asks for 2Gi; the only matching PV (same class, RWO) is 5Gi. What happens and what does kubectl get pvc show as CAPACITY?

It binds (capacity ≥ request) and shows 5Gi — binding is 1:1 to the whole PV; the extra 3Gi can't be used by anyone else.

3 replicas run at 80% average CPU, target 50%, maxReplicas 10. How many replicas does the HPA want?

ceil(3 × 80 / 50) = ceil(4.8) = 5 (within max, and a 3→5 jump is allowed by the default scale-up policy).

kubectl get hpa shows cpu: <unknown>/50%. Give two likely causes.

Metrics Server isn't installed/ready (kubectl top pods fails), or the target pods have no resources.requests.cpu so utilization can't be computed.

The readiness probe fails on one pod. Is the container restarted? What changes?

No restart. The pod shows 0/1 READY and is removed from the Service's endpoints until it passes again. Only a liveness (or startup) failure restarts the container.

Startup probe: periodSeconds: 10, failureThreshold: 30. What's the maximum boot time allowed?

30 × 10 s = 300 s (5 min). Liveness and readiness don't run until it succeeds.

Why does the Postgres Deployment use strategy: Recreate, and why WaitForFirstConsumer on EKS?

RWO volume can attach to one node: RollingUpdate would start a second pod that can't mount it (Multi-Attach error). WFFC delays EBS creation until the pod is scheduled, so the disk is created in the same AZ as the node.

Why is it a bad idea for the API's liveness probe to query Postgres?

A DB blip makes every API pod fail liveness at once → mass restarts (restart storm) and CrashLoopBackOff, even though restarting the API can't fix the DB. Liveness should check only the process itself.
