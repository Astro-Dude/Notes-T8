1 Volumes: emptyDir, hostPath & friends

The problem

The API keeps a warm cache in /tmp. Then its container gets OOM-killed and restarted:

$ kubectl exec taskflow-api-5d7f9c8b6-4kq2x -n taskflow -- sh -c 'echo warm > /tmp/cache.txt'
   # … the container is OOMKilled and restarted: RESTARTS 0 → 1 …
$ kubectl exec taskflow-api-5d7f9c8b6-4kq2x -n taskflow -- cat /tmp/cache.txt
cat: can't open '/tmp/cache.txt': No such file or directory

Same pod name, but a restart in Kubernetes is a brand-new container with a fresh writable layer (Session 6). There's a second problem too: a log-shipper sidecar in the same pod can't read the API's log files, because each container has its own filesystem.

The idea

A volume is a directory that belongs to the pod, not to a container. You declare it once in spec.volumes and mount it into each container that needs it with volumeMounts. How long the data lives depends on the volume type.

 Pod emptydir-demo
 ┌─────────────────────────────────────────────────────┐
 │  container writer            container reader       │
 │   mounts /cache ──┐       ┌── mounts /cache (ro)    │
 │                   ▼       ▼                         │
 │            volume "cache" (emptyDir)                │ ← created when the pod lands on a node,
 └─────────────────────────────────────────────────────┘   deleted when the pod is removed

 lifetime:  container layer  <  emptyDir (pod)  <  hostPath (node)  <  PVC → PV (independent)
Think of it like this

A restaurant kitchen. Each cook (container) has a personal whiteboard (the writable layer) that's wiped when the cook is replaced. A station (pod) has a shared tray (emptyDir) that every cook at the station can use, and it goes when the station closes. A shelf bolted into one building (hostPath) is useless if you move to another branch. For things that must last there's the walk-in freezer (a PersistentVolume, §2). The kitchen comes back in every section on this page.

See it: two containers sharing a folder

emptydir-demo.yaml
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
  namespace: taskflow
spec:
  containers:
    - name: writer
      image: busybox:1.36
      command: ["sh", "-c", "while true; do date >> /cache/heartbeat.log; sleep 5; done"]
      volumeMounts:
        - name: cache                  # must match a name under spec.volumes
          mountPath: /cache            # where it appears inside THIS container
    - name: reader
      image: busybox:1.36
      command: ["sh", "-c", "until [ -f /cache/heartbeat.log ]; do sleep 1; done; tail -f /cache/heartbeat.log"]
      volumeMounts:
        - name: cache
          mountPath: /cache
          readOnly: true               # reader can't modify the file
  volumes:
    - name: cache
      emptyDir:
        sizeLimit: 100Mi               # the pod is evicted if it writes more than this
$ kubectl apply -f emptydir-demo.yaml
pod/emptydir-demo created
$ kubectl get pod emptydir-demo -n taskflow
NAME            READY   STATUS    RESTARTS   AGE
emptydir-demo   2/2     Running   0          12s
$ kubectl logs emptydir-demo -n taskflow -c reader --tail=3
Fri Oct  9 05:41:02 UTC 2026
Fri Oct  9 05:41:07 UTC 2026
Fri Oct  9 05:41:12 UTC 2026
$ kubectl delete pod emptydir-demo -n taskflow     # heartbeat.log is gone for good
pod "emptydir-demo" deleted

The reader prints lines the writer wrote, so the two containers really share /cache. The volume's name is the link between spec.volumes and each volumeMounts entry, and each container may mount it at a different mountPath. On the node it lives under /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~empty-dir/cache.

What it does not do: survive the pod. A container restart keeps the emptyDir, but deleting the pod (or evicting or rescheduling it) deletes the directory.

Build it up: hostPath, and the full list

pod.spec.volumes (snippet: for node agents only)
volumes:
  - name: varlog
    hostPath:
      path: /var/log           # a directory on the NODE, not in the image
      type: Directory          # must already exist; DirectoryOrCreate / File / FileOrCreate / Socket also valid

hostPath hands the pod a real directory on whichever node it runs on. That's right for a log collector reading /var/log, and wrong for Postgres. On a 3-node cluster the pod gets rescheduled to another node and finds an empty directory, while its data sits on the old node. It's also a security risk, because it can mount /.

Volume typeLifetimeUse forWatch out
emptyDirPod (survives container restarts)Scratch space, caches, sharing files between containersmedium: Memory = tmpfs, which counts toward the memory limit
hostPathNodeNode agents only (log collectors, node-exporter reading /proc)Different data on each node; security risk. Never for app data.
configMap / secretThe ConfigMap/Secret objectConfig files, certs (Session 12)Read-only; with subPath, updates aren't propagated
persistentVolumeClaimIndependent of pods, until the PVC is deletedDatabases, uploads: anything that must survive§2–§3
nfs, csi, projected, downwardAPIVariesNetwork shares, cloud disks, combined sources, pod metadata as filesUsually used through PVs, not directly
Exam trap

"An emptyDir is wiped every time the container restarts." ✗ It belongs to the pod, so it survives container restarts. Only removing the pod deletes it. (The container's own filesystem is the thing that's wiped.)

"hostPath is fine for database data." ✗ Only on a single-node cluster, and only by luck. Use a PVC.

Remember

Declare in spec.volumes, mount with volumeMounts, linked by name.
container layer < emptyDir (pod) < hostPath (node) < PVC (independent).

Mastery check
Q1. Predict: in emptydir-demo, the writer container crashes and is restarted. Is heartbeat.log still there?

Yes. The emptyDir belongs to the pod, which still exists, so the file keeps growing after the restart. It's only lost when the pod itself is deleted or evicted.

Q2. Spot the bug: a container mounts name: cache-vol, but spec.volumes lists name: cache.

The pod is rejected (spec.containers[0].volumeMounts[0].name: Not found: "cache-vol"). Mounts refer to volumes by name, and the names must match exactly.

Q3. A pod with limits.memory: 256Mi writes 300 MiB into an emptyDir with medium: Memory. What happens?

It gets OOM-killed or evicted. A memory-backed emptyDir is tmpfs, and its pages count toward the container's memory limit.

Q4. Fill in: a volume is declared at the ________ level and mounted by each ________; an emptyDir lives as long as the ________.

Pod · container · pod.

2 PersistentVolume & PersistentVolumeClaim

The problem

Postgres from Session 12 keeps its data inside the container. Watch what one pod deletion does:

$ kubectl exec deploy/taskflow-db -n taskflow -- psql -U taskflow -tc "SELECT count(*) FROM tasks;"
    42
$ kubectl delete pod -l app=taskflow-db -n taskflow      # a node drain or eviction does the same
pod "taskflow-db-7f6d8c9b5-l4vzt" deleted
$ kubectl exec deploy/taskflow-db -n taskflow -- psql -U taskflow -tc "SELECT count(*) FROM tasks;"
ERROR:  relation "tasks" does not exist
LINE 1: SELECT count(*) FROM tasks;
                             ^

All 42 tasks are gone. You need storage that outlives any pod. And because the real disk is different on every cluster (an EBS volume on EKS, an NFS share on-prem, a folder on minikube), the app's YAML shouldn't have to say which.

The idea

Kubernetes splits storage into two objects. A PersistentVolume (PV) is a real piece of storage. It's cluster-scoped and created by an admin (static) or a provisioner (dynamic, §3). A PersistentVolumeClaim (PVC) is a namespaced request: size + access mode + StorageClass. The control plane binds a claim to one PV that has the same storageClassName, the requested access mode and enough capacity. Binding is 1:1 and exclusive. The pod only ever names the claim.

 developer writes                                admin (or a provisioner) supplies
 PVC pg-manual-claim   (namespace taskflow)      PV taskflow-pv-manual   (cluster-scoped)
   2Gi · RWO · class manual   ─── binds 1:1 ───▶   5Gi · RWO · class manual · Retain
         ▲                                              │
 Pod: volumes[].persistentVolumeClaim.claimName         ▼ backed by a real disk (here: hostPath /data/taskflow-pg)
Think of it like this

The station doesn't build its own freezer. It hands in an order slip (the PVC: "5 GB of freezer space, one station"). Management assigns a freezer unit (the PV) that fits, and that unit is now reserved for that slip only, even if it's bigger than asked. Cooks come and go, and the freezer and its contents stay.

See it: an admin-made PV, then a claim

pv-manual.yaml
apiVersion: v1
kind: PersistentVolume                 # cluster-scoped: no namespace
metadata:
  name: taskflow-pv-manual
spec:
  capacity:
    storage: 5Gi                       # size this PV offers
  volumeMode: Filesystem               # default; "Block" = raw device
  accessModes:
    - ReadWriteOnce                    # RWO: mountable read-write by one node
  persistentVolumeReclaimPolicy: Retain  # keep data when the claim is deleted
  storageClassName: manual             # a PVC must ask for the same class to bind
  hostPath:
    path: /data/taskflow-pg            # minikube persists /data across restarts
pvc-manual.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pg-manual-claim
  namespace: taskflow                  # pods can only use PVCs in their own namespace
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual             # same class as the PV → static binding
  resources:
    requests:
      storage: 2Gi                     # "at least 2Gi"
$ kubectl apply -f pv-manual.yaml && kubectl get pv
persistentvolume/taskflow-pv-manual created
NAME                 CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
taskflow-pv-manual   5Gi        RWO            Retain           Available           manual         <unset>                          6s
$ kubectl apply -f pvc-manual.yaml && kubectl get pvc -n taskflow
persistentvolumeclaim/pg-manual-claim created
NAME              STATUS   VOLUME               CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
pg-manual-claim   Bound    taskflow-pv-manual   5Gi        RWO            manual         <unset>                 4s

The PV went from Available to Bound. Notice CAPACITY: the claim asked for 2Gi and got 5Gi, because it binds a whole PV. The other 3Gi can't go to anyone else. (VOLUMEATTRIBUTESCLASS is a newer column for tuning IOPS, and <unset> is normal.)

What it does not do: a bound PVC holds space but mounts nothing until a pod names it in volumes[].persistentVolumeClaim.claimName (§3 does that for Postgres).

FieldMeaningGotcha
capacity.storageSize offered (Mi, Gi, Ti).Not enforced for hostPath. It's just a label for matching.

persistentVolumeReclaimPolicyWhat happens to the PV when its PVC is deleted.Manual PVs default to Retain, dynamic ones to Delete.

Build it up: access modes and reclaim policies

ModeShortMeaningTypical backends
ReadWriteOnceRWORead-write by one node (several pods on that node can share it)AWS EBS, GCE PD, Azure Disk, hostPath
ReadOnlyManyROXRead-only by many nodesNFS, pre-filled disks
ReadWriteManyRWXRead-write by many nodes at onceNFS, AWS EFS, Azure Files, CephFS

Now delete the claim and watch Retain do its job:

$ kubectl delete pvc pg-manual-claim -n taskflow
persistentvolumeclaim "pg-manual-claim" deleted
$ kubectl get pv taskflow-pv-manual
NAME                 CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM                      STORAGECLASS   VOLUMEATTRIBUTESCLASS   REASON   AGE
taskflow-pv-manual   5Gi        RWO            Retain           Released   taskflow/pg-manual-claim   manual         <unset>                          9m
$ kubectl patch pv taskflow-pv-manual -p '{"spec":{"claimRef":null}}'   # → Available again, data still on disk
persistentvolume/taskflow-pv-manual patched

Released means the data is kept but the PV still remembers its old claim, so no new claim can bind it until an admin clears claimRef. The three policies: Retain keeps the PV and data (production databases), Delete deletes the PV and the real disk (dev/test, the dynamic default), and Recycle is deprecated. PV phases run Available → Bound → Released (or Failed). PVC phases are Pending → Bound (or Lost if its PV vanished).

Exam trap

"ReadWriteOnce means one pod." ✗ It means one node. Two pods on the same node can both mount it. One pod in the whole cluster is ReadWriteOncePod.

"A PVC with no storageClassName binds my manual PV." ✗ On minikube it gets the default class standard, so a new PV is provisioned and yours stays Available. Name the same class on both (or "").

"PVs live in a namespace." ✗ PVs (and StorageClasses) are cluster-scoped. Only PVCs are namespaced.

Remember

PV = the disk (cluster-wide) · PVC = the request (namespaced) · binding is 1:1 by class + mode + size.
Retain keeps data · Delete destroys the disk.

Mastery check
Q1. A PVC requests ReadWriteMany, class manual, 2Gi. The only manual PV is 5Gi RWO. Predict the PVC's STATUS and how you'd find out why.

Pending, because the PV doesn't offer RWX, so no PV matches. kubectl describe pvc shows the binder's event. Fix: request RWO, or provide an RWX-capable PV (NFS, EFS).

Q2. Reclaim policy Retain. You delete the PVC, then create a new identical PVC. Does it get the old data?

Not automatically. The PV is Released and still holds a claimRef to the old claim, so the new PVC can't bind it (it stays Pending, or a default class provisions a fresh empty PV). Clear claimRef to make the PV Available, and then it binds with the data intact.

Q3. kubectl delete pvc taskflow-db-data hangs, and the PVC shows Terminating. Why?

A pod still uses it. The kubernetes.io/pvc-protection finalizer blocks deletion until no pod mounts the claim. Delete or scale down the pod first.

Q4. Fill in: a PV is ________-scoped, a PVC is ________-scoped, and a pod refers to ________ only.

Cluster · namespace · the PVC (by claimName).

3 StorageClass & dynamic provisioning

The problem

With static PVs, every claim waits for a human. A team files a PVC for 20Gi at 2 a.m. and it sits Pending until an admin wakes up, creates an EBS volume in the right availability zone, and writes a PV for it. Multiply that by every team, every environment and every database.

The idea

A StorageClass (SC) is a cluster-scoped "type of storage" plus the provisioner (a CSI driver) that can create disks of that type. When a PVC names a class, the provisioner creates a disk and a matching PV (named pvc-<uid>) on demand and binds it. That's dynamic provisioning. One class can be the default, used by PVCs that don't name one.

  Pod ──volumes.claimName──▶ PVC ──────binds 1:1──────▶ PV ──backed by──▶ real disk
                             "5Gi, RWO,                 "pvc-8f6c…, 5Gi"   (EBS vol / hostPath dir / NFS)
                              class: gp3"                    ▲
                                 │                            │ creates (dynamic)
                                 └──storageClassName──▶ StorageClass ──provisioner──▶ CSI driver
                                                         "gp3"            ebs.csi.aws.com
Think of it like this

Instead of management pre-buying freezers, the kitchen has a supplier catalog (StorageClass): "gp3 freezer, delivered by AWS". Hand in an order slip that names the catalog entry, and a brand-new freezer shows up, sized exactly to the order.

See it: the class minikube gives you

$ kubectl get storageclass
NAME                 PROVISIONER                RECLAIMPOLICY   VOLUMEBINDINGMODE   ALLOWVOLUMEEXPANSION   AGE
standard (default)   k8s.io/minikube-hostpath   Delete          Immediate           false                  3d

Left to right: standard is the default class, its provisioner makes host folders, deleting a claim deletes the volume, volumes are created as soon as the PVC exists, and they can't grow. kind's standard uses rancher.io/local-path with WaitForFirstConsumer.

What it does not do: a StorageClass creates nothing on its own. No PVC, no disk.

Build it up

A real class: gp3 on EKS

storageclass-gp3.yaml (EKS)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # PVCs without a class get this one
provisioner: ebs.csi.aws.com           # AWS EBS CSI driver creates the volumes
parameters:                            # passed to the provisioner as-is (driver-specific strings)
  type: gp3                            # EBS volume type
  csi.storage.k8s.io/fstype: ext4
  encrypted: "true"
reclaimPolicy: Delete                  # default; Retain for prod DBs
volumeBindingMode: WaitForFirstConsumer  # create the disk only after the pod is scheduled
allowVolumeExpansion: true             # lets you grow a PVC later
FieldMeaning
provisionerWhich driver makes the PV: ebs.csi.aws.com, pd.csi.storage.gke.io, disk.csi.azure.com, k8s.io/minikube-hostpath.
parametersOpaque key/values for that driver (disk type, IOPS, encryption). Values must be strings.
reclaimPolicyCopied into every PV this class creates. Default Delete.
volumeBindingModeImmediate (default) provisions as soon as the PVC exists. WaitForFirstConsumer waits until a pod using it is scheduled, then creates the disk in that pod's zone. EBS volumes live in one AZ, so Immediate could put the disk in ap-south-1a and the pod in ap-south-1b, and it could never attach.
allowVolumeExpansionIf true, raise the PVC's requests.storage to grow it. Shrinking is never allowed.

TaskFlow: Postgres on a dynamically provisioned PVC

The password comes from Session 12's Secret taskflow-db-secret (keys POSTGRES_PASSWORD and DATABASE_URL).

k8s/postgres.yaml
# --- 1. The claim: "give me 5Gi of the standard class" ---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: taskflow-db-data
  namespace: taskflow
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: standard           # minikube default; gp3 on EKS; omit = cluster default
  resources:
    requests: { storage: 5Gi }
---
# --- 2. Postgres itself (probes are added in §6; Session 15 makes it a StatefulSet) ---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-db
  namespace: taskflow
spec:
  replicas: 1                          # one writer; 2 replicas would NOT replicate data
  strategy:
    type: Recreate                     # stop the old pod before starting the new → RWO disk is free
  selector:
    matchLabels: { app: taskflow-db }
  template:
    metadata:
      labels: { app: taskflow-db }     # the Service below selects this
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports:
            - { name: postgres, containerPort: 5432 }
          env:
            - { name: POSTGRES_DB,   value: taskflow }
            - { name: POSTGRES_USER, value: taskflow }
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: taskflow-db-secret
                  key: POSTGRES_PASSWORD
            - name: PGDATA                               # a sub-directory of the mount: a fresh ext4
              value: /var/lib/postgresql/data/pgdata     # disk has lost+found, which initdb rejects
          resources:
            requests: { cpu: 250m, memory: 256Mi }
            limits:   { memory: 512Mi }
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data        # postgres:16's data directory
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: taskflow-db-data  # ← the PVC above, same namespace
---
# --- 3. Stable name "taskflow-db" for the API's DATABASE_URL ---
apiVersion: v1
kind: Service
metadata:
  name: taskflow-db
  namespace: taskflow
spec:
  selector: { app: taskflow-db }
  ports:
    - { name: postgres, port: 5432, targetPort: postgres }

Exam trap

"My PVC is Pending, so something is broken." ✗ With WaitForFirstConsumer, Pending plus the event waiting for first consumer to be created before binding is normal until a pod uses it.

"Dynamically provisioned PVs are kept when the claim goes, like manual ones." ✗ They inherit the class's reclaimPolicy, which defaults to Delete, so deleting the PVC deletes the real disk. Use a Retain class for data you can't lose.

Remember

PVC names a StorageClass → provisioner creates a pvc-<uid> PV → bound automatically.
Multi-AZ cloud → WaitForFirstConsumer · single-writer DB → Recreate.

Mastery check
Q1. Someone switches taskflow-db back to the default RollingUpdate on EKS and changes the image tag. Predict what kubectl get pods shows.

The new pod sticks in ContainerCreating with Multi-Attach error for volume "pvc-…": the RWO EBS disk is still attached to the old pod's node, and RollingUpdate won't stop the old pod until the new one is ready. That's a deadlock. Recreate stops the old pod first.

Q2. "Let's run Postgres with replicas: 2 for high availability." What actually happens with this RWO PVC?

At best, both pods land on one node and two Postgres processes write the same files, which corrupts the data. Otherwise the second pod can't attach the disk. Replicas of a Deployment don't replicate data. Real HA needs a StatefulSet with a volume per pod and Postgres replication (Session 15) or a managed DB.

Q3. Predict: on minikube you run kubectl patch pvc taskflow-db-data -n taskflow -p '{"spec":{"resources":{"requests":{"storage":"10Gi"}}}}'. Same command on EKS with the gp3 class?

minikube: Error from server (Forbidden): … only dynamically provisioned pvc can be resized and the storageclass that provisions the pvc must support resize, because standard shows ALLOWVOLUMEEXPANSION false. EKS: it succeeds, since gp3 has allowVolumeExpansion: true, and the CSI driver grows the EBS volume and filesystem. Shrinking is never allowed.

4 Metrics Server & kubectl top

The problem

You're about to autoscale on CPU, so first ask the cluster how busy things are:

$ kubectl top nodes
error: Metrics API not available
$ kubectl get hpa -n taskflow                # if an HPA already existed
NAME           REFERENCE                 TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
taskflow-api   Deployment/taskflow-api   cpu: <unknown>/50%   2         10        2          3m

The kubelets measure CPU and memory, but nothing collects those numbers into an API that kubectl and the autoscaler can read.

The idea

Metrics Server is a cluster add-on (a Deployment in kube-system). It scrapes every kubelet's resource metrics about every 15 s and serves the latest values through the metrics.k8s.io API. kubectl top and the HPA both read that API.

kubelet (cAdvisor) ──/metrics/resource──▶ metrics-server ──▶ metrics.k8s.io API ──▶ kubectl top
  on every node        scraped every 15s     latest values      (API aggregation)    HPA controller
                                             in memory only
Think of it like this

The floor manager walks the kitchen with a clipboard every 15 seconds, noting how busy each cook is right now. Last week's numbers aren't on the clipboard. For history and charts you need a proper logbook (Prometheus, Session 22).

See it: switch it on, then read the numbers

$ minikube addons enable metrics-server

5 Horizontal Pod Autoscaler (HPA)

The problem

Monday, 9 a.m.: the whole batch opens TaskFlow before a deadline. Two API pods sit at 190% of their CPU request, and /tasks takes 4 s. At 3 a.m. the same two pods idle at 4%. Hard-code replicas: 8 and you pay for the peak all night. Hard-code 2 and Monday breaks. Nobody wants to run kubectl scale by hand at 9 a.m.

The idea

The HorizontalPodAutoscaler is a control loop in kube-controller-manager. Every 15 s it reads the pods' metrics, computes how many replicas would bring the average back to your target, clamps that to [minReplicas, maxReplicas], and writes it into the Deployment's spec.replicas. CPU utilization is a percentage of resources.requests.cpu, so no request means no percentage.

 metrics-server ──avg CPU = 190% of request──▶ HPA controller (every 15 s)
                                                │ desired = ceil(2 × 190 / 50) = 8
                                                │ clamp to [2, 10], apply behavior limits → 6
                                                ▼
                         Deployment taskflow-api  spec.replicas: 2 → 6 ──▶ ReplicaSet ──▶ +4 pods
Think of it like this

The floor manager reads the clipboard (§4). If the average cook is busier than 50%, she calls in more cooks. When it's quiet she sends some home, but never below 2 cooks and never above 10. She also waits 5 minutes of quiet before sending anyone home, so a short lull doesn't empty the kitchen.

See it: one command

$ kubectl autoscale deployment taskflow-api -n taskflow --cpu=50% --min=2 --max=10
horizontalpodautoscaler.autoscaling/taskflow-api autoscaled
$ kubectl get hpa -n taskflow
NAME           REFERENCE                 TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
taskflow-api   Deployment/taskflow-api   cpu: 4%/50%   2         10        2          40s
TokenMeaning
autoscale deployment taskflow-apiCreate an HPA (named after the Deployment) that targets it
--cpu=50%Target average CPU = 50% of each pod's request (older kubectl: --cpu-percent=50)
--min=2 --max=10Never fewer than 2 or more than 10 replicas
TARGETS cpu: 4%/50%Current average / target

What it does not do: add nodes, or make one pod bigger. And if the pods have no CPU request, TARGETS stays <unknown> forever.

Build it up

The declarative version, with a scaling behavior

Delete the imperative HPA first (kubectl delete hpa taskflow-api -n taskflow); otherwise you just update it. The Deployment's request that the percentages are measured against (full file in §7):

          resources:
            requests:
              cpu: 100m          # 50% target ⇒ the HPA aims for 50m average per pod
            limits:
              cpu: 500m          # a pod can burst to 500% of its request
k8s/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: taskflow-api
  namespace: taskflow
spec:
  scaleTargetRef:                      # WHAT to scale
    apiVersion: apps/v1
    kind: Deployment
    name: taskflow-api
  minReplicas: 2                       # floor: keep 2 for availability
  maxReplicas: 10                      # ceiling: cost / quota guard
  metrics:
    - type: Resource                   # CPU/memory from metrics-server
      resource:
        name: cpu
        target:
          type: Utilization            # % of requests.cpu
          averageUtilization: 50       # keep the average pod at 50%
  behavior:                            # optional: how fast to scale (scaleUp = the defaults)
    scaleUp:
      stabilizationWindowSeconds: 0    # react immediately
      selectPolicy: Max                # pick whichever policy allows MORE change
      policies:
        - type: Percent
          value: 100                   # at most double…
          periodSeconds: 15
        - type: Pods
          value: 4                     # …or +4 pods, per 15 s
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300  # use the highest recommendation of the last 5 min
      policies:
        - type: Percent
          value: 50                    # remove at most half the pods per minute
          periodSeconds: 60
FieldMeaning
autoscaling/v2The current API (several metrics, behavior). autoscaling/v1 only has targetCPUUtilizationPercentage.
scaleTargetRefThe workload whose replicas the HPA controls, in the same namespace. Anything with a scale subresource (Deployment, StatefulSet), not a DaemonSet.
metrics[].typeResource (pod CPU/memory), ContainerResource, Pods (custom, e.g. requests/s), Object, External (e.g. SQS queue length). Non-Resource types need an adapter (Prometheus Adapter, KEDA).
target.typeUtilization (% of request) · AverageValue (absolute per pod, e.g. 200Mi) · Value (a total, for Object/External).
behaviorstabilizationWindowSeconds = look-back window (scale-down uses the max recommendation in it). policies = rate limits per periodSeconds. selectPolicy: Max|Min|Disabled.

Exam trap

"Leave replicas: 2 in deployment.yaml; the HPA will cope." ✗ Every kubectl apply resets the count to 2 and fights the HPA. Remove the field once an HPA owns the Deployment.

"The HPA adds nodes when pods don't fit." ✗ It's horizontal: it only changes replica counts. Bigger pods is the VPA add-on (vertical). More nodes is the Cluster Autoscaler or Karpenter. Without those, extra pods sit Pending (Session 14).

"Scale the Node API on memory." ✗ V8's heap usually stays high after the load is gone, so it scales up and rarely back down. Prefer CPU or requests/second.

desired = ceil(current × actual ÷ target), clamped to [min, max], limited by behavior.

Mastery check
Q1. 3 replicas at 80% average CPU, target 50%, max 10. How many replicas does the HPA want?

ceil(3 × 80 / 50) = ceil(4.8) = 5. That's within max, and +2 is allowed by the default scale-up policy.

Q2. 4 replicas at 53%, target 50%. Predict the change.

None. The ratio is 53/50 = 1.06, within the 0.1 tolerance, so the HPA leaves it at 4 (even though ceil(4 × 1.06) = 5).

Q3. kubectl get hpa shows cpu: <unknown>/50% and kubectl top pods works fine. What's the likely cause, and where is the proof?

A container in the target pods has no resources.requests.cpu, so utilization can't be computed. kubectl describe hpa shows FailedGetResourceMetric … missing request for cpu.

Q4. The load stops. Why does it take over 5 minutes for 8 pods to drop to 2, while scaling up took under a minute?

The scale-down stabilizationWindowSeconds: 300 uses the highest recommendation of the last 5 minutes (to avoid flapping), then the policy removes at most 50% per minute: 8 → 4 → 2. Scale-up has a 0 s window and allows doubling every 15 s.

6 Readiness & liveness probes

The problem

Two failures Kubernetes can't see on its own. One: during every rollout, each new pod shows Running while Node is still connecting to Postgres, and the Ingress sends it traffic anyway, so users get a few seconds of 502s per pod. Two: a bug blocks the event loop. The process is alive, so Kubernetes is happy, but every request hangs:

$ kubectl get pods -n taskflow -l app=taskflow-api
NAME                           READY   STATUS    RESTARTS   AGE
taskflow-api-5d7f9c8b6-r7k2m   1/1     Running   0          3h          # "healthy", says Kubernetes
$ curl -m 5 -k https://taskflow.local/api/tasks
curl: (28) Operation timed out after 5001 milliseconds with 0 bytes received   # says the user

Without probes, the only health signal Kubernetes has is "the process exists".

The idea

A probe is a health check the kubelet runs against a container on a schedule. A readiness probe answers "can it take traffic right now?" When it fails, the pod is marked NotReady and removed from the Service's endpoints, but it is not restarted. A liveness probe answers "is it stuck?" When it fails, the kubelet kills and restarts the container.

                     kubelet probes the container every periodSeconds
 readiness ✗ × failureThreshold ──▶ READY 0/1 ──▶ removed from EndpointSlice ──▶ no traffic (no restart)
 readiness ✓                     ──▶ READY 1/1 ──▶ added back
 liveness  ✗ × failureThreshold ──▶ container killed ──▶ restarted ──▶ RESTARTS +1
Think of it like this

Readiness: "is this cook ready to take tickets?" A cook still setting up their station gets no tickets, but nobody fires them. Liveness: "has this cook frozen?" A cook standing motionless for 30 seconds is replaced with a fresh one.

See it: a readiness probe

          readinessProbe:
            httpGet:
              path: /health          # GET http://<pod-ip>:3000/health
              port: http             # the container port NAMED http (3000)
            periodSeconds: 5         # every 5 s; success = HTTP 200–399
$ kubectl get pods -n taskflow -l app=taskflow-api -w
NAME                           READY   STATUS              RESTARTS   AGE
taskflow-api-5d7f9c8b6-r7k2m   0/1     ContainerCreating   0          1s
taskflow-api-5d7f9c8b6-r7k2m   0/1     Running             0          2s     ← running, not ready: no traffic yet
taskflow-api-5d7f9c8b6-r7k2m   1/1     Running             0          6s     ← /health returned 200

READY 0/1 while Running is the probe holding traffic back. Only at 1/1 does the pod's IP go into the EndpointSlice, and that's also what a rolling update waits for before removing an old pod. That solves failure one.

What it does not do: restart anything. A pod that fails readiness forever just sits at 0/1 forever.

Build it up

Add liveness (failure two)

          livenessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 10
            timeoutSeconds: 2        # a hung event loop never answers → counts as a failure
            failureThreshold: 3      # 3 misses × 10 s ≈ 30 s stuck → restart
$ kubectl describe pod taskflow-api-5d7f9c8b6-r7k2m -n taskflow | sed -n '/Events:/,$p'
Events:
  Type     Reason     Age                From     Message
  ----     ------     ----               ----     -------
  Warning  Unhealthy  41s (x6 over 56s)  kubelet  Readiness probe failed: Get "http://10.244.0.21:3000/health": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
  Warning  Unhealthy  40s (x3 over 60s)  kubelet  Liveness probe failed: Get "http://10.244.0.21:3000/health": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
  Normal   Killing    40s                kubelet  Container api failed liveness probe, will be restarted

Read the sequence. Readiness failed first (period 5 s), so the pod left the Service. Liveness failed three times, and the kubelet killed and restarted the container. The stuck pod now heals itself instead of hanging for hours.

Exam trap

"A failing readiness probe restarts the container." ✗ Readiness only controls traffic (endpoints). Only liveness (and startup) failures restart.

"Liveness should check the database too, to be thorough." ✗ If Postgres blips for 20 s, every API pod fails liveness at once and restarts (a restart storm), and restarting the API can't fix the DB. Liveness checks only the process itself.

"Probe the Service port, 80." ✗ The kubelet probes the container directly: port 3000, or the name http.

Remember

Readiness → traffic (0/1, out of endpoints, no restart).
Liveness → restarts (RESTARTS +1). Keep it cheap: no DB calls.

Mastery check
Q1. A pod shows 0/1 Running with RESTARTS 0 for ten minutes. Which probe is failing, and what does kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api show for it?

Readiness (liveness would have restarted it). The pod's IP is missing from the ready endpoints, so the Service sends it nothing. describe pod shows Readiness probe failed: ….

Q2. Spot the bug: readinessProbe: httpGet: {path: /healthz, port: http}, and the app serves /health.

Every probe gets 404, which counts as a failure, so the pod never becomes ready and the rollout stalls. The event says Readiness probe failed: HTTP probe failed with statuscode: 404. Fix the path.

Q3. Professor's claim: "With a liveness probe you don't need a readiness probe." True or false?

False. Liveness never removes a pod from traffic. It only restarts after it's stuck. A booting or temporarily overloaded pod would still receive requests and return errors. You want both, doing different jobs.

7 Startup probes & probe timing

The problem

Version 1.2.0 runs database migrations on boot. On a busy node, a cold start now takes about 90 s, but the liveness probe from §6 starts checking straight away:

$ kubectl get pods -n taskflow -l app=taskflow-api -w
NAME                           READY   STATUS             RESTARTS      AGE
taskflow-api-6c9d7b5f8-wq4zn   0/1     Running            0             25s
taskflow-api-6c9d7b5f8-wq4zn   0/1     Running            1 (1s ago)    32s
taskflow-api-6c9d7b5f8-wq4zn   0/1     CrashLoopBackOff   1 (31s ago)   63s
taskflow-api-6c9d7b5f8-wq4zn   0/1     Running            2 (1s ago)    74s
$ kubectl describe pod taskflow-api-6c9d7b5f8-wq4zn -n taskflow | tail -2
  Warning  Unhealthy  13s (x6 over 63s)  kubelet  Liveness probe failed: Get "http://10.244.0.27:3000/health": dial tcp 10.244.0.27:3000: connect: connection refused
  Normal   Killing    13s (x2 over 43s)  kubelet  Container api failed liveness probe, will be restarted

Liveness kills it after about 30 s, every time, so it never finishes booting. No code is broken. Adding initialDelaySeconds: 90 to liveness would "fix" it, but then a pod that really hangs in its first 90 s is never caught, and the day a boot takes 100 s the loop starts again.

The idea

A startup probe runs first, and only at startup. While it hasn't succeeded yet, liveness and readiness are switched off. Once it passes, it never runs again, and the other two take over. If it fails failureThreshold times in a row, the container is killed and restarted. Its boot budget is failureThreshold × periodSeconds, and every probe's timing follows the same rule.

 t=0          startup probe every 2 s (up to 30 tries = 60 s budget)        first ✓ at t≈40 s
 ├────────────────────────────────────────────────────────────────────────┤
 │  liveness + readiness are OFF                                           │ then: readiness every 5 s,
                                                                             liveness every 10 s, forever
Think of it like this

A new cook gets up to 60 seconds to set up their station, and the manager checks every 2 seconds whether they're done. Nobody asks "are you frozen?" during set-up. If they're still not ready after 60 seconds, they're replaced.

See it: the startup probe

          startupProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 2
            failureThreshold: 30     # 30 × 2 s = 60 s to boot; liveness waits until this passes

Same endpoint as liveness, with a generous threshold. A fast boot passes at the first success (say 4 s), so it costs almost nothing. A slow boot gets the full 60 s.

What it does not do: run after startup. If the app hangs at minute 30, that's liveness's job.

Build it up: the full TaskFlow API Deployment

k8s/deployment.yaml

            successThreshold: 1        # 1 success → back in

            httpGet: { path: /health, port: http }
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3        # 3 × 10 s = 30 s hung → restart
Field / lineDefaultMeaning, and why it's set here
initialDelaySeconds0Wait after container start before the first probe. Not needed once a startup probe exists.
periodSeconds10How often to probe.
timeoutSeconds1A slower answer counts as a failure. Raised to 2, because 1 s is tight for a busy Node event loop and spurious timeouts cause restarts.
failureThreshold3Consecutive failures before acting (restart / NotReady).
successThreshold1Consecutive successes to count as passing again. Must be 1 for liveness and startup.
maxUnavailable: 0 + readiness—Zero-downtime rollouts: an old pod goes only once a new one passes readiness.
Same /health ×3—TaskFlow has one health endpoint. A bigger app adds /ready (checks warm caches/deps) and keeps /health process-only.
Worked example: timing math (failureThreshold × periodSeconds)
  • Boot budget: startup 30 × 2 s = 60 s. A pod still failing at 60 s is restarted.
  • Event loop blocks at t = 0: readiness fails at ~5, 10 and 15 s, so the pod leaves the Service at ≈15 s. Liveness fails at ~10, 20 and 30 s, so the restart comes at ≈30 s (each attempt can add the 2 s timeout).
  • Between 15 s and 30 s the pod gets no traffic but isn't killed. If it recovers in that window (a long GC pause), no restart happens.

Exam trap

"A startup probe keeps running alongside liveness." ✗ It stops for good after its first success. Liveness and readiness only start then.

Mastery check
Q1. Startup probe: periodSeconds: 10, failureThreshold: 30. What's the maximum boot time allowed, and what runs during it?

30 × 10 s = 300 s (5 min). Only the startup probe runs. Liveness and readiness don't start until it succeeds.

Q2. Readiness: period 5 s, threshold 3. Liveness: period 10 s, threshold 3. The app freezes at t = 0 and recovers at t = 20 s. Predict what happens.

At ≈15 s readiness has failed 3 times, so the pod leaves the Service. Liveness has failed only twice (10 s, 20 s) when the app recovers, so there's no restart. Readiness passes again and the pod rejoins. Traffic was paused for about 5–10 s, with no restart.

Q3. Spot the bug: no startup probe, livenessProbe.initialDelaySeconds: 60, and the app sometimes needs 70 s to boot.

On a slow boot, liveness starts at 60 s, fails, and kills the container before it's up, and the same thing happens on every retry: CrashLoopBackOff. Replace the delay with a startup probe whose budget covers the worst boot (e.g. 30 × 5 s = 150 s).

★ Putting it all together

The big idea

TaskFlow's Postgres keeps its data on a PVC that the standard (or gp3) StorageClass provisioned, so deleting the pod loses nothing. The API declares CPU requests, which lets Metrics Server and the HPA hold average CPU near 50% with 2–10 replicas. Startup, readiness and liveness probes make sure each replica gets traffic only once it's ready and is restarted if it hangs. That's why autoscaling and rolling updates never send users to a pod that can't answer.

Final mastery check — combine everything
Q1. During a load spike the HPA scales taskflow-api from 2 to 8. Users see a burst of 502s while the new pods start. Which section's feature is missing, and why does it matter more with autoscaling?

A readiness probe (§6). Without one, a new pod counts as ready the moment its process starts, so it joins the Service while Node is still booting. Autoscaling adds pods exactly when traffic is highest, so the unready pods get hit hard. Add readiness (and a startup probe for slow boots).

Q2. The HPA's TARGETS show <unknown>/50%, and kubectl top pods also fails. Then, after fixing that, TARGETS is still <unknown> for the API but fine for another app. Two causes, in order?

First, Metrics Server isn't installed or ready (§4): enable it and check the metrics.k8s.io APIService. Second, the API's pods have no resources.requests.cpu (§5), so a percentage can't be computed. describe hpa shows missing request for cpu.

Q3. Postgres's liveness probe runs pg_isready with timeoutSeconds: 1. Under heavy load from 8 API replicas it times out, the DB container is restarted, and all API pods go 0/1. Explain the chain and two fixes.

More replicas (§5) → more DB load → slow pg_isready → liveness kills Postgres (§6) → the API's readiness fails while the DB restarts → no ready API endpoints. Fixes: make liveness gentler (a tcpSocket check, timeoutSeconds: 5, a higher failureThreshold), keep pg_isready for readiness only, and cap maxReplicas or add DB connection pooling.

Q4. The cluster's StorageClass is gp3 with WaitForFirstConsumer. You apply only the PVC part of k8s/postgres.yaml. Predict the PVC's STATUS, then what changes once the Deployment is applied.

Pending, with the event waiting for first consumer to be created before binding, which is normal. Once the Postgres pod is scheduled to a node in, say, ap-south-1b, the EBS CSI driver creates a 5Gi gp3 volume in that AZ, a pvc-… PV appears, the claim goes Bound, and the pod mounts it.

Q5. A teammate deletes and re-applies k8s/postgres.yaml to "reset the pod", and all tasks vanish. A second teammate deleted only the pod last week and lost nothing. Explain both.

Deleting the pod leaves the PVC, so the new pod mounts the same PV with the data intact (§3). Deleting the file also deletes the PVC, and with the class's reclaim policy Delete, the PV and the real disk are destroyed (§2). Keep the PVC in a separate file, or use Retain for production data.

Q6. A slow node makes the API take 80 s to boot. The pods have only a liveness probe (period 10 s, threshold 3), and the HPA keeps adding replicas that never become ready. What's happening, and what's the fix?

Liveness kills each new container at about 30 s, before it ever finishes booting (§7), so the pods crash-loop. The existing pods stay overloaded, so the HPA (§5) keeps asking for more pods, and those crash-loop too. Add a startup probe with a budget above 80 s (e.g. periodSeconds: 5, failureThreshold: 24 = 120 s) and a readiness probe.
