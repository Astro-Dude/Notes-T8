1 Your first script

The problem

Every TaskFlow deploy in Session 2 meant typing the same ten commands by hand, in order, at 2 a.m. Miss one (npm ci) and the service crash-loops. You want to write the steps down once and have the computer replay them exactly.

The idea

A shell script is a text file of commands that Bash runs top to bottom, exactly as if you'd typed them. Line 1 is the shebang, which tells the kernel which interpreter should read the file:

 ./hello.sh
     │  the kernel reads line 1:   #!/usr/bin/env bash
     ▼
 /usr/bin/env bash ./hello.sh       env finds bash on your PATH and hands it the file
     │
     ▼
 bash runs the lines top to bottom, in a NEW process (a child of your shell)
Think of it like this

A script is a recipe card for a robot cook (we'll keep this robot all session). It follows every line literally and never guesses what you meant. The shebang says which robot reads the card; chmod +x stamps it "approved to run".

See it

hello.sh
#!/usr/bin/env bash
# hello.sh - first script
echo "Hello from $(hostname), I am $(whoami)"
echo "Today is $(date +%A)"
$ ./hello.sh
bash: ./hello.sh: Permission denied
$ chmod +x hello.sh
$ ./hello.sh
Hello from web-01, I am shaurya
Today is Friday
TokenMeaning
#!/usr/bin/env bashShebang: run me with whichever bash is first on PATH (portable). #!/bin/bash hard-codes the path.
$(hostname)Command substitution: run hostname and paste its output into the line (section 2)
chmod +xAdd the execute bit (Session 2), needed once per file
./hello.sh"The file hello.sh in this directory". Plain hello.sh fails with command not found, because . isn't on PATH.

What ./hello.sh does not do: change your current shell. It runs in a child process, so any variable it sets or cd it does vanishes when it exits.

Build it up: three ways to run a file

Exam trap

"sh script.sh runs it with bash." ✗ On Ubuntu /bin/sh is dash, so bash features break, and the script may even carry on and exit 0: shtest.sh: 3: [[: not found. Use ./script.sh or bash script.sh.

"bash script.sh needs chmod +x." ✗ Only ./script.sh does. With bash script.sh, bash just reads the file as input.

Remember

Shebang + chmod +x + ./script.sh. Scripts run in a child; source runs in your shell.

Mastery check
Q1. A script does cd /opt/taskflow. You run ./go.sh and then pwd. Where are you? What if you'd run source go.sh?

With ./go.sh, still where you started: the cd ran in a child that has exited. With source, you end up in /opt/taskflow, because it ran in your shell.

Q2. hello.sh is in your current directory and has x. Why does typing hello.sh say command not found?

Bare names are looked up only in PATH, and . isn't on it (deliberately). ./hello.sh is an explicit path.

Q3. Fill in: ./script.sh runs in a ________ process; source script.sh runs in the ________ shell.

A new (child) process · the current shell. That is why only source can change your variables or directory.

2 Variables & quoting

The problem

$ APP = taskflow
APP: command not found
$ FILE="my notes.txt"; touch $FILE; ls -1
my
notes.txt

Two tiny lines, two surprises: a variable that became a command, and one file that became two. Both come from the same fact about the shell: it splits every line into words on spaces before it does anything else.

The idea

Assign with NAME=value, with no spaces (with spaces, the first word APP is taken as a command). Read the value with $NAME. Then quotes decide what happens to the value:

APP=taskflow   FILE="my notes.txt"
echo "$APP-api"    → taskflow-api      "double": expand $…, keep the result as ONE word
echo '$APP-api'    → $APP-api          'single': nothing expands, everything literal
touch $FILE        → my  notes.txt     no quotes: expand, then SPLIT on spaces → 2 words, 2 files
touch "$FILE"      → my notes.txt      quoted: one word, one file
Think of it like this

A variable is a labelled jar. "$FILE" = hand over the contents in one piece. '$FILE' = read the label aloud, jar unopened. Plain $FILE = tip the jar out, and the robot splits the contents at every space.

See it

vars.sh
#!/usr/bin/env bash
APP="taskflow"                    # no spaces around =
PORT=3000
NOW=$(date +%H:%M)                # command substitution: output of a command
echo "1: $APP runs on $PORT"      # double quotes: variables expand
echo '2: $APP runs on $PORT'      # single quotes: everything literal
echo "3: ${APP}-api"              # braces mark where the name ends
echo "4: $APP_api"                # looks for a variable called APP_api (unset)
echo "5: started at $NOW"
echo "6: next port $((PORT + 1))"            # arithmetic expansion
echo "7: env is ${NODE_ENV:-development}"    # default if unset or empty
echo "8: length of APP = ${#APP}"
$ ./vars.sh
1: taskflow runs on 3000
2: $APP runs on $PORT
3: taskflow-api
4:
5: started at 10:30
6: next port 3001
7: env is development
8: length of APP = 8

Line 4 is the sneaky one: _ is a legal name character, so Bash looked up APP_api, found nothing and printed "" without an error; ${APP} fixes it. What an unset variable does not do: complain. It silently expands to "", which is how scripts end up running rm -rf /old (section 8).

Build it up

$ APP=taskflow; bash -c 'echo "child sees: [$APP]"'
child sees: []
$ export APP; bash -c 'echo "child sees: [$APP]"'      # export = copy into child processes' environment
child sees: [taskflow]
$ readonly VERSION="1.4.0"; VERSION="2.0"
bash: VERSION: readonly variable
$ env | grep -E "^(HOME|USER|PATH)="                  # env / printenv list environment variables
HOME=/home/shaurya
USER=shaurya
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

A plain variable lives only in the current shell; export copies it into every child's environment. That's how PORT=4000 npm start (Session 1) and systemd's Environment= (Session 2) reach process.env.

Exam trap

"echo '$HOME' prints your home directory." ✗ Single quotes are literal: it prints $HOME.

"A variable set in ./script.sh is available in my shell afterwards." ✗ The script ran in a child. Use source, or export to pass values down to children (never up).

Remember

NAME=value (no spaces) · "$NAME" expands as one word · '$NAME' literal · $(cmd) output · $((a+b)) maths · ${VAR:-default}. Always quote: "$var".

Mastery check
Q1. Predict: X=5; echo '$X' "$X" "${X}0" "$X0"

$X 5 50 and an empty string: literal, expanded, braces end the name, and $X0 is an unset variable called X0.

Q2. DIR="/var/backups/task flow". Why does ls $DIR fail, and what does it actually run?

Unquoted, it splits on the space: ls /var/backups/task flow, two arguments that don't exist. ls "$DIR" passes one.

Q3. Fill in: LOG_DIR=________ so the script uses $LOG_DIR from the environment if set, else /var/log/taskflow.

LOG_DIR="${LOG_DIR:-/var/log/taskflow}". Then LOG_DIR=/tmp/logs ./script.sh overrides it for one run.

3 Arguments

The problem

A one-line script, echo "Hello, $1! You are a $2.", called with only one argument:

$ ./greet.sh Shaurya
Hello, Shaurya! You are a .
$ ./greet.sh "Shaurya Verma" student
Hello, Shaurya Verma! You are a student.

The missing $2 didn't cause an error. It was just empty. Imagine that line was deploy $1 to $2, and you deployed to "" because you forgot an argument.

The idea

Words after the script name are positional parameters, numbered from 1. A few special variables describe them:

 ./deploy.sh   prod   1.4.0
     $0         $1     $2          $# = 2      "$@" = "prod" "1.4.0"      $? = last exit code
Think of it like this

Arguments are the order slip clipped to the recipe card: $1 is the first item, $# the number of items. The robot never checks the slip is complete; your recipe must.

See it

args.sh
#!/usr/bin/env bash
echo "script name : $0"
echo "first arg   : $1"
echo "second arg  : $2"
echo "arg count   : $#"
echo "PID         : $$"
echo '--- for a in "$@"'
for a in "$@"; do echo "  [$a]"; done
echo '--- for a in "$*"'
for a in "$*"; do echo "  [$a]"; done
echo '--- for a in $*'
for a in $*; do echo "  [$a]"; done
shift                             # drop $1; $2 becomes $1
echo "after shift : \$1=$1  \$#=$#"
$ ./args.sh "my file.txt" prod 42
script name : ./args.sh
first arg   : my file.txt
second arg  : prod
arg count   : 3
PID         : 3527
--- for a in "$@"
  [my file.txt]
  [prod]
  [42]
--- for a in "$*"
  [my file.txt prod 42]
--- for a in $*
  [my]
  [file.txt]
  [prod]
  [42]
after shift : $1=prod  $#=2

Same arguments, three loops. "$@" keeps each argument whole (what you want 99% of the time), "$*" glues them into one string, and unquoted $* splits on every space. shift drops $1 and moves the rest down.

The rest of the family: ${10} needs braces from 10 on, $# never counts $0, $$ is this script's PID and $! the PID of the last background job.

Build it up: validate before doing anything

deploy.sh
#!/usr/bin/env bash
# deploy.sh <environment> [version]
if [[ $# -lt 1 ]]; then
  echo "Usage: $0 <environment> [version]" >&2   # errors go to stderr
  exit 1                                          # non-zero = failure
fi
ENV="$1"
VERSION="${2:-latest}"            # optional 2nd arg with a default
echo "Deploying taskflow-api:$VERSION to $ENV"
$ ./deploy.sh; echo "exit=$?"
Usage: ./deploy.sh <environment> [version]
exit=1
$ ./deploy.sh staging
Deploying taskflow-api:latest to staging
$ ./deploy.sh prod 1.4.0
Deploying taskflow-api:1.4.0 to prod

The pattern for any script with arguments: check $#, print Usage: to stderr (>&2, section 7), exit 1, and give optional ones defaults with ${2:-…}. What Bash does not do: check arguments for you.

Exam trap

""$@" and "$*" are the same." ✗ Quoted, "$@" keeps each argument separate and "$*" joins them into one.

"$# includes the script name." ✗ $0 isn't counted. ./deploy.sh prod 1.4.0 gives $# = 2.

Remember

$1..$9 positional · $# count · "$@" all, separately · shift drops $1. Check $# → Usage to stderr → exit 1.

Mastery check
Q1. A script is called as ./s.sh "a b" c. How many times does each loop run: for x in "$@", for x in "$*", for x in $*?

2 (a b, c) · 1 (a b c) · 3 (a, b, c).

Q2. Predict: ./deploy.sh prod with the file above. What does it print, and what is $? afterwards?

Deploying taskflow-api:latest to prod, exit 0. $# = 1 passes the check, and ${2:-latest} fills in the missing version.

Q3. Inside a script, after DEST="$1"; shift, what does "$@" contain?

Every argument except the first, which is how backup.sh (section 9) separates the destination from the source list.

4 Conditions & exit codes

The problem

$ NAME=""
$ [ $NAME = "admin" ] && echo yes
bash: [: =: unary operator expected

A perfectly reasonable test crashed because a variable was empty. To see why, you need to know what if and [ actually are.

The idea

Every command finishes with an exit code: 0 = success, anything else = failure. if doesn't evaluate expressions. It runs a command and looks at its exit code. [ … ] and [[ … ]] are just commands that test something and exit 0 (true) or 1 (false).

if COMMAND; then …          ← runs COMMAND, looks only at $?
   exit 0   → the then-branch
   exit ≠ 0 → elif / else

[ $NAME = "admin" ]   with NAME empty  →  [ = "admin" ]    ← "=" has nothing on its left: syntax error
[[ $NAME = "admin" ]] with NAME empty  →  compares "" with "admin" → exit 1 (false), no error
Think of it like this

After every step the robot raises a thumbs up (0) or thumbs down (any other number). if only ever looks at the thumb. [[ -f config ]] is a step whose whole job is to raise a thumb.

See it: exit codes

$ ls /opt/taskflow > /dev/null; echo $?
0
$ ls /nope; echo $?
ls: cannot access '/nope': No such file or directory
2
$ grep -q zzz /etc/passwd; echo $?          # grep: 0 found, 1 not found, 2 error
1
$ nosuchcmd; echo $?
nosuchcmd: command not found
127
$ /tmp/noexec.sh; echo $?                   # file exists but has no x bit
bash: /tmp/noexec.sh: Permission denied
126

The codes worth knowing: 0 success (the only "true") · 1, 2 general error / misuse (each tool documents its own) · 126 found but not executable · 127 command not found · 128+N killed by signal N (130 = Ctrl+C, 137 = SIGKILL / OOM, 143 = SIGTERM).

What $? does not do: remember. It's overwritten by the very next command, even by echo, so read it immediately or save it: rc=$?.

Build it up

Short chains and case

$ mkdir -p /tmp/build && cd /tmp/build      # run the 2nd only if the 1st succeeded
$ cd /opt/taskflow || exit 1                 # run the 2nd only if the 1st failed
$ systemctl is-active --quiet taskflow && echo "up" || echo "down"

svc.sh
#!/usr/bin/env bash
case "$1" in
  start|up)   echo "starting taskflow" ;;
  stop|down)  echo "stopping taskflow" ;;
  restart)    echo "restarting taskflow" ;;
  *.tar.gz)   echo "restoring from archive $1" ;;
  *)          echo "Usage: $0 {start|stop|restart|<backup.tar.gz>}" >&2
              exit 1 ;;
esac
$ ./svc.sh down; ./svc.sh backup-20261009.tar.gz; ./svc.sh foo; echo "exit=$?"
stopping taskflow
restoring from archive backup-20261009.tar.gz
Usage: ./svc.sh {start|stop|restart|<backup.tar.gz>}
exit=1

case matches one value against glob patterns, top to bottom. | separates alternatives, ;; ends a branch, and *) catches everything else.

Exam trap

"[[ 10 > 9 ]] is true." ✗ Inside [[ ]], > compares strings ("10" sorts before "9"). Use -gt or (( )).

"a && b || c is an if/else." ✗ If b fails, c runs too. Use a real if when b can fail.

"if [[$X == 1]] is fine." ✗ The spaces inside the brackets are required: [[1: command not found.

Remember

0 = success. if tests an exit code, and [[ ]] is just a command that sets one. Files -f -d -x · strings -z = =~ · numbers -eq -gt or (( )).

Mastery check
Q1. Predict $? after each: grep -q root /etc/passwd · grep -q zzz /etc/passwd · gerp root /etc/passwd · [[ -d /etc ]].

0 (found) · 1 (not found) · 127 (no such command) · 0 (it is a directory).

Q2. Spot the bug: if [ $DISK_USED > 90 ]; then echo full; fi

Inside [ ], > is a redirection: it creates a file named 90, and the remaining test is always true. Use [[ $DISK_USED -gt 90 ]] or (( DISK_USED > 90 )).

Q3. What does mkdir /tmp/x && echo made || echo failed print the second time you run it?

mkdir: cannot create directory '/tmp/x': File exists, then failed: mkdir exited non-zero, so echo made was skipped and the || branch ran.

5 Loops

The problem

You want to report on every log file. The obvious way, looping over ls, breaks as soon as a file name contains a space:

$ ls
app.log  old app.log
$ for f in $(ls); do echo "[$f]"; done
[app.log]
[old]
[app.log]

Three "files", two of them wrong. It's section 2's word splitting again: $(ls) is unquoted text, so it splits on every space.

The idea

Three loops. for runs once per item, and the safe list of files is a glob like *.log, which expands to real names without splitting them. while runs as long as a command succeeds; until as long as it fails.

for x in LIST; do …; done       once per item: words, globs (*.log), {1..5}, "$@"
while CMD; do …; done           while CMD exits 0  (classic: while read -r line … done < file)
until CMD; do …; done           while CMD exits non-0 (retry until it works)
break → leave the loop · continue → skip to the next item
Think of it like this

for is "for each plate on this list, do the steps". while is "while there are order slips on the rail, take one and cook it". until is "keep checking the oven until it's hot".

See it

$ for f in *; do echo "[$f]"; done            # a glob: real names, never split
[app.log]
[old app.log]

What a glob does not do: disappear when nothing matches. for f in /var/log/none/*.log runs once with the literal text /var/log/none/*.log, unless you set shopt -s nullglob.

Build it up

loops.sh
#!/usr/bin/env bash
for svc in api db web; do                     # 1. over a list of words
  echo "checking taskflow-$svc"
done

  echo "attempt $i"
done

echo {1..5}                                   # brace expansion
echo {01..10..3}                              # zero-padded, step 3
echo server-{a,b,c}

readloop.sh
#!/usr/bin/env bash
while read -r name ip; do                     # read 2 fields per line
  [[ -z "$name" || "$name" == \#* ]] && continue   # skip blank and comment lines
  echo "$name -> $ip"
done < servers.txt                            # feed the file into the loop

count=0
until [[ $count -ge 3 ]]; do                  # until = loop while the condition is FALSE
  count=$((count + 1))
  echo "until: count=$count"
done

for code in 200 200 500 200 404; do
  [[ $code == 200 ]] && continue              # skip to the next iteration
  echo "first non-200: $code"
  break                                       # leave the loop
done
$ ./readloop.sh

web-02 -> 10.0.1.11
db-01 -> 10.0.2.20
until: count=1
until: count=2
until: count=3
first non-200: 500

read -r name ip splits each line on whitespace: field 1 → name, the rest → ip. -r keeps backslashes literal (while IFS= read -r line also keeps leading spaces). done < servers.txt feeds the file to the whole loop.

Exam trap

"A piped loop updates my variables." ✗ In cat f | while read …, the loop runs in a subshell:

$ total=0; cat servers.txt | while read -r line; do total=$((total + 1)); done; echo "total=$total"
total=0
$ total=0; while read -r line; do total=$((total + 1)); done < servers.txt; echo "total=$total"
total=4

"{1..$n} counts to n." ✗ Brace expansion happens before variables expand, so n=3; echo {1..$n} prints {1..3}. Use seq 1 "$n" or for ((i=1; i<=n; i++)).

Remember

Files → for f in *.log (never $(ls)) · lines → while read -r … done < file · counting → for ((i=1; i<=n; i++)).

Mastery check
Q1. Predict: for x in "a b" c; do echo "[$x]"; done

[a b] then [c]: two iterations, because the quotes make a b one word.

Q2. Spot the bug: n=0; grep ERROR app.log | while read -r l; do n=$((n+1)); done; echo $n always prints 0.

The pipe runs the loop in a subshell, whose n dies with it. Use done < <(grep ERROR app.log), or simply grep -c ERROR app.log.

Q3. Write a loop that tries curl -sf localhost:3000/health up to 5 times, 2 s apart, and stops as soon as it succeeds.

for ((i=1; i<=5; i++)); do curl -sf localhost:3000/health && break; sleep 2; done. && break exits on the first success, the same retry idea as healthcheck.sh.

6 Functions

The problem

Your backup script has the same six lines copy-pasted for /opt/taskflow, /etc/taskflow and /var/lib/taskflow. You fix a bug in the first copy and forget the other two, so last night's config backup silently used the old, broken logic.

The idea

A function is a named block of commands inside the script that you call like any other command. Inside it, $1, $2, $# and "$@" are the function's arguments. It hands back a result in one of two ways:

name() {                     define it BEFORE you call it
  local x="$1"               $1 = the function's 1st argument; local = private to this call
  …
}
name arg1 arg2               call it like a command
yes/no answer  → exit status:  return 0 / return 1     →  if name …; then
data answer    → output:       echo "value"            →  v=$(name …)
Think of it like this

A function is a sub-recipe card ("make the sauce") the main recipe calls by name. local gives it its own mixing bowl; without it, it uses the shared ones.

See it

funcs.sh
#!/usr/bin/env bash
greet() {
  local name="$1"                       # $1 inside a function = the function's 1st arg
  local role="${2:-developer}"
  echo "Hi $name ($role), you passed $# arg(s)"
}

is_port_open() {                        # answer via EXIT STATUS (0 = yes)
  local port="$1"
  ss -tln | grep -q ":${port} "
}

disk_usage() {                          # answer via OUTPUT (capture with $(...))
  df --output=pcent "${1:-/}" | tail -1 | tr -dc '0-9'
}

greet Shaurya
greet Riya "SRE"

if is_port_open 3000; then
  echo "port 3000: something is listening"
else
  echo "port 3000: free"
fi

used=$(disk_usage /)
echo "root disk is ${used}% used"

counter=0
bump() { counter=$((counter + 1)); local temp="gone"; }
bump; bump
echo "counter=$counter temp=${temp:-<unset>}"   # globals change, locals vanish
$ ./funcs.sh
Hi Shaurya (developer), you passed 1 arg(s)
Hi Riya (SRE), you passed 2 arg(s)
port 3000: something is listening
root disk is 31% used
counter=2 temp=<unset>

is_port_open has no return: a function's status is its last command's, here grep -q, so if is_port_open 3000 just works. disk_usage prints its answer for $(…) to capture. What return does not do: return data. It only sets a 0–255 exit code:

$ get_version() { return "1.4.0"; }; get_version; echo "status=$?"
bash: return: 1.4.0: numeric argument required
status=2

Build it up

That gives two real ways to hand back a result: exit status for yes/no (if is_port_open 3000) and output for data (used=$(disk_usage /)). Globals (no local, like counter) work but are easy to abuse.

One catch with output-style functions: everything they print to stdout ends up in the captured value. Send log messages from inside them to stderr (echo "checking…" >&2) so they don't pollute $(…).

Exam trap

"Variables inside a function are local by default." ✗ They're global unless declared local. That's why counter changed above.

"Inside a function, $1 is the script's first argument." ✗ It's the function's. Pass the script's arguments on explicitly: main "$@".

Remember

name() { local x="$1"; … } · yes/no → exit status · data → echo + $(…) · always local.

Mastery check
Q1. Predict: f() { echo "got $# args, first=$1"; }; f "a b" c

got 2 args, first=a b. The function has its own positional parameters, and the quotes keep a b as one argument.

Q2. Spot the bug: get_port() { echo "reading config"; echo 3000; }; PORT=$(get_port). What is $PORT?

Two lines, reading config and then 3000, because $(…) captures all of stdout. Send the log line to stderr: echo "reading config" >&2.

Q3. You need is_healthy to work in if is_healthy; then. Should it echo yes or return 0?

return 0 (or end on a command that succeeds): if reads the exit status, not the output. A version that did echo no would still be "true", since echo succeeds.

7 Pipes & redirection

The problem

$ ls /opt /nope > listing.txt
ls: cannot access '/nope': No such file or directory
$ cat listing.txt
/opt:
taskflow

The output went to the file, but the error still hit your screen and isn't in the file. When cron runs your backup at 2 a.m. with no screen, that error, your only clue, simply vanishes.

The idea

Every process has three numbered streams: 0 stdin (input), 1 stdout (normal output) and 2 stderr (errors). > redirects only stream 1. Redirection rewires each stream separately, and a pipe | connects one command's stdout to the next command's stdin.

              ┌───────────┐ 1 stdout ──▶ screen    (> file, >> file, | next-command)
 0 stdin  ──▶ │  command  │
 (< file)     └───────────┘ 2 stderr ──▶ screen    (2> file, 2>&1 = "wherever 1 points right now")

 grep " 500 " access.log  |  wc -l        stdout of grep → stdin of wc;  grep's stderr still goes to the screen
Think of it like this

The robot has two output trays, plates (stdout) and complaint slips (stderr), and one input hatch (stdin). > file moves only the plate tray, so complaints keep landing in front of you. A pipe is a conveyor belt from one robot's plate tray to the next one's hatch.

See it

$ echo "line 1" > out.txt; echo "line 2" > out.txt; cat out.txt     # > overwrote
line 2
$ echo "line 3" >> out.txt; cat out.txt                             # >> appends
line 2
line 3
$ ls /opt /nope > ok.txt 2> err.txt; cat err.txt                     # split the two streams
ls: cannot access '/nope': No such file or directory
$ ls /opt /nope > all.txt 2>&1; cat all.txt                         # both into one file (fixes the problem)
ls: cannot access '/nope': No such file or directory
/opt:
taskflow
$ ls /opt /nope 2>&1 > only-stdout.txt                               # WRONG order: 2 copied the old 1 (the screen)
ls: cannot access '/nope': No such file or directory

Redirections apply left to right, and 2>&1 means "point 2 wherever 1 points right now". So > file 2>&1 sends both to the file, while 2>&1 > file copies the screen first, then moves only stdout. What > does not do: ask before overwriting.

Build it up

$ echo "deploy v1.4.0 ok" | tee -a deploy.log                         # screen AND append to a file

$ printf '%s\n' web-01 web-02 | xargs -I {} echo "ssh {} uptime"      # lines → arguments

Exam trap

"cmd 2>&1 > out.log puts both streams in the file." ✗ Left to right: stderr is pointed at the terminal first, then only stdout moves. Write > out.log 2>&1.

"A pipe carries error messages to the next command." ✗ | connects stdout only. Use 2>&1 | (or |&) to pipe both.

Q2. Write the cron-safe way to run backup.sh so that every run's output and errors are appended to /var/log/taskflow/backup-cron.log.

Q3. Why does grep ERROR /nope/app.log | wc -l print 0 and an error message?

8 Safe scripts: strict mode & debugging

The problem

cp /opt/taskflow/.env /backup/          ← fails: /backup doesn't exist
rm -rf "$BACKUP_DIRR/old"               ← typo: BACKUP_DIRR is unset → expands to "" → rm -rf /old

By default Bash carries on after a failed command and treats a misspelled variable as an empty string. Put those together in a script that deletes things, and you get a disaster with exit code 0.

The idea

Put set -euo pipefail at the top of every script. It turns all three silent failures into hard stops:

OptionEffectWithout it
-eExit as soon as a command fails (except in if/while conditions and &&/|| chains)The script carries on after a failed cp and does damage
-uUsing an unset variable is an errorA typo expands to "" (rm -rf "$BACKUP_DIRR/old" → rm -rf /old)
-o pipefailA pipeline fails if any command in it failsOnly the last command's status counts
Think of it like this

Without strict mode, the robot that drops the eggs keeps cooking and serves an omelette with no eggs. set -e makes it stop at the failed step; -u makes it refuse a jar that doesn't exist instead of pretending it was empty.

See it

strict.sh
#!/usr/bin/env bash

exit=1
$ bash -c 'set -u; rm -rf "$BACKUP_DIRR/old"'                       # -u catches the typo

$ bash -c 'grep ERROR /nope/app.log 2>/dev/null | wc -l; echo "exit=$?"'

$ bash -c 'set -o pipefail; grep ERROR /nope/app.log 2>/dev/null | wc -l; echo "exit=$?"'

What set -e does not do: catch everything. A failure used as a condition (if cmd, cmd || …) counts as handled, and that covers a whole function called in such a list. So check important commands yourself (if ! tar …; then in backup.sh).

Exam trap

"(( count++ )) is a safe way to count under set -e." ✗ (( expr )) returns status 1 when the value is 0, and count++ evaluates to the old value, 0, so the script dies:

9 Automation script 1: backup.sh

The problem

TaskFlow's code (/opt/taskflow) and secrets (/etc/taskflow) exist only on web-01. You need nightly archives of both, old ones removed so the disk doesn't fill (Session 2's 99%), a log, and a non-zero exit if anything failed, so cron or monitoring notices.

The idea

Combine every block on this page: arguments + validation (3), a function per directory (6), a loop over "$@" (5), a timestamped tar, find -mtime cleanup, logging with tee (7), all under strict mode (8).

backup.sh /var/backups/taskflow /opt/taskflow /etc/taskflow
   │ 1. validate: ≥ 2 args? RETENTION_DAYS a number?             → else Usage, exit 1
   │ 2. for each source: backup_dir()  → tar -czf NAME-TIMESTAMP.tar.gz → log INFO (or WARN, count failure)
   │ 3. find DEST -name '*.tar.gz' -mtime +7 -delete              → log each deleted file
   ▼ 4. failures > 0 ?  → log ERROR, exit 1   :   log "finished OK", exit 0

See it: the whole file

It archives any number of directories into timestamped .tar.gz files, deletes archives older than 7 days, logs everything, and exits non-zero if anything failed.

/opt/taskflow/scripts/backup.sh
#!/usr/bin/env bash
#
# backup.sh - archive one or more directories into timestamped .tar.gz files
#             and delete archives older than RETENTION_DAYS.
#
# Usage:   backup.sh <backup_dir> <source_dir> [source_dir ...]
# Example: backup.sh /var/backups/taskflow /opt/taskflow /etc/taskflow
# Env:     RETENTION_DAYS (default 7), LOG_FILE (default /var/log/taskflow/backup.log)

set -euo pipefail                            # stop on errors, unset vars, failed pipes
umask 077                                    # archives can contain secrets -> owner-only files

RETENTION_DAYS="${RETENTION_DAYS:-7}"
LOG_FILE="${LOG_FILE:-/var/log/taskflow/backup.log}"
TIMESTAMP="$(date +%Y%m%d-%H%M%S)"           # e.g. 20261009-023000

log() {                                      # usage: log LEVEL message...
  local level="$1"
  shift                                      # drop LEVEL; "$*" is now the message
  echo "$(date '+%Y-%m-%d %H:%M:%S') [$level] $*" | tee -a "$LOG_FILE"
}

usage() {
  echo "Usage: $(basename "$0") <backup_dir> <source_dir> [source_dir ...]" >&2
  exit 1
}

backup_dir() {                               # usage: backup_dir SOURCE DEST
  local src="${1%/}"                         # strip a trailing slash
  local dest="$2"
  local name archive size

  if [[ ! -d "$src" ]]; then
    log WARN "skipping '$src' (not a directory)"
    return 1
  fi

  name="$(echo "${src#/}" | tr '/' '_')"     # /opt/taskflow -> opt_taskflow
  archive="${dest}/${name}-${TIMESTAMP}.tar.gz"

  if ! tar --exclude='node_modules' -czf "$archive" -C "$(dirname "$src")" "$(basename "$src")"; then
    log ERROR "tar failed for '$src'"
    return 1
  fi
  size="$(du -h "$archive" | cut -f1)"
  log INFO "created $archive ($size)"
}

# ---- 1. validate input ----
[[ $# -ge 2 ]] || usage
if ! [[ "$RETENTION_DAYS" =~ ^[0-9]+$ ]]; then
  echo "Error: RETENTION_DAYS must be a whole number (got '$RETENTION_DAYS')" >&2
  exit 1
fi

DEST="$1"
shift                                        # now "$@" = only the source dirs
mkdir -p "$DEST" "$(dirname "$LOG_FILE")"

# ---- 2. back up every source directory ----
log INFO "backup started: $# source(s) -> $DEST"
failed=0
for src in "$@"; do
  backup_dir "$src" "$DEST" || failed=$((failed + 1))
done

# ---- 3. delete archives older than RETENTION_DAYS ----
find "$DEST" -maxdepth 1 -type f -name '*.tar.gz' -mtime +"$RETENTION_DAYS" -print -delete |
  while IFS= read -r old; do
    log INFO "deleted old backup $old"
  done

# ---- 4. summary + exit code ----
if (( failed > 0 )); then
  log ERROR "finished with $failed failure(s)"
  exit 1
fi
log INFO "backup finished OK"
Line(s)Why
set -euo pipefailStop on the first failure, on unset variables, and on failures inside pipes (section 8)
umask 077The archives contain .env / taskflow.env secrets, so files are created rw------- (Session 2)
RETENTION_DAYS="${RETENTION_DAYS:-7}", LOG_FILE=…Configurable from the environment with a default: RETENTION_DAYS=30 ./backup.sh …

10 Automation script 2: healthcheck.sh

The problem

systemd restarts TaskFlow when the process dies (Session 2). But sometimes the process is alive and stuck: it's still running, so systemd is happy, but /health never answers. Users get timeouts, and nothing restarts it.

The idea

Check what users see: ask /health over HTTP and, after several failures in a row, restart the service and check again. It uses set -uo pipefail without -e, because a failing curl is the normal "down" case to handle, not to die on.

curl /health ── 200 ──▶ exit 0 (quiet: the log stays small)
     │ not 200 (000 = no connection)
     ▼ retry: 3 attempts, 5 s apart
systemctl restart taskflow ──▶ wait 5 s ──▶ curl again ── 200 ──▶ log RECOVERED, exit 0
                                                       └─ else ─▶ log CRITICAL, exit 1

See it: the whole file

/opt/taskflow/scripts/healthcheck.sh
#!/usr/bin/env bash
#
# healthcheck.sh - check TaskFlow's /health endpoint and restart the service if it is down.
# Run as root (systemctl restart needs it), e.g. from root's crontab every 2 minutes.
# Exit codes: 0 = healthy or recovered, 1 = still down after a restart

set -uo pipefail                 # no -e: a failing curl is expected here and handled below

URL="${HEALTH_URL:-http://localhost:3000/health}"
SERVICE="taskflow"
RETRIES=3                        # attempts before restarting
WAIT=5                           # seconds between attempts
LOG_FILE="/var/log/taskflow/healthcheck.log"

log() {
  echo "$(date '+%Y-%m-%d %H:%M:%S') $*" >> "$LOG_FILE"
}

http_status() {                  # prints the HTTP status code; 000 = could not connect
  curl -s -o /dev/null -w '%{http_code}' --max-time 3 "$URL"
}

for ((i = 1; i <= RETRIES; i++)); do
  code="$(http_status)"
  if [[ "$code" == "200" ]]; then
    exit 0                       # healthy: stay quiet so the log doesn't grow every run
  fi
  log "WARN attempt $i/$RETRIES: $URL returned $code"
  sleep "$WAIT"
done

log "ERROR $SERVICE is down - restarting"
systemctl restart "$SERVICE"
sleep "$WAIT"

code="$(http_status)"
if [[ "$code" == "200" ]]; then
  log "RECOVERED $SERVICE is healthy again"
  exit 0
fi
log "CRITICAL $SERVICE still down after restart (HTTP $code)"
exit 1

Mastery check
Q1. TaskFlow is up but its DB is down, so /health returns 500. Trace the script.

Q2. What does curl -s -o /dev/null -w '%{http_code}' --max-time 3 http://localhost:3000/health print when nothing listens on 3000? When the request takes 10 s?

Q3. Why retry 3 times before restarting, instead of restarting on the first failed check?

One slow response (a GC pause, a slow query) is not an outage. Restarting drops every in-flight request, so you only do it once the failure has repeated.

11 Scheduling with cron

The problem

Nobody is awake at 02:30 to run the backup, and nobody wants to type the health check every 2 minutes. And the classic surprise: a scheduled script that works in your terminal silently does nothing from the scheduler.

The idea

cron is a daemon that runs commands on a schedule. Each user (and root) has a crontab: one line per job, five time fields, then the command. cron starts the command in a bare environment: /bin/sh, a minimal PATH, no ~/.bashrc, no terminal.

┌───────────── minute        (0–59)
│ ┌─────────── hour          (0–23)
│ │ ┌───────── day of month  (1–31)
│ │ │ ┌─────── month         (1–12 or jan–dec)
│ │ │ │ ┌───── day of week   (0–7; 0 and 7 = Sunday; or sun–sat)
│ │ │ │ │
* * * * *   command-to-run
Think of it like this

cron is the kitchen's timer board ("02:30 daily: run the backup card"), but the robot it sends in walks into an empty kitchen. None of the jars on your counter (PATH, variables, current directory) are there, so the card must name everything.

See it: read a schedule

ScheduleRuns

* every value · */N every N · a-b range · a,b list. What cron does not do: catch up. If the server was off at 02:30, that night's backup never runs. A systemd .timer with Persistent=true can catch up, and Kubernetes has CronJobs (Session 15).

Build it up: TaskFlow's crontab

$ sudo crontab -e          # edit ROOT's crontab (opens an editor; saved = installed)
$ crontab -e               # edit YOUR user's crontab
$ sudo crontab -l          # list it
root's crontab (sudo crontab -l)
# m   h   dom  mon  dow   command
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=""

# every 2 minutes: health check (restarts taskflow if /health fails)
*/2   *   *    *    *     /opt/taskflow/scripts/healthcheck.sh

# daily at 02:30: back up code + config, keep 7 days
30    2   *    *    *     /opt/taskflow/scripts/backup.sh /var/backups/taskflow /opt/taskflow /etc/taskflow >> /var/log/taskflow/backup-cron.log 2>&1

# Sundays at 04:00: trim the systemd journal to the last 14 days
0     4   *    *    0     journalctl --vacuum-time=14d
LineWhy
SHELL=/bin/bashcron runs commands with /bin/sh (dash) by default
PATH=…cron's default PATH is only /usr/bin:/bin. Anything in /usr/local/bin or /usr/sbin is "command not found" without this.
MAILTO=""Don't try to email the output. Most servers have no mail setup, and cron would log No MTA installed, discarding output.
*/2 … healthcheck.shEvery 2 minutes. No redirect needed: the script writes its own log.
30 2 … backup.sh … >> …/backup-cron.log 2>&1Daily 02:30. Keep stdout and errors from each run (section 7), otherwise they're lost.
0 4 * * 0 journalctl --vacuum-time=14dSundays 04:00: stop the journal growing forever (Session 2)
Comments on their own linecron only treats # at the start of a line as a comment. FOO=bar # note really sets FOO to bar # note. On a job line the text is handed to the shell with the command, and any % in it is still mangled.
 
$ grep CRON /var/log/syslog | tail -2                        # did it run?  (or: journalctl -u cron)
2026-10-09T02:30:01.617363+05:30 web-01 CRON[8812]: (root) CMD (/opt/taskflow/scripts/backup.sh /var/backups/taskflow /opt/taskflow /etc/taskflow >> /var/log/taskflow/backup-cron.log 2>&1)
2026-10-09T02:30:01.617495+05:30 web-01 CRON[8813]: (root) CMD (/opt/taskflow/scripts/healthcheck.sh)
$ tail -1 /var/log/taskflow/backup-cron.log                  # what did it print?
2026-10-09 02:30:01 [INFO] backup finished OK

The alternative is a system cron file, which has an extra user column:

/etc/cron.d/taskflow
# /etc/cron.d/taskflow - system cron file: note the extra USER column
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=""

# m   h   dom  mon  dow   user   command
*/2   *   *    *    *     root   /opt/taskflow/scripts/healthcheck.sh
30    2   *    *    *     root   /opt/taskflow/scripts/backup.sh /var/backups/taskflow /opt/taskflow /etc/taskflow >> /var/log/taskflow/backup-cron.log 2>&1

Same jobs and environment lines; the sixth field, root, names the user. It lives with the system config (deployable by Ansible or a package), while crontab -e edits a per-user table.

Why "it works in my terminal but not in cron"
  • PATH and environment: only /usr/bin:/bin, no ~/.bashrc, no exported variables, a different working directory, so aws: command not found. Set PATH= and use absolute paths.
  • % means newline in crontab: echo "run at $(date +%F)" is cut at the % (cron logged CMD (echo "run at $(date +)). Escape it as \% or use a script.
  • /etc/cron.d rules: the file must be owned by root (cron logs WRONG FILE OWNER), must not be group- or world-writable, and its name may not contain a dot, so taskflow.cron is silently ignored.
  • Day-of-month and day-of-week both set (e.g. 0 0 13 * 5): it runs when either matches, so every 13th and every Friday.
Exam trap

"cron jobs run with my normal shell environment." ✗ They get /bin/sh, PATH=/usr/bin:/bin and none of your variables.

"crontab -r reloads the crontab." ✗ It removes your whole crontab without asking, and r is right next to e. Keep a copy: crontab -l > crontab.bak.

Remember

m h dom mon dow command. In every crontab: SHELL, PATH, absolute paths, >> log 2>&1, escape %. Check with grep CRON /var/log/syslog.

Mastery check
Q1. Write the schedule for "every weekday at 18:30" and for "every 10 minutes".

30 18 * * 1-5 and */10 * * * *.

Q2. Spot the bug: 0 3 * * * tar -czf /backups/db-$(date +%F).tar.gz /var/lib/taskflow

% becomes a newline, so the command is cut at date + and the rest is fed in as stdin. Escape it (\%F) or move the command into a script.

Q3. grep CRON /var/log/syslog shows the job's CMD line at 02:30, but there's no new backup. What does that tell you, and where do you look next?

cron did start it, so the schedule is fine and the script failed. Read its redirected output (tail /var/log/taskflow/backup-cron.log). Usually it's PATH, permissions or a missing argument.

★ Putting it all together

The big idea

The shell is literal: it splits words on spaces, treats unset variables as empty and carries on after failures, unless you quote, validate and use strict mode. With that in hand, scripts turn Session 2's commands into repeatable automation. backup.sh uses arguments, validation, a function per directory, a loop over "$@", a timestamped tar, find -mtime cleanup and tee logging. healthcheck.sh uses a retry loop, captured output and systemctl self-healing. cron runs both, in an environment you spell out. The same skills come back in Dockerfile RUN lines, CI run: steps and Kubernetes probes.

Final mastery check — combine everything
Q1. backup.sh works when you run it with sudo, but from root's crontab it logs nothing and makes no archives. grep CRON /var/log/syslog shows the CMD line. List three likely causes using sections 1, 7 and 11.

(1) A % in the line (a new date +%F?) cut the command short (11). (2) No redirect, so the error went nowhere (7). (3) A missing PATH=/SHELL=, a relative path, or no x bit (1, 11).

Q2. Predict, and fix: for f in $(ls /var/backups); do rm $f; done run from your home directory, with a file called old backup.tar.gz in there.

It loops over old and backup.tar.gz (split on the space) and runs rm old in your current directory, because ls prints bare names. Fix: for f in /var/backups/*; do rm -- "$f"; done.

Q3. Why does backup.sh use set -e but healthcheck.sh doesn't, and how does backup.sh still continue after one bad directory?

A surprise failure should stop a backup, but a failing curl is what the health check exists to handle. backup.sh keeps going because backup_dir … || failed=… is an || list, which is exempt from -e, and the function uses return 1, not exit.

Q4. Spot every bug: #!/bin/sh / DIR = $1 / if [ -d $DIR ]; then tar -cvfz $DIR.tar.gz $DIR; fi

(1) /bin/sh is dash; use #!/usr/bin/env bash. (2) DIR = $1 runs a command called DIR. (3) Unquoted $DIR breaks on spaces, and with no argument [ -d ] is true. (4) -cvfz makes an archive named z; use -czvf "$DIR.tar.gz" "$DIR". (5) No $# check.

Q5. Write a one-line crontab entry that runs healthcheck.sh every minute during office hours (09:00–17:59, Monday–Friday) and keeps any output it prints.

* 9-17 * * 1-5 /opt/taskflow/scripts/healthcheck.sh >> /var/log/taskflow/hc-cron.log 2>&1. Fields: every minute, hours 9–17, any day of month, any month, Mon–Fri. Use an absolute path, and append both streams.
