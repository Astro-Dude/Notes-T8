1 Ingress & Ingress Controllers

Explain like I'm 5

One front door with a receptionist who reads the address on each letter and walks it to the right room — instead of building a separate door for every room.

Why Ingress

  • With only Services, exposing taskflow-web and taskflow-api means two LoadBalancer Services → two cloud load balancers, two IPs, two bills, TLS set up twice.
  • An Ingress is an L7 (HTTP/HTTPS) routing table: "Host api.taskflow.local → Service taskflow-api; path / → taskflow-web". One load balancer in front, TLS terminated once.
LoadBalancer ServiceIngress
OSI layerL4 (TCP/UDP)L7 (HTTP/HTTPS)
Routing byPort onlyHost name + URL path
Cloud LBsOne per ServiceOne for the whole cluster (the controller's)
TLSApp or LB does it, per ServiceTerminated at the Ingress, one Secret per host
ProtocolsAnything (Postgres, gRPC, raw TCP)HTTP(S) only

Status in 2026

The Ingress API (networking.k8s.io/v1) is stable and not going away, but it is feature-frozen; Kubernetes recommends Gateway API (Gateway + HTTPRoute) for new designs. The community ingress-nginx controller was retired (no fixes after March 2026). It still works and is fine for learning on minikube; for production pick a maintained controller.

2 Host & path-based routing

Explain like I'm 5

Host-based = which building the letter is addressed to. Path-based = which floor inside the building.

We need a second backend. Stand-in for taskflow-web (nginx serving the static frontend):

$ kubectl create deployment taskflow-web --image=nginx:1.27-alpine
deployment.apps/taskflow-web created
$ kubectl expose deployment taskflow-web --port=80
service/taskflow-web exposed                 # ClusterIP Service, port 80

TaskFlow's API serves /health and /tasks (no /api prefix). So the file has two Ingress objects: one plain (host-based), one that strips /api (path-based with rewrite).

k8s/ingress.yaml
apiVersion: networking.k8s.io/v1      # the only Ingress API since K8s 1.22
kind: Ingress
metadata:
  name: taskflow
  namespace: taskflow                 # backends must be Services in THIS namespace
spec:
  ingressClassName: nginx             # handled by ingress-nginx
  rules:
    - host: taskflow.local            # HOST-based rule 1: the website
      http:
        paths:
          - path: /
            pathType: Prefix          # "/" + Prefix = everything on this host
            backend:
              service:
                name: taskflow-web
                port:
                  number: 80          # the Service's port (not the Pod's)
    - host: api.taskflow.local        # HOST-based rule 2: API on its own subdomain
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: taskflow-api
                port:
                  name: http          # or number: 80 — refers to the Service port name
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: taskflow-api-path
  namespace: taskflow
  annotations:                        # controller-specific options live in annotations
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2   # send only capture group 2 upstream
spec:
  ingressClassName: nginx
  rules:
    - host: taskflow.local            # PATH-based: same host, /api/... → API
      http:
        paths:
          - path: /api(/|$)(.*)       # group1 = "/" or end, group2 = the rest
            pathType: ImplementationSpecific   # regex needs this, not Prefix
            backend:
              service:
                name: taskflow-api
                port:
                  number: 80
FieldMeaningGotcha
ingressClassNameWhich controller owns this Ingress.Missing/wrong → ignored, ADDRESS stays empty.
rules[].hostMatch the HTTP Host header. Omit = any host. Wildcards like *.taskflow.local allowed.No IPs, no ports — just a DNS name.
http.paths[].pathURL path to match.Must start with / (except regex with ImplementationSpecific).
pathTypePrefix / Exact / ImplementationSpecific (table below).Required field in v1.
backend.service.nameTarget Service (same namespace).Old serviceName/servicePort syntax was removed with v1beta1.
backend.service.portnumber: or name: of the Service port.Use 80 (Service port), not 3000 (targetPort).
rewrite-target: /$2ingress-nginx rewrites the upstream path to capture group 2.Applies to every path in that Ingress — hence the separate object.

pathType

pathType / path/api/api//api/tasks/apis/API
Exact /api✔✘✘✘✘
Prefix /api✔✔✔✘ (not a path element)✘ (case-sensitive)
ImplementationSpecificController decides. ingress-nginx: treated as a regex when use-regex/rewrite-target is set.

When several paths match, the longest wins (Exact beats Prefix on a tie). So /api/... goes to the API even though / also matches.

Example: how rewrite-target maps paths
Browser requestsGroup 1 / Group 2API receives
/api"" / ""/
/api/tasks"/" / "tasks"/tasks
/api/tasks/7?done=true"/" / "tasks/7"/tasks/7?done=true

Without the rewrite, the API would get /api/tasks and answer 404 — the single most common Ingress bug.

Common mistakes
  • kubectl get ingress shows no ADDRESS → no controller running or wrong ingressClassName.
  • 503 Service Temporarily Unavailable → backend Service has no ready endpoints (Session 11 selector bug).
  • Old tutorials use apiVersion: extensions/v1beta1 and serviceName: — rejected since 1.22 (no matches for kind "Ingress" in version ...).
  • Regex in a Prefix path → newer ingress-nginx rejects it; use ImplementationSpecific.
  • Pointing a backend at a Service in another namespace — not allowed; create the Ingress in that namespace.
Recap rules[].host = host-based, paths[].path + pathType = path-based, longest match wins. Backends point at Service ports. Use rewrite-target when the app doesn't know the URL prefix.

3 TLS for Ingress

Explain like I'm 5

The receptionist checks your ID card (certificate) at the door and opens the sealed envelope; inside the building, letters move normally.

  • TLS termination at the Ingress: the browser speaks HTTPS to the controller, which decrypts and forwards plain HTTP to the Pods. Apps don't touch certificates.
  • The certificate + private key live in a Secret of type kubernetes.io/tls (keys tls.crt, tls.key), in the same namespace as the Ingress.

1. Make a self-signed certificate (local only)

$ openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
    -keyout taskflow.key -out taskflow.crt \
    -subj "/CN=taskflow.local" \
    -addext "subjectAltName=DNS:taskflow.local,DNS:api.taskflow.local"
.....+.........+++++++
writing new private key to 'taskflow.key'
-----
$ openssl x509 -in taskflow.crt -noout -ext subjectAltName      # verify the host names
X509v3 Subject Alternative Name:
    DNS:taskflow.local, DNS:api.taskflow.local
FlagMeaning
req -x509Output a self-signed certificate instead of a signing request.
-nodesDon't encrypt the private key ("no DES"; OpenSSL 3 also accepts -noenc). The controller must read it without a passphrase.
-days 365 -newkey rsa:2048Valid one year; create a new 2048-bit RSA key.
-subj "/CN=..."Subject without interactive prompts.
-addext subjectAltName=...Host names the cert is valid for. Browsers/curl check SAN, not CN. Needs OpenSSL 1.1.1+ (or LibreSSL 3.x).

2. Store it as a TLS Secret

$ kubectl create secret tls taskflow-tls --cert=taskflow.crt --key=taskflow.key
secret/taskflow-tls created
$ kubectl get secret taskflow-tls
NAME           TYPE                DATA   AGE
taskflow-tls   kubernetes.io/tls   2      5s          # DATA 2 = tls.crt + tls.key

3. Add a tls block to the Ingress

k8s/ingress.yaml (spec of Ingress "taskflow")
spec:
  ingressClassName: nginx
  tls:                                # NEW: which hosts get HTTPS, with which cert
    - hosts:
        - taskflow.local              # must match rules[].host AND the cert's SAN
        - api.taskflow.local
      secretName: taskflow-tls        # kubernetes.io/tls Secret, same namespace
  rules:
    # ... unchanged ...

Add the same block (hosts: taskflow.local) to taskflow-api-path, then apply.

$ kubectl apply -f k8s/ingress.yaml
$ kubectl get ingress taskflow
NAME       CLASS   HOSTS                               ADDRESS        PORTS     AGE
taskflow   nginx   taskflow.local,api.taskflow.local   192.168.49.2   80, 443   20m

$ curl -I http://taskflow.local/                    # ingress-nginx redirects HTTP → HTTPS once TLS is set
HTTP/1.1 308 Permanent Redirect
Location: https://taskflow.local/
$ curl https://api.taskflow.local/health
curl: (60) SSL certificate problem: self-signed certificate      # expected: nobody trusts our CA
$ curl --cacert taskflow.crt https://api.taskflow.local/health      # trust it explicitly
{"status":"ok"}
$ curl -k https://taskflow.local/api/health          # -k = skip verification (testing only)
{"status":"ok"}

Real certificates: cert-manager

cert-manager is a controller that obtains and renews certificates (e.g. free Let's Encrypt) and writes them into the TLS Secret for you. Install it once, create a ClusterIssuer, then just annotate the Ingress:

metadata:
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod   # which issuer to ask
spec:
  tls:
    - hosts: [taskflow.example.com]                   # must be a real public domain for Let's Encrypt
      secretName: taskflow-tls                        # cert-manager creates + renews this Secret
Common mistakes
  • Browser shows "Kubernetes Ingress Controller Fake Certificate" → the controller couldn't use your Secret: wrong secretName, Secret in another namespace, or the host isn't in the cert's SAN.
  • tls.hosts lists a host that has no matching rules[].host → no route for it.
  • Committing taskflow.key to Git. Add *.key and *.crt to .gitignore.
Recap openssl req -x509 → kubectl create secret tls → spec.tls[].hosts + secretName. HTTP gets a 308 to HTTPS. In production let cert-manager issue and renew certs.

4 ConfigMaps

Explain like I'm 5

The same toy (image) with a different instruction card (ConfigMap) for each playroom: dev, staging, prod.

  • A ConfigMap stores non-secret config as key/value strings (max 1 MiB). Same image, different ConfigMap per environment — the 12-factor "config in the environment" rule.
  • Pods consume it as env vars (one key or all keys) or as files in a volume.

Three ways to create one

$ kubectl create configmap demo-literal --from-literal=LOG_LEVEL=info --from-literal=NODE_ENV=production
configmap/demo-literal created

$ cat features.json
{
  "enableSignup": true,
  "maxTasksPerUser": 100
}
$ kubectl create configmap taskflow-features --from-file=features.json    # key = file name
configmap/taskflow-features created

$ kubectl create configmap demo-env --from-env-file=app.env       # each KEY=value line → one key; add --dry-run=client -o yaml to just print YAML

The declarative version that goes in the repo:

k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: taskflow-config
  namespace: taskflow
  labels:
    app: taskflow
data:                                 # all values are STRINGS
  NODE_ENV: production
  LOG_LEVEL: info
  PORT: "3000"                         # quote numbers/booleans
  DB_HOST: taskflow-db                # the Service from Session 11
  DB_PORT: "5432"
  DB_NAME: taskflow
# immutable: true                     # optional: can't be edited, must be replaced (safer, less API load)
  • data: string keys (letters, digits, - _ .) → string values. PORT: 3000 unquoted fails with cannot unmarshal number into Go struct field ConfigMap.data of type string.
  • Embed a whole file with key: | + an indented block; binaryData takes base64 for non-UTF-8 content.
  • immutable: true: data can't change — create taskflow-config-v2 and point the Deployment at it instead.
$ kubectl apply -f k8s/configmap.yaml
configmap/taskflow-config created
$ kubectl get configmaps
NAME                DATA   AGE
kube-root-ca.crt    1      2d         # auto-created in every namespace
taskflow-config     6      5s
taskflow-features   1      40s

Three ways to consume it

# (a) one key → one env var (you choose the variable name)
          env:
            - name: LOG_LEVEL
              valueFrom:
                configMapKeyRef:
                  name: taskflow-config
                  key: LOG_LEVEL
                  optional: true            # start even if the key/ConfigMap is missing

# (b) every key → env var of the same name
          envFrom:
            - configMapRef:
                name: taskflow-config

# (c) every key → a file in a directory
          volumeMounts:
            - name: features
              mountPath: /etc/taskflow      # /etc/taskflow/features.json
              readOnly: true
      volumes:                              # at Pod spec level, next to containers:
        - name: features
          configMap:
            name: taskflow-features

Recap ConfigMap = non-secret strings. Create with --from-literal / --from-file / YAML. Consume via configMapKeyRef, envFrom or a volume. Env needs a restart to update; mounted files update on their own.

5 Secrets

Explain like I'm 5

A Secret is a ConfigMap in a sealed envelope — but the envelope is see-through unless you lock the drawer (RBAC + encryption).

  • A Secret holds sensitive values: passwords, tokens, TLS keys, registry credentials (max 1 MiB).
  • Values are stored base64-encoded. Kubernetes treats Secrets more carefully than ConfigMaps (kept in tmpfs on nodes, only sent to nodes that run Pods using them, hidden in describe), but base64 is not encryption.

Create one imperatively (the safe default — no file to leak)

$ kubectl create secret generic taskflow-db-secret \
    --from-literal=POSTGRES_USER=taskflow \
    --from-literal=POSTGRES_PASSWORD='s3cr3t-Tf9x'     # single quotes: shell won't touch special chars
secret/taskflow-db-secret created
$ kubectl get secret taskflow-db-secret
NAME                 TYPE     DATA   AGE
taskflow-db-secret   Opaque   2      5s          # describe shows only byte sizes, not values

base64, and why echo -n

$ echo -n 'taskflow' | base64
dGFza2Zsb3c=
$ echo 'taskflow' | base64                # without -n the trailing newline is encoded too
dGFza2Zsb3cK                            # = "taskflow\n" → Postgres login fails, very hard to spot
$ echo -n 's3cr3t-Tf9x' | base64
czNjcjN0LVRmOXg=
$ kubectl get secret taskflow-db-secret -o jsonpath='{.data.POSTGRES_PASSWORD}' | base64 -d
s3cr3t-Tf9x                             # anyone who can "get secrets" can read it

The YAML form

k8s/secret.yaml (local/dev only — git-ignored; commit a secret.example.yaml with placeholders)
apiVersion: v1
kind: Secret
metadata:
  name: taskflow-db-secret
  namespace: taskflow
type: Opaque                          # generic key/value secret
data:                                 # values MUST be base64
  POSTGRES_USER: dGFza2Zsb3c=         # "taskflow"
  POSTGRES_PASSWORD: czNjcjN0LVRmOXg= # "s3cr3t-Tf9x"

Or write plain text under stringData — the API server base64-encodes it into data (write-only; get -o yaml shows data; wins if a key is in both):

stringData:                           # replaces the data: block above
  POSTGRES_USER: taskflow
  POSTGRES_PASSWORD: s3cr3t-Tf9x

Plain text under data: is rejected: illegal base64 data at input byte .... type tells K8s which keys to expect (table below).

k8s/postgres.yaml (container excerpt — replaces the plain-text env from Session 11)
        - name: postgres
          image: postgres:16
          envFrom:
            - secretRef:
                name: taskflow-db-secret     # POSTGRES_USER + POSTGRES_PASSWORD
          env:
            - name: POSTGRES_DB
              value: taskflow

Best practices

  • Never commit real Secrets to Git — history is forever. Use kubectl create secret, CI secrets, or the tools below.
  • RBAC: only the app's ServiceAccount and admins may get/list Secrets. Anyone who can create Pods in the namespace can mount any Secret there (Session 16).
  • Encryption at rest: by default etcd holds them as base64. Enable an API-server EncryptionConfiguration (KMS provider on EKS/GKE/AKS).
  • External Secrets Operator: the real value lives in AWS Secrets Manager / Vault and is synced into a K8s Secret. Sealed Secrets: kubeseal encrypts it into a SealedSecret that is safe to commit (GitOps, Session 22).
  • Prefer volume mounts for very sensitive values — env vars leak into crash dumps, child processes and kubectl exec -- env.
  • Rotate: update the Secret, rollout restart, and change the password in the DB itself.

Common mistakes
  • Thinking base64 = encrypted and pasting secret.yaml into a public repo. Rotate the password immediately if you did.
  • echo without -n → hidden \n in the password.
  • Secret created in default while the Pod runs in taskflow → CreateContainerConfigError: secret "taskflow-db-secret" not found. Secrets are namespaced.
Recap Secret = base64 key/values with types (Opaque, tls, dockerconfigjson). base64 ≠ encryption: protect with RBAC, encryption at rest, and keep real values out of Git (External/Sealed Secrets).

kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
  labels: { app: taskflow, tier: api }
spec:
  replicas: 3
  selector:
    matchLabels: { app: taskflow, tier: api }
  template:
    metadata:
      labels: { app: taskflow, tier: api }
    spec:
      containers:
        - name: api
          image: shauryav/taskflow-api:1.1.0
          ports:
            - name: http
              containerPort: 3000
          envFrom:                              # 1) NODE_ENV, LOG_LEVEL, PORT, DB_HOST, DB_PORT, DB_NAME
            - configMapRef:
                name: taskflow-config
          env:                                  # processed after envFrom; same name here wins
            - name: DB_USER                     # 2) from the Secret, renamed
              valueFrom:
                secretKeyRef:
                  name: taskflow-db-secret
                  key: POSTGRES_USER
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: taskflow-db-secret
                  key: POSTGRES_PASSWORD
            - name: DATABASE_URL                # 3) composed from vars defined ABOVE
              value: "postgres://$(DB_USER):$(DB_PASSWORD)@$(DB_HOST):$(DB_PORT)/$(DB_NAME)"
            - name: POD_NAME                    # 4) downward API: who am I?
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: POD_IP
              valueFrom:
                fieldRef:
                  fieldPath: status.podIP
            - name: NODE_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName
            - name: MEMORY_LIMIT_MB             # 5) my own memory limit, in MiB
              valueFrom:
                resourceFieldRef:
                  resource: limits.memory
                  divisor: 1Mi
          volumeMounts:
            - name: features                    # 6) ConfigMap as a file
              mountPath: /etc/taskflow
              readOnly: true
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          readinessProbe:
            httpGet: { path: /health, port: http }
            periodSeconds: 5
      volumes:
        - name: features
          configMap:
            name: taskflow-features

Key takeaway

Precedence: env beats envFrom; among several envFrom sources the last one wins. Order inside env matters only for $(VAR) references.

Recap Env vars come from literals, ConfigMaps, Secrets, the downward API and resource fields. Compose with $(VAR). Verify with kubectl exec ... -- env and kubectl describe pod.

★ Putting it all together

The big idea

The ingress-nginx controller is TaskFlow's single front door: it terminates TLS with the taskflow-tls Secret, routes taskflow.local to the web Service, /api/* and api.taskflow.local to the API Service, and those Services pick the Pods. The image stays the same in every environment — taskflow-config supplies settings, taskflow-db-secret supplies credentials, and the Deployment turns both (plus downward-API facts) into env vars and files, composing DATABASE_URL on the way. Change config → restart for env, wait for files.

Quick self-check

You applied an Ingress but kubectl get ingress shows no ADDRESS and curl gets "connection refused". Most likely cause?

No Ingress Controller is running (or ingressClassName doesn't match one). The Ingress object alone does nothing — minikube addons enable ingress.

Path /api(/|$)(.*) with rewrite-target: /$2. What path does the API receive for /api/tasks/7?

/tasks/7 — group 2 is tasks/7, prefixed by /.

Does pathType: Prefix, path: /api match /apis? And /api/?

/apis: no (prefix matching is per path element). /api/: yes.

Is a Kubernetes Secret encrypted? What does data.POSTGRES_PASSWORD: czNjcjN0LVRmOXg= protect against?

Only base64-encoded by default (encrypted in etcd only if encryption at rest is configured). base64 protects against nothing — base64 -d reveals s3cr3t-Tf9x. Protection comes from RBAC + encryption at rest.

You changed LOG_LEVEL in the ConfigMap. The mounted features.json updated by itself but the env var didn't. Why, and what do you run?

Env vars are set once at container start; projected volume files are refreshed by the kubelet. Run kubectl rollout restart deployment/taskflow-api.

A Pod is stuck in CreateContainerConfigError. Name two likely causes.

A referenced ConfigMap/Secret doesn't exist in the Pod's namespace, or a referenced key is missing (and optional isn't set).

Why echo -n when base64-encoding a password?

Plain echo adds a newline, which gets encoded into the value (...Zsb3cK instead of ...Zsb3c=), so the stored password ends with \n and authentication fails.
