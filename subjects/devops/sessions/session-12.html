1 Ingress & Ingress Controllers

The problem

TaskFlow now has two things users need: the website (taskflow-web, nginx serving the frontend) and the API (taskflow-api). With Session 11's tools, each gets its own LoadBalancer Service:

taskflow-web   LoadBalancer   EXTERNAL-IP 13.233.41.7     → cloud load balancer #1, billed per hour
taskflow-api   LoadBalancer   EXTERNAL-IP 13.126.200.18   → cloud load balancer #2, billed per hour
                                                            + a TLS certificate on each

Two IPs, two bills, two certificates, and a third set the day you add an admin app. What you want is one name, taskflow.local, with / going to the website and /api/… to the API. A LoadBalancer Service can't do that. It works at layer 4 and only sees "a TCP connection to port 443". It never reads the URL.

The idea

An Ingress is a set of HTTP routing rules stored in the cluster: "requests for this host and this path go to that Service". An Ingress Controller is a reverse proxy (usually nginx) running as pods. It reads those rules and does the routing. You put one load balancer in front of the controller, and the controller fans requests out by host and path.

 browser: https://taskflow.local/api/tasks
        │   one IP, one load balancer
        ▼
 ┌──── Ingress Controller pod (ingress-nginx) ────┐   watches   ┌─────────────────────────┐
 │  reads Host + path, terminates TLS             │◀────────────│ Ingress objects (rules) │
 └──────────┬───────────────────────┬─────────────┘             └─────────────────────────┘
     /api/* │                     / │
            ▼                       ▼
 Service taskflow-api:80     Service taskflow-web:80
            ▼                       ▼
     api pods :3000           web pods :80

Notice the two halves. The Ingress object is only data. The controller is the program that acts on it. You need both.

Think of it like this

An office building with one front door. The Ingress is the directory board in the lobby ("API team: floor 2 · Website: floor 1"). The Ingress Controller is the receptionist who reads each letter's address and walks it to the right floor. A board with no receptionist helps nobody, and a receptionist with no board sends every letter back (404). Each floor's front desk is a Service, and the people behind it are the pods. This building comes back in every section.

See it: an Ingress with no controller

Commands on this page assume taskflow is your default namespace (kubectl config set-context --current --namespace=taskflow, Session 10). First, a stand-in website so the Ingress has something to route to:

$ kubectl create deployment taskflow-web --image=nginx:1.27-alpine
deployment.apps/taskflow-web created
$ kubectl expose deployment taskflow-web --port=80
service/taskflow-web exposed              # ClusterIP Service, port 80, selector app=taskflow-web

Now the smallest useful Ingress, which sends every request to that Service:

web-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx        # which controller should handle this Ingress
  rules:
    - http:                      # no "host:" = any host name
        paths:
          - path: /
            pathType: Prefix     # "/" as a prefix = every path
            backend:
              service:
                name: taskflow-web
                port:
                  number: 80     # the SERVICE's port, not the pod's
FieldMeaning
networking.k8s.io/v1The only Ingress API since Kubernetes 1.22. Old tutorials' extensions/v1beta1 is rejected.
ingressClassNameNames the controller (via its IngressClass). A cluster can run several.
rules[].http.paths[].backendThe routing table: match a path, send it to a Service in the same namespace. §2 adds hosts.
 
$ kubectl apply -f web-ingress.yaml
ingress.networking.k8s.io/web created
$ kubectl get ingress web
NAME   CLASS   HOSTS   ADDRESS   PORTS   AGE
web    nginx   *                 80      30s                 # ADDRESS is empty
$ kubectl get ingressclass
No resources found

The API server accepted the object, yet ADDRESS stays empty and nothing listens on port 80. No controller is installed, so nobody reads the rules. That's the missing receptionist.

The controller found the rule and published its address. It doesn't go through the Service's ClusterIP: it reads the Service's EndpointSlices (Session 11) and proxies straight to pod IPs.

What it does not do: an Ingress creates no pods, Services or load balancers, and it can't carry non-HTTP traffic such as Postgres on 5432. On a cloud cluster the controller's own Service is the single LoadBalancer.

The exam table

LoadBalancer ServiceIngress (+ controller)
OSI layerL4 (TCP/UDP)L7 (HTTP/HTTPS)
Routes byPort onlyHost name + URL path
Cloud load balancersOne per ServiceOne for the whole cluster (the controller's)
TLSPer Service, in the app or the LBTerminated once at the Ingress
ProtocolsAnything (Postgres, gRPC, raw TCP)HTTP(S) only
Without the other halfn/aRules but no controller: ADDRESS empty · controller but no rules: 404 for everything

Common controllers and their ingressClassName: ingress-nginx → nginx (minikube addon) · Traefik → traefik (k3s default) · AWS Load Balancer Controller → alb (each Ingress becomes an AWS ALB) · GKE gce, Azure azure-application-gateway, plus HAProxy, Kong and Contour. If you omit ingressClassName, only an IngressClass annotated ingressclass.kubernetes.io/is-default-class: "true" picks the Ingress up, so always set it. The old kubernetes.io/ingress.class annotation is deprecated.

Status in 2026

The Ingress API is stable but feature-frozen. Kubernetes recommends Gateway API (Gateway + HTTPRoute) for new designs. The community ingress-nginx controller was retired (no fixes after March 2026). It's fine for learning on minikube. For production, pick a maintained controller.

Exam trap

"Creating an Ingress exposes my app." ✗ Only if a controller with a matching class is running. Without one, the Ingress is inert data.

"Ingress replaces Services." ✗ Every Ingress backend is a Service. The controller uses that Service's endpoints.

"Put Postgres behind the Ingress so I can reach it from my laptop." ✗ Ingress is HTTP(S) only. Use kubectl port-forward, a NodePort or a LoadBalancer for raw TCP.

Remember

Ingress = the rules (data) · Ingress Controller = the proxy that obeys them.
No controller → no ADDRESS → nothing happens.

Mastery check
Q1. On a fresh kind cluster you apply web-ingress.yaml. Predict kubectl get ingress web, and explain it.

Listed with CLASS nginx but an empty ADDRESS. kind ships no Ingress Controller, so nothing watches the object. Install one and the ADDRESS appears.

Q2. Your professor says: "An Ingress is a fourth Service type, after ClusterIP, NodePort and LoadBalancer." True or false?

False. Ingress is a separate kind (networking.k8s.io/v1, kind: Ingress) that sits in front of Services and routes HTTP to them. Service types are L4. Ingress is L7.

Q3. A cluster runs ingress-nginx and Traefik. Your Ingress has ingressClassName: traefik. Which controller serves it, and what does the other one do?

Traefik serves it. ingress-nginx ignores it because the class isn't nginx. That's exactly what the field is for.

Q4. Fill in: a LoadBalancer Service routes at layer ____ by ____; an Ingress routes at layer ____ by ____ and ____.

4 · port · 7 · host name · URL path.

2 Host & path-based routing

The problem

One front door now exists, but everything behind it goes to the website. TaskFlow needs three URL shapes on one IP:

http://taskflow.local/             → website  (taskflow-web)
http://taskflow.local/api/tasks    → API      (taskflow-api), which only knows "/tasks"
http://api.taskflow.local/health   → API      (for the mobile app and partners)

The controller has to tell these apart, and the only clues it has are inside the HTTP request itself.

The idea

Every HTTP request carries a path and the host name the client typed:

GET /api/tasks HTTP/1.1         ← path-based routing reads the path here
Host: taskflow.local            ← host-based routing reads this header

Host-based routing picks a backend by the Host header (rules[].host). Path-based routing picks one by URL path (paths[].path + pathType). You can combine them: one host with several paths. Here's the table TaskFlow's controller will hold by the end of this section:

 Host taskflow.local       path /api/…  ──▶  Service taskflow-api:80  (path rewritten to /…)
 Host taskflow.local       path /       ──▶  Service taskflow-web:80
 Host api.taskflow.local   path /       ──▶  Service taskflow-api:80
 anything else                          ──▶  controller's default backend: 404
Think of it like this

The receptionist reads two parts of each address. The host is the company name (which floor). The path is the department line ("/api: the API desk"). Path rewriting is the receptionist crossing out "/api" before handing the letter over, because the API desk doesn't know it's called "/api" in the lobby.

See it: host-based routing

Remove the catch-all from §1, then apply the first half of TaskFlow's real Ingress (two host rules):

$ kubectl delete ingress web
ingress.networking.k8s.io "web" deleted
$ kubectl apply -f k8s/ingress.yaml          # the "taskflow" object below
$ curl -H "Host: api.taskflow.local" http://$(minikube ip)/health
{"status":"ok"}
$ curl -s -H "Host: taskflow.local" http://$(minikube ip)/ | grep title
<title>Welcome to nginx!</title>               # same IP, other host → the website
$ curl -i http://$(minikube ip)/              # Host is just the IP: no rule matches
HTTP/1.1 404 Not Found
…
<center><h1>404 Not Found</h1></center>
<hr><center>nginx</center>

-H "Host: …" sends the header a browser would send for that name, while the connection goes to the node IP where the controller listens (-i prints the status line). The 404 page signed "nginx" comes from the controller, not from TaskFlow.

What it does not do: make the names resolve. curl http://api.taskflow.local/health fails with Could not resolve host. The Ingress only matches names. DNS is your job, and locally that means /etc/hosts:

# Linux / VM drivers: point the names at the node IP
$ echo "$(minikube ip) taskflow.local api.taskflow.local" | sudo tee -a /etc/hosts
192.168.49.2 taskflow.local api.taskflow.local
# macOS / Windows with the Docker driver: the node IP isn't reachable, so tunnel and use 127.0.0.1
$ minikube tunnel                         # keep this terminal open (asks for sudo to bind 80/443)
$ echo "127.0.0.1 taskflow.local api.taskflow.local" | sudo tee -a /etc/hosts

Build it up: path-based routing

First attempt: add path: /api (Prefix) → taskflow-api under the taskflow.local host. It routes, but:

$ curl -s http://taskflow.local/api/tasks | grep pre
<pre>Cannot GET /api/tasks</pre>           # Express's 404: the API has /tasks, not /api/tasks

The controller forwards the path unchanged, and the API doesn't know it lives under /api. This is the most common Ingress bug. The fix is a path rewrite, in a second Ingress object (why separate: see the table):

k8s/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: taskflow
  namespace: taskflow                 # backends must be Services in THIS namespace
spec:
  ingressClassName: nginx
  rules:
    - host: taskflow.local            # HOST rule 1: the website
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: taskflow-web
                port:
                  number: 80
    - host: api.taskflow.local        # HOST rule 2: the API on its own subdomain
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: taskflow-api
                port:
                  name: http          # the Service port named "http" (= 80)
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: taskflow-api-path
  namespace: taskflow
  annotations:                        # controller-specific options live in annotations
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2   # send only capture group 2 upstream
spec:
  ingressClassName: nginx
  rules:
    - host: taskflow.local            # PATH rule: same host, /api/... → API
      http:
        paths:
          - path: /api(/|$)(.*)       # group 1 = "/" or end, group 2 = the rest
            pathType: ImplementationSpecific   # regex needs this, not Prefix
            backend:
              service:
                name: taskflow-api
                port:
                  number: 80
FieldMeaningGotcha
rules[].hostMatch the Host header. Omit = any host. Wildcards like *.taskflow.local are allowed.A DNS name only: no IPs, no ports.
paths[].path + pathTypeURL path to match and how (table below). pathType is required.Starts with /, except regexes under ImplementationSpecific.
backend.service.portThe Service port: number: 80 or name: http.Not 3000. That's the targetPort, which the Service handles.
rewrite-target: /$2ingress-nginx replaces the upstream path with capture group 2.Applies to every path in that Ingress object, which is why it lives in its own object.
use-regex: "true"Treat paths as regular expressions.ingress-nginx then treats all paths for that host, across Ingress objects, as case-insensitive regexes.
 
$ kubectl apply -f k8s/ingress.yaml
ingress.networking.k8s.io/taskflow configured
ingress.networking.k8s.io/taskflow-api-path created
$ kubectl describe ingress taskflow | sed -n '/Rules:/,$p'
Rules:
  Host                Path  Backends
  ----                ----  --------
  taskflow.local
                      /   taskflow-web:80 (10.244.0.21:80)
  api.taskflow.local
                      /   taskflow-api:http (10.244.0.13:3000,10.244.0.14:3000,10.244.0.15:3000)  # pod IPs = endpoints found
$ curl http://taskflow.local/api/health    # path rule: the API receives "/health"
{"status":"ok"}

How the rewrite maps paths, and which rule wins

Group 2 is everything after /api/, so /api → /, /api/tasks → /tasks, and /api/tasks/7?done=true → /tasks/7?done=true (the query string is kept).

pathType, path /api/api/api//api/tasks/apis/API
Exact✔✘✘✘✘
Prefix✔✔✔✘ (not a whole path element)✘ (case-sensitive)
ImplementationSpecificThe controller decides. ingress-nginx: a regex when use-regex or rewrite-target is set.

When several paths match, the longest wins, and on a tie Exact beats Prefix. So /api/tasks goes to the API even though / also matches it.

Exam trap

"The backend port is the container port, 3000." ✗ It's the Service's port (80, or its name http). The Service maps that to targetPort 3000.

"Prefix /api also matches /apis." ✗ Prefix matching works on whole path elements split by /.

"An Ingress can route to a Service in another namespace." ✗ Backends must be in the Ingress's namespace. Create the Ingress where the Service lives.

"A 503 from the Ingress means the rule is wrong." ✗ 503 means a rule matched but its Service has no ready endpoints (Session 11's selector bug, or pods failing readiness). No matching rule gives 404.

Remember

host = which site · path = which part of it · longest path wins.
Backends point at Service ports. Rewrite when the app doesn't know its prefix.

Mastery check
Q1. With the final k8s/ingress.yaml, what path does the API receive for http://taskflow.local/api/tasks/7? And for http://api.taskflow.local/tasks/7?

/tasks/7 both times. The first matches the regex rule, and rewrite-target: /$2 strips /api. The second matches host rule 2 (/ Prefix), which forwards the path unchanged.

Q2. Predict: curl http://$(minikube ip)/api/health with no Host header. Which rule matches?

None. Every rule has a host:, and the Host header is the bare IP, so the controller's default backend answers 404. Add -H "Host: taskflow.local".

Q3. Paths / (Prefix → web) and /api (Exact → api) on one host. Where does /api/tasks go?

To the web Service. Exact /api matches only /api itself, so the only match left is / Prefix. Use Prefix (or the regex rule) for a whole subtree.

3 TLS for Ingress

The problem

Everything above is plain HTTP. On the college Wi-Fi, anyone running a packet sniffer sees each TaskFlow request word for word:

POST /api/tasks HTTP/1.1
Host: taskflow.local
Cookie: session=4f9c2e…            ← copy this and you're logged in as that user
{"title":"Submit DevOps project"}

You could add certificates to every app, but then every pod holds the private key and every renewal means redeploying every service.

The idea

TLS termination at the Ingress: the browser speaks HTTPS to the controller, which decrypts and forwards plain HTTP to the pods. The certificate and private key live in one Secret of type kubernetes.io/tls (keys tls.crt and tls.key), in the same namespace as the Ingress.

 browser ══ HTTPS: encrypted, cert checked ══▶ ingress-nginx ── plain HTTP ──▶ taskflow-api pods
                                                   │
                                     reads Secret taskflow-tls (tls.crt + tls.key)
                                     named in the Ingress's spec.tls[].secretName
Think of it like this

Letters now arrive in sealed envelopes. The receptionist shows visitors the building's ID card (the certificate) and holds the only letter-opener (the private key). She opens each envelope at the front desk, then carries the letter upstairs inside the building as normal. Teams upstairs never handle envelopes or keys.

See it: make a certificate

Locally there's no public CA to sign for taskflow.local, so you make a self-signed one:

$ openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
    -keyout taskflow.key -out taskflow.crt \
    -subj "/CN=taskflow.local" \
    -addext "subjectAltName=DNS:taskflow.local,DNS:api.taskflow.local"
.......+.......+.....+++++++++++++++++++++++++++++++++++++++*...+.......
-----
$ openssl x509 -in taskflow.crt -noout -ext subjectAltName     # check the host names
X509v3 Subject Alternative Name:
    DNS:taskflow.local, DNS:api.taskflow.local
TokenMeaning
req -x509Output a self-signed certificate instead of a signing request
-nodes"No DES": don't encrypt the private key (OpenSSL 3 also accepts -noenc). The controller must read it without a passphrase.
-days 365 -newkey rsa:2048Valid for one year, with a new 2048-bit RSA key
-keyout / -outWhere to write the private key / the certificate
-subj "/CN=…"The subject, given inline so there are no prompts
-addext subjectAltName=…The host names the cert is valid for. Browsers and curl check the SAN, not the CN. Needs OpenSSL 1.1.1+ or LibreSSL 3.x.

What it does not do: make anyone trust it. The cert is signed by itself, so browsers and curl will refuse it until you trust it explicitly. That's fine for learning and wrong for production.

Build it up: Secret → tls block → HTTPS

$ kubectl create secret tls taskflow-tls --cert=taskflow.crt --key=taskflow.key
secret/taskflow-tls created
$ kubectl get secret taskflow-tls
NAME           TYPE                DATA   AGE
taskflow-tls   kubernetes.io/tls   2      5s                # DATA 2 = tls.crt + tls.key
k8s/ingress.yaml (spec of Ingress "taskflow")
spec:
  ingressClassName: nginx
  tls:                                # NEW: which hosts get HTTPS, with which cert
    - hosts:
        - taskflow.local              # must match rules[].host AND the cert's SAN
        - api.taskflow.local
      secretName: taskflow-tls        # kubernetes.io/tls Secret, same namespace
  rules:
    # ... unchanged ...

Add the same block (hosts: taskflow.local) to taskflow-api-path, then apply:

$ kubectl apply -f k8s/ingress.yaml && kubectl get ingress taskflow
ingress.networking.k8s.io/taskflow configured
ingress.networking.k8s.io/taskflow-api-path configured
NAME       CLASS   HOSTS                               ADDRESS        PORTS     AGE
taskflow   nginx   taskflow.local,api.taskflow.local   192.168.49.2   80, 443   20m
$ curl -I http://taskflow.local/                # once TLS is set, ingress-nginx redirects HTTP
HTTP/1.1 308 Permanent Redirect
Location: https://taskflow.local/
$ curl https://api.taskflow.local/health
curl: (60) SSL certificate problem: self-signed certificate      # expected: nobody trusts it yet
$ curl --cacert taskflow.crt https://api.taskflow.local/health      # trust this one cert
{"status":"ok"}
$ curl -k https://taskflow.local/api/health     # -k = skip verification (testing only)
{"status":"ok"}

PORTS now shows 80, 443. Port 80 stays open only to send the 308 redirect.

Real certificates: cert-manager

cert-manager is a controller that obtains and renews certificates (e.g. from Let's Encrypt) and writes them into the TLS Secret. Install it, create a ClusterIssuer, then annotate the Ingress:

metadata:
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod   # which issuer to ask
spec:
  tls:
    - hosts: [taskflow.example.com]                   # must be a real public domain for Let's Encrypt
      secretName: taskflow-tls                        # cert-manager creates and renews this Secret
Exam trap

"With TLS on the Ingress, traffic is encrypted all the way to the pod." ✗ It's decrypted at the controller. The controller → pod hop is plain HTTP inside the cluster (unless you add a service mesh or re-encrypt to the backend).

"Browsers check the certificate's CN." ✗ They check the SAN list. A cert without subjectAltName fails even when the CN is right.

"The TLS Secret can live in the ingress-nginx namespace." ✗ secretName refers to a Secret in the Ingress's own namespace.

Remember

openssl req -x509 → kubectl create secret tls → spec.tls[].hosts + secretName.
TLS ends at the Ingress. HTTP gets a 308 to HTTPS.

Mastery check
Q1. The browser shows "Kubernetes Ingress Controller Fake Certificate". Give three likely causes.

The controller couldn't use your Secret, so it fell back to its built-in cert: secretName is misspelled, the Secret is in another namespace, or the host isn't in tls.hosts / the cert's SAN.

Q2. Predict curl -I http://taskflow.local/ before and after adding the tls: block.

Before: 200 OK. After: 308 Permanent Redirect to https://taskflow.local/, because ingress-nginx redirects HTTP to HTTPS for TLS hosts by default.

Q3. You make a cert with only -subj "/CN=taskflow.local" (no -addext). curl --cacert taskflow.crt https://taskflow.local/ still fails. Why?

Modern clients ignore the CN and match the host against the Subject Alternative Name list, which is missing. Re-create the cert with -addext "subjectAltName=DNS:taskflow.local,…".

Q4. Fill in: a TLS Secret has type ________ and exactly two keys, ________ and ________.

kubernetes.io/tls · tls.crt · tls.key.

4 ConfigMaps

The problem

TaskFlow's settings are currently baked into the image. Dev wants verbose logs, prod doesn't, so you end up building two images:

shauryav/taskflow-api:1.1.0-dev    LOG_LEVEL=debug   NODE_ENV=development
shauryav/taskflow-api:1.1.0-prod   LOG_LEVEL=info    NODE_ENV=production
                                   → different digests (Session 6)

Now the image you tested isn't the image you ship, and changing one log level means a rebuild, a push and a deploy. Config belongs next to the image, not inside it.

The idea

A ConfigMap stores non-secret settings as key/value strings (up to 1 MiB). Pods consume it as environment variables or as files in a volume. Same image everywhere, a different ConfigMap per environment: the 12-factor "config in the environment" rule.

                       ConfigMap taskflow-config
                       LOG_LEVEL: info   NODE_ENV: production …
                          │                         │
           env / envFrom  │                         │  volume
                          ▼                         ▼
      container env: LOG_LEVEL=info      file: /etc/taskflow/features.json
                └──────── same image: shauryav/taskflow-api:1.1.0 ────────┘
Think of it like this

Every desk gets an instruction card: "log level: info, database: taskflow-db". The worker (the image) is identical everywhere. Only the card differs between the dev building and the prod building. Cards are written in pencil and anyone can read them, so a password never goes on one (§5).

See it: the smallest ConfigMap

$ kubectl create configmap demo-literal --from-literal=LOG_LEVEL=info --from-literal=NODE_ENV=production
configmap/demo-literal created
$ kubectl get configmap demo-literal -o yaml      # trimmed
apiVersion: v1
data:
  LOG_LEVEL: info
  NODE_ENV: production
kind: ConfigMap
metadata:
  name: demo-literal
  namespace: taskflow

create configmap demo-literal makes the object in the current namespace. Each --from-literal=KEY=value adds one key. -o yaml shows what's stored: your settings, under data:, in plain text.

What it does not do: reach any pod. A ConfigMap does nothing until a pod spec references it, and containers only read it when they start (more on that below).

Build it up

Two more ways to create one

$ cat features.json
{ "enableSignup": true, "maxTasksPerUser": 100 }
$ kubectl create configmap taskflow-features --from-file=features.json    # key = file name
configmap/taskflow-features created
$ kubectl create configmap demo-env --from-env-file=app.env       # each KEY=value line → one key

Add --dry-run=client -o yaml to print the YAML instead of creating the object. The declarative version that goes in the repo:

k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: taskflow-config
  namespace: taskflow
  labels:
    app: taskflow-api
data:                                 # every value is a STRING
  NODE_ENV: production
  LOG_LEVEL: info
  PORT: "3000"                         # quote numbers and booleans
  DB_HOST: taskflow-db                # the Service from Session 11
  DB_PORT: "5432"
  DB_NAME: taskflow
# immutable: true                     # optional: data can't be edited, only replaced
  • data maps string keys (letters, digits, - _ .) to string values. Unquoted PORT: 3000 fails with cannot unmarshal number into Go struct field ConfigMap.data of type string.
  • Embed a whole file with key: | plus an indented block. binaryData takes base64. With immutable: true you create taskflow-config-v2 instead of editing, which is safer and lighter on the API server.

Three ways to consume it

Exam trap

"Editing a ConfigMap updates the env vars of running pods." ✗ Env is read once at start. Only mounted files (without subPath) refresh.

"ConfigMap values can be numbers or booleans." ✗ They're always strings. Quote "3000" and "true".

Mastery check
Q1. Spot the bug: data: { PORT: 3000, ENABLE_SIGNUP: true } in a ConfigMap.

Both values must be strings. kubectl apply rejects the file (cannot unmarshal number …). Write PORT: "3000" and ENABLE_SIGNUP: "true".

Q2. You patch LOG_LEVEL to debug and wait five minutes. printenv LOG_LEVEL in the pod still says info. Broken cluster?

No, that's expected. Env vars are copied in when the container starts. Run kubectl rollout restart deployment/taskflow-api so new pods start with the new value.

Q3. envFrom: configMapRef or a volume mount for features.json: which one, and why?

A volume mount. It's a structured file the app reads with a JSON parser, and mounted files update in place without a restart (if the app re-reads them). envFrom suits flat KEY=value settings.

5 Secrets

The problem

Session 11's k8s/postgres.yaml still carries the database password in plain text, and anyone who can read the Deployment can read the password:

$ kubectl get deploy taskflow-db -o yaml | grep -A1 POSTGRES_PASSWORD
        - name: POSTGRES_PASSWORD
          value: changeme                 # also committed to GitHub, forever, in the history

The API needs the same password in its DATABASE_URL. You want it out of Git, the image and the Deployment YAML, while both pods still get it.

The idea

A Secret is a ConfigMap for sensitive values: passwords, tokens, TLS keys, registry credentials (up to 1 MiB). Kubernetes handles them more carefully: sent only to nodes running a pod that uses them, kept in tmpfs when mounted, hidden in describe. Values are stored base64-encoded, and base64 is not encryption.

 kubectl create secret ─▶ API server ─▶ etcd       (base64; encrypted ONLY if encryption at rest is on)
                             │ only to nodes running a pod that references it
                             ▼
                      kubelet on that node ─▶ container: env var DATABASE_URL=postgres://…
                                            └▶ or file in a tmpfs volume (never touches disk)
Think of it like this

If the ConfigMap is the pencil card on the desk, a Secret is a sealed envelope in a drawer. The catch: the envelope is see-through (base64), so the real protection is who holds the drawer key (RBAC) and whether the building's safe is locked (encryption at rest).

See it: create one, then read it back

$ kubectl create secret generic taskflow-db-secret \
    --from-literal=POSTGRES_PASSWORD='tf-pass-2026' \
    --from-literal=DATABASE_URL='postgres://taskflow:tf-pass-2026@taskflow-db:5432/taskflow'
secret/taskflow-db-secret created
$ kubectl describe secret taskflow-db-secret
Name:         taskflow-db-secret
Namespace:    taskflow
Type:  Opaque

Data
====
DATABASE_URL:       58 bytes
POSTGRES_PASSWORD:  12 bytes                       # sizes only, never values
$ kubectl get secret taskflow-db-secret -o jsonpath='{.data.POSTGRES_PASSWORD}' | base64 -d
tf-pass-2026
TokenMeaning
create secret genericAn Opaque Secret: arbitrary keys (the tls and docker-registry subcommands make the typed ones)
--from-literal=K='v'One key per flag. Single quotes stop the shell from touching special characters.
-o jsonpath='{.data.POSTGRES_PASSWORD}'Print just that field, which is base64
| base64 -dDecode it. Three commands from "hidden" to plain text.

Creating Secrets imperatively is the safe default, because there's no file to commit by accident. Sessions 13, 17 and 23 make this same Secret the same way.

What it does not do: encrypt anything. Anyone allowed to get secrets here can do what you just did.

Build it up

The YAML form, and why echo -n

$ echo -n 'tf-pass-2026' | base64
dGYtcGFzcy0yMDI2
$ echo 'tf-pass-2026' | base64             # without -n, echo's newline is encoded too
dGYtcGFzcy0yMDI2Cg==                      # = "tf-pass-2026\n" → Postgres login fails, very hard to spot
k8s/secret.yaml (local/dev only: git-ignored; commit a secret.example.yaml with placeholders)
apiVersion: v1
kind: Secret
metadata:
  name: taskflow-db-secret
  namespace: taskflow
type: Opaque                          # generic key/value Secret
data:                                 # values MUST be base64
  POSTGRES_PASSWORD: dGYtcGFzcy0yMDI2  # "tf-pass-2026"
  DATABASE_URL: cG9zdGdyZXM6Ly90YXNrZmxvdzp0Zi1wYXNzLTIwMjZAdGFza2Zsb3ctZGI6NTQzMi90YXNrZmxvdw==

Plain text under data: is rejected (illegal base64 data at input byte …). Plain text goes under stringData:, which the API server encodes into data for you. It's write-only, and it wins if a key is in both:

stringData:                           # replaces the data: block above
  POSTGRES_PASSWORD: tf-pass-2026
  DATABASE_URL: postgres://taskflow:tf-pass-2026@taskflow-db:5432/taskflow

Postgres reads its password from the Secret

k8s/postgres.yaml (container excerpt: replaces Session 11's plain-text value)
        - name: postgres
          image: postgres:16
          env:
            - name: POSTGRES_USER
              value: taskflow
            - name: POSTGRES_DB
              value: taskflow
            - name: POSTGRES_PASSWORD         # was "value: changeme"
              valueFrom:
                secretKeyRef:
                  name: taskflow-db-secret
                  key: POSTGRES_PASSWORD

The Deployment YAML now holds only a reference, so it's safe to commit. The API reads DATABASE_URL from the same Secret in §6.

Keeping Secrets secret

  • Never commit real Secrets: Git history is forever. RBAC: only the app's ServiceAccount and admins may get/list Secrets (Session 16).
  • Encryption at rest: enable an API-server EncryptionConfiguration (a KMS provider on EKS/GKE/AKS). By default etcd holds base64.
  • External Secrets Operator syncs the value from AWS Secrets Manager or Vault. Sealed Secrets (kubeseal) encrypts it into a SealedSecret that is safe to commit (GitOps, Session 22).
  • Prefer volume mounts for very sensitive values, since env vars leak into crash dumps and child processes. Rotate: update the Secret, rollout restart, and change the password in the database too.

Exam trap

"Kubernetes Secrets are encrypted." ✗ They're base64-encoded, encrypted in etcd only if an admin enabled encryption at rest, and always plain text inside the container.

"base64 makes secret.yaml safe to push." ✗ base64 -d reverses it instantly. If it happened, rotate the password first, then clean the history.

"Only admins can read a Secret." ✗ Anyone allowed to get secrets, or to create a pod that mounts it, can read it.

Remember

Secret = base64, not encryption. Protection = RBAC + encryption at rest + keeping it out of Git.
Always echo -n before base64.

Mastery check
Q1. A teammate's secret.yaml has POSTGRES_PASSWORD: dGYtcGFzcy0yMDI2Cg== and Postgres logins fail with the "right" password. What's wrong?

The trailing Cg== is an encoded newline: the value is tf-pass-2026\n. It was made with echo instead of echo -n. Re-encode with echo -n, or use stringData or kubectl create secret.

Q2. Predict: you apply a Secret with data: { POSTGRES_PASSWORD: tf-pass-2026 }.

It's rejected with illegal base64 data at input byte …, because data must be base64 and - isn't a base64 character. Put plain text under stringData instead.

Q3. Pods in taskflow must pull ghcr.io/shauryav/taskflow-api:1.1.0 (a private package). Which Secret type, which command, and which pod field?

kubernetes.io/dockerconfigjson, made with kubectl create secret docker-registry ghcr-cred --docker-server=ghcr.io … in the pods' namespace, then referenced in spec.imagePullSecrets (or attached to the namespace's default ServiceAccount).

6 Environment variables

The problem

The API container needs four kinds of information at startup, from four different places:

DATABASE_URL     → lives in the Secret taskflow-db-secret
LOG_LEVEL, PORT… → live in the ConfigMap taskflow-config
POD_NAME         → "which replica served this?" It's random (taskflow-api-7d9c5b8f4c-k2xvp),
                   so you can't write it into YAML
MEMORY_LIMIT_MB  → Node should size its heap to the container's memory limit

The app itself should just read process.env and know nothing about Kubernetes.

The idea

The kubelet assembles the container's environment before the process starts, from five kinds of source declared in the pod spec:

 literal value ─────────────┐
 ConfigMap (key or all keys) ┤
 Secret    (key or all keys) ┼──▶ kubelet builds the env ──▶ node server.js reads process.env
 downward API (pod facts) ───┤      (once, at container start)
 resource fields (limits) ───┘
Think of it like this

Before a worker arrives, the receptionist sets their desk: your sticky note (literal), a line from the instruction card (ConfigMap), a note from the sealed envelope (Secret), a name badge (downward API) and "your drawer holds 256 MiB" (resource field). The worker reads the desk once, at the start of the shift.

See it: one value Kubernetes fills in

          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name      # this pod's own name
$ kubectl exec taskflow-api-7d9c5b8f4c-k2xvp -- printenv POD_NAME
taskflow-api-7d9c5b8f4c-k2xvp

valueFrom means "look the value up". fieldRef is the downward API: facts about the pod itself, such as metadata.name, metadata.namespace, status.podIP and spec.nodeName. Each replica gets its own name, so logs can say which pod handled a request.

What it does not do: stay live. If something it points at changes later (a label, say), the env var keeps its start-time value.

Build it up: TaskFlow's API, fully wired

k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment

  name: taskflow-api

    app: taskflow-api

  selector:
    matchLabels:
      app: taskflow-api

        app: taskflow-api                 # the Service taskflow-api selects this

      containers:

          ports:
            - name: http
              containerPort: 3000

                  name: taskflow-db-secret

            - name: POD_NAME                    # 3) downward API: who am I?

Composing a variable from others

If the Secret held only the password, you could build DATABASE_URL from pieces. $(VAR) is replaced with the value of a variable defined earlier (including ones from envFrom):

            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef: { name: taskflow-db-secret, key: POSTGRES_PASSWORD }
            - name: DATABASE_URL
              value: "postgres://taskflow:$(DB_PASSWORD)@$(DB_HOST):$(DB_PORT)/$(DB_NAME)"

An undefined name stays as literal text, $$ escapes a dollar sign, and the password must be URL-safe. Precedence: env beats envFrom, and among several envFrom sources the last one wins.

Exam trap

"$(VAR) can refer to a variable defined further down the list." ✗ Only to ones defined earlier (or from envFrom). Otherwise it stays as literal text.

"If a key is in both envFrom and env, envFrom wins." ✗ env wins.

"kubectl describe pod hides the password, so people with exec access can't see it." ✗ kubectl exec … -- env prints it.

Remember

Five sources: value · configMapKeyRef/envFrom · secretKeyRef/envFrom · fieldRef · resourceFieldRef.
Built once at start · env beats envFrom · check with exec env + describe.

Mastery check
Q1. Spot the bug: DATABASE_URL uses $(DB_PASSWORD), but the DB_PASSWORD entry sits below it in env. What does the app receive?

The literal text postgres://taskflow:$(DB_PASSWORD)@taskflow-db:5432/taskflow, so the login fails. References only resolve to variables defined earlier. Move DB_PASSWORD above DATABASE_URL.

Q2. taskflow-config has LOG_LEVEL: info (via envFrom), and env also sets LOG_LEVEL: debug. Predict printenv LOG_LEVEL.

debug. Explicit env entries override keys imported by envFrom.

Q3. Which source gives each value: (a) the pod's IP, (b) 256 from limits.memory, (c) one key of taskflow-db-secret, (d) every key of taskflow-config?

(a) fieldRef: status.podIP · (b) resourceFieldRef with divisor: 1Mi · (c) secretKeyRef · (d) envFrom.configMapRef.

Q4. API pods show CreateContainerConfigError, and describe pod says Error: secret "taskflow-db-secret" not found. A teammate runs kubectl get secret taskflow-db-secret and it's there. How can both be true?

Secrets are namespaced. The teammate's default namespace is probably default, where they made it, but the pods run in taskflow. Create it with -n taskflow and the kubelet retries by itself. The other cause of this status is a missing key (Session 14).

★ Putting it all together

The big idea

The ingress-nginx controller is TaskFlow's single front door. It terminates TLS with the taskflow-tls Secret, then routes taskflow.local to the web Service, and /api/* and api.taskflow.local to the API Service. The image is the same everywhere: taskflow-config supplies the settings, taskflow-db-secret the credentials, and the Deployment turns both, plus downward-API facts, into env vars and files as each container starts. After a config change, restart for env vars or wait for mounted files.

Final mastery check — combine everything
Q1. Trace curl https://taskflow.local/api/tasks from your laptop to Postgres, naming every object it touches.

/etc/hosts → node IP (or 127.0.0.1 via the tunnel) → ingress-nginx does TLS with Secret taskflow-tls → Ingress taskflow-api-path's regex matches and rewrites to /tasks → Service taskflow-api:80's EndpointSlices → a ready pod on 3000 → DATABASE_URL (Secret taskflow-db-secret) → Service taskflow-db:5432 → the Postgres pod, whose POSTGRES_PASSWORD came from the same Secret.

Q2. After a deploy, https://taskflow.local/api/tasks returns 503 and the API pods show CreateContainerConfigError. Explain the chain from cause to the 503.

A referenced Secret or key is missing, so the containers never start → no pod becomes ready → the Service taskflow-api has no ready endpoints → ingress-nginx has nowhere to send the request and returns 503. Fix the Secret (describe pod names it). The kubelet retries and the 503 clears by itself.

Q3. "To keep it simple, put DB_HOST, LOG_LEVEL and the DB password in one ConfigMap and mount it with envFrom." Give two problems.

(1) The password is plain text, and kubectl describe configmap shows it to anyone who can read ConfigMaps. (2) You lose the Secret-only protections: tmpfs on nodes, separate RBAC for secrets, and encryption at rest. Split it: settings in taskflow-config, the password in taskflow-db-secret.

Q4. You edit both LOG_LEVEL in taskflow-config and features.json in taskflow-features. A minute later the file in /etc/taskflow is new, but LOG_LEVEL is old. Why the difference, and what do you run?

LOG_LEVEL arrived via envFrom, which is copied once at container start. features.json is a mounted ConfigMap volume, which the kubelet refreshes by flipping the ..data symlink. Run kubectl rollout restart deployment/taskflow-api.

Q5. A teammate pushes a Secret manifest for taskflow-tls (with tls.key) to a public repo, saying "it's base64, so it's fine". What exactly leaked, and what do you do?

The private key: base64 -d recovers it, so anyone can impersonate taskflow.local. Generate a new key and cert, replace the Secret (kubectl create secret tls … --dry-run=client -o yaml | kubectl apply -f -), purge the file from Git history and add *.key to .gitignore. In production, also revoke the old cert.

Q6. After adding the tls: block, curl -k https://taskflow.local/api/health works but curl -k https://api.taskflow.local/health shows the controller's fake certificate. Only Ingress taskflow-api-path has a tls: block. What's missing?

Ingress taskflow (which owns the api.taskflow.local rule) has no tls: entry for that host, so the controller doesn't know which cert to serve and falls back to its default. Add tls: [{hosts: [taskflow.local, api.taskflow.local], secretName: taskflow-tls}] to that Ingress too.
