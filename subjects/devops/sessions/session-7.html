1 Dockerfile & docker build

Explain like I'm 5

A Dockerfile is a recipe card. docker build follows it top to bottom and bakes an image; every step is a cake layer that can be reused next time.

  • A Dockerfile is a text file of instructions (FROM, RUN, COPY…). docker build turns it into an image.
  • The build context is the folder you pass (the final .). Only files in it can be COPY-ed; it is sent to the builder (BuildKit) first.
  • RUN, COPY, ADD add filesystem layers. Everything else (ENV, CMD, EXPOSE, USER…) only changes image metadata (0 B layers).
  • BuildKit is the default builder since Docker Engine 23; docker build = docker buildx build.
  • Comments: a line starting with #. A # after an instruction is not a comment — it becomes part of the arguments.

The app we're packaging — TaskFlow's dependency manifest:

package.json
{
  "name": "taskflow-api",
  "version": "1.0.0",
  "main": "server.js",
  "scripts": { "start": "node server.js", "test": "jest" },
  "dependencies":    { "express": "^5.1.0", "pg": "^8.13.1", "prom-client": "^15.1.3" },
  "devDependencies": { "jest": "^29.7.0", "supertest": "^7.0.0" }
}

dependencies are needed at runtime; devDependencies only for tests. npm ci --omit=dev installs just the first group, exactly as pinned in package-lock.json.

First working Dockerfile (single stage; we improve it in §6):

Dockerfile (v1)
# base image: Node 20 on Alpine Linux (~135 MB)
FROM node:20-alpine
# all following paths are relative to /app (created if missing)
WORKDIR /app
# dependency manifests first → the npm ci layer stays cached until they change
COPY package*.json ./
RUN npm ci --omit=dev
# then the source code (changes often)
COPY . .
ENV PORT=3000
EXPOSE 3000
USER node
CMD ["node", "server.js"]

  • WORKDIR /app # set dir — the "comment" becomes part of the path. Put comments on their own line.
  • Forgetting the trailing .: ERROR: "docker buildx build" requires exactly 1 argument.

Recap Dockerfile + context → docker build -t name:tag . → image. RUN/COPY/ADD = layers; the rest = metadata. Use docker history to see layers and sizes.

2 FROM, RUN, COPY (and ADD)

Explain like I'm 5

FROM picks the starting kitchen, RUN cooks something in it, COPY brings ingredients in from your bag.

FROM — the base image

  • Must be the first instruction (only ARG and parser directives like # syntax= may come before it).
  • Forms: FROM node:20-alpine · FROM node:20-alpine AS build (named stage) · FROM node:20-alpine@sha256:2d07… (pinned by digest — immutable).
  • Pin at least the major version. FROM node means node:latest → a new Node major can break your build overnight.
BaseWhat's inside~SizeShell / pkg mgrUse for
node:20Full Debian + gcc, python, git~1.1 GByes / aptBuild stages that compile native modules
node:20-slimMinimal Debian (glibc)~200 MByes / aptRuntime when a dependency needs glibc
node:20-alpineAlpine Linux (musl libc, busybox)~135 MByes / apkDefault small runtime
gcr.io/distroless/nodejs20-debian12Node + libs only; no shell, no package manager~130 MBno / noHardened runtime stage (fewer CVEs)
scratchEmpty0 Bno / noStatic binaries (Go, Rust)
Version note

Node 20 reached end-of-life in April 2026. The course uses 20 for consistency; for a real project use node:22-alpine or node:24-alpine — with the ARG NODE_VERSION trick (§3) it's a one-flag change.

RUN — execute a command at build time

  • Shell form RUN npm ci → runs /bin/sh -c "npm ci" (variables, &&, pipes work).
  • Exec form RUN ["npm", "ci"] → no shell. Rarely needed for RUN.
  • Each RUN is a new shell and a new layer. RUN cd /app does nothing for the next line — use WORKDIR.
  • Deleting a file in a later layer doesn't shrink the image — the earlier layer still contains it. Install and clean up in the same RUN.
Bad — 3 layers, stale cache, no size saving
FROM node:20-slim
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
Good — 1 layer, always-fresh index, cleaned
FROM node:20-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
PieceWhy
apt-get update && install togetherRUN's cache key is the command text. A separate cached apt-get update layer is reused forever → later installs hit a stale index ("Unable to locate package").
-yNo interactive prompt (there's no keyboard during a build).
--no-install-recommendsSkip "recommended" extras — often 30–50% smaller.
rm -rf /var/lib/apt/lists/*Remove the ~40 MB package index in the same layer.
\ at line endLine continuation; still one instruction.

On Alpine the equivalent is one short line: RUN apk add --no-cache curl (--no-cache = don't store the index at all).

COPY vs ADD

COPY package.json package-lock.json ./
COPY --chown=node:node . .
COPY --chmod=755 scripts/entrypoint.sh /usr/local/bin/
COPY --from=build /app/node_modules ./node_modules
  • COPY <src>... <dest>: src is relative to the build context; dest is relative to WORKDIR. With several sources, dest must end in /.
  • --chown=user:group sets ownership (default is root). --chmod sets permissions. --from=<stage|image> copies from another stage or image (§6).
COPYADD
Local files / directories✅✅
Remote URL (ADD https://…/file /x)❌✅ downloads it (not extracted; use --checksum=sha256:…)
Auto-extracts local .tar, .tar.gz, .tgz, .tar.xz…❌✅
Git repo URL❌✅ (BuildKit)
Predictable?Yes — does one thing"Magic" behaviour surprises people
Rule of thumbDefault choiceOnly when you need extraction or a URL
Recap Pin FROM tags; prefer alpine/slim/distroless. Chain install + cleanup in one RUN with &&. Use COPY unless you specifically need ADD's URL/tar features.

3 WORKDIR, ENV, ARG, EXPOSE, USER, LABEL, HEALTHCHECK

Explain like I'm 5

These are the labels and settings stuck on the box: which folder to work in, what settings to start with, which door the app listens at, and who's allowed to run it.

WORKDIR

WORKDIR /app
WORKDIR src
# prints /app/src — relative WORKDIR builds on the previous one
RUN pwd
  • Creates the directory if missing and sets the cwd for RUN, CMD, ENTRYPOINT, COPY, ADD — and for docker exec.
  • Always use absolute paths; never RUN cd ….

ENV vs ARG

Dockerfile (excerpt)
# ARG before FROM: usable only in FROM lines
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine
# ARG inside the stage: available to the RUN/ENV lines below, NOT at runtime
ARG APP_VERSION=dev
# ENV: baked into the image, visible to the running app
ENV NODE_ENV=production \
    PORT=3000 \
    APP_VERSION=${APP_VERSION}
$ docker build --build-arg NODE_VERSION=22 --build-arg APP_VERSION=1.2.0 -t shauryav/taskflow-api:1.2.0 .
$ docker run --rm shauryav/taskflow-api:1.2.0 node -e "console.log(process.version, process.env.APP_VERSION, process.env.PORT)"
v22.20.0 1.2.0 3000
$ docker run --rm -e PORT=8080 shauryav/taskflow-api:1.2.0 node -e "console.log(process.env.PORT)"

EXPOSE

  • EXPOSE 3000 (default TCP; EXPOSE 53/udp) is documentation only. It does not open or publish anything.
  • Publishing happens at run time: -p 8080:3000. -P publishes every EXPOSEd port to a random host port.
$ docker run -d -P --name api2 shauryav/taskflow-api:1.0
$ docker port api2
3000/tcp -> 0.0.0.0:32768
3000/tcp -> [::]:32768

USER

  • Containers run as root by default. If the app is compromised, root in the container is a big step toward the host.
  • Official Node images ship a node user (uid 1000). Other images: Alpine RUN addgroup -S app && adduser -S -G app app; Debian RUN groupadd -r app && useradd -r -g app app.
  • Applies to every RUN / CMD / ENTRYPOINT after it. Put it late (after installs that need root).
$ docker run --rm shauryav/taskflow-api:1.0 id
uid=1000(node) gid=1000(node) groups=1000(node)

LABEL

LABEL org.opencontainers.image.title="taskflow-api" \
      org.opencontainers.image.version="1.0.0" \
      org.opencontainers.image.source="https://github.com/shauryav/taskflow"

Key/value metadata. The org.opencontainers.image.* keys are the OCI standard; GHCR uses …source to link the image to its repo (S19). Read them: docker inspect --format '{{json .Config.Labels}}' shauryav/taskflow-api:1.0.

HEALTHCHECK

  CMD wget -qO- http://127.0.0.1:3000/health || exit 1

CMD …Exit 0 = healthy, 1 = unhealthy. wget is in Alpine (busybox); -slim images have neither curl nor wget.

Docker and Compose use HEALTHCHECK (Compose's depends_on: condition: service_healthy, S8). Kubernetes ignores it and uses its own probes (S13).

Common mistakes
  • Files copied before USER node are owned by root → app crashes with EACCES: permission denied, open '/app/uploads/…'. Fix: COPY --chown=node:node.
  • Passing a token via --build-arg NPM_TOKEN=… — BuildKit even warns: SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data. Use build secrets (§7).
  • Thinking EXPOSE makes the app reachable. It doesn't; -p does.
Recap WORKDIR = cwd. ARG = build-time, ENV = build + run time. EXPOSE = docs. USER = drop root. LABEL = metadata. HEALTHCHECK = Docker-level liveness (not used by K8s).

4 CMD vs ENTRYPOINT

Explain like I'm 5

ENTRYPOINT is the machine (a blender); CMD is the default thing you put in it (a banana). You can easily swap the banana; swapping the machine needs a special flag.

  • CMD — the default command/arguments. Replaced by anything you type after the image name in docker run.
  • ENTRYPOINT — the fixed executable. Args after the image name are appended to it. Replace it only with --entrypoint.
  • Only the last CMD and the last ENTRYPOINT in a Dockerfile count.

Shell form vs exec form

Exec form CMD ["node", "server.js"]Shell form CMD node server.js

$PORT expansionNo (no shell)Yes
Needs /bin/sh in the imageNo (works on distroless/scratch)Yes

Use exec form for CMD and ENTRYPOINT. BuildKit warns otherwise:

 1 warning found (use docker --debug to expand):
 - JSONArgsRecommended: JSON arguments recommended for CMD to prevent unintended behavior related to OS signals (line 12)

PID 1 and signals (why docker stop takes 10 seconds)

  • docker stop sends SIGTERM, waits 10 s (-t to change), then sends SIGKILL → exit code 137.
  • The Linux kernel ignores signals sent to PID 1 unless that process installed a handler. Node doesn't install a SIGTERM handler by default → even with exec form, an unprepared Node app ignores SIGTERM.
  • Fix (do one or both): handle SIGTERM in code, and/or run a tiny init as PID 1 (docker run --init, or tini in the image) that forwards signals and reaps zombie processes.
server.js (excerpt)
// listen on all interfaces — 127.0.0.1 would be unreachable from outside the container
const server = app.listen(PORT, '0.0.0.0', () => console.log(`listening on ${PORT}`));

// docker stop / kubectl delete pod send SIGTERM
process.on('SIGTERM', () => {
  console.log('SIGTERM received, closing server');
  server.close(() => process.exit(0));   // finish in-flight requests, then exit 0
});
# before the handler

# after adding the SIGTERM handler (or with tini / --init)
$ time docker stop api

Overriding on the TaskFlow image

Entrypoint script pattern

When you need setup before the app starts, use a script as ENTRYPOINT that ends with exec "$@":

taskflow-entrypoint.sh
#!/bin/sh
# stop on the first error
set -e

# one-time setup before the main process (only if enabled)
if [ "$RUN_MIGRATIONS" = "true" ]; then
  echo "running migrations..."
  node scripts/migrate.js
fi

# "$@" = the CMD ("node server.js"). exec REPLACES this shell,
# so node becomes PID 1 and receives SIGTERM directly.
exec "$@"
COPY --chmod=755 taskflow-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["taskflow-entrypoint.sh"]
CMD ["node", "server.js"]

The official node image does exactly this: ENTRYPOINT ["docker-entrypoint.sh"] + CMD ["node"]. That's why docker run node:20-alpine -v prints the Node version.

Common mistakes
  • CMD ['node', 'server.js'] (single quotes) is invalid JSON → silently treated as shell form → /bin/sh: [node,: not found.
  • Entrypoint script without exec → the shell stays PID 1 → slow stops, exit 137.
  • Script copied from Windows with CRLF line endings → exec /usr/local/bin/taskflow-entrypoint.sh: no such file or directory. Convert with dos2unix.
  • docker run img --entrypoint sh — flags after the image name are passed to the container, not to Docker.
Recap Always exec form. ENTRYPOINT = fixed program, CMD = overridable defaults. Handle SIGTERM or use tini/--init so docker stop is instant.

5 .dockerignore & layer caching

Explain like I'm 5

.dockerignore is the "don't pack" list for your suitcase. Caching is the builder remembering steps it already did, as long as nothing before them changed.

.dockerignore

  • Lives in the root of the build context. Matching paths are never sent to the builder → faster builds, smaller images, no leaked secrets via COPY . ..
  • Syntax like .gitignore but rooted at the context: node_modules matches only the top-level folder; **/node_modules matches at any depth; ! re-includes.
  • # comments only at the start of a line (inline # becomes part of the pattern).

How the layer cache decides

  1. The builder walks instructions top to bottom.
  2. A step is a cache hit if: its parent layer was a hit, the instruction text is identical, and (for COPY/ADD) the checksums of the copied files are identical.
  3. The first miss invalidates every step after it.
  4. RUN is keyed only on its text — it won't re-run just because the internet has newer packages. Use --no-cache or --pull when you want fresh.
# edit server.js, rebuild
$ docker build -t shauryav/taskflow-api:1.0 .

 => CACHED [4/5] RUN npm ci --omit=dev                                           0.0s
 => [5/5] COPY . .                                                               0.1s
[+] Building 1.4s (10/10) FINISHED
Change you makeBad order: COPY . . → RUN npm ciGood order: manifests → npm ci → COPY . .
Edit server.jsnpm ci re-runs (~14 s)Only COPY . . (~1 s)
Add a dependencynpm ci re-runsnpm ci re-runs (expected)

Cache mounts (BuildKit)

RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

Keeps npm's download cache between builds outside the image. Even when package.json changes, packages already downloaded aren't fetched again — and the cache never bloats the layer.

Common mistake

No .dockerignore on a Mac: host node_modules (with macOS-compiled bcrypt/sharp) overwrites the Linux ones → Error: … invalid ELF header at startup.

Recap Ignore node_modules, .git, .env. Order: rarely-changing steps first, source last. First cache miss rebuilds everything below it.

6 Multi-stage builds

Explain like I'm 5

Build the furniture in a messy workshop, then move only the finished chair into your clean living room. The tools stay behind.

  • A Dockerfile with several FROM lines = several stages. Only the last stage (or the --target) becomes the image.
  • COPY --from=<stage> pulls just the files you need from an earlier stage. Compilers, dev dependencies, test files and caches stay behind.
  • BuildKit builds only the stages the target depends on, running independent stages in parallel.

The final TaskFlow Dockerfile

Dockerfile
# syntax=docker/dockerfile:1

# Node major version — override with --build-arg NODE_VERSION=22
ARG NODE_VERSION=20

# ================= Stage 1: build — all deps + tests =================
FROM node:${NODE_VERSION}-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
# the build FAILS here if any test fails → no broken image is produced
RUN npm test
# drop devDependencies (jest, supertest) from node_modules
RUN npm prune --omit=dev

# ================= Stage 2: runtime — only what prod needs =================
FROM node:${NODE_VERSION}-alpine AS runtime
# tini: tiny init for PID 1 — forwards signals, reaps zombies
RUN apk add --no-cache tini
WORKDIR /app
ENV NODE_ENV=production \
    PORT=3000
LABEL org.opencontainers.image.title="taskflow-api" \
      org.opencontainers.image.source="https://github.com/shauryav/taskflow"
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/package.json /app/server.js ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://127.0.0.1:3000/health || exit 1
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "server.js"]
Line(s)Why
# syntax=docker/dockerfile:1Parser directive: use the latest stable 1.x Dockerfile frontend (cache/secret mounts etc.). Must be the very first line.
ARG NODE_VERSION=20Global ARG, usable in both FROM lines → one place to bump Node.
AS build / AS runtimeStage names for --from= and --target.
npm ci (build stage)All deps including dev — needed for jest. Cache mount speeds re-downloads.
RUN npm testTests are a build gate. Because runtime copies from build, this stage always runs.

Go example: down to a few MB with scratch

Dockerfile (Go service)
FROM golang:1.25-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# CGO_ENABLED=0 → fully static binary (no libc needed); -s -w strips debug info
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /out/server .

FROM scratch
# scratch has no CA bundle — copy it or HTTPS calls fail with "x509: certificate signed by unknown authority"
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/server /server
# "nobody" — scratch has no /etc/passwd, so use a numeric uid:gid
USER 65534:65534
EXPOSE 8080
ENTRYPOINT ["/server"]

Common mistakes
  • A test stage that nothing copies from is skipped by BuildKit when you build the final stage. Either copy from it (as above) or build it explicitly: docker build --target test .
  • COPY --from=build /app . copies everything back, dev deps and tests included — be specific.
  • Shell-form CMD in a scratch/distroless image → exec: "/bin/sh": stat /bin/sh: no such file or directory.
Recap Build/test in a fat stage, copy only artifacts into a slim stage. --target picks a stage. Go/Rust → scratch or distroless for single-digit MB images.

Secrets leak through layers — demo

Dockerfile.leaky (DON'T)
FROM node:20-alpine
ARG NPM_TOKEN
WORKDIR /app
COPY package*.json ./
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc && npm ci && rm .npmrc
$ docker build -f Dockerfile.leaky --build-arg NPM_TOKEN=npm_9fQx2LkP7aB3 -t leaky .
$ docker history --no-trunc leaky | grep authToken
<missing>   1 minute ago   RUN |1 NPM_TOKEN=npm_9fQx2LkP7aB3 /bin/sh -c echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc …

The rm .npmrc worked, but the token is in the image metadata forever. Same if you COPY .env and delete it later — it's still in that layer (docker save leaky | tar -x and look).

Dockerfile (fixed: build secret)
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
# the secret is mounted only for this RUN; it is never written to a layer
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci --omit=dev
$ docker build --secret id=npmrc,src=$HOME/.npmrc -t shauryav/taskflow-api:1.0 .

Common mistake

Built on an M1/M2/M3 Mac, deployed to an amd64 server → container exits immediately with exec /sbin/tini: exec format error. Rebuild with --platform linux/amd64, or publish one multi-arch tag: docker buildx build --platform linux/amd64,linux/arm64 -t shauryav/taskflow-api:1.0 --push .

Key takeaway

Anything that ever lands in a layer is public to whoever can pull the image. Keep secrets out with .dockerignore + --mount=type=secret, and inject runtime secrets via env/Secrets.

Recap Small base + prod deps only + multi-stage + non-root + no secrets + scan. Measure with docker images, docker history, dive.

★ Putting it all together

The big idea

The TaskFlow Dockerfile is a pipeline: a pinned FROM, cache-friendly COPY → RUN npm ci → COPY . ., tests as a build gate in the build stage, and a slim runtime stage that copies only prod files, runs as node, declares ENV/EXPOSE/HEALTHCHECK, and starts via exec-form ENTRYPOINT + CMD so signals work. .dockerignore keeps the context tiny and secrets out. Result: a ~140 MB, non-root, testable image that Compose (S8) and Kubernetes (S9+) will run.

Quick self-check

Image has ENTRYPOINT ["python", "app.py"] and CMD ["--port", "80"]. What runs for docker run img --port 9000?

python app.py --port 9000. Arguments after the image name replace CMD and are appended to ENTRYPOINT.

Why doesn't RUN rm /app/.env remove a secret copied in an earlier COPY . .?

Layers are immutable and stacked; the rm only hides the file in a new layer. The earlier layer (inside the image) still contains it. Exclude it via .dockerignore instead.

ARG vs ENV — which one can the running Node app read with process.env?

Only ENV. ARG exists during the build only (unless you copy it into an ENV, e.g. ENV APP_VERSION=${APP_VERSION}).

A container takes exactly 10 s to stop and exits with 137. Why, and two fixes?

SIGTERM wasn't handled (shell-form CMD, or Node as PID 1 without a handler), so Docker sent SIGKILL after the 10 s grace period (128 + 9 = 137). Fix: exec-form CMD plus a SIGTERM handler, and/or tini / docker run --init.

Does EXPOSE 3000 make the app reachable at localhost:3000?

No. EXPOSE is documentation (and used by -P). You must publish with -p 3000:3000.

Why copy package*.json and run npm ci before COPY . .?

Cache: the expensive install layer only rebuilds when the manifests change. Editing source only invalidates the final COPY . . layer.

In the TaskFlow multi-stage build, what is in the final image and what is left behind?

Final: Alpine + Node + tini + prod node_modules + package.json + server.js. Left behind in build: jest/supertest, tests, npm cache, everything else from the context.
