1 Dockerfile & docker build

The problem

Session 6 ended with a 4-line Dockerfile that ran hello.js. Point the same four lines at the real API:

Dockerfile (attempt 1)
FROM node:20-alpine
WORKDIR /app
COPY server.js .
CMD ["node", "server.js"]
$ docker build -t taskflow-api:0.1 .            # builds fine
$ docker run --rm taskflow-api:0.1
Error: Cannot find module 'express'
Require stack:
- /app/server.js
…
Node.js v20.19.5

The build worked and the container crashed. The image holds exactly what the Dockerfile put in it: Alpine, Node and one file. Nothing ran npm, and your laptop's node_modules isn't inside.

The idea

A Dockerfile is a build script. docker build sends a folder, the build context, to the builder (BuildKit, the default since Docker 23), which runs the instructions top to bottom. FROM picks the starting layers. Each RUN, COPY or ADD changes files in the image-in-progress, and BuildKit saves that change as a new layer. The other instructions only write the image's config.

 build context (your folder)        Dockerfile, top to bottom          image shauryav/taskflow-api:1.0
 ├── Dockerfile                     FROM node:20-alpine        ────▶  layers 1–4  Alpine + Node 20
 ├── package.json  ──────┐          WORKDIR /app               ────▶  layer 5     empty /app folder
 ├── package-lock.json ──┴────────▶ COPY package*.json ./      ────▶  layer 6     2 files
 │                                  RUN npm ci --omit=dev      ────▶  layer 7     node_modules
 ├── server.js  ─────────┐          (runs INSIDE the image being built)
 └── test/  ─────────────┴────────▶ COPY . .                   ────▶  layer 8     your code
                                    ENV · EXPOSE · USER · CMD  ────▶  config only (0 B)

This is Session 6's layer stack, now with the line that made each layer.

Think of it like this

Compiling a program. The Dockerfile is the source code, docker build is the compiler, the image is the binary and a container is the program running. A failed RUN is a compile error; "Cannot find module" is a runtime error. You don't hex-edit a binary or patch an image with docker exec: you fix the source and rebuild.

See it: what the API needs

package.json
{
  "name": "taskflow-api",
  "version": "1.0.0",
  "main": "server.js",
  "scripts": { "start": "node server.js", "test": "jest" },
  "dependencies":    { "express": "^5.1.0", "pg": "^8.13.1", "prom-client": "^15.1.3" },
  "devDependencies": { "jest": "^29.7.0", "supertest": "^7.0.0" }
}

dependencies are needed at run time, devDependencies only for tests. package-lock.json pins every exact version, and npm ci --omit=dev installs exactly those, minus the dev group.

Which lines made layers?

$ docker history --format 'table {{.CreatedBy}}\t{{.Size}}' shauryav/taskflow-api:1.0   # newest first

Rows with a size are layers: the two COPYs, the RUN, and the WORKDIR (it had to create /app). ENV, EXPOSE, USER and CMD are 0B because they only changed config. The last two rows come from node:20-alpine itself. Its ENTRYPOINT matters in §4.

When a step fails

BuildKit collapses each step's output. Add --progress=plain to see everything a RUN printed, plus --no-cache if the step is cached from an earlier success. (Two more flags: -f path builds from a file not named Dockerfile, and -t can be repeated.)

$ docker build --progress=plain --no-cache -t shauryav/taskflow-api:1.0 . 2>&1 | grep -A3 "npm ci"
#8 [4/5] RUN npm ci --omit=dev
#8 12.904 added 71 packages, and audited 72 packages in 12s
#8 12.906 found 0 vulnerabilities
#8 DONE 13.4s
Exam trap

"docker build runs the app to check it works." ✗ Only RUN lines execute during a build. CMD runs when a container starts, which is why attempt 1 built fine and then crashed.

"A # after an instruction starts a comment." ✗ Only at the start of a line. WORKDIR /app # set dir creates a folder literally named /app # set dir, and RUN pwd prints exactly that.

"COPY ../shared ./ works if the folder exists." ✗ COPY only reads inside the context. Use the parent folder as the context, with -f for the Dockerfile.

Remember

Dockerfile = source · build = compile · image = binary · container = running program.
RUN / COPY / ADD (and a new WORKDIR) → layers · everything else → config (0 B).

Mastery check
Q1. docker history shows ENV PORT=3000 0B. Did that line do anything?

Yes. It set PORT=3000 in the image's config, so every container starts with it. It's 0 B because no files changed, and only file changes take up layer space.

Q2. Spot the bug: docker build -t shauryav/taskflow-api:1.0

The build context is missing. Docker answers 'docker buildx build' requires 1 argument. Add the folder to send, usually . at the end.

Q3. You run docker build -t api . inside ~/taskflow/src, but the Dockerfile is in ~/taskflow. What happens? Give two fixes.

It fails with failed to read dockerfile: open Dockerfile: no such file or directory, because Docker looks in the context root. Fix: cd .. first, or run docker build -f ../Dockerfile -t api ...

Q4. Predict: you add RUN npm ci --omit=dev to attempt 1, right after COPY server.js .. Fixed?

No. Now the build fails, because npm ci finds no package.json or lockfile in /app. Only files you COPY exist in the image, so copy the manifests first, as v1 does.

2 FROM, RUN, COPY (and ADD)

The problem

A puzzle. This Dockerfile creates a 50 MB file and then deletes it:

Dockerfile.fat
FROM alpine:3.20
RUN dd if=/dev/zero of=/big.bin bs=1M count=50
RUN rm /big.bin
$ docker build -f Dockerfile.fat -t fat .
$ docker images --format 'table {{.Repository}}:{{.Tag}}\t{{.Size}}' | grep -E 'TAG|fat|alpine'
REPOSITORY:TAG   SIZE
fat:latest       66.1MB
alpine:3.20      13.7MB

The file is gone, so why is the image 52 MB bigger than plain Alpine?

The idea

Three instructions do almost all the work. FROM chooses the bottom layers. RUN runs a shell command inside the image being built and saves the changed files as a new layer. COPY copies files from the build context into a new layer. Layers only ever stack up: a later layer can hide a file, but it can't take bytes out of an earlier one.

# docker history fat, drawn as a stack
 layer 3  RUN rm /big.bin          4.1kB    ← a "deleted" marker that hides /big.bin
 layer 2   RUN dd … of=/big.bin     52.4MB   ← still in the image, still pulled
 layer 1   FROM alpine:3.20         ~8MB
           the image = all layers stacked; pull and push move every one
Think of it like this

Transparent sheets on an overhead projector. FROM is the first stack, and every RUN or COPY lays another sheet on top. "Deleting" a file paints over it on a new sheet. The screen looks clean, but the old sheet is still in the pile you carry to every server.

See it: the fix is one RUN

Dockerfile.thin
FROM alpine:3.20
RUN dd if=/dev/zero of=/big.bin bs=1M count=50 && rm /big.bin
$ docker images --format 'table {{.Repository}}:{{.Tag}}\t{{.Size}}' thin
REPOSITORY:TAG   SIZE
thin:latest      13.6MB

Created and deleted inside one step, the file is never in that step's snapshot. That's the rule behind every "clean up in the same RUN" tip. What RUN does not do: run when the container starts. It runs once, at build time, and only its result is kept.

Build it up

FROM: pick the starting point

FROM comes first (only ARG and parser directives like # syntax= may precede it). Its forms: FROM node:20-alpine, … AS build (a named stage, §6) and …@sha256:2d07… (pinned by digest). Pin at least the major version, because FROM node means node:latest and a new Node major can break your build overnight.

Version note

Node 20 reached end-of-life in April 2026. The course keeps 20 for consistency, but real projects should use node:22-alpine or node:24-alpine: a one-flag change with §3's ARG NODE_VERSION.

RUN: two rules

Rule 1: each RUN is a fresh shell. RUN npm ci really runs /bin/sh -c "npm ci", so &&, pipes and $VARS work, but the shell's state ends with the line:

RUN mkdir /app && cd /app
RUN pwd
#6 [3/3] RUN pwd
#6 0.093 /

The folder survives because it's a file change. The cd doesn't. Use WORKDIR to change directory (§3).

Rule 2: install and clean up in the same RUN. That's the puzzle applied to real package managers:

Bad: 3 layers, stale cache, no size saving
FROM node:20-slim
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
Good: 1 layer, fresh index, cleaned
FROM node:20-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates \
 && rm -rf /var/lib/apt/lists/*
PieceWhy
update && install in one RUNA RUN is cached by its text (§5). A separate apt-get update layer stays cached for months, so later installs read a stale index
-yNo prompts: there's no keyboard during a build
--no-install-recommendsSkip "recommended" extras, often 30–50% smaller
rm -rf /var/lib/apt/lists/*Delete the ~40 MB index in the same layer, so it never ships
\ at the end of a lineLine continuation: still one instruction, one layer

On Alpine it's one short line: RUN apk add --no-cache curl. Here --no-cache means "don't store the package index at all".

COPY (and ADD)

COPY package.json package-lock.json ./
COPY --chown=node:node . .
COPY --chmod=755 scripts/entrypoint.sh /usr/local/bin/
COPY --from=build /app/node_modules ./node_modules

Sources are relative to the build context, the destination to WORKDIR. Copied files belong to root unless you add --chown. --chmod sets permissions, and --from copies out of another stage (§6). ADD can do everything COPY does, plus a few tricks:

COPYADD
Local files and folders✅✅
Remote URL (ADD https://…/file /x)❌✅ downloads it, without extracting; pin it with --checksum=sha256:…
Auto-extracts local .tar, .tar.gz, .tgz, .tar.xz❌✅
Rule of thumbThe default. It does one predictable thing.Only when you want the extraction or the download
Exam trap

"RUN rm in a later step makes the image smaller." ✗ The bytes stay in the earlier layer; the new one only hides them.

"RUN cd /app sets the directory for the following steps." ✗ Each RUN starts a new shell in the current WORKDIR.

"ADD is an upgraded COPY, so use it everywhere." ✗ Its auto-extract and download surprise people. Use COPY unless you need them.

Remember

FROM = start from · RUN = do, at build time · COPY = bring in from the context.
Layers only add. Create and clean up in the same RUN.

Mastery check
Q1. Spot the bug: a Dockerfile has RUN apt-get update on one line and RUN apt-get install -y curl on the next. Months later you add jq to the install line and the build fails with "Unable to locate package". Why?

The unchanged apt-get update line is reused from cache, months old. Only the edited install re-runs, against a stale index. Put update && install in one RUN.

Q2. You want assets.tar.gz inside the image as a tarball, not unpacked. COPY or ADD?

COPY. ADD auto-extracts local tar archives, so you'd get a folder of files instead.

Q3. Spot the bug: COPY package.json package-lock.json ./app

With more than one source, the destination must be a directory ending in /, so BuildKit rejects it. Write ./app/, or just ./ after WORKDIR /app.

Q4. TaskFlow adds a native module that only ships prebuilt binaries for glibc. The build on node:20-alpine fails. Which base do you try next, and why not node:20?

node:20-slim: minimal Debian, so it has glibc, at ~200 MB. node:20 works too but ships ~1.1 GB of compilers you don't need at run time. If the module must be compiled, do that in a node:20 build stage (§6).

3 WORKDIR, ENV, ARG, EXPOSE, USER, LABEL, HEALTHCHECK

The problem

A teammate's draft of Dockerfile v1 added ARG APP_VERSION, kept EXPOSE 3000 and lost the USER line. Three puzzles:

$ docker build --build-arg APP_VERSION=1.2.0 -t shauryav/taskflow-api:1.2.0 .
$ docker run --rm shauryav/taskflow-api:1.2.0 node -e "console.log(process.env.APP_VERSION)"
undefined                                                      # 1. where did 1.2.0 go?
$ docker run -d --name api shauryav/taskflow-api:1.2.0
$ curl localhost:3000/health
curl: (7) Failed to connect to localhost port 3000 after 0 ms: Couldn't connect to server
                                                               # 2. but it says EXPOSE 3000!
$ docker exec api id
uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),3(sys),…   # 3. the API runs as root

The idea

These instructions add no files (apart from WORKDIR's folder). They set what the build and the container start with. For each one, ask: build time, run time, or just a note?

               docker build (RUN lines)       stored in image       docker run (the container)
 ARG           ✔ available                    ✘ dropped             ✘ gone
 ENV           ✔ available                    ✔ saved        ─────▶ ✔ set (override with -e)
 WORKDIR       ✔ cwd for RUN / COPY           ✔ saved        ─────▶ ✔ cwd for CMD and docker exec
 USER          ✔ user for later RUN           ✔ saved        ─────▶ ✔ the process's user
 EXPOSE        —                              ✔ a note       ─────▶ ✘ publishes nothing (-p does)
 LABEL         —                              ✔ metadata            read by tools and registries
 HEALTHCHECK   —                              ✔ saved        ─────▶ ✔ Docker runs it every 30 s

All three puzzles are answered in this table: read the ARG, EXPOSE and USER rows.

Think of it like this

A cake factory. ARG is a note to the baker ("use 3 eggs"), thrown away before the cake ships. ENV is the card in the box ("store at 4 °C") that every owner reads. EXPOSE is the "serve with a fork" label: it doesn't hand you a fork. That's -p's job.

See it: ARG vs ENV

Dockerfile
FROM alpine:3.20
ARG BUILD_COLOR=blue
ENV RUN_COLOR=green
RUN echo "during build: BUILD_COLOR=$BUILD_COLOR RUN_COLOR=$RUN_COLOR"
CMD ["sh", "-c", "echo at run time: BUILD_COLOR=$BUILD_COLOR RUN_COLOR=$RUN_COLOR"]
$ docker build --progress=plain -t colors . 2>&1 | grep "0.0.*during build"
#5 0.061 during build: BUILD_COLOR=blue RUN_COLOR=green
$ docker run --rm colors
at run time: BUILD_COLOR= RUN_COLOR=green
$ docker build --build-arg BUILD_COLOR=red -t colors . && docker run --rm -e RUN_COLOR=purple colors
at run time: BUILD_COLOR= RUN_COLOR=purple

During the build both exist. In the container only the ENV survives, and -e overrides it. What ARG does not do: reach your app. That solves puzzle 1. To keep a build-time value, copy it into an ENV:

Dockerfile (excerpt)
# ARG before FROM: usable only in FROM lines
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine
# ARG inside the stage: visible to the lines below, not at run time
ARG APP_VERSION=dev
# ENV: baked into the image, so the running app sees it
ENV NODE_ENV=production \
    PORT=3000 \
    APP_VERSION=${APP_VERSION}
$ docker build --build-arg NODE_VERSION=22 --build-arg APP_VERSION=1.2.0 -t shauryav/taskflow-api:1.2.0 .
$ docker run --rm shauryav/taskflow-api:1.2.0 node -e "console.log(process.version, process.env.APP_VERSION, process.env.PORT)"
v22.20.0 1.2.0 3000

Build it up: the rest of the settings

EXPOSE: a note, not a door (puzzle 2)

EXPOSE 3000 (TCP unless you write 53/udp) records the app's port. Nothing is published until docker run -p 3000:3000 (Session 6, §7). Only -P reads it, publishing every exposed port on a random host port:

$ docker run -d -P --name api2 shauryav/taskflow-api:1.0
$ docker port api2
3000/tcp -> 0.0.0.0:32768
3000/tcp -> [::]:32768

USER: don't run as root (puzzle 3)

Containers run as root unless the image says otherwise, and root in a container is one kernel bug away from root on the host (Session 6, §2). Official Node images ship a node user (uid 1000). Elsewhere, create one (RUN addgroup -S app && adduser -S -G app app on Alpine). USER applies to every later RUN, CMD and ENTRYPOINT, so put it after steps that need root, like package installs.

$ docker run --rm shauryav/taskflow-api:1.0 id
uid=1000(node) gid=1000(node) groups=1000(node)

Files COPY-ed earlier still belong to root, so an app that writes into /app hits EACCES: permission denied. Use COPY --chown=node:node.

WORKDIR and LABEL

WORKDIR creates the folder and sets the working directory for RUN, COPY, CMD, ENTRYPOINT and docker exec. A relative one builds on the previous (/app then src → /app/src), so use absolute paths. LABEL adds key/value metadata:

LABEL org.opencontainers.image.title="taskflow-api" \
      org.opencontainers.image.version="1.0.0" \
      org.opencontainers.image.source="https://github.com/shauryav/taskflow"

The org.opencontainers.image.* keys are the OCI standard. GHCR uses …source to link an image to its repository (Session 19). Read them with docker inspect --format '{{json .Config.Labels}}' img.

HEALTHCHECK: "running" isn't "working"

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD wget -qO- http://127.0.0.1:3000/health || exit 1
OptionDefaultMeaning
--interval / --timeout30s / 30sTime between checks / a slower check counts as failed
--start-period0sBoot grace period: failures don't count yet
--retries3Failures in a row before unhealthy
CMD …Exit 0 = healthy, 1 = unhealthy. Alpine has busybox wget; -slim has neither curl nor wget.
 
$ docker ps --format 'table {{.Names}}\t{{.Status}}'
NAMES     STATUS
api       Up 48 seconds (healthy)
$ docker inspect --format '{{.State.Health.Status}} {{.State.Health.FailingStreak}}' api
healthy 0

Compose waits on this status (condition: service_healthy, Session 8). Kubernetes ignores it and uses probes (Session 13).

Exam trap

"EXPOSE 3000 makes the app reachable on port 3000." ✗ It's documentation (and input for -P). Only -p publishes.

"--build-arg sets an environment variable for the app." ✗ ARG exists only during the build. Copy it into an ENV.

"Kubernetes restarts containers that fail their HEALTHCHECK." ✗ It ignores HEALTHCHECK and uses liveness and readiness probes.

Remember

ARG = build time only · ENV = build time + run time.
EXPOSE documents, -p publishes.
USER node goes late; COPY --chown before it.

Mastery check
Q1. Predict: a Dockerfile starts with ARG NODE_VERSION=20, then FROM node:${NODE_VERSION}-alpine, then RUN echo "v=$NODE_VERSION". What does the RUN print?

v=, an empty value. An ARG declared before FROM is only usable in FROM lines. Add ARG NODE_VERSION (no value) inside the stage to bring it into scope.

Q2. The image has ENV PORT=3000 and EXPOSE 3000, and the app listens on $PORT. You run docker run -d -P -e PORT=8080 img. Which port does the app listen on, and does the published port work?

The app listens on 8080, because -e overrides the ENV. -P still publishes the exposed port, 3000, where nothing listens, so connections fail. EXPOSE is a static note. Use -p 8080:8080.

Q3. Spot the bug: USER node comes right after FROM, followed by RUN apk add --no-cache curl.

apk needs root, so the build fails with ERROR: Unable to lock database: Permission denied. Install packages first, then switch to USER node.

Q4. docker ps shows Up 2 minutes (unhealthy), but curl localhost:3000/health from the host works. Give a likely cause and the command that confirms it.

The check is failing, not the app: often a HEALTHCHECK that calls curl or wget in an image without it (e.g. -slim). docker inspect --format '{{json .State.Health.Log}}' api shows each check's exit code and output.

4 CMD vs ENTRYPOINT

The problem

A teammate moved the API to node:20-slim (a dependency needed glibc) and "tidied" the last line to CMD node server.js. Since then:

$ time docker stop api
api
real    0m10.38s
$ docker inspect --format '{{.State.ExitCode}}' api
137

That's Session 6's 10-second stop, yet server.js still has its SIGTERM handler. Puzzle 2: docker run --rm node:20-alpine -v prints v20.19.5. How did a flag become a command?

The idea

Two instructions build the start command. ENTRYPOINT is the fixed program. CMD is its default arguments, and anything after the image name in docker run replaces CMD. Each has an exec form (a JSON array, run directly as PID 1) and a shell form (a plain string, wrapped in /bin/sh -c).

 Dockerfile                               docker run IMAGE [ARGS…]
 ENTRYPOINT ["tini", "--"]   ─┐
                              ├──▶ final command = ENTRYPOINT + (ARGS if given, else CMD)
 CMD ["node", "server.js"]   ─┘
      no ARGS            →  tini -- node server.js
      ARGS = node -v     →  tini -- node -v           (CMD replaced)
      --entrypoint sh    →  sh                         (ENTRYPOINT replaced, CMD dropped)

 shell form:  CMD node server.js   →   /bin/sh -c "node server.js"
Think of it like this

A blender. ENTRYPOINT is the machine, CMD is the default fruit (a banana). docker run img strawberry swaps the fruit. --entrypoint swaps the machine, and the banana goes too: it was meant for the blender.

See it: a 3-line image

Dockerfile (greet)
FROM alpine:3.20
ENTRYPOINT ["echo", "Hello,"]
CMD ["world"]
$ docker run --rm greet
Hello, world
$ docker run --rm greet TaskFlow
Hello, TaskFlow
$ docker run --rm --entrypoint uname greet
Linux
You runProcess inside the container
greetecho Hello, world: ENTRYPOINT + CMD
greet TaskFlowecho Hello, TaskFlow: your argument replaced CMD
--entrypoint uname greetuname, not uname world: a new ENTRYPOINT drops the default CMD

What run arguments do not do: add to CMD. They replace it. --entrypoint is a Docker flag, so it goes before the image name.

Build it up

Shell form vs exec form (puzzle 1)

Shell form hands your string to /bin/sh -c. Whether that shell stays as PID 1 depends on the image's shell:

$ docker run -d --name t1 ubuntu:24.04 /bin/sh -c "sleep 300"     # Debian/Ubuntu: sh is dash
$ docker exec t1 ps -o pid,cmd
    PID CMD
      1 /bin/sh -c sleep 300
      7 sleep 300
$ docker run -d --name t2 alpine:3.20 /bin/sh -c "sleep 300"      # Alpine: sh is busybox
$ docker exec t2 ps
PID   USER     TIME  COMMAND
    1 root      0:00 sleep 300

On node:20-slim (Debian), CMD node server.js makes sh PID 1 and node its child. docker stop signals PID 1, the shell, which has no handler and so ignores it (Session 6, §8). Node never hears SIGTERM, and after 10 s comes SIGKILL: exit 137. That's puzzle 1. The fix is exec form, CMD ["node", "server.js"], which makes node PID 1. Busybox execs a single simple command, which is why the bug hid on Alpine. Don't rely on that: add one && and the shell stays. BuildKit flags every shell-form CMD with a JSONArgsRecommended warning.

The entrypoint-script pattern (puzzle 2)

When something must happen before the app starts, make a script the ENTRYPOINT and end it with exec "$@":

taskflow-entrypoint.sh
#!/bin/sh
# stop on the first error
set -e

# one-time setup before the main process (only if enabled)
if [ "$RUN_MIGRATIONS" = "true" ]; then
  echo "running migrations..."
  node scripts/migrate.js
fi

# "$@" is the CMD ("node server.js"). exec REPLACES this shell,
# so node becomes PID 1 and receives SIGTERM directly.
exec "$@"
COPY --chmod=755 taskflow-entrypoint.sh /usr/local/bin/
ENTRYPOINT ["taskflow-entrypoint.sh"]
CMD ["node", "server.js"]

The official node image does exactly this: ENTRYPOINT ["docker-entrypoint.sh"] + CMD ["node"], both visible in §1's docker history. If the first argument starts with - or isn't a command, the script puts node in front, so docker run node:20-alpine -v runs node -v. That's puzzle 2.

Exam trap

"Arguments after the image name are appended to CMD." ✗ They replace CMD and are appended to ENTRYPOINT.

"CMD ['node', 'server.js'] is fine." ✗ Single quotes aren't valid JSON, so Docker treats the line as shell form. The container dies with /bin/sh: [node,: not found (exit 127).

"Exec form expands $PORT." ✗ No shell, no expansion. Read it in code, or use ["sh", "-c", "exec node server.js --port $PORT"].

Remember

ENTRYPOINT = the program · CMD = its default arguments (run args replace CMD).
Always exec form, with double quotes.
Entrypoint scripts end with exec "$@".

Mastery check
Q1. An image has ENTRYPOINT ["python", "app.py"] and CMD ["--port", "80"]. What runs for docker run img --port 9000?

python app.py --port 9000. The arguments replace CMD (--port 80) and are appended to ENTRYPOINT.

Q2. Predict: docker run --rm greet --entrypoint sh (the greet image from above).

Hello, --entrypoint sh. Everything after the image name goes to the container, so --entrypoint sh replaced CMD and was echoed. Docker never saw a flag.

Q3. Spot the bug: an entrypoint script does its setup and ends with node server.js (no exec). What symptom do you expect?

The script's shell stays PID 1, with node as a child that never gets SIGTERM. Every stop takes 10 s and exits 137. End with exec "$@".

Q4. Fill in: shell form runs ______ -c "…"; exec form runs the command ______ as PID ___, which is why only exec form works on a ______ image that has no shell.

/bin/sh · directly · 1 · scratch or distroless.

5 .dockerignore & layer caching

The problem

A classmate's Dockerfile copies everything first and installs after: COPY . . → RUN npm ci --omit=dev. There's no .dockerignore. They change one line of server.js and rebuild:

$ docker build -t shauryav/taskflow-api:1.0 .
 => [internal] load build context                                                6.9s
 => => transferring context: 312.45MB                                           6.8s
 => CACHED [2/4] WORKDIR /app                                                    0.0s
 => [3/4] COPY . .                                                               2.1s
 => [4/4] RUN npm ci --omit=dev                                                 14.1s
[+] Building 23.9s (9/9) FINISHED

24 seconds, 312 MB uploaded and every package reinstalled, for one line. Two separate problems hide here.

The idea

First, the CLI sends the whole context to BuildKit, minus what .dockerignore excludes. Second, for each step BuildKit asks: "Have I run exactly this, on exactly this parent layer?" If yes, it reuses the layer (CACHED). If not, it runs the step, and every step after it runs again, because their parent changed.

 step                      cache key: parent + instruction text (+ checksums of copied files)
 FROM node:20-alpine       same digest                       → CACHED
 WORKDIR /app              same text                         → CACHED
 COPY package*.json ./     same 2 files                      → CACHED   (you didn't touch them)
 RUN npm ci --omit=dev     same text, same parent            → CACHED   (14 s saved)
 COPY . .                  server.js changed                 → MISS ✗   first miss
 everything below                                            → runs again
Think of it like this

Save points in a video game. Change something at level 5 and you reload from level 4, but replay level 5 and every level after it. So put the levels you keep changing last. .dockerignore lists what never goes into the game at all.

See it: the good order

Dockerfile v1 (§1) copies the manifests and installs before COPY . .. Edit server.js and rebuild:

$ docker build -t shauryav/taskflow-api:1.0 .
 => CACHED [2/5] WORKDIR /app                                                    0.0s
 => CACHED [3/5] COPY package*.json ./                                           0.0s
 => CACHED [4/5] RUN npm ci --omit=dev                                           0.0s
 => [5/5] COPY . .                                                               0.1s
[+] Building 1.4s (10/10) FINISHED

From 24 s to 1.4 s. What the cache does not do: notice that the internet changed. A RUN's key is its text and its parent, so a cached npm ci won't re-run because a newer patch exists. --no-cache ignores the cache, and --pull re-checks the base image.

Cache mounts: faster even on a miss

RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

npm's download cache is kept between builds, outside the image. When npm ci must re-run, already-downloaded packages aren't fetched again, and the cache never bloats a layer.

Exam trap

"When a step changes, only that layer is rebuilt." ✗ The first miss invalidates every step below it.

"Without .dockerignore it's only slower." ✗ On a Mac, host node_modules (macOS-built bcrypt) overwrites the Linux ones, giving invalid ELF header, and .env lands in a layer.

Remember

Rarely-changing first, often-changing last: manifests → install → source.
First cache miss → everything below rebuilds.
Always ignore node_modules, .git and .env.

Mastery check
Q1. Predict: with Dockerfile v1, you add jest to devDependencies and rebuild. Which steps run, and which are CACHED?

FROM and WORKDIR are CACHED. COPY package*.json ./ misses (checksums changed), so npm ci and COPY . . run again. The result is identical, since --omit=dev skips jest, but the cache can't know that.

Q2. True or false: "If a Dockerfile line is identical to last time, it's always a cache hit."

False. Its parent must also be a hit (any earlier miss invalidates it), and for COPY and ADD the checksums of the copied files must match too. Same text with different files is a miss.

Q3. Spot the bug: in a monorepo, .dockerignore says node_modules, yet packages/api/node_modules still ends up in the context.

Patterns are anchored at the context root, so node_modules only matches the top-level folder. Use **/node_modules.

6 Multi-stage builds

The problem

You want the build to run TaskFlow's tests, so a broken API never becomes an image. The tests need jest and supertest, but production must not ship them. A single stage can't have both:

 single stage, with tests          what ends up in the image you push
 RUN npm ci          (all deps)    jest, supertest and ~300 packages they pull in
 COPY . .  →  RUN npm test         test/, its fixtures, npm's download cache
                                   … and Alpine + Node + the app: the only part you wanted

The idea

Each FROM starts a new stage with a fresh filesystem. Only the last stage (or the --target) becomes the image. COPY --from=<stage> carries chosen files forward; everything else stays behind.

 stage "build" (node:20-alpine)             stage "runtime" (node:20-alpine)
 ┌──────────────────────────────┐          ┌───────────────────────────────┐
 │ npm ci        all deps       │          │ apk add tini                  │
 │ COPY . .      src + tests    │  COPY    │ node_modules  (prod only)  ◀──┼──┐
 │ RUN npm test  ← the gate     │  --from= │ package.json, server.js    ◀──┼──┤
 │ npm prune --omit=dev         │  build ──┼───────────────────────────────┼──┘
 └──────────────────────────────┘          │ USER node · HEALTHCHECK · CMD │
   thrown away: never pushed               └───────────────────────────────┘ ← the image
Think of it like this

A workshop and a living room. You build the chair in the workshop (build stage), with saws and sawdust everywhere. COPY --from carries only the chair into the clean living room (runtime stage). Guests only see the living room.

See it: two stages, one survivor

Dockerfile (two-stage)
FROM alpine:3.20 AS build
RUN echo "built in stage 1" > /artifact.txt && dd if=/dev/zero of=/junk.bin bs=1M count=30

FROM alpine:3.20
COPY --from=build /artifact.txt /
CMD ["cat", "/artifact.txt"]
$ docker build -t two-stage .
 => [build 1/2] FROM docker.io/library/alpine:3.20@sha256:d9e853e87e55…
 => [build 2/2] RUN echo "built in stage 1" > /artifact.txt && dd if=/dev/zero of=/junk.bin …
 => [stage-1 2/2] COPY --from=build /artifact.txt /
$ docker run --rm two-stage

$ docker run --rm two-stage ls /junk.bin
ls: /junk.bin: No such file or directory

AS build names stage 0, and the unnamed second stage shows up as stage-1. COPY --from=build reads that stage's filesystem instead of the context. docker images reports 13.6MB, plain-Alpine size: unlike §2's puzzle, the 30 MB junk stayed behind. What a build stage does not do: get pushed. It only lives in your local build cache.

Build it up: the final TaskFlow Dockerfile

Dockerfile

    PORT=3000

  CMD wget -qO- http://127.0.0.1:3000/health || exit 1

Compiled languages: down to scratch

Dockerfile (Go service)
FROM golang:1.25-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# CGO_ENABLED=0 builds a fully static binary (no libc needed); -s -w strips debug info
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /out/server .

# scratch has no CA bundle: copy it, or HTTPS calls fail with "x509: certificate signed by unknown authority"
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/server /server
# "nobody": scratch has no /etc/passwd, so use a numeric uid:gid
USER 65534:65534
EXPOSE 8080
ENTRYPOINT ["/server"]

One golang:1.25-alpine stage would be ~300 MB. On scratch it's ~8 MB, and ~10 MB on gcr.io/distroless/static-debian12:nonroot, which includes CA certs, tzdata and a non-root user. Neither has a shell.

Exam trap

"Every stage ends up in the final image." ✗ Only the last (or --target) does. Others contribute only what COPY --from takes.

"A test stage always runs." ✗ BuildKit skips stages the target doesn't depend on (Q2 below).

"COPY --from=build /app . is fine." ✗ It carries dev dependencies and tests straight back in. Copy specific paths.

Remember

Build fat, ship thin: only the last stage ships.
COPY --from=stage picks what crosses over · --target stops at a stage.

Mastery check
Q1. In the final TaskFlow image, what is inside, and what was left behind?

Inside: Alpine, Node, tini, production node_modules, package.json and server.js. Left in build: jest and supertest, test/, the npm cache and every other file from the context.

Q2. Predict: stages are build, test (FROM build, runs npm test) and runtime, which copies only from build. Does docker build . run the tests?

No. Nothing in runtime depends on test, so BuildKit skips it and a failing test won't stop the image. Run docker build --target test . in CI, or make runtime copy from test.

Q3. Spot the bug: the Go image ends with CMD ./server on FROM scratch.

Shell form needs /bin/sh, and scratch has none: exec: "/bin/sh": stat /bin/sh: no such file or directory. Use ENTRYPOINT ["/server"].

Q4. The Go service on scratch starts fine, but every call to an HTTPS API fails with x509: certificate signed by unknown authority. Why?

scratch is empty, so there's no CA certificate bundle to verify servers with. Copy /etc/ssl/certs/ca-certificates.crt from the build stage, or use distroless/static, which ships one.

7 Image optimization

The problem

Here is the very first TaskFlow image a classmate built, v0-naive:

Dockerfile (v0-naive)
FROM node:20
COPY . .
RUN npm install
CMD npm start

It's 1.21 GB: every CI run pushes it, every server pulls it, the scanner finds hundreds of CVEs in packages the app never uses, and COPY . . swept the project's .npmrc (with an npm token) into a layer anyone can read. By the end of this section you can name six problems in those four lines.

The idea

Every byte is downloaded, stored and scanned on every machine, and every layer is readable by anyone who can pull. So: ship less (small base, prod deps only, multi-stage), ship safely (non-root, no secrets, scanned) and build reproducibly (pinned versions, a lockfile). Same app, five Dockerfiles:

 tag             what changed                                   uncompressed size
 v0-naive        node:20, COPY . ., npm install, no .dockerignore  ████████████████████████  1.21 GB
 v1-slim         node:20-slim, npm ci --omit=dev, .dockerignore    █████                     243 MB
 v2-alpine       Alpine base (§1 Dockerfile)                       ███                       152 MB
 v3-multistage   §6 Dockerfile: no npm cache, no tests             ███                       141 MB
 v4-distroless   runtime stage FROM distroless/nodejs20            ███                       138 MB

For Node, most of the win is the base image and dropping dev dependencies. For compiled languages, multi-stage is a 30–100× win (§6). v3 and v4 also gain where size doesn't show: tests gate the build, and distroless has no shell or package manager, so far fewer CVEs.

Think of it like this

Packing for a flight: a carry-on, not a wardrobe (small base), and no packing tools (multi-stage). Never write your password on the luggage tag. Everyone who handles the bag reads it, and peeling it off later (RUN rm) is useless: it was photographed at check-in (the layer).

See it: a secret leaks through a layer

Dockerfile.leaky (DON'T)
FROM node:20-alpine
ARG NPM_TOKEN
WORKDIR /app
COPY package*.json ./
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc && npm ci && rm .npmrc
$ docker build -f Dockerfile.leaky --build-arg NPM_TOKEN=npm_9fQx2LkP7aB3 -t leaky .

$ docker history --no-trunc --format '{{.CreatedBy}}' leaky | grep npm_9f
RUN |1 NPM_TOKEN=npm_9fQx2LkP7aB3 /bin/sh -c echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > .npmrc && npm ci && rm .npmrc # buildkit
ARG NPM_TOKEN=npm_9fQx2LkP7aB3

The rm .npmrc worked, yet the token is recorded twice in the history, forever. A COPY .env followed by a later delete is just as bad: docker save leaky | tar -x shows the file in its layer. What rm does not do: un-ship anything (§2). Use a build secret, mounted only while that one RUN executes:

Dockerfile (fixed: build secret)
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
# the secret is mounted only for this RUN; it is never written to a layer
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci --omit=dev
$ docker build --secret id=npmrc,src=$HOME/.npmrc -t shauryav/taskflow-api:1.0 .

Mastery check
Q1. Name the six problems in v0-naive (FROM node:20 / COPY . . / RUN npm install / CMD npm start).

(1) ~1.1 GB Debian base → -alpine/-slim. (2) No .dockerignore → node_modules, .git, .env, .npmrc copied in. (3) COPY . . before the install → every code change reinstalls. (4) npm install adds dev deps and doesn't install strictly from the lockfile → npm ci --omit=dev. (5) Runs as root → USER node. (6) Shell-form CMD through npm → signals miss node; use CMD ["node", "server.js"]. (Bonus: no WORKDIR, so files land in /.)

Q2. Spot the bug: COPY .env . then, two lines later, RUN rm .env. Give two fixes.

The secret is still in the COPY layer. Fixes: list .env in .dockerignore and pass values at run time (-e, --env-file, Compose, Kubernetes Secrets). If the build needs a secret, use RUN --mount=type=secret.

Q3. docker scout quickview reports a Medium CVE in the base image. Your code hasn't changed. How do you fix it?

Rebuild on a patched base: bump the pinned tag or digest, or rebuild with --pull if you track a moving tag. The CVE lives in the base's packages, so no code change can fix it.

Q4. The image works on your M2 Mac, but on EC2 the container exits at once with exec format error. Why, and what are two fixes?

It was built for arm64 and the server is amd64, so the CPU can't execute the binaries. Rebuild with --platform linux/amd64, or push a multi-arch image with docker buildx build --platform linux/amd64,linux/arm64 … --push.

★ Putting it all together

The big idea

A Dockerfile is source code for an image: each instruction either adds a layer (RUN, COPY, ADD) or sets config. TaskFlow's Dockerfile uses a pinned FROM and a cache-friendly order (manifests → npm ci → COPY . .), with .dockerignore keeping the context tiny and secrets out. Tests gate the build stage. A slim runtime stage copies only production files, runs as node, sets ENV/EXPOSE/HEALTHCHECK and starts via exec-form ENTRYPOINT + CMD so signals reach the app. The result, a ~140 MB non-root tested image, is what Compose (Session 8) and Kubernetes (Session 9 on) will run.

Final mastery check — combine everything
Q1. You edit one line of server.js and rebuild the final Dockerfile. Walk through each stage: which steps are CACHED, which run, and what changes in the image?

build: FROM, WORKDIR, COPY package*.json and npm ci are CACHED (manifests unchanged). COPY . . misses, so npm test and npm prune re-run: the first miss invalidates everything below. runtime: FROM, apk add tini, WORKDIR, ENV and LABEL are CACHED. The node_modules COPY stays cached as long as its content is identical (BuildKit compares checksums, not timestamps). The server.js COPY runs, so one small layer is new.

Q2. docker run --rm shauryav/taskflow-api:1.0 node -v: what exactly runs as PID 1, as which user, and in which folder?

/sbin/tini -- node -v: ENTRYPOINT stays and your arguments replace CMD. tini is PID 1 with node as its child, running as node (USER) in /app (WORKDIR). It prints the version and exits 0.

Q3. You switch the runtime stage to FROM gcr.io/distroless/nodejs20-debian12 and change nothing else. Name three things that break.

(1) RUN apk add tini fails: no shell, no package manager (§2). (2) The HEALTHCHECK's wget doesn't exist, so it would report unhealthy (§3). (3) distroless's ENTRYPOINT is already node, so drop the tini ENTRYPOINT and write CMD ["server.js"]. ["node", "server.js"] would run node node server.js (§4). Also, there's no node user: use the :nonroot tag.

Q4. A teammate builds with --build-arg NODE_VERSION=22 --build-arg APP_VERSION=1.2.0 using the final Dockerfile. Which Node version runs, and can the app read APP_VERSION?

Node 22, because the global ARG feeds both FROM lines. But the final Dockerfile never declares ARG APP_VERSION or copies it into an ENV, so process.env.APP_VERSION is undefined, and Docker gives no warning. Add ARG APP_VERSION + ENV APP_VERSION=${APP_VERSION} to the runtime stage (§3).

Q5. Correct every error: "EXPOSE 3000 opens the port; RUN rm .env removes the secret; and since CMD node server.js is exec form, docker stop is instant."

(1) EXPOSE only documents; -p publishes. (2) .env is still in the earlier layer: exclude it with .dockerignore and pass values at run time. (3) Without brackets it's shell form. On a Debian base sh is PID 1 and swallows SIGTERM: 10 s, exit 137. Write CMD ["node", "server.js"].
