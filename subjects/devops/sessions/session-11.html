1 Pod networking

The problem

In Session 8, containers on one Docker host talked over a bridge network, and anything else needed -p port mappings. Now TaskFlow's API pods run on node-1 and Postgres runs on node-2. With Docker rules you'd be juggling published ports on every server and hoping nothing clashes. How does a pod on one node reach a pod on another?

The idea

Kubernetes sets one simple rule set, the network model, and every cluster must obey it:

  1. Every pod gets its own IP, taken from its node's podCIDR.
  2. Any pod can reach any other pod, on any node, by that IP, without NAT.
  3. Node agents (the kubelet) can reach every pod on their node.
  4. Containers in one pod share the IP and talk over localhost (Session 10).
 Node minikube (192.168.49.2)             Node minikube-m02 (192.168.49.3)
 podCIDR 10.244.0.0/24                    podCIDR 10.244.1.0/24
┌───────────────────────────────┐        ┌───────────────────────────────┐
│ pod taskflow-api  10.244.0.12 │        │ pod taskflow-api  10.244.1.7  │
│ pod taskflow-api  10.244.0.13 │        │ pod taskflow-db   10.244.1.9  │
│   veth pairs ─► bridge cni0   │        │   veth pairs ─► bridge cni0   │
└───────────────┬───────────────┘        └───────────────┬───────────────┘
                └── CNI: routes / VXLAN / BGP / eBPF ────┘
       10.244.0.12 → 10.244.1.9:5432 directly, source IP preserved (no NAT)

Kubernetes doesn't wire this itself. When a pod starts, the runtime calls a CNI (Container Network Interface) plugin, which creates the pod's veth pair, assigns the IP and sets routes.

Think of it like this

In the restaurant, every station (pod) gets its own direct phone extension, and any station can dial any other one directly, even in another kitchen. There are no operators and no "dial 9 first" (NAT). The CNI plugin is the phone company that wires a line to each new station. There's a catch, which you'll see below: a replaced station gets a new extension.

A brand-new pod reached an API pod directly on its IP and port 3000. No -p, no published port. What it does not do: load-balance or stay put. You picked one pod by hand, and its IP is about to become useless:

Build it up: pod IPs are ephemeral

Every reschedule, rollout (Session 10) or scale event changes the pod IPs, so anything that stored 10.244.0.12 is now broken. The fix is a stable front door, a Service (section 2). Which CNI plugin does the wiring depends on the cluster:

Exam trap

"Pods on different nodes need a NodePort or port mapping to talk." ✗ Pod-to-pod works directly by pod IP across nodes, with no NAT. That's rule 2 of the model.

"Kubernetes implements pod networking itself." ✗ It defines the rules. A CNI plugin (Calico, Flannel, Cilium…) implements them.

Remember

Every pod gets an IP · any pod ↔ any pod, no NAT · a CNI plugin makes it so.
Pod IPs are ephemeral, so never put one in config.

Mastery check
Q1. A pod on node-1 (10.244.0.12) connects to Postgres on node-2 (10.244.1.9:5432). What source IP does Postgres see?

10.244.0.12, the pod's own IP. Pod-to-pod traffic isn't NATed, so the source is preserved.

Q2. Predict: you hard-code DATABASE_URL=…@10.244.1.9:5432/taskflow, and the Postgres pod is later rescheduled. What happens?

The new Postgres pod gets a different IP, so the API's connections fail ("connection refused" or a timeout). Use the Service name taskflow-db instead (sections 2 and 4).

Q3. True or false: "Two pods on the same node can talk to each other over localhost."

False. localhost is per pod (one network namespace each). Only containers inside one pod share it. Separate pods use each other's pod IP, or better, a Service.

2 Services & ClusterIP

The problem

Section 1 left two gaps. The API needs one address for Postgres that survives the DB pod being replaced. And the web tier needs one address for "the API", even though the API is three pods whose IPs keep changing, and it should spread its requests across them.

The idea

A Service picks a set of pods by label selector (Session 10) and gives them three things: a stable virtual IP, the ClusterIP, that never changes while the Service exists; a stable DNS name (taskflow-api, section 4); and L4 (TCP/UDP) load balancing across the matching pods that are ready. Type ClusterIP, the default, is reachable only from inside the cluster.

 any pod ──▶ taskflow-api  =  10.96.120.15:80        ← stable: survives every pod change
                   │  selector app=taskflow-api, load-balanced
         ┌─────────┼──────────┐
         ▼         ▼          ▼
  10.244.0.13  10.244.0.14  10.244.0.15   :3000       ← pods come and go
Think of it like this

A Service is the "API counter" phone number. Stations open and close and their extensions change, but staff always dial the counter, and the call is put through to whichever API station is ready. ClusterIP is an internal extension: it works from any phone in the building, but not from the street.

See it: a Service for the API

k8s/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api                # becomes the DNS name
  namespace: taskflow
  labels:
    app: taskflow-api
spec:
  type: ClusterIP                   # default: reachable only inside the cluster
  selector:                         # send traffic to Pods with this label
    app: taskflow-api
  ports:
    - name: http                    # required once a Service has >1 port; good habit anyway
      protocol: TCP                 # default TCP; UDP/SCTP also possible
      port: 80                      # what clients dial: taskflow-api:80
      targetPort: http              # the Pod's port named "http" (= 3000 in deployment.yaml)

Build it up: the database gets a Service too

Here's a temporary k8s/postgres.yaml. The password moves to the Secret taskflow-db-secret in Session 12, and the data to a PVC in Session 13.

Exam trap

"A Service is a load-balancer pod that traffic passes through." ✗ It's an API object. The forwarding is kernel rules on every node (section 3).

"A Service sends traffic to every pod matching its selector." ✗ Only to the ready ones. A pod failing its readiness probe is left out.

Remember

Service = stable ClusterIP + DNS name + load balancing over the ready pods its selector picks.
ClusterIP = inside the cluster only.

Mastery check
Q1. During a rollout every API pod is replaced. Which addresses change: pod IPs, the ClusterIP, the DNS name?

Only the pod IPs. The ClusterIP and the name taskflow-api stay the same for the Service's whole life, which is the point of having one.

Q2. Spot the bug: spec: { selector: { matchLabels: { app: taskflow-api } }, ports: [ … ] } in a Service.

Service selectors are a plain map: selector: { app: taskflow-api }. matchLabels belongs to Deployments and ReplicaSets, and the API server rejects it here.

Q3. Why does taskflow-db's Deployment use app: taskflow-db rather than app: taskflow-api?

The API Service selects app: taskflow-api. If the DB pod carried that label, the API Service would send some HTTP requests to Postgres. Different apps get different app labels.

3 Selectors, EndpointSlices & kube-proxy

The problem

Two puzzles. First, a teammate's Service exists and its name resolves, yet every request fails with Connection refused. Second, wget taskflow-api/health works but ping 10.96.120.15 gets no reply at all. How can an address that serves HTTP not answer a ping?

The idea

A Service never talks to pods itself. It's a three-step pipeline, and each step is a controller from Session 9:

 Service taskflow-api        selector: app=taskflow-api
      │  ① EndpointSlice controller: watch pods, keep the READY matches
      ▼
 EndpointSlice taskflow-api-x7k2p     10.244.0.13, .14, .15 : 3000
      │  ② kube-proxy on EVERY node: watch slices, write kernel rules
      ▼
 iptables / nftables:  10.96.120.15:80  →  DNAT to one endpoint, port 3000
      │  ③ the kernel rewrites each packet; no process ever "listens" on the ClusterIP
      ▼
 pod 10.244.0.14:3000

An EndpointSlice is the Service's live list of ready pod IP:port pairs, and kube-proxy turns that list into NAT rules.

Think of it like this

The EndpointSlice is the counter's on-shift list, rewritten every time a station opens, closes or stops being ready. kube-proxy is the switchboard wiring in every kitchen. There's no operator who answers, just wiring that redirects calls for the counter to someone on the list. If the list is empty, the call is refused. And a ping is like knocking on the counter itself: there's nobody standing there to answer.

See it: the live list

$ kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api
NAME                 ADDRESSTYPE   PORTS   ENDPOINTS                             AGE
taskflow-api-x7k2p   IPv4          3000    10.244.0.13,10.244.0.14,10.244.0.15   2m
$ kubectl get endpoints taskflow-api            # older API, still works
Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice
NAME           ENDPOINTS                                            AGE
taskflow-api   10.244.0.13:3000,10.244.0.14:3000,10.244.0.15:3000   2m
$ minikube ssh -- sudo iptables -t nat -L KUBE-SERVICES -n | grep taskflow
KUBE-SVC-K2Q3ZVJ7VQX5DJ3O  tcp  --  0.0.0.0/0  10.96.120.15  /* taskflow/taskflow-api:http cluster IP */ tcp dpt:80
KUBE-SVC-5QZKX2NYV4C7HJ6M  tcp  --  0.0.0.0/0  10.96.48.200  /* taskflow/taskflow-db:postgres cluster IP */ tcp dpt:5432

Slices carry their Service's name as the label kubernetes.io/service-name, and a big Service can have several. In the NAT table, each KUBE-SVC-… chain matches one ClusterIP:port and jumps to per-endpoint rules. That solves puzzle 2. The rules match TCP port 80 only, so a ping isn't handled and usually gets no reply. Test with wget/curl. What it does not do: pick the least busy pod. iptables mode picks at random per connection. Other modes are nftables (GA since 1.33, the future default) and ipvs (deprecated in 1.35), and Cilium can replace kube-proxy with eBPF.

Build it up: "Service has no endpoints"

Puzzle 1 is the most common Service bug. The teammate's selector says app: taskflow:

$ kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- taskflow-api/health
wget: can't connect to remote host (10.96.120.15): Connection refused
$ kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api
NAME                 ADDRESSTYPE   PORTS     ENDPOINTS   AGE
taskflow-api-x7k2p   IPv4          <unset>   <unset>     1m          # ← empty list: nobody to forward to
$ kubectl get svc taskflow-api -o jsonpath='{.spec.selector}'
{"app":"taskflow"}
$ kubectl get pods -l app=taskflow
No resources found in taskflow namespace.                     # ← selector matches nothing
$ kubectl get pods --show-labels | head -2
NAME                            READY   STATUS    RESTARTS   AGE   LABELS
taskflow-api-5b9c4f7d8b-fq5rl   1/1     Running   0          9m    app=taskflow-api,pod-template-hash=5b9c4f7d8b

DNS worked (it resolved to 10.96.120.15), but the list was empty, and kube-proxy rejects connections to a Service with no endpoints. Fix: make the selector a subset of the pod labels (app: taskflow-api) and re-apply, and endpoints appear within a second. The same symptom appears when every pod fails readiness. The safest way to get a selector right is to copy it from the Deployment:

$ kubectl expose deployment taskflow-api --port=80 --target-port=3000 --dry-run=client -o yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    app: taskflow-api
  name: taskflow-api            # name defaults to the Deployment's name
spec:
  ports:
  - port: 80
    protocol: TCP
    targetPort: 3000
  selector:                     # copied from the Deployment's selector
    app: taskflow-api
status:
  loadBalancer: {}

Without --dry-run=client -o yaml it creates the Service (service/taskflow-api exposed), and --type=NodePort gives section 5's type. For the repo, save the YAML and apply it.

Spot the bug: a selector that's too broad

Suppose both TaskFlow Deployments had also been given the recommended label app.kubernetes.io/part-of: taskflow, and someone "simplified" the API Service to selector: { app.kubernetes.io/part-of: taskflow } with targetPort: 3000:

NAME                 ADDRESSTYPE   PORTS   ENDPOINTS                                         AGE
taskflow-api-x7k2p   IPv4          3000    10.244.0.13,10.244.0.14,10.244.0.15,10.244.0.20   1m

The fourth endpoint is the Postgres pod, so about 1 in 4 requests go to Postgres on port 3000 and get "connection refused". Fix: select on app: taskflow-api. A named targetPort: http would also have skipped the DB pod, which has no port named http.

Exam trap

"ping the ClusterIP to check a Service." ✗ The ClusterIP is virtual. Only its TCP/UDP ports are wired up, so test with wget/curl.

"The pods match my selector, so there must be endpoints." ✗ Endpoints list only ready pods. If all of them fail readiness, the list is empty and clients get "connection refused".

Remember

selector → EndpointSlice (ready pods) → kube-proxy rules on every node.
Empty endpoints = selector mismatch or no ready pods. First command: kubectl get endpointslices -l kubernetes.io/service-name=NAME.

Mastery check
Q1. Name the controller or component behind each step: (a) keeping the ready pod list, (b) turning it into NAT rules, (c) rewriting the packet.

(a) The EndpointSlice controller (in kube-controller-manager). (b) kube-proxy on each node. (c) The Linux kernel (iptables/nftables). No Kubernetes process sits in the data path.

Q2. Predict: a Service's selector matches 3 pods, but 2 are failing their readiness probe. How many endpoints, and what share of traffic does the healthy pod get?

One endpoint, and it gets all the traffic. Unready pods are dropped from the slice until they pass again.

Q3. Selector { app: taskflow-api, version: "1.1.0" }; pods have app=taskflow-api,pod-template-hash=…. Any endpoints? Why?

None. A selector ANDs its labels, so every selector label must be on the pod, and these pods have no version label. Selector ⊆ pod labels, never the other way round.

4 Kubernetes DNS & service discovery

The problem

The ClusterIP 10.96.48.200 is stable, but hard-coding it is still fragile. It's different on minikube and on EKS, and if someone deletes and recreates the Service, it changes. In Compose (Session 8) the API simply connected to the hostname db. You want that here too.

The idea

Service discovery means finding where a service lives. Kubernetes does it with DNS. CoreDNS runs in kube-system behind a Service still called kube-dns. It watches Services and answers names of the form <service>.<namespace>.svc.cluster.local. The kubelet writes every pod's /etc/resolv.conf to point at CoreDNS, with a search list that makes short names work.

 api pod:  connect("taskflow-db:5432")
    │  /etc/resolv.conf → nameserver 10.96.0.10, search taskflow.svc.cluster.local …
    ▼
 CoreDNS (Service kube-dns, 10.96.0.10):  taskflow-db.taskflow.svc.cluster.local → 10.96.48.200
    ▼
 10.96.48.200:5432 ── kube-proxy rules (section 3) ──▶ postgres pod 10.244.1.9:5432

So TaskFlow's connection string in Kubernetes is postgres://taskflow:tf-pass-2026@taskflow-db:5432/taskflow (it moves into the Secret taskflow-db-secret in Session 12). It's the same as Compose's db, with a different host name.

Think of it like this

CoreDNS is the staff directory: dial "taskflow-db" instead of an extension number. The restaurant is split into sections (namespaces). Inside your own section the first name is enough. From another section you add the section's name ("taskflow-db.taskflow"), like a surname.

Headless Services: clusterIP: None

A headless Service gets no virtual IP and no kube-proxy balancing. Instead, DNS returns every ready pod's IP. You use it when a client must pick a specific pod (StatefulSets like postgres-0, Session 15) or balances load itself.

headless-demo.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api-headless
spec:
  clusterIP: None                   # ← the only difference that matters
  selector: { app: taskflow-api }
  ports:
    - name: http
      port: 3000
      targetPort: http
/ # nslookup taskflow-api-headless.taskflow.svc.cluster.local

Exam trap

"A Service's short name works from every namespace." ✗ The search list starts with the pod's own namespace. From elsewhere, use svc.namespace or the FQDN.

"The API reaches Postgres on localhost:5432." ✗ localhost is the API's own pod. Postgres is a different pod, so use taskflow-db:5432.

Remember

<svc>.<ns>.svc.cluster.local · short name in-namespace, svc.ns across namespaces.
Prefer DNS over env vars · headless (clusterIP: None) = DNS returns pod IPs.

Mastery check
Q1. A pod in namespace monitoring gets bad address 'taskflow-api'. Why, and which name should it use?

Its search list starts with monitoring.svc.cluster.local, so taskflow-api becomes taskflow-api.monitoring.svc.cluster.local, which doesn't exist. Use taskflow-api.taskflow or the FQDN.

Q2. Predict: you create the taskflow-db Service after the API pods started. Does taskflow-db resolve inside them? Is TASKFLOW_DB_SERVICE_HOST set?

DNS: yes, straight away, because CoreDNS watches Services live. The env var: no. Env vars are frozen at pod start, so you'd need to restart the pods to get it.

Q3. Every name lookup in every pod fails (bad address even for kubernetes.default). What do you check first?

CoreDNS itself: kubectl get pods -n kube-system -l k8s-app=kube-dns (running? ready?) and its logs. If nameserver 10.96.0.10 doesn't answer, nothing resolves.

5 NodePort & LoadBalancer

The problem

$ curl -m 5 http://10.96.120.15/health          # from your laptop
curl: (28) Connection timed out after 5001 milliseconds

The ClusterIP only exists inside the cluster's rules, so your laptop and your users can't reach it. You need a way in from outside.

The idea

Service types nest. Each type adds an outer layer on top of the previous one:

 internet ─▶ LoadBalancer  cloud LB, e.g. a3f9…elb.amazonaws.com:80      ← type: LoadBalancer adds this
               └─▶ every node's IP : 31467  (nodePort)                     ← type: NodePort adds this
                      └─▶ ClusterIP 10.98.211.40 : 80  (port)              ← every Service has this
                             └─▶ pod IPs : 3000  (targetPort)

A NodePort Service opens one port (30000–32767) on every node's IP. A LoadBalancer Service also gets the cloud-controller-manager (Session 9) to create a real external load balancer that sends traffic to those node ports.

Think of it like this

ClusterIP is the internal extension. NodePort is a numbered side door on every kitchen: door 30080 on any kitchen leads to the API counter. LoadBalancer is the landlord (the cloud) building a proper street entrance with a doorman who spreads visitors across the side doors. No landlord, no street entrance, which is why it stays <pending> on minikube.

See it: NodePort

k8s/service-nodeport.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api-nodeport
  namespace: taskflow
spec:
  type: NodePort                    # ClusterIP + a port on every node's IP
  selector: { app: taskflow-api }
  ports:
    - name: http
      port: 80                      # ClusterIP port (still works inside)
      targetPort: http              # Pod port 3000
      nodePort: 30080                # 30000–32767; omit to get a random one
$ kubectl apply -f k8s/service-nodeport.yaml
$ kubectl get svc taskflow-api-nodeport
NAME                    TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
taskflow-api-nodeport   NodePort   10.104.33.170   <none>        80:30080/TCP   5s   # port:nodePort
$ curl http://$(minikube ip):30080/health      # Linux, or VM drivers: the node IP is reachable
{"status":"ok"}
$ minikube service taskflow-api-nodeport -n taskflow --url   # macOS/Windows + Docker driver
http://127.0.0.1:58123
❗  Because you are using a Docker driver on darwin, the terminal needs to be open to run it.

80:30080 reads port:nodePort, and $(minikube ip) is the node's IP. With the Mac Docker driver that IP is unreachable, so minikube service --url tunnels to it (keep the terminal open). What it does not do: give users a friendly address. They'd need a node IP and a 30000+ port, and that node could disappear.

Build it up

LoadBalancer: ask the cloud

k8s/service-lb.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api-lb
  namespace: taskflow
spec:
  type: LoadBalancer                # NodePort + ClusterIP + an external LB from the cloud
  selector: { app: taskflow-api }
  ports:
    - name: http
      port: 80                      # port the LB listens on
      targetPort: http
$ kubectl get svc taskflow-api-lb
NAME              TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
taskflow-api-lb   LoadBalancer   10.98.211.40   <pending>     80:31467/TCP   10s   # it got a nodePort too
$ minikube tunnel                            # separate terminal, keep it open; may ask for sudo
✅  Tunnel successfully started
🏃  Starting tunnel for service taskflow-api-lb.
$ kubectl get svc taskflow-api-lb
NAME              TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
taskflow-api-lb   LoadBalancer   10.98.211.40   127.0.0.1     80:31467/TCP   1m   # Linux shows the ClusterIP here
$ curl http://127.0.0.1/health
{"status":"ok"}
# the same Service on EKS (ap-south-1):
NAME              TYPE           CLUSTER-IP     EXTERNAL-IP                                                                PORT(S)        AGE
taskflow-api-lb   LoadBalancer   172.20.87.14   a3f9c1e2b4d54e6f8a9b0c1d2e3f4a5b-1234567890.ap-south-1.elb.amazonaws.com   80:31467/TCP   2m

On EKS the cloud-controller-manager created a real AWS load balancer pointing at every node's port 31467 (options go in service.beta.kubernetes.io/aws-load-balancer-… annotations). On minikube, minikube tunnel stands in for the cloud.

port-forward: a debugging shortcut, not exposure

$ kubectl port-forward svc/taskflow-api 8080:80     # laptop:8080 → Service port 80
Forwarding from 127.0.0.1:8080 -> 3000                # resolved to the targetPort of ONE Pod
$ curl localhost:8080/health                      # second terminal
{"status":"ok"}

It tunnels through the API server to a single pod, with no load balancing, until you press Ctrl-C. It's handy for poking at the DB without exposing it: kubectl port-forward svc/taskflow-db 5432:5432 → psql -h localhost -U taskflow.

Exam trap

"A LoadBalancer Service replaces the ClusterIP and NodePort." ✗ It adds to them. A LoadBalancer Service still has a ClusterIP and a nodePort (80:31467), and the cloud LB forwards to that nodePort.

"nodePort: 8080 is fine." ✗ spec.ports[0].nodePort: Invalid value: 8080: provided port is not in the valid range. The range of valid ports is 30000-32767.

Remember

ClusterIP ⊂ NodePort ⊂ LoadBalancer: each type adds an outer layer.
minikube: minikube service --url for NodePort, minikube tunnel for LoadBalancer · port-forward = debugging only.

Mastery check
Q1. A LoadBalancer Service on minikube shows EXTERNAL-IP <pending> for 10 minutes. Why, and how do you test it?

There's no cloud-controller-manager to create a load balancer. Run minikube tunnel in another terminal and EXTERNAL-IP becomes reachable. Meanwhile its nodePort already works.

Q2. A 3-node cluster has a NodePort Service on 30080. The only API pod runs on node-2. Does curl node-1:30080 work?

Yes. Every node opens the nodePort, and node-1's kube-proxy rules forward the connection across the pod network to node-2's pod (by default, externalTrafficPolicy: Cluster).

Q3. You expose 6 HTTP microservices with 6 LoadBalancer Services on AWS. What's the downside, and the alternative?

Six cloud load balancers, each billed separately with its own hostname. Use one Ingress controller behind one LB and route by host/path (Session 12).

6 port vs targetPort vs nodePort

The problem

The endpoints look healthy, the selector is right, and yet:

$ kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api
NAME                 ADDRESSTYPE   PORTS   ENDPOINTS                             AGE
taskflow-api-x7k2p   IPv4          8080    10.244.0.13,10.244.0.14,10.244.0.15   5m
/ # wget -qO- taskflow-api/health
wget: can't connect to remote host (10.96.120.15): Connection refused

Three pods were found, so this isn't a selector problem. Look at the PORTS column.

The idea

A request crosses up to three port numbers, one per hop, and each is defined in a different place. Clients use port (inside) or nodePort (outside). The app only ever sees targetPort, and only targetPort must match what the app actually listens on.

  curl from your laptop                     another pod in the cluster
          │                                          │
          ▼                                          ▼
  192.168.49.2:30080   ── nodePort ──►   10.96.120.15:80   (= taskflow-api:80)   ── port
  (any node's IP)                              │  kube-proxy DNAT + load-balance
                                               ▼
                                  10.244.0.13:3000   ── targetPort  (= containerPort "http")
                                  node server.js listening on PORT=3000
Think of it like this

Three numbers on one call. nodePort is the side-door number (30080) an outsider walks up to. port is the counter's extension (80) that staff dial. targetPort is the station's own extension (3000), where the cook actually picks up. If the switchboard forwards to extension 8080 and the cook sits at 3000, the phone rings at an empty desk: connection refused.

See it: the four fields

FieldDefined inWho connects to itDefault / range
containerPortPod/Deployment ports[]Nobody directly. It documents the app port and gives it a name.—
targetPortService ports[]kube-proxy's rules, on the pod IPSame as port if omitted; a number or a name
portService ports[]Clients inside the cluster: taskflow-api:80Required
nodePortService ports[] (NodePort/LB only)Clients outside: <NodeIP>:3008030000–32767, random if omitted

Now the opening puzzle is easy. The EndpointSlice's PORTS column is the resolved targetPort: 8080. TaskFlow listens on 3000, so kube-proxy forwards to a port where nothing is listening. Bypassing the Service proves it:

/ # wget -qO- 10.244.0.13:3000/health                 # straight to a pod on the real port: fine
{"status":"ok"}

Fix: targetPort: http (or 3000) and re-apply. What it does not do: port doesn't have to equal anything in the pod. 80 → 3000 is normal, and lets clients use the default HTTP port. The same symptom (endpoints present, connection refused) also appears when the app binds to 127.0.0.1 instead of 0.0.0.0 (Session 4).

Build it up: named ports

k8s/deployment.yaml (excerpt) + k8s/service.yaml (excerpt)
# Deployment → Pod template
          ports:
            - name: http              # the name
              containerPort: 3000     # the number lives only here
# Service
  ports:
    - name: http
      port: 80
      targetPort: http                # refer by name, not 3000
  • Moving the app to 8080? Change containerPort (and PORT) only, and the Service follows the name.
  • Different pods behind one Service can use different numbers for the same name (during a migration, say).
  • Pods without the named port are skipped, a cheap guard against an over-broad selector (section 3).

Docker comparison: in docker run -p 8080:3000, 8080 ≈ nodePort and 3000 ≈ targetPort. Kubernetes adds the middle layer, port, on the Service's own IP.

Exam trap

"port must equal containerPort." ✗ Only targetPort must match the container. port is whatever clients should dial.

"Changing containerPort in the Deployment makes the app listen on the new port." ✗ containerPort is documentation. The app listens wherever its code or PORT env says, so change both together.

Remember

nodePort (node, 30000–32767) → port (Service ClusterIP) → targetPort (pod = containerPort).
No endpoints → selector. Endpoints but refused → targetPort (or a 127.0.0.1 bind).

Mastery check
Q1. A Service has port: 80, targetPort: 3000, nodePort: 30080. Which port does another pod use, which does your browser use, and where must the app listen?

A pod uses taskflow-api:80; the browser uses <NodeIP>:30080; the app listens on 3000 (targetPort).

Q2. Predict: you omit targetPort from a Service with port: 80. TaskFlow listens on 3000. What happens?

targetPort defaults to port, i.e. 80. The endpoints show port 80, nothing listens there, and clients get "connection refused". Always set targetPort (ideally to the name http).

Q3. The team moves TaskFlow to port 8080. With targetPort: http, which files change? With targetPort: 3000?

Named: only the Deployment (containerPort: 8080 and PORT=8080), and the Service follows the name. Numeric: the Service too, or traffic keeps going to 3000.

★ Putting it all together

The big idea

Every TaskFlow pod gets its own routable IP from the CNI, but those IPs change on every rollout. A Service selects pods by label, the EndpointSlice controller lists the ready ones, and kube-proxy on every node load-balances the stable ClusterIP across them. CoreDNS names it, so the API dials taskflow-db:5432 and other pods dial taskflow-api:80, which lands on targetPort 3000. To reach the API from outside, wrap it in a NodePort (dev) or LoadBalancer (cloud). For HTTP, an Ingress is usually better (next session).

Final mastery check — combine everything
Q1. A web pod runs wget taskflow-api/health. Trace the request hop by hop, naming the component or file at each step.

/etc/resolv.conf (written by the kubelet) sends the lookup to CoreDNS (10.96.0.10). The search list expands it to taskflow-api.taskflow.svc.cluster.local → ClusterIP 10.96.120.15. The connection to 10.96.120.15:80 is DNATed by kube-proxy's rules (built from the EndpointSlice) to a ready pod, e.g. 10.244.0.14:3000 (targetPort http), and the CNI's pod network carries it there, across nodes if needed.

Q2. A rollout (Session 10) replaced all three API pods. What did you have to change in the web tier's config, and which components updated what?

Nothing. The web tier uses the name taskflow-api, and the name and ClusterIP never changed. The EndpointSlice controller swapped the old pod IPs for the new ones as each new pod turned ready, and kube-proxy rewrote the rules on every node.

Q3. Map each symptom to its likely layer: (a) bad address 'taskflow-api'; (b) Connection refused and the EndpointSlice is empty; (c) Connection refused and the EndpointSlice lists 3 IPs on port 80.

(a) DNS: wrong namespace (use taskflow-api.taskflow), a typo, or CoreDNS down. (b) Selector mismatch, or no pods ready (readiness failing). (c) targetPort wrong (80 vs the app's 3000, perhaps from omitting it), or the app bound to 127.0.0.1.

Q4. The taskflow-api Service has port: 80, targetPort: http and type NodePort with nodePort 30080. How do you reach it from (a) a pod in taskflow, (b) a pod in default, (c) your laptop on Linux minikube, (d) a Mac with the Docker driver?

(a) taskflow-api:80 · (b) taskflow-api.taskflow:80 · (c) http://$(minikube ip):30080 · (d) the URL from minikube service taskflow-api -n taskflow --url (or kubectl port-forward svc/taskflow-api 8080:80 for quick debugging).

Q5. True or false, with reasons: "A LoadBalancer Service gives each pod a public IP, and kube-proxy forwards every packet through its own process."

False twice. The LB gets one external address and forwards to the nodePort on the nodes. Pods keep their private pod IPs. kube-proxy only writes kernel rules (iptables/nftables), and the kernel rewrites packets, so no Kubernetes process sits in the data path.

Q6. You add a second container to the API pods that listens on 9090 for metrics. How do you expose it through the same Service, and what becomes mandatory?

Name the container port (name: metrics, containerPort: 9090) and add a second Service port (name: metrics, port: 9090, targetPort: metrics). With more than one port, every Service port must be named. Both containers share the pod IP (Session 10), so the same endpoints serve both ports.
