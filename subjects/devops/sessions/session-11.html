1 Pod networking

Explain like I'm 5

Every flat (Pod) in the city gets its own street address, and anyone can post a letter to any address directly — no forwarding office in between.

The Kubernetes network model (the rules every cluster must follow)

  1. Every Pod gets its own IP (from its node's podCIDR).
  2. Any Pod can reach any other Pod, on any node, using that IP — without NAT.
  3. Node agents (kubelet) can reach all Pods on their node.
  4. Containers in one Pod share the IP and talk over localhost (a tiny pause container holds the network namespace).

Compare Docker (Session 8): there you publish ports with -p and containers on different hosts can't see each other. In K8s, flat Pod-to-Pod networking is guaranteed.

CNI plugins implement the model

Kubernetes doesn't do Pod networking itself. The kubelet asks the runtime to call a CNI (Container Network Interface) plugin, which creates the veth pair, assigns the IP and sets routes.

Key takeaway

Pod IPs are real but ephemeral — every reschedule, rollout or scale event changes them. Never put a Pod IP in config. You need a stable front door: a Service.

Recap Every Pod has an IP; Pod ↔ Pod works across nodes without NAT; a CNI plugin (Calico, Flannel, Cilium…) makes it happen. Pod IPs change constantly → Services.

2 Services, ClusterIP & selectors

Explain like I'm 5

A Service is a shop's phone number. Staff (Pods) come and go, but you always dial the same number and whoever is free picks up.

A Service gives a set of Pods (picked by a label selector):

  • a stable virtual IP — the ClusterIP — that never changes while the Service exists;
  • a stable DNS name: taskflow-api (§3);
  • L4 (TCP/UDP) load balancing across the ready matching Pods.
k8s/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api                # becomes the DNS name
  namespace: taskflow
  labels:
    app: taskflow
    tier: api
spec:
  type: ClusterIP                   # default: reachable only inside the cluster
  selector:                         # send traffic to Pods with BOTH labels
    app: taskflow
    tier: api
  ports:
    - name: http                    # required once a Service has >1 port; good habit anyway
      protocol: TCP                 # default TCP; UDP/SCTP also possible
      port: 80                      # what clients dial: taskflow-api:80
      targetPort: http              # the Pod's port named "http" (= 3000 in deployment.yaml)
FieldMeaningGotcha
metadata.nameService name = DNS name inside the namespace.Must be a valid DNS label (lowercase, -, ≤ 63 chars).
spec.typeClusterIP (default), NodePort, LoadBalancer, ExternalName.Each type builds on the previous one (§4).
spec.selectorPlain label map (equality only, ANDed).No matchLabels/matchExpressions here — unlike Deployments.
ports[].portPort on the ClusterIP.Can differ from the app's port.
ports[].targetPortPort on the Pod (number or container port name).Defaults to port if omitted. Full story in §5.
spec.clusterIPAuto-assigned from the service CIDR (minikube: 10.96.0.0/12).Set to None for a headless Service (§3).

Endpoints / EndpointSlices — the Service's live Pod list

The EndpointSlice controller watches Pods matching the selector and writes their ready IP:port pairs into EndpointSlice objects. Not ready (readiness probe failing) = not listed = no traffic.

$ kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api
NAME                 ADDRESSTYPE   PORTS   ENDPOINTS                             AGE
taskflow-api-x7k2p   IPv4          3000    10.244.0.13,10.244.0.14,10.244.0.15   2m

$ kubectl get endpoints taskflow-api            # older API, still works
Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice
NAME           ENDPOINTS                                            AGE
taskflow-api   10.244.0.13:3000,10.244.0.14:3000,10.244.0.15:3000   2m

How the ClusterIP actually works: kube-proxy

  • No process listens on 10.96.120.15. It's a virtual IP.
  • kube-proxy (one per node) watches Services + EndpointSlices and writes kernel rules: "packet to 10.96.120.15:80 → DNAT to a random endpoint, port 3000".
  • Modes: iptables (default), nftables (GA since 1.33, the recommended future), ipvs (deprecated in 1.35). Cilium can replace kube-proxy entirely with eBPF.
$ minikube ssh -- sudo iptables -t nat -L KUBE-SERVICES -n | grep taskflow
KUBE-SVC-K2Q3ZVJ7VQX5DJ3O  tcp  --  0.0.0.0/0  10.96.120.15  /* taskflow/taskflow-api:http cluster IP */ tcp dpt:80
KUBE-SVC-5QZKX2NYV4C7HJ6M  tcp  --  0.0.0.0/0  10.96.48.200  /* taskflow/taskflow-db:postgres cluster IP */ tcp dpt:5432

Because it's only NAT rules, ping 10.96.120.15 usually fails even when the Service works. Test with TCP (wget/curl), not ping.

Selector bugs (the #1 Service problem)

Example 1: "Service has no endpoints"

Someone writes selector: { app: taskflow-api } but the Pods are labelled app=taskflow.

$ kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- taskflow-api/health
wget: can't connect to remote host (10.96.120.15): Connection refused
$ kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api
NAME                 ADDRESSTYPE   PORTS     ENDPOINTS   AGE
taskflow-api-x7k2p   IPv4          <unset>   <unset>     1m
$ kubectl get svc taskflow-api -o jsonpath='{.spec.selector}'
{"app":"taskflow-api"}
$ kubectl get pods -l app=taskflow-api
No resources found in taskflow namespace.          # ← selector matches nothing
$ kubectl get pods --show-labels | head -2
NAME                            READY   STATUS    RESTARTS   AGE   LABELS
taskflow-api-5b9c4f7d8b-fq5rl   1/1     Running   0          9m    app=taskflow,pod-template-hash=5b9c4f7d8b,tier=api

Fix: make the Service selector a subset of the Pod labels (app: taskflow, tier: api) and re-apply. Endpoints appear within a second. Same symptom if every Pod is failing readiness.

Example 2: selector too broad

selector: { app: taskflow } with targetPort: 3000 also matches the Postgres Pod (app=taskflow,tier=db):

$ kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api
NAME                 ADDRESSTYPE   PORTS   ENDPOINTS                                         AGE
taskflow-api-x7k2p   IPv4          3000    10.244.0.13,10.244.0.14,10.244.0.15,10.244.0.20   1m

~1 in 4 requests go to Postgres on port 3000 → random "connection refused". Fix: add tier: api to the selector. (A named targetPort: http would also have skipped the DB Pod, since it has no port named http.)

Generate a Service with kubectl expose

$ kubectl expose deployment taskflow-api --port=80 --target-port=3000 --dry-run=client -o yaml
apiVersion: v1
kind: Service
metadata:
  labels:
    app: taskflow
    tier: api
  name: taskflow-api            # name defaults to the Deployment's name
spec:
  ports:
  - port: 80
    protocol: TCP
    targetPort: 3000
  selector:                     # copied from the Deployment's selector
    app: taskflow
    tier: api
status:
  loadBalancer: {}

Drop --dry-run=client -o yaml to create it directly (service/taskflow-api exposed); add --type=NodePort for §4. For the repo, save the YAML and apply it.

Recap Service = stable ClusterIP + DNS name + load balancing over ready Pods matched by label selector. EndpointSlices hold the live Pod list; empty list = selector or readiness problem. kube-proxy turns it into NAT rules on every node.

3 Kubernetes DNS & service discovery

Explain like I'm 5

Instead of memorising the shop's phone number, you look up "taskflow-db" in the cluster's phone book.

  • Service discovery = how a client finds where a service lives. In K8s: DNS (preferred) or injected environment variables.
  • CoreDNS runs as a Deployment in kube-system, behind a Service still called kube-dns. It watches Services and answers DNS queries for them.
$ kubectl get deploy,svc -n kube-system -l k8s-app=kube-dns
NAME                      READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/coredns   1/1     1            1           3d

NAME               TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)                  AGE
service/kube-dns   ClusterIP   10.96.0.10   <none>        53/UDP,53/TCP,9153/TCP   3d

DNS names you can use

Format: <service>.<namespace>.svc.<cluster-domain>, cluster domain = cluster.local.

Name queriedResolves toWorks from
taskflow-db10.96.48.200 (ClusterIP)Pods in the same namespace (taskflow)
taskflow-db.taskflowsameAny namespace
taskflow-db.taskflow.svc.cluster.localsame (FQDN)Any namespace
_postgres._tcp.taskflow-db.taskflow.svc.cluster.localSRV record: port 5432 + hostAny (needs a named port)
Headless Service nameThe Pod IPs directly (below)Any

So TaskFlow's connection string in K8s is postgres://taskflow:<pw>@taskflow-db:5432/taskflow — same as Compose's db, just a different host name.

Why short names work: /etc/resolv.conf in every Pod

$ kubectl exec deploy/taskflow-api -- cat /etc/resolv.conf
search taskflow.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
LineMeaning
nameserver 10.96.0.10Send DNS queries to the kube-dns Service (CoreDNS), written by the kubelet.
search taskflow.svc.cluster.local ...Suffixes tried in order. taskflow-db → taskflow-db.taskflow.svc.cluster.local ✔. The first entry is the Pod's own namespace — that's why short names only work in-namespace.
options ndots:5Names with fewer than 5 dots try the search list first. api.github.com causes a few wasted lookups before the real one; a trailing dot (api.github.com.) skips them.

Headless Services (clusterIP: None)

No virtual IP, no kube-proxy load balancing — DNS returns every ready Pod IP. Used when the client must pick a specific Pod (StatefulSets like postgres-0, Session 15) or does its own balancing.

headless-demo.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api-headless
spec:
  clusterIP: None                   # ← the only difference that matters
  selector: { app: taskflow, tier: api }
  ports:
    - name: http
      port: 3000
      targetPort: http

Common mistakes
  • bad address 'taskflow-api' → wrong namespace (use taskflow-api.taskflow), typo, or CoreDNS down (kubectl get pods -n kube-system -l k8s-app=kube-dns).
  • Using localhost:5432 from the API to reach Postgres. localhost is the API's own Pod; use taskflow-db.
  • busybox's nslookup may print extra NXDOMAIN lines for search domains it tries — harmless; look for the Address: line.
Recap CoreDNS answers svc.ns.svc.cluster.local; the search list makes svc work in-namespace and svc.ns across namespaces. Prefer DNS over env vars. Headless = DNS returns Pod IPs.

4 NodePort & LoadBalancer

Explain like I'm 5

ClusterIP is an internal extension number. NodePort opens a side door on every building. LoadBalancer hires a receptionist at the main gate.

NodePort — open a port on every node

k8s/service-nodeport.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api-nodeport
  namespace: taskflow
spec:
  type: NodePort                    # ClusterIP + a port on every node's IP
  selector: { app: taskflow, tier: api }
  ports:
    - name: http
      port: 80                      # ClusterIP port (still works inside)
      targetPort: http              # Pod port 3000
      nodePort: 30080                # 30000–32767; omit to get a random one
$ kubectl apply -f k8s/service-nodeport.yaml
service/taskflow-api-nodeport created
$ kubectl get svc taskflow-api-nodeport
NAME                    TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
taskflow-api-nodeport   NodePort   10.104.33.170   <none>        80:30080/TCP   5s   # port:nodePort

# Linux, or VM drivers: the node IP is reachable
$ curl http://$(minikube ip):30080/health
{"status":"ok"}

# macOS/Windows with the Docker driver: node IP is NOT reachable → let minikube tunnel it
$ minikube service taskflow-api-nodeport -n taskflow --url
http://127.0.0.1:58123
❗  Because you are using a Docker driver on darwin, the terminal needs to be open to run it.
$ curl http://127.0.0.1:58123/health        # from a second terminal
{"status":"ok"}

LoadBalancer — ask the cloud for an external load balancer

k8s/service-lb.yaml
apiVersion: v1
kind: Service
metadata:
  name: taskflow-api-lb
  namespace: taskflow
spec:
  type: LoadBalancer                # NodePort + ClusterIP + an external LB from the cloud
  selector: { app: taskflow, tier: api }
  ports:
    - name: http
      port: 80                      # port the LB listens on
      targetPort: http
  • The cloud-controller-manager sees the Service and creates a real load balancer (AWS NLB/ELB, Azure LB, GCP LB), pointing at every node's nodePort.
  • Cloud-specific behaviour is set with annotations, e.g. service.beta.kubernetes.io/aws-load-balancer-... on EKS.
  • minikube has no cloud → EXTERNAL-IP stays <pending> until you run minikube tunnel.

port-forward — debugging shortcut, not exposure

$ kubectl port-forward svc/taskflow-api 8080:80     # laptop:8080 → Service port 80
Forwarding from 127.0.0.1:8080 -> 3000
Forwarding from [::1]:8080 -> 3000                # resolved to the targetPort of ONE Pod
$ curl localhost:8080/health                      # second terminal
{"status":"ok"}

It tunnels through the API server to a single Pod — no load balancing, dies when you press Ctrl-C. Great for checking a Service/DB without exposing it (kubectl port-forward svc/taskflow-db 5432:5432 → psql -h localhost -U taskflow).

Service types compared (exam favourite)

For many HTTP services behind one entry point, use an Ingress instead of many LoadBalancers (Session 12).

Common mistakes
  • nodePort: 8080 → spec.ports[0].nodePort: Invalid value: 8080: provided port is not in the valid range. The range of valid ports is 30000-32767.
  • Waiting forever for <pending> on minikube/kind — there's no cloud. Run minikube tunnel (or install MetalLB on bare metal).
  • On AWS, NodePort traffic is blocked unless the node Security Group allows 30000–32767 (Session 21).
Recap ClusterIP ⊂ NodePort ⊂ LoadBalancer — each type adds an outer layer. minikube: minikube service --url for NodePort, minikube tunnel for LoadBalancer. port-forward is for debugging only.

5 port vs targetPort vs nodePort

Explain like I'm 5

nodePort is the building's side door, port is the reception desk's extension, targetPort is the actual desk where the worker sits.

  curl from your laptop                     another Pod in the cluster
          │                                          │
          ▼                                          ▼
  192.168.49.2:30080   ── nodePort ──►   10.96.120.15:80   (= taskflow-api:80)   ── port
  (any node's IP)                              │  kube-proxy DNAT + load-balance
                                               ▼
                                  10.244.0.13:3000   ── targetPort  (= containerPort "http")
                                  node server.js listening on PORT=3000
FieldDefined inWho connects to itDefault / range
containerPortPod/Deployment ports[]Nobody directly — documents the app port and gives it a name—
targetPortService ports[]kube-proxy, on the Pod IPSame as port if omitted; number or name
portService ports[]Clients inside the cluster: taskflow-api:80Required
nodePortService ports[] (NodePort/LB only)Clients outside: <NodeIP>:3008030000–32767, random if omitted

Docker analogy: docker run -p 8080:3000 → 8080 ≈ nodePort, 3000 ≈ targetPort. Kubernetes adds the middle layer, port, on the Service's own IP.

Named ports

k8s/deployment.yaml (excerpt) + k8s/service.yaml (excerpt)
# Deployment → Pod template
          ports:
            - name: http              # the name
              containerPort: 3000     # the number lives only here
# Service
  ports:
    - name: http
      port: 80
      targetPort: http                # refer by name, not 3000
  • Move the app to 8080? Change containerPort (and PORT) only — the Service follows the name.
  • Different Pods behind one Service can use different numbers for the same name (e.g. during a migration).
  • Pods that don't have the named port are skipped — a cheap guard against over-broad selectors (§2).
Worked example: endpoints exist but connection refused

Service has port: 80, targetPort: 8080; TaskFlow listens on 3000.

$ kubectl get endpointslices -l kubernetes.io/service-name=taskflow-api
NAME                 ADDRESSTYPE   PORTS   ENDPOINTS                             AGE

Key takeaway

Clients use port (inside) or nodePort (outside). The app only ever sees targetPort. Only targetPort must equal what the app really listens on.

Recap nodePort (node, 30000–32767) → port (Service ClusterIP) → targetPort (Pod = containerPort). Name your ports and point targetPort at the name.

★ Putting it all together

The big idea

Every TaskFlow Pod gets its own routable IP from the CNI, but those IPs change on every rollout. A Service selects the Pods by label, publishes their ready IPs as EndpointSlices, and kube-proxy load-balances its stable ClusterIP across them. CoreDNS names it, so the API simply dials taskflow-db:5432 and other Pods dial taskflow-api:80, which lands on targetPort 3000. To reach the API from outside, wrap it in a NodePort (dev) or LoadBalancer (cloud) — or, better for HTTP, an Ingress (next session).

Quick self-check

Service: port: 80, targetPort: 3000, nodePort: 30080. Which port does another Pod use, which does your browser use, and where must the app listen?

Pod → taskflow-api:80; browser → <NodeIP>:30080; the app listens on 3000 (targetPort).

kubectl get endpoints taskflow-api shows <none>. Give two causes.

(1) The selector doesn't match any Pod's labels; (2) matching Pods exist but none are Ready (readiness probe failing / still starting).

A Pod in namespace default gets bad address 'taskflow-api'. Why, and what name should it use?

The search list starts with the Pod's own namespace (default.svc.cluster.local). Use taskflow-api.taskflow or the FQDN taskflow-api.taskflow.svc.cluster.local.

Why not just connect to Pod IPs directly?

Pod IPs are ephemeral (new IP on every restart/reschedule/rollout) and there are several replicas; a Service gives one stable IP + DNS name and load-balances across ready Pods.

A LoadBalancer Service on minikube shows EXTERNAL-IP <pending>. Why, and how do you test it?

No cloud-controller-manager to create a load balancer. Run minikube tunnel in another terminal; EXTERNAL-IP becomes reachable (127.0.0.1 on macOS Docker driver).

What does a DNS lookup of a headless Service return, versus a normal ClusterIP Service?

Headless (clusterIP: None): one A record per ready Pod IP. Normal: a single A record with the ClusterIP.

Endpoints list three Pod IPs, but requests to the Service get "Connection refused". What's the likely bug?

targetPort doesn't match the port the app listens on (or the app binds to 127.0.0.1). Check the PORTS column of the EndpointSlice vs the container's port.
