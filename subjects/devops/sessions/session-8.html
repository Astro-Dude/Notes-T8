1 Docker networking & drivers

Explain like I'm 5

A Docker network is a private Wi-Fi for containers. Containers on the same network can talk; containers on different networks can't hear each other.

  • Every container gets its own network namespace: its own interfaces, IP, routing table and ports. localhost inside a container = that container only.
  • Docker connects containers to virtual networks using a network driver. Three networks exist out of the box:
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
5c1f3e2a9b10   bridge    bridge    local
a8d2c6e4f7b3   host      host      local
0e9b7d1c2f45   none      null      local
DriverWhat you getDNS by nameUse for
bridge (default network)Private subnet 172.17.0.0/16 on the docker0 bridge, NAT to the outside❌Quick one-off containers
user-defined bridgeYour own isolated subnet (docker network create)✅Multi-container apps on one host (Compose uses this)
hostNo network isolation — container uses the host's interfaces; -p is ignoredn/aMax performance, many ports. Linux only (Docker Desktop: opt-in setting)
noneOnly loopback lon/aFully isolated batch jobs
overlayOne network spanning many hosts (VXLAN)✅Docker Swarm (K8s uses CNI instead, S11)
macvlan / ipvlanContainer gets an IP on your physical LAN—Legacy apps that must look like a real machine

How the default bridge works on a Linux host:

host (Ubuntu)                                   eth0 192.168.1.20 ──▶ internet
┌──────────────────────────────────────────────────────┐
│  docker0 (bridge) 172.17.0.1                         │
│     ├── veth ─── container web1   172.17.0.2         │
│     └── veth ─── container web2   172.17.0.3         │
│  iptables: MASQUERADE (outbound NAT), DNAT for -p    │
└──────────────────────────────────────────────────────┘
$ docker run -d --name web1 nginx:1.28-alpine
$ docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web1
172.17.0.2
$ docker run --rm --network none alpine:3.22 ip addr
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo              ← no eth0 at all
$ docker run -d --name web-host --network host nginx:1.28-alpine     # now on host port 80 directly
Recap Each container has its own network stack. Default bridge = NAT'd private subnet without name resolution; use user-defined bridges for real apps; host removes isolation; none removes networking.

2 Container-to-container communication

Explain like I'm 5

On a user-defined network Docker keeps a phone book, so the API can just "call db" instead of remembering db's number.

The default bridge has no name resolution

$ docker run -d --name db -e POSTGRES_PASSWORD=devpass postgres:16-alpine
$ docker run --rm busybox:1.36 ping -c1 db
ping: bad address 'db'
$ docker rm -f db

User-defined bridge: TaskFlow API → db by name

$ docker network create taskflow-net
9f2c4e7a1b3d58e6c0a9f1b2d3e4c5a6b7f8091a2b3c4d5e6f708192a3b4c5d6

$ docker run -d --name db --network taskflow-net \
    -e POSTGRES_USER=taskflow -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=taskflow \
    postgres:16-alpine

$ docker run -d --name api --network taskflow-net -p 3000:3000 \
    -e DATABASE_URL=postgres://taskflow:devpass@db:5432/taskflow \
    shauryav/taskflow-api:1.0

$ docker run --rm --network taskflow-net busybox:1.36 ping -c1 db
PING db (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.091 ms

--- db ping statistics ---
1 packets transmitted, 1 packets received, 0% packet loss

$ curl -s localhost:3000/tasks
[]
  • Docker runs an embedded DNS server at 127.0.0.11 in every container on a user-defined network. It answers with the container name (and any --network-alias).
  • Containers talk to each other on the container port (db:5432). Publishing (-p) is only for traffic from outside Docker.
$ docker exec api cat /etc/resolv.conf | grep -v '^#'
nameserver 127.0.0.11
options ndots:0

$ docker network inspect taskflow-net --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
db 172.18.0.2/16
api 172.18.0.3/16

# attach a running container to a second network (and give it an extra DNS name)
$ docker network connect --alias web taskflow-net web1
$ docker inspect -f '{{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}' web1
bridge taskflow-net
$ docker network disconnect bridge web1

Common mistakes
  • DATABASE_URL=postgres://…@localhost:5432/… inside the API container → Error: connect ECONNREFUSED 127.0.0.1:5432. localhost is the API container itself; use the name db.
  • Using the host-published port between containers (db:15432) — inside the network it's always the container port.
  • Need to reach a service on your laptop from a container? Use host.docker.internal (Docker Desktop; on Linux add --add-host=host.docker.internal:host-gateway).
Recap docker network create → --network on each container → reach others as name:containerPort. Different networks = no connectivity.

3 Port mapping

Explain like I'm 5

The host is a building with numbered front doors. -p 8080:3000 means "anyone knocking on door 8080 gets sent to room 3000 of this container".

browser ── http://192.168.1.20:8080 ──▶ host :8080 ──(iptables DNAT)──▶ 172.18.0.3:3000  (api container)
FlagMeaning
-p 8080:3000Host port 8080 on all interfaces (0.0.0.0 and [::]) → container port 3000. Format is always HOST:CONTAINER.
-p 127.0.0.1:8080:3000Only reachable from this machine (good for DBs, admin UIs).
-p 3000Random free host port → container 3000.
-PEvery EXPOSEd port → random host ports (S7).
-p 5353:53/udpUDP (default is TCP).
-p 8080-8081:3000-3001Port ranges.
 
$ docker run -d --name api-pub -p 8080:3000 shauryav/taskflow-api:1.0
$ docker port api-pub
3000/tcp -> 0.0.0.0:8080
3000/tcp -> [::]:8080
$ docker ps --format 'table {{.Names}}\t{{.Ports}}'
NAMES     PORTS
api-pub   0.0.0.0:8080->3000/tcp, [::]:8080->3000/tcp

# same host port twice
$ docker run -d --name api-pub2 -p 8080:3000 shauryav/taskflow-api:1.0
docker: Error response from daemon: driver failed programming external connectivity on endpoint api-pub2 (3c5e…): Bind for 0.0.0.0:8080 failed: port is already allocated.

# host port held by a non-Docker process (e.g. `node server.js` running on the host)
$ docker run -d --name api-pub3 -p 3000:3000 shauryav/taskflow-api:1.0
docker: Error response from daemon: … 0.0.0.0:3000 … bind: address already in use.
$ sudo ss -tulpn | grep ':3000'
tcp   LISTEN 0   511   0.0.0.0:3000   0.0.0.0:*   users:(("node",pid=48211,fd=21))

Fix: pick another host port (-p 8081:3000), or stop the other container/process.

Example: app bound to 127.0.0.1 inside the container 
# server.js has app.listen(3000, '127.0.0.1')
$ curl localhost:8080/health
curl: (56) Recv failure: Connection reset by peer

The port mapping works, but the app only accepts connections from inside its own namespace. Listen on 0.0.0.0 (S4) — Docker's NAT delivers traffic to the container's eth0, not its loopback.

Common mistakes
  • Reversing the order: -p 3000:8080 maps host 3000 to container 8080, where nothing listens.
  • On an Ubuntu server with ufw: Docker writes its own iptables rules, so -p 5432:5432 is reachable from the internet even if ufw denies 5432. Bind to 127.0.0.1 or don't publish internal services at all.
Recap -p HOST:CONTAINER, optionally prefixed with a host IP. Publish only the entry point (web), keep DBs internal. App must listen on 0.0.0.0.

4 Docker volumes

Explain like I'm 5

A container is a hotel room — cleaned out when you leave. A volume is a locker you rent: whatever you put in stays, no matter how many rooms you check in and out of.

  • A container's writable layer is deleted with docker rm. Anything that must survive (DB files, uploads) goes on a mount.
  • A named volume is storage managed by Docker, stored at /var/lib/docker/volumes/<name>/_data on Linux (inside the Docker Desktop VM on Mac/Windows).
┌──────────── container ────────────┐
│ /var/lib/postgresql/data  ────────┼──▶ volume  pgdata   (Docker-managed area)
│ /app                      ────────┼──▶ bind    /home/shaurya/taskflow (any host path)
│ /tmp                      ────────┼──▶ tmpfs   host RAM, gone when container stops
└───────────────────────────────────┘

Demo: Postgres data survives docker rm

$ docker volume create pgdata
pgdata
$ docker run -d --name db --network taskflow-net \
    -e POSTGRES_USER=taskflow -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=taskflow \
    -v pgdata:/var/lib/postgresql/data \
    postgres:16-alpine
$ docker exec db psql -U taskflow -c "CREATE TABLE notes(msg text);"
CREATE TABLE
$ docker exec db psql -U taskflow -c "INSERT INTO notes VALUES ('survives rm');"
INSERT 0 1

$ docker rm -f db                         # container gone…
$ docker run -d --name db --network taskflow-net \
    -e POSTGRES_USER=taskflow -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=taskflow \
    -v pgdata:/var/lib/postgresql/data postgres:16-alpine
$ docker exec db psql -U taskflow -c "SELECT * FROM notes;"
     msg
-------------
 survives rm
(1 row)

$ docker volume prune -a         # also unused NAMED volumes — data loss!
  • The long hex name above is an anonymous volume: the postgres image declares VOLUME /var/lib/postgresql/data, so a container started without -v gets a random-named one. Hard to find again — always name your volumes.
  • docker rm -v <ctr> and docker run --rm delete anonymous volumes with the container; named volumes are never deleted implicitly.
  • Long syntax (same thing): --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data.

Backups

# logical DB backup (preferred for databases)
$ docker exec db pg_dump -U taskflow taskflow > taskflow-2026-10-09.sql
# raw copy of any volume via a throwaway container
$ docker run --rm -v pgdata:/data:ro -v "$(pwd)":/backup alpine:3.22 \
    tar czf /backup/pgdata-2026-10-09.tgz -C /data .
Common mistakes
  • Typo in the volume name (-v pgdta:/var/lib/…) silently creates a new empty volume → "my data is gone".
  • postgres:18+ moved its data directory: mount the volume at /var/lib/postgresql, not …/data. This page uses postgres:16, where /var/lib/postgresql/data is correct.
  • Copying a live Postgres volume with tar can produce a corrupt backup — stop the container first or use pg_dump.
Recap Named volume = persistent, Docker-managed storage that outlives containers. -v name:/path. Prune carefully: prune = anonymous only, prune -a = named too.

5 Bind mounts & tmpfs

Explain like I'm 5

A bind mount is a window from the container straight into a folder on your laptop. Change a file on either side, the other side sees it instantly.

  • A bind mount maps an existing host path into the container. You choose the path; Docker doesn't manage it.
  • Main uses: live code reload in development, injecting config files (:ro), sharing host files like /var/run/docker.sock (dangerous — full control of Docker).

Dev live-reload for TaskFlow

$ cd ~/taskflow
$ docker run -d --name api-dev --network taskflow-net -p 3000:3000 \
    -e DATABASE_URL=postgres://taskflow:devpass@db:5432/taskflow \
    -v "$(pwd)":/app \
    -v /app/node_modules \
    shauryav/taskflow-api:1.0 node --watch server.js
$ docker logs -f api-dev
listening on 3000
Restarting 'server.js'
listening on 3000     ← after you saved server.js on the host
PartMeaning
-v "$(pwd)":/appHost project folder replaces the image's /app. Quote it — paths with spaces break otherwise.
-v /app/node_modulesAnonymous volume over node_modules so the image's Linux-built modules aren't hidden by your host (macOS) folder.
node --watch server.jsOverrides CMD; Node restarts on file change (or use nodemon).

Read-only config & the two syntaxes

# -v short syntax, read-only
$ docker run -d --name web -p 8080:80 \
    -v "$(pwd)"/web/nginx.conf:/etc/nginx/conf.d/default.conf:ro nginx:1.28-alpine
# --mount long syntax — same effect, explicit keys
$ docker run -d --name web -p 8080:80 \
    --mount type=bind,src="$(pwd)"/web/nginx.conf,dst=/etc/nginx/conf.d/default.conf,readonly \
    nginx:1.28-alpine
Host path doesn't existResult
-v ./nginx.conf:/etc/nginx/conf.d/default.confDocker creates an empty directory named nginx.conf → error mounting … not a directory: Are you trying to mount a directory onto a file (or vice-versa)?
--mount type=bind,src=./nginx.conf,…Fails fast: invalid mount config for type "bind": bind source path does not exist: /home/shaurya/taskflow/nginx.conf

tmpfs

$ docker run -d --read-only --tmpfs /tmp:size=64m shauryav/taskflow-api:1.0
$ docker run -d --mount type=tmpfs,dst=/tmp,tmpfs-size=64m shauryav/taskflow-api:1.0

In-memory, never written to disk, gone when the container stops (Linux only). Pairs well with --read-only root filesystems.

Volumes vs bind mounts vs tmpfs

Named volumeBind mounttmpfs
Where data lives/var/lib/docker/volumes/…Any host path you pickHost RAM
Managed by Docker (docker volume ls)✅❌❌
Survives docker rm✅✅ (it's your folder)❌
Pre-filled from image✅ empty volume gets the image's files at that path❌ host folder hides image files❌

Rule of thumb: -v value starting with / or . = bind mount; a plain name = named volume.

Common mistake (Linux)

A container running as root writes files into your bind-mounted folder → they show up owned by root and you can't edit them. Run with --user "$(id -u):$(id -g)" or use an image with a matching non-root user (node = uid 1000 = usually your user).

Recap Bind mount = host folder inside the container (dev, config). Volume = Docker-managed persistence (DBs). tmpfs = RAM only. Prefer --mount when you want errors instead of surprises.

6 Docker Compose: the files

Explain like I'm 5

Instead of shouting ten long docker run commands, you write one shopping list. docker compose up buys everything on it, in the right order.

  • Docker Compose describes a multi-container app — services, networks, volumes — in one YAML file and runs it with docker compose (v2, a Docker CLI plugin; the old Python docker-compose is retired).
  • Default file name compose.yaml (docker-compose.yml still works). The top-level version: key is obsolete — leave it out.
  • Compose creates a network per project, so every service can reach every other by its service name (db, redis…).
taskflow/
├── compose.yaml              # the stack
├── compose.override.yaml     # dev-only tweaks, auto-merged (§7)
├── .env                      # variables for ${…} substitution (gitignored)
├── .env.example              # committed template of .env
├── api.env                   # env vars injected into the api container
├── Dockerfile  .dockerignore  server.js  package.json  package-lock.json
├── db/init.sql               # creates the tasks table on first start
└── web/
    ├── nginx.conf            # reverse proxy config
    └── public/index.html     # static frontend
browser ──:8080──▶ web (nginx :80) ──/api/*──▶ api (:3000) ──▶ db (postgres :5432)
                   └─ frontend net ─┘           │  └───────▶ redis (:6379)
                                                └──────── backend net ────────┘

api sits on both networks; web can't reach db at all.

compose.yaml
name: taskflow                                    # project name → prefix for containers/networks/volumes

services:
  web:
    image: nginx:1.28-alpine
    ports:
      - "${WEB_PORT:-8080}:80"                    # the ONLY public entry point
    volumes:
      - ./web/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./web/public:/usr/share/nginx/html:ro
    depends_on:
      api:
        condition: service_healthy                # nginx needs "api" resolvable at startup
    networks: [frontend]
    restart: unless-stopped

  api:
    build:
      context: .                                  # folder containing the Dockerfile (S7)
      target: runtime                             # stage to build
    image: shauryav/taskflow-api:${TAG:-dev}      # name:tag for the built image
    env_file: ./api.env                           # NODE_ENV, LOG_LEVEL, … into the container
    environment:
      PORT: "3000"
      DATABASE_URL: postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      REDIS_URL: redis://redis:6379
    ports:
      - "127.0.0.1:3000:3000"                     # debug access from this machine only
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:3000/health"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 10s
    depends_on:
      db:
        condition: service_healthy                # wait until pg_isready succeeds
      redis:
        condition: service_started
    networks: [frontend, backend]
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - db-data:/var/lib/postgresql/data          # named volume → survives "down"
      - ./db/init.sql:/docker-entrypoint-initdb.d/01-init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [backend]                           # no ports: → not reachable from the host
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]   # persist to /data
    volumes:
      - redis-data:/data
    networks: [backend]
    restart: unless-stopped

networks:
  frontend:
  backend:

volumes:
  db-data:
  redis-data:

Syntax in compose.yamlResult
${TAG}Value from shell env or .env (shell wins); empty string + warning if unset.
${WEB_PORT:-8080}Default 8080 if unset or empty.
${POSTGRES_PASSWORD:?msg}Abort with msg if unset — fail fast instead of an empty DB password.
$$HOMELiteral $HOME, expanded later inside the container.

Inside a container, precedence (highest first): docker compose run -e → environment: → env_file: → image ENV.

Supporting files

web/nginx.conf
# mounted as /etc/nginx/conf.d/default.conf
server {
    listen 80;
    server_name _;

    # static frontend
    root  /usr/share/nginx/html;
    index index.html;

    # /api/tasks → http://api:3000/tasks  (trailing "/" on proxy_pass strips the /api prefix)
    location /api/ {
        proxy_pass http://api:3000/;
        proxy_set_header Host            $host;
        proxy_set_header X-Real-IP       $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # single-page app: unknown paths fall back to index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}
db/init.sql
-- runs ONCE: only when the db-data volume is empty (first start)
CREATE TABLE IF NOT EXISTS tasks (
  id         SERIAL PRIMARY KEY,
  title      TEXT        NOT NULL,
  done       BOOLEAN     NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
Common mistakes
  • Changed init.sql or POSTGRES_PASSWORD but nothing happened? Both apply only when the data volume is empty. Existing volume = old password, old schema. (Reset with down -v — destroys data.)
  • depends_on: [db] (short form) only waits for the container to start, not for Postgres to accept connections → API crashes with ECONNREFUSED on first boot. Use condition: service_healthy + a healthcheck.
  • Putting secrets in compose.yaml and committing it. Keep them in .env (gitignored).
Recap services + networks + volumes in one file. .env = substitution, env_file/environment = container env. depends_on + service_healthy for real readiness.

Dev override file

compose.override.yaml
# merged automatically on top of compose.yaml by `docker compose up` (dev only)
services:
  api:
    command: ["node", "--watch", "server.js"]   # replaces CMD: restart on file change
    environment:
      NODE_ENV: development                        # merged key by key with the base file
      LOG_LEVEL: debug
    volumes:
      - ./:/app                                    # bind mount: live source code
      - /app/node_modules                          # keep the image's node_modules
  db:
    ports:
      - "127.0.0.1:5432:5432"                      # psql / DBeaver from the host
  • Merge rules: single values (command, image) are replaced; environment merges by key; ports/volumes are combined.
  • Passing -f disables the automatic override: production = docker compose -f compose.yaml up -d (or -f compose.yaml -f compose.prod.yaml).
  • docker compose config shows the merged result. (Alternative for dev: develop.watch + docker compose watch syncs files without bind mounts.)
Common mistakes
  • docker compose up -d --scale api=3 fails with port is already allocated — three replicas can't share host port 3000. Remove ports: from scaled services and go through nginx.
  • Edited code but docker compose up -d runs the old version → you forgot --build.
  • nginx: [emerg] host not found in upstream "api" → web started before api existed or isn't on a shared network.
Key takeaway

down is safe for data; down -v is not. Everything in the stack is reproducible from compose.yaml + .env — except what lives in volumes.

Recap config → up -d --build → ps / logs -f / exec → down. Override files for dev, -f for prod.

★ Putting it all together

The big idea

TaskFlow is four containers that find each other by name over user-defined bridge networks (Docker's DNS at 127.0.0.11), with only nginx published to the host via -p/ports. Postgres and Redis keep state in named volumes that survive down; bind mounts feed nginx its config and give you live reload in dev. compose.yaml + .env capture all of it, and depends_on: service_healthy starts things in the right order. Kubernetes (S9+) replaces these pieces with Services, PersistentVolumes and Deployments across many machines.

Quick self-check

Two containers on the default bridge can't reach each other by name, but on a network you created they can. Why?

Only user-defined networks get Docker's embedded DNS (127.0.0.11) that resolves container/service names. The default bridge supports IPs only (or legacy --link).

In -p 8080:3000, which number is the container port, and what URL does another container on the same network use?

3000 is the container port (format HOST:CONTAINER). Another container uses http://api:3000 — the published 8080 is only for the host/outside.

What's the difference between docker compose down and docker compose down -v?

down removes containers and networks but keeps named volumes (data survives). -v also removes the named volumes declared in the file — the database is wiped.

Named volume vs bind mount — which would you use for Postgres data and which for live-reloading source code?

Named volume for Postgres (Docker-managed, portable, fast, survives container removal). Bind mount for source code (you edit host files, the container sees them immediately).

The API crashes on docker compose up with ECONNREFUSED db:5432, then works after a restart. Fix?

Postgres wasn't ready yet. Add a pg_isready healthcheck to db and depends_on: db: condition: service_healthy on api (plus retry logic in the app).

.env vs env_file: — which one puts variables inside the container?

env_file: (and environment:). The project .env is read by Compose only for ${VAR} substitution in the YAML.
