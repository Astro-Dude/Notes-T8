1 Docker networking & drivers

The problem

Session 7 built shauryav/taskflow-api:1.0. Run it next to a database, the Session 6 way:

$ docker run -d --name taskflow-db -e POSTGRES_USER=taskflow -e POSTGRES_PASSWORD=devpass \
    -e POSTGRES_DB=taskflow postgres:16-alpine
$ docker run -d --name api -p 3000:3000 \
    -e DATABASE_URL=postgres://taskflow:devpass@localhost:5432/taskflow shauryav/taskflow-api:1.0
$ docker logs api
Error: connect ECONNREFUSED 127.0.0.1:5432
$ docker rm -f api                       # try the container's name instead of localhost
$ docker run -d --name api -p 3000:3000 \
    -e DATABASE_URL=postgres://taskflow:devpass@taskflow-db:5432/taskflow shauryav/taskflow-api:1.0
$ docker logs api
Error: getaddrinfo ENOTFOUND taskflow-db

Postgres is running and listening on 5432. Puzzle 1: why does localhost:5432 refuse? Puzzle 2 (§2): why doesn't Docker know the name taskflow-db?

The idea

Every container has its own network namespace (Session 6, §2): its own interfaces, IP address, routing table and ports, and its own localhost. A network driver wires those namespaces together. The default driver, bridge, is a virtual switch on the host called docker0, with one virtual cable (a veth pair) per container and NAT for traffic leaving the host.

 host (Ubuntu)                                          eth0 192.168.1.20 ──▶ internet
 ┌───────────────────────────────────────────────────────────────┐
 │  docker0 bridge 172.17.0.1   (a virtual switch)               │
 │    ├── veth ── taskflow-db   eth0 172.17.0.2   lo 127.0.0.1   │ ← Postgres listens here
 │    └── veth ── api           eth0 172.17.0.3   lo 127.0.0.1   │ ← api's OWN localhost
 │  iptables: MASQUERADE (containers → internet), DNAT (for -p)  │
 └───────────────────────────────────────────────────────────────┘

That solves puzzle 1. Inside api, localhost:5432 is api's own loopback, where nothing listens. Postgres has a different localhost, one veth cable away.

Think of it like this

The Session 6 hotel again. Every room has its own phone, and "this room, extension 5432" (localhost:5432) rings in your room. docker0 is the hotel switchboard that connects rooms to each other, and calls to the outside world go out through reception (NAT).

What a bridge IP does not do: make the container reachable from outside the host. 172.17.0.2 exists only on this machine. Outsiders need a published port (§3).

Exam trap

"localhost inside a container means the host." ✗ It means that container. The host is a different machine on the network.

"Containers on the default bridge can't reach each other." ✗ They can, by IP. What they lack is name lookup (§2).

Remember

Every container has its own network stack and its own localhost.
Default network = bridge: docker0, 172.17.0.0/16, NAT.

Mastery check
Q1. docker inspect says taskflow-db is 172.17.0.2. Would DATABASE_URL=…@172.17.0.2:5432/… work from api? Is it a good idea?

It works, because both are on the same bridge. It's fragile, though: IPs are assigned at start, so after a restart or re-create the database may get another one. Use names on a user-defined network (§2).

Q2. Pick the driver: (a) a batch job that must have no network, (b) a monitoring agent that must see the host's own interfaces, (c) one network across several Swarm hosts.

(a) none · (b) host · (c) overlay.

Q3. Predict: two nginx containers, both listening on port 80 inside, started without -p. Conflict?

No. Each has its own network namespace, so each has its own port 80. Ports only clash on the host, when you publish both to the same host port (Session 6, §7).

2 Container-to-container communication

The problem

Puzzle 2, reduced to its core:

$ docker run --rm alpine:3.20 ping -c1 taskflow-db
ping: bad address 'taskflow-db'
$ docker run --rm alpine:3.20 ping -c1 172.17.0.2
PING 172.17.0.2 (172.17.0.2): 56 data bytes
64 bytes from 172.17.0.2: seq=0 ttl=64 time=0.597 ms

The IP works and the name doesn't. You can't hard-code IPs either, because they're handed out at start time.

The idea

On a user-defined bridge network, Docker runs an embedded DNS server at 127.0.0.11 inside every container. It answers container names (and aliases) with their current IPs. The default bridge doesn't have it: containers there get the host's DNS server, which has never heard of taskflow-db.

 taskflow-net (user-defined bridge, 172.18.0.0/16)
 ┌─────────────────────────────────────────────────────────────────┐
 │  api ── "where is db?" ──▶ 127.0.0.11 (Docker's DNS) ── 172.18.0.2 │
 │   └──────────────── TCP db:5432 ─────────────────────────▶ db    │
 └─────────────────────────────────────────────────────────────────┘
   default bridge: no 127.0.0.11, only the host's DNS → "bad address"
   a different network: not connected at all, not even by IP
Think of it like this

On your own floor (a user-defined network), reception keeps a phone book, so you dial "db" and always reach the right room, even after the guest moves rooms. The old lobby (the default bridge) has no phone book. You can only dial room numbers, and those change.

See it: a network with a phone book

$ docker network create taskflow-net
9425feb7e4622d7a4d987735b1b14aad66c88acfd89edcd495641236f1a52fc4
$ docker run -d --name db --network taskflow-net alpine:3.20 sleep 300     # a stand-in for Postgres
$ docker run --rm --network taskflow-net alpine:3.20 ping -c1 db
PING db (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.327 ms
$ docker run --rm --network taskflow-net alpine:3.20 grep nameserver /etc/resolv.conf
nameserver 127.0.0.11
$ docker run --rm alpine:3.20 grep nameserver /etc/resolv.conf               # default bridge
nameserver 10.0.0.2                                                         # copied from the host
TokenMeaning
docker network create taskflow-netA new user-defined bridge with its own subnet (here 172.18.0.0/16)
--network taskflow-netAttach the container to it at start
--name dbThe container name is also its DNS name on that network

What a network does not do: publish anything. db is reachable from containers on taskflow-net and from nothing else.

Build it up: TaskFlow by name

$ docker rm -f db                         # drop the stand-in
$ docker run -d --name db --network taskflow-net \

    postgres:16-alpine
$ docker run -d --name api --network taskflow-net -p 3000:3000 \

Both puzzles are solved: the API reaches Postgres as db:5432, the container port, with no -p on the database at all. Session 6's web container is still on the default bridge. You can attach it without restarting it, and give it an extra name:

$ docker inspect -f '{{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}' web

Exam trap

"Containers talk to each other on the published port." ✗ They use the container port (db:5432). -p is only for traffic from outside Docker.

"The default bridge resolves container names." ✗ Only user-defined networks have the embedded DNS.

Remember

network create → --network on each container → call them as name:containerPort.
Names resolve only on user-defined networks (DNS at 127.0.0.11).

Mastery check
Q1. api is on taskflow-net. A redis container was started without --network. The API logs getaddrinfo ENOTFOUND redis. Why, and what's the one-command fix?

redis is on the default bridge: a different network with no shared DNS. Run docker network connect taskflow-net redis, and the name resolves at once.

Q2. db is also published with -p 15432:5432. Which host and port goes in the API's DATABASE_URL, and which does psql on your laptop use?

The API, on the same network, uses db:5432. Your laptop is outside Docker, so it uses the published port: localhost:15432.

Q3. On Docker Desktop, a container must call a dev server running on your Mac at port 4000. What hostname does it use?

host.docker.internal:4000. localhost would be the container itself. On Linux, add --add-host=host.docker.internal:host-gateway to get the same name.

3 Port mapping

The problem

Session 6 taught -p HOST:CONTAINER. Two things it didn't explain:

# puzzle 1: a teammate's build, where server.js says app.listen(3000, '127.0.0.1')
$ docker run -d --name api-pub -p 8080:3000 shauryav/taskflow-api:bad-bind
$ curl localhost:8080/health
curl: (56) Recv failure: Connection reset by peer

# puzzle 2: an Ubuntu server where ufw allows only 22 and 80
$ docker run -d --name db -p 5432:5432 -e POSTGRES_PASSWORD=devpass postgres:16-alpine
laptop$ nc -zv 203.0.113.10 5432                  # from the internet
Connection to 203.0.113.10 port 5432 [tcp/postgresql] succeeded!

The mapping exists, yet the API resets the connection. And the firewall says no, yet the database is open to the world.

The idea

Publishing a port makes Docker add a NAT rule: packets arriving at the host's IP and port are rewritten (DNAT) to the container's IP and port, then forwarded over docker0. Two consequences follow. The packet arrives on the container's eth0, not its lo. And forwarded packets go through iptables' FORWARD chain, never the INPUT chain where ufw's rules live.

 client ─▶ 203.0.113.10:5432 ─▶ nat PREROUTING: DNAT → 172.17.0.2:5432 ─▶ FORWARD ─▶ eth0 of db
                                 (Docker's rule)                         (ufw's INPUT rules never run)
 -p 127.0.0.1:5432:5432  → the rule only matches traffic sent to 127.0.0.1, i.e. from this machine
 the app inside must listen on 0.0.0.0 (all interfaces, incl. eth0), not 127.0.0.1 (lo only)

Puzzle 1: the API listened only on lo, so the forwarded packet found no listener on eth0 and the connection was reset. Listen on 0.0.0.0 (Session 4). Puzzle 2: ufw never saw the packet.

Think of it like this

Reception forwards calls from the hotel's main number to a room extension (Session 6). A guest who only answers calls made from inside their own room (127.0.0.1) never picks up a forwarded one. And the switchboard forwards the call before the front-desk security list (ufw) is ever checked.

See it: what's published

$ docker port api-pub
3000/tcp -> 0.0.0.0:8080
3000/tcp -> [::]:8080
$ docker ps --format 'table {{.Names}}\t{{.Ports}}'
NAMES     PORTS
api-pub   0.0.0.0:8080->3000/tcp, [::]:8080->3000/tcp
FlagMeaning
-p 8080:3000Host port 8080 on all interfaces (0.0.0.0 and [::]) → container port 3000
-p 127.0.0.1:8080:3000Reachable only from this machine. Use it for databases and admin UIs.
-p 3000A random free host port → container 3000 (read it with docker port)
-PEvery EXPOSEd port → random host ports (Session 7, §3)
-p 5353:53/udpUDP (the default is TCP)
-p 8080-8081:3000-3001Port ranges

What -p does not do: open your cloud firewall. An EC2 security group must still allow the port (Session 21).

Build it up: the two errors and the fix for puzzle 2

# same host port twice
$ docker run -d --name api-pub2 -p 8080:3000 shauryav/taskflow-api:1.0
docker: Error response from daemon: driver failed programming external connectivity on endpoint api-pub2 (3c5e…): Bind for 0.0.0.0:8080 failed: port is already allocated.

# host port held by a non-Docker process (`node server.js` running on the host)
$ docker run -d --name api-pub3 -p 3000:3000 shauryav/taskflow-api:1.0
docker: Error response from daemon: … 0.0.0.0:3000 … bind: address already in use.
$ sudo ss -tulpn | grep ':3000'
tcp   LISTEN 0   511   0.0.0.0:3000   0.0.0.0:*   users:(("node",pid=48211,fd=21))

"Already allocated" means another container holds the port (docker ps). "Already in use" means a host process does (ss). For puzzle 2, never publish internal services to 0.0.0.0. Use -p 127.0.0.1:5432:5432 if you need host access, or don't publish at all: containers on the same network reach it anyway (§2).

Exam trap

"ufw deny 5432 protects a published container port." ✗ Docker's NAT rules run first, and the packet takes the FORWARD path. Bind to 127.0.0.1 or filter in the DOCKER-USER chain.

"-P publishes every port the app listens on." ✗ Only the ports the image EXPOSEs.

Remember

-p [HOST_IP:]HOST:CONTAINER · publish only the entry point.
The app inside listens on 0.0.0.0 · private ports bind to 127.0.0.1.

Mastery check
Q1. True or false: "Docker bypassed ufw, so it will bypass the EC2 security group too: -p 8080:3000 is enough to reach the API from my laptop."

False. ufw runs inside the host, where Docker's rules come first. A security group filters before packets reach the instance, so port 8080 must be allowed there too (Session 21).

Q2. Spot the bug: a DNS server container is published with -p 53:53, and lookups from outside time out.

-p defaults to TCP, but DNS queries mostly use UDP. Add -p 53:53/udp.

Q3. An admin UI on port 8081 must be reachable only through an SSH tunnel to the server. Write the -p.

-p 127.0.0.1:8081:80 (assuming the UI listens on 80 inside). Only connections from the server itself, including your SSH tunnel's end, match the rule.

4 Docker volumes

The problem

Session 6 left two loose ends. The note written in container a vanished with docker rm, and its final check promised to explain what happens to Postgres data without -v. §1 of this page started taskflow-db without -v. Look at the disk now:

$ docker volume ls
DRIVER    VOLUME NAME
local     4e1f9c2b7a0d63e58f1a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f7
local     taskflow-pgdata

Who made the volume with the 64-character name, and why does nothing use it?

The idea

A volume is a directory Docker manages outside every container's writable layer (/var/lib/docker/volumes/<name>/_data on Linux, inside the VM on Docker Desktop), mounted into a container at a path. Delete the container and the volume stays. Mount it into the next container and the data is back.

 docker run -v taskflow-pgdata:/var/lib/postgresql/data … ─▶ db (container #1) ─┐
 docker rm -f db             (its writable layer is deleted)                     ├─▶ volume taskflow-pgdata
 docker run -v taskflow-pgdata:/var/lib/postgresql/data … ─▶ db (container #2) ─┘   (untouched by rm)
Think of it like this

A hotel room is cleaned out when you check out (rm deletes the writable layer). A volume is a rented locker downstairs: your things stay in it, and you can take the key to whichever room you check into next.

See it: a note that survives

$ docker volume create notes
notes
$ docker run --rm -v notes:/data alpine:3.20 sh -c 'echo "remember milk" > /data/note.txt'
$ docker run --rm -v notes:/data alpine:3.20 cat /data/note.txt
remember milk

Two different containers, both deleted by --rm, and the note survived. In -v notes:/data, notes is the volume name (a plain name means a named volume) and /data is where it appears inside the container. What a volume does not do: back up or replicate anything. The default local driver keeps the data on this one host.

Build it up

Postgres data survives docker rm

$ docker rm -f db
$ docker run -d --name db --network taskflow-net \
    -e POSTGRES_USER=taskflow -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=taskflow \

The mystery volume, and managing volumes

The postgres image's Dockerfile says VOLUME /var/lib/postgresql/data. Start it without -v and Docker creates an anonymous volume with a random 64-character name. That's the mystery volume: §1's taskflow-db got it. Remove that container and the data still exists on disk, but nothing points at it, and a re-created container gets a fresh, empty one.

$ docker volume inspect taskflow-pgdata --format '{{.Mountpoint}}'
/var/lib/docker/volumes/taskflow-pgdata/_data
$ docker volume rm taskflow-pgdata
Error response from daemon: remove taskflow-pgdata: volume is in use - [8b1e4f2a9c7d…]
$ docker rm -f taskflow-db         # §1's container; its anonymous volume stays behind
$ docker volume prune            # removes unused ANONYMOUS volumes only
WARNING! This will remove anonymous local volumes not used by at least one container.
Are you sure you want to continue? [y/N] y
Deleted Volumes:
4e1f9c2b7a0d63e58f1a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f7

Total reclaimed space: 47.2MB
$ docker volume prune -a         # also unused NAMED volumes: data loss!
  • Named volumes are never deleted implicitly. Anonymous ones go with their container only via docker rm -v or docker run --rm.
  • The same mount in long syntax: --mount type=volume,src=taskflow-pgdata,dst=/var/lib/postgresql/data.
  • Backups: docker exec db pg_dump -U taskflow taskflow > taskflow-2026-10-09.sql for databases. For any other volume, use a throwaway container: docker run --rm -v taskflow-pgdata:/data:ro -v "$(pwd)":/backup alpine:3.20 tar czf /backup/pgdata.tgz -C /data . (stop Postgres first, or the copy may be corrupt).
Version note

postgres:18 and later moved the data directory: mount the volume at /var/lib/postgresql. This page uses postgres:16, where /var/lib/postgresql/data is correct.

Exam trap

"A typo in the volume name gives an error." ✗ -v pgdta:/var/lib/… silently creates a new, empty volume, and "the data is gone".

"docker rm deletes the container's volumes." ✗ Named volumes survive it. That's the point of them.

Remember

The writable layer dies with the container; a volume outlives it.
-v name:/path · always name database volumes · prune = anonymous only, prune -a = named too.

Mastery check
Q1. You change POSTGRES_PASSWORD and re-create db with the same volume. The new password is rejected. Why?

The postgres image creates the user and password only when the data directory is empty, on first start. The volume already holds a database with the old password. Change it with ALTER USER, or start from an empty volume (losing the data).

Q2. docker volume rm taskflow-pgdata says "volume is in use", but db is stopped. Why?

A stopped container still references its volumes. Remove the container (docker rm db) first, then the volume.

Q3. Predict: docker run --rm -v /data alpine:3.20 sh -c 'echo x > /data/f'. Where is f afterwards?

Gone. -v /data (no name) made an anonymous volume, and --rm deletes anonymous volumes along with the container.

5 Bind mounts & tmpfs

The problem

Developing the API with the Session 7 image is slow: edit server.js → docker build → docker rm -f → docker run, about 20 seconds per change. You want to save the file and see the change at once, without reinstalling packages on every start as Session 6's run-from-source command did.

The idea

A bind mount maps an existing host path into the container. They are the same files, not a copy, so a change on either side is visible on the other immediately. You choose the path and Docker doesn't manage it. A tmpfs mount lives in RAM only.

┌──────────── container ─────────────┐
│ /var/lib/postgresql/data  ─────────┼──▶ volume  taskflow-pgdata  (Docker-managed area)
│ /app                      ─────────┼──▶ bind    /home/shaurya/taskflow  (any host path, live)
│ /tmp                      ─────────┼──▶ tmpfs   host RAM, gone when the container stops
└────────────────────────────────────┘
Think of it like this

A volume is a locker Docker rents you. A bind mount is a window from the hotel room straight into your own flat: move something on either side and both sides see it. tmpfs is a whiteboard, wiped when you leave.

See it: serve a folder from your laptop

$ mkdir site && echo '<h1>hi from my laptop</h1>' > site/index.html
$ docker run -d --name site -p 8081:80 -v "$(pwd)/site":/usr/share/nginx/html:ro nginx:1.27-alpine
$ curl -s localhost:8081
<h1>hi from my laptop</h1>
$ echo '<h1>edited</h1>' > site/index.html && curl -s localhost:8081
<h1>edited</h1>
TokenMeaning
"$(pwd)/site"Host path: absolute, quoted so spaces don't break it. Starting with / or . is what makes it a bind mount, not a volume name.
/usr/share/nginx/htmlWhere it appears inside the container
:roRead-only for the container. Writes fail with "Read-only file system".

No rebuild, no restart: the edit was live. What a bind mount does not do: merge folders. It hides whatever the image had at that path, here nginx's default index.html.

tmpfs, and the comparison

$ docker run --rm --tmpfs /scratch:size=64m alpine:3.20 df -h /scratch
Filesystem                Size      Used Available Use% Mounted on
tmpfs                    64.0M         0     64.0M   0% /scratch

A tmpfs mount is never written to disk and vanishes when the container stops (Linux only). It pairs well with --read-only root filesystems.

Exam trap

"A typo in a -v host path fails with an error." ✗ -v creates the missing path as an empty directory. --mount fails instead.

"Files written through a bind mount belong to you." ✗ On Linux they belong to the container's user, root by default, so you can't edit them. Run with --user "$(id -u):$(id -g)" or a non-root image user.

Remember

Volume = Docker's storage (databases) · bind = your folder (dev code, config) · tmpfs = RAM.
A -v value starting with / or . is a bind mount; a plain name is a volume.

Mastery check
Q1. Predict: you mount an empty host folder over /usr/share/nginx/html, then try a new, empty named volume there instead. What does curl localhost return each time?

Bind mount: 403 Forbidden, because the empty folder hides nginx's index.html. Named volume: "Welcome to nginx!", because an empty volume is first filled with the image's files at that path.

Q2. In the live-reload command, what breaks if you drop -v /app/node_modules?

The bind mount puts your host folder over /app, including your host node_modules (or none). On a Mac that means macOS-built native modules (invalid ELF header), or "Cannot find module" if you never installed locally.

Q3. Pick the mount type: Postgres data · nginx.conf · source code in development · a decrypted key you never want on disk.

Named volume · bind mount (:ro) · bind mount · tmpfs.

6 Docker Compose: the file

The problem

Everything so far, for the full TaskFlow stack, typed by every teammate, in the right order:

docker network create taskflow_frontend && docker network create taskflow_backend
docker volume create taskflow_db-data
docker run -d --name db --network taskflow_backend -e POSTGRES_USER=… -e POSTGRES_PASSWORD=… -e POSTGRES_DB=… -v …
docker run -d --name redis --network taskflow_backend -v … redis:7-alpine redis-server --appendonly yes
docker build -t shauryav/taskflow-api:dev . && docker run -d --name api --network taskflow_backend -e … -p …
docker network connect taskflow_frontend api
docker run -d --name web --network taskflow_frontend -p 8080:80 -v …nginx.conf…:ro nginx:1.27-alpine

That's seven commands and about forty flags. Forget one and you're back at §1's puzzles. Tearing it down is another six commands.

The idea

Docker Compose lets you describe the stack in one YAML file: services, networks and volumes. docker compose up creates whatever is missing, in dependency order, and docker compose down removes it. Every key maps to a docker run flag you already know. Compose also gives the project a network, so every service reaches every other by its service name.

 compose.yaml ── docker compose up ──▶
     browser ──:8080──▶ web (nginx :80) ──/api/*──▶ api (:3000) ──▶ db (postgres :5432)
                        └─── frontend network ───┘       │  └──────▶ redis (:6379)
                                                         └────── backend network ──────┘

api sits on both networks. web can't reach db at all.

Think of it like this

Session 6's restaurant again. Instead of telling the waiter one dish at a time, you hand over the whole table's written order. The kitchen makes everything, starters first, and the same order works on any night (any machine).

See it: two services

compose.yaml (minimal)

    image: shauryav/taskflow-api:1.0

      - "3000:3000"

Compose named everything after the folder (taskflow), created a user-defined network (so db resolves, §2) and started both containers. docker compose is the Compose plugin for the Docker CLI (v2 and later; the old Python docker-compose is retired). What it does not do: wait for Postgres to be ready. Without depends_on, both containers start in parallel, and an API that queries the database at boot can lose that race. The full file fixes this.

Exam trap

"A compose file must start with version: "3.8"." ✗ The top-level version key is obsolete: Compose ignores it and warns. The default file name is compose.yaml (docker-compose.yml still works).

"depends_on: [db] waits until the database is ready." ✗ The short form only orders container starts. Waiting for readiness needs a healthcheck plus condition: service_healthy.

Mastery check
Q1. Translate: docker run -d --name cache --network backend -v redis-data:/data --restart unless-stopped redis:7-alpine redis-server --appendonly yes.

It's the redis service above, under the name cache: image: redis:7-alpine, command: ["redis-server", "--appendonly", "yes"], volumes: [redis-data:/data], networks: [backend], restart: unless-stopped, plus redis-data and backend declared at the top level. -d has no key: up -d covers it.

Q2. In the full file, which services can open a connection to db:5432, and can your laptop?

api and redis, the other services on backend (only api ever does). web can't, because it's only on frontend. Your laptop can't either: db has no ports:.

Q3. The folder is called tf and you delete the name: taskflow line. What is the API container called now?

tf-api-1. The project name defaults to the folder name, and containers are named <project>-<service>-<n>. The volumes become tf_db-data, so your old taskflow_db-data data isn't used.

The problem

Clone the repo, run the full file, and:

The idea

Compose reads a .env file in the project folder only to fill in ${VAR} in compose.yaml. A value reaches a container only through environment: or env_file:. Config files reach containers as read-only bind mounts.

 web/nginx.conf, db/init.sql ─────── volumes (bind, :ro) ──────────▶ web: default.conf · db: 01-init.sql

${TAG}The value from your shell or .env (the shell wins). Unset → empty string plus a warning, like POSTGRES_USER above.

A dev override file

compose.override.yaml
# merged automatically on top of compose.yaml by `docker compose up` (dev only)
services:
  api:
    command: ["node", "--watch", "server.js"]   # replaces CMD: restart on file change
    environment:
      NODE_ENV: development                        # merged key by key with the base file
      LOG_LEVEL: debug
    volumes:
      - ./:/app                                    # bind mount: live source code (§5)
      - /app/node_modules                          # keep the image's node_modules
  db:
    ports:
      - "127.0.0.1:5432:5432"                      # psql / DBeaver from this machine only (§3)

Single values (command, image) are replaced, environment merges by key, and ports and volumes are combined. Passing -f switches the automatic merge off, so production runs docker compose -f compose.yaml up -d (or -f compose.yaml -f compose.prod.yaml). docker compose config shows the merged result.

Exam trap

"docker compose down deletes the database." ✗ It keeps named volumes. down -v deletes them.

"Edit init.sql and up applies the new schema." ✗ Init scripts run only on an empty data volume, like the password in §4.

".env sets environment variables in every container." ✗ It only feeds ${VAR} substitution. Containers get what environment: and env_file: give them.

Remember

config → up -d --build → ps / logs -f / exec → down.
down is safe for data; down -v is not.

Mastery check
Q1. You edited server.js, ran docker compose up -d, and the old code is still running. Why?

Without --build, Compose reuses the image it built last time (shauryav/taskflow-api:1.0, from TAG in .env) and sees no config change, so nothing is re-created. Run docker compose up -d --build. (In dev, the override's bind mount makes this unnecessary.)

Q2. docker compose up -d --scale api=3 fails with "port is already allocated". Why, and what's the fix?

All three replicas try to bind host 127.0.0.1:3000. Remove ports: from the scaled service and reach it through nginx (api:3000 on the network). Docker's DNS returns all three replicas' IPs.

Q3. web keeps restarting with nginx: [emerg] host not found in upstream "api". Give two possible causes.

(1) web and api share no network (e.g. you removed frontend from api). (2) api wasn't up when nginx started: without depends_on: api: condition: service_healthy, nginx may resolve api before it exists.

★ Putting it all together

The big idea

Each container has its own network stack, so localhost means "me". TaskFlow's four containers find each other by name on user-defined bridge networks (Docker's DNS at 127.0.0.11), using container ports. Only nginx is published to the host with -p/ports. Postgres and Redis keep their state in named volumes that outlive any container, and bind mounts feed nginx its config and give you live reload in development. compose.yaml + .env capture all of this, with depends_on: service_healthy starting things in the right order. Kubernetes (Session 9 onwards) replaces these pieces with Services, PersistentVolumes and Deployments across many machines.

Final mastery check — combine everything
Q1. With the plain docker run commands from §1 the API logs ENOTFOUND taskflow-db, but the same image works under Compose with DATABASE_URL=…@db:5432/…. What does Compose do that the commands didn't?

Compose puts every service on a user-defined network (here backend), which has Docker's embedded DNS, and the service name db is the DNS name. The §1 containers were on the default bridge, which has no name resolution (§1, §2, §6).

Q2. Four actions: compose down then up; compose down -v then up; docker rm -f taskflow-db-1 then compose up -d; changing POSTGRES_PASSWORD in .env then up -d. After each, are the tasks still there, and does the new password work?

(1) Tasks kept: named volume. (2) Gone: -v deleted the volume, and init.sql runs again on the empty one. (3) Kept: Compose re-creates the container with the same taskflow_db-data volume. (4) Tasks kept, but the new password is rejected, because Postgres only sets it on an empty data directory (§4, §7).

Q3. On the Ubuntu server, someone copied the dev override into production, so db is published as "5432:5432". ufw blocks 5432. Is the database exposed? What should the file say?

Yes. Docker's DNAT rules bypass ufw's INPUT chain (§3). Production shouldn't publish db at all, since api reaches it over backend (§2). If host access is needed, use "127.0.0.1:5432:5432", and run production with -f compose.yaml so the override isn't merged (§7).

Q4. A teammate changes db's volume line to - ./pgdata:/var/lib/postgresql/data. List four things that change.

It's now a bind mount, not a named volume (§5). (1) The data lives in the repo folder, so pgdata/ must be gitignored and dockerignored. (2) It no longer appears in docker volume ls, and down -v no longer deletes it (§7). (3) The files belong to the container's postgres user (uid 70 on Alpine), so you may not be able to read or delete them. (4) On Docker Desktop it's slower, because of file sharing. For a database, keep the named volume (§4).

Q5. Correct every error: "Containers on one host talk via localhost; to let the API reach Postgres you must publish 5432; docker compose down wipes the data unless you add -v."

(1) localhost is each container's own loopback, so they talk via service or container names on a shared network (§1, §2). (2) No publishing is needed between containers: the API uses db:5432, and -p is only for outside access (§3). (3) Backwards: down keeps named volumes, and down -v deletes them (§4, §7).
