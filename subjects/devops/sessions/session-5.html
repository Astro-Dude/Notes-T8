1 Git vs GitHub & setup

The problem

TaskFlow without version control, one week in:

taskflow/
├── server.js
├── server_old.js
├── server_final.js
├── server_final_v2_REALLY_FINAL.js
└── taskflow_from_aditi.zip        ← she edited server.js too. Whose version wins?

On Tuesday /health broke. Which file changed what, when, and who did it? Nobody knows, and merging Aditi's zip by hand will overwrite someone's work.

The idea

Git is a distributed version control system. It records snapshots of your project in a hidden .git/ folder, each with who, when and why. Every copy (clone) holds the full history, so committing and browsing history work offline. GitHub hosts Git repositories: one more copy everyone syncs with, plus team features (pull requests, reviews, issues, CI with Actions).

 your laptop                    GitHub (origin)                 Aditi's laptop
 taskflow/.git ◀── push/fetch ──▶ shauryav/taskflow ◀── push/fetch ──▶ taskflow/.git
 full history                     full history                    full history
 commit, branch, log, diff        + pull requests, reviews, issues, Actions (CI/CD), permissions
Think of it like this

Git is a camera plus a photo album. Every commit is a photo of the whole folder, with a caption, the photographer and the date. GitHub is a shared album in the cloud, where the team swaps photos and discusses them before they enter the main album. This page keeps using the album.

See it: Git's first question

$ git commit -m "first"            # your first commit on a fresh Ubuntu machine (trimmed)
Author identity unknown

*** Please tell me who you are.
…
fatal: unable to auto-detect email address (got 'shaurya@taskflow-vm.(none)')
$ git config --global user.name "Shaurya Verma"
$ git config --global user.email "shaurya@example.com"
$ git config --global init.defaultBranch main
$ git config --list --show-origin
file:/home/shaurya/.gitconfig	user.name=Shaurya Verma
file:/home/shaurya/.gitconfig	user.email=shaurya@example.com
file:/home/shaurya/.gitconfig	init.defaultbranch=main
TokenMeaning
config --globalWrite a setting for your user, in ~/.gitconfig, so it applies to every repo
user.name / user.emailStamped on every commit. Use an email on your GitHub account so commits link to your profile.
init.defaultBranch mainNew repos start on main. Without it, Git 2.x still uses master and prints a long hint.

What it does not do: log you into GitHub or prove who you are. user.email is a label anyone can set to anything. Authentication is separate (below).

Build it up

Those commands wrote ~/.gitconfig. Here is a fuller one. In this format # starts a comment anywhere on a line, so each line carries its own explanation:

~/.gitconfig
[user]
	name = Shaurya Verma                    # author name stamped on every commit
	email = shaurya@example.com             # must match an email on your GitHub account
[init]
	defaultBranch = main                    # new repos start on "main", not "master"
[pull]
	rebase = false                          # git pull = fetch + merge (section 7)
[push]
	autoSetupRemote = true                  # first "git push" of a new branch sets its upstream
[core]
	editor = code --wait                    # editor for commit messages (default: vim)
	autocrlf = input                        # store LF line endings, even if Windows wrote CRLF
[alias]
	lg = log --oneline --graph --all --decorate
	st = status -sb

Two lines need context. Without [pull] rebase, Git refuses to pull once your branch and GitHub's have both moved (section 7). And CRLF line endings break .sh scripts on Linux (Session 3).

Settings have three scopes, and the most specific wins: --system (/etc/gitconfig) < --global (~/.gitconfig) < --local (.git/config, the default inside a repo). That's how you use a college email in one repo only:

$ git config user.email "shaurya.verma@college.example"     # no flag = --local
$ git config --show-scope --get-all user.email
global	shaurya@example.com
local	shaurya.verma@college.example                # the last one listed wins

Authenticate to GitHub

$ ssh-keygen -t ed25519 -C "shaurya@example.com"   # creates ~/.ssh/id_ed25519 and id_ed25519.pub
$ cat ~/.ssh/id_ed25519.pub                          # paste into GitHub → Settings → SSH and GPG keys
$ ssh -T git@github.com
Hi shauryav! You've successfully authenticated, but GitHub does not provide shell access.

Your GitHub password no longer works for pushes (Support for password authentication was removed). Use an SSH key, gh auth login, or a Personal Access Token.

Exam trap

"Git and GitHub are the same thing." ✗ Git is the tool on your machine. GitHub is one company's hosting for Git repos, and Git works with GitLab, Bitbucket or no server at all.

"You need internet access to commit." ✗ Commit, branch, log and diff are local. Only push, fetch, pull and clone talk to a remote.

Remember

Git = the tool + your local history · GitHub = a hosted copy + team features.
user.email labels commits; SSH keys or tokens authenticate.

Mastery check
Q1. Predict: you're on a train with no internet. Which work: git commit, git log, git switch -c feature/x, git push?

The first three, because they only touch your local .git, which holds the full history. git push fails until you're online. Then it uploads everything you committed meanwhile.

Q2. Your commits show on GitHub with a grey avatar, not linked to your profile, although the push worked. What's wrong?

The commits' user.email isn't on your GitHub account. The push worked because authentication (SSH key or token) is separate from the author label. Fix the email, or add it to your account.

Q3. Predict: in your home folder (not inside any repo) you run git config user.email "shaurya.verma@college.example". What happens?

It fails with fatal: not in a git directory. With no flag, git config writes the local scope (.git/config), and there's no repo here. Add --global, or run it inside the repo.

2 Repository: the three areas

The problem

In the TaskFlow folder right now:

server.js      reads PORT from the environment: finished and tested    → commit this
package.json   a half-done "dev" script                                 → not yet
.env           the database password                                    → never
node_modules/  40,000 files that npm can recreate                       → never

A single "save everything" button would mix all four. You need to choose exactly what goes into each snapshot.

The idea

Git has three areas. You edit files in the working directory. git add copies a file's current content into the staging area (the index), the draft of your next commit. git commit saves everything staged as a permanent snapshot in the repository (.git/).

 Working directory          Staging area (index)          Repository (.git)
 the files you edit         "what the next commit is"     every commit, forever
        │ ── git add ────────────▶ │ ── git commit ──────────────▶ │
        │ ◀── git restore ─────────┼ ◀── git restore --staged ─────│     (section 9)
        └── git diff ──────────────┘└──── git diff --staged ───────┘
            working vs staged             staged vs last commit
Think of it like this

The working directory is the room. Staging is arranging the frame, with server.js in shot and the mess out of it. Commit is pressing the shutter, and the photo goes into the album for good. Rearranging is free, but a photo is permanent.

See it: the first commit

$ cd taskflow && git init
Initialized empty Git repository in /home/shaurya/taskflow/.git/
$ git status -s                   # ?? = untracked: Git has never been told about these files
?? .env
?? node_modules/
?? package-lock.json
?? package.json
?? server.js
$ git add server.js package.json package-lock.json
$ git commit -m "Initial commit: Express API with /health"
[main (root-commit) 95b5735] Initial commit: Express API with /health

 create mode 100644 package.json
 create mode 100644 server.js

(root-commit) 95b5735The first commit (no parent), and the start of its ID (SHA, section 3)
create mode 100644A new, normal file (100755 = executable)

What it does not do: upload anything. The snapshot lives only in this folder's .git until you push (section 7).

Exam trap

"git commit sends my work to GitHub." ✗ It saves to your local .git. Only git push uploads.

"git diff shows everything I've changed." ✗ Only unstaged changes. After git add . it prints nothing. Use git diff --staged.

Remember

edit → add (stage) → commit (snapshot).
diff = working vs staged · diff --staged = staged vs last commit.

Mastery check
Q1. You run git add server.js, then edit server.js again. What does git status -s show, and what will git commit save?

MM server.js. The commit saves the version as of your git add, because staging copies content at that moment. The later edits stay unstaged until you add again.

Q2. Predict: you edit package.json and immediately run git commit -m "Add dev script". What happens?

Nothing is committed: no changes added to commit (use "git add" and/or "git commit -a"), because nothing was staged. git commit -am would first stage all tracked modified files (never untracked ones).

Q3. You staged package.json by mistake. Which command undoes that without losing your edits? (Hint: reread the long git status output.)

git restore --staged package.json, which status itself suggests ("to unstage"). Afterwards git status -s shows  M package.json: modified, not staged.

3 Commits & history

The problem

After one more commit (the dev script and README), section 1's questions come back. Which commit changed server.js, who made it, and what exactly changed? And how do you tell Aditi "use that version" with no ambiguity?

The idea

A commit is a full snapshot of every tracked file (a tree), plus metadata (author, committer, date, message) and a pointer to its parent. Git hashes all of that into a 40-hex-digit SHA, the commit's ID. History is the chain you get by following parents back:

95b5735 ◀── 7b6c9ea ◀── 8c5b6ba   ◀── main ◀── HEAD
Initial     Read PORT    Add dev script
commit      and HOST     and README
each commit = tree (all files) + parent + author + committer + message → hashed into its SHA
Think of it like this

Every photo has a caption, the photographer, the date and a note: "follows photo 7b6c9ea". Its ID is stamped from its content. Change a pixel, the caption or the "follows" note and you get a different ID, which is why an ID always finds the exact photo.

See it

$ git log --oneline
8c5b6ba Add dev script and README
7b6c9ea Read PORT and HOST from env
95b5735 Initial commit: Express API with /health

log walks back through parents, newest first. --oneline shows a short SHA (any unique prefix works in commands) and the first line of the message. What it does not do: show every commit in the repo, only those reachable from where you are. Other branches need git log --all (section 5).

Build it up

$ git log --oneline -- server.js  # only commits that touched server.js
7b6c9ea Read PORT and HOST from env
95b5735 Initial commit: Express API with /health
$ git show --stat HEAD~1          # one commit: metadata + files (drop --stat for the full diff)
commit 7b6c9eaf702bc1b6b1b15b8a1911d543bc32135d
Author: Shaurya Verma <shaurya@example.com>
Date:   Fri Oct 9 16:52:40 2026 +0530

    Read PORT and HOST from env

 server.js | 7 +++++--
 1 file changed, 5 insertions(+), 2 deletions(-)

log -- file answers "which commit", and show answers "what exactly". Plain git log prints that same full header (SHA, author, date, message) for every commit. HEAD is the commit you're on, HEAD~1 its parent and HEAD~2 its grandparent.

What a commit really is

$ git cat-file -p HEAD            # the raw commit object
tree e9b6f23f5590067ba3178880086d19fb0bc218f1
parent 7b6c9eaf702bc1b6b1b15b8a1911d543bc32135d
author Shaurya Verma <shaurya@example.com> 1791545103 +0530
committer Shaurya Verma <shaurya@example.com> 1791545103 +0530

Add dev script and README
$ git cat-file -p 'HEAD^{tree}'   # the tree: a directory listing of the snapshot
100644 blob e193560fbc1ddc18eea9f44ec92905c2a61511f7	README.md
100644 blob dfbc088533ea61cb79896320caa12ca76fb1ad8a	package-lock.json
100644 blob 83f1b739a5b144a5fc7a60b9ebb08c8051b7c2c2	package.json
100644 blob 2c2d5a09b80bf6866f87102b0d1c2a81e1830d92	server.js
  • tree → the complete snapshot: every file (blob) and its hash. 83f1b73… is the "after" hash from section 2's diff.
  • parent → the previous commit. A root commit has none, and a merge commit has two (section 6).
  • author wrote the change and committer applied it (they differ after a rebase). Timestamps are Unix seconds plus the timezone.

Everything is content-addressed: same content, same ID, on any machine. echo 'hello' | git hash-object --stdin prints ce013625030ba8dba906f756967f9e9ca394464a for everyone. Docker digests work the same way (Session 6). It's also why editing an old commit changes its SHA and every later one, since each commit includes its parent's SHA.

Exam trap

"A commit stores only the lines that changed." ✗ Conceptually it's a full snapshot (a tree of all files). Diffs are computed on demand, and unchanged files reuse the same blob.

"I can fix a typo in an old commit's message and keep its SHA." ✗ The message is hashed too, so you get a new commit with a new SHA.

Remember

Commit = snapshot (tree) + parent + author + message → SHA.
log = follow parents · show = one commit · log -- file = who touched it.

Mastery check
Q1. Predict: you and Aditi each commit identical files with the identical message on the same parent, on two laptops. Same SHA?

Almost certainly not. The author and committer lines (names, emails, timestamps) are hashed too. The trees would match, because the files are identical.

Q2. Which command shows what changed in server.js between the initial commit and now?

git diff 95b5735 HEAD -- server.js (or git log -p -- server.js for commit-by-commit).

Q3. Aditi says she committed a fix, but git log --oneline on your main doesn't show it. Give two possible reasons.

(1) It's on another branch: git log --all shows every local branch. (2) It's only on GitHub and you haven't fetched: git fetch, then git log origin/main (section 7). Log only shows what your repo has.

4 .gitignore

The problem

.env and node_modules/ appear in every git status, and one careless git add . would commit your password and 40,000 dependency files. Ask Git what it would add:

$ git add --dry-run .             # -n: list what would be staged, stage nothing
add '.env'
add 'node_modules/accepts/package.json'
add 'node_modules/express/index.js'
add 'node_modules/express/package.json'
…

The idea

A .gitignore file lists patterns for untracked files that Git should act as if it can't see. They vanish from status, and git add . skips them. You commit .gitignore itself, so the whole team ignores the same things.

Think of it like this

A "never photograph these" sign next to the camera. The photographer skips those items in every new photo, but the sign can't remove them from photos already in the album.

See it: one line

$ echo 'node_modules/' > .gitignore && git status -s
?? .env
?? .gitignore

The 40,000 files are gone from view, and .env stays because nothing matches it yet. What it does not do: delete anything (node_modules/ is still on disk), or affect files that are already tracked.

Build it up: TaskFlow's real .gitignore

.gitignore
# ---- dependencies (recreated by "npm ci") ----
node_modules/
# ---- secrets: never commit real passwords ----
.env
.env.*
# ...but DO commit the template with dummy values
!.env.example
# ---- logs ----

# ---- test & build output ----

# ---- OS / editor junk ----

# ---- Terraform (Session 20) ----

$ git check-ignore -v .env app.log .env.example logs/y.txt     # which line decided?
.gitignore:4:.env	.env
.gitignore:9:*.log	app.log

$ git add .gitignore && git commit -m "Add .gitignore"

Each line reads file:line:pattern, then the path. For .env.example, the deciding pattern is the ! line, so it is not ignored.

Common mistake: the file is already tracked 
$ echo '.env' >> .gitignore && git status -s     # .env was committed last week
 M .env
 M .gitignore
$ git rm --cached .env             # stop tracking it; the file stays on disk
rm '.env'

Commit that, then rotate the password. It's still in every old commit, which every clone has (Session 19 covers purging history).

Exam trap

"node_modules/ # deps ignores node_modules." ✗ In .gitignore, comments only work at the start of a line. This is one literal pattern that matches nothing. (~/.gitconfig is a different format and does allow trailing comments.)

"logs/ then !logs/keep.txt keeps one file." ✗ Git never looks inside an excluded directory. Write logs/* (the contents) and then !logs/keep.txt.

Remember

.gitignore hides untracked files only · already tracked → git rm --cached.
Last matching line wins · # only at the start of a line.

Mastery check
Q1. Spot the bug: a teammate's .gitignore has !.env.example on line 3 and .env.* on line 4. Is .env.example committed?

No, it's ignored. Line 4 matches last, so it wins: git check-ignore -v .env.example prints .gitignore:4:.env.*. Swap the lines.

Q2. Write the pattern that ignores dist/ at the repo root but not docs/dist/.

/dist/. The leading slash anchors it to the root, and the trailing slash means directories only.

Q3. Predict: .gitignore has *.log. git add debug.log refuses, so you run git add -f debug.log and commit. Later you edit debug.log. Does git status show it?

Yes, as  M debug.log. -f forced the ignored file in, and once a file is tracked, .gitignore no longer applies to it.

5 Branching

The problem

You're halfway through adding request logging, and server.js doesn't run yet. Then: production's default port is wrong and needs a fix within the hour, made from clean code. Copying the folder to taskflow_fix/ is section 1's mess again.

The idea

A branch is a movable pointer to a commit: a tiny file holding a SHA. HEAD points to the branch you're on. Each commit moves that branch forward and leaves the others where they are, so several lines of work sit side by side and switching takes a second.

before:   95b5735 ◀ 7b6c9ea ◀ 8c5b6ba ◀ b29ae5c   ← main ← HEAD

after "git switch -c feature/request-logging" and one commit:
          95b5735 ◀ 7b6c9ea ◀ 8c5b6ba ◀ b29ae5c   ← main
                                         ▲
                                         └── 42d02cc   ← feature/request-logging ← HEAD
Think of it like this

A branch is a bookmark on one photo, and HEAD is the bookmark you're holding. Each new photo goes right after your bookmark, and the bookmark moves onto it while the others stay put. A new bookmark costs nothing, because nothing is copied.

See it: a branch is a 41-byte file

$ cat .git/HEAD && cat .git/refs/heads/main
ref: refs/heads/main
b29ae5cb36babf65056253c1b5a95a106d6f2106             # the .gitignore commit from section 4
$ git switch -c feature/request-logging
Switched to a new branch 'feature/request-logging'
$ cat .git/HEAD
ref: refs/heads/feature/request-logging
TokenMeaning
switchMove HEAD to a branch and update the working files to match it
-cCreate the branch first, at the current commit (old style: git checkout -b)
feature/request-loggingThe name. feature/… and fix/… are conventions, and / is just part of the name.

What it does not do: copy files, create a commit or touch GitHub. The new branch points at the same commit as main until you commit on it.

Build it up

$ git commit -am "Log every request"           # -a stages modified tracked files
[feature/request-logging 42d02cc] Log every request
 1 file changed, 4 insertions(+)
$ git branch -vv                                 # * = current; each tip's SHA and message
* feature/request-logging 42d02cc Log every request
  main                    b29ae5c Add .gitignore
$ git switch main && grep -c "req.method" server.js
Switched to branch 'main'
0                                              # main has no logging line; switch back and it's 1 again
$ git switch feature/request-logging            # with an uncommitted edit to server.js on main
error: Your local changes to the following files would be overwritten by checkout:
	server.js
Please commit your changes or stash them before you switch branches.
Aborting
$ git branch -d experiment                      # a branch whose commits exist nowhere else
error: the branch 'experiment' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D experiment'

Same folder, different snapshot, so the urgent fix is easy. git switch main, then git switch -c fix/default-port, commit, and come back later. Git refuses to switch over uncommitted edits (commit or stash first, section 9). -d deletes only merged branches, -D forces it, and -m old new renames.

Older tutorials use git checkout for all of this, and Git ≥ 2.23 splits it up: checkout main → switch main, checkout -b x → switch -c x, checkout -- file → restore file, checkout 7b6c9ea → switch --detach 7b6c9ea. The last gives a detached HEAD (HEAD detached at 7b6c9ea). That's fine for looking around, but commits made there belong to no branch. Run git switch -c rescue before leaving, or they'll be garbage-collected.

Exam trap

"A branch is a copy of the code." ✗ It's a 41-byte pointer. Switching rewrites your working files from that commit's snapshot.

"git branch feature/x switches to it." ✗ It only creates the branch. git switch -c creates and switches.

Remember

Branch = movable pointer · HEAD = the branch you're on · a commit moves only HEAD's branch.

Mastery check
Q1. Predict: on main you run git branch feature/x, edit a file and commit. Which branch gets the commit?

main. git branch didn't switch, so HEAD still pointed at main and main moved. feature/x stays on the old commit.

Q2. git branch -d experiment says "not fully merged". What does that tell you, and when is -D right?

The branch has commits no other branch contains, so deleting it orphans them. Use -D only when you want that work gone. (Until garbage collection, git reflog can still find it.)

Q3. You switch from main to feature/request-logging. Which files on disk change? What happens to an untracked notes.txt?

Only tracked files that differ between the two commits are rewritten: here server.js gains the logging line. notes.txt is in neither snapshot, so Git leaves it alone and it follows you.

6 Merge & rebase

The problem

feature/request-logging is done. How do its commits get into main? Either main hasn't moved since you branched, or teammates have added commits to it meanwhile.

The idea

Merge joins histories. If main hasn't moved, Git slides its pointer forward: a fast-forward, with no new commit. If both sides moved, Git compares three snapshots (the common ancestor and both tips) and records a merge commit with two parents. Rebase instead replays your commits on top of main's newest one, which gives new commits, new SHAs and a straight line.

Fast-forward                       3-way merge                          Rebase
A ◀ B           ← main             A ◀ B ◀ E          ← main            A ◀ B ◀ E          ← main
     ◀ C ◀ D    ← feature               ◀ D           ← feature                   ◀ D'     ← feature
git merge → main jumps to D        git merge → A ◀ B ◀ E ◀ M  ← main    (D' = D replayed: new SHA;
(no new commit)                                   ◀ D ◀┘ (M: 2 parents)  then main can fast-forward)
Think of it like this

Fast-forward is sliding the main bookmark to your newest photo. A merge commit is a photo with two "follows" notes, joining two lines of photos. Rebase is re-shooting your photos on top of the newest page: same scenes, new photos, new IDs.

The golden rule of rebasing

Never rebase commits that others already have (anything on main or a shared branch). Rebase replaces commits, so teammates' history stops matching yours. Your own unshared branch is fine. If you'd already pushed it, update it with git push --force-with-lease, which refuses if someone else pushed meanwhile and is safer than --force.

Tidy your own commits: interactive rebase

# Rebase 44e6c0b..830460d onto 44e6c0b (3 commands)
# Commands:
# p, pick <commit> = use commit
# s, squash <commit> = use commit, but meld into previous commit

Mastery check
Q1. Aditi pulled your pushed feature/env-example (with d37bdda) before you rebased it, and you force-pushed the result (82bde8e). What happens on her next pull?

Her copy and the remote have diverged: she has the old commits, the remote has replacements with the same messages. A plain pull merges them, giving duplicate-looking commits and possibly conflicts. That's the golden rule: coordinate, or don't rebase shared branches.

Q2. Predict: main gets git merge --squash feature/b (3 commits) then git commit. How many new commits on main, with how many parents?

One commit with one parent, holding all three commits' changes. feature/b's own commits aren't in main's history, so git branch -d feature/b later says "not fully merged".

Q3. Spot the bug: to bring a finished feature into main, someone runs git switch main && git rebase feature/x.

It's backwards: it replays main's commits onto feature/x. Any main commits that feature/x lacks get new SHAs, which rewrites the shared branch and breaks the golden rule. Run git merge feature/x on main, or git rebase main on feature/x first.

7 Remotes & pull requests

The problem

Everything so far lives in one .git on your laptop. Aditi can't see it, CI (Session 18) can't test it, and a dead disk takes it all. And once there is a shared copy, nobody should push straight into its main without a second pair of eyes.

The idea

A remote is a named URL for another copy of the repo, conventionally origin. push uploads commits. fetch downloads into remote-tracking branches like origin/main (your snapshot of GitHub's main) and never touches your own branches. pull = fetch + merge. A pull request (PR) is a GitHub page asking to merge one branch into another, with the diff, a review and CI checks.

 your laptop                                  GitHub (origin)

 origin/main ◀─────── git fetch ───────────── main        (fetch never touches your main)
 main ◀── git pull = fetch + merge origin/main
 feature/x ── git push -u origin feature/x ──▶ feature/x ──▶ Pull Request #7 → review + CI → merge into main
Think of it like this

GitHub is the shared album. push uploads your photos. fetch downloads everyone else's into a "their copy" section (origin/main) without moving your bookmarks, and pull downloads and merges. A PR is a note saying "please add my photos to the main album", reviewed before anything is glued in.

Mastery check
Q1. After git fetch, status says [behind 2]. Have any of your working files changed? How do you see what's coming?

No. fetch only updated origin/main. Inspect with git log --oneline main..origin/main or git diff main origin/main, then git pull when ready.

Q2. Branch protection requires the ci / test check to pass, and a PR's tests fail. What can the author do, and what can't they?

They can push more commits to the same branch, and the PR and CI update automatically. They can't merge until the check is green, and they can't bypass it by pushing to main, because pushes to protected main are rejected.

Q3. Predict: you create feature/y and run a plain git push (no -u, no autoSetupRemote). What happens?

8 Merge conflicts

The problem

Aditi sets TaskFlow's default port to 8080 on fix/default-port. Meanwhile you set the same line to 4000 on main. Each commit is fine on its own, but both can't win.

The idea

Git merges different files, and different lines of one file, automatically. A merge conflict happens only when both sides changed the same lines (or one edited a file the other deleted). Git stops mid-merge, writes both versions into the file between markers, and waits for you.

             merge base:  const PORT = process.env.PORT || 3000;
              ┌──────────────────────┴───────────────────────┐
 main (ours):  … || 4000;                    fix/default-port (theirs):  … || 8080;
              └──────────────────────┬───────────────────────┘
                 same line changed on both sides → CONFLICT, you decide
Think of it like this

Two people retouched the same spot in the same photo. Git happily combines edits to different parts of the picture, but here it puts both versions side by side and asks you to pick one, or paint something new.

See it: create one

$ git switch -c fix/default-port
$ sed -i 's/|| 3000/|| 8080/' server.js && git commit -qam "Change default port to 8080"
$ git switch main
$ sed -i 's/|| 3000/|| 4000/' server.js && git commit -qam "Change default port to 4000"
$ git merge fix/default-port
Auto-merging server.js
CONFLICT (content): Merge conflict in server.js
Automatic merge failed; fix conflicts and then commit the result.
server.js (lines 10–15, during the conflict)
<<<<<<< HEAD
const PORT = process.env.PORT || 4000;
=======
const PORT = process.env.PORT || 8080;
>>>>>>> fix/default-port
const HOST = process.env.HOST || '0.0.0.0';
LineMeaning
<<<<<<< HEADStart of your side: the branch you're on (main)
=======The divider between the two versions
>>>>>>> fix/default-portEnd of their side: the branch being merged in
const HOST …Outside the markers: no conflict, already merged

What it does not do: pick a winner or commit. Every non-conflicting change is already merged and staged, and only these lines wait for you. Until you fix them, the file isn't valid JavaScript.

Build it up: resolve it

$ git status                       # trimmed

  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

	both modified:   server.js

#    (the team agreed to keep 3000: const PORT = process.env.PORT || 3000;)
$ grep -nE '^(<<<<<<<|=======|>>>>>>>)' server.js     # 2. no output = no markers left
$ git add server.js                         # 3. mark it resolved
$ git commit --no-edit                      # 4. finish the merge with the default message
[main adab73f] Merge branch 'fix/default-port'
  • Panic button: git merge --abort restores everything to how it was before git merge.
  • One whole side: git checkout --ours server.js (or --theirs), then git add.
  • Rebase conflicts look the same but say error: could not apply f5bb065... Change default port to 8080. Resolve, git add, then git rebase --continue (or --abort / --skip).
  • Prevention: merge main into your branch daily, keep PRs small, don't reformat whole files.
Exam trap

"Two people editing the same file always conflict." ✗ Only overlapping changes to the same lines do. Edits in different functions merge automatically.

"During a rebase, --ours is my branch." ✗ A rebase replays your commits onto main, so "ours" is the branch you're rebasing onto and "theirs" is your commit.

Remember

Conflict = same lines changed on both sides.
Edit → delete markers → git add → git commit (or --abort).

Mastery check
Q1. Spot the bug: after resolving, the API crashes with SyntaxError: Unexpected token '==='. What happened, and what would have caught it?

A ======= marker was left in and committed. git diff --cached --check reports leftover conflict marker and exits non-zero, and so does the grep above.

Q2. Predict: Aditi changes the /health handler and you change the PORT line, both in server.js. Conflict?

No. Different, non-adjacent lines merge automatically into one file with both changes. (Directly adjacent lines can still conflict.)

Q3. Predict: one branch deleted README.md and the other edited it. What does the merge say, and what are your two ways out?

CONFLICT (modify/delete): README.md deleted in del and modified in HEAD, and status shows deleted by them: README.md. Keep it with git add README.md, or accept the deletion with git rm README.md, then commit.

9 Undoing mistakes, stash & tags

The problem

1. You edited server.js, it's broken, and you want the committed version back.
2. You staged the wrong file.
3. Your last commit's message says "Pin Node 20 wiht .nvmrc".
4. A commit that logs request bodies (passwords included!) is already on GitHub's main.
5. You're mid-feature when an urgent bug arrives.

Each needs a different tool. The wrong one either fails, or rewrites history your teammates already have.

The idea

Choose by where the mistake lives, using section 2's three areas plus "already pushed":

 Working dir        Staging               Local commits (not pushed)        Pushed / shared commits
 git restore f      git restore           git commit --amend                git revert <sha>
 (discard edits)    --staged f (unstage)  git reset --soft|--mixed|--hard    (a NEW commit that undoes it)
 ───────────────────────────────────────────────────────────────────────────────────────────────
 safety net for anything that was ever committed: git reflog
Think of it like this

restore tidies the room or the frame. reset tears photos out of your own album, which is fine while nobody has copies. revert adds a photo that undoes an old one, the polite option once the album is shared. reflog is the security-camera log of every photo you ever held.

See it: mistakes 1 and 2

$ git status -s

$ git restore server.js            # working file ← its staged/committed version; status is now clean
$ git add server.js && git restore --staged server.js && git status -s     # unstage, keep edits
 M server.js

What it does not do: git restore file has no undo. Those edits were never committed, so not even reflog can bring them back.

Exam trap

"reset --hard is safe because reflog can undo it." ✗ Reflog brings back commits. Uncommitted changes wiped by --hard are gone for good.

"git revert deletes the commit from history." ✗ It adds a new commit. The old one, and any secret in it, stays.

Remember

Not pushed → amend / reset · Pushed → revert · Lost a commit → reflog.
soft = staged · mixed = unstaged · hard = gone.

Mastery check
Q1. A bad commit is already on GitHub's main. reset or revert? Why?

git revert <sha>. It undoes the change with a new commit and rewrites nothing, so teammates' clones stay valid and a normal push works. reset plus a force push rewrites shared history (and protected main rejects it).

Q2. Predict: you run git stash (without -u) with a modified server.js and a new notes.txt, then git switch main. Which file is in your working directory on main?

notes.txt. Plain stash only shelves tracked changes, so the untracked file stays and follows you. git stash -u includes it.

Q3. CI is set to build a release image on tags. You created v1.1.0 and ran git push, but nothing was built. Why?

A plain push sends branches, not tags, so the tag exists only on your laptop. Run git push origin v1.1.0. (git ls-remote --tags origin lists the tags GitHub has.)

"Commit messages don't matter." ✗ "changes" or "final2" tell reviewers nothing. Write the why, in the imperative mood: fix: return 400 when title is missing.

Remember

pull main → switch -c → code + test → commit → rebase on origin/main → push -u → PR → CI + review → squash-merge → pull → tag.

Mastery check
Q1. After the squash merge you run git fetch --prune, then git branch -d feature/tasks-endpoint (suppose gh hadn't deleted it). Predict the result.

It refuses: "not fully merged". The squash made a new commit, so your original commits aren't ancestors of main. The work is in main, so -D is correct.

Q2. Step 5 used git rebase origin/main. When would you git merge origin/main into the branch instead?

When others already work on the same branch, or you'd rather not rewrite it after pushing. A merge rewrites nothing. Rebasing a pushed branch means git push --force-with-lease and re-syncing.

Q3. Predict: in step 5 the rebase stops with a conflict in server.js. What exactly do you type next, and does step 6's push need --force?

Fix the file, then git add server.js → git rebase --continue (or git rebase --abort to back out). No force: the branch was never pushed, so step 6 is its first push.

★ Putting it all together

The big idea

Git stores TaskFlow as a chain of content-addressed snapshots, and staging picks what goes into each one. Branches are cheap pointers into that chain, so every change starts on its own branch. Merge keeps true history and is safe everywhere. Rebase makes history linear by rewriting SHAs, so use it only on your own branches. GitHub adds the team layer: a PR with review and CI, guarded by branch protection, is the only way into main, which the rest of the course builds, scans and deploys.

Final mastery check — combine everything
Q1. You made two commits directly on local main, and git push is rejected because main is protected. Move the work onto a PR without losing anything.

git switch -c feature/x (the new branch points at your two commits) → git switch main && git reset --hard origin/main (safe: the commits live on feature/x) → git switch feature/x && git push -u origin feature/x → gh pr create.

Q2. You committed .env with the real DB password and pushed it to your PR branch. What do you do, in order?

(1) Rotate the password, and assume it has leaked. (2) Add .env to .gitignore and git rm --cached .env. (3) It's your own unmerged branch, so rewrite it until no commit holds the secret (interactive rebase: edit or drop that commit), then git push --force-with-lease. git revert would leave the password in history.

Q3. main is at A. On feature you commit B and C, while main gets D. Draw the history after (a) git merge feature on main, (b) git rebase main on feature, then a merge on main.

(a) A ◀ D ◀ M, with M's second parent C (A ◀ B ◀ C): a merge commit with two parents. (b) A ◀ D ◀ B' ◀ C', a straight line. B and C get new SHAs and main fast-forwards to C'.

Q4. git status -sb shows ## main...origin/main [ahead 1, behind 2]. What happened, what will git pull do with section 1's config, and what could go wrong?

You committed once while 2 commits reached GitHub: diverged. With pull.rebase = false, pull fetches and makes a merge commit, with a conflict to resolve if both sides changed the same lines (section 8). Then a normal push works.

Q5. Correct every error: "git pull only downloads, so it's always safe. If I mess up main I'll git reset --hard HEAD~1 and git push --force. My release tags go up with git push."

(1) pull = fetch + merge, so it can create merge commits and conflicts (fetch only downloads). (2) Reset plus force-push on shared main rewrites history and deletes teammates' commits. Use git revert, which protected main requires anyway. (3) Tags need git push origin v1.0.0 or --tags.
