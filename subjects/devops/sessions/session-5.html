1 Git vs GitHub & setup

Explain like I'm 5

Git is the save-game system on your laptop. GitHub is the cloud locker where the whole team keeps and reviews those saves.

GitGitHub
WhatDistributed version control system (a CLI tool)Hosting service for Git repositories + collaboration
RunsLocally; works fully offlineIn the cloud (github.com) or GitHub Enterprise
Made byLinus Torvalds, 2005 (for the Linux kernel); open sourceGitHub Inc., owned by Microsoft
Gives youCommits, branches, merges, history, diffRemote repos, pull requests, code review, issues, Actions (CI/CD), branch protection, GHCR, Pages
AlternativesSVN (centralised), MercurialGitLab (built-in CI via .gitlab-ci.yml, self-hostable), Bitbucket (Atlassian, Jira integration), Azure Repos
  • Distributed = every clone has the full history. GitHub is just one more copy everyone agrees to sync with (origin).
  • GitHub calls them pull requests; GitLab calls the same thing merge requests.

One-time setup

$ git --version
git version 2.43.0
$ git config --global user.name "Shaurya Verma"
$ git config --global user.email "shaurya@example.com"     # must match your GitHub email to link commits
$ git config --global init.defaultBranch main              # new repos start on "main", not "master"
$ git config --global pull.rebase false                    # "git pull" merges (avoids the divergent-branches error)
$ git config --list --show-origin | grep user

file:/home/shaurya/.gitconfig	user.email=shaurya@example.com

2 Repository & commits

Explain like I'm 5

You put things in a box (staging), then take a photo of the box (commit). The photo album is the repository.

  • A repository = your project folder + a hidden .git/ directory holding every snapshot.
  • A commit = a full snapshot of the staged files + author + message + pointer to its parent commit.
  • The staging area (index) lets you choose exactly what goes into the next commit.
 Working directory      Staging area (index)       Local repo (.git)          Remote (GitHub "origin")
 files you edit         the next commit            committed history
      │ ── git add ─────────▶ │ ── git commit ──────────▶ │ ── git push ───────────▶ │
      │ ◀─ git restore --staged (unstage)                │ ◀── git fetch ────────── │
      │ ◀──────── git restore file / git switch ──────── │
      │ ◀─────────────────── git pull  (= fetch + merge into your branch) ──────── │

  • SHA (40 hex chars) = hash of the commit's content. Change anything (message, parent, a file) → new SHA. That's why rewriting history changes SHAs.
  • tree → snapshot of all files (blobs). parent → previous commit (merge commits have 2; the first commit has none).
  • author wrote the change, committer applied it (differ after rebase/cherry-pick). Timestamp is Unix seconds + timezone.

Common mistakes
  • Inline comments don't work: node_modules/ # deps is one literal pattern and ignores nothing. (Git config files like ~/.gitconfig do allow trailing # comments — different format, different rules.)
  • .gitignore doesn't affect files already tracked. Committed .env by accident? git rm --cached .env → commit → and rotate the password: it's still in history.
  • git add . before writing .gitignore → 40,000 files from node_modules staged. git rm -r --cached node_modules.
Recap Edit → git add (stage) → git commit (snapshot with SHA + parent). status, log --oneline --graph, diff/diff --staged tell you where everything is. Ignore deps, secrets, logs, build output.

3 Branching

Explain like I'm 5

A branch is a sticky note on a commit saying "my work continues here". HEAD is the "you are here" marker.

  • A branch is a movable pointer to a commit — literally a file containing a SHA. Creating one is instant and free.
  • HEAD points to the branch you're on; a new commit moves that branch forward.
  • Work on short-lived branches (feature/tasks-endpoint, fix/default-port), keep main always deployable.

Commit or git stash first (section 6). And detached HEAD (git checkout <sha> or a tag): commits you make there belong to no branch — run git switch -c rescue-branch before leaving or they'll be garbage-collected.

4 Merge & rebase

Explain like I'm 5

Merge ties two strings together with a knot (a merge commit). Rebase unties your string and re-attaches it at the end of the other one, as if you'd started later.

Fast-forward merge (no divergence)

Before                                     After: git switch main && git merge feature/tasks-endpoint
  A ── B              ← main                 A ── B ── C ── D    ← main, feature/tasks-endpoint
        └── C ── D    ← feature              (main just slides forward — no new commit)
$ git merge feature/tasks-endpoint
Updating 3f2a9c1..5d8a0f2
Fast-forward
 server.js | 12 ++++++++++++
 1 file changed, 12 insertions(+)

Three-way merge (both sides moved)

Before                                     After: git merge feature/post-tasks
        ┌── D         ← feature                     ┌── D ──┐       ← feature
  A ── B ── E         ← main               A ── B ── E ───── M      ← main
                                           (M = merge commit with TWO parents: E and D)
$ git merge feature/post-tasks
Merge made by the 'ort' strategy.
 server.js | 9 +++++++++
 1 file changed, 9 insertions(+)

"Three-way" because Git compares three snapshots: the common ancestor (B) and both tips (E, D). ort is Git's default merge strategy.

  • git merge --no-ff feature/x — always create a merge commit, even if fast-forward was possible (keeps "this was one feature" visible).
  • git merge --squash feature/x — stage all of the branch's changes as one; you then git commit a single commit. Output: Squash commit -- not updating HEAD.

Rebase

Before                                     After: git switch feature && git rebase main
        ┌── C ── D    ← feature                         ┌── C' ── D'   ← feature  (NEW SHAs)
  A ── B ── E         ← main               A ── B ── E                ← main
                                           then on main: git merge feature  → fast-forward, linear history
$ git switch feature/tasks-endpoint
$ git rebase main
Successfully rebased and updated refs/heads/feature/tasks-endpoint.
$ git log --oneline --graph -4
* 6da9ae3 (HEAD -> feature/tasks-endpoint) Add POST /tasks
* 2c41b0e Add GET /tasks
* 16d8b16 (main) Add README
* 3f2a9c1 Initial commit: Express API with /health
  • Rebase replays your commits one by one on top of the new base → each gets a new SHA. On conflict: fix, git add, git rebase --continue (or --abort).
  • git pull --rebase = fetch + rebase your local commits on top of origin/main (no "Merge branch 'main' of …" noise).
  • Squash your own messy commits before a PR with interactive rebase: git rebase -i HEAD~3 opens this todo file:
.git/rebase-merge/git-rebase-todo (opened in your editor)
pick 2c41b0e Add GET /tasks
squash 6da9ae3 Add POST /tasks
fixup 8e1f2a3 fix typo

# Rebase 16d8b16..8e1f2a3 onto 16d8b16 (3 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# s, squash <commit> = use commit, but meld into previous commit
# …
VerbEffect
pickKeep the commit as-is
squashFold into the commit above and combine both messages (editor opens)
fixupFold into the commit above, discard this commit's message
reword / edit / dropChange the message / stop to amend the commit / delete it

Save and close: the three commits become one ("Add GET /tasks" + "Add POST /tasks" messages).

Golden rule of rebasing

Never rebase commits that others already have (pushed to main or a shared branch). New SHAs = your teammates' history no longer matches. Rebasing your own feature branch is fine; push it with git push --force-with-lease (refuses if someone else pushed meanwhile — safer than --force).

MergeRebase
HistoryTrue, non-linear; shows when branches joinedLinear, as if work happened sequentially
New commitsOne merge commit (unless fast-forward)Rewrites your commits (new SHAs)
Safe on shared branches?✅ Yes — never rewrites❌ No — only on your private branches
ConflictsResolved once, in the merge commitMay resolve per replayed commit
Undogit revert -m 1 <merge-sha>Harder — git reflog

Recap Fast-forward = pointer slides; 3-way = merge commit with 2 parents; rebase = replay commits on a new base (new SHAs). Merge shared branches, rebase only private ones.

Branch protection (Settings → Branches / Rules)

  • Require a pull request before merging + required approvals: 1 → nobody pushes straight to main.
  • Require status checks to pass → the CI workflow (Session 18) must be green. Add security scans as checks in Session 19 (security gates).
  • Require branches to be up to date, require conversation resolution, block force pushes and deletions, optionally require linear history.
Recap push -u once, then push/pull. fetch = download only; pull = fetch + merge. PR = branch → review + CI → merge (squash is the common default), enforced by branch protection.

6 Merge conflicts & undoing mistakes

Explain like I'm 5

Two people edited the same sentence differently. Git can't guess who's right, so it shows both and asks you to pick.

A merge conflict happens when both branches changed the same lines of a file (or one deleted a file the other edited). Different lines or files merge automatically.

Create one, step by step

$ git switch -c fix/default-port
$ sed -i 's/|| 3000/|| 8080/' server.js && git commit -qam "Change default port to 8080"
$ git switch main
$ sed -i 's/|| 3000/|| 4000/' server.js && git commit -qam "Change default port to 4000"
$ git merge fix/default-port
Auto-merging server.js
CONFLICT (content): Merge conflict in server.js
Automatic merge failed; fix conflicts and then commit the result.
$ git status

Common mistakes
  • git reset --hard with uncommitted work — reflog can't save changes that were never committed. Stash or commit first.

Common mistakes
  • Working directly on main → branch protection rejects the push. Fix: git switch -c feature/x (your commits come with you), then git switch main && git reset --hard origin/main.

★ Putting it all together

The big idea

Git stores TaskFlow as a chain of content-addressed snapshots; branches are cheap pointers into that chain, so every change starts on its own branch. Merge and rebase are two ways to join the chains — merge keeps true history and is safe everywhere, rebase makes it linear but rewrites SHAs, so only on private branches. GitHub adds the team layer: a pull request with review and CI checks, guarded by branch protection, is the only way into main — and that same main is what the rest of the course builds, scans and deploys.

Quick self-check

What's the difference between Git and GitHub? Name two GitHub alternatives.

Git is the distributed version control tool that runs locally (commits, branches, merges). GitHub is a hosting service for Git repos adding PRs, reviews, issues, Actions, permissions. Alternatives: GitLab, Bitbucket (also Azure Repos).

You ran git add server.js, then edited server.js again. What does git status -s show and what will git commit save?

MM server.js. The commit saves only the version that was staged (at the time of git add); the later edits stay unstaged until you git add again.

When does git merge fast-forward, and when does it create a merge commit?

Fast-forward when the target branch has no new commits since the feature branched off (its tip is an ancestor of the feature) — the pointer just moves. If both branches have new commits, Git does a 3-way merge and creates a merge commit with two parents (unless --no-ff forces one anyway).

State the golden rule of rebasing and why it exists.

Never rebase commits that have been pushed to a shared/public branch. Rebase creates new commits with new SHAs; anyone who based work on the old SHAs now has diverging history and painful merges/duplicates.

Explain the three parts of a conflict block and how you finish the merge.

<<<<<<< HEAD … your current branch's version; ======= divider; … their version >>>>>>> branch. Edit to the correct final content, delete all markers, git add the file, then git commit (or git merge --abort to cancel).

A bad commit is already on GitHub's main. reset or revert? Why?

git revert <sha>: it adds a new commit that undoes the change, without rewriting history, so teammates' clones stay valid. reset + force push would rewrite shared history.

git fetch vs git pull?

fetch downloads new commits into remote-tracking branches (origin/main) without touching your branch or files. pull = fetch + merge (or rebase with --rebase) into your current branch, and can cause conflicts.
