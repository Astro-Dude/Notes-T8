1 Cloud fundamentals

Explain like I'm 5

Instead of buying a generator for your house, you plug into the power grid and pay for the units you use. Cloud is the grid for computers.

Cloud computing = on-demand compute, storage and networking over the internet, paid per use. NIST's five characteristics: on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service.

On-premisesCloud
Cost modelCapEx: buy servers up front, depreciate over yearsOpEx: pay-as-you-go, monthly bill
Getting a serverWeeks (order, rack, cable)Minutes (API call / terraform apply)
ScalingBuy for peak; idle the rest of the timeElasticity: scale out and back in automatically
MaintenanceYou: power, cooling, disks, hardware failuresProvider runs the data centres
Global reachOne buildingRegions on every continent
ControlFull (hardware, network)Limited to what the provider exposes
Example: TaskFlow launch day

Normal load needs 2 servers; launch-day peak needs 10 for 3 hours. On-prem you buy 10 and 8 sit idle almost all year. In the cloud you run 2, auto-scale to 10, and pay for 8 × 3 extra instance-hours.

Deployment models: public (AWS, Azure, GCP), private (your own OpenStack/VMware), hybrid (on-prem + public, connected by VPN/Direct Connect), multi-cloud (several public clouds).

Shared responsibility model

AWS — security of the cloudYou — security in the cloud
Data centres, physical access, hardware, hypervisor, global network, internals of managed servicesYour data, IAM users/policies, OS patches on EC2, app code, security group rules, encryption settings, keys

The line moves with the service: on EC2 you patch Ubuntu; on RDS AWS patches the OS and Postgres, you manage DB users and network access; on S3 you only own bucket policies, encryption and "block public access".

3 Regions & Availability Zones

Explain like I'm 5

A region is a city where AWS has data centres; AZs are separate buildings in that city, on different power and network lines. If one building floods, the others keep running.

  • Region = a geographic area with its own independent set of services, e.g. ap-south-1 (Mumbai), ap-south-2 (Hyderabad), us-east-1 (N. Virginia). Most resources (VPC, EC2) live in exactly one region.
  • Availability Zone (AZ) = one or more isolated data centres inside a region, connected by low-latency links: ap-south-1a, -1b, -1c.
  • Edge locations (CloudFront CDN, Route 53) are many more, smaller sites close to users.
$ aws ec2 describe-availability-zones --region ap-south-1 \
    --query "AvailabilityZones[].[ZoneName,ZoneId,State]" --output table

+--------------+------------+-------------+

$ aws ec2 describe-regions --all-regions --query "Regions[?starts_with(RegionName,'ap-south')].[RegionName,OptInStatus]" --output text

ZoneName (ap-south-1a) is mapped to a physical zone differently per account; ZoneId (aps1-az1) is the same for everyone. Newer regions like Hyderabad are opt-in.

Pick a region byTaskFlow reasoning
Latency to usersUsers in India: Mumbai ≈ 10–30 ms vs us-east-1 ≈ 200+ ms
Compliance / data residencyCustomer data may need to stay in India (contracts, India's DPDP Act 2023)
Service availabilityNew services/instance types often launch in us-east-1 first
PriceSame service costs differ by region; us-east-1 is usually cheapest
Example: multi-AZ for high availability

Run 2 TaskFlow instances, one in ap-south-1a and one in ap-south-1b, behind a load balancer; RDS in Multi-AZ mode (standby in another AZ). Losing a whole AZ halves capacity but nothing goes down. One instance in one AZ = single point of failure.

Common mistake

"My EC2 instance disappeared!" — the console is showing a different region (top-right selector). Resources are per region; Terraform created them in var.aws_region.

Recap Region = city, AZ = isolated building(s) in it. Choose region by latency, compliance, services, price; spread across ≥ 2 AZs for HA.

4 VPC, subnets & route tables

Explain like I'm 5

The VPC is your private gated campus, subnets are the buildings, route tables are the signposts, the Internet Gateway is the main gate, and a NAT gateway is an exit-only turnstile.

  • VPC (Virtual Private Cloud) = your logically isolated network in one region, spanning all its AZs. You pick its private IP range as a CIDR, between /16 and /28 — TaskFlow uses 10.0.0.0/16 (65,536 addresses, RFC 1918 private, Session 4).
  • Every region has a default VPC (172.31.0.0/16, all subnets public) — fine for a quick test, not for real projects.
AWS VPCAzure VNetGCP VPC
ScopeOne regionOne regionGlobal
Subnet scopeOne AZWhole region (spans zones)One region
FirewallSecurity groups + NACLsNSGsFirewall rules

Subnets

  • A subnet is a slice of the VPC CIDR that lives in exactly one AZ.
  • Public subnet = its route table sends 0.0.0.0/0 to an Internet Gateway (and instances get a public IP). Private subnet = no route to the IGW; reachable only from inside the VPC.
  • AWS reserves 5 IPs in every subnet. In 10.0.1.0/24: .0 network, .1 VPC router, .2 DNS, .3 reserved, .255 broadcast → 256 − 5 = 251 usable (10.0.1.4–10.0.1.254). Azure also reserves 5; GCP 4.

private-a10.0.11.0/24ap-south-1aprivate (app / DB)251
private-b10.0.12.0/24ap-south-1bprivate251

> cidrsubnet("10.0.0.0/16", 8, 1)        # add 8 bits to /16 → /24, take network number 1
"10.0.1.0/24"

Route tables

  • A route table is a list of destination CIDR → target. Each subnet is associated with exactly one (the VPC's main table if you don't choose).
  • Every table has an automatic local route for the VPC CIDR. The most specific match wins: 10.0.11.25 matches both 10.0.0.0/16 and 0.0.0.0/0 → /16 wins, traffic stays inside.

5 Security groups vs NACLs

Explain like I'm 5

A security group is a bouncer at each flat's door who remembers who went out, so they can come back in. A NACL is a guard at the building gate with a checklist who checks everyone, in both directions, every time.

  • Security group (SG): virtual firewall on an instance's network interface. Stateful: if a request is allowed in, its reply is allowed out automatically. Allow rules only; anything not allowed is denied. A new SG allows all outbound, no inbound.
  • A rule's source can be a CIDR or another security group ("anything wearing the app-SG badge").

TaskFlow app SG (what §6 creates):

DirectionPortSource / destinationWhy
Inbound22 (SSH)203.0.113.45/32Only your laptop
Inbound80 (HTTP)0.0.0.0/0Public web
Inbound30000.0.0.0/0TaskFlow API directly
OutboundAll0.0.0.0/0apt-get, Docker Hub pulls

A database SG that trusts the app servers by SG reference instead of IPs (for a future RDS in the private subnets):

resource "aws_security_group" "db" {
  name   = "taskflow-dev-db-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    description     = "Postgres from app servers only"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id]   # source = another SG, not a CIDR
  }
}
  • Network ACL (NACL): firewall at the subnet boundary. Stateless: replies must be allowed explicitly. Has allow and deny rules, evaluated in rule-number order, first match wins. The default NACL allows everything; a new custom NACL denies everything.
Rule #DirectionPortSource / destAction
90InAll198.51.100.0/24DENY (abusive range)
100In80, 30000.0.0.0/0ALLOW
110In22203.0.113.45/32ALLOW
120In1024–655350.0.0.0/0ALLOW (replies to our apt/docker downloads)
100Out80, 4430.0.0.0/0ALLOW
110Out1024–655350.0.0.0/0ALLOW (replies to clients)
*BothAll0.0.0.0/0DENY (implicit last rule)
Example: why "stateless" needs ephemeral ports

Your laptop 203.0.113.45:51514 calls 10.0.1.37:3000. The reply goes back to port 51514. The SG lets it out automatically (stateful). The NACL only lets it out because of outbound rule 110 for 1024–65535 — delete that rule and the request arrives but the reply is dropped: curl just hangs.

Security groupNetwork ACL
LevelInstance (network interface)Subnet
StateStateful — replies auto-allowedStateless — allow replies explicitly
RulesAllow onlyAllow and deny
EvaluationAll rules, most permissive winsIn number order, first match wins
Source can beCIDR or another SGCIDR only
DefaultNew SG: no inbound, all outboundDefault NACL: allow all; custom NACL: deny all

Common mistakes

In Terraform, aws_security_group removes AWS's default allow-all egress rule. Forget the egress block and the instance can't reach apt or Docker Hub; user_data fails silently.
Opening port 22 to 0.0.0.0/0: bots start brute-forcing SSH within minutes. Use /32 of your IP (or SSM Session Manager).

Recap SG = stateful, allow-only, per instance, can reference other SGs. NACL = stateless, allow + deny, numbered, per subnet, needs ephemeral-port rules for replies.

terraform {
  required_version = ">= 1.10.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"

provider "aws" {
  region = var.aws_region            # ap-south-1

  default_tags {                     # merged into the tags of EVERY resource below

      Environment = var.environment

resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true                          # Amazon DNS at 10.0.0.2
  enable_dns_hostnames = true                          # instances get ec2-…compute.amazonaws.com names

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "${local.name}-igw" }
}

resource "aws_subnet" "public" {
  count                   = length(var.public_subnet_cidrs)       # 2 → public[0], public[1]
  vpc_id                  = aws_vpc.main.id
  cidr_block              = var.public_subnet_cidrs[count.index]
  availability_zone       = var.azs[count.index]
  map_public_ip_on_launch = true                       # instances here get a public IPv4
  tags = { Name = "${local.name}-public-${var.azs[count.index]}", Tier = "public" }
}

resource "aws_subnet" "private" {
  count             = length(var.private_subnet_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.private_subnet_cidrs[count.index]
  availability_zone = var.azs[count.index]
  tags = { Name = "${local.name}-private-${var.azs[count.index]}", Tier = "private" }
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id
  route {
    cidr_block = "0.0.0.0/0"                           # everything not local…
    gateway_id = aws_internet_gateway.main.id          # …goes to the internet gateway
  }
  tags = { Name = "${local.name}-public-rt" }
}

resource "aws_route_table_association" "public" {
  count          = length(var.public_subnet_cidrs)
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id           # THIS is what makes the subnet "public"
}

resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id                             # only the implicit local route
  tags   = { Name = "${local.name}-private-rt" }
}

resource "aws_route_table_association" "private" {
  count          = length(var.private_subnet_cidrs)
  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private.id
}

# ---------- Optional NAT (off by default: ~$40/month) ----------
resource "aws_eip" "nat" {
  count  = var.enable_nat_gateway ? 1 : 0
  domain = "vpc"
}

resource "aws_nat_gateway" "main" {
  count         = var.enable_nat_gateway ? 1 : 0
  allocation_id = aws_eip.nat[0].id
  subnet_id     = aws_subnet.public[0].id              # a NAT gateway lives in a PUBLIC subnet
  depends_on    = [aws_internet_gateway.main]
  tags          = { Name = "${local.name}-nat" }
}

resource "aws_route" "private_nat" {
  count                  = var.enable_nat_gateway ? 1 : 0
  route_table_id         = aws_route_table.private.id
  destination_cidr_block = "0.0.0.0/0"
  nat_gateway_id         = aws_nat_gateway.main[0].id
}

#!/bin/bash
# Rendered by Terraform templatefile(); cloud-init runs it ONCE, as root, on first boot.
# Output goes to /var/log/cloud-init-output.log
set -euxo pipefail                     # stop on errors, echo every command into the log

# 1. Docker from Ubuntu's own repo; let the 'ubuntu' user run docker without sudo
apt-get update -y
apt-get install -y docker.io
systemctl enable --now docker
usermod -aG docker ubuntu

# 2. Config for both containers. ${db_password} is replaced by TERRAFORM before bash runs.
#    'EOF' is quoted so bash doesn't expand $ inside; set -x doesn't print heredoc lines.
mkdir -p /opt/taskflow
cat > /opt/taskflow/app.env <<'EOF'
POSTGRES_USER=taskflow
POSTGRES_DB=taskflow
POSTGRES_PASSWORD=${db_password}
PORT=3000
DATABASE_URL=postgres://taskflow:${db_password}@db:5432/taskflow
EOF
chmod 600 /opt/taskflow/app.env

# 3. Network + Postgres + API (same as Session 8, without Compose)
docker network create taskflow-net
docker run -d --name db --network taskflow-net --restart unless-stopped \
  --env-file /opt/taskflow/app.env \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16
docker run -d --name api --network taskflow-net --restart unless-stopped \
  --env-file /opt/taskflow/app.env \
  -p 80:3000 -p 3000:3000 \
  ${app_image}

echo "TaskFlow bootstrapped on $(hostname) at $(date -Is)"
LineWhy
${db_password}, ${app_image}Template variables passed in templatefile(). Terraform only treats ${…} and %{…} specially, so $(hostname) is left for bash. A literal bash ${VAR} must be written $${VAR}.
<<'EOF'Quoted heredoc: bash writes the lines exactly as rendered (a $ in the password stays a $).
--env-file (not -e POSTGRES_PASSWORD=…)With set -x, every command line is copied into /var/log/cloud-init-output.log; a password passed with -e would end up in that log.
--restart unless-stoppedThe API may start before Postgres is ready and exit; Docker restarts it until the DB answers. Also survives reboots.
-p 80:3000 -p 3000:3000Same container on two host ports: http://IP/ and http://IP:3000/.
-v pgdata:…Named volume, so data survives a container restart (not instance termination — use RDS or EBS snapshots for that).

★ Putting it all together

The big idea

EC2 is IaaS: you rent a VM in an AZ of a region and own everything from the OS up. It lives in a VPC you design: subnets per AZ, route tables that decide which are public (route to the IGW) and which are private (local, or NAT for outbound), and security groups that statefully allow only ports 22 (from you), 80 and 3000. Terraform turns that design into 15 resources from a handful of files, boots TaskFlow with a user_data template, and removes all of it with one destroy so the bill stops.

Quick self-check

How many usable IPs does a /24 subnet have on AWS, and why?

251. 256 addresses minus 5 reserved by AWS: network (.0), VPC router (.1), DNS (.2), future use (.3), broadcast (.255).

What exactly makes a subnet "public"?

Its associated route table has 0.0.0.0/0 → Internet Gateway. Instances also need a public IP (map_public_ip_on_launch or an Elastic IP) to be reachable.

An SG allows inbound 3000 and has no outbound rule for high ports. Does the HTTP reply get out? What about a NACL with the same rules?

SG: yes — stateful, replies are allowed automatically. NACL: no — stateless, it needs an outbound rule for ephemeral ports 1024–65535.

Internet Gateway vs NAT Gateway?

IGW: two-way internet access for public subnets, free, attached to the VPC. NAT GW: outbound-only access for private subnets, lives in a public subnet with an Elastic IP, billed hourly + per GB.

TaskFlow on EC2 vs on RDS + Elastic Beanstalk — who patches the OS in each case?

EC2 is IaaS: you patch Ubuntu. Beanstalk/RDS are PaaS-style managed services: AWS patches the OS (and the DB engine); you manage the app, data and access rules.

terraform apply succeeded but curl IP:3000/health fails. List the checks in order.

Wait for cloud-init (cloud-init status --wait) → docker ps / docker logs api → SG has port 3000 → subnet associated with the public route table (0.0.0.0/0 → igw) → instance has a public IP → app listens on 0.0.0.0, not 127.0.0.1.

Why lifecycle { ignore_changes = [ami] } on the instance?

data "aws_ami" with most_recent = true returns a new ID whenever Canonical publishes an image; without ignoring it, the next plan would replace (destroy) the running server.
