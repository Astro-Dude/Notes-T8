1 Cloud fundamentals

The problem

TaskFlow is launching. Normal traffic needs 2 servers. Launch day needs 10, for about three hours.

                      Mon  Tue  Wed  Thu  LAUNCH  Sat  Sun
servers needed          2    2    2    2     10     2    2
on-prem: you OWN       10   10   10   10     10    10   10   bought up front, weeks to arrive,
                                                             8 sit idle 6 days out of 7
cloud: you RENT         2    2    2    2     10     2    2   started by an API call in minutes,
                                                             billed for what actually ran

The idea

Cloud computing is renting compute, storage and networking from a provider's data centres: on demand, over an API, paid per use. NIST lists five characteristics: on-demand self-service, broad network access, resource pooling, rapid elasticity and measured service. All five are visible in one request:

 you (laptop)                             AWS · region ap-south-1 (Mumbai)
 aws CLI / terraform ─── HTTPS API ────▶ ┌────────────────────────────────────────┐
   "run 1 × t3.micro"   (self-service,   │ pooled hardware shared by many         │
                         network access) │ customers (resource pooling)           │
   seconds later ◀──── instance ID ───── │  ▢ your VM   ▢ someone's VM   ▢ …      │
   "now run 10" ───────────────────────▶ │  scale out, later back in (elasticity) │
                                         └────────────────────────────────────────┘
   month end ◀── bill: instance-hours × hourly price (measured service)
Think of it like this

You don't build a power station for one Diwali night. You plug into the grid and pay per unit on the meter. Cloud is the grid for computers; on-prem is owning the generator.

Exam trap

"The cloud is always cheaper." ✗ You pay for elasticity. A steady 24/7 load can be cheaper on owned or reserved hardware, and forgotten resources bill forever.

"AWS secures my EC2 instance." ✗ On EC2 the OS, its patches, the open ports and the app are yours.

"Use the root user's access keys for Terraform." ✗ MFA on root, never used day to day; use an IAM user or Identity Center (aws sso login). AmazonEC2FullAccess is enough here: VPC APIs are ec2:*.

Remember

CapEx = buy up front · OpEx = pay as you go
AWS secures OF the cloud · you secure what's IN it

Mastery check
Q1. Launch day needs 8 extra servers for 3 hours. What do you pay for in the cloud, and what would you buy on-prem?

Cloud: 8 × 3 = 24 extra instance-hours, then scale back in. On-prem: 8 servers bought outright, idle most of the year. That gap is elasticity, and OpEx vs CapEx.

Q2. Whose job is it: (a) a failed disk in the Mumbai data centre, (b) a security group allowing port 22 from 0.0.0.0/0, (c) a Postgres patch on RDS, (d) an OpenSSL patch on your EC2's Ubuntu?

(a) AWS, (b) you, (c) AWS, (d) you. Hardware and managed-service internals are AWS's; configuration and anything on an EC2 OS are yours.

Q3. aws sts get-caller-identity prints Unable to locate credentials. What's missing, and does Terraform work?

No credentials in any place the CLI looks (env vars, ~/.aws/, SSO, an instance role). Terraform searches the same places and fails too (No valid credential sources found). Run aws configure or aws sso login.

2 IaaS, PaaS, SaaS

The problem

Saturday, 2 a.m.: a critical OpenSSL bug in Ubuntu is announced. Who patches the machine running TaskFlow? That depends on what you rented.

The idea

The models differ in one thing: where the line falls between what the provider runs and what you run. CaaS and FaaS (below) sit between IaaS and PaaS.

                     On-prem    IaaS (EC2)      PaaS (Beanstalk,   SaaS (Gmail,
                                                Heroku)            Slack)
 Application         YOU        YOU             YOU                provider
 Data                YOU        YOU             YOU                provider (you own the content)
 Runtime (Node 20)   YOU        YOU             provider           provider
 Operating system    YOU        YOU ◀── 2 a.m.  provider           provider
 Virtualization      YOU        provider        provider           provider
 Hardware, network   YOU        provider        provider           provider
                     ◀──── more control ──────────────── less ops work ────▶
Think of it like this

Pizza. On-prem: your own kitchen. IaaS: a rented kitchen; building, gas and oven are theirs, but you clean the oven, buy ingredients and cook. PaaS: hand your recipe and ingredients (code, data) to a kitchen whose staff run the ovens. SaaS: eat at the restaurant.

See it: TaskFlow three ways

# IaaS: you get a bare Ubuntu VM and do everything from the OS up
$ ssh ubuntu@13.233.150.21 'sudo apt-get install -y docker.io && sudo docker run -d -p 3000:3000 shauryav/taskflow-api:1.0'
# PaaS: you hand over code; the platform builds, runs, patches and scales it
$ git push heroku main
# SaaS: nothing to deploy. If you sold TaskFlow as a website, your customers would be using SaaS.

What it does not do: PaaS doesn't make your code or data someone else's problem (a SQL injection in server.js is still yours), and IaaS never patches the OS for you.

Exam trap

"Serverless means there are no servers." ✗ You just never manage, patch or pay for idle ones.

"RDS is IaaS because it runs on EC2 underneath." ✗ Classify by what you manage: AWS patches its OS and engine, so it's a managed (PaaS-style) service.

"With SaaS, the provider owns your data." ✗ It runs the storage; the content, and who you share it with, are yours.

Remember

IaaS = you manage from the OS up · PaaS = app + data · SaaS = just use it
Moving right = less control, less ops work.

Mastery check
Q1. The 2 a.m. OpenSSL patch: who applies it if TaskFlow runs on (a) EC2, (b) Elastic Beanstalk, (c) you only use Gmail?

(a) You: it's your Ubuntu. (b) AWS, via Beanstalk's managed platform updates. (c) Google. Same bug, three answers: the line moved.

Q2. Classify: Lambda, ECS on Fargate, EC2, Elastic Beanstalk, Slack, EKS.

Lambda: FaaS. Fargate: CaaS. EC2: IaaS. Beanstalk: PaaS. Slack: SaaS. EKS: CaaS (AWS runs the control plane; your workloads, and often the nodes, are yours).

Q3. Fill in: on IaaS you manage everything from the ________ up; on PaaS, only the ________ and the ________.

Operating system · application · data.

3 Regions & Availability Zones

The problem

Two scares. terraform apply says the EC2 instance exists, but the console shows Instances (0), with N. Virginia in the top-right selector. And a power failure takes out one Mumbai data centre: does TaskFlow go down?

The idea

A region is a separate geographic area with its own independent copy of the services; VPCs and instances live in exactly one. An Availability Zone (AZ) is one or more isolated data centres in a region, with their own power, cooling and network, linked by fast private fibre.

 AWS: dozens of regions worldwide, each independent of the others
 ┌───────────────────────── Region ap-south-1 (Mumbai) ──────────────────────────┐
 │  ┌── AZ ap-south-1a ──┐   ┌── AZ ap-south-1b ──┐   ┌── AZ ap-south-1c ──┐     │
 │  │ data centre(s)     │◀─▶│ data centre(s)     │◀─▶│ data centre(s)     │     │
 │  │ own power, cooling │   │ own power, cooling │   │ own power, cooling │     │
 │  │ and network        │   │ and network        │   │ and network        │     │
 │  └────────────────────┘   └────────────────────┘   └────────────────────┘     │
 │           low-latency private links between AZs (a few milliseconds)          │
 └───────────────────────────────────────────────────────────────────────────────┘
 Region ap-south-2 (Hyderabad), us-east-1 (N. Virginia) …: separate, own resources
 Edge locations (CloudFront, Route 53): many more, smaller sites close to users

Both scares answered: the console was showing another region, and one data centre's outage takes down one AZ, so TaskFlow survives only if it also runs in another.

Think of it like this

A region is a city; AZs are separate buildings in it, on different power lines and flood plains, joined by fast private roads. When one floods, only those with copies in another building carry on.

Build it up

Pick a region byTaskFlow reasoning
Latency to usersUsers in India: Mumbai ≈ 10–30 ms vs us-east-1 ≈ 200+ ms

For high availability, run two of everything in different AZs: TaskFlow instances in ap-south-1a and -1b behind a load balancer, RDS Multi-AZ with a standby in the other. Losing an AZ halves capacity; nothing goes down.

Exam trap

"An AZ is a single data centre." ✗ It's one or more data centres, isolated from the other AZs.

"Resources are global; the region only changes the price." ✗ VPCs, subnets and instances exist in exactly one region (a few services, like IAM, are global).

Remember

Region = city · AZ = separate buildings in it
≥ 2 AZs = you survive one building going dark.

Mastery check
Q1. TaskFlow's users are in India and a client contract says their data must stay in India. Which region, and which two reasons decide it?

ap-south-1 (Mumbai) or ap-south-2 (Hyderabad): compliance rules out regions abroad, and latency to Indian users is lowest there. Price comes after.

Q2. TaskFlow runs on one EC2 instance in ap-south-1a. That AZ has an outage. What happens, and what design change fixes it?

It goes down: one instance in one AZ is a single point of failure. Add a second in ap-south-1b behind a load balancer, and make the database Multi-AZ.

Q3. main.tf never writes Project = "taskflow", yet every resource has that tag. Where does it come from?

From default_tags in the provider block, which merges those tags into every resource the provider creates (visible as tags_all in the plan).

4 VPC (and Azure VNet)

The problem

TaskFlow needs an API server and a database. Launched bare, they get addresses you didn't choose, in a network shared with other experiments, with nothing keeping the database off the internet. You want your own network: your address plan, a fence, doors you control.

The idea

A VPC (Virtual Private Cloud) is a logically isolated network in one region, spanning all its AZs, with a private IPv4 CIDR you choose between /16 and /28 (TaskFlow: 10.0.0.0/16, RFC 1918, Session 4). Subnets, routes, gateways and firewalls (§5–7) live inside it; nothing gets in or out until you add a gateway and a route.

 City = region ap-south-1 (Mumbai)
 ╔════════════════ your VPC: taskflow-dev-vpc · 10.0.0.0/16 ═════════════════╗
 ║  room-numbering plan: 10.0.0.0 – 10.0.255.255 (65,536 addresses, yours)   ║
 ║                                                                           ║
 ║    building = AZ ap-south-1a           building = AZ ap-south-1b          ║
 ║    ┌───────────────────────┐           ┌───────────────────────┐          ║
 ║    │  floors = subnets     │           │  floors = subnets     │  (§5)    ║
 ║    └───────────────────────┘           └───────────────────────┘          ║
 ║                                                                           ║
 ╚═════ fence all round · NO gate yet (the gate = Internet Gateway, §6) ═════╝
   Another account's VPC can also be 10.0.0.0/16: separate fences, no clash.
Think of it like this

The VPC is your company's fenced office space across two of the city's buildings, with a room-numbering plan you choose (the CIDR). No gate yet, so nobody gets in or out; neighbours can reuse your room numbers behind their own fences.

Exam trap

"A VPC lives in one AZ." ✗ A VPC spans every AZ of its region. Subnets are the per-AZ pieces.

"Two VPCs with 10.0.0.0/16 conflict." ✗ Only if you connect them (peering, VPN, Transit Gateway). Isolated VPCs can reuse ranges freely.

Mastery check
Q1. How many addresses are in 10.0.0.0/16? In 10.0.0.0/20?

232−16 = 65,536 and 232−20 = 4,096 (before subtracting AWS's reserved addresses per subnet, §5).

Q2. You apply only aws_vpc.main and try to launch an EC2 instance "into the VPC". What's missing?

A subnet: instances launch into subnets, never a bare VPC. Even then it couldn't reach the internet: no IGW, and the main route table has only local.

Q3. Predict: vpc_cidr = "10.0.0.0/8".

Apply fails: a VPC's CIDR must be between /16 and /28, and AWS rejects a /8 (InvalidVpc.Range). Plan can't catch it, because only the API knows the rule.

5 Subnets

The problem

In one flat 10.0.0.0/16, what must face the internet sits next to what never should, and you want copies in two buildings. The network has to be cut into pieces, each in one place, with its own rules.

The idea

A subnet is a slice of the VPC's CIDR that lives in exactly one AZ. Instances launch into a subnet and take an IP from its range. Whether it's public or private depends only on its route table (§6).

 VPC 10.0.0.0/16
    building = AZ ap-south-1a                   building = AZ ap-south-1b
    ┌──────────────────────────────────┐        ┌──────────────────────────────────┐
    │ floor 11 · private 10.0.11.0/24  │        │ floor 12 · private 10.0.12.0/24  │  app / DB
    │ no door to the street            │        │ no door to the street            │
    ├──────────────────────────────────┤        ├──────────────────────────────────┤
    │ floor 1  · public  10.0.1.0/24   │        │ floor 2  · public  10.0.2.0/24   │  EC2, ALB, NAT
    │ lobby with a street door (§6)    │        │ lobby with a street door (§6)    │
    └──────────────────────────────────┘        └──────────────────────────────────┘
    4 × /24 = 1,024 of the VPC's 65,536 addresses; the rest is free for later floors

Every floor also has five rooms you can't rent. AWS reserves them in every subnet:

 floor 10.0.1.0/24 = rooms 10.0.1.0 … 10.0.1.255 (256)
   .0           network address: the floor's own number
   .1           the VPC router: the lift to every other floor
   .2           reserved for DNS (the resolver itself lives at the VPC base + 2, 10.0.0.2)
   .3           reserved by AWS for future use
   .4 … .254    ← 251 rooms you can actually use
   .255         broadcast address, reserved (VPCs don't do broadcast)
Think of it like this

Subnets are the floors, each in exactly one building. Ground floors have a lobby that can open to the street; upper floors don't. Room numbers come from the company's plan, minus a few the building keeps for its lift and reception.

See it: subnet maths in terraform console

$ terraform console

What it does not do: create anything. It's the subnet arithmetic from Session 4, done by a function instead of by hand.

Build it up: TaskFlow's four subnets

infra/main.tf (part 3 of 6: subnets)
resource "aws_subnet" "public" {
  count                   = length(var.public_subnet_cidrs)       # 2 → public[0], public[1]
  vpc_id                  = aws_vpc.main.id
  cidr_block              = var.public_subnet_cidrs[count.index]
  availability_zone       = var.azs[count.index]
  map_public_ip_on_launch = true                       # instances here get a public IPv4
  tags                    = { Name = "${local.name}-public-${var.azs[count.index]}", Tier = "public" }
}

resource "aws_subnet" "private" {
  count             = length(var.private_subnet_cidrs)
  vpc_id            = aws_vpc.main.id

6 Route tables, IGW & NAT

The problem

An instance sits in "public" subnet 10.0.1.0/24 with public IP 13.233.150.21, and its security group allows port 3000. Yet:

$ curl -m 10 http://13.233.150.21:3000/health
curl: (28) Connection timed out after 10002 milliseconds

Its boot log tells the same story the other way: Could not connect to ap-south-1.ec2.archive.ubuntu.com:80 … connection timed out. No firewall is blocking anything. So what's missing?

The idea

A route table is a list of destination CIDR → target. Each subnet uses exactly one, by default the VPC's main table, which has only the automatic local route. The Internet Gateway (IGW) is the VPC's two-way door to the internet; a NAT gateway lets private subnets reach out without anyone reaching in. When several routes match, the most specific (longest prefix) wins.

                                       Internet
                                         ▲ │
 VPC 10.0.0.0/16 ══════════════ [ IGW: the main gate ] ════════════════════════════
                                         │ │      ① public: in AND out
   public floor 10.0.1.0/24              │ ▼              sign at the lift (public-rt):
   ┌──────────────────────────────────────────┐            10.0.0.0/16 → local

7 Security groups vs NACLs

The problem

Packets can reach the instance. TaskFlow wants SSH only from your laptop, 80 and 3000 from anyone, Postgres only from the API servers, and one abusive range blocked for the whole subnet. AWS has two firewalls, and they differ in one crucial way: whether they remember a connection.

The idea

A security group (SG) is a firewall on an instance's network interface: stateful (an allowed request's reply goes out automatically), allow rules only, sources can be CIDRs or other SGs. A network ACL (NACL) guards the subnet boundary: stateless (replies need their own rule), numbered allow and deny rules, first match wins. Follow one request and its reply:

 laptop 203.0.113.45:51514 ── GET :3000 ──▶ IGW ──▶ route table (public-rt)
 ┌─ subnet 10.0.1.0/24 ── NACL = floor checkpoint (stateless) ─────────────────────┐
 │ IN:  rule 100  allow tcp 3000 from 0.0.0.0/0                                ✔   │
 │   ┌─ EC2 10.0.1.37 ── SG = door lock (stateful) ────────────────────────────┐   │
 │   │ IN:  3000 from 0.0.0.0/0                                       ✔        │   │
 │   │      taskflow-api answers → reply to 203.0.113.45:51514                 │   │
 │   │ OUT: reply allowed automatically: the SG remembers the request ✔        │   │
 │   └─────────────────────────────────────────────────────────────────────────┘   │
 │ OUT: checked AGAIN: rule 110 allow tcp 1024–65535 to 0.0.0.0/0              ✔   │
 └─────────────────────────────────────────────────────────────────────────────────┘
 reply ──▶ laptop:51514       delete NACL rule 110 → request arrives, reply dropped, curl hangs
Think of it like this

The SG is each office's door lock, with a guest list and a doorman who remembers who stepped out. The NACL is the floor checkpoint with a numbered rule book: checks everyone in and out, remembers nobody, and alone can say "banned".

See it: one SG rule

ingress {
  from_port   = 3000                 # a port RANGE: 3000 to 3000
  to_port     = 3000
  protocol    = "tcp"                # "tcp", "udp", "icmp" or "-1" (all)
  cidr_blocks = ["0.0.0.0/0"]        # the source: anywhere
}

That opens TCP 3000 to the world; the reply needs no rule. What it does not do: deny. An SG can't block one address while allowing 0.0.0.0/0; whatever isn't allowed is denied, and that's all it can say. A new SG allows all outbound, no inbound.

"Add a deny rule to the security group for the bad IP range." ✗ SGs have no deny rules. Blocking a range is a NACL job.

Mastery check
Q1. An SG allows inbound 3000 and has no outbound rule for high ports. Does the HTTP reply get out? And through a NACL with the same rules?

Q2. Spot the bug: a NACL has rule 100 "allow all inbound" and rule 200 "deny 198.51.100.0/24".

Q3. The DB SG trusts aws_security_group.app.id instead of 10.0.1.0/24. What do you gain when you add a third API server in another subnet?

Nothing to edit: any instance wearing the app SG "badge" is allowed, whatever its IP or subnet. A CIDR rule would need changing, and would trust anything else in that subnet.

Q4. You delete the egress block "because SGs allow all outbound by default". After apply, the boot script hangs at apt-get update. Why?

Terraform's aws_security_group removes AWS's default allow-all egress and creates only the rules you write, so nothing can leave the instance.

9 First boot: user_data & cloud-init

The problem

The instance boots a blank Ubuntu: no Docker, no TaskFlow. Installing it all over SSH is ClickOps again (Session 20, §1): unrecorded, and the next server won't match. The machine must set itself up on first boot.

The idea

An instance's user_data is a script that cloud-init runs once, as root, on first boot. Terraform builds that script from a template with templatefile(), filling in the image name and the password before AWS ever sees it.

 terraform apply ─▶ aws_instance.app: running (t3.micro, Ubuntu 24.04, subnet public[0], SG app)
                    │  apply finishes HERE; the boot script is only starting
                    ▼ first boot: cloud-init runs user_data as root, once
                 apt-get install docker.io          needs the IGW route (§6) → depends_on (§8)
                 write /opt/taskflow/app.env        password rendered in by templatefile()
                 docker run postgres:16             container "db"
                 docker run taskflow-api:1.0        container "api" on :3000 and :80
                    ▼ about 2 minutes later
                 curl http://PUBLIC_IP:3000/health → {"status":"ok"}
Think of it like this

user_data is the first-day instructions envelope on a new hire's desk: read once, on day one; rewrite it and only a new hire sees it. templatefile() is HR filling in the blanks before sealing it.

See it: render a template

A two-line template, hello.sh.tftpl, rendered in terraform console:

$ cat hello.sh.tftpl
#!/bin/bash
echo "pulling ${app_image} on $(hostname)"
$ terraform console
> templatefile("hello.sh.tftpl", { app_image = "shauryav/taskflow-api:1.0" })
<<EOT
#!/bin/bash
echo "pulling shauryav/taskflow-api:1.0 on $(hostname)"

EOT

${app_image} is Terraform's, so it was filled in; $(hostname) is bash's, so it was left for the instance. Only ${…} and %{…} are special; a literal bash ${VAR} is written $${VAR}. What it does not do: run anything. It returns a string; cloud-init runs it later, on the instance.

Mastery check
Q1. You add echo "home is ${HOME}" to the template. What happens at plan time, and what's the fix?

Terraform treats ${HOME} as a template variable that wasn't passed in: Invalid value for "vars" parameter: vars map does not contain key "HOME". Write $${HOME}; the rendered script then contains ${HOME} for bash.

Q2. You fix a typo in user_data.sh.tftpl and run plan. Which symbol appears on aws_instance.app, and what does it cost?

-/+, because of user_data_replace_on_change: a new instance, a new public IP, and the old instance's Postgres volume is gone.

Q3. Spot the bug: a comment in the template reads # ${db_password} is filled in by Terraform.

Comments aren't special to templatefile(), so the password is rendered into the comment too, one more copy in the script AWS stores. Reword the comment, or write $${db_password}.

Mastery check
Q1. terraform apply succeeded, but five minutes later curl IP:3000/health still times out. List your checks in order.

(1) Over SSH: cloud-init status --wait, docker ps, docker logs api. (2) The SG allows 3000. (3) The subnet uses the public route table (0.0.0.0/0 → igw). (4) There's a public IP. (5) The app listens on 0.0.0.0, not 127.0.0.1. A timeout points to (2)–(4); refused points to (1) or (5).

Q2. You move to a café and SSH times out, but curl IP:3000 still works. Why, and what's the fix?

Port 22 only allows your old /32; port 3000 allows everyone. Set the new IP in my_ip_cidr and terraform apply: an in-place ~ change to the SG, no new server.

The big idea

EC2 is IaaS: a rented VM in one AZ of one region, yours from the OS up, inside a VPC you design: subnets per AZ, route tables that make them public (to the IGW) or private (local, or NAT out), stateful SGs allowing only 22 (from you), 80 and 3000, optional stateless NACLs. Terraform builds it as 15 resources, boots TaskFlow from a user_data template, and removes it all with one destroy.

Final mastery check: combine everything
Q1. Trace one GET :3000/health from your laptop to taskflow-api and back. Name every hop and every check.

Laptop → IGW (public IP → 10.0.1.37) → route table (local) → NACL in (default: allow) → SG in (3000 from anywhere) → Docker -p 3000:3000 → API. Back: SG passes the reply (stateful) → NACL out checks again (ephemeral ports) → route 0.0.0.0/0 → igw → IGW (back to the public IP) → laptop.

Q2. You change only subnet_id to aws_subnet.private[0].id and apply. What breaks, and in what order?

The instance is replaced, with no public IP. On first boot apt-get hangs (private route table: only local, NAT off), so Docker never starts. Even with NAT your laptop can't reach it: no public IP, no route in. The fix is the 3-tier picture: ALB in public subnets, NAT out, app in private.

Q3. A professor says: "For high availability, run two TaskFlow instances in subnet 10.0.1.0/24." Correct it.

A subnet lives in one AZ, so both would be in ap-south-1a and one outage takes both down. Put the second in 10.0.2.0/24 (ap-south-1b) behind a load balancer.

Q4. Name three things about TaskFlow on EC2 that AWS will never do for you, and where this page handles each.

Patch Ubuntu and Docker (IaaS: yours from the OS up; a new AMI replaces the instance, §8). Restrict network access (SG rules, §7). Protect the DB password (it's in user_data and state; use SSM or Secrets Manager, §9). And back up Postgres, sitting in a Docker volume on one instance.

Q5. You need the same stack in Hyderabad. Which inputs change, and which hidden value would break if it were hard-coded?

aws_region = "ap-south-2" and azs = ["ap-south-2a", "ap-south-2b"], with a separate state. A hard-coded AMI ID would break (AMI IDs are per region); §3's data "aws_ami" finds Hyderabad's itself. Hyderabad is opt-in, so enable it first.
