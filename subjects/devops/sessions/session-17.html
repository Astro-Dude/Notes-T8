1 What is Helm?

The problem

TaskFlow's k8s/ folder has 7 YAML files. Production needs the same app with a few different numbers, so you copy the folder:

$ cp -r k8s k8s-prod && vim k8s-prod/*.yaml       # change replicas, image tag, host, resources…
$ diff -r k8s k8s-prod | grep '^[<>]' | head -4
<   replicas: 2
>   replicas: 3
<           image: shauryav/taskflow-api:1.0.0
>           image: shauryav/taskflow-api:1.2.0

Now every fix must be made twice (three times with staging), and the copies drift apart. Nothing says which set of files is running in prod. Rolling back means digging old files out of Git and re-applying them by hand, and there's no clean "uninstall the whole app".

The idea

Helm writes the YAML once as templates, keeps the differences in values, renders the two together on your machine, and applies the result. It records every install and upgrade as a numbered revision, so you can list, upgrade, roll back or uninstall the whole app as one unit.

values.yaml + -f values-prod.yaml + --set image.tag=1.2.0
                │
templates/*.yaml ──► helm (Go templating, on YOUR machine) ──► plain K8s YAML ──► kube-apiserver
                                                                        │
                                         release record stored as a Secret in the release namespace
                                         (sh.helm.release.v1.taskflow.v3) → history & rollback
ConceptMeaningTaskFlow example
ChartPackage: templates + default values + metadatacharts/taskflow/
ValuesSettings injected into templatesimage.tag=1.2.0, replicaCount=3
ReleaseOne installed instance of a chart in a namespacerelease taskflow in ns taskflow
RevisionVersion of a release; +1 on every install/upgrade/rollbackrevision 1, 2, 3…
RepositoryWhere charts are published (HTTP index or OCI registry)bitnami, oci://ghcr.io/shauryav/charts

Helm 3+ is client-only: it uses your kubeconfig and your RBAC permissions (Session 16). Helm 2 needed an in-cluster server, Tiller, usually running with cluster-admin rights. That was a security hole, and Helm 3 removed it.

Think of it like this

Helm is npm for Kubernetes. A chart is a package, a repository is the registry, and helm install is npm install. One twist: you can install the same chart many times, each copy a named release. It's Session 6's class and object again: chart = class, release = object, and each revision is a saved version of that object.

Helm 3 vs Helm 4

Helm 4 went GA in Nov 2025 (brew install helm now gives v4.x; Helm 3 still gets patches). Charts (apiVersion: v2) and every command here work in both. In v4, --atomic is renamed --rollback-on-failure (the old name still works, with a deprecation warning), --force becomes --force-replace, and installs use server-side apply by default.

Common mistakes

Forgetting -n taskflow on status/uninstall gives Error: release: not found. Old versions in helm search repo mean a stale cached index: run helm repo update. And Bitnami's free images are now published only as latest (catalog change, Sept 2025): fine for learning, but pin a digest or use another image source in production.

Exam trap

"Helm needs a server component (Tiller) in the cluster." ✗ That was Helm 2. Helm 3+ is a client that talks to the API server with your own credentials.

"A chart and a release are the same thing." ✗ The chart is the package; a release is one named install of it. One chart can have many releases.

Remember

Chart = package (class) · release = a named install (object) · revision = its version · values = its settings.
Helm renders on your machine, applies with your RBAC, and keeps history as Secrets.

Mastery check
Q1. Predict: you run helm install my-redis bitnami/redis -n taskflow a second time. And with the name cache2?

The first fails: cannot re-use a name that is still in use, because release names are unique per namespace. cache2 succeeds: a second, independent release (two objects from one class).

Q2. You just installed a release, but helm list shows nothing. What's the likely cause?

It lists the current namespace (usually default) and the release is in taskflow. Use helm list -n taskflow or -A.

Q3. True or false: "With Helm 3, a developer without RBAC rights in taskflow can still install there, because Helm does it for them."

False. Helm acts with the developer's own kubeconfig. If RBAC says no, the install fails with the same 403 that kubectl would get.

2 Chart structure & Chart.yaml

The problem

Look again at section 1's helm list: CHART redis-28.3.1 and APP VERSION 8.10.2. Two version numbers for one install. Which one is Redis? And to package TaskFlow yourself, which files does Helm expect, and where?

The idea

A chart is a folder with a fixed layout. Chart.yaml is its ID card, and it carries two versions: version is the chart's own version (its templates and defaults), and appVersion is the version of the software it installs. So Redis is 8.10.2, packaged by chart 28.3.1.

charts/taskflow/            ← folder name = Chart.yaml's name
├── Chart.yaml              WHO am I: name, version 0.1.0 (chart), appVersion "1.0.0" (TaskFlow)
├── values.yaml             DEFAULTS for every {{ .Values.x }}
├── values-dev.yaml         overrides for minikube     ┐ ours (not generated),
├── values-prod.yaml        overrides for production   ┘ passed with -f
├── .helmignore             files left out of "helm package"
├── charts/                 sub-charts (dependencies); empty for us
└── templates/              YAML with blanks → rendered → sent to the cluster
    ├── _helpers.tpl   deployment.yaml   service.yaml   NOTES.txt
    └── ingress.yaml (only if ingress.enabled)   hpa.yaml (only if autoscaling.enabled)
Think of it like this

A Lego box. The box version (chart version) covers the instructions and the piece list. The model on the front (appVersion) is the car you build. Reprint the instructions with a fix and you have a new box version of the same car. A new car model needs a new box too.

Exam trap

"version: 0.1 is a fine chart version." ✗ YAML reads it as a number: [ERROR] Chart.yaml: version should be of type string but it's of type float64. version: abc fails as not a valid SemVer. Use 0.1.0.

"Bumping appVersion is enough after editing a template." ✗ Then two different charts share version 0.1.0 in your registry. Template changes bump version.

Remember

Chart.yaml: apiVersion: v2 · version = the chart (SemVer) · appVersion = the app inside.
Files starting with _ in templates/ aren't rendered.

Mastery check
Q1. You raise the default memory limit in values.yaml but ship the same TaskFlow image. Which field(s) in Chart.yaml change?

Only version (e.g. 0.1.0 → 0.1.1). The app inside is unchanged, so appVersion stays.

Q2. helm list shows CHART taskflow-0.2.0 and APP VERSION 1.0.0, but the pods run image :1.2.0. Is something broken?

No. APP VERSION comes from Chart.yaml; the actual tag came from values (--set image.tag=1.2.0 or values-prod). helm get values shows the real tag.

Q3. Why can't you helm install a chart with type: library?

A library chart only provides named templates (helpers) for other charts. It renders no manifests of its own, so there is nothing to install.

3 values.yaml

The problem

Strip away the copy-paste of section 1 and this is the entire difference between TaskFlow's environments:

dev (minikube)prod
Replicas1 (fixed)HPA 3–10 at 70% CPU
Image1.0.0 (appVersion)1.2.0
Loggingdevelopment / debugproduction / warn
Requests50m CPU / 64Mi250m CPU / 256Mi
Hosttaskflow.localtaskflow.example.com

Where do these numbers live, and who wins when the defaults say 2 replicas, the dev file says 1 and the command line says 3?

The idea

values.yaml holds a default for every setting. A per-environment file (-f values-dev.yaml) overrides only what differs, and --set overrides single values on the command line. Helm merges them in a fixed order, and the later source wins:

chart's values.yaml  <  parent chart's values  <  -f file1.yaml  <  -f file2.yaml  <  --set / --set-string
   (lowest)                                       (later -f wins)                    (highest)
maps merge deeply (unset keys survive) · lists are replaced whole · key: null removes a default
Think of it like this

A function with default parameters, called with spread objects: render({ ...valuesYaml, ...valuesDev, ...cliSet }). Later spreads overwrite earlier keys, except that Helm merges nested maps instead of replacing them.

See it: who wins

$ helm template taskflow charts/taskflow -f charts/taskflow/values-dev.yaml --set replicaCount=3 | grep replicas
  replicas: 3      # values.yaml says 2, values-dev.yaml says 1, --set says 3 → 3

helm template RELEASE CHART renders the chart locally and prints the YAML. -f adds a values file (repeatable); --set key=value sets one value, with dots for nesting (image.tag=1.2.0), commas for several (a=1,b=2) and brackets for lists (hosts[0]=x). What it does not do: touch the cluster. Nothing is installed.

Common mistake: unquoted versions

In a values file, YAML reads tag: 1.20 as the number 1.2, so the chart deploys shauryav/taskflow-api:1.2 (verified with helm template). Always write tag: "1.20". On the command line, --set image.tag=1.20 keeps the text (also verified), but --set does turn true, false, null and plain integers into typed values, so use --set-string when a value must stay a string.

Exam trap

"-f values-prod.yaml replaces values.yaml." ✗ It's merged on top. Keys it doesn't mention keep their defaults, which is why the prod file is 17 lines, not 50.

Remember

chart defaults < -f files (last wins) < --set.
Maps merge, lists replace, quote every version.

Mastery check
Q1. values.yaml sets replicaCount: 2, a.yaml sets 4 and b.yaml sets 1. Predict replicaCount for -f a.yaml --set replicaCount=6, -f a.yaml -f b.yaml and -f b.yaml -f a.yaml.

6 (--set beats files), then 1, then 4: the later -f wins.

Q2. Your values file has tag: 2.10 and the pod pulls :2.1. Why?

YAML parsed the unquoted 2.10 as a float (2.1). Quote it: tag: "2.10".

Q3. The defaults have hosts: [a.local, b.local] and a prod file sets hosts: [taskflow.example.com]. How many hosts render?

One. Lists are replaced whole, not merged, so only taskflow.example.com remains.

Q4. By mistake you run -f values-prod.yaml -f values-dev.yaml. Predict LOG_LEVEL, the image tag, and whether replicas: renders.

LOG_LEVEL debug: dev comes later and sets it. Image 1.2.0: dev doesn't mention the tag, so prod's survives the merge. No replicas: line: prod's autoscaling.enabled: true survives too, so you get prod's HPA and dev's replicaCount: 1 is ignored (verified with helm template).

4 Templates & helpers

The problem

values.yaml says tag: "" and Chart.yaml says appVersion: "1.0.0". The Deployment must end up with image: "shauryav/taskflow-api:1.0.0" in dev and :1.2.0 in prod. Something has to read values and write YAML. And every object needs the same five labels and the same name: copy-paste again?

The idea

A template is YAML with {{ }} actions in it, written in Go templates plus the Sprig function library. Everything inside {{ }} is evaluated, and the rest is copied as is. Values flow through pipes like a shell: {{ .Values.env.LOG_LEVEL | upper | quote }} → "INFO".

 template   image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
                           │                               │                     │
 values     repository: shauryav/taskflow-api            tag: "" ──(empty)──▶ default ──▶ appVersion "1.0.0"
 rendered   image: "shauryav/taskflow-api:1.0.0"
Think of it like this

A JavaScript template literal: `image: ${values.image.repository}:${values.image.tag || chart.appVersion}`. | default is the ||, and a named template in _helpers.tpl is a helper function you call with include.

See it: one line, two renders

$ helm template taskflow charts/taskflow --show-only templates/deployment.yaml | grep image:
          image: "shauryav/taskflow-api:1.0.0"
$ helm template taskflow charts/taskflow --show-only templates/deployment.yaml --set image.tag=1.2.0 | grep image:
          image: "shauryav/taskflow-api:1.2.0"
TokenMeaning
--show-only templates/deployment.yamlPrint only that file's output
.Values.image.tagThe merged value (section 3). The leading . is the current scope.
| default .Chart.AppVersionUse the piped value, or this fallback if it's empty ("", 0, false, nil)

What it does not do: check the result against Kubernetes. helm template never contacts the API server, so a misspelled field renders happily. Section 9 adds a server-side dry run.

"Write # notes in a template; they're comments." ✗ Outside {{ }} everything is copied to the output, comments included. Template comments are {{/* … */}}.

Q1. Predict the output of {{ .Values.env.LOG_LEVEL | upper | quote }} with the default values, then with -f values-dev.yaml.

"INFO", then "DEBUG". The value passes left to right through upper, then quote.

5 The Deployment template

The problem

Plain substitution isn't enough for TaskFlow's Deployment. Some lines are optional (replicas must vanish when an HPA owns it), some lists have unknown length (env vars), whole blocks come straight from values (resources, security contexts), and one input is mandatory (the DB Secret's name).

The idea

Go templates have control structures for each case, and two Sprig functions turn a values map back into correctly indented YAML:

 shape in values.yaml                       template construct
 on/off flag    autoscaling.enabled         {{- if not .Values.autoscaling.enabled }} … {{- end }}
 a block        resources: {…}              {{- with .Values.resources }} … {{- toYaml . | nindent 12 }} … {{- end }}
 a map to loop  env: {NODE_ENV: …}          {{- range $key, $value := .Values.env }} … {{- end }}
 must be set    database.existingSecret     {{ required "msg" .Values.database.existingSecret }}
Think of it like this

It's ordinary code: if is an if, range is a for…of, toYaml is JSON.stringify for YAML, and required is throw new Error("…") when an argument is missing.

See it: a block from values

          {{- with .Values.resources }}
          resources:
            {{- toYaml . | nindent 12 }}
          {{- end }}
# renders, with the default values, to:
          resources:
            limits:
              cpu: 500m
              memory: 256Mi
            requests:
              cpu: 100m
              memory: 128Mi

7 Install & upgrade

The problem

You could pipe helm template into kubectl apply -f - and the app would run. But Helm would record nothing: no release, no revision, no history to roll back to, and no way to tell later which values are live.

The idea

helm install renders, applies, and saves the result as revision 1 of a named release. helm upgrade renders again with the new values, compares with the last revision, patches only what changed, and saves revision 2. helm upgrade --install does whichever applies, which is what CI uses.

 helm install taskflow ./charts/taskflow -n taskflow -f values-dev.yaml
   render ──▶ apply objects ──▶ save revision 1  (Secret sh.helm.release.v1.taskflow.v1)
 helm upgrade taskflow ./charts/taskflow -n taskflow -f values-dev.yaml --set image.tag=1.1.0
   render ──▶ compare with revision 1 ──▶ patch the Deployment ──▶ save revision 2
               (the Deployment then rolls out as usual: Session 10)
Think of it like this

Git for the whole app (Session 5). install is the first commit, every upgrade is a new commit, and the release Secrets are the .git folder.

Q1. Why use helm upgrade --install --atomic --wait in CI instead of helm install?

Q2. helm get values taskflow shows only four keys, but the pods clearly have resource limits. Where are the limits coming from?

From the chart's values.yaml defaults. get values shows only user-supplied values; --all shows the merged set.

Q3. Predict: you upgrade with --set image.tag=1.3.0 only. Which settings change besides the tag?

Everything dev set reverts to the defaults: replicas 1 → 2, LOG_LEVEL debug → info, smaller requests → 100m/128Mi, and the Ingress disappears (ingress.enabled defaults to false).

8 Rollback & release history

The problem

Revision 3 ships a tag that doesn't exist. The new pod can't pull it, but the rolling update keeps an old pod serving, and Helm reported success anyway:

$ helm upgrade taskflow ./charts/taskflow -n taskflow -f charts/taskflow/values-dev.yaml --set image.tag=1.3.0-typo
Release "taskflow" has been upgraded. Happy Helming!      # no --wait → Helm doesn't check pods!
$ kubectl get pods -n taskflow -l app=taskflow-api
NAME                            READY   STATUS             RESTARTS   AGE
taskflow-api-7c5d8b9f4-q8w2x    1/1     Running            0          9m
taskflow-api-86f7d6c5b9-lm4zt   0/1     ImagePullBackOff   0          50s

The idea

Every revision keeps its full manifest and values, so helm rollback RELEASE REV re-applies an old revision. History is append-only: the rollback is recorded as a new revision that copies the old one. --atomic does the same automatically when an upgrade fails.

 rev 1 install ── rev 2 upgrade 1.1.0 ── rev 3 upgrade 1.3.0-typo ── rev 4 "Rollback to 2" (= copy of rev 2)
 superseded       superseded              superseded                  deployed
Think of it like this

git revert from Session 5. You don't erase the bad commit; you add a new commit that undoes it, so history always moves forward.

See it

It's not either/or: Argo CD (Session 22) deploys Helm charts and Kustomize overlays alike.

Common mistakes
  • Pods stuck in CreateContainerConfigError → the taskflow-db-secret Secret is missing in that namespace (Helm doesn't create it).
  • Running kubectl edit on Helm-managed objects → the next helm upgrade overwrites your edit. Change values, not live objects.
Exam trap

"helm uninstall removes everything the app created." ✗ It removes the release's objects and history. PVCs stamped out by StatefulSets, Secrets made outside the chart (taskflow-db-secret) and the namespace itself stay.

Remember

lint → template (+ server dry run) → upgrade --install --atomic --wait with per-env -f → verify → rollback if needed.
Secrets and the database live outside the chart; package + push to OCI to share it.

Mastery check
Q1. Why run helm template … | kubectl apply --dry-run=server -f - when helm lint already passed?

Lint only checks the chart and YAML syntax. The server dry run sends the rendered objects to the real API server, which validates field names, types and admission rules (Pod Security, quotas) without saving anything.

Q2. Prod pods are stuck in CreateContainerConfigError right after step 7. Dev works. What's missing?

The taskflow-db-secret Secret in taskflow-prod. Pods can only use Secrets from their own namespace, and the chart deliberately doesn't create it.

Q3. A teammate hot-fixes prod with kubectl set image deploy/taskflow-api api=…:1.2.1. What happens at the next helm upgrade with values-prod.yaml?

Helm renders 1.2.0 from values-prod and puts it back, undoing the hot-fix. Put the fix in values (or --set image.tag=1.2.1) so the chart, not the live object, is the source of truth.

★ Putting it all together

The big idea

TaskFlow's Deployment, Service, Ingress and HPA are now written once, as templates in charts/taskflow. Chart.yaml versions the package, values.yaml holds the defaults, and values-dev.yaml/values-prod.yaml hold only the differences. Helm merges them, renders the templates on your machine, and applies the result as a numbered revision of a release, so helm upgrade --install --atomic --wait deploys any environment in one command and a bad release is one helm rollback away. CI will run this same command with the new image tag.

Final mastery check — combine everything
Q1. You install with -f values-prod.yaml --set image.tag=1.2.5. Predict the rendered image, the replica line, and which object kinds exist.

shauryav/taskflow-api:1.2.5 (--set beats the file's 1.2.0). No replicas: line, because prod enables autoscaling. Kinds: Service, Deployment, HorizontalPodAutoscaler, Ingress.

Q2. helm list says CHART taskflow-0.1.0, APP VERSION 1.0.0, yet prod runs 1.2.0. After you fix a typo in ingress.yaml, what do you bump, and how would you confirm the live tag?

Bump the chart version (0.1.0 → 0.1.1), since a template changed. APP VERSION is just Chart.yaml's appVersion; confirm the real tag with helm get values taskflow -n taskflow-prod or helm get manifest … | grep image:.

Q3. A CI upgrade with --atomic --timeout 2m fails on a bad tag. What does helm history show afterwards, and which Kubernetes objects hold that history?

A failed revision ("context deadline exceeded") followed by a deployed revision "Rollback to N", the last good one. Each revision is a Secret sh.helm.release.v1.taskflow.vN in the release's namespace.

Q4. Spot the bugs in this values-prod.yaml line set: image: {tag: 1.10}, autoscaling: {enabled: true}, replicaCount: 6. The team expects 6 pods of 1.10.

(1) The unquoted 1.10 becomes 1.1, so the wrong image is pulled; write "1.10". (2) With autoscaling on, the template drops replicas, so replicaCount: 6 is ignored; the HPA decides between minReplicas and maxReplicas.

Q5. In the end-to-end run, which steps would fail if you skipped creating taskflow-db-secret, and at what moment would you notice with and without --wait?

Rendering and install succeed, because the template only names the Secret (required checks the value, not the cluster). The pods then hit CreateContainerConfigError. Without --wait, Helm says "deployed" and you notice at the curl. With --wait --atomic, the command times out and rolls back, so CI fails loudly.
