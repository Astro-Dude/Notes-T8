1 Monolith vs Microservices

Explain like I'm 5

A monolith is one big restaurant kitchen where every dish is cooked together. Microservices are a food court: each stall has its own kitchen, staff and menu, and can open, close or expand without the others.

  • Monolith: one codebase, built and deployed as one unit (one .jar, one Node process), usually with one shared database. Modules call each other as in-process function calls.
  • Microservices: the app is split into small services, each owning one business capability, running in its own process, with its own database, deployed independently, talking over the network (HTTP/gRPC/messages).
  • Both are valid. Microservices solve organisational and scaling problems and create operational ones — which is exactly why DevOps tooling exists.

Worked split: ShopKart e-commerce

  MONOLITH  (one deployable)                   MICROSERVICES  (4 deployables)

Trade-offs (exam favourite)

AspectMonolithMicroservices
DeploymentWhole app every time; a 1-line fix redeploys everythingEach service deploys on its own schedule
ScalingClone the entire appScale only the hot service
Tech stackOne language/frameworkPer service (polyglot) — but standardise tooling
Failure isolationA memory leak in payments can crash the whole appPayments down → browsing still works (if designed for it)
Data consistencyOne DB, ACID transactions across modulesSeparate DBs → eventual consistency, sagas
Module-to-module callFunction call (nanoseconds, never "times out")Network call (milliseconds, can fail or time out)
DebuggingOne log file, one stack traceNeeds centralised logs + distributed tracing
TestingEasy to run end-to-end locallyContract tests; many services to start
Ops overheadLow: one pipeline, one serverHigh: N pipelines, containers, orchestration, service discovery, monitoring
Best fitSmall team, early product, unclear domainMany teams, clear domain boundaries, uneven load
Example: Big Billion Day traffic

Search traffic jumps 50× but checkout only 3×. The monolith image is 2 GB RAM per copy; to handle search you run 10 copies = 20 GB, scaling checkout, users and payments for no reason. With microservices you run 10 copies of the 200 MB catalog-service (2 GB) + 3 copies of order-service + 1 each of the rest ≈ 3 GB.

  • Rule of thumb: start with a modular monolith (clean module boundaries, one deployable). Split a module out when it needs different scaling, a different release pace, or a separate team.
Common mistake: the distributed monolith

Services that share one database, or that must all be deployed together because of tight API coupling, give you the network failures of microservices and the coupling of a monolith. Each service must own its data and be releasable alone.

Recap Monolith = one deployable + one DB; microservices = many small, independently deployable services, each with its own DB. Microservices buy independent scaling/deploys and fault isolation at the cost of network calls, eventual consistency and heavy ops work.

The API gateway is the mall's reception desk, service discovery is the phone directory of shops, and the load balancer is the guard who sends you to the shortest queue.

  • Client-side discovery: the caller asks a registry (Consul/Eureka) for instances and picks one. Server-side discovery: the caller hits a stable name/VIP and the platform routes it (K8s Service, AWS ALB). Kubernetes uses server-side + DNS.
  • DB per service consequence: no SQL JOIN across services. To show "orders with product names", order-service calls catalog-service, or keeps a local copy updated by events.

Gateway + load balancer in one file (illustration)

gateway/conf.d/shopkart.conf
upstream catalog {                          # a pool of 3 catalog copies (round-robin by default)
    server catalog-1:8080;
    server catalog-2:8080;
    server catalog-3:8080;
}

server {
    listen 80;
    server_name api.shopkart.in;            # only requests for this Host header

    location /api/users/    { proxy_pass http://user-service:8080/users/; }
    location /api/products/ { proxy_pass http://catalog/products/; }     # → upstream pool
    location /api/orders/   { proxy_pass http://order-service:8080/orders/; }
}
LineMeaning
upstream catalog { … }Named group of backends. NGINX load-balances across them and skips ones that fail.
location /api/products/Matches any path starting with /api/products/.
proxy_pass http://catalog/products/;Because a URI (/products/) is given, the matched prefix is replaced: GET /api/products/42 → GET /products/42 on e.g. catalog-2:8080.

Synchronous vs asynchronous communication

Sync — REST (JSON over HTTP). order-service checks stock before accepting an order:

$ curl -s http://catalog-service:8080/products/42
{"id":42,"name":"USB-C Cable","price":299,"stock":120}

Sync — gRPC (Protobuf over HTTP/2). The contract is a .proto file; client and server code is generated from it:

proto/payment.proto
syntax = "proto3";                       // Protobuf version 3
package payment.v1;                      // namespace + API version

service PaymentService {                 // the remote "class"
  rpc Charge (ChargeRequest) returns (ChargeReply);   // one remote method
}

message ChargeRequest {
  string order_id     = 1;               // = 1, = 2 … are field numbers used on the wire,
  int64  amount_paise = 2;               // never reuse or renumber them
  string currency     = 3;
}

message ChargeReply {
  string payment_id = 1;
  string status     = 2;                 // e.g. "CAPTURED" or "DECLINED"
}

Async — event on a broker. After saving the order, order-service publishes and returns immediately. Email, inventory and analytics services consume it in their own time:

Kafka topic: order.placed (one message)
{"event":"OrderPlaced","orderId":"ord_9001","userId":"u_17","items":[{"productId":42,"qty":2}],"total":598,"at":"2026-10-09T10:15:02Z"}
Synchronous (REST / gRPC)Asynchronous (queue / Kafka)
Caller waits?Yes, blocks until the replyNo, publishes and moves on
Both must be up?Yes (temporal coupling)No — broker buffers messages
Failure modeTimeouts cascade up the call chainMessages wait; retries; dead-letter queue
Use forNeed an answer now: price, stock check, charge cardSide effects: send email, update search index, analytics
ExamplesREST: JSON, human-readable, easy curl. gRPC: binary, typed contract, faster, streamingKafka (event log, replayable), RabbitMQ / SQS (work queues)
Common mistake: long chains of sync calls

If one request passes through 5 services in series, each 99.9% available, the chain is 0.9995 ≈ 99.5% — about 3.6 hours of failure per 30-day month instead of 43 minutes. Keep sync chains short, add timeouts + retries, and move side effects to async events.

Recap Client → DNS → load balancer → API gateway → services, each with its own DB. Service discovery finds instances; use sync calls when you need an answer now and async events for everything else.

3 What is DevOps?

Explain like I'm 5

Instead of builders throwing a finished house over the fence to the people who live in it, both groups work together and share one scoreboard: "does the house work for the family?"

  • DevOps = culture + practices + tools that join development (Dev) and operations (Ops) so software ships faster and more reliably. The term dates to 2009 (Patrick Debois, DevOpsDays).
  • It is not a single tool or just a job title. Key practices: version control for everything, CI/CD, infrastructure as code, containers, monitoring, small frequent releases, shared on-call, blameless postmortems.

The problem it fixes: the wall of confusion

        DEVELOPERS                    ║                 OPERATIONS
   rewarded for: shipping features    ║    rewarded for: uptime, stability
   "works on my machine"              ║    "who changed what, and when?!"
   release.zip + 40-step Word doc  ───╫──▶ manual deploy, Saturday 2 a.m.
                                      ║    outage → ticket back to devs
            ◀─────────────────────────╫──── "it's a code problem"
                         the wall of confusion

ServersHand-configured "snowflakes"Infrastructure as code, containers

CALMS — the five pillars

LetterMeansIn practice (TaskFlow)
C — CultureShared ownership, trust, blameless learningThe dev who wrote /tasks is on the on-call rota for it
A — AutomationAutomate build, test, deploy, infraEvery push runs tests in GitHub Actions; Terraform creates the AWS network

Common mistake

Renaming the ops team "DevOps team" or buying a CI tool without changing how teams work. You get the same silos with new tools. Culture first, then automation.

Recap DevOps breaks the Dev vs Ops wall with shared goals and automation. Remember CALMS: Culture, Automation, Lean, Measurement, Sharing.

5 CI/CD Overview & DORA Metrics

Explain like I'm 5

CI: everyone adds their puzzle piece many times a day and a robot checks it fits. CD: the robot also packs the puzzle and either waits for your "OK" (delivery) or ships it straight away (deployment).

  • Continuous Integration (CI): developers merge small changes into main at least daily; every push triggers an automated build + tests. A red build is fixed first. Prevents "integration hell" from long-lived branches.
  • Continuous Delivery: every change that passes the pipeline is releasable and is deployed to staging automatically; going to production is a manual button.
  • Continuous Deployment: no button — every change that passes all checks goes to production automatically.

First look at a pipeline file

This is what CI looks like for TaskFlow (built properly in Session 18). Committed to the repo, GitHub runs it on every push and PR:

.github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]              # run on every push to main…
  pull_request:                   # …and on every pull request
jobs:
  test:
    runs-on: ubuntu-latest        # fresh GitHub-hosted Linux VM
    steps:
      - uses: actions/checkout@v4       # clone the repo
      - uses: actions/setup-node@v4     # install Node
        with:
          node-version: 20
          cache: npm                     # cache ~/.npm between runs
      - run: npm ci                      # exact install from package-lock.json
      - run: npm test                    # non-zero exit → red ✗ on the PR
KeyMeaning
on:Events that trigger the workflow.
jobs.testA job named test; jobs run in parallel unless linked with needs:.
runs-onThe machine (runner) the job runs on.
uses vs runuses = reuse a published action; run = a shell command.
npm ciClean install that fails if package-lock.json doesn't match package.json — reproducible builds.

DORA metrics — how you measure DevOps

MetricMeasuresElite teams (DORA)Type
Deployment frequencyHow often you deploy to productionOn demand, many per dayThroughput
Lead time for changesCommit → running in productionLess than a dayThroughput
Change failure rate% of deploys that cause a failure (rollback, hotfix, incident)Low (≈ 0–15%)Stability
MTTR / failed deployment recovery timeTime to restore service after a failed changeLess than an hourStability
Example: TaskFlow's week
  • 10 production deploys Mon–Fri → deployment frequency = 2/day.
  • Issue #12 commit at 10:00, live at 14:30 → lead time = 4.5 h.
  • 1 of 10 deploys caused 5xx errors and was rolled back → change failure rate = 10%.
  • Alert at 15:02, rollback finished 15:20 → MTTR = 18 min.
Key takeaway

Speed and stability are not a trade-off: elite teams deploy more often and fail less, because small changes are easier to test and to roll back.

Common mistake

"We have Jenkins, so we do CI." If feature branches live for weeks and are merged once a month, that is not CI — integration is still painful and late.

Recap CI = build + test every change. Delivery = always releasable, human presses deploy. Deployment = automatic to prod. Measure with DORA: frequency + lead time (speed), failure rate + MTTR (stability).

taskflow/server.js
// server.js — TaskFlow API (starter version, Session 1)
const express = require('express');

const app = express();
const PORT = process.env.PORT || 3000;          // config from the environment, default 3000

app.use(express.json());                        // parse JSON request bodies (for POST /tasks later)

app.get('/health', (req, res) => {              // used by load balancers, K8s probes, healthcheck.sh
  res.json({ status: 'ok' });
});

const server = app.listen(PORT, () => {         // listens on all interfaces, not just localhost
  console.log(`TaskFlow API listening on port ${PORT}`);
});

process.on('SIGTERM', () => {                   // systemd / Docker / K8s send SIGTERM to stop us
  console.log('SIGTERM received, shutting down');
  server.close(() => process.exit(0));          // finish in-flight requests, then exit 0
});
LineWhy it matters for DevOps
process.env.PORT || 3000Config via environment variables (12-factor). The same build runs on a laptop, in Docker (-e PORT=8080) and in K8s.
GET /healthA cheap endpoint that says "I'm alive". Every later tool (systemd health script, Docker HEALTHCHECK, K8s probes, load balancers) calls it.
app.listen(PORT)Without a host argument Node binds to all interfaces (:: / 0.0.0.0), so it is reachable from outside a container.
process.on('SIGTERM')Graceful shutdown: stop accepting connections, finish open requests, exit 0. (Signals: Session 2.)

★ Putting it all together

The big idea

Splitting an app into microservices lets teams deploy and scale pieces independently, but multiplies the number of things to build, ship and watch. DevOps answers that with culture (shared ownership, CALMS) and automation along the whole lifecycle loop — CI/CD from commit to production, measured by DORA metrics. TaskFlow is our one app to practise every step: today it answers /health; by Session 23 it is tested, scanned, containerised, deployed by Helm/Argo CD to Kubernetes on AWS, and monitored in Grafana.

Quick self-check

Only product search gets a 50× traffic spike. Why is that cheaper to handle with microservices?

You scale only catalog-service. A monolith must be cloned whole, so you pay RAM/CPU for users, orders and payments copies you don't need.

Continuous Delivery vs Continuous Deployment — what's the one difference?

Delivery keeps every change releasable but needs a human to approve the production deploy; Deployment pushes every passing change to production automatically.

Name the four DORA metrics. Which two measure stability?

Deployment frequency, lead time for changes (throughput); change failure rate and MTTR / failed deployment recovery time (stability).

Checkout calls 4 other services synchronously in series, all 99.9% available. What's the overall availability and what would you change?

0.9995 ≈ 99.5% (≈3.6 h/month of failures). Shorten the chain, add timeouts/retries, and make side effects (emails, analytics) async via a message broker.

What does CALMS stand for?

Culture, Automation, Lean, Measurement, Sharing.

Two "microservices" read and write the same orders table and must be released together. What's wrong?

It's a distributed monolith: shared DB and lock-step releases. Give one service ownership of the data; the other uses its API or events.

Why does TaskFlow read PORT from process.env and handle SIGTERM?

Env-based config lets the same build run anywhere (laptop, Docker, K8s) with different settings. SIGTERM is how systemd, Docker and Kubernetes ask a process to stop; handling it lets in-flight requests finish before exit.
