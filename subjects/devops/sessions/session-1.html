1 Monolith vs microservices

The problem

ShopKart is an online shop built as one Node.js app: users, catalog, orders and payments in one codebase, one process, one database. One bad week:

Mon  one-line fix on the payment page   → rebuild + redeploy ALL of ShopKart; search is down for 2 min
Wed  memory leak in the payments code   → the whole process crashes; nobody can even browse
Fri  Big Billion Day: search ×50, checkout ×3 → you clone the entire 2 GB app 10 times

None of these is a search problem, yet search suffers each time, because everything ships, fails and scales as one unit.

The idea

A monolith is one codebase built and deployed as one unit, usually with one shared database; modules call each other as functions. Microservices split the app by business capability: each service runs in its own process, owns its own database, is deployed independently, and talks to the others over the network.

  MONOLITH  (one deployable)                   MICROSERVICES  (4 deployables)
 ┌─────────────────────────────────────┐        ┌─────────────────────────────┐
 │  web UI + REST controllers          │        │         API gateway         │
 │  ┌───────┬─────────┬────────┬─────┐ │        └───┬───────┬───────┬──────┬──┘
 │  │ users │ catalog │ orders │ pay │ │ split ▶    │       │       │      │
 │  └───────┴─────────┴────────┴─────┘ │          users  catalog orders   pay     ← own process each
 └──────────────────┬──────────────────┘            │       │       │      │
               ┌────▼─────┐                        [DB]    [DB]    [DB]   [DB]    ← DB per service
               │  one DB  │
               └──────────┘   users, products, orders, payments tables
Think of it like this

A monolith is one big restaurant: one kitchen, one pantry (the database), one staff. A fryer fire closes everything, and a busy pizza night means hiring for everything. Microservices are a food court: each stall has its own kitchen (process), pantry (database) and staff (team), and opens, closes or grows on its own. We'll keep this food court for three sections.

See it: one call, two worlds

The smallest real difference: the order code needs a product.

// Monolith: the catalog module lives in the same process
const product = catalog.getProduct(42);                        // function call: nanoseconds, can't time out

// Microservices: order-service asks catalog-service over the network
const res = await fetch('http://catalog-service:8080/products/42');  // HTTP request: milliseconds, can fail
const product = await res.json();
$ curl -s http://catalog-service:8080/products/42
{"id":42,"name":"USB-C Cable","price":299,"stock":120}
TokenMeaning
http://Protocol: a plain HTTP request (REST)
catalog-serviceThe service's name. Something must turn it into the current IP of a running copy (section 2).
:8080The port catalog-service listens on
/products/42The resource: product 42, answered as JSON

What splitting does not do: remove complexity. It moves it into the network: the function call can't time out, be refused or hit a restarting copy, and the HTTP call can do all three.

Build it up: the ShopKart split

ServiceOwnsOwn data storeExample API
user-serviceSign-up, login, profiles, addressesPostgreSQL usersPOST /users, POST /login
catalog-serviceProducts, prices, search, stockPostgreSQL + ElasticsearchGET /products?q=cable
order-serviceCart → order, order statusPostgreSQL ordersPOST /orders
payment-serviceCharge, refund (talks to Razorpay/Stripe)PostgreSQL paymentsgRPC Charge()

Replay the week. Friday: the monolith needs 10 × 2 GB = 20 GB of RAM. Microservices run 10 copies of the 200 MB catalog-service, 3 of order-service and 1 of each of the rest: about 3 GB. Monday's fix ships only payment-service; Wednesday's leak kills only payments.

The exam table

AspectMonolithMicroservices
DeploymentWhole app every time; a 1-line fix redeploys everythingEach service deploys on its own schedule
ScalingClone the entire appScale only the hot service
Tech stackOne language/frameworkPer service (polyglot), but standardise tooling
Failure isolationA leak in payments can crash the whole appPayments down → browsing still works (if designed for it)
Data consistencyOne DB, ACID transactions across modulesSeparate DBs → eventual consistency, sagas
Module-to-module callFunction call (nanoseconds, never times out)Network call (milliseconds, can fail or time out)
DebuggingOne log file, one stack traceNeeds centralised logs + distributed tracing
TestingEasy to run end-to-end locallyContract tests; many services to start
Ops overheadLow: one pipeline, one serverHigh: N pipelines, containers, orchestration, discovery, monitoring
Best fitSmall team, early product, unclear domainMany teams, clear domain boundaries, uneven load

Rule of thumb: start with a modular monolith (clean module boundaries, one deployable). Split a module out when it needs a different scale, a different release pace, or its own team.

Exam trap

"Microservices are always better than a monolith." ✗ They solve team and scaling problems and create operational ones. A small team with a new product usually moves faster with a modular monolith.

"Microservices just means small codebases." ✗ The defining property is independent deployability with its own data. Small services that share a database and release together are a distributed monolith: microservices' network failures plus a monolith's coupling.

"Splitting makes the app faster." ✗ Calls get slower (network, not memory). You gain independent scaling, deploys and failure.

Remember

Monolith = 1 deployable + 1 DB.
Microservices = N deployables, each with its own DB, released independently.
You buy independent deploy/scale/failure and pay in network calls + ops work.

Mastery check
Q1. Predict: payment-service crashes. Can a user still search for products? Answer for the monolith and for microservices.

Monolith: no. Payments runs in the same process, so a crash takes search down too. Microservices: yes. catalog-service is a separate process with its own DB; only checkout fails.

Q2. Spot the problem: order-service and invoice-service both read and write the orders table, and every release must ship both together.

A distributed monolith: shared data, lock-step releases. Give one service ownership of orders; the other uses its API or its events (section 3).

Q3. True or false: "Microservices make the system simpler."

False. Each service is simpler, but the system gains network failures, eventual consistency, N pipelines, discovery and tracing. That load is why DevOps tooling exists.

2 Microservices architecture

The problem

ShopKart is now four services, and new questions appear at once:

mobile app:     which address do I call? user-svc:8080? catalog-svc:8080? order-svc:8080?
order-service:  catalog has 3 copies, and catalog-2 just restarted: 10.0.1.7 → 10.0.1.12. Where is it now?
every service:  who checks the login token? All four, separately?

The idea

Put standard pieces in front of and between the services. Clients see one address: DNS resolves it to the load balancer, the load balancer spreads requests over healthy copies, and the API gateway checks auth and routes each path. Service discovery tracks where copies run, and each service keeps its own database.

                          client (browser / mobile app)
                                    │  https://api.shopkart.in  (DNS: name → load balancer IP)
                          ┌─────────▼─────────┐
                          │   Load balancer   │   spreads traffic over healthy gateway copies
                          └─────────┬─────────┘
                  ┌─────────────────▼─────────────────┐   TLS, auth (JWT), rate limit, routing:
                  │            API gateway            │     /api/users/*    → user-service
                  └───┬──────────────┬─────────────┬──┘     /api/products/* → catalog-service
                      │              │             │        /api/orders/*   → order-service
             ┌────────▼───────┐ ┌────▼─────┐ ┌─────▼───────┐         ┌─────────────┐
             │  user-service  │ │catalog ×3│ │order-service│─ gRPC ─▶│ payment-svc │
             └────────┬───────┘ └────┬─────┘ └─────┬───────┘         └──────┬──────┘
                 [users DB]     [catalog DB]  [orders DB]             [payments DB]
   service discovery (registry / K8s DNS) tells the gateway + services where each copy runs
Think of it like this

At the food court, the API gateway is the entrance info desk: it checks your wristband (auth) and points you to a stall. The load balancer is the queue marshal picking the shortest of three pizza counters. Service discovery is the directory board, updated when a stall moves. DB per service: the dosa stall can't raid the pizza stall's fridge; it must ask at the counter (the API).

See it: follow one request

A phone asks for GET https://api.shopkart.in/api/products/42:

1. DNS          api.shopkart.in → 13.235.40.10            (the load balancer's public IP)
2. Load bal.    picks a healthy gateway copy
3. API gateway  checks the JWT, matches /api/products/ → the "catalog" pool, rewrites to /products/42
4. Discovery    "catalog" = catalog-1, catalog-2, catalog-3 at their current IPs
5. Service      catalog-2 reads ITS OWN database and returns {"id":42,…}

Steps 2–4 fit in one small nginx config. Here nginx plays both gateway and load balancer:

gateway/conf.d/shopkart.conf
upstream catalog {                          # a pool of 3 catalog copies (round-robin by default)
    server catalog-1:8080;
    server catalog-2:8080;
    server catalog-3:8080;
}

server {
    listen 80;
    server_name api.shopkart.in;            # only requests for this Host header

    location /api/users/    { proxy_pass http://user-service:8080/users/; }
    location /api/products/ { proxy_pass http://catalog/products/; }     # → upstream pool
    location /api/orders/   { proxy_pass http://order-service:8080/orders/; }
}
LineMeaning
upstream catalog { … }A named group of backends. nginx load-balances across them and skips any that fail.
listen 80; / server_nameAccept HTTP on port 80, only for requests whose Host header is api.shopkart.in
location /api/products/Path-based routing: matches any path starting with /api/products/ (users and orders work the same way)
proxy_pass http://catalog/products/;Forward to the pool. A URI is given, so the matched prefix is replaced: GET /api/products/42 → GET /products/42 on, say, catalog-2:8080.

What this file does not do: discover anything. Add catalog-4 and someone must edit the file and reload nginx. Real service discovery does that automatically; Kubernetes does it with Services and DNS (Session 11), with Ingress as the gateway (Session 12).

Exam trap

"An API gateway and a load balancer are the same thing." ✗ A load balancer spreads requests across copies of one service. A gateway routes by path or host to different services and adds auth, rate limiting and TLS. nginx can do both, as above, but they're different jobs.

"Database per service means one database server per service." ✗ It means separate ownership. Two schemas can share a Postgres server if only the owner touches its tables.

Remember

DNS finds the front door → LB picks a copy → gateway picks the service → discovery knows where copies live → each service owns its data.

Mastery check
Q1. With the nginx file above, what request does the catalog copy actually receive for GET /api/products/42?q=cable?

GET /products/42?q=cable on one of catalog-1/2/3, port 8080. proxy_pass includes a URI, so the prefix is replaced; the query string passes through unchanged.

Q2. catalog-3 crashes. Which component stops sending it traffic, and how does it know?

The load balancer (nginx's upstream pool). Health checks, or in plain nginx failed connection attempts, mark catalog-3 down, so requests go to catalog-1 and 2.

Q3. The order history page needs product names, but the orders DB only stores product IDs. Why can't you just JOIN, and what are your two options?

Products live in catalog-service's database, which order-service must not touch. Either call catalog's API for the names (sync), or keep a local copy updated by catalog's events (async).

3 How services talk: sync vs async

The problem

After Pay, checkout does five things: check stock, charge the card, save the order, send the email, update analytics. If order-service calls each in turn and waits:

email-svc is down for 10 minutes   → every checkout fails for 10 minutes, over an email
5 services in series, each 99.9% up → 0.999⁵ ≈ 99.5% → about 3.6 h of failures a month instead of 43 min

The email doesn't have to be sent before the user sees "Order placed". Only the stock check and the payment do.

The idea

Synchronous (REST or gRPC): the caller sends a request and waits for the answer. Asynchronous: the caller publishes an event to a message broker and carries on; the broker holds it until consumers are ready.

SYNC   order-svc ──"stock for 42?"──▶ catalog-svc         order-svc waits…
       order-svc ◀──"120 in stock"─── catalog-svc         …then continues

ASYNC  order-svc ──OrderPlaced──▶ [ Kafka topic: order.placed ] ──▶ email-svc      (when it's ready)
       (replies to the user now)                                └─▶ analytics-svc  (when it's ready)
Think of it like this

Sync is waiting at the counter for your dosa: you get your answer, but you're stuck, and if the cook is on a break you get nothing. Async is taking a token and walking away: the slip waits on the ticket rail (the broker) until the kitchen gets to it.

See it: the three styles

Sync, REST (JSON over HTTP): the curl to catalog-service in section 1. Readable and easy to test.

Sync, gRPC (Protobuf over HTTP/2): the contract is a .proto file that client and server code are generated from.

proto/payment.proto
syntax = "proto3";                       // Protobuf version 3
package payment.v1;                      // namespace + API version

service PaymentService {                 // the remote "class"
  rpc Charge (ChargeRequest) returns (ChargeReply);   // one remote method: send a request, wait for the reply
}

message ChargeRequest {
  string order_id     = 1;               // = 1, = 2 … are field numbers used on the wire,
  int64  amount_paise = 2;               // never reuse or renumber them
  string currency     = 3;
}

message ChargeReply {
  string payment_id = 1;
  string status     = 2;                 // e.g. "CAPTURED" or "DECLINED"
}

Async, an event on a broker: after saving the order, order-service publishes one message and returns immediately. Email, inventory and analytics consume it in their own time.

Kafka topic: order.placed (one message)
{"event":"OrderPlaced","orderId":"ord_9001","userId":"u_17","items":[{"productId":42,"qty":2}],"total":598,"at":"2026-10-09T10:15:02Z"}

The event says what happened (OrderPlaced), not what to do, so any number of services can react without order-service knowing which.

What async does not do: give the caller an answer. order-service never learns whether the email went out, so anything you need now ("was the card charged?") stays synchronous.

The exam table

Synchronous (REST / gRPC)Asynchronous (queue / Kafka)
Caller waits?Yes, blocks until the replyNo, publishes and moves on
Both must be up?Yes (temporal coupling)No: the broker buffers messages
Failure modeTimeouts cascade up the call chainMessages wait; retries; dead-letter queue
Use forNeed an answer now: price, stock check, charge cardSide effects: send email, update search index, analytics
ExamplesREST: JSON, readable, easy curl. gRPC: binary, typed contract, faster, streamingKafka (event log, replayable), RabbitMQ / SQS (work queues)

Back to checkout: stock and charge stay sync, and email and analytics consume OrderPlaced. The sync chain shrinks from 5 hops to 2, and an email outage fails no orders. Give every remaining sync call a timeout and a retry.

Exam trap

"Async is better because it's faster." ✗ It's decoupled, not faster: the caller doesn't wait, and doesn't get an answer either.

"gRPC is a message queue." ✗ gRPC is synchronous remote calls over HTTP/2. There's no broker storing messages.

"In .proto, = 1 is the default value." ✗ It's the wire field number; changing it breaks existing clients.

Remember

Need the answer now → sync (REST / gRPC). Side effect that can wait → async (event on a broker).
In a sync chain, availabilities multiply.

Mastery check
Q1. Sync or async: (a) check stock before accepting an order, (b) charge the card, (c) send the confirmation email, (d) update the search index after a price change?

(a) and (b) sync: the order can't proceed without the answer. (c) and (d) async: side effects that can happen seconds later and shouldn't fail the request.

Q2. A request passes through 4 services in series, each 99.9% available. End-to-end availability, failure per 30-day month, and your fix?

0.999⁴ ≈ 99.6%: about 0.4% of 43,200 min ≈ 173 min (≈ 2.9 h). Shorten the chain, add timeouts and retries, and move anything not needed for the reply to events.

Q3. email-svc is down for 10 minutes while 300 orders are placed. With the Kafka design, what happens to those 300 events?

They wait in the order.placed topic. email-svc resumes from its last read position and sends all 300, a few minutes late. No checkout failed.

4 What is DevOps?

The problem: the wall of confusion

Microservices turn one deployment into dozens, and the old way of shipping breaks down. Dev and Ops sat in separate teams with opposite goals:

        DEVELOPERS                    ║                 OPERATIONS
   rewarded for: shipping features    ║    rewarded for: uptime, stability
   "works on my machine"              ║    "who changed what, and when?!"
   release.zip + 40-step Word doc  ───╫──▶ manual deploy, Saturday 2 a.m.
                                      ║    outage → ticket back to devs
            ◀─────────────────────────╫──── "it's a code problem"
                         the wall of confusion

Dev wants change, Ops wants nothing to change, so releases get bigger, rarer and scarier, and every outage becomes a blame game.

The idea

DevOps is culture + practices + tools that join development and operations into one flow, so software ships faster and more reliably. The term dates from 2009 (Patrick Debois, the first DevOpsDays). Core practices: version control for everything, CI/CD, infrastructure as code, containers, monitoring, small frequent releases, shared on-call, blameless postmortems.

Think of it like this

In the old restaurant, chefs (Dev) are paid for new dishes and floor staff (Ops) for zero complaints, so one side pushes dishes out and the other fights to freeze the menu. DevOps makes them one team that owns the dish from recipe to plate, tasting together and fixing the recipe instead of blaming.

See it: the same one-line fix, two ways

Siloed   Mon code done → ticket to Ops → change board Thu → manual deploy Sat 02:00 → bug found Mon → blame
DevOps   10:00 code done → PR + CI tests 10:05 → merged 10:20 → auto-deploy 10:30 → dashboard spikes 10:32 → rollback 10:35

The DevOps version broke too. But the change was small, the dashboard caught it in two minutes, and the rollback took three. No waiting until Monday, no blame.

Build it up

AspectTraditional (siloed)DevOps
Release frequencyQuarterly "big bang"Daily or on demand, small batches
Deploy methodManual runbookAutomated pipeline, same steps every time
ServersHand-configured "snowflakes"Infrastructure as code, containers
OwnershipDev writes, Ops runs"You build it, you run it"
FeedbackUsers report bugs days laterMonitoring alerts within minutes
After an outageFind someone to blameBlameless postmortem → fix the system

The usual way to remember what DevOps is made of is CALMS:

LetterMeansIn practice (TaskFlow)

A — AutomationAutomate build, test, deploy, infraEvery push runs tests in GitHub Actions; Terraform creates the AWS network

Exam trap

"DevOps is a tool" or "We renamed ops to the DevOps team." ✗ New tools or names without new ways of working give you the same silos. Culture first, then automation.

"DevOps means developers do ops, so operations disappears." ✗ Ops work still exists; it's shared and automated instead of thrown over a wall.

"DevOps trades stability for speed." ✗ Teams that ship small changes often also fail less and recover faster (section 6).

Remember

DevOps = culture + practices + tools → faster AND safer releases.
CALMS: Culture · Automation · Lean · Measurement · Sharing. "You build it, you run it."

Mastery check
Q1. In one sentence: why are Dev and Ops in conflict in a siloed company?

Opposite incentives: Dev is rewarded for change, Ops for stability, so every release is a fight across the wall.

Q2. Match each to its CALMS letter: blameless postmortem · Terraform for the VPC · 50-line PRs · Grafana p95 panel · runbook in the repo.

Culture · Automation · Lean · Measurement · Sharing.

Q3. A config typo by Riya caused a 20-minute outage. What does a siloed team do, and what does a DevOps team do?

Siloed: blame Riya and add a manual approval. DevOps: a blameless postmortem asking why the system allowed it, then validate config in CI or add an alert that fires in 2 minutes, not 20.

5 The DevOps lifecycle

The problem

Tuesday 4 p.m.: TaskFlow's "due dates" feature is deployed. Done? On Wednesday GET /tasks slows from 40 ms to 300 ms because the new query has no index. If "done" means "deployed", nobody is watching, and you hear about it from angry users on Friday.

The idea

DevOps treats delivery as a loop, not a line: eight stages, Dev on the left, Ops on the right, and monitoring feeding back into planning.

  ┌────────────────── DEV ───────────────────┐     ┌─────────── OPS ────────────┐
  Plan ──▶ Code ──▶ Build ──▶ Test ──▶ Release ──▶ Deploy ──▶ Operate ──▶ Monitor
   ▲                                                                         │
   └──────────── feedback: bugs, metrics, alerts, user requests ◀────────────┘
                  (drawn as an ∞ "infinity loop" in most textbooks)
Think of it like this

A restaurant doesn't stop caring when a dish leaves the kitchen. It plans, cooks, tastes and serves, then watches what comes back (cold plates, half-eaten portions), and that feedback shapes next week's menu.

See it: one feature going round the loop

Mon        Plan     issue #12 "Tasks need a due date"
Tue 10:00  Code     git switch -c feat/due-dates … PR opened
Tue 10:02  Build    CI installs deps, builds the image
Tue 10:04  Test     unit tests + scans pass (2 min) → reviewed → merged
Tue 16:00  Release  tag v1.4.0, image pushed to the registry
Tue 16:05  Deploy   staging, smoke test, then production
Tue–Wed    Operate  HPA scales API pods 2 → 6 at lunchtime peak
Wed 11:00  Monitor  Grafana: GET /tasks p95 40 ms → 300 ms
Wed 11:10  Plan     issue #13 "add an index on due_date" → the loop starts again

Catching Wednesday's slowdown is exactly what the Monitor stage is for.

Exam trap

"The lifecycle ends at Deploy." ✗ Operate and Monitor follow, and monitoring feeds back into Plan. That's why it's drawn as a loop.

"Release and Deploy are the same stage." ✗ Release produces a versioned artifact (tag v1.4.0, image in the registry). Deploy puts it onto servers, maybe staging today and production tomorrow.

Remember

Plan → Code → Build → Test → Release → Deploy → Operate → Monitor → back to Plan.
Left half = Dev, right half = Ops, and DevOps connects and automates the whole loop.

Mastery check
Q1. Which stage? (a) Trivy finds a critical CVE in the image, (b) HPA adds pods at peak, (c) git tag v1.4.0 and push the image, (d) an alert fires for 5xx > 5%.

(a) Test · (b) Operate · (c) Release · (d) Monitor.

Q2. Image 1.4.0 is in the registry and running in staging, but not yet in production. Has it been released? Deployed?

Released, yes (a versioned artifact in the registry). Deployed to staging, yes; to production, not yet.

Q3. Why is the lifecycle drawn as a loop and not a straight line?

What Operate and Monitor reveal (latency, errors, user requests) becomes the next Plan. Software is never "finished", so each trip round should be small and fast.

6 CI/CD overview & DORA metrics

The problem: integration hell

3 developers · 3 feature branches · each 3 weeks old
Friday "merge day":  47 conflicts · 12 failing tests · "whose change broke login?"
release slips a week

Each branch worked alone. They broke only when combined, after three weeks of changes had tangled together.

The idea

  • Continuous Integration (CI): merge small changes into main at least daily; every push triggers an automated build and tests, and a red build is fixed first.
  • Continuous Delivery: CI, plus every passing change is packaged and deployed to staging, so it's always releasable. Production is a manual button.
  • Continuous Deployment: no button. Every change that passes all checks reaches production automatically.
CI:                      commit → build → test ✔                          ← stops here
Continuous Delivery:     commit → build → test → staging → [👤 Approve] → prod
Continuous Deployment:   commit → build → test → staging → (automatic) → prod
Think of it like this

CI is tasting every sauce the moment it's made, not finding out on Friday that five sauces clash. Continuous Delivery is the dish waiting on the pass for the head chef's "serve". Continuous Deployment is a conveyor belt taking every dish that passes tasting straight to the table.

See it: the smallest CI pipeline

This file is the whole of TaskFlow's CI (Session 18 builds it out):

.github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]              # run on every push to main…
  pull_request:                   # …and on every pull request
jobs:
  test:
    runs-on: ubuntu-latest        # fresh GitHub-hosted Linux VM
    steps:
      - uses: actions/checkout@v4       # clone the repo
      - uses: actions/setup-node@v4     # install Node
        with:
          node-version: 20
          cache: npm                     # cache ~/.npm between runs
      - run: npm ci                      # exact install from package-lock.json
      - run: npm test                    # non-zero exit → red ✗ on the PR
KeyMeaning
name / on:The label on the PR's checks / the events that trigger it: pushes to main and any pull request
jobs.test / runs-onA job named test (jobs run in parallel unless linked with needs:) / the runner: a fresh VM each time

On the PR it shows as ✓ CI / test (pull_request) or ✗ … Failing after 41s, and branch protection can block merging until it's green. What it does not do: build an image or deploy. This is CI only; Continuous Delivery needs the package-and-deploy steps of Session 19.

DORA metrics: how you measure all this

The DORA research programme found four numbers that separate strong delivery teams from weak ones, two for speed and two for stability:

MetricMeasuresElite teams (DORA)Type
Deployment frequencyHow often you deploy to productionOn demand, many per dayThroughput
Lead time for changesCommit → running in productionLess than a dayThroughput
Change failure rate% of deploys that cause a failure (rollback, hotfix, incident)Low (≈ 0–15%)Stability
MTTR / failed deployment recovery timeTime to restore service after a failed changeLess than an hourStability
Example: TaskFlow's week
  • 10 production deploys Mon–Fri → deployment frequency = 2/day.
  • Issue #12 committed at 10:00, live at 14:30 → lead time = 4.5 h.
  • 1 of 10 deploys caused 5xx errors and was rolled back → change failure rate = 10%.
  • Alert at 15:02, rollback finished 15:20 → MTTR = 18 min.

Elite teams score well on all four at once. Speed and stability aren't a trade-off: small changes are easier to test, review and roll back.

Exam trap

"Continuous Delivery means every change goes to production automatically." ✗ That's Continuous Deployment. With Delivery a human approves production.

"We have Jenkins, so we do CI." ✗ Branches that live for weeks still integrate late. CI is the habit of merging small changes often; the tool only supports it.

"Deploying more often means more failures." ✗ DORA's data shows frequent deployers fail less.

Remember

CI = build + test every push · Delivery = always releasable, a human clicks · Deployment = no click.
DORA = 2 speed (deploy frequency, lead time) + 2 stability (change failure rate, MTTR).

Mastery check
Q1. A bank's pipeline deploys every merged change to staging automatically. Production needs a manager's approval in the pipeline. CI, Continuous Delivery or Continuous Deployment?

Continuous Delivery: everything automated and releasable, with a human gate before production. Remove the gate and it's Continuous Deployment.

Q2. Predict: ci.yml's on: block only has push: branches: [main]. You open a PR from feat/due-dates. Does CI run on the PR?

No. Without the pull_request trigger, broken code is caught only after it's merged, which is why the real file has both triggers.

Q3. In a month: 40 deploys, 6 rollbacks, 50 min average recovery, 3 days from commit to production. Which DORA metric is furthest from elite, and what would you work on?

Change failure rate 6/40 = 15% (borderline) and MTTR 50 min (fine). Lead time is worst: 3 days vs under a day. Shorten review queues, merge smaller changes, automate the path to production.

Q4. Why does CI use npm ci instead of npm install?

npm ci installs exactly the lock file and fails on a mismatch, so every run tests the same versions. npm install may update the lock file between runs.

DevOps vs SRE: DevOps is the philosophy; SRE is one concrete implementation with numeric targets ("class SRE implements interface DevOps", as Google puts it). The key number is the error budget:

Example: TaskFlow's error budget

SLO: the API is available 99.9% of each 30-day month. 30 × 24 × 60 = 43,200 min, so the budget is 0.1% = 43.2 minutes of downtime. If a bad deploy burns 30 of them in week one, the team slows risky releases and works on reliability until the budget recovers.

Exam trap

"SRE is just a new name for the ops team." ✗ SREs are engineers who manage reliability with SLOs and error budgets and automate away toil.

"Terraform and Ansible do the same job." ✗ Terraform provisions infrastructure (VPC, servers). Ansible configures existing servers (packages, files). They're often used together.

Remember

Every tool sits in a lifecycle stage. Learn the stage, then the tool.
SRE = reliability with numbers: SLO → error budget → slow down when it's spent.

Mastery check
Q1. The SLO is 99.95% over 30 days. How many minutes of downtime is the error budget?

0.05% of 43,200 min = 21.6 minutes.

Q2. Which role? (a) builds a "create a new service" template that comes with CI, a Dockerfile and dashboards; (b) sets SLOs and runs the incident review; (c) writes the VPC and IAM Terraform modules.

(a) Platform Engineer · (b) SRE · (c) Cloud Engineer.

Q3. Place each tool in its lifecycle stage: Trivy, Argo CD, Prometheus, GHCR, Jira.

Trivy → Test · Argo CD → Deploy · Prometheus → Monitor · GHCR → Release (artifact registry) · Jira → Plan.

8 TaskFlow: the course project

The problem

Twenty-odd tools in 23 sessions. If each session used a different toy app, you'd write a Dockerfile for one and a Helm chart for another, and never see one change travel the whole loop from section 5.

The idea

One small app, TaskFlow, goes through every stage, and each session adds one layer.

  • taskflow-api: Node.js 20 + Express. Listens on PORT (default 3000); GET /health → {"status":"ok"}, GET/POST /tasks, GET /metrics (Prometheus).
  • taskflow-db: PostgreSQL 16, DB and user taskflow; DATABASE_URL=postgres://taskflow:<pw>@db:5432/taskflow.
  • Optional redis:7 cache and taskflow-web (nginx serving the frontend on port 80) for multi-container and Ingress examples.

// server.js — TaskFlow API (starter version, Session 1)
const express = require('express');

const app = express();
const PORT = process.env.PORT || 3000;          // config from the environment, default 3000

app.use(express.json());                        // parse JSON request bodies (for POST /tasks later)

app.get('/health', (req, res) => {              // used by load balancers, K8s probes, healthcheck.sh
  res.json({ status: 'ok' });
});

const server = app.listen(PORT, () => {         // listens on all interfaces, not just localhost
  console.log(`TaskFlow API listening on port ${PORT}`);
});

process.on('SIGTERM', () => {                   // systemd / Docker / K8s send SIGTERM to stop us
  console.log('SIGTERM received, shutting down');
  server.close(() => process.exit(0));          // finish in-flight requests, then exit 0
});

app.listen(PORT)No host argument → binds to all interfaces (:: / 0.0.0.0), so it's reachable from outside a container
process.on('SIGTERM')Graceful shutdown: stop accepting connections, finish open requests, exit 0 (signals: Session 2)

Common mistakes on day one

Error: Cannot find module 'express' → you skipped npm install. EADDRINUSE … :::3000 → the port is taken; use PORT=4000 or find the culprit (Session 2). Never commit node_modules/ (Session 5).

Exam trap

"app.listen(3000) only accepts connections from localhost." ✗ With no host argument Node listens on all interfaces, which is what containers and load balancers need.

"Hard-coding the port and DB password is fine for now." ✗ Every environment then needs its own build, and the secret lands in Git. Config belongs in environment variables.

Remember

Config from env (PORT) · /health for machines · handle SIGTERM for a clean exit.
Every later tool, from systemd to Kubernetes, relies on these three habits.

Mastery check
Q1. Predict: you run PORT=4000 npm start, then curl localhost:3000/health. What happens?

curl: (7) Failed to connect to localhost port 3000 after 0 ms: Couldn't connect to server (connection refused). The server read PORT=4000, so nothing listens on 3000. Port 4000 works.

Q2. You kill the server (SIGTERM) while a request is in flight. What happens with the handler, and without it?

With it: stop accepting connections, finish the request, exit 0. Without it, Node's default action ends the process at once and the request fails.

Q3. Why does the load balancer from section 2 call /health rather than /tasks?

/health is cheap and side-effect free, so it can be called every few seconds without loading the DB. A failure takes that copy out of the pool.

The big idea

Microservices let teams deploy, scale and fail independently, but add network calls, gateways, discovery, a DB per service and many more things to ship and watch. DevOps answers with shared ownership (CALMS) and automation around the lifecycle loop: CI/CD carries every change to production, measured by DORA. Final mastery check — combine everything
Q1. Big Billion Day: search traffic ×50. Which ShopKart service do you scale, which component spreads requests across its copies, and which one sends /api/products/* to them?

Only catalog-service. The load balancer (the upstream catalog pool) spreads requests over its copies; the gateway's location /api/products/ sends those paths there; discovery keeps the copy list current.

Q2. Checkout calls stock → payment → email → analytics synchronously. Email has a 10-minute outage and checkout fails. Which design change fixes it, and which lifecycle stage should have told you before users did?

Keep stock and payment sync; make email and analytics async consumers of an OrderPlaced event, which the broker holds until email-svc returns. The Monitor stage (an alert on checkout 5xx rate) should have fired within minutes.

Q3. Correct every error: "DevOps is the team that runs Jenkins. Continuous Delivery means every commit goes straight to production. Microservices should share one database to keep data consistent."

(1) DevOps is culture + practices + tools shared by Dev and Ops, not a team or a tool. (2) That's Continuous Deployment; Delivery has a human approve production. (3) A shared DB makes a distributed monolith. Each service owns its data; consistency comes from APIs and events.

Q4. ShopKart's services must always be deployed together because they share tables. Which DORA metrics suffer, and why?

Deployment frequency and lead time, because every change waits for a joint release. Change failure rate usually rises too: big joint releases carry more changes that can break.

Q5. TaskFlow's team wants Continuous Deployment. Name three things they need first, each mapped to a lifecycle stage.

Reliable automated tests in CI (Test), since no human checks before production. Alerts on errors and latency (Monitor), to catch a bad deploy in minutes. Fast rollback or feature flags (Deploy/Operate), to keep MTTR low.

Q6. Why do the load balancer (section 2), the pipeline (section 6) and Kubernetes (later) all rely on TaskFlow's /health, PORT env var and SIGTERM handler?

/health tells machines whether a copy gets traffic or a restart. PORT lets one build run in every environment. The SIGTERM handler lets the platform replace a copy mid-deploy without dropping requests.
