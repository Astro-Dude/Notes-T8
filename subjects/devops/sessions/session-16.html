1 Authentication, authorization & RBAC

Explain like I'm 5

Authentication is the guard checking your ID card. Authorization is the list of rooms that card opens. RBAC is how Kubernetes writes that list.

Every request to the API server (from kubectl, a controller, or a pod) passes three gates in order:

kubectl / pod ──HTTPS──► kube-apiserver
   1. Authentication  "who are you?"         client cert, bearer token, OIDC   ✘ → 401 Unauthorized
   2. Authorization   "may you do this?"     RBAC: verb + resource + namespace ✘ → 403 Forbidden
   3. Admission       "is this object OK?"   PodSecurity, ResourceQuota, ...   ✘ → request rejected
   4. Stored in etcd → controllers / scheduler act on it
  • Authentication (authn) proves identity. Kubernetes has no User object: humans come from outside — a client certificate (CN = username, O = group), or an OIDC token from SSO (Google, Okta, AWS IAM on EKS).
  • Programs running inside the cluster use ServiceAccounts — real API objects (topic 2).
  • Authorization (authz) decides if that identity may do the action. The standard authorizer is RBAC (Role-Based Access Control). RBAC is allow-only: no rule = denied; there are no "deny" rules.

The four RBAC objects

ObjectScopeContainsUse it for
RoleOne namespaceRules (what is allowed)"read pods in taskflow"
ClusterRoleCluster-wideRulesCluster-scoped resources (nodes, PVs, namespaces) or a reusable rule set
RoleBindingOne namespaceSubjects + roleRefGive a Role or ClusterRole to someone, only in this namespace
ClusterRoleBindingCluster-wideSubjects + roleRefGive a ClusterRole in every namespace

A rule = apiGroups + resources + verbs. Find the group of any resource with kubectl api-resources:

$ kubectl api-resources -o wide | grep -E '^(NAME|pods |deployments|ingresses|networkpolicies)'
NAME              SHORTNAMES   APIVERSION             NAMESPACED   KIND            VERBS
pods              po           v1                     true         Pod             create,delete,deletecollection,get,list,patch,update,watch
deployments       deploy       apps/v1                true         Deployment      create,delete,deletecollection,get,list,patch,update,watch
ingresses         ing          networking.k8s.io/v1   true         Ingress         create,delete,deletecollection,get,list,patch,update,watch
networkpolicies   netpol       networking.k8s.io/v1   true         NetworkPolicy   create,delete,deletecollection,get,list,patch,update,watch
  • APIVERSION v1 (no slash) → core group, written "" in a Role. apps/v1 → group apps.
  • kubectl → verb: get pod x = get · get pods = list · -w = watch · apply = get + create/patch · edit = patch · logs = get on pods/log · exec = create on pods/exec.

A read-only "dev" role for the taskflow namespace

k8s/rbac-dev.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dev-readonly
  namespace: taskflow            # a Role only grants things inside this namespace
rules:
  - apiGroups: [""]               # "" = core group (v1): pods, services, configmaps, secrets...
    resources: ["pods", "pods/log", "services", "configmaps", "events"]
    verbs: ["get", "list", "watch"]  # read-only verbs
  - apiGroups: ["apps"]           # Deployments/ReplicaSets/StatefulSets live in apps/v1
    resources: ["deployments", "replicasets", "statefulsets"]
    verbs: ["get", "list", "watch"]
  # "secrets" is deliberately missing → devs can't read the DB password
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-readonly-binding
  namespace: taskflow
subjects:                        # WHO gets the permissions (list)
  - kind: User
    name: riya                     # must equal the cert CN / OIDC username exactly
    apiGroup: rbac.authorization.k8s.io
  - kind: Group
    name: dev                      # everyone whose cert has O=dev
    apiGroup: rbac.authorization.k8s.io
roleRef:                         # WHICH role — immutable once created
  kind: Role
  name: dev-readonly
  apiGroup: rbac.authorization.k8s.io
FieldMeaning
rules[].apiGroupsAPI group of the resources. "" core, apps, batch (Jobs), networking.k8s.io (Ingress, NetworkPolicy), autoscaling (HPA).
rules[].resourcesPlural lowercase names. Subresources (pods/log, pods/exec, deployments/scale) must be listed separately.
rules[].verbsget list watch create update patch delete deletecollection, or "*" (avoid).
rules[].resourceNamesOptional: limit to named objects, e.g. only the ConfigMap taskflow-config.
subjects[].kindUser, Group or ServiceAccount (the last needs namespace, no apiGroup).
roleRefThe Role/ClusterRole being granted. Can't be edited — delete and recreate the binding to change it.

ClusterRoles and the built-in roles

# nodes are cluster-scoped → needs ClusterRole + ClusterRoleBinding
$ kubectl create clusterrole node-reader --verb=get,list,watch --resource=nodes
clusterrole.rbac.authorization.k8s.io/node-reader created
$ kubectl create clusterrolebinding dev-node-reader --clusterrole=node-reader --group=dev
clusterrolebinding.rbac.authorization.k8s.io/dev-node-reader created

# reuse the built-in "view" ClusterRole, but only inside taskflow (RoleBinding!)
$ kubectl create rolebinding riya-view --clusterrole=view --user=riya -n taskflow
rolebinding.rbac.authorization.k8s.io/riya-view created
CombinationResult
Role + RoleBindingPermissions in that one namespace.
ClusterRole + RoleBindingClusterRole's rules, but only in the RoleBinding's namespace (reuse one definition across namespaces).
ClusterRole + ClusterRoleBindingRules in all namespaces + cluster-scoped resources.
Role + ClusterRoleBindingNot possible — a ClusterRoleBinding can only reference a ClusterRole.

Built-in ClusterRoles: cluster-admin (everything), admin (all in a namespace incl. RBAC), edit (read/write most objects, incl. reading Secrets, no RBAC), view (read-only, no Secrets).

Example: a real certificate user "riya" on minikube

The cert's CN becomes the username and O the group, signed by the cluster CA. After this, kubectl --context riya@minikube get pods works and get secrets returns Forbidden.

$ openssl genrsa -out riya.key 2048
$ openssl req -new -key riya.key -out riya.csr -subj "/CN=riya/O=dev"
$ openssl x509 -req -in riya.csr -CA ~/.minikube/ca.crt -CAkey ~/.minikube/ca.key -CAcreateserial -out riya.crt -days 30
$ kubectl config set-credentials riya --client-certificate=riya.crt --client-key=riya.key
User "riya" set.
$ kubectl config set-context riya@minikube --cluster=minikube --user=riya --namespace=taskflow
Context "riya@minikube" created.
$ kubectl --context riya@minikube get secrets
Error from server (Forbidden): secrets is forbidden: User "riya" cannot list resource "secrets" in API group "" in the namespace "taskflow"
Common mistakes
  • apiGroups: [""] for deployments → still denied. Deployments are in apps.
  • RoleBinding created in default instead of taskflow → permissions apply to the wrong namespace.
  • Granting pods but not pods/log → kubectl logs is Forbidden.
  • Binding cluster-admin "to make it work" — gives full control of every namespace.
Recap Authn = who (401), authz = allowed? (403), then admission. Role/ClusterRole say what; RoleBinding/ClusterRoleBinding say who and where. Test with kubectl auth can-i ... --as.

2 ServiceAccounts

Explain like I'm 5

A ServiceAccount is an ID badge for a program instead of a person, so RBAC can decide what that program may touch.

  • Every namespace gets a default ServiceAccount; a pod without serviceAccountName uses it.
  • Its username in RBAC is system:serviceaccount:<namespace>:<name>.
  • The kubelet mounts a short-lived, auto-rotated token into the pod at /var/run/secrets/kubernetes.io/serviceaccount/ (token, ca.crt, namespace). Since v1.24 no long-lived token Secret is created automatically.
  • Who needs one? Anything that calls the Kubernetes API: CI deployers, operators, Prometheus (lists pods), Argo CD. TaskFlow's API never calls the K8s API → it should get no token at all.
k8s/serviceaccounts.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: taskflow-api
  namespace: taskflow
automountServiceAccountToken: false   # app never talks to the K8s API → no token in its pods
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: ci-deployer                   # identity used by the CI pipeline (Session 19)
  namespace: taskflow
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployer
  namespace: taskflow
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: ["apps"]
    resources: ["replicasets"]       # read-only: needed by "kubectl rollout status/history"
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
  # no "delete", no "secrets", nothing outside taskflow
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: ci-deployer-binding
  namespace: taskflow
subjects:
  - kind: ServiceAccount              # ServiceAccount subjects: namespace required, no apiGroup
    name: ci-deployer
    namespace: taskflow
roleRef:
  kind: Role
  name: deployer
  apiGroup: rbac.authorization.k8s.io

Use it in the pod template of k8s/deployment.yaml:

    spec:
      serviceAccountName: taskflow-api          # must exist in the SAME namespace as the pod
      automountServiceAccountToken: false       # pod-level value overrides the SA's value
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0

Common mistake

Pods never appear and kubectl describe rs shows Error creating: pods "taskflow-api-..." is forbidden: error looking up service account taskflow/taskflow-api: serviceaccount "taskflow-api" not found. Apply serviceaccounts.yaml before the Deployment (or fix the name/namespace).

Recap ServiceAccount = identity for pods/CI. Bind it to a minimal Role. Turn off token mounting (automountServiceAccountToken: false) for apps that don't call the API.

3 Pod securityContext & Pod Security Standards

Explain like I'm 5

RBAC controls what people can do to the cluster; securityContext controls what a container can do on the node if it gets hacked.

By default a container runs as whatever user the image says (often root), with a writable filesystem and a default set of Linux capabilities. Harden TaskFlow's API:

k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
spec:
  replicas: 3
  selector:
    matchLabels:
      app: taskflow-api
  template:
    metadata:
      labels:
        app: taskflow-api
    spec:
      serviceAccountName: taskflow-api
      automountServiceAccountToken: false
      securityContext:                    # POD level → applies to every container
        runAsNonRoot: true                 # kubelet refuses to start a container as UID 0
        runAsUser: 1000                    # UID 1000 = "node" user in node:20-alpine
        runAsGroup: 1000
        fsGroup: 1000                      # mounted volumes become group-owned by GID 1000
        seccompProfile:
          type: RuntimeDefault            # block dangerous syscalls (container runtime's default filter)
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0
          ports:
            - containerPort: 3000
          envFrom:
            - secretRef:
                name: taskflow-db         # DATABASE_URL (Session 12)
          securityContext:                # CONTAINER level → overrides pod level
            allowPrivilegeEscalation: false # no setuid/sudo tricks to gain root
            readOnlyRootFilesystem: true   # attacker can't drop files into the image FS
            capabilities:
              drop: ["ALL"]               # no NET_RAW, CHOWN, ... — Node apps need none
          volumeMounts:
            - name: tmp
              mountPath: /tmp             # the only writable path (read-only root FS)
      volumes:
        - name: tmp
          emptyDir: {}
FieldLevelWhat it prevents
runAsNonRoot: truepod/containerRunning as root. Kubelet checks the UID before start.
runAsUser / runAsGrouppod/containerForces numeric UID/GID regardless of the image's USER.
fsGrouppod only"Permission denied" on volumes — files get this GID.
seccompProfile: RuntimeDefaultpod/containerRare, dangerous syscalls (e.g. kernel module loading).
allowPrivilegeEscalation: falsecontainerA process gaining more privileges than its parent (setuid binaries).
readOnlyRootFilesystem: truecontainerWriting anywhere except mounted volumes.
capabilities.drop: ["ALL"]containerRoot-like powers (raw sockets, chown, bind <1024). Add back one with add: ["NET_BIND_SERVICE"].
privileged: truecontainerThe opposite: full host access. Never for apps.
 
$ kubectl exec -n taskflow deploy/taskflow-api -- id
uid=1000(node) gid=1000(node) groups=1000(node)
$ kubectl exec -n taskflow deploy/taskflow-api -- touch /app/hacked.js
touch: /app/hacked.js: Read-only file system
command terminated with exit code 1
$ kubectl exec -n taskflow deploy/taskflow-api -- touch /tmp/ok && echo writable
writable
Common mistakes
  • runAsNonRoot: true without runAsUser on an image with USER node → CreateContainerConfigError: "container has runAsNonRoot and image has non-numeric user (node), cannot verify user is non-root". Set runAsUser: 1000 (or USER 1000 in the Dockerfile).
  • Image that runs as root + runAsNonRoot: true → "container has runAsNonRoot and image will run as root". Fix the image, don't drop the check.
  • readOnlyRootFilesystem: true and the app crashes with EROFS: read-only file system → mount an emptyDir where it writes (/tmp, cache dirs).

Pod Security Standards (PSS) — enforced per namespace

Instead of trusting every YAML author, the built-in Pod Security Admission controller checks pods against one of three levels, chosen with namespace labels. (It replaced PodSecurityPolicy, removed in v1.25.)

LevelAllowsTypical namespace
privilegedEverything (no checks)kube-system, CNI/storage agents
baselineBlocks known escalations: privileged, hostNetwork/hostPID, hostPath volumes, host ports, extra capabilitiesGeneral apps, easy default
restrictedBaseline plus: runAsNonRoot: true, allowPrivilegeEscalation: false, capabilities.drop: ["ALL"], seccomp RuntimeDefault/Localhost, limited volume typesYour app namespaces (taskflow)

Note: readOnlyRootFilesystem is good practice but not required by restricted.

k8s/namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: taskflow
  labels:
    pod-security.kubernetes.io/enforce: restricted         # reject violating pods
    pod-security.kubernetes.io/enforce-version: latest     # rules of the cluster's K8s version
    pod-security.kubernetes.io/warn: restricted            # print a warning to kubectl users
    pod-security.kubernetes.io/audit: restricted           # record violations in the audit log
# preview first: which running pods would violate? (nothing is changed)
$ kubectl label --dry-run=server --overwrite ns taskflow pod-security.kubernetes.io/enforce=restricted
Warning: existing pods in namespace "taskflow" violate the new PodSecurity enforce level "restricted:latest"
Warning: postgres-0: allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile
namespace/taskflow labeled

# a Deployment without securityContext in an enforced namespace:
$ kubectl apply -f bad-deploy.yaml

deployment.apps/bad-api created
$ kubectl get deploy bad-api -n taskflow
NAME      READY   UP-TO-DATE   AVAILABLE   AGE
bad-api   0/2     0            0           20s
$ kubectl describe rs -n taskflow -l app=bad-api | grep FailedCreate

Key takeaway

PSS checks pods, so a bad Deployment is still "created" — it just has 0 pods. Always check READY and the ReplicaSet events.

Postgres needs the same treatment before you enforce restricted: in the official postgres:16 image the postgres user is UID 999, so set runAsUser: 999, fsGroup: 999 plus the container settings above (or keep the database in a separate namespace labelled baseline).

Recap securityContext hardens one pod (non-root, no escalation, drop ALL caps, read-only FS). Pod Security Standards enforce a minimum level for a whole namespace via pod-security.kubernetes.io/enforce.

4 NetworkPolicies

Explain like I'm 5

By default every pod can phone every other pod. A NetworkPolicy is a firewall rule saying "only the API may call the database".

  • Default: all pods can reach all pods in all namespaces. A compromised pod can hit Postgres on 5432 directly.
  • A NetworkPolicy selects pods (podSelector) and lists what is allowed in (ingress) and/or out (egress).
  • Once any policy selects a pod for a direction, everything not explicitly allowed in that direction is denied. Policies are additive (union of allows).
  • Enforced by the CNI plugin, not by Kubernetes itself. Calico and Cilium enforce; minikube's default CNI does not — policies are silently ignored.
namespace ingress-nginx              namespace taskflow
  ingress controller ──TCP 3000 ✔──► taskflow-api ──TCP 5432 ✔──► taskflow-db (postgres-0)
                                     any other pod ──── 3000 ✘ ──► taskflow-api
                                     any other pod ──── 5432 ✘ ──► taskflow-db
k8s/networkpolicy.yaml
# 1) Deny all inbound traffic to every pod in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: taskflow
spec:
  podSelector: {}                 # {} = ALL pods in this namespace
  policyTypes:
    - Ingress                     # Ingress listed, but no ingress rules → nothing allowed in
---
# 2) Allow ONLY taskflow-api pods → taskflow-db pods on TCP 5432
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
  namespace: taskflow
spec:
  podSelector:                    # the pods this policy PROTECTS (destination)
    matchLabels:
      app: taskflow-db
  policyTypes:
    - Ingress
  ingress:
    - from:                       # allowed sources
        - podSelector:            # pods with this label, in the SAME namespace
            matchLabels:
              app: taskflow-api
      ports:                      # ...and only to this port
        - protocol: TCP
          port: 5432
---
# 3) Allow the ingress controller → API pods on 3000 (else the website dies)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-to-api
  namespace: taskflow
spec:
  podSelector:
    matchLabels:
      app: taskflow-api
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:      # every namespace gets this label automatically
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
      ports:
        - protocol: TCP
          port: 3000               # the container port (targetPort), not the Service port 80
FieldMeaning
spec.podSelectorWhich pods the policy applies to. {} = all pods in the namespace.
policyTypesIngress (incoming), Egress (outgoing), or both. A listed type with no rules = deny all for that direction.
ingress[].from[]Sources: podSelector, namespaceSelector, or ipBlock (CIDR, e.g. 10.0.0.0/16).
ports[]Destination port on the pod (container port), with protocol.
egress[].to[]Same selectors, for outgoing traffic.

Test it. A pod started with kubectl run gets label run=<name>, so it is blocked; give it the API's label and it is allowed:

$ kubectl apply -f k8s/networkpolicy.yaml
networkpolicy.networking.k8s.io/default-deny-ingress created
networkpolicy.networking.k8s.io/allow-api-to-db created
networkpolicy.networking.k8s.io/allow-ingress-to-api created
$ kubectl get netpol -n taskflow
NAME                   POD-SELECTOR       AGE
allow-api-to-db        app=taskflow-db    10s
allow-ingress-to-api   app=taskflow-api   10s
default-deny-ingress   <none>             10s

$ kubectl run pgtest -n taskflow --rm -it --restart=Never --image=postgres:16 -- pg_isready -h taskflow-db -t 3
taskflow-db:5432 - no response
$ kubectl run pgtest -n taskflow --rm -it --restart=Never --image=postgres:16 --labels=app=taskflow-api -- pg_isready -h taskflow-db -t 3
taskflow-db:5432 - accepting connections

Two gotchas

1. AND vs OR. Two list items under from = OR. One item holding both selectors = AND:

  ingress:
    - from:
        - namespaceSelector: {matchLabels: {team: web}}   # item 1
        - podSelector: {matchLabels: {app: taskflow-api}}  # item 2 → OR: ANY pod in team=web namespaces, OR api pods here
    - from:
        - namespaceSelector: {matchLabels: {team: web}}
          podSelector: {matchLabels: {app: frontend}}      # same item → AND: frontend pods IN team=web namespaces

2. Default-deny egress kills DNS. With policyTypes: [Egress] you must allow UDP/TCP 53 to kube-dns, or every hostname lookup (even taskflow-db) times out:

  egress:
    - to:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}
          podSelector: {matchLabels: {k8s-app: kube-dns}}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}
Common mistakes
  • Policy "does nothing" on minikube → cluster started without --cni=calico. Check kubectl get pods -n kube-system | grep calico.
  • Default-deny applied, website returns 504 → you forgot the ingress-controller → API allow (policy 3).
  • port: 80 in the policy when the container listens on 3000 → blocked. Policies see pod ports, not Service ports.
Recap Start with default-deny-ingress, then allow exact flows (ingress → api:3000, api → db:5432). Needs an enforcing CNI. Separate from items = OR, same item = AND.

5 Scheduling: nodeSelector, affinity & spreading

Explain like I'm 5

The scheduler is a seating planner. nodeSelector and affinity are the pod saying "seat me near the window"; anti-affinity is "don't seat my twins at the same table".

The scheduler first filters nodes that can't run the pod (not enough requested CPU/memory, wrong labels, untolerated taints), then scores the rest. These fields steer both steps:

MechanismSet onEffect
nodeSelectorPodHard rule: node must have all these labels (exact match).
nodeAffinityPodExpressive node rules (In, NotIn, Exists, Gt…), hard (required) or soft (preferred).
podAffinity / podAntiAffinityPodPlace near / away from other pods with given labels.
topologySpreadConstraintsPodKeep replica counts balanced across nodes/zones (max skew).
Taints + tolerationsNode + PodNode repels pods unless they tolerate (topic 6).

nodeSelector — the simple one

$ kubectl label nodes minikube-m03 disktype=ssd
node/minikube-m03 labeled
$ kubectl get nodes -L disktype
NAME           STATUS   ROLES           AGE   VERSION   DISKTYPE
minikube       Ready    control-plane   1d    v1.35.0
minikube-m02   Ready    <none>          1d    v1.35.0
minikube-m03   Ready    <none>          1d    v1.35.0   ssd
    spec:                    # Postgres StatefulSet pod template
      nodeSelector:
        disktype: ssd          # only nodes labelled disktype=ssd

nodeAffinity — required vs preferred

    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:     # HARD: no match → Pending
            nodeSelectorTerms:                                # terms are OR-ed
              - matchExpressions:                             # expressions inside a term are AND-ed
                  - key: disktype
                    operator: In
                    values: ["ssd", "nvme"]
          preferredDuringSchedulingIgnoredDuringExecution:    # SOFT: adds score, never blocks
            - weight: 80                                      # 1–100, higher = stronger preference
              preference:
                matchExpressions:
                  - key: topology.kubernetes.io/zone
                    operator: In
                    values: ["ap-south-1a"]
  • IgnoredDuringExecution = if node labels change later, running pods are not evicted.
  • Well-known node labels: kubernetes.io/hostname, topology.kubernetes.io/zone (e.g. ap-south-1a on EKS), kubernetes.io/arch, node.kubernetes.io/instance-type.

podAntiAffinity — spread API replicas across nodes

If all 3 taskflow-api pods land on one node and it dies, the app is down. Ask the scheduler to avoid nodes that already run one:

    spec:                                         # taskflow-api Deployment pod template
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: taskflow-api                # "other pods like me"
                topologyKey: kubernetes.io/hostname  # "same node" = same hostname label
$ kubectl get pods -n taskflow -l app=taskflow-api -o wide
NAME                            READY   STATUS    RESTARTS   AGE   IP              NODE           NOMINATED NODE   READINESS GATES
taskflow-api-6b8d9c7f5d-2xk9p   1/1     Running   0          40s   10.244.120.71   minikube       <none>           <none>
taskflow-api-6b8d9c7f5d-8qwrt   1/1     Running   0          40s   10.244.205.194  minikube-m02   <none>           <none>
taskflow-api-6b8d9c7f5d-tz4mn   1/1     Running   0          40s   10.244.151.3    minikube-m03   <none>           <none>

Use preferred here: with required anti-affinity, replica #4 on a 3-node cluster stays Pending forever. podAffinity (same shape) does the opposite, e.g. put the API next to its Redis cache.

topologySpreadConstraints (brief)

      topologySpreadConstraints:
        - maxSkew: 1                              # zones may differ by at most 1 pod
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway       # or DoNotSchedule (hard)
          labelSelector:
            matchLabels:
              app: taskflow-api

6 replicas over ap-south-1a/b/c → 2/2/2. Anti-affinity says "not together"; spread constraints say "evenly".

Pod stuck in Pending? The scheduler explains why in the Events:

$ kubectl describe pod postgres-0 -n taskflow | tail -3
Events:
  Type     Reason            Age   From               Message
  Warning  FailedScheduling  12s   default-scheduler  0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
Common mistakes
  • Typo in the label (diskType vs disktype — labels are case-sensitive) or the node was never labelled → Pending as above.
  • Required anti-affinity with more replicas than nodes → extra replicas Pending. Use preferred or add nodes.
Recap nodeSelector = exact labels (hard). nodeAffinity = expressions, required or preferred. podAntiAffinity + topologyKey: kubernetes.io/hostname spreads replicas for HA.

6 Taints & tolerations

Explain like I'm 5

A taint is a "Staff only" sign on a node. Only pods carrying the matching pass (a toleration) may enter.

  • Affinity attracts pods to nodes (set on the pod). A taint repels pods from a node (set on the node).
  • A toleration on a pod lets it ignore a matching taint. It does not force the pod onto that node.
  • Format: key=value:Effect. Remove with a trailing -.
$ kubectl taint nodes minikube-m03 dedicated=db:NoSchedule
node/minikube-m03 tainted
$ kubectl describe node minikube-m03 | grep Taints
Taints:             dedicated=db:NoSchedule
$ kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
NAME           TAINTS
minikube       <none>
minikube-m02   <none>
minikube-m03   [map[effect:NoSchedule key:dedicated value:db]]
$ kubectl taint nodes minikube-m03 dedicated=db:NoSchedule-      # remove
node/minikube-m03 untainted
EffectNew pods without tolerationAlready-running pods
NoScheduleNot scheduled (hard)Stay
PreferNoScheduleAvoided if possible (soft)Stay
NoExecuteNot scheduledEvicted (after tolerationSeconds, if they tolerate with a time limit)

Dedicated database node = taint + toleration + nodeSelector

$ kubectl taint nodes minikube-m03 dedicated=db:NoSchedule    # keep everything else OFF m03
$ kubectl label nodes minikube-m03 dedicated=db               # label so postgres can target m03
k8s/postgres.yaml (StatefulSet pod template excerpt)
    spec:
      tolerations:
        - key: dedicated          # matches taint key
          operator: Equal         # Equal → value must match; Exists → any value (omit value)
          value: db
          effect: NoSchedule      # must match the taint's effect (omit = all effects)
      nodeSelector:
        dedicated: db             # toleration ALLOWS m03; nodeSelector REQUIRES m03
      containers:
        - name: postgres
          image: postgres:16
# a pod that only tolerates node failure for 60s instead of the default 300s
      tolerations:
        - key: node.kubernetes.io/unreachable
          operator: Exists
          effect: NoExecute
          tolerationSeconds: 60   # evicted 60s after the node becomes unreachable

Kubernetes taints nodes itself: node.kubernetes.io/not-ready, unreachable, disk-pressure, memory-pressure, and kubeadm control planes carry node-role.kubernetes.io/control-plane:NoSchedule (why app pods don't run there). DaemonSets tolerate most of these automatically.

Node affinity / nodeSelectorTaints & tolerations
Set onPodTaint on node, toleration on pod
DirectionPull: "I want those nodes"Push: "this node rejects you"
GuaranteesPod goes only to matching nodesOther pods stay off the node
Can evict running pods?NoYes, with NoExecute
Use forHardware needs (SSD, GPU, zone)Dedicated / special nodes, node problems
Common mistake

Adding only the toleration and expecting Postgres to move to m03 — it may still land on m01/m02. Dedicated nodes need both: taint + toleration (keeps others out) and nodeSelector/affinity (pulls this pod in). Pending event for a missing toleration: 0/3 nodes are available: 1 node(s) had untolerated taint {dedicated: db}, 2 node(s) didn't match Pod's node affinity/selector.

Recap kubectl taint nodes N key=val:NoSchedule repels; a toleration permits; nodeSelector attracts. NoExecute also evicts running pods.

7 Node maintenance: cordon, drain & PodDisruptionBudgets

Explain like I'm 5

Cordon = "no new guests at this table". Drain = politely move the current guests to other tables. A PDB = "never move so many at once that the party stops".

CommandWhat it does
kubectl cordon NMarks node unschedulable. Running pods stay.
kubectl drain NCordons, then evicts pods (respecting PDBs); controllers recreate them elsewhere.
kubectl uncordon NSchedulable again. Pods do not move back automatically.

PodDisruptionBudget first

k8s/pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: taskflow-api-pdb
  namespace: taskflow
spec:
  minAvailable: 2          # at least 2 api pods must stay up during voluntary disruptions
  # maxUnavailable: 1     # alternative (use ONE of the two); also accepts "25%"
  selector:
    matchLabels:
      app: taskflow-api    # which pods the budget protects
$ kubectl apply -f k8s/pdb.yaml
$ kubectl get pdb -n taskflow
NAME               MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
taskflow-api-pdb   2               N/A               1                     6s

3 healthy replicas − minAvailable 2 = 1 allowed disruption: drain may evict one API pod at a time.

Draining a node for an upgrade

$ kubectl drain minikube-m02 --ignore-daemonsets --delete-emptydir-data
node/minikube-m02 cordoned
Warning: ignoring DaemonSet-managed Pods: kube-system/calico-node-7xk2p, kube-system/kube-proxy-q9z8d
evicting pod taskflow/taskflow-api-6b8d9c7f5d-8qwrt
pod/taskflow-api-6b8d9c7f5d-8qwrt evicted
node/minikube-m02 drained

$ kubectl get nodes
NAME           STATUS                     ROLES           AGE   VERSION
minikube       Ready                      control-plane   1d    v1.35.0
minikube-m02   Ready,SchedulingDisabled   <none>          1d    v1.35.0
minikube-m03   Ready                      <none>          1d    v1.35.0

# ... patch / reboot the node ...
$ kubectl uncordon minikube-m02
node/minikube-m02 uncordoned
drain flagWhy you need it
--ignore-daemonsetsDaemonSet pods can't be moved (one per node). Without it drain refuses to start.
--delete-emptydir-dataPods with emptyDir (like our /tmp) lose that data; drain makes you confirm.
--forceAlso delete bare pods with no controller (they will not come back).
--timeout=5mGive up instead of retrying forever.
Example: the PDB doing its job

One API pod per node. Drain m02: its pod is evicted (1 disruption allowed). Drain m03 straight away while the replacement is still starting (not Ready yet): ALLOWED DISRUPTIONS is now 0, so the eviction waits:

evicting pod taskflow/taskflow-api-6b8d9c7f5d-tz4mn
error when evicting pods/"taskflow-api-6b8d9c7f5d-tz4mn" -n "taskflow" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
...
pod/taskflow-api-6b8d9c7f5d-tz4mn evicted

Drain retries until a replacement pod is Ready elsewhere, so 2 replicas keep serving throughout.

Common mistakes
  • PDB with minAvailable equal to replicas (e.g. 3 of 3) or a single-replica app with minAvailable: 1 → ALLOWED DISRUPTIONS 0 → drain hangs forever.
  • PDBs only cover voluntary evictions (drain, autoscaler). They don't stop a node crash or kubectl delete pod, and don't govern rolling updates (that's maxUnavailable in the Deployment).
  • Forgetting uncordon — the node stays SchedulingDisabled and new pods pile onto the others.
Recap cordon → drain --ignore-daemonsets --delete-emptydir-data → maintain → uncordon. A PDB (policy/v1) caps how many pods voluntary evictions may take down at once.

★ Putting it all together

The big idea

Security is layered. RBAC decides which humans and ServiceAccounts may change the taskflow namespace (Riya reads, ci-deployer patches Deployments). securityContext and the restricted Pod Security level limit what a hacked TaskFlow container can do; NetworkPolicies limit whom it can reach (only the API talks to Postgres). Scheduling controls placement: anti-affinity spreads API replicas, taints + nodeSelector reserve a node for Postgres, and a PDB lets you drain nodes without dropping below 2 API pods.

Quick self-check

A user gets "403 Forbidden" from the API server. Did authentication or authorization fail?

Authorization. Authentication succeeded (the server knows who they are); RBAC found no rule allowing the verb on that resource. Failed authentication returns 401.

You bind the built-in ClusterRole edit to Riya using a RoleBinding in namespace taskflow. Where can she edit things?

Only in taskflow. A RoleBinding limits a ClusterRole's rules to its own namespace. A ClusterRoleBinding would grant it everywhere.

Your Role allows apiGroups: [""], resources: ["deployments"], verbs ["patch"], but CI still can't patch the Deployment. Why?

Deployments are in the apps group, not the core group. Use apiGroups: ["apps"].

What does podSelector: {} with policyTypes: [Ingress] and no ingress rules do?

Selects every pod in the namespace and allows no inbound traffic: a default-deny for ingress. Other policies then add specific allows.

Difference between a taint with NoSchedule and NoExecute?

NoSchedule only stops new non-tolerating pods from being scheduled. NoExecute also evicts already-running pods that don't tolerate it (after tolerationSeconds if set).

A Deployment has 3 replicas and a PDB with minAvailable: 3. What happens on kubectl drain?

ALLOWED DISRUPTIONS is 0, so every eviction is refused ("would violate the pod's disruption budget") and drain retries forever. Use minAvailable: 2 or maxUnavailable: 1.

Pods are rejected with "image has non-numeric user (node), cannot verify user is non-root". Fix?

runAsNonRoot: true can't verify a username. Add runAsUser: 1000 to the securityContext (or use USER 1000 in the Dockerfile).
