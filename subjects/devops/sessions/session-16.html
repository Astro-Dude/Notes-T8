1 Authentication vs authorization

The problem

Everyone on the project team uses a copy of the same minikube kubeconfig. Ask what that identity may do:

$ kubectl config view --minify -o jsonpath='{.contexts[0].context.user}{"\n"}'
minikube
$ kubectl auth can-i '*' '*' --all-namespaces
yes

Everyone is the same all-powerful user, so one script aimed at the wrong context can kubectl delete namespace taskflow. You can't give a new teammate "logs only", and the audit log can't say who did what.

The idea

Every request to the API server, from kubectl, a controller or a pod, passes three gates in order:

kubectl / pod ──HTTPS──► kube-apiserver
   1. Authentication  "who are you?"         client cert, bearer token, OIDC   ✘ → 401 Unauthorized
   2. Authorization   "may you do this?"     RBAC: verb + resource + namespace ✘ → 403 Forbidden
   3. Admission       "is this object OK?"   PodSecurity, ResourceQuota, ...   ✘ → request rejected
   4. Stored in etcd → controllers / scheduler act on it

Authentication (authn) proves identity. Kubernetes has no User object: a human is whoever a trusted credential names, either a client certificate signed by the cluster CA (CN = username, O = group) or an OIDC token from SSO (Google, Okta, AWS IAM on EKS). Programs in the cluster use ServiceAccounts (section 3). Authorization (authz), here RBAC (section 2), then decides if that identity may act.

Think of it like this

Back in Session 15's office building. Authentication is the guard at the door checking your ID card. Authorization is your keycard's access list: which doors it opens and what you may do inside. Admission is the security scanner checking what you carry in. There's no guest list: the guard trusts any ID its own office (the cluster CA) issued.

See it: a real user called Riya

$ openssl genrsa -out riya.key 2048
$ openssl req -new -key riya.key -out riya.csr -subj "/CN=riya/O=dev"
$ openssl x509 -req -in riya.csr -CA ~/.minikube/ca.crt -CAkey ~/.minikube/ca.key -CAcreateserial -out riya.crt -days 30
$ kubectl config set-credentials riya --client-certificate=riya.crt --client-key=riya.key
User "riya" set.
$ kubectl config set-context riya@minikube --cluster=minikube --user=riya --namespace=taskflow
Context "riya@minikube" created.
$ kubectl --context riya@minikube get pods
Error from server (Forbidden): pods is forbidden: User "riya" cannot list resource "pods" in API group "" in the namespace "taskflow"
TokenMeaning
-subj "/CN=riya/O=dev"The identity inside the certificate: username riya, group dev
x509 -req … -CA ~/.minikube/ca.crt -CAkey …Sign it with the cluster's own CA, which is what makes the API server trust it
set-credentials / set-contextAdd the cert to your kubeconfig and pair it with the cluster as context riya@minikube
Forbidden (403)Gate 1 passed: the server knows this is Riya. Gate 2 failed: nothing allows her anything yet.

What it does not do: grant anything, or create a user anywhere. kubectl get users answers error: the server doesn't have a resource type "users". A forged or expired cert fails at gate 1 instead: error: You must be logged in to the server (Unauthorized). Section 2 gives Riya her permissions.

Exam trap

"Kubernetes stores users and passwords in etcd." ✗ There are no User objects. Users come from certificates or an external identity provider. Only ServiceAccounts are API objects.

"403 Forbidden means wrong credentials." ✗ Wrong or missing credentials are 401. 403 means the server knows who you are and RBAC said no.

Remember

Authn = who are you? (401) · Authz = may you? (403) · Admission = is this object OK?
Humans = certs / OIDC · programs = ServiceAccounts.

Mastery check
Q1. Thirty days later Riya's commands fail with You must be logged in to the server (Unauthorized). Which gate failed, and why?

Authentication. The cert was signed with -days 30 and has expired, so the server no longer accepts it as proof of identity. RBAC is never even consulted.

Q2. A cert has subject /CN=arjun/O=dev/O=qa. What are the username and groups?

Username arjun, groups dev and qa (plus the built-in system:authenticated). RBAC can bind to any of them.

Q3. Riya, with no permissions, applies a pod spec that would also break the namespace's Pod Security level. Which error does she see?

403 Forbidden. Authorization (gate 2) runs before admission (gate 3), so the pod spec is never inspected.

2 RBAC: Roles & bindings

The problem

Riya is now authenticated, but everything returns 403. You want her to read pods, logs and Deployments in taskflow, but not Secrets (the DB password lives there), and nothing in other namespaces. You need a way to write "this person may do these verbs on these resources, here".

The idea

RBAC (Role-Based Access Control) splits that sentence in two. A Role lists what is allowed: verbs on resources, inside one namespace. A RoleBinding says who gets that Role, in that namespace. RBAC is allow-only: there are no deny rules, and anything not allowed is denied.

 Role dev-readonly  (ns: taskflow)              RoleBinding dev-readonly-binding  (ns: taskflow)
   rules: get, list, watch on                     subjects: User riya, Group dev
          pods, pods/log, services, …   ◀─────── roleRef:  Role dev-readonly
   "WHAT may be done"                           "WHO gets it, and WHERE"

 ClusterRole / ClusterRoleBinding: the same pair, cluster-wide
Think of it like this

A Role is an access profile written on paper: "may read files in the taskflow office". A RoleBinding loads that profile onto specific keycards (Riya's, everyone in group dev). No profile says "deny". A door just stays shut unless some profile opens it.

See it: two one-liners

$ kubectl create role pod-reader --verb=get,list,watch --resource=pods -n taskflow
role.rbac.authorization.k8s.io/pod-reader created
$ kubectl create rolebinding riya-pod-reader --role=pod-reader --user=riya -n taskflow
rolebinding.rbac.authorization.k8s.io/riya-pod-reader created
$ kubectl auth can-i list pods -n taskflow --as riya
yes
$ kubectl auth can-i delete pods -n taskflow --as riya
no
TokenMeaning
--verb=get,list,watch --resource=podsOne rule: these verbs on pods
--role=pod-reader --user=riyaBind that Role to a user (or --group=dev, --serviceaccount=taskflow:ci-deployer)
auth can-i VERB RESOURCEAsk the authorizer yes/no without doing anything
--as riyaAsk as Riya (impersonation, which your admin user is allowed to do). No need to log in as her.

What it does not do: can-i performs nothing, and the Role reaches no other namespace. Add --dry-run=client -o yaml to either create to get the YAML instead.

Build it up: the real role, as a file

A rule is apiGroups + resources + verbs. kubectl api-resources tells you each resource's group:

$ kubectl api-resources -o wide | grep -E '^(NAME|pods |deployments|networkpolicies)'
NAME              SHORTNAMES   APIVERSION             NAMESPACED   KIND            VERBS
pods              po           v1                     true         Pod             create,delete,deletecollection,get,list,patch,update,watch
deployments       deploy       apps/v1                true         Deployment      create,delete,deletecollection,get,list,patch,update,watch
networkpolicies   netpol       networking.k8s.io/v1   true         NetworkPolicy   create,delete,deletecollection,get,list,patch,update,watch

APIVERSION v1 (no slash) is the core group, written "" in a Role; apps/v1 is group apps. kubectl commands map to verbs: get pod x = get · get pods = list · -w = watch · apply = get + create/patch · edit = patch · logs = get on pods/log · exec = create on pods/exec.

k8s/rbac-dev.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: dev-readonly
  namespace: taskflow            # a Role only grants things inside this namespace
rules:
  - apiGroups: [""]               # "" = core group (v1): pods, services, configmaps, secrets...
    resources: ["pods", "pods/log", "services", "configmaps", "events"]
    verbs: ["get", "list", "watch"]  # read-only verbs
  - apiGroups: ["apps"]           # Deployments/ReplicaSets/StatefulSets live in apps/v1
    resources: ["deployments", "replicasets", "statefulsets"]
    verbs: ["get", "list", "watch"]
  # "secrets" is deliberately missing → devs can't read the DB password
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-readonly-binding
  namespace: taskflow
subjects:                        # WHO gets the permissions (list)
  - kind: User
    name: riya                     # must equal the cert CN / OIDC username exactly
    apiGroup: rbac.authorization.k8s.io
  - kind: Group
    name: dev                      # everyone whose cert has O=dev
    apiGroup: rbac.authorization.k8s.io
roleRef:                         # WHICH role — immutable once created
  kind: Role
  name: dev-readonly
  apiGroup: rbac.authorization.k8s.io
FieldMeaning
rules[].apiGroups"" core, apps, batch (Jobs), networking.k8s.io (Ingress, NetworkPolicy), autoscaling (HPA)
rules[].resourcesPlural lowercase names. Subresources (pods/log, pods/exec, deployments/scale) must be listed separately.
rules[].verbsget list watch create update patch delete deletecollection, or "*" (avoid)
rules[].resourceNamesOptional: only named objects, e.g. just the ConfigMap taskflow-config
subjects[].kindUser, Group or ServiceAccount (the last needs namespace and no apiGroup)
roleRefThe Role or ClusterRole granted. It can't be edited: delete and recreate the binding to change it.

$ kubectl auth can-i list pods -n default --as riya                       # other namespace

$ kubectl auth can-i list deployments -n taskflow --as anyone --as-group dev

$ kubectl auth can-i --list -n taskflow --as riya

ClusterRoles and the built-in roles

# nodes are cluster-scoped → needs ClusterRole + ClusterRoleBinding
$ kubectl create clusterrole node-reader --verb=get,list,watch --resource=nodes
clusterrole.rbac.authorization.k8s.io/node-reader created
$ kubectl create clusterrolebinding dev-node-reader --clusterrole=node-reader --group=dev
clusterrolebinding.rbac.authorization.k8s.io/dev-node-reader created

# reuse the built-in "view" ClusterRole, but only inside taskflow (RoleBinding!)
$ kubectl create rolebinding riya-view --clusterrole=view --user=riya -n taskflow
rolebinding.rbac.authorization.k8s.io/riya-view created
CombinationResult
Role + RoleBindingPermissions in that one namespace
ClusterRole + RoleBindingThe ClusterRole's rules, but only in the RoleBinding's namespace (one definition, reused per namespace)
ClusterRole + ClusterRoleBindingRules in all namespaces, plus cluster-scoped resources
Role + ClusterRoleBindingNot possible: a ClusterRoleBinding can only reference a ClusterRole

Built-in ClusterRoles: cluster-admin (everything), admin (everything in a namespace, RBAC included), edit (read/write most objects, including reading Secrets, but no RBAC), view (read-only, no Secrets).

Exam trap

"Add a deny rule for Secrets." ✗ RBAC has no deny. You leave Secrets out, and permissions from all bindings add up.

"Binding cluster-admin to the CI user is fine if it makes the deploy work." ✗ That gives full control of every namespace. Grant the few verbs it needs (section 3).

Remember

Role / ClusterRole = WHAT (apiGroups + resources + verbs) · RoleBinding / ClusterRoleBinding = WHO and WHERE.
Allow-only. Test with kubectl auth can-i … --as.

Mastery check
Q1. Spot the bug: a Role allows apiGroups: [""], resources: ["deployments"], verbs: ["patch"], but CI still can't patch the Deployment.

Deployments live in the apps group, not the core group. Use apiGroups: ["apps"].

Q2. You bind the built-in ClusterRole edit to Riya with a RoleBinding in taskflow. Where can she edit things? Can she read the DB password?

Only in taskflow: a RoleBinding limits a ClusterRole to its own namespace. And yes, edit includes reading Secrets, so she can. view wouldn't allow it.

Q3. kubectl --context riya@minikube get pods works, but kubectl logs taskflow-api-… is Forbidden. Why?

Logs are the subresource pods/log, which must be granted separately. Add it to the Role's resources (our dev-readonly has it; the one-liner pod-reader didn't).

Q4. You created the RoleBinding without -n taskflow. Predict kubectl auth can-i list pods -n taskflow --as riya.

no. The binding landed in default, so it grants nothing in taskflow (and refers to a Role that doesn't exist in default).

3 ServiceAccounts

The problem

Look inside an API pod:

$ kubectl exec -n taskflow deploy/taskflow-api -- ls /var/run/secrets/kubernetes.io/serviceaccount
ca.crt
namespace
token
$ kubectl get pods -n taskflow -l app=taskflow-api -o jsonpath='{.items[0].spec.serviceAccountName}{"\n"}'
default

TaskFlow's API never calls the Kubernetes API, yet every API pod carries a live token, free to anyone who breaks into the app. Meanwhile CI (Session 19) does need to deploy, and handing it your admin kubeconfig is section 1's problem again.

The idea

A ServiceAccount (SA) is an identity for processes running in pods, and unlike users it's a real API object. Every namespace gets a default SA, which pods use unless they name another. In RBAC its username is system:serviceaccount:<namespace>:<name>. The kubelet mounts a short-lived, auto-rotated token into the pod; since v1.24 no long-lived token Secret is created.

 pod  (serviceAccountName: ci-deployer)
   └─ /var/run/secrets/kubernetes.io/serviceaccount/token   (signed JWT, rotated by the kubelet)
         │  Authorization: Bearer <token>
         ▼
 kube-apiserver  authn → "system:serviceaccount:taskflow:ci-deployer"
                 authz → RoleBinding ci-deployer-binding → Role deployer → patch deployments ✔ · delete ✘
Think of it like this

A ServiceAccount is a badge for a robot rather than a person. The delivery robot (CI) gets a badge that opens only the loading bay. The vending machine (TaskFlow's API), which never needs to open a door, shouldn't carry a badge at all.

See it: an identity with no permissions

$ kubectl create serviceaccount ci-deployer -n taskflow
serviceaccount/ci-deployer created
$ kubectl auth can-i patch deployments -n taskflow --as=system:serviceaccount:taskflow:ci-deployer
no

What it does not do: grant anything. A ServiceAccount is just a name until a RoleBinding gives it a Role, exactly like Riya in section 1.

Build it up: one SA per job

k8s/serviceaccounts.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: taskflow-api
  namespace: taskflow
automountServiceAccountToken: false   # app never talks to the K8s API → no token in its pods
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: ci-deployer                   # identity used by the CI pipeline (Session 19)
  namespace: taskflow
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deployer
  namespace: taskflow
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: ["apps"]
    resources: ["replicasets"]       # read-only: needed by "kubectl rollout status/history"
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
  # no "delete", no "secrets", nothing outside taskflow
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: ci-deployer-binding
  namespace: taskflow
subjects:
  - kind: ServiceAccount              # ServiceAccount subjects: namespace required, no apiGroup
    name: ci-deployer
    namespace: taskflow
roleRef:
  kind: Role
  name: deployer
  apiGroup: rbac.authorization.k8s.io

The Role is the minimum kubectl apply + kubectl rollout status need: write Deployments, Services and ConfigMaps, read ReplicaSets and pods. Use the SA in the pod template of k8s/deployment.yaml:

    spec:
      serviceAccountName: taskflow-api          # must exist in the SAME namespace as the pod
      automountServiceAccountToken: false       # pod-level value overrides the SA's value
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0

$ kubectl get serviceaccounts -n taskflow

$ kubectl auth can-i delete namespaces --as=system:serviceaccount:taskflow:ci-deployer

Common mistake

Pods never appear, and kubectl describe rs shows Error creating: pods "taskflow-api-..." is forbidden: error looking up service account taskflow/taskflow-api: serviceaccount "taskflow-api" not found. Apply serviceaccounts.yaml before the Deployment, or fix the name or namespace.

Exam trap

"A pod without serviceAccountName has no identity." ✗ It runs as the namespace's default SA, with a token mounted unless automount is off.

Remember

ServiceAccount = identity for pods/CI: system:serviceaccount:ns:name.
One SA per job, a minimal Role, and automountServiceAccountToken: false for apps that never call the API.

Mastery check
Q1. The SA has automountServiceAccountToken: false, but a pod using it sets automountServiceAccountToken: true. Is the token mounted?

Yes. The pod-level setting overrides the ServiceAccount's.

Q2. Fill in: the ci-deployer SA's RBAC username is ________, and you test its rights with kubectl auth can-i … --as=________.

system:serviceaccount:taskflow:ci-deployer, both times.

Q3. Predict: CI runs kubectl delete pod taskflow-api-xyz -n taskflow with the ci-deployer token. What happens, and why is that good?

403 Forbidden: the deployer Role has no delete verb. A leaked CI token can roll out a new image but can't wipe the namespace or read Secrets.

4 Pod securityContext

The problem

A teammate deploys the draft image from Session 7, the one that lost its USER node line. Now suppose an attacker finds a remote-code bug in an npm package:

$ kubectl exec -n taskflow deploy/taskflow-api -- id
uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),11(floppy),20(dialout),26(tape),27(video)
$ kubectl exec -n taskflow deploy/taskflow-api -- sh -c 'echo "// backdoor" >> /app/server.js && echo appended'
appended

Kubernetes ran a root image without complaint, and a hijacked process could rewrite the app's own code. By default a container runs as whatever user its image says, with a writable filesystem and a default set of Linux capabilities.

The idea

A securityContext tells the kubelet and the runtime what a container is not allowed to do. It exists at two levels: the pod level applies to every container, and the container level overrides it. This is the Session 6 point made concrete: root in a container is root on a shared kernel, so take every power the app doesn't need.

 what a hijacked API process could do        securityContext line that stops it
 run as root                                  runAsNonRoot: true · runAsUser: 1000
 gain root via setuid / sudo                  allowPrivilegeEscalation: false
 raw sockets, chown, bind <1024 …            capabilities: drop: ["ALL"]
 write a backdoor into /app                   readOnlyRootFilesystem: true
 call rare, dangerous syscalls                seccompProfile: RuntimeDefault
Think of it like this

RBAC controls what people may do to the building. securityContext controls what a worker inside a room can do if they turn rogue: no master key (non-root), no toolbox (capabilities dropped), furniture bolted down (read-only filesystem).

See it: one line that refuses root

    spec:
      securityContext:
        runAsNonRoot: true            # kubelet checks the UID before starting the container
$ kubectl get pods -n taskflow -l app=taskflow-api
NAME                            READY   STATUS                       RESTARTS   AGE
taskflow-api-5d8c7b9f6d-p2m4x   0/1     CreateContainerConfigError   0          12s
$ kubectl describe pod taskflow-api-5d8c7b9f6d-p2m4x -n taskflow | grep Error:
  Warning  Failed  10s (x2 over 12s)  kubelet  Error: container has runAsNonRoot and image will run as root

What it does not do: fix the image. It only refuses to start it. Rebuild with USER node (Session 7) or set runAsUser.

Build it up: TaskFlow's hardened Deployment

k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: taskflow-api
  namespace: taskflow
spec:
  replicas: 3
  selector:
    matchLabels:
      app: taskflow-api
  template:
    metadata:
      labels:
        app: taskflow-api
    spec:
      serviceAccountName: taskflow-api
      automountServiceAccountToken: false
      securityContext:                    # POD level → applies to every container
        runAsNonRoot: true                 # kubelet refuses to start a container as UID 0
        runAsUser: 1000                    # UID 1000 = "node" user in node:20-alpine
        runAsGroup: 1000
        fsGroup: 1000                      # mounted volumes become group-owned by GID 1000
        seccompProfile:
          type: RuntimeDefault            # block dangerous syscalls (container runtime's default filter)
      containers:
        - name: api
          image: shauryav/taskflow-api:1.0.0
          ports:
            - containerPort: 3000
          envFrom:
            - secretRef:
                name: taskflow-db-secret  # DATABASE_URL + POSTGRES_PASSWORD (Sessions 12–13)
          securityContext:                # CONTAINER level → overrides pod level
            allowPrivilegeEscalation: false # no setuid/sudo tricks to gain root
            readOnlyRootFilesystem: true   # attacker can't drop files into the image FS
            capabilities:
              drop: ["ALL"]               # no NET_RAW, CHOWN, ... — Node apps need none
          volumeMounts:
            - name: tmp
              mountPath: /tmp             # the only writable path (read-only root FS)
      volumes:
        - name: tmp
          emptyDir: {}
FieldLevelWhat it prevents
runAsNonRoot: truepod/containerRunning as root: the kubelet checks the UID before start
runAsUser / runAsGrouppod/containerForces a numeric UID/GID, whatever the image's USER says
fsGrouppod only"Permission denied" on volumes: their files get this GID
seccompProfile: RuntimeDefaultpod/containerRare, dangerous syscalls (e.g. loading kernel modules)
allowPrivilegeEscalation: falsecontainerA process gaining more privileges than its parent (setuid binaries)
readOnlyRootFilesystem: truecontainerWriting anywhere except mounted volumes (here /tmp, an emptyDir)

privileged: truecontainerThe opposite: full host access. Never for apps.

Common mistakes
  • runAsNonRoot: true without runAsUser on an image with USER node → CreateContainerConfigError: "container has runAsNonRoot and image has non-numeric user (node), cannot verify user is non-root". Set runAsUser: 1000 (or USER 1000 in the Dockerfile).
  • readOnlyRootFilesystem: true and the app crashes with EROFS: read-only file system → mount an emptyDir where it writes (/tmp, cache dirs).
Exam trap

"The image says USER node, so the pod is guaranteed non-root." ✗ Only for that image. Without runAsNonRoot, the next image (like the draft) runs as root without a word. The securityContext makes it a rule.

Remember

Non-root · no privilege escalation · drop ALL capabilities · read-only root FS · seccomp RuntimeDefault.
Pod level applies to all containers; container level overrides.

Mastery check
Q1. The pod level says runAsUser: 1000 and the container level says runAsUser: 2000. Which UID does the container run as?

2000. Container-level settings override pod-level ones for that container.

Q2. After adding readOnlyRootFilesystem: true, the API crashes writing /app/uploads/tmp-123. Give the fix that keeps the hardening.

Mount an emptyDir (or a PVC if the data must last) at /app/uploads. Only mounted volumes are writable; the image's files stay read-only.

Q3. Diagnose: CreateContainerConfigError with "image has non-numeric user (node), cannot verify user is non-root".

The kubelet can't map the name node to a UID, so it can't prove non-root. Add runAsUser: 1000, or use USER 1000 in the Dockerfile.

5 Pod Security Standards

The problem

Section 4 works only if every YAML author remembers it. Next week someone applies bad-deploy.yaml with no securityContext at all, and it deploys happily. You want a minimum for the whole namespace that nobody can forget.

The idea

The built-in Pod Security Admission controller checks every new pod against one of three Pod Security Standards, chosen with namespace labels. It runs at admission, gate 3 from section 1. (It replaced PodSecurityPolicy, which was removed in v1.25.) Each label also has a mode: enforce rejects, warn prints a warning, audit logs.

 namespace taskflow   pod-security.kubernetes.io/enforce=restricted
   kubectl apply bad-deploy.yaml ──▶ Deployment ✔ created         (PSA checks PODS, not Deployments)
         ReplicaSet creates pods ──▶ PSA: violates "restricted" ──▶ ✘ FailedCreate
   result:  deployment bad-api   READY 0/2
Think of it like this

The building code for a tenant's floor. Inspectors at the door turn away any worker who breaks it. The company's hiring plan (the Deployment) is still filed, but none of its workers (pods) get in.

See it: label the namespace

k8s/namespace.yaml (Session 15's file, with Pod Security labels)
apiVersion: v1
kind: Namespace
metadata:
  name: taskflow
  labels:
    app.kubernetes.io/part-of: taskflow
    env: dev
    pod-security.kubernetes.io/enforce: restricted         # reject violating pods
    pod-security.kubernetes.io/enforce-version: latest     # rules of the cluster's K8s version
    pod-security.kubernetes.io/warn: restricted            # print a warning to kubectl users
    pod-security.kubernetes.io/audit: restricted           # record violations in the audit log
# preview first: which running pods would violate? (nothing is changed)

What it does not do: touch running pods. postgres-0 keeps running even after you enforce; the check applies when a pod is created. Fix Postgres first: in the official postgres:16 image the postgres user is UID 999, so set runAsUser: 999, fsGroup: 999 plus section 4's container settings, or run the database in a separate namespace labelled baseline.

"Pod Security Admission rejects the bad Deployment." ✗ It checks pods. The Deployment is created with 0 pods, so always check READY and the ReplicaSet events.

Mastery check
Q1. In a baseline namespace, which is rejected: (a) a pod running as root with default capabilities, (b) a pod with hostNetwork: true?

(b). Baseline blocks host namespaces, hostPath and privileged pods, but still allows root. Rejecting (a) takes restricted.

Q2. Why would putting Session 15's node-exporter DaemonSet in taskflow fail, and where should it live?

It uses hostNetwork, hostPID and hostPath, which even baseline forbids. Node agents belong in their own namespace (monitoring) labelled privileged.

Q3. You set only warn: restricted, not enforce. What happens to bad-deploy.yaml?

kubectl prints the same "would violate" warning, but the pods are created and run. Teams often start with warn/audit, fix the warnings, then switch on enforce.

6 NetworkPolicies

The problem

Session 15 said namespaces don't block traffic. Prove it: can a random pod reach Postgres?

$ kubectl run pgtest -n taskflow --rm -it --restart=Never --image=postgres:16 -- pg_isready -h taskflow-db -t 3
taskflow-db:5432 - accepting connections
$ kubectl run pgtest -n riya-demo --rm -it --restart=Never --image=postgres:16 -- pg_isready -h taskflow-db.taskflow -t 3
taskflow-db.taskflow:5432 - accepting connections      # from ANOTHER namespace, too

Every pod can reach every pod. If any pod in the cluster is compromised, Postgres is one network hop away, guarded only by its password.

The idea

A NetworkPolicy selects pods (podSelector) and lists the traffic allowed in (ingress) or out (egress). Once any policy selects a pod for a direction, everything not allowed in that direction is denied, and policies add up (a union of allows). The CNI plugin enforces them, not Kubernetes: Calico and Cilium do; minikube's default CNI silently ignores them.

namespace ingress-nginx              namespace taskflow
  ingress controller ──TCP 3000 ✔──► taskflow-api ──TCP 5432 ✔──► taskflow-db (postgres-0)
                                     any other pod ──── 3000 ✘ ──► taskflow-api
                                     any other pod ──── 5432 ✘ ──► taskflow-db
Think of it like this

The building's internal phone system. By default any room can dial any room. NetworkPolicies are the switchboard rules: "the database room only takes calls from the API room's extension". A switchboard without rule support (some CNIs) ignores them silently.

See it: deny everything in

The smallest useful policy selects every pod in the namespace and allows nothing in:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: taskflow
spec:
  podSelector: {}                 # {} = ALL pods in this namespace
  policyTypes:
    - Ingress                     # Ingress listed, but no ingress rules → nothing allowed in
$ kubectl run pgtest -n taskflow --rm -it --restart=Never --image=postgres:16 -- pg_isready -h taskflow-db -t 3
taskflow-db:5432 - no response

What it does not do: limit outgoing traffic (only Ingress is listed), or affect other namespaces. It also blocks the traffic you want: right now the API can't reach the DB and the Ingress can't reach the API. The full file adds those two flows back.

Build it up: allow exactly TaskFlow's flows

k8s/networkpolicy.yaml
# 1) Deny all inbound traffic to every pod in the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: taskflow
spec:
  podSelector: {}                 # {} = ALL pods in this namespace
  policyTypes:
    - Ingress                     # Ingress listed, but no ingress rules → nothing allowed in
---
# 2) Allow ONLY taskflow-api pods → taskflow-db pods on TCP 5432
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
  namespace: taskflow
spec:
  podSelector:                    # the pods this policy PROTECTS (destination)
    matchLabels:
      app: taskflow-db
  policyTypes:
    - Ingress
  ingress:
    - from:                       # allowed sources
        - podSelector:            # pods with this label, in the SAME namespace
            matchLabels:
              app: taskflow-api
      ports:                      # ...and only to this port
        - protocol: TCP
          port: 5432
---
# 3) Allow the ingress controller → API pods on 3000 (else the website dies)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-to-api
  namespace: taskflow
spec:
  podSelector:
    matchLabels:
      app: taskflow-api
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:      # every namespace gets this label automatically
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
      ports:
        - protocol: TCP
          port: 3000               # the container port (targetPort), not the Service port 80
FieldMeaning
spec.podSelectorWhich pods the policy applies to. {} = all pods in the namespace.
policyTypesIngress (incoming), Egress (outgoing) or both. A listed type with no rules = deny all in that direction.
ingress[].from[]Sources: podSelector, namespaceSelector, or ipBlock (a CIDR such as 10.0.0.0/16)
ports[]Destination port on the pod (the container port), with protocol

$ kubectl get netpol -n taskflow

$ kubectl run pgtest -n taskflow --rm -it --restart=Never --image=postgres:16 -- pg_isready -h taskflow-db -t 3
taskflow-db:5432 - no response
$ kubectl run pgtest -n taskflow --rm -it --restart=Never --image=postgres:16 --labels=app=taskflow-api -- pg_isready -h taskflow-db -t 3
taskflow-db:5432 - accepting connections

Two gotchas

1. AND vs OR. Two list items under from = OR. One item holding both selectors = AND:

  ingress:
    - from:
        - namespaceSelector: {matchLabels: {team: web}}   # item 1
        - podSelector: {matchLabels: {app: taskflow-api}}  # item 2 → OR: ANY pod in team=web namespaces, OR api pods here
    - from:
        - namespaceSelector: {matchLabels: {team: web}}
          podSelector: {matchLabels: {app: frontend}}      # same item → AND: frontend pods IN team=web namespaces

2. Default-deny egress kills DNS. With policyTypes: [Egress] you must allow UDP/TCP 53 to kube-dns, or every lookup (even taskflow-db) times out:

  egress:
    - to:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}
          podSelector: {matchLabels: {k8s-app: kube-dns}}
      ports:
        - {protocol: UDP, port: 53}
        - {protocol: TCP, port: 53}
Exam trap

"I applied a NetworkPolicy, so the traffic is blocked." ✗ Only if the CNI enforces it. On a cluster started without --cni=calico, check kubectl get pods -n kube-system | grep calico first.

"The policy port is the Service port (80)." ✗ Policies see traffic arriving at the pod, after the Service, so it's the container port: 3000.

Remember

Default-deny first, then allow exact flows (ingress → api:3000, api → db:5432).
Needs an enforcing CNI · separate from items = OR, same item = AND · egress deny? allow DNS.

Mastery check
Q1. After applying only default-deny-ingress and allow-api-to-db, http://taskflow.local returns 504. Why?

Default-deny also blocks the ingress controller's traffic to the API pods. Add allow-ingress-to-api (namespaceSelector ingress-nginx, port 3000).

Q2. Predict: kubectl run pgtest -n riya-demo --labels=app=taskflow-api … pg_isready -h taskflow-db.taskflow.

no response. A bare podSelector in from only matches pods in the policy's own namespace, so the label doesn't help from riya-demo.

Q3. What does podSelector: {} with policyTypes: [Egress] and no egress rules do to the API?

It blocks all outgoing traffic from every pod in the namespace, DNS included, so the API can't even resolve taskflow-db. Add allows for DNS and for port 5432.

7 nodeSelector, affinity & spreading

The problem

You scale the API to 3 replicas on the 3-node cluster and check where they landed:

$ kubectl get pods -n taskflow -l app=taskflow-api -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
NAME                            NODE
taskflow-api-6b8d9c7f5d-2xk9p   minikube-m02
taskflow-api-6b8d9c7f5d-8qwrt   minikube-m02
taskflow-api-6b8d9c7f5d-tz4mn   minikube-m02

All three are on minikube-m02. Built-in spreading is only a soft preference (skew ≤ 3 per node), so this is legal, and if m02 dies, so does TaskFlow. Postgres, meanwhile, should sit on the node with the fast SSD (minikube-m03), but nothing says so.

The idea

The scheduler (Session 9) first filters out nodes that can't run the pod, then scores the rest. Fields on the pod steer both steps:

 new pod ──▶ FILTER (hard rules)                         ──▶ SCORE (soft preferences) ──▶ bind to best node
              requests fit? (S15) · nodeSelector               preferred node affinity
              required node affinity                           preferred pod (anti-)affinity
              required pod anti-affinity · taints (section 8)  spread: ScheduleAnyway
MechanismSet onEffect
nodeSelectorPodHard rule: the node must have all these labels (exact match)
nodeAffinityPodExpressive node rules (In, NotIn, Exists, Gt…), hard (required) or soft (preferred)
podAffinity / podAntiAffinityPodPlace near / away from other pods with given labels
topologySpreadConstraintsPodKeep replica counts balanced across nodes/zones (max skew)
Taints + tolerationsNode + PodThe node repels pods unless they tolerate it (section 8)
Think of it like this

The building's seating planner. nodeSelector = "I need a room with a sink" (no sink, no seat). Preferred affinity = "a window would be nice". Anti-affinity = "don't seat the twins in the same room", so one fire can't get both. Spread = "keep the team evenly across floors".

See it: nodeSelector

$ kubectl label nodes minikube-m03 disktype=ssd
node/minikube-m03 labeled
$ kubectl get nodes -L disktype
NAME           STATUS   ROLES           AGE   VERSION   DISKTYPE
minikube       Ready    control-plane   1d    v1.35.0
minikube-m02   Ready    <none>          1d    v1.35.0
minikube-m03   Ready    <none>          1d    v1.35.0   ssd
    spec:                    # Postgres StatefulSet pod template
      nodeSelector:
        disktype: ssd          # only nodes labelled disktype=ssd

-L disktype shows that label as a column. What it does not do: keep other pods off m03. It pulls Postgres there; it doesn't reserve the node (section 8 does that). And if no node has the label, the pod stays Pending.

Build it up

nodeAffinity: required vs preferred

    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:     # HARD: no match → Pending
            nodeSelectorTerms:                                # terms are OR-ed
              - matchExpressions:                             # expressions inside a term are AND-ed
                  - key: disktype
                    operator: In
                    values: ["ssd", "nvme"]
          preferredDuringSchedulingIgnoredDuringExecution:    # SOFT: adds score, never blocks
            - weight: 80                                      # 1–100, higher = stronger preference
              preference:
                matchExpressions:
                  - key: topology.kubernetes.io/zone
                    operator: In
                    values: ["ap-south-1a"]

IgnoredDuringExecution means that if node labels change later, running pods are not evicted. Well-known node labels: kubernetes.io/hostname, topology.kubernetes.io/zone (e.g. ap-south-1a on EKS), kubernetes.io/arch, node.kubernetes.io/instance-type.

podAntiAffinity: spread the API replicas (solves the problem)

    spec:                                         # taskflow-api Deployment pod template
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels:
                    app: taskflow-api                # "other pods like me"
                topologyKey: kubernetes.io/hostname  # "same node" = same hostname label
$ kubectl get pods -n taskflow -l app=taskflow-api -o wide
NAME                            READY   STATUS    RESTARTS   AGE   IP              NODE           NOMINATED NODE   READINESS GATES
taskflow-api-6b8d9c7f5d-2xk9p   1/1     Running   0          40s   10.244.120.71   minikube       <none>           <none>
taskflow-api-6b8d9c7f5d-8qwrt   1/1     Running   0          40s   10.244.205.194  minikube-m02   <none>           <none>
taskflow-api-6b8d9c7f5d-tz4mn   1/1     Running   0          40s   10.244.151.3    minikube-m03   <none>           <none>

Use preferred here: with required anti-affinity, replica 4 on a 3-node cluster stays Pending forever. podAffinity has the same shape and does the opposite, e.g. put the API next to its Redis cache.

topologySpreadConstraints (brief)

      topologySpreadConstraints:
        - maxSkew: 1                              # zones may differ by at most 1 pod
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway       # or DoNotSchedule (hard)
          labelSelector:
            matchLabels:
              app: taskflow-api

6 replicas over ap-south-1a/b/c → 2/2/2. Anti-affinity says "not together"; spread says "evenly". When a pod is stuck Pending, the scheduler explains why:

$ kubectl describe pod postgres-0 -n taskflow | tail -3
Events:
  Type     Reason            Age   From               Message
  Warning  FailedScheduling  12s   default-scheduler  0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
Exam trap

"Required anti-affinity is always safer." ✗ With more replicas than nodes, the extras stay Pending. Prefer preferred unless co-location is truly forbidden.

"Changing a node's labels moves running pods off it." ✗ IgnoredDuringExecution: rules apply at scheduling time only.

Remember

nodeSelector = exact labels (hard) · nodeAffinity = expressions, required or preferred.
podAntiAffinity + topologyKey: kubernetes.io/hostname = one replica per node, for HA.

Mastery check
Q1. Spot the bug: the node is labelled disktype=ssd, the pod's nodeSelector says diskType: ssd, and the pod is Pending.

Labels are case-sensitive: diskType ≠ disktype. No node matches, hence "didn't match Pod's node affinity/selector".

Q2. Four API replicas, three nodes, required pod anti-affinity on kubernetes.io/hostname. Predict the pods. And with preferred?

Required: 3 Running (one per node), 1 Pending forever. Preferred: all 4 Running, with two sharing a node, because the rule only lowers that node's score.

Q3. Fill in: nodeSelector and required affinity act in the scheduler's ________ step; preferred rules act in the ________ step.

Filter · score.

8 Taints & tolerations

The problem

The nodeSelector pulled Postgres onto minikube-m03. Now look at who else is there:

$ kubectl get pods -A --field-selector spec.nodeName=minikube-m03 -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name
NS            NAME
kube-system   calico-node-x7k2p
kube-system   kube-proxy-9tq2w
taskflow      postgres-0
taskflow      taskflow-api-6b8d9c7f5d-tz4mn
riya-demo     loadgen-5f7b9c8d6-2kq8m

Riya's load generator is eating the database node's CPU and disk. A nodeSelector attracts a pod; it can't keep others away.

The idea

Affinity attracts pods to nodes and is set on the pod. A taint repels pods from a node and is set on the node. A toleration on a pod lets it ignore a matching taint, but does not send it there. A taint is written key=value:Effect.

 node minikube-m03   taint  dedicated=db:NoSchedule              "Staff only"
   postgres-0     toleration dedicated=db  ✔ may enter    + nodeSelector dedicated=db → must go here
   taskflow-api   no toleration            ✘ repelled
   loadgen        no toleration            ✘ repelled
 a reserved node needs BOTH: taint + toleration (keeps others out) AND nodeSelector (pulls this pod in)
Think of it like this

A taint is a "Staff only" sign on a room. A toleration is the staff pass: it lets you ignore the sign, but nobody sends you into the room just because you hold one. The nodeSelector is what actually seats you there.

See it

$ kubectl taint nodes minikube-m03 dedicated=db:NoSchedule
node/minikube-m03 tainted
$ kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
NAME           TAINTS
minikube       <none>
minikube-m02   <none>
minikube-m03   [map[effect:NoSchedule key:dedicated value:db]]
$ kubectl taint nodes minikube-m03 dedicated=db:NoSchedule-      # trailing "-" removes it
node/minikube-m03 untainted

kubectl describe node minikube-m03 | grep Taints shows the same thing. What it does not do: evict anything. With NoSchedule, the load generator already on m03 stays put until it's rescheduled; only NoExecute evicts running pods.

Build it up: a dedicated database node

EffectNew pods without tolerationAlready-running pods
NoScheduleNot scheduled (hard)Stay
PreferNoScheduleAvoided if possible (soft)Stay
NoExecuteNot scheduledEvicted (after tolerationSeconds, if they tolerate with a time limit)
 
$ kubectl taint nodes minikube-m03 dedicated=db:NoSchedule    # keep everything else OFF m03
$ kubectl label nodes minikube-m03 dedicated=db               # label so postgres can target m03
k8s/postgres.yaml (StatefulSet pod template excerpt)
    spec:
      tolerations:
        - key: dedicated          # matches taint key
          operator: Equal         # Equal → value must match; Exists → any value (omit value)
          value: db
          effect: NoSchedule      # must match the taint's effect (omit = all effects)
      nodeSelector:
        dedicated: db             # toleration ALLOWS m03; nodeSelector REQUIRES m03
      containers:
        - name: postgres
          image: postgres:16

Kubernetes taints nodes itself, too: node.kubernetes.io/not-ready, unreachable, disk-pressure, memory-pressure, and kubeadm control planes carry node-role.kubernetes.io/control-plane:NoSchedule (Session 15's DaemonSet needed a toleration for it). Every pod gets a default 300-second toleration for not-ready and unreachable; shorten it to fail over faster:

# a pod that only tolerates node failure for 60s instead of the default 300s
      tolerations:
        - key: node.kubernetes.io/unreachable
          operator: Exists
          effect: NoExecute
          tolerationSeconds: 60   # evicted 60s after the node becomes unreachable

Exam trap

"Give Postgres a toleration and it will move to m03." ✗ A toleration only permits m03; Postgres may still land on m01 or m02. Pending event for the opposite mistake, a nodeSelector without the toleration: 0/3 nodes are available: 1 node(s) had untolerated taint {dedicated: db}, 2 node(s) didn't match Pod's node affinity/selector.

Remember

Taint (node) repels · toleration (pod) permits · nodeSelector/affinity (pod) attracts.
NoSchedule = no new pods · NoExecute = also evicts running ones.

Mastery check
Q1. You taint m03 with dedicated=db:NoExecute instead of NoSchedule. Predict what happens to the load generator and the API pod already on m03.

Both are evicted at once (no toleration) and recreated elsewhere by their Deployments. So is postgres-0: its toleration says effect: NoSchedule, which doesn't match a NoExecute taint. Its replacement then stays Pending, because the nodeSelector requires m03 and m03 repels it. Change the toleration to effect: NoExecute, or omit the effect.

Q2. A toleration uses operator: Exists with key: dedicated and no value. Which taints does it tolerate?

Any taint with key dedicated, whatever its value (db, gpu…), for the given effect, or for all effects if effect is omitted.

9 Cordon, drain & PodDisruptionBudgets

The problem

minikube-m02 needs a kernel patch and a reboot. The naive way is to delete its pods:

$ kubectl delete pod taskflow-api-6b8d9c7f5d-8qwrt -n taskflow
$ kubectl get pods -n taskflow -l app=taskflow-api -o wide | grep m02
taskflow-api-6b8d9c7f5d-w7r2c   1/1     Running   0          6s    10.244.205.197   minikube-m02   <none>           <none>

The replacement landed straight back on m02, because the scheduler sees nothing wrong with it. And a script that deletes every pod on a node at once can take down every replica it hosts at the same moment.

The idea

Cordon marks a node unschedulable, so no new pods land there. Drain cordons it, then evicts its pods one by one through the Eviction API, so their controllers recreate them elsewhere. A PodDisruptionBudget (PDB) caps how many of an app's pods voluntary evictions may take down at once, and drain respects it.

 cordon m02 ──▶ drain m02 (evict pod by pod) ──────────────────▶ patch / reboot ──▶ uncordon m02
 no new pods    each eviction asks the PDB: "3 healthy − minAvailable 2      node empty      schedulable again
                = 1 allowed" → evict one, wait until its replacement is Ready
Think of it like this

Renovating a floor. Cordon = stop seating new people there. Drain = move the current staff, politely, to other floors. The PDB is the rule "at least 2 receptionists on duty at all times", so they move one at a time.

See it: cordon

$ kubectl cordon minikube-m02
node/minikube-m02 cordoned
$ kubectl get nodes
NAME           STATUS                     ROLES           AGE   VERSION
minikube       Ready                      control-plane   1d    v1.35.0
minikube-m02   Ready,SchedulingDisabled   <none>          1d    v1.35.0
minikube-m03   Ready                      <none>          1d    v1.35.0

What it does not do: move anything. Running pods stay on m02. Cordon only stops new arrivals, so a deleted pod's replacement now goes elsewhere. kubectl uncordon minikube-m02 reverses it.

Build it up: a budget, then a drain

k8s/pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: taskflow-api-pdb
  namespace: taskflow
spec:
  minAvailable: 2          # at least 2 api pods must stay up during voluntary disruptions
  # maxUnavailable: 1     # alternative (use ONE of the two); also accepts "25%"
  selector:

Exam trap

"A PDB protects pods from node crashes." ✗ PDBs cover voluntary evictions only (drain, cluster autoscaler). A crashed node or kubectl delete pod ignores them, and rolling updates follow the Deployment's maxUnavailable instead.

"Uncordon moves the pods back." ✗ It only makes the node schedulable again. Existing pods stay where they are.

Remember

cordon → drain --ignore-daemonsets --delete-emptydir-data → maintain → uncordon.
PDB (policy/v1): allowed disruptions = healthy − minAvailable.

Mastery check
Q1. A Deployment has 3 replicas and a PDB with minAvailable: 3. What happens on kubectl drain?

ALLOWED DISRUPTIONS is 0, so every eviction is refused and drain retries forever. Use minAvailable: 2 or maxUnavailable: 1. A single-replica app with minAvailable: 1 blocks drain the same way.

Q2. You forgot uncordon after the reboot. What do you see over the next week?

m02 stays Ready,SchedulingDisabled. It runs nothing new, so every new pod piles onto the other two nodes.

Q3. Fill in: with maxUnavailable: 1 and 4 healthy replicas, ALLOWED DISRUPTIONS = ____; with minAvailable: 50% and 4 healthy, it's ____.

1 · 2 (4 − 2).

★ Putting it all together

The big idea

Security is layered. Authentication says who is calling, and RBAC decides what each human and ServiceAccount may change in taskflow: Riya reads, ci-deployer patches Deployments, the API holds no token at all. A securityContext and the restricted Pod Security level limit what a hacked container can do; NetworkPolicies limit whom it can reach (only the API talks to Postgres). Scheduling controls placement: anti-affinity spreads the API replicas, a taint plus a nodeSelector reserve a node for Postgres, and a PDB lets you drain nodes without dropping below 2 API pods.

Final mastery check — combine everything
Q1. In CI (Session 19) helm upgrade runs with the ci-deployer token and fails: secrets is forbidden: User "system:serviceaccount:taskflow:ci-deployer" cannot list resource "secrets". The Deployment permissions are fine. Why, and what's the minimal fix?

Helm stores each release's state as Secrets in the namespace (Session 17), and the deployer Role deliberately has no Secrets access. Add a rule for secrets with only the verbs Helm needs (get, list, create, update, delete), plus rules for every other kind the chart creates (Ingress in networking.k8s.io, HPA in autoscaling). Don't bind cluster-admin.

Q2. You enforce restricted on taskflow. A week later you drain Postgres's node (section 9), and postgres-0 never comes back. Diagnose and give two fixes.

The drain evicted the pod, and the StatefulSet's new postgres-0 is rejected by Pod Security, because the Postgres pod never got a securityContext. Running pods are never re-checked, so the problem only shows when a pod is re-created. Fix: add runAsUser: 999, fsGroup: 999, runAsNonRoot, allowPrivilegeEscalation: false, drop ALL and seccomp RuntimeDefault, or move the DB to a namespace labelled baseline.

Q3. Riya (bound to dev-readonly) wants to test the DB from inside the cluster: kubectl run dbg -n taskflow --image=postgres:16 -- pg_isready -h taskflow-db. Two separate layers stop her. Which?

(1) RBAC: her role has no create on pods, so she gets 403 Forbidden. (2) Even when an admin runs it, the pod is labelled run=dbg, and allow-api-to-db only admits app: taskflow-api, so the answer is no response. Authorization and network policy are independent.

Q4. You reserve m03 with the dedicated=db:NoSchedule taint. Session 15's node-exporter DaemonSet (tolerating only the control-plane taint) now shows DESIRED one lower. Why, and how do you fix it?

A DaemonSet pod needs to tolerate a node's taints too, and node-exporter has no toleration for dedicated=db, so m03 is no longer eligible. Add that toleration, or use operator: Exists with no key to tolerate every taint, which is common for node agents.

Q5. Three API replicas, one per node via required anti-affinity, and a PDB with minAvailable: 2. You drain m02 and it finishes. Then you drain m03, and it hangs. Explain.

The pod evicted from m02 can't be placed: m02 is cordoned, and both other nodes already run an API pod, which required anti-affinity forbids. It stays Pending, so only 2 are healthy and ALLOWED DISRUPTIONS = 2 − 2 = 0. Every eviction on m03 is refused. Use preferred anti-affinity, or uncordon m02 first.
